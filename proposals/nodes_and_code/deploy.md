# Ernest: The Deploy, the reasons

Status: the reasons behind [`mvp3.2.md`](mvp3.2.md), the ordered rolling restart, in the order of its section 6. Written on 2026-10-07 as a thinking document, read against four readers ([`other_systems.md`](other_systems.md), section 7), tried in six programs and the library they share ([`experiments/code_update/`](experiments/code_update/README.md)), and decided with the user one question at a time, each decision dated where it stands; synced on 2026-10-08 after the review of the three proposals by six readers, whose verdicts changed the proposal and so this document. Nothing here is normative: the proposal states the rules, and this document says why. The reasons for a key's peers and for the find by the key alone, which change `mvp3.0.md`, are [`nodes.md`](nodes.md)'s section 14; the reasons for the cache on a node's disk and for a type's identity by its shape, which change `mvp3.1.md`, are [`code.md`](code.md)'s sections 5 and 2. The test of every decision was that the team that deploys writes and does only what no tool can know, and that nothing a tool does is invisible.

## 1. The aim

After MVP 3.1 a deploy is a rolling restart, and it is what Orleans, Akka, Elixir, WhatsApp and the cloud do (*V2*, *V10*, *U7*, *U9*). Done by hand it is done blind: the operator chooses the order of the nodes and guesses the drain; a changed protocol is found in production, where it parts old clients from new services or, decoded before its version is checked, takes a service down (*V5*); a service's state is lost at its node's stop unless it lives outside; and the rollout is tested by hand or not at all (*V14*, *U7*). Ernest knows what the operator guesses: the hashes say which definitions changed, down to each service's protocol and the type of each kept state; a service is found by a key that carries its type's identity; and a kept state is a value of a declared type that the runtime holds between steps, which crosses as any value does. So the runtime orders and checks the restart, and the team writes only what no tool can know, told by the plan which.

## 2. The plan

**The plan comes from the hashes the nodes run.** `ern diff` over what each node runs and the new build is the plan's first half, so that the coordinator keeps no record of its own and no baseline is committed (*V13*). For each key: a protocol and a state type unchanged is nothing to do; a changed protocol is accepted only where the new build offers the key at the old identity too; a changed state type is accepted only with a `migrate` the program wrote; and a build that drops a protocol is accepted only where no node runs a build older than the one that first served both. Everything the two builds decide is refused before the rollout, with the member or the key named, since a refusal at planning costs nothing and one during a rollout costs a half-rolled system (*U5*). A rollout and its way back put at most three builds in flight, and every check runs against every build any node runs or any state file holds, not the last alone (*S4*).

**What the coordinator asks, and what it does before the yes.** Decided with the user on 2026-10-08. One frame asks a node what nothing else can tell: the root it started from, its release and scheme version, its time, its configuration's digest, any rollout mark, the keys it offers with their identities, and the kept states it holds with their identities and sizes; `ern status` asks the same and prints it, which is how an operator sees what runs, since the plan is kept nowhere. The next build's root is told to every node before the plan is printed, and each fetches what it lacks into its cache then, so that a node whose disk is full or whose cache refuses fails the plan before anything has stopped, and the yes is asked only when every node holds the next build whole. A node that does not answer refuses the plan, since its build cannot be known and the drop rule cannot be checked for it; `--without node` goes on, with a line saying that node must be deployed by hand before any build that drops a protocol. A node marked by another coordinator refuses the plan too, so that two operators cannot roll one system at once. Free disk is compared against each kept state's size, since a state file that cannot be written is a state lost.

## 3. What the program writes, and what `ern diff` prints

**Nothing is derived into source.** Decided with the user on 2026-10-08. A derivation needs three forms the grammar does not have, a field's default, a hole the checker refuses, and a word for a renamed field, and a tool that writes into source; and a tool-chosen default for an added field is the one defect the migration tools of the field all shipped (*D4*). What the program writes instead is a few lines, and it is told which by the plan. `migrate` is a member on the new type from the old, `fn Count.migrate(old : CountV1.Count) : Count`, and one on the old from the new for the way back, both in the newer build; the plan finds each by its type and pairs old and new by the key, never by a name, so that two types of one shape are one to it. A protocol that gained constructors is offered at the old identity as `via(service, convert)` with a pure conversion from the old type to the new, which is §6.5's adapted address and needs no process; a protocol that retired or changed a request is offered through a forwarder the program starts, whose `forward` answers the retired request on the old side, as the counter experiment wrote it in 7 lines. `ern diff` prints the `migrate` and the conversion that the matching fields and constructors give, with what needs a decision left empty, as text for the program to paste and complete: what is pasted is seen, read and committed like any line, and the tool edits nothing.

**What it costs**, stated with the decision: a `migrate` is a full record rebuild, since two records of different types have no update between them, and it is written both ways, so a one-field change to a record of eight is two functions of about ten lines; a kept state that is a record of smaller records changes less at a time, which the guide teaches. A protocol of ten constructors that gains one needs ten arms of a conversion, pasted. A state of a prelude type has no way back, since `migrate` is a member and `Int` takes none, so such a change is forward-only, and the guide teaches a kept state as a type of the program's from the start. A changed meaning behind an unchanged type is invisible to any diff, so a program may give a `migrate` whose types are equal (*D5*). A conversation has no point between its messages where versions can change, so a protocol is of independent requests and a conversation is a process of its own (*D12*).

**A type many protocols carry costs each of them.** Changing an item three services' protocols carried cost a copy of each service, retyped, and a `forward` each, 84 lines, against 37 where each protocol owned its types. The guide teaches a protocol's types as its own, small and of independent requests, with that number.

**A stored state is the store's, and its row type is Ernest's.** A stored value migrates when next read and is written back in the new form at the next write, as every system read does (*V12*, *D9*), and a `migrate` pure by its effect row pays nothing for being lazy (*D8*). A schema change is expand then contract in the database too; the plan checks the service's side and says it cannot check the database's.

## 4. The old shape's module

Decided with the user on 2026-10-08, with a type's identity by its shape (`code.md`, section 2). A changed declaration keeps its module, its name and its key, so that no client is renamed and one key serves the service through every version; what must exist beside it, while any node may hold a value of the old shape, is the old shape itself. Two types in one module cannot share constructor names, so the old shape is kept under another name in a module of its own, `counter_v1.ern`, pasted from the form `ern diff` prints, and its identity is unchanged by the name, so an old client's key and an old state file match it. Deleting that module is the act that drops the version, an edit a reviewer sees, and `migrate` and the conversion go with it.

## 5. Two builds for a changed protocol

The first build offers the key at both identities, the new and the old through a conversion or a forwarder, so that an old client and a new service meet in any order; the second drops the old. This is the two deployments of Akka's rollout without degradation (*V11*) and the industry's expand then contract (*S3*), made a rule the tool checks: a build that changes a protocol and drops the old at once is refused, so that the discipline cannot be forgotten.

## 6. The order

Decided with the user on 2026-10-07. A new service serves an old client through the old identity, and nothing lets an old service serve a new one, whose find with the new identity on a node not yet reached answers `OtherType`. The coordinator knows which keys each node offers and which keys each node's code finds, a find being a reference the hashes see, so it restarts the nodes that offer changed services before the nodes whose code calls them, and the window closes. Where the graph has a cycle no order avoids a wait, so the coordinator picks one and the plan names the finds that will wait. The team states nothing about order.

**Who is in the order.** Decided with the user on 2026-10-08. A build is a build directory, the set of entry points compiled together, and a node's root is the hash of the entry point it runs, since the store, the desk and the board run three entry points of one build; the coordinator tells each node the root of the entry point of its own qualified name in the next build, and a build that lacks that name refuses the plan. Only the running nodes whose root differs between the two builds are in the order, so a change to the store's `count` restarts the store and not the desk, which the plan says; a program that is not running, a desk that asks once and ends, is in no order, is started with the build it should run, and is a limit the plan cannot see.

## 7. The planned stop

**Termination is the planned stop, and the one way a node ends.** Decided with the user on 2026-10-08. A stop by `ernest.pid` is a signal, and a signal carries nothing, so a planned stop that `ern stop` alone could run would leave the service manager, which stops nodes in practice, with the worse end; and every service manager sends termination and waits, as `init:stop`'s callers expect. So termination, from the service manager, from `ern stop --config-dir dir` and from `kill -TERM` alike, withdraws the keys, drains, writes the kept states and closes, and the operator learns no second command. The interrupt is the quick end, as §8.6 has it for a program, and a second termination during the drain ends the drain and goes on to the states and the close, so that an impatient operator loses no state. The coordinator sends the same four steps as one frame, carrying the next build's root, and a node accepts that frame only from a peer its configuration marks as a coordinator, holding a mark through its restart, so that neither the desk nor a second operator can stop the store.

**The keys first.** A node about to stop stops offering, so that a find goes to another of the key's peers, as Orleans's placement stops placing on a silo about to stop (*V3*). Nothing tells a finder of the withdrawal, so a standing address learns of the stop at the close; the service is therefore away from the moment its state is written to its first offer, a limit.

**The drain.** Decided with the user on 2026-10-07 as a minute, ended early when nothing waits, and on 2026-10-08 as the node's own: the bound is `drain` in `ernest.conf`, the node's time, since a signal carries no number and the knob belongs where the operator already is; the node tells the coordinator its time, which bounds the coordinator's wait for the node to be back as well, since a node that reads a large state at its start needs more of both, and the plan prints each node's time and each kept state's size so that an operator sees which node to give more. What the drain waits for is what the node can see: no call waiting in its own table of calls, which the call's note fills for a remote caller, and every `kept` loop idle, between two steps with an empty mailbox, which the runtime knows since it owns the loop; a mailbox's emptiness alone was no condition, a busy service never being empty, and a request in flight between an empty mailbox and an empty table cannot be seen by anyone. A drain is a courtesy with a bound, not a guarantee: a request in flight at its end, or in another process's hands, is lost with what the loop holds, as any restart loses it, which the plan said before the yes. The survey's precedents are ten and fifteen minutes for proxies holding thousands of long connections (*U13*); a few nodes with one owner, whose calls carry deadlines of seconds, need none of it. The drain does not grow firmer: the runtime holds no connections of its own to close, and a program that holds them has what it needs, its keys withdrawn first and its own listener to stop accepting on.

**The state, written.** Decided with the user on 2026-10-08, in place of the state moved to another of its key's peers, which was decided on 2026-10-07 and withdrawn. A moved state made two owners: the node restarted with the new build evaluates its own `kept` binding, finds the key's state neither in its file nor handed to it, and starts a second loop from `init` while the other node holds the first; every repair made the configuration decide which node's binding runs, against principle 3, and none closed the race of two nodes starting while a third is out of reach. So nothing moves: at the planned stop the node asks each `kept` loop for its state between two steps, writes it to the state file, and the loop holds what arrives until the close; the next start reads the file. One owner holds at every instant by construction, since only one process can hold the state and the file holds it between two, where Orleans's shutdown can make a second (*V2*). What the move bought was the seconds of a singleton's restart, and a service that must not be away for them needs a hot standby that knows who is leader, which is a lease in a store outside the nodes, a library's (section 16). A state that cannot cross, by §3.11's rule, which the compiler already decides, is not written, and the plan lists it before the yes. A write that fails, the disk full, ends the stop before the close: the loops go on, the keys are offered again, and the coordinator stops and prints it, since a close after a failed write is a state lost silently.

**What a kept state is.** Decided with the user on 2026-10-08. A loop with its state in its arguments can be asked for its state by nothing: the state is on the process's stack, in the host's memory, behind a mailbox the host owns, so no runtime can read it, drain it or make the old process forward. A state that is to outlive a deploy is therefore held where the runtime can reach it: `kept(key, init, step)` is a function of `restarting`'s family that runs a loop the runtime owns, calling `step` on each message, so that the runtime holds the state between steps and asks for it between two, as a supervisor asks a child for a restart (§6.9). It composes with `spawn` and `restarting`, so the report's service, a binding that holds an address (§6.5), is unchanged and the store's counter changes by one line; a fault in `step` restarts the loop from `init`, as §6.9 says of every restart. The shape is not a library with a loop and an envelope type of its own, which was written first and withdrawn the same day: that made the proposal's "service" a different thing from the report's, with an address of another type, where the report's own precedent, a function of §9.5 implemented by the runtime that reaches the process outside its mailbox type, needed no new word. A process the program loops itself begins afresh at its node's restart, and a deploy promises it nothing. On one node the program writes `kept` and no offer, and `ern stop` writes the state and the next start reads it: keeping a state is not a peer thing, and the key is its name for the file.

**The close and the restart.** The close is the ordinary loss as `mvp3.0.md` has it, so nothing new is added for it: a call still waiting answers `None`, a monitor on one of the node's processes gives `ProgramEnd`, a message in flight is gone, and a client finds the service again through its standing address. Connections drain to their own end, since no system moves one across machines (*U12*). Decided with the user on 2026-10-08: a stop that carries a next build does not end the host process. After the close no process of Ernest's would run on the machine, the coordinator is a node of the host's distribution and can reach only a connected node, a node cannot leave a successor behind through `Os.start`, whose process group is killed when its owner ends, and whatever else starts the node runs the old command line. The host offers a restart of the runtime inside the running process from the same boot arguments, so the runtime restarts inside it and `ern` runs the build the directory's `build` file names, which the stop wrote before the close; the pid is unchanged, `ernest.pid` stays true, and the service manager sees nothing. The same file makes any start from outside land on the planned build: `ern run --config-dir dir` with no `.erc` runs what the file names, so a service manager with its old command line, or an operator, starts the right build. A start that fails goes back by the node's own act: a restart whose initializer faults writes the previous build to the file and restarts into it once, and a second fault ends the node as a faulting initializer ends a program; for the fallback to find its state, the state files are removed once the node listens, every initializer having its value, and not at their read.

**The standing address is a library's.** Decided with the user on 2026-10-08, in place of `Peer.standing`, an operation of the runtime's decided on 2026-10-07 and withdrawn. A forwarder the runtime spawns and the program never sees broke every rule the report states for an address: `kill` through it killed the forwarder, `Process.fromAddress` named it, a call through it had it as callee, it belonged to no one and never ended, it found again at a cadence stated nowhere against MVP 3.0's rule that the runtime retries nothing, and it failed at its first find, so that every client wrote the loop it existed to remove. Every repair in the runtime added a special case for one kind of address. Written in Ernest over `Peer.find` and `monitor`, `Standing.start(key, ms)` is an ordinary process the program spawned, with the mailbox `Message(m) | Went(Down)` and the caller given `via` of it, and every rule of the report holds of its address as of any process's; it always answers an address, finds again at the service's `Down` and with `ms` between failed finds, and ends with its caller, so nothing is leaked. A program that is to monitor the service itself holds the address `Peer.find` gives; the two are different tools and say so.

## 8. The state file

Decided with the user on 2026-10-07, and on 2026-10-08 for its syncing, its reading and its removal. Its place is `state/` in the configuration directory, which the node owns as it owns `ernest.pid`, so nothing new is created or secured; one file per key, named by the key's name; a program without `--config-dir` is no node, and `./.ernest`, §11.3's default directory, is where its states go, so that a single program keeps its state with no node at all. Its form is the hash of the state type's identity and then the value in the encoding a value crosses between nodes in, so that the `kept` loop that reads it knows which `migrate` applies, or that none does; the hash is read before the value is decoded, so that a build without the `migrate` decodes constructors it does not declare on no account. It is written to a temporary name, synced, and renamed, so that a stop that dies mid-write leaves the previous file or none, and a power loss after a completed stop leaves the old file or the new and never an empty one. The `kept` loop under the key reads it at its start in place of `init`, through `migrate` where the hash differs from its own; a loop that finds a hash its build cannot migrate from begins with `init` and says so, which the plan told the operator before the yes. The files read are removed once the node listens, not at their read, so that a start which fails leaves them for the build that comes back. When the coordinator says the next build is older, the stop writes the state through the reverse `migrate`, which the stopping build holds, so that the way back needs nothing of the old build.

## 9. The coordinator and the lockstep

**One command, keeping nothing.** Decided with the user on 2026-10-07: `ern deploy build --config-dir dir` prints the plan, waits for a yes, and does the rest; a job of `ern`, written in Ernest, and a node like the shell, listed by the nodes it deploys to, so that nothing new is trusted. It keeps no record of the rollout, since a record can be lost or disagree with the nodes, and each node answers which build it runs; so a second `ern deploy` after a crash or a cancel continues from where the nodes are. The team's whole burden for a deploy is to build, run one command, and read the plan before the yes.

**A yes per node.** Decided with the user on 2026-10-08. The field's canary and its pause between nodes are a universal practice, and both come for free when the coordinator asks before each node rather than once: the plan, a yes, the first node stopped, restarted and checked, then `next` or `all`. The operator watches the first node as long as they like, and no option is added for the pause, the canary or the one node.

**It acts on nothing the yes did not cover.** Decided with the user on 2026-10-08. A rollback the coordinator makes by itself, at a node that does not answer in time, is a rollback nobody said yes to and the runtime's second attempt, which MVP 3.0 forbids. So the coordinator never rolls a node back: at a node not back within its time, or one it loses to a partition, it stops and prints what stands at which version, and `ern deploy` of either build, with its own yes, is the way on or back; a node whose initializer faults at its restart goes back by its own act (section 7). A cancel ends the coordinator alone, the node in its stop finishing its four steps and restarting itself. A node lost mid-rollout stands as it is. Before each stop the coordinator asks the node its configuration's digest again and stops where it differs from the plan's, since a plan over a configuration that changed under it is a plan over nothing.

**The check is the protocol's.** After each node's restart the coordinator finds every key the node offers at the identity the plan expects, which says that the services are up and of the right version, where a process being alive says neither. The coordinator starts nothing and puts nothing back: the node restarts itself and goes back by itself (section 7), where nginx keeps its old master (*U14*) and OTP's failure past its point of no return reboots into the old release (*U5*). Nothing is suspended and nothing restarts the whole system.

**What the plan prints.** Decided with the user on 2026-10-08, from what the field's operators ask at three in the morning: every node's release and scheme version first, each service's line, the order, the nodes skipped since their root is unchanged, each node's time and their sum as the most the rollout takes, a line saying the target is older than what runs where it is, the way back as the command to type, what a standing address drops meanwhile, the builds the way back can reach after this rollout, and each refusal naming the member or the key to write. `ern state path` prints a state file's type and value as Ernest literals, which the descriptors already allow, so that what a stop wrote can be read.

## 10. The way back

The previous build cannot hold a function from a type written after it (*V11*, *S11*, *V13*), so the reverse `migrate` is written in the newer build beside the forward one, a member on the old type from the new; a change without a reverse `migrate` is forward-only, which the plan says, a state of a prelude type among them, since it takes no member. During a rollout the way back is the previous build, node by node, accepted while every protocol it speaks is still served, which holds until the build that drops one; after that the way back is forward. `ern deploy` of the previous build is the command, which the plan prints, and the coordinator takes it only with its own yes (section 9).

## 11. The cache

The reason is `code.md`'s section 5: one exchange moves code between nodes, MVP 3.1's, on two occasions, a spawn and a root a node is told before a planned stop, and a node restarts into a build from its own disk. Decided with the user on 2026-10-08: the in-memory table from a hash to the host's module and function is the code table, since nothing leaves it while the node runs, and the disk store, which holds each form with its compiled unit and lets a build go, is the cache; a node told a root fetches from the coordinator, which ships the build directory's forms as a node ships its own, compiles, writes and loads nothing; at a restart every form is verified against its hash and nothing is compiled, since the drain's bound could not afford a compile. What is the deploy's: every node fetches the next build before the plan is printed, so that a node that cannot take the code fails the plan before anything has stopped and the restart does not wait on the network; and a build leaves the cache when the plan has printed that no way back reaches it, the drop of its protocols, so that the cache holds exactly the builds a rollout or its way back can need, and the operator is told which those are. A machine rebuilt from nothing has a new key and an empty cache, and its first start is by hand with a build directory, a limit.

## 12. The runtime's surface, and a release of `ern`

Decided with the user on 2026-10-07 to be this milestone's and not one of its own, which the plan had held as MVP 3.1a. MVP 3.1 puts `ern`'s whole version in the cookie because shipped code calls the runtime by name and nothing hashes that surface, which is honest; its cost is that a release of `ern` stops every node, which is exactly what the deploy exists to avoid. The surface's value appears when a deploy is a rollout the runtime orders, so it is named, versioned and put in the cookie here, where the deploy's tests exercise it; and it is best named once the exchange runs and shows what shipped code calls by name. Decided with the user on 2026-10-08: the surface takes in the identity of the standard library's own Ernest, so that two releases whose standard library differs do not connect and a spawned function never meets a standard-library binding of another identity on a peer; the scheme version changes with any change to what runs before hashing, so that two releases hash one source alike or refuse each other. The runtime cannot carry a new `ern` to a machine, the runtime, the compiler and the helper being loaded from the installed tree and never crossing, so the operator installs a release on each machine, and `ern deploy` with the build the nodes run restarts each node whose release is not the coordinator's, which its line says. A release that changes the surface still stops every node, and the first deploy to nodes of this milestone is by hand, since nodes of an earlier release refuse the coordinator at the handshake.

## 13. The refusal

A supervised process's restart runs the function the child was spawned with, so an upgrade in place of one vanished at its first fault in the supervisor experiment, and `Supervisor.child`'s function run again inside the child made the group count a fault that had not happened, since the inner function read the outer child's start cause. An operation by which a child replaces the function its restart runs was decided and withdrawn the same day with the change of logic in place (section 15); what remains is to refuse the call, `Fault("a process runs one child function")`, the smaller of the two answers, since nothing of the deploy needs the other.

## 14. The test

Decided with the user on 2026-10-07. The test's channel into and out of every kept state is the state file of the planned stop, so that it sends no message of any protocol and the team writes no test of its own: values generated for each state type go in as the files a stop would have written, and the states the stops write come out. The test is given the two builds. The oracle is identity where the state type is unchanged and the round trip through the reverse `migrate` where it changed; a property a human writes is asked for only where there is no reverse, which the plan has named forward-only, the one piece no system has automated (*D14*, *V14*). The test covers the deploy's whole path and not the service's logic, which the program's own tests cover. The cost of testing a rollout by hand is the stated reason the field does it seldom (*U7*, *U9*), and the generated run is the answer.

## 15. Why not in place

The six experiments asked what upgrading a running process in place would cost. A change of logic took one message and kept everything: the counter's total, the store's items and listener, the chat server's connections. Any other change failed at the type, since the loop's mailbox type names its protocol and its state; in place it needs `become`, a gate through which a running process's mailbox type changes, which would be the language's one addition for step D and its riskiest, the only part the soundness argument would have to carry beyond MVP 3.1's. A replace, a successor with the state and the old address forwarding, ran today for every other change, and the planned stop's third step is its half that writes the state out.

What in place keeps that a restart loses is a process's connections through a change of its state or protocol, and a process can keep them another way: it owns the sockets behind a small protocol that never changes, and the logic that changes is a service beside it. So in place is set aside, and no change of code in place stays, not even the change of logic the experiments ran: decided with the user on 2026-10-07. The rolling restart is the one way to deploy; a change of logic in place would be a second, would reach the library's services and not a module's loops and helpers, leaving mixed versions on one node, and would need `Supervisor`'s operation. What would bring `become` back is a program that must change the protocol of a process holding connections, where the shape above does not serve. The library's `Upgrade` stays in the experiments as the record of what in place would have been; §6.10 stays in the report as a statement that a process takes new code only by its own act, by a message that carries a function on one node, and that there is no other way, which nothing of the deploy builds on; and part two of `code.md` stays as the record of the thinking for in place.
