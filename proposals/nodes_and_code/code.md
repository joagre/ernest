# Ernest: Code, the reasons

Status: the reasons for code as designed through MVP 3.1, in the order of [`mvp3.1.md`](mvp3.1.md)'s section 6, kept in sync with the latest proposal that touches code; nothing here is normative, and the proposals state what this argues. Part one, sections 1 to 6, is the reasons, synced on 2026-10-08 to `mvp3.1.md` as the review of the three proposals left it ([`deploy.md`](deploy.md) holds the reasons of MVP 3.2 that reach into it). Part two, section 7, is the record of the thinking for a running process that takes new code in place, which MVP 3.2 decided against for an ordered rolling restart, [`deploy.md`](deploy.md)'s section 15 saying why; it is kept as it was thought and is not synced. The reasons for nodes are [`nodes.md`](nodes.md)'s; what other systems do is [`other_systems.md`](other_systems.md), its section 6 the three readers for this milestone.

## 1. The aim

Unison names every definition by a hash of its content. Builds become incremental, two versions of a definition are two things and never conflict, a rename costs nothing, since code refers to a definition by its hash and a name is a label on the hash, and code can move between machines because its identity is exact. Ernest takes that idea openly (the plan's MVP 3.1), with the rename of a function and of a type, since neither's hash holds its own name; a binding's identity holds its name, since a binding is a thing that exists on a node, so renaming one is a change (section 2). The aim is to do what it promises soundly and realistically:

- **Sound.** What holds across nodes is argued, as [`soundness.md`](../../docs/soundness.md) argues the core, before it is built (MVP 3.0's first item). Failure is part of the language: a peer's loss puts its processes out of reach and tells their monitors so, with `Unreachable` ([`nodes.md`](nodes.md), section 8), a message is sent at most once, a call waits with a deadline, and a reply is checked.
- **Typed processes as the unit of distribution.** Shipping code is spawning a typed process on a peer, its protocol's hash checked.
- **Realistic.** Source stays text files under git, edited and reviewed as any code; the compiler computes the hashes. The runtime is the BEAM, with its decades of production behaviour, on machines a program's owner runs, listed in `ernest.conf` and authenticated by mutual TLS, with no platform to depend on. What hash modules cost on the BEAM, atoms and code memory, is measured before anything is promised.

**The four steps.** Moved here from `mvp3.0.md`'s section 11 on 2026-10-07, being code's roadmap and not nodes'. MVP 3.0 loads no new code: a new version is a stop of every node. Loading new code is four steps, of which MVP 3.0 is the first.

| Step | What it gives | Where |
|---|---|---|
| A | one build on every node, and a deploy that stops them all | MVP 3.0 |
| B | nodes of different builds connect; a message is accepted by the address it was sent through, and a spawned function only where the peer has its module, and all that module depends on, unchanged; no code crosses | a step after MVP 3.0, to be weighed |
| C | a hash for each definition; code crosses by one exchange, at a spawn, and in step D when a node is told a build's root; two versions stand side by side on a node | MVP 3.1 |
| D | a running system takes new code, as an ordered rolling restart | MVP 3.2, [`mvp3.2.md`](mvp3.2.md) |

Step B parts two rules that step A holds as one: that no code crosses, and that every node is the same build. Without the second, nodes are restarted one at a time wherever a change does not touch what they exchange, and the build's checksum falls away; a changed module that spawns or finds on a node still holding the old one fails until that node has it too. Step B only relaxes step A, by the first of `mvp3.0.md`'s rules for what comes after. Replacing a module under running processes, as Erlang's `code` module does, is none of these steps: it changes code with nothing to check its types against.

Unison has shipped for years, and Ernest has a design, so "better" is true only when MVP 3.0 and 3.1 run and their numbers hold. Unison's codebase is a database rather than text files, and its distributed promise lives largely in its hosted cloud; what is said of its internals is said from the outside, and modestly.

## 2. The hash

**The canonical typed tree, references by hash, no own name.** The hash is over the canonical typed tree, not an intermediate form, since the toolchain has none and one kept only to hash would be a second representation of every program; `ern_interface:hash/1` already canonicalizes an interface the same way. A reference is the hash of what it names alone, so that a rename changes no dependent's hash, which is what hashing is for; a foreign declaration, having no hash, is referred to by name and type. A function's own name and positions are out, as in Unison: the spawn site travels in the spawn frame and a trace names a hash by this build's name for it. A type's hash is its shape, its parameters by position and its constructors in declared order with their fields' names and the hashes of their types, and not its qualified name. Decided on 2026-10-08: a type's representation at the boundary is its constructors and fields, with no module in sight, so two declarations of one shape under two names are one type where a value crosses, and nothing is lost in saying so; a type renamed or moved between modules keeps its identity and its dependents' hashes, and the old shape of a changed type can be kept under another name in a module of its own, which is what lets a changed declaration keep its module, its name and its key across a deploy ([`deploy.md`](deploy.md)). A renamed constructor or field is a change, since both are the shape. Within a build the checker tells two declarations apart by name as it does today. A value ordered under one order never meets another, since `compare` stands in the identity; no other member does, decided on 2026-10-08, since every other member is the receiver's own code and changes nothing of a value, and an identity that took every member's hash would make a line added to a member, or to anything it calls, a protocol change across a rollout. A group is one hash with positions, the strongly connected component in source order, since an order by hash ties where two members differ only in which other member they name (*H3*). No project name, since two codebases that agree on a type's name and definition agree on the type. A type's `compare` stands beside its hash as its identity and not inside it, since a member's tree names the type and a hash must not contain a hash that names it (*H6*). Two words serve, defined once in the proposal: a definition's *hash* is the SHA-256 of its canonical form and nothing else, and its *identity* is what a reference names and a find compares, a function's its hash, a binding's its qualified name with its hash, a type's its hash with its `compare`'s. The scheme's version is mixed into every hash, so that hashes of two schemes are never equal (*H7*), and it changes with any change to what runs before hashing, the canonical form and the checker among it, so that two releases of `ern` hash one source alike or refuse each other, which the coordinator of MVP 3.2 relies on (decided on 2026-10-08). Messages across builds carry nothing of their type, by MVP 3.0's induction: every remote address came from a find, a spawn or an agreed message. A local address that outlives a load is outside that induction, and section 6 says what holds it. Names stay in the `.ern` files: a build resolves every name afresh and writes the table from name to hash, derived and never edited, so that no operation points a name at a hash and no source names one; within one build a name has one meaning, and an old version still needed keeps a name of its own in the source. What an abstract type's hash covers beyond its declaration, the types of its module's exported declarations or nothing, is the canonical form's document to decide, MVP 3.1's item 2.

## 3. The cookie, and what the hashes leave out

**To keep in mind, 2026-10-07.** A library under `libs/` written in Ernest is hashed code: it crosses with a spawn, differs between builds, and is deployed with a program; a library's shim over its own Erlang is where the library is, and a bare node lacks it, while a shim over OTP's or `ern`'s modules is everywhere. The standard library is `ern`'s, the same on every connected node by the cookie, so today the advantage is a library's; it would reach the standard library only if it were ever deployed with programs rather than with `ern`. That weighs on the long run of what is written as Ernest and what as a shim, without changing anything decided now.

**The cookie without the build.** The cookie is the digest of the protocol's version, the hash scheme's version, OTP's version and the runtime surface's version, the build's checksum of MVP 3.0 leaving it; the proposal's section 6 states it once and everything else points there. The surface is what shipped code calls by name, the runtime's functions and the standard library's foreign declarations, and, decided on 2026-10-08, the identity of the standard library's own Ernest, since a spawned function on a peer whose standard library differed would meet a binding of another identity and fail with `NotLoaded`. Two releases of `ern` with one surface connect; the operator installs a release on each machine and MVP 3.2's `ern deploy` restarts each node into it, carrying nothing of the release, since the runtime, the compiler and the helper never cross ([`deploy.md`](deploy.md)). What the hashes leave out agrees by the cookie, and a release that changes the surface, or a new OTP, is a stop of every node: each node restarts, and state leaves it first or is lost.

## 4. Messages, keys and bindings across builds

The reasons are [`nodes.md`](nodes.md)'s: section 7 for a message that carries nothing of its type across builds, section 14 for a key that carries its type's identity, section 15 for bindings held by identity and the bare node. What is code's here is the identity itself: a type's identity is its hash with its `compare`'s beside it, not inside, since a member's tree names the type; and a binding's identity is its qualified name with its definition's hash, since a function's hash leaves out its own name and two bindings with one initializer would otherwise be one value on a node.

**Bindings, decided.** A node holds its bindings' values by identity and initializes nothing for a peer, since an initializer may spawn and the types do not tell a constant from a service. One rule for what a spawned function carries, decided on 2026-10-08: a top-level binding it names is the peer's, resolved by identity and `NotLoaded` where the peer did not run it, and a value it is to carry from the spawner is bound to a local first, `let key = Counter.key`, and captured as any local is; so what crosses is read off the function's locals alone, and no binding's value travels by a rule a reader would have to guess from the example. A service is one per node, since a node runs one build, and an old client meets a new service by its key where the type's identity holds. So the second service started empty, which this section feared, cannot arise: a find ships no code and a spawn initializes nothing. A binding's identity is its qualified name with its definition's hash, since a function's hash leaves out its own name and two bindings with one initializer, `let a = spawn(worker)` and `let b = spawn(worker)`, would otherwise be one value on a node; a binding is a thing that exists, as a service is, and so holds its name where a type, which is a shape, does not. A renamed binding is a new binding, which section 2 asked. A closure the peer cannot load fails the spawn with `Refused`, the peer's refusal with the peer's text, since none of the seven failures fit and a new constructor would break every match; `Refused` is that alone, since a connection the handshake refused is `Unreachable` to the dialer, the host telling it nothing of the reason ([`nodes.md`](nodes.md)).

## 5. A node's code, and the exchange at a spawn

**No module for each definition, and nothing unloaded.** A module of the host for each definition cannot run on a node that lives long: OTP 29 lets a node load 65,536 module names in its life and exits at the limit, unloading gives none back, and fun and export entries live for ever. So the host's unit is the runtime's own grouping, invisible to the program and the protocol: what arrives in one exchange is one unit, the own build one unit per source module, and a table from hash to module and function is the code table, the disk store below being the cache; no module is named by a hash, which later lets names be reused from a pool, and a unit's functions are named by their position in it, so that the atom table, which the host never shrinks either, grows by the unit's name alone. Nothing is unloaded in MVP 3.1: unloading would free only the code bytes and not the names, a purge signals every process, and the VM does not track closures, so an unload would break a fun held in a value; a rolling deploy restarts each node and bounds what it holds, and a node says when it nears a limit. The compiled code lives once, as loaded modules; a received definition's canonical form is kept beside it so that the node can ship it onward. A node with no `.erc` at all is a bare node, the diskless node below, arriving for free; its entry process evaluates the standard library's bindings and waits, the node ending by termination, and no rollout restarts it, since it has no root and nothing of a build is its own. The memory of code is bounded, not reclaimed: the host's limits on module names, lambdas and atoms, with the node's warning at four fifths of any, and a node warned is stopped by its operator with `ern stop` and started again by its service manager; nothing of it is left to another milestone to measure. The host's embedded mode is not used, since a unit off the code path is loaded on demand in no mode, and the node loads otherwise as `ern run` does.

**A node keeps its code on its disk, by hash.** Decided on 2026-10-07, with MVP 3.2's deploy, and made one exchange on two occasions on 2026-10-08. A deploy that copied a build directory to each node would be a second way of moving code between nodes beside the exchange at a spawn, so the exchange has two occasions and one set of frames: a spawn, where the spawner names the function's hash and the peer compiles, loads and starts; and a root a node is told before a planned stop, where the coordinator names it, ships the forms of the build directory it was given from its `.erc` files as a node ships its own, and the node compiles, writes to its cache and loads nothing. The cache holds each definition's canonical form with the unit the node compiled it into, so that a restart compiles nothing within the node's time; at the restart every form is verified against its hash before it loads and the node refuses to start naming the first that fails, while the units are trusted as a build directory's `.erc` files are, since the node alone wrote them. A node's own build is in the cache as what it received is, so that a node restarts into any build it holds. The cache's argument, which every cache owes: it holds the builds the node has run and the one it is about to run, and lets a build go when the plan has printed that no way back reaches it, which is the drop of the old protocols ([`deploy.md`](deploy.md)). Every node fetches the next build before the plan is printed, so a node that cannot take the code fails the plan before anything has stopped. What a node runs is still never unloaded while it runs; what it keeps on disk goes when the plan says.

**The exchange: the root first, the hashed form, quarantine and one load.** The root's hash goes first, so that the common case, a peer that has it, costs one round trip and no list; the list, the lacks and the code follow only where the peer lacks the root, as Unison does and as Git's negotiation over commits suggests ([`other_systems.md`](other_systems.md), section 6). The frame carries the hashed form, since by Nix's rule a content-addressed object verifies itself and a binary named by its source's hash can only be trusted; the peer compiles with its own back end and keeps form and unit in its cache by hash. Arrivals wait in quarantine until the closure is complete and verified, then one atomic load, which Git's quarantine and Unison's temp entities both argue; what the peer said it has is pinned meanwhile, as Nix pins. A foreign declaration the peer lacks is `NotLoaded`, known from the list before any code moves. A faulty frame ends the connection, as in MVP 3.0.

**Risks.** Normalization, where an error costs most: two hashes for identical code or, worse, one hash for different code. And the time to compile when a node receives much code at once, typically as it starts.

## 6. `Code`, the shell, the rolling deploy

**`Code` is two functions for the toolchain and the tools.** Under hashes a program has nothing to load by name, since it names every function it calls, so `Code` is `load`, which is `ern run`'s loading of a compiled module and its closure, and `hashes`, which answers a module's definitions as name and hash. The host's checkless load is not offered; a load changes nothing under a running process; letting code go is the runtime's, and nothing goes. The shell's `:load` and `:reload` stand on it, compiling staying the toolchain's. These answer the six decisions the plan held for `Code`. `Code.load` evaluates the closure's bindings in a fresh process at `Never` while the caller waits, decided on 2026-10-08, since the soundness argument that an initializer at `Never` is safe rests on an empty mailbox, which a caller's is not. `Code.Error` is `NotFound`, `Stale`, `Incomplete` and `Faulted(cause)`, a type of its own since `Io.Error`'s other constructors do not fit and a program writes what it matches on; `Faulted` since a fault in the fresh process reaches the caller as a value or not at all.

**A load on one node, decided 2026-10-07.** A client of one version and a service of another meet on one node as across nodes. Across nodes a find compares identities before any address crosses, so a new client never holds an old address. On one node there is no find. A client takes an address from a binding or from a value held since before the load, a local address is a pid alone, and constructors of one name in two versions are one term, so nothing at run time tells a message of the new version from one the old process matches, and `receive` would leave it in the mailbox for ever (§6.3). The induction of section 2 covers remote addresses and not a local one that outlives a load, so the guard on one node is the checker: a type in a node's scope is its hash, a value keeps the hash it was checked under through a load, and a message of one version to an address of the other is a type error. Two versions of a type are then two types in one scope, as across nodes, and claim 5 of the proposal holds on both sides. The shell is where the rule shows, since `:reload` is the one load that puts two hashes of one name in one scope; a tool's own compiled code holds the hashes it was compiled with and names nothing a `Code.load` adds, though it meets what the loaded bindings do, a service offered under a key among it.

**No second version of a unit.** §11.2 ends a previous version's processes at a further reload with `Fault("its code was unloaded")`, which the host's limit of two versions of a module forces, and which claim 4, nothing a process runs is ever taken from it, and section 5's *nothing unloaded* forbid. The two agree once a load never gives a unit of the host's a second version: what one load brings to a node that holds the module's unit already is compiled into a unit of its own, as what arrives in one exchange is, from the forms its `.erc` or its source holds, and the table from hash to module and function points each version to its unit. The host's limit then never bites, and the fault goes from §11.2, and with it from §7.4 and §8.4, since nothing is unloaded anywhere, the shell's purge included: `:reload` is a load of the modules whose source changed, with nothing purged. A previous version's process runs on until it ends or is killed, reachable through the addresses of its version alone, its key offered again only once it has ended. The price is that a load counts against the host's lifetime limits of section 7, as an exchange does, which is what the four-fifths line is for.

**The rolling deploy, and `ern diff`.** Step C's deploy is a rolling restart by the operator's hand, one node at a time, services met by key, and a changed protocol answering `OtherType` across the rollout, which the program handles as it handles `Unreachable`; step D's `ern deploy` carries the build and the order ([`deploy.md`](deploy.md)). `ern diff old-build new-build` is the one tool: the definitions whose hash changed, `changed` where the form did and `follows` where a reference did, and the keys whose identity changed; a list and not a plan, since a plan that orders a rollout and checks translations is step D's. A build directory is never changed under a running node, each build in a directory of its own, since a node reads its own forms from its `.erc` files when it ships them, and the operator's copy over a running node would ship forms that fail their hashes. The discipline of part two's 7.4, a service's protocol small, stable and its own, is what makes most deploys silent, and is the guide's to teach.

## 7. Code change in running processes, the thinking for step D

Thought before the peer design and MVP 3.1 were settled, and left as it was. [`deploy.md`](deploy.md), the reasons for MVP 3.2, sets upgrading in place aside for an ordered rolling restart, its section 15 saying why, and this part stays here as the record of the thinking for in place. What MVP 3.1 has since decided and this part assumes otherwise: no message or address carries a hash, a key carries a type's identity, a service is found by its key and not by its binding's hash, nothing is unloaded and the host reclaims no module name, and a deploy is a rolling restart. Section 7.3's findings on a service across builds and after its node restarts are answered by keys for step C, and stand for step D only where a process is to take new code in place. The milestone after MVP 3.1 writes its proposal from this part the way `mvp3.1.md` was written from the thinking before it.

### 7.1 Loading and upgrade in place

**The objection.** A typed language, it is said, cannot have Erlang's code loading. Of the mechanism that is true. Erlang swaps a module under every process that runs it, a state takes a new shape in `code_change`, and messages of any shape keep arriving: the types of live data and of messages in flight change with nothing to check them against. Of what the mechanism is for it is not true. A running system upgraded without a stop, old and new code side by side, has a typed form, and §6.10 is a start of it: a process takes a message in its own type that carries the new loop, checked against its mailbox type before it arrives, and carries its state over by a typed function, Erlang's `code_change` checked. What a typed process cannot do is change its mailbox type silently, since its clients hold an address of the old type. In Erlang the same mismatch shows at run time, as messages nobody matches; Ernest would make a program say how old clients are served, as a function from the old messages to the new, and with that function the type may change in place (below).

**Loading never disturbs running code.** A hash module never changes, so loading only adds. A process keeps the code it runs until its own upgrade case moves it, or until it ends, so loading new code is as safe as starting a process. BEAM's limit of two versions of a module, which kills a process still in the old one on a third load, does not arise. The cost moves to unloading: code stays loaded while any process, message or value refers to it, and memory no collection reclaims is a defect, so code is collected.

**A load moves names, and compiled code holds hashes.** A name is resolved to a hash when code is compiled, never when it is called. A load is a build's result brought into a running node, by a deploy or by the shell's `:load` and `:reload`. It gives a new hash to each definition that changed, and to each definition that refers to one of those, in whatever module, since a definition's hash covers the hashes of what it refers to. The rest keep theirs, and nothing is loaded for them. A hash is a definition's or a group's, and a module has none. The table from name to hash, the build's and a shell session's, then gives each of those names its new hash. What is compiled from then on, a shell input or a module built against it, reaches the new code. What was compiled before holds the old hashes and runs the old code, a running process and a function held in a value among it. Erlang's call by a module's name finds the latest version at each call, and the shell's reload leans on that today: it compiles again a module that uses a reloaded one only where the interface changed (§11.2). Under hashes a definition that refers to a changed one always gets a new hash, linked again where its text did not change. A service binding is no exception: one whose loop changed is another binding, and code compiled after the load reaches a second service (section 7.3).

**An upgrade arrives as code does, by a spawn.** A function does not cross nodes in a message (§3.11). A process on another node is sent its upgrade by a process spawned on that node, to which the spawn gives the new function (§6.10).

**An upgrade in place is not a restart.** It is a tail call. Nothing the process asked the runtime for is cancelled, its alarms, monitors and subscriptions; its mailbox is kept; and the replies it holds go on in its state. A restart begins afresh (§6.9).

**The service that never ends.** A short-lived process ends on its old code, and its successor begins on the new. A long-serving service never ends, so it sees new code only through an upgrade case of its own; the runtime cannot migrate a state it cannot see, which lives in the loop's arguments. A process whose type has no upgrade case is replaced instead. A change of logic behind the same protocol upgrades in place with no outage: the address stays, and what arrives meanwhile waits in the mailbox. It is the common case of a fix, and not of a service that grows: a feature is most often a new message, so a change of protocol is ordinary and has to be as safe.

### 7.2 A change of protocol

**A change of protocol is an upgrade in place, with a translation.** Three answers were weighed and left. A forwarder, a second process that holds the old protocol and hands each message on, is a loop written and kept by hand around the one thing that cannot be avoided, the function from an old message to a new one. A rule that a type with one more constructor is accepted where the old one is needs a subtyping the language does not have (principle 5). And a service whose protocol may never change is too little. What is left is that function alone. The process stays, as in any upgrade in place: its identity, its state, what it holds and what it asked the runtime for. Its mailbox type changes through one gate, under the working name `become`: `become : ((old) -> new, () -> Unit with new) -> Unit with old`. It takes the translation and the new loop, and runs the loop in place of what called it. It is the one place a process's mailbox type changes, and it cannot be called without the translation. Its result type is `Unit` and not a type variable, though it never returns to its caller, so that §6.6 holds it to its replies (section 7.3). An `Upgrade` case of §6.10's shape carries it with no change to the old protocol: the `next` it hands over has the old mailbox type, and is a function that calls `become`.

**Old addresses keep their meaning.** An address made before the change is an address of the old protocol, and what is sent to it is translated by the service itself as it takes the message. So are the messages waiting in the mailbox at the switch, and what the service's own alarms and monitors deliver, whose `wrap` functions were written to make old messages: one rule, that what is addressed to an older protocol passes through the translation. A translation that faults is then the service's own fault, as a fault in its loop is. A process that has changed its protocol twice translates through both, for as long as the build holds both (section 7.3).

**The translation is total.** The inclination is that it answers a new message for every old one, and never nothing. The reply rule then does the rest (§6.6): the translation is pure and cannot answer, and a reply is consumed exactly once, so each old request's reply must go into a new message, and no old caller is dropped. Where the answer's type changed, the reply is adapted as an address is, by a `via` for replies of `via`'s own shape, `(Reply(old), (new) -> old) -> Reply(new)`: answering the adapted reply answers the old caller with the converted answer. A request the new protocol retires still has a reply to place, in a constructor the new service answers with the old answer type's failure; an old request whose answer type has no failure cannot be retired while an old client may ask, which is the promise the old protocol made. So a service's answers hold a failure from the start.

**Nothing dies, so nothing is told.** No monitor sees the change, as none sees a restart (§6.9); a call waiting on the service waits on, since its callee has not ended; a socket the service owns is still owned; `Process.fromAddress` gives one process for an old address and a new one; and `kill` through an old address kills the service.

**An additive change** is the translation that maps each old constructor to its namesake. It is written, and so seen (principle 3), and the deploy tool, which holds both builds, could write it.

**A forwarder written by hand** remains possible in the language as it is, and is what a program falls back on where a point of this proves wrong.

**A discipline around upgrade types.** An upgrade case each service writes by hand is forgotten, or written in a shape of its own, and then nothing upgrades services alike. A fixed shape lets a supervisor, the shell or a tool upgrade any service, as OTP's system messages reach every behaviour, but visibly, in each protocol's type (principle 3). One form is a library type over the language's own: a service's mailbox `Service(Msg, State)`, its messages and an `Upgrade` that carries the new loop as `(State) -> Unit`, which adds no concept (principle 5). A rule of the language that every service binding holds one would be stronger, and would bind services that never change.

**The state as a schema.** In that form, the state's type at the switch is the service's contract with its later versions: the new code is handed a `State`. What it does with it is its own. Behind the same protocol a new loop holds any state it likes inside and hands over a `State` at its next upgrade. With a change of protocol the new `Service` type names its own state, and the function that calls `become` carries the old state into it, as `migrate` does in §6.10.

**A restart after an upgrade.** `restarting(limit, f)` and a supervisor's child hold `f` by its hash. A service upgraded and then faulting would restart into the `f` it was spawned with, and the fix would vanish at the first fault. Erlang's restart calls the start function by name and finds the new module. An upgrade would have to replace what a restart runs, so the discipline reaches `restarting` and `Supervisor`, not the loop alone. After a change of protocol it is no longer a matter of keeping a fix: a restart into the old function would run a loop of the old mailbox type under addresses of the new one. `become` runs its loop in place of the old stack, the `restarting` function the old loop ran under included, so the new loop states its own: `become(translate, restarting(limit, fn() = loop(state)))`. That is written and seen (principle 3), and the runtime replaces no function behind the program. The count of restarts begins anew. A supervisor's child states its own the same way, through `Supervisor.child` again; a child is known to its group by its process, which `become` keeps, so a join from a process the group holds keeps its place.

**Clients of two versions.** Clients that share a protocol type share its hash, and the service sees one type from all of them, whatever their own code's version. A client built against another version of the protocol holds an address of another type, and an address carries its mailbox type's hash, so no message of one version is read as the other's. Nor does such a client reach the service through its binding as the rules stand: its own binding is another binding, which starts a second service on the peer (section 7.3). The price is strictness. A type's hash covers what it refers to, so a change to a record deep in a protocol is a new protocol, and a change to a type many protocols share means replacing every service that carries it. So the discipline has a second half: a service's protocol types are small, stable and its own, not built from types shared across a program, and most changes are then changes of logic behind a stable protocol.

**Compatible evolution.** A second version that adds a constructor and is accepted where the first is, as protobuf's systems allow, would be an exception to "two versions of a type are two types", and a subtyping. It stays out: the additive translation above does its work, written.

**Where the thinking stands on a change of protocol**, on 6 October 2026. Settled means the thinking no longer weighs it; it is no decision of the report's until it goes to its owner.

Settled:

- A change of protocol is an upgrade in place: the same process, with a total translation from its old messages to its new, through `become` alone. No forwarder is written, no subtyping is added, and no protocol is fixed for a service's life.
- What is addressed to an older protocol is translated by the service as it takes it. Every old reply is carried into a new message, by the reply rule, and adapted by a `via` for replies where the answer's type changed. A retired request keeps a constructor that answers its old callers with a failure.
- Nothing is told of the change: no monitor, no waiting call, no owner of a resource.
- The new loop states its own `restarting` function and its own place under a supervisor. Its closure holds the state as it was at the switch, so a fault in the new loop runs it again from that state. That is the rollback a change of protocol has (section 7.3).
- `become` has the result type `Unit`, so a reply held where it is called is carried into the new loop or is an error (section 7.3).
- An old protocol is served for as long as the build holds its type and its translation, and no longer (section 7.3).
- On a peer, an address's hash says which protocol it is of, and a node accepts each protocol its process serves. After a restart of the service's node the old name is a view of the new service in the source, a service binding is matched by its name and protocol, and a second service is never started unseen (section 7.3).

Open, each in section 7.6: how a process tells an older protocol's message from its own on the host, and what `receive` does on intake; the `via` for replies, its name and how it crosses nodes; whether a join from a process its group holds keeps the child's place, read against `Supervisor`; how the tool tells a service to drop a protocol; what makes a binding a service binding for the matching rule; and `become`'s name.

### 7.3 Across builds and nodes

What reading the hashes beside sections 7.1 and 7.2 shows of code change. Each is a finding to weigh, not a verdict.

**A service across two builds.** §8.7 gives a top-level binding the hash of its definition, with everything the definition refers to. A service binding refers to the loop it spawns, so a fix to the loop gives the binding a new hash. §8.7 says what follows: a binding whose definition differs from the peer's by hash is another binding, and code of the new build that names the service starts a second one on the peer, running the new version, beside the first. That is versions side by side, as designed, and it is replacement with no handover: the new service starts empty, and the old one runs on for the clients of the old build, with nothing to end it. An upgrade in place needs the opposite, code of the new build reaching the service that runs. As the rules stand it cannot name it: its own binding is another binding, and no source names a hash. Two shapes of answer are in sight.

- *The binding's identity changes.* A service's identity across builds is its binding's qualified name and its protocol's hash, in place of its definition's hash, so that the new build's binding is the running service wherever the protocol is unchanged. That gives a binding an identity unlike every other definition's (principle 2), and lets new clients talk to old code until the upgrade lands, which nothing in their text shows (principle 3).
- *The deploy tool bridges the builds.* The language stays as it is, and the tool does what it alone can, since it holds both builds' name tables. It finds the running service with the old build's code. It sends the upgrade with the new build's, the address captured as a value. Then it has the node take the running process as the value of the new build's binding, so that later code of the new build finds it and starts no second one. That adoption is a new operation of the runtime, checked by the protocol's hash, and no change to the language.

**After the service's node restarts.** The protocols a process has had live in the process, and a restart of its node ends it. The new build starts a service of the new protocol alone. A client of the old build on another node that finds the service again does so by `Peer.find`, which ships a function that reads the binding, and that function names the old definition's hash. As the rules stand the node fetches the old code and starts a second service of the old version beside the new one, empty, with nothing failing and nothing said. That is the worst of the outcomes, and it stands whether or not a protocol ever changes in place. Nothing can keep what the restart ended: the old client knows the service's name, its old definition's hash and its old protocol's hash, and the definition is gone on purpose, so the name and the protocol are all there is to find it by. Two answers follow, which go together. The new build serves the old name: the new service takes a new name, as its protocol does, and the old name stays in the source as a view of it through the translation, `let counter : Address(CounterMsg) = via(counter2, translate)`. And a service binding that shipped code names is matched on the peer by its name and its protocol where the definition's hash is unknown there: the same name and protocol is the peer's own binding, the view; the same name and another protocol is a failure `Peer.find` answers, the service being at another version; and a second service is never started. This is the first shape above, kept to the one direction in which its cost is small: an old client reaches new code through a translation the new build states in a line, where the worry was a new client reaching old code with nothing in its text. With the tool's adoption, a running service is one process under both builds' bindings, each at its own protocol. A node restarts for more than a fault, a new runtime or a new OTP among the reasons (below), so the view is in the source wherever old clients are to be served, and `become` takes the function the view is made with: one translation, used twice.

**The hash in an address is its protocol's version.** *Superseded by MVP 3.1: no message and no address carries a hash, a key does, and a process that serves two protocols is matched at a find by either identity (`mvp3.1.md`, section 11).* The thinking had the address carry the hash of its process's mailbox type, and the receiving node check it. After a change of protocol every old client on a peer would fail that check, and lose its connection as a faulty peer. The check becomes that the hash is of a protocol the process has had; the message is then decoded with that protocol's types and translated, as a local old client's is. No peer needs new code, and none is told. An adapted reply that leaves the node crosses as an adapted address does, the conversion applied on the node that made it. On the host a local address is a pid alone, and constructors of one name in two protocols are one term, so an address made after a change has to carry which protocol it is of; a process that never changes its protocol pays nothing.

**A rollback across a change of protocol.** Section 3.4's rollback resumes the old loop. After a change of protocol the old loop has the old mailbox type, and addresses of the new protocol may already have left the service, through `self()` or a binding, so resuming it would need the opposite translation, from new messages to old. What a rollback is for is the state, which a fault in new code must not lose, and that is had without going back: the function the new loop's `restarting` runs is a closure over the state as it was at the switch (section 7.2), so a fault runs the new loop again from that state, under the same mailbox type, with no address made wrong. A loop that keeps faulting meets its limit and its supervisor. What it handled between the switch and the fault is lost, as at any restart (§6.9). Going back to the old protocol is going forward: a later build whose translation runs the other way.

**A reply held when the protocol changes.** §6.6 excuses a path that cannot return from answering its replies, since a fault ends the process and every call waiting on it. A function whose result type is a type variable is such a path. `become` ends nothing, so a reply dropped there would leave its caller waiting, and `become` is given the result type `Unit`: it is then no such path, and the reply rule holds as anywhere. A reply held where `become` is called is captured by the loop handed over, which the rule already counts as handing it on, or it is the error of a reply not answered on every path. What is written after a call of `become` is checked and never runs, as after a loop that does not end.

**How long an old protocol is served.** A service that changes its protocol ten times would hold ten, and translate the first one's messages nine times over. The source decides, as it does for names (section 2): a service serves an old protocol for as long as the build holds that protocol's type and its translation. A later build that deletes them retires it. The deploy tool sees the deletion, since it compares the two builds, and tells the service at that upgrade to drop the protocol. From then on a message to it is one to an ended process, and a client that looks the service up by it is answered that the service is at another version. So an old protocol ends by an act a reviewer sees, the deletion of code, taken with the count of messages still translated from it (section 7.4), and not by a timer. Until then only its own clients pay for the chain.

**A changed protocol takes a new name.** A translation names the old protocol and the new one in one build. A type's hash covers its qualified name, and within one build a name has one meaning. So the old type cannot be the one renamed: under another name it has another hash, and the old clients' addresses no longer fit it. The new protocol takes the new name, `CounterMsg2` beside `CounterMsg`, and the old type stays in the source unchanged, with every type it refers to, for as long as the translation serves it. A protocol whose service must outlive the change is then not edited: a new type is added beside it.

**An upgrade case is a permission.** An address is the permission to send, so whoever holds a service's address may send its upgrade. A service would hand its clients an address of its requests alone, made with `via`, and keep the address of its whole protocol for what deploys it; `via` gives that with no new concept. On the wire an adapted address holds its target's address, so between nodes this narrows nothing that the trust in a peer has not already granted.

**MVP 3.0 alone upgrades nothing.** MVP 3.0 ships code between nodes of one build, and a peer of another build is refused. Until MVP 3.1 a deploy stops every node and starts every node, and everything in section 3 waits for the hashes.

### 7.4 In practice

Most production systems, Erlang's among them, do not upgrade in place. They start the new version beside the old, move the traffic and drain the old, with the state kept outside the processes. An upgrade in place serves where reconnecting costs: a telephone call, a chat or game server holding many connections, a trading gateway. So the thinking is to make the ordinary path excellent and the upgrade in place safe.

- **A deploy planned from the hashes.** For each service binding, by its name in the two builds' name tables: its definition and its protocol unchanged is nothing to do; its definition changed behind the same protocol is an upgrade in place; its protocol changed is an upgrade in place with a translation, which the plan asks for and checks is there. Erlang's `appup` files say this by hand. A tool that prints the plan before a deploy, and refuses what it cannot do safely, is worth more than a feature of the language.
- **A keeper.** A service built as a process that holds the state behind a small protocol that seldom changes, with the logic that changes often in processes cheap to replace, or in functions the keeper upgrades. Most deploys are then changes of logic. The guide would teach it as the ordinary way to build a service.
- **Rollback by default.** Where the new loop faults within a limit, the old loop resumes with the state it handed over. Across a change of protocol the new loop is run again from that state instead (section 7.3).
- **A restart follows the upgrade**, as in section 7.2.
- **The code's hash in `Process.info`**, so that a deploy lists the processes still on old code.
- **A protocol change run by the tool.** The tool checks that the new build holds a translation from each protocol a running service speaks, writes the additive one, and sends the upgrade. The service counts the messages it translates from each older protocol, so that an operator sees when the old clients are gone and the view may leave the source.
- **An upgrade tested.** Each build tested against the last release's: the old started, the plan applied, the state checked. A path that runs once a quarter decays unless a machine runs it on every commit.

The order the thinking suggests: the plan from the hashes and the code's hash in `Process.info`; then the upgrade in place with its rollback; then the change of protocol by translation.

### 7.5 The story

Not "hot code loading, but typed": that promises the mechanism, the part that cannot be typed. The story is about deploys:

> Ernest knows exactly what changed between two builds, down to each process's protocol. Before a deploy, it tells you which services upgrade in place without a dropped connection, which change their protocol and by what translation, and which are untouched. And the compiler guarantees that a client and a service of different protocol versions never exchange a message.

It is told only once it runs: a demo, a chat server holding many connections upgraded in place with none dropped, then a protocol change carried by its translation, the old clients served on, with the plan printed before each step. Its limits are stated with it: a service cooperates; a protocol change needs a translation, and a retired request an answer; strict hashes make a shared type ripple; a new runtime or a new OTP restarts each node; and a client on another node finds its service again after a loss.
