# Ernest: Code by its hash, thinking for MVP 3.1

Status: raw material for `mvp3.1.md`, which is written the way [`mvp3.0.md`](mvp3.0.md) was, before MVP 3.0 is built. All of it was thought before the peer design was settled and none of it is weighed against it; where the two differ, [`mvp3.0.md`](mvp3.0.md) and its section 11 hold. Nothing here is a decision.

## 1. The aim

Unison names every definition by a hash of its content. Builds become incremental, two versions of a definition are two things and never conflict, a rename costs nothing, since code refers to a definition by its hash and a name is a label on the hash, and code can move between machines because its identity is exact. Ernest takes that idea openly (the plan's MVP 3.1), all but the rename: as the design stands a name is part of what is hashed, and a rename is a change (section 2.5). The aim is to do what it promises soundly and realistically:

- **Sound.** What holds across nodes is argued, as [`soundness.md`](../../docs/soundness.md) argues the core, before it is built (MVP 3.0's first item). Failure is part of the language: a peer's loss puts its processes out of reach and tells their monitors so, with `Unreachable` ([`nodes.md`](nodes.md), section 1.3), a message is sent at most once, a call waits with a deadline, and a reply is checked.
- **Typed processes as the unit of distribution.** Shipping code is spawning a typed process on a peer, its protocol's hash checked.
- **Realistic.** Source stays text files under git, edited and reviewed as any code; the compiler computes the hashes. The runtime is the BEAM, with its decades of production behaviour, on machines a program's owner runs, listed in `ernest.conf` and authenticated by mutual TLS, with no platform to depend on. What hash modules cost on the BEAM, atoms and code memory, is measured before anything is promised.

Unison has shipped for years, and Ernest has a design, so "better" is true only when MVP 3.0 and 3.1 run and their numbers hold. Unison's codebase is a database rather than text files, and its distributed promise lives largely in its hosted cloud; what is said of its internals is said from the outside, and modestly.

## 2. Code by its hash

### 2.1 Identity

**Decided for `mvp3.1.md`, 2026-10-07.** The hash is over the canonical typed tree, not an intermediate form, since the toolchain has none and one kept only to hash would be a second representation of every program; `ern_interface:hash/1` already canonicalizes an interface the same way. A reference is the hash of what it names alone, so that a rename changes no dependent's hash, which is what hashing is for; a foreign declaration, having no hash, is referred to by name and type. A function's own name and positions are out, as in Unison: the spawn site travels in the spawn frame and a trace names a hash by this build's name for it. A type's hash is nominal, with its members, so that two types of one shape stay two and a value ordered under one order never meets another. A group is one hash with positions. No project name, since two codebases that agree on a type's name and definition agree on the type. Amended the same day from the first reader ([`other_systems.md`](other_systems.md), section 6): a group is the strongly connected component in source order, since Unison's order by hash ties and has been defective since 2022; a type's members stand beside its hash as its identity and not inside it, since a member's tree names the type and a hash must not contain a hash that names it; a type rename is a new type and is said so; the scheme's version is mixed into every hash. Messages across builds carry nothing of their type, by the same induction that lets a bound value go unchecked in MVP 3.0: every remote address came from a find, a spawn or an agreed message. The paragraphs below are the thinking before that decision.

**What is hashed.** A definition's hash is the SHA-256, by `crypto:hash/2`, of its canonical form: the version of the format first; each external reference as its qualified name and the hash of what it names; local variables numbered by position; the hashes of the types it uses; named fields in declared order, and construction in source evaluation order (§8.7). Comments and layout are not hashed. Mutually recursive definitions are hashed as one group. The toolchain has no IR today: the emitter goes from the typed tree to Erlang's abstract format in one pass, and whether an IR is added or the typed tree made canonical is the first decision of the plan's MVP 3.1.

**Hash modules.** Each hash, and each group's, is compiled to a module of its own on the host, named `ern#` and the hash in base32. A hash module never changes.

**Types.** A type's hash covers its qualified name, its parameters by position, its constructors by name in declared order, each constructor's field names, and the hashes of its fields' types. An abstract type's hash also covers the types of its module's exported declarations. So renaming a type or a constructor, or moving a type to another module, is a change of protocol between processes. Two unrelated codebases with a type of one qualified name and definition share its hash.

**Names.** The `.ern` files are the source of truth for names. Each build resolves every name afresh and writes a table from name to hash, derived and never edited: no operation points a name at a hash, and no source names a hash. The build keeps every hash it has built in a store that only grows. A definition changes by editing and rebuilding. Its dependents get new hashes, and where a type changed they fail to compile until they are edited, so a build is never half migrated. At run time names serve entry points and debugging, and each node keeps a table from hash back to name. Names are local to a build, and nodes share hashes: nodes built from different commits cooperate through the hashes they share. Within one build a name has one meaning, and an old version still needed keeps a name of its own in the source.

### 2.2 What the hashes leave out

**To keep in mind, 2026-10-07.** A function of the standard library written in Ernest is hashed code: it crosses with a spawn, differs between builds, and is deployed with a program. A shim is the platform's: fixed by `ern`'s version, changed only by an upgrade of `ern`, which in MVP 3.1 stops every node and in MVP 3.1a rolls. So the pure half of the library has an advantage the shim half has not, in how it moves and how it changes, and that weighs on the long run of what is written as Ernest and what as a shim, without changing anything decided now.

**Decided for `mvp3.1.md`, 2026-10-07.** The cookie is the digest of the protocol's version, the hash scheme's version, `ern`'s version and OTP's version, the build's checksum of MVP 3.0 leaving it. `ern`'s version stands for the runtime, the back end and the standard library at once, so an upgrade of `ern` is a stop of every node, which is honest: shipped code calls the runtime by name and nothing hashes that surface. A later milestone narrows it to the surface alone. The paragraph below is the thinking before that decision.

**What the hashes leave out.** Three things are not hashed and must agree across nodes: the hash scheme, checked in the handshake; the compiler's back end, on every node, whose version keys the cached binaries; and what hashed code calls by name, the host's built-in functions and Ernest's runtime, pinned for each deployment with the OTP version. The prelude's types and the standard library are hashed as a program's code is. Their foreign declarations are excepted, and are each node's own (§8.7).

### 2.3 A node's code

**One kind of node.** Each node has a cache of code keyed by hash: persistent, on disk and possibly filled at deployment, or volatile, in memory and empty at start. A program's code may be absent, and a node receives what it needs from its peers. The platform may not be absent: the host and its applications, Ernest's runtime and loader, and the compiler's back end. A diskless node can boot the platform over the network by `-loader inet` and `erl_boot_server`, which use no Erlang distribution and no TLS.

**The loader** stands beside the host's unchanged `code_server`, which keeps its table of loaded modules, its purging and its serialized loads. The loader's cache is ETS, from hash to code and compiled binary, and on a persistent node one file for each hash. It verifies first: the hash of incoming code is computed before anything else, and a mismatch rejects it. It compiles to a binary by `compile:forms` with `deterministic`, and caches the binary under the hash, the back end's version and OTP's. Every unit lists the hashes it references, so a fetched closure is known to be complete before any of it is loaded. The closure is loaded at once, all of it or none, by `code:prepare_loading/1` and `code:atomic_load/1`; the first does the heavy work in the calling process, so the one `code_server` should not become a bottleneck, which the plan's MVP 3.1 measures. Nodes run in the host's embedded mode, which loads nothing from the code path on demand, so a missing module is an honest failure.

**Decided for `mvp3.1.md`, 2026-10-07: the exchange.** The root's hash goes first, so that the common case, a peer that has it, costs one round trip and no list; the list, the lacks and the code follow only where the peer lacks the root, as Unison does and as Git's negotiation over commits suggests ([`other_systems.md`](other_systems.md), section 6). The frame carries the hashed form, since by Nix's rule a content-addressed object verifies itself and a binary named by its source's hash can only be trusted; the peer compiles with its own back end and caches by hash. Arrivals wait in quarantine until the closure is complete and verified, then one atomic load, which Git's quarantine and Unison's temp entities both argue; what the peer said it has is pinned meanwhile, as Nix pins. A foreign declaration the peer lacks is `NotLoaded`, known from the list before any code moves. A faulty frame ends the connection, as in MVP 3.0.

**Have and want.** Only a spawn on a peer ships code (§8.7). Before a spawn frame's payload is decoded, the sender lists the hashes, of code and types, that the function references transitively, its captures included. The receiver answers with those it lacks, and the sender sends them. The receiver verifies, compiles and loads them. Only then is the payload decoded, since a value cannot be read before its types are loaded, and the process starts. So the whole closure is present before anything runs. A failed exchange is a resolution failure, which faults the caller of the spawn.

**Risks.** Normalization, where an error costs most: two hashes for identical code or, worse, one hash for different code. And the time to compile when a node receives much code at once, typically as it starts.

### 2.4 The memory of code

**Unloading.** A hash may be unloaded, and removed from the cache, when no name table on the node refers to it, no loaded hash depends on it, and `code:delete/1` followed by `code:soft_purge/1` succeeds, the host checking that no process runs its code or holds a function of it. It is tried after a configured idle time. The host's check sees the closures in each process's state, so nothing counts references.

**Atoms and lambdas.** Every module's name is an atom, and the host never collects atoms; its limit is about a million. The host's table of lambdas grows the same way, an entry for each lambda of each version loaded, up to 524,288, and unloading frees neither. So a long-lived node that receives many versions leaks both. The note's answer is that a node counts its atoms and, above a threshold, drains and restarts: every process on it dies, and every address to it is dead. In reserve it holds a hybrid: incoming code is interpreted first, and compiled to a hash module only when hot, so that cold code costs no atom.

### 2.5 Findings

What reading the two notes' design beside this note's thinking shows of the hashes and of a node's code. Each is a finding to weigh, not a verdict.

**Decided for `mvp3.1.md`, 2026-10-07: bindings across builds.** A node holds its bindings' values by hash and initializes nothing for a peer, since an initializer may spawn and the types do not tell a constant from a service; a spawned function captures what it needs. A service is one per node, since a node runs one build, and an old client meets a new service by its key where the type's identity holds. So the second service started empty, which this section feared, cannot arise: a find ships no code and a spawn initializes nothing.

**A rename is a change.** Section 1 counts a rename that costs nothing among what Unison's hashes give. There code is kept as hashes: a definition refers to another by its hash alone, a name is a label on a hash, and a rename moves the label and changes no code. Ernest's source is text, so a rename edits the definition and every use of it. What it could spare is the hashes, and as section 2.1 and §8.7 stand it spares none. A type's qualified name is in its hash by decision, being what makes two types of one shape two types, so renaming a type, a constructor or a field is a change of protocol. A function's follows from the normal form, which keeps each external reference as its qualified name beside the hash of what it names: renaming a function, or moving it to another module, changes the hash of every definition that refers to it, and of all that refer to those. The deploy plan then reports each service that reaches the function as changed, an upgrade in place of each, where no code changed; for a function of the standard library, every service. Whether the renamed function's own hash changes is *D8*. The hash of what a reference names already says what is called, so what the name beside it is for is to be found before it is kept. Three things lean on it. A foreign declaration is found on a peer by its qualified name (§8.7). A top-level binding is evaluated once on a node for each hash of its definition (§8.7), so two service bindings of one initializer, `let a = spawn(worker)` and `let b = spawn(worker)`, are two services where the program starts and one on a peer, unless its name is part of what a binding is. And a spawn's site and a fault's trace name a declaration, which a node's table from hash back to name answers only while a hash has one name, as *D11* asks of two definitions that differ in a line. A build or a `:load` is the other act: the name stays and is given a new hash, the table from name to hash written afresh (section 2.1, *Names*), where a rename gives a hash another name.

**Positions in the hash.** The distribution note asks whether source positions are hashed (*D11*), since a spawn's site names its line. The deploy plan weighs on it: with positions hashed, a line added above a definition changes its hash, and the plan reports every definition below an edit as changed.

**The order in a type's identity.** The plan's MVP 3.1 asks whether a type's identity holds the hash of its `compare`. The state handed over at an upgrade weighs on it. With it, a new `compare` is a new state type, a change of protocol, and declared. Without it, an ordered set carried through the upgrade is misordered, and nothing says so.

**The platform is outside the hashes.** The deploy plan compares hashes, and the hash scheme, the back end, the runtime and OTP are not hashed: a hello whose versions differ is refused. So a new runtime, or a new OTP, is no upgrade in place. Each node restarts, every process on it ends, and state leaves the node first or is lost. The standard library is hashed as a program's code is, so a release that changes one of its functions changes the hash of everything that uses it, an upgrade in place of every such service at once; and a change to a library type that protocols carry is a change of each of those protocols.

**What holds old code.** Code is collected when nothing refers to it, and several things refer in ways the thinking added or the notes left open: the function `restarting`, or a supervisor's child, restarts into; the old loop a rollback keeps; a translation, which holds the old protocol's types for as long as its process lives or its view stands in the source; a binding's evaluation on a node; and an adapted address, whose `{hash, env}` a peer may still send to after the node that made it would unload the code (*D14*). Each needs its answer before "old code is collected" is true.

**A drain and restart ends the service that never ends.** An upgrade in place loads new hash modules: an atom, and its lambdas, for each definition whose hash changed, its dependents included. The node that upgrades without a stop is the one that never sheds them. The distribution note's drain and restart is then the very outage the upgrade was to avoid, on a schedule the leak sets, and the plan's MVP 3.1 already questions it by the rule that memory no collection reclaims is fixed at its cause. So the leak is the floor under the whole story. It wants a number first: how many definitions change hash in an ordinary deploy, and so how many deploys a node takes. Then its cause, in three directions, none tried against the host: whether a module's name must be the hash, or can be drawn from names reused once a module is unloaded, with the node's registry from hash to module; whether a closure in a hash module must be a lambda of the host's, since a function already crosses as `{hash, env}`; and the hybrid, which moves from a reserve toward the main road.

### 2.6 Open questions

**The hash**

- The full normalization rules, written apart before MVP 3.1: how references inside a group are numbered; how literals, closures and constructors are made canonical; and how type expressions such as `Msg(Int)`, function types and `with m` are hashed, since an address carries the hash of an instantiated mailbox type. (*D5*)
- When the format that is hashed is frozen: every change to it changes every hash, a cutover of every node. (*D3*)
- Whether a function's own name is in its hash; §8.7 names only its references'. (*D8*)

- Whether a reference to a function is hashed with its qualified name, as §8.7's normal form keeps it, or by the hash of what it names alone, and so what a rename costs; and whether a top-level binding's own name is part of what it is on a peer. Decided with *D8* and *D11* (section 2.5).
- Whether a mutually recursive group is one module, each member's identity derived from the group's hash. (*D12*)
- Whether a project name at the top of every qualified name parts two unrelated codebases' types of one name and definition. (*D16*)
- Whether a type's identity holds the hash of its `compare`, which the plan's MVP 3.1 asks (section 2.5).

**Resolution and foreign code**

- Whether a node running hash modules keeps embedded mode, or finds a `foreign fn`'s Erlang module on the load path as §11.2 does. (*D9*)
- What makes a peer's foreign declaration compatible with the one a shipped function names: the same type and implementation, or the same type alone. (*D10*)
- How the exchange finds a system module the peer's runtime lacks and a foreign definition that differs, which §8.7 counts as resolution failures and the hashes leave out; and whether code that fails verification is a resolution failure or the loss of the peer. (*D13*)
- Whether a code frame carries the form that is hashed, which the receiving node compiles, or the compiled module, trusted as its peer is. The first is checked against its hash on arrival, serves a node of another back end, and can be interpreted. The second needs no compiler on the receiving node and no wait at a first spawn, and is among what the distribution note left out (*D17*). The form that is hashed is needed either way, being what a definition's identity is of.

**The memory of code**

- How unloading keeps code present: a delete before a soft purge that fails leaves a hash with no current code, and an adapted address sent to a peer carries a `{hash, env}` whose code the making node may unload while the peer can still send to it. (*D14*)

## 3. Code change in running processes

### 3.1 Loading and upgrade in place

**Decided for `mvp3.1.md`, 2026-10-07: `Code`.** Under hashes a program has nothing to load by name, since it names every function it calls, so `Code` is two functions for the toolchain's Ernest code and for tools: `load`, which is `ern run`'s loading of a compiled module and its closure, and `hashes`, which answers a module's definitions as name and hash. The host's checkless load is not offered; a load changes nothing under a running process; letting code go is the runtime's. The shell's `:load` and `:reload` stand on it, compiling staying the toolchain's. These answer the six decisions the plan held for `Code`.

**The objection.** A typed language, it is said, cannot have Erlang's code loading. Of the mechanism that is true. Erlang swaps a module under every process that runs it, a state takes a new shape in `code_change`, and messages of any shape keep arriving: the types of live data and of messages in flight change with nothing to check them against. Of what the mechanism is for it is not true. A running system upgraded without a stop, old and new code side by side, has a typed form, and §6.10 is a start of it: a process takes a message in its own type that carries the new loop, checked against its mailbox type before it arrives, and carries its state over by a typed function, Erlang's `code_change` checked. What a typed process cannot do is change its mailbox type silently, since its clients hold an address of the old type. In Erlang the same mismatch shows at run time, as messages nobody matches; Ernest would make a program say how old clients are served, as a function from the old messages to the new, and with that function the type may change in place (below).

**Loading never disturbs running code.** A hash module never changes, so loading only adds. A process keeps the code it runs until its own upgrade case moves it, or until it ends, so loading new code is as safe as starting a process. BEAM's limit of two versions of a module, which kills a process still in the old one on a third load, does not arise. The cost moves to unloading: code stays loaded while any process, message or value refers to it, and memory no collection reclaims is a defect, so code is collected.

**A load moves names, and compiled code holds hashes.** A name is resolved to a hash when code is compiled, never when it is called. A load is a build's result brought into a running node, by a deploy or by the shell's `:load` and `:reload`. It gives a new hash to each definition that changed, and to each definition that refers to one of those, in whatever module, since a definition's hash covers the hashes of what it refers to. The rest keep theirs, and nothing is loaded for them. A hash is a definition's or a group's, and a module has none. The table from name to hash, the build's and a shell session's, then gives each of those names its new hash. What is compiled from then on, a shell input or a module built against it, reaches the new code. What was compiled before holds the old hashes and runs the old code, a running process and a function held in a value among it. Erlang's call by a module's name finds the latest version at each call, and the shell's reload leans on that today: it compiles again a module that uses a reloaded one only where the interface changed (§11.2). Under hashes a definition that refers to a changed one always gets a new hash, linked again where its text did not change. A service binding is no exception: one whose loop changed is another binding, and code compiled after the load reaches a second service (section 3.3).

**An upgrade arrives as code does, by a spawn.** A function does not cross nodes in a message (§3.11). A process on another node is sent its upgrade by a process spawned on that node, to which the spawn gives the new function (§6.10).

**An upgrade in place is not a restart.** It is a tail call. Nothing the process asked the runtime for is cancelled, its alarms, monitors and subscriptions; its mailbox is kept; and the replies it holds go on in its state. A restart begins afresh (§6.9).

**The service that never ends.** A short-lived process ends on its old code, and its successor begins on the new. A long-serving service never ends, so it sees new code only through an upgrade case of its own; the runtime cannot migrate a state it cannot see, which lives in the loop's arguments. A process whose type has no upgrade case is replaced instead. A change of logic behind the same protocol upgrades in place with no outage: the address stays, and what arrives meanwhile waits in the mailbox. It is the common case of a fix, and not of a service that grows: a feature is most often a new message, so a change of protocol is ordinary and has to be as safe.

### 3.2 A change of protocol

**A change of protocol is an upgrade in place, with a translation.** Three answers were weighed and left. A forwarder, a second process that holds the old protocol and hands each message on, is a loop written and kept by hand around the one thing that cannot be avoided, the function from an old message to a new one. A rule that a type with one more constructor is accepted where the old one is needs a subtyping the language does not have (principle 5). And a service whose protocol may never change is too little. What is left is that function alone. The process stays, as in any upgrade in place: its identity, its state, what it holds and what it asked the runtime for. Its mailbox type changes through one gate, under the working name `become`: `become : ((old) -> new, () -> Unit with new) -> Unit with old`. It takes the translation and the new loop, and runs the loop in place of what called it. It is the one place a process's mailbox type changes, and it cannot be called without the translation. Its result type is `Unit` and not a type variable, though it never returns to its caller, so that §6.6 holds it to its replies (section 3.3). An `Upgrade` case of §6.10's shape carries it with no change to the old protocol: the `next` it hands over has the old mailbox type, and is a function that calls `become`.

**Old addresses keep their meaning.** An address made before the change is an address of the old protocol, and what is sent to it is translated by the service itself as it takes the message. So are the messages waiting in the mailbox at the switch, and what the service's own alarms and monitors deliver, whose `wrap` functions were written to make old messages: one rule, that what is addressed to an older protocol passes through the translation. A translation that faults is then the service's own fault, as a fault in its loop is. A process that has changed its protocol twice translates through both, for as long as the build holds both (section 3.3).

**The translation is total.** The inclination is that it answers a new message for every old one, and never nothing. The reply rule then does the rest (§6.6): the translation is pure and cannot answer, and a reply is consumed exactly once, so each old request's reply must go into a new message, and no old caller is dropped. Where the answer's type changed, the reply is adapted as an address is, by a `via` for replies of `via`'s own shape, `(Reply(old), (new) -> old) -> Reply(new)`: answering the adapted reply answers the old caller with the converted answer. A request the new protocol retires still has a reply to place, in a constructor the new service answers with the old answer type's failure; an old request whose answer type has no failure cannot be retired while an old client may ask, which is the promise the old protocol made. So a service's answers hold a failure from the start.

**Nothing dies, so nothing is told.** No monitor sees the change, as none sees a restart (§6.9); a call waiting on the service waits on, since its callee has not ended; a socket the service owns is still owned; `Process.fromAddress` gives one process for an old address and a new one; and `kill` through an old address kills the service.

**An additive change** is the translation that maps each old constructor to its namesake. It is written, and so seen (principle 3), and the deploy tool, which holds both builds, could write it.

**A forwarder written by hand** remains possible in the language as it is, and is what a program falls back on where a point of this proves wrong.

**A discipline around upgrade types.** An upgrade case each service writes by hand is forgotten, or written in a shape of its own, and then nothing upgrades services alike. A fixed shape lets a supervisor, the shell or a tool upgrade any service, as OTP's system messages reach every behaviour, but visibly, in each protocol's type (principle 3). One form is a library type over the language's own: a service's mailbox `Service(Msg, State)`, its messages and an `Upgrade` that carries the new loop as `(State) -> Unit`, which adds no concept (principle 5). A rule of the language that every service binding holds one would be stronger, and would bind services that never change.

**The state as a schema.** In that form, the state's type at the switch is the service's contract with its later versions: the new code is handed a `State`. What it does with it is its own. Behind the same protocol a new loop holds any state it likes inside and hands over a `State` at its next upgrade. With a change of protocol the new `Service` type names its own state, and the function that calls `become` carries the old state into it, as `migrate` does in §6.10.

**A restart after an upgrade.** `restarting(limit, f)` and a supervisor's child hold `f` by its hash. A service upgraded and then faulting would restart into the `f` it was spawned with, and the fix would vanish at the first fault. Erlang's restart calls the start function by name and finds the new module. An upgrade would have to replace what a restart runs, so the discipline reaches `restarting` and `Supervisor`, not the loop alone. After a change of protocol it is no longer a matter of keeping a fix: a restart into the old function would run a loop of the old mailbox type under addresses of the new one. `become` runs its loop in place of the old stack, the `restarting` function the old loop ran under included, so the new loop states its own: `become(translate, restarting(limit, fn() = loop(state)))`. That is written and seen (principle 3), and the runtime replaces no function behind the program. The count of restarts begins anew. A supervisor's child states its own the same way, through `Supervisor.child` again; a child is known to its group by its process, which `become` keeps, so a join from a process the group holds keeps its place.

**Clients of two versions.** Clients that share a protocol type share its hash, and the service sees one type from all of them, whatever their own code's version. A client built against another version of the protocol holds an address of another type, and an address carries its mailbox type's hash, so no message of one version is read as the other's. Nor does such a client reach the service through its binding as the rules stand: its own binding is another binding, which starts a second service on the peer (section 3.3). The price is strictness. A type's hash covers what it refers to, so a change to a record deep in a protocol is a new protocol, and a change to a type many protocols share means replacing every service that carries it. So the discipline has a second half: a service's protocol types are small, stable and its own, not built from types shared across a program, and most changes are then changes of logic behind a stable protocol.

**Compatible evolution.** A second version that adds a constructor and is accepted where the first is, as protobuf's systems allow, would be an exception to "two versions of a type are two types", and a subtyping. It stays out: the additive translation above does its work, written.

**Where the thinking stands on a change of protocol**, on 6 October 2026. Settled means the thinking no longer weighs it; it is no decision of the report's until it goes to its owner.

Settled:

- A change of protocol is an upgrade in place: the same process, with a total translation from its old messages to its new, through `become` alone. No forwarder is written, no subtyping is added, and no protocol is fixed for a service's life.
- What is addressed to an older protocol is translated by the service as it takes it. Every old reply is carried into a new message, by the reply rule, and adapted by a `via` for replies where the answer's type changed. A retired request keeps a constructor that answers its old callers with a failure.
- Nothing is told of the change: no monitor, no waiting call, no owner of a resource.
- The new loop states its own `restarting` function and its own place under a supervisor. Its closure holds the state as it was at the switch, so a fault in the new loop runs it again from that state. That is the rollback a change of protocol has (section 3.3).
- `become` has the result type `Unit`, so a reply held where it is called is carried into the new loop or is an error (section 3.3).
- An old protocol is served for as long as the build holds its type and its translation, and no longer (section 3.3).
- On a peer, an address's hash says which protocol it is of, and a node accepts each protocol its process serves. After a restart of the service's node the old name is a view of the new service in the source, a service binding is matched by its name and protocol, and a second service is never started unseen (section 3.3).

Open, each in section 3.6: how a process tells an older protocol's message from its own on the host, and what `receive` does on intake; the `via` for replies, its name and how it crosses nodes; whether a join from a process its group holds keeps the child's place, read against `Supervisor`; how the tool tells a service to drop a protocol; what makes a binding a service binding for the matching rule; and `become`'s name.

### 3.3 Across builds and nodes

What reading sections 2 and 3 beside sections 4.1 and 4.2 shows of code change. Each is a finding to weigh, not a verdict.

**A service across two builds.** §8.7 gives a top-level binding the hash of its definition, with everything the definition refers to. A service binding refers to the loop it spawns, so a fix to the loop gives the binding a new hash. §8.7 says what follows: a binding whose definition differs from the peer's by hash is another binding, and code of the new build that names the service starts a second one on the peer, running the new version, beside the first. That is versions side by side, as designed, and it is replacement with no handover: the new service starts empty, and the old one runs on for the clients of the old build, with nothing to end it. An upgrade in place needs the opposite, code of the new build reaching the service that runs. As the rules stand it cannot name it: its own binding is another binding, and no source names a hash. Two shapes of answer are in sight.

- *The binding's identity changes.* A service's identity across builds is its binding's qualified name and its protocol's hash, in place of its definition's hash, so that the new build's binding is the running service wherever the protocol is unchanged. That gives a binding an identity unlike every other definition's (principle 2), and lets new clients talk to old code until the upgrade lands, which nothing in their text shows (principle 3).
- *The deploy tool bridges the builds.* The language stays as it is, and the tool does what it alone can, since it holds both builds' name tables. It finds the running service with the old build's code. It sends the upgrade with the new build's, the address captured as a value. Then it has the node take the running process as the value of the new build's binding, so that later code of the new build finds it and starts no second one. That adoption is a new operation of the runtime, checked by the protocol's hash, and no change to the language.

**After the service's node restarts.** The protocols a process has had live in the process, and a restart of its node ends it. The new build starts a service of the new protocol alone. A client of the old build on another node that finds the service again does so by `Peer.find`, which ships a function that reads the binding, and that function names the old definition's hash. As the rules stand the node fetches the old code and starts a second service of the old version beside the new one, empty, with nothing failing and nothing said. That is the worst of the outcomes, and it stands whether or not a protocol ever changes in place. Nothing can keep what the restart ended: the old client knows the service's name, its old definition's hash and its old protocol's hash, and the definition is gone on purpose, so the name and the protocol are all there is to find it by. Two answers follow, which go together. The new build serves the old name: the new service takes a new name, as its protocol does, and the old name stays in the source as a view of it through the translation, `let counter : Address(CounterMsg) = via(counter2, translate)`. And a service binding that shipped code names is matched on the peer by its name and its protocol where the definition's hash is unknown there: the same name and protocol is the peer's own binding, the view; the same name and another protocol is a failure `Peer.find` answers, the service being at another version; and a second service is never started. This is the first shape above, kept to the one direction in which its cost is small: an old client reaches new code through a translation the new build states in a line, where the worry was a new client reaching old code with nothing in its text. With the tool's adoption, a running service is one process under both builds' bindings, each at its own protocol. A node restarts for more than a fault, a new runtime or a new OTP among the reasons (below), so the view is in the source wherever old clients are to be served, and `become` takes the function the view is made with: one translation, used twice.

**The hash in an address is its protocol's version.** [`nodes.md`](nodes.md), section 1.4's address carries the hash of its process's mailbox type, and the receiving node checks it. After a change of protocol every old client on a peer would fail that check, and lose its connection as a faulty peer. The check becomes that the hash is of a protocol the process has had; the message is then decoded with that protocol's types and translated, as a local old client's is. No peer needs new code, and none is told. An adapted reply that leaves the node crosses as an adapted address does, the conversion applied on the node that made it. On the host a local address is a pid alone, and constructors of one name in two protocols are one term, so an address made after a change has to carry which protocol it is of; a process that never changes its protocol pays nothing.

**A rollback across a change of protocol.** Section 3.4's rollback resumes the old loop. After a change of protocol the old loop has the old mailbox type, and addresses of the new protocol may already have left the service, through `self()` or a binding, so resuming it would need the opposite translation, from new messages to old. What a rollback is for is the state, which a fault in new code must not lose, and that is had without going back: the function the new loop's `restarting` runs is a closure over the state as it was at the switch (section 3.2), so a fault runs the new loop again from that state, under the same mailbox type, with no address made wrong. A loop that keeps faulting meets its limit and its supervisor. What it handled between the switch and the fault is lost, as at any restart (§6.9). Going back to the old protocol is going forward: a later build whose translation runs the other way.

**A reply held when the protocol changes.** §6.6 excuses a path that cannot return from answering its replies, since a fault ends the process and every call waiting on it. A function whose result type is a type variable is such a path. `become` ends nothing, so a reply dropped there would leave its caller waiting, and `become` is given the result type `Unit`: it is then no such path, and the reply rule holds as anywhere. A reply held where `become` is called is captured by the loop handed over, which the rule already counts as handing it on, or it is the error of a reply not answered on every path. What is written after a call of `become` is checked and never runs, as after a loop that does not end.

**How long an old protocol is served.** A service that changes its protocol ten times would hold ten, and translate the first one's messages nine times over. The source decides, as it does for names (section 2.1): a service serves an old protocol for as long as the build holds that protocol's type and its translation. A later build that deletes them retires it. The deploy tool sees the deletion, since it compares the two builds, and tells the service at that upgrade to drop the protocol. From then on a message to it is one to an ended process, and a client that looks the service up by it is answered that the service is at another version. So an old protocol ends by an act a reviewer sees, the deletion of code, taken with the count of messages still translated from it (section 3.4), and not by a timer. Until then only its own clients pay for the chain.

**A changed protocol takes a new name.** A translation names the old protocol and the new one in one build. A type's hash covers its qualified name, and within one build a name has one meaning. So the old type cannot be the one renamed: under another name it has another hash, and the old clients' addresses no longer fit it. The new protocol takes the new name, `CounterMsg2` beside `CounterMsg`, and the old type stays in the source unchanged, with every type it refers to, for as long as the translation serves it. A protocol whose service must outlive the change is then not edited: a new type is added beside it.

**An upgrade case is a permission.** An address is the permission to send, so whoever holds a service's address may send its upgrade. A service would hand its clients an address of its requests alone, made with `via`, and keep the address of its whole protocol for what deploys it; `via` gives that with no new concept. On the wire an adapted address holds its target's address, so between nodes this narrows nothing that the trust in a peer has not already granted.

**MVP 3.0 alone upgrades nothing.** MVP 3.0 ships code between nodes of one build, and a peer of another build is refused. Until MVP 3.1 a deploy stops every node and starts every node, and everything in section 3 waits for the hashes.

### 3.4 In practice

**Decided for `mvp3.1.md`, 2026-10-07: the rolling deploy.** Step C's deploy is a rolling restart, one node at a time, services met by key, and a changed protocol answering `OtherType` across the rollout, which the program handles as it handles `Unreachable`. `ern diff old-build new-build` is the one tool: the definitions whose hash changed and the keys whose identity changed, a list and not a plan, since a plan that orders a rollout and checks translations is step D's. The discipline below, a service's protocol small, stable and its own, is what makes most deploys silent, and is the guide's to teach.

Most production systems, Erlang's among them, do not upgrade in place. They start the new version beside the old, move the traffic and drain the old, with the state kept outside the processes. An upgrade in place serves where reconnecting costs: a telephone call, a chat or game server holding many connections, a trading gateway. So the thinking is to make the ordinary path excellent and the upgrade in place safe.

- **A deploy planned from the hashes.** For each service binding, by its name in the two builds' name tables: its definition and its protocol unchanged is nothing to do; its definition changed behind the same protocol is an upgrade in place; its protocol changed is an upgrade in place with a translation, which the plan asks for and checks is there. Erlang's `appup` files say this by hand. A tool that prints the plan before a deploy, and refuses what it cannot do safely, is worth more than a feature of the language.
- **A keeper.** A service built as a process that holds the state behind a small protocol that seldom changes, with the logic that changes often in processes cheap to replace, or in functions the keeper upgrades. Most deploys are then changes of logic. The guide would teach it as the ordinary way to build a service.
- **Rollback by default.** Where the new loop faults within a limit, the old loop resumes with the state it handed over. Across a change of protocol the new loop is run again from that state instead (section 3.3).
- **A restart follows the upgrade**, as in section 3.2.
- **The code's hash in `Process.info`**, so that a deploy lists the processes still on old code.
- **A protocol change run by the tool.** The tool checks that the new build holds a translation from each protocol a running service speaks, writes the additive one, and sends the upgrade. The service counts the messages it translates from each older protocol, so that an operator sees when the old clients are gone and the view may leave the source.
- **An upgrade tested.** Each build tested against the last release's: the old started, the plan applied, the state checked. A path that runs once a quarter decays unless a machine runs it on every commit.

The order the thinking suggests: the plan from the hashes and the code's hash in `Process.info`; then the upgrade in place with its rollback; then the change of protocol by translation.

### 3.5 The story

Not "hot code loading, but typed": that promises the mechanism, the part that cannot be typed. The story is about deploys:

> Ernest knows exactly what changed between two builds, down to each process's protocol. Before a deploy, it tells you which services upgrade in place without a dropped connection, which change their protocol and by what translation, and which are untouched. And the compiler guarantees that a client and a service of different protocol versions never exchange a message.

It is told only once it runs: a demo, a chat server holding many connections upgraded in place with none dropped, then a protocol change carried by its translation, the old clients served on, with the plan printed before each step. Its limits are stated with it: a service cooperates; a protocol change needs a translation, and a retired request an answer; strict hashes make a shared type ripple; a new runtime or a new OTP restarts each node; and a client on another node finds its service again after a loss.
