# Ernest: Code, the reasons

Status: the reasons for code and for termination told as [`mvp3.1.md`](mvp3.1.md) designs them, written on 2026-10-08 with the rewritten proposal and changed on its read-through the same day, when the kept state gave way to a program told of its end, in the order of its section 6, and kept in sync with the latest proposal that touches code; nothing here is normative, and the proposal states what this argues. Each paragraph is dated where it was decided; one the rewriting proposes and the read-through has not yet settled is marked *proposed*. The reasons for the first design, code by its hash with nodes of different builds working together, are [`set_aside/code.md`](set_aside/code.md), kept whole as the record beside the proposal it argued for, and its part two is the record of the thinking for a running process that takes new code in place, which stays out; the reasons for the kept state's first design, with the deploy around it, are [`set_aside/deploy.md`](set_aside/deploy.md). The reasons for nodes are [`nodes.md`](nodes.md)'s, the end that tells its subscribers in its section 4 and the standing address in its section 14; what other systems do is [`other_systems.md`](other_systems.md), sections 6 and 7.

## 1. The aim

Unison names every definition by a hash of its content, so that two versions of a definition are two things and never conflict, a rename costs nothing, since code refers to a definition by its hash and a name is a label on the hash, and code can move between machines because its identity is exact. Ernest takes the idea for one use: code that crosses with a spawn. With one build on every node, which MVP 3.0's fingerprint holds, nothing else needs an identity that a name does not give. Two things want code to cross, and neither has anything to do with a deploy: the shell as a node, which spawns on a peer what was typed at it, today `NotLoaded` since no peer has the shell's module; and the bare node, a worker pool the program fills with code, a machine with `ern` on it and nothing else. The same mechanism makes `NotLoaded` exact, by binding rather than by module, since the closure a spawn names says which bindings a function reaches (decided on 2026-10-08, the log's *The Milestones After 3.0, Weighed Again*).

**The four steps.** Loading new code was four steps, of which MVP 3.0 is the first. On 2026-10-08 step D was set aside and step C trimmed to what the two uses above need; of step D the planned stop and the kept state were kept at first and set aside on the read-through the same day, and in their place a program is told of its termination (section 7).

| Step | What it gives | Where |
|---|---|---|
| A | one build on every node, and a deploy that stops them all | MVP 3.0, built |
| B | nodes of different builds connect; no code crosses | not built on its own, and set aside with C's second half |
| C | a hash for each definition; code crosses by one exchange, at a spawn; two versions stand side by side on a node, across the shell's reload | MVP 3.1, `mvp3.1.md` |
| D | a running system takes new code, as an ordered rolling restart | set aside, [`set_aside/ordered_rolling_restart.md`](set_aside/ordered_rolling_restart.md) |

What went, and why: a coordinator, a plan from the hashes, lockstep, `ern deploy`, `ern diff`, `ern status` and `ern state` order a rollout across machines, which Erlang leaves to release tooling and Go to the platform, so a reader who knows Erlang expects it outside the runtime (principle 1), and they add eight or nine concepts for a system of a few nodes listed by hand (principle 5); the identity by shape that lets two builds connect and the bookkeeping of which types changed between builds exist so that an old node and a new one run side by side during a rollout, and with one build per deployment they do little and are the complicated half. A deploy is stop all and start all, by `ern stop` and `ern run`, which an operator orders with a script, as a balancer is a library and not a feature. Replacing a module under running processes, as Erlang's `code` module does, is none of the steps: it changes code with nothing to check its types against.

## 2. The hash

**The canonical typed tree, references by hash, no own name.** Decided on 2026-10-07 and 2026-10-08. The hash is over the canonical typed tree, not an intermediate form, since the toolchain has none and one kept only to hash would be a second representation of every program; `ern_interface:hash/1` already canonicalizes an interface the same way. A reference is the hash of what it names alone, so that a rename changes no dependent's hash, which is what hashing is for; a foreign declaration, having no hash, is referred to by name and type, and each node resolves it for itself. A function's own name and positions are out, as in Unison: the spawn site travels in the spawn frame and a trace names a hash by this build's name for it. A binding's identity is its qualified name with its definition's hash, since a function's hash leaves out its own name and two bindings with one initializer, `let a = spawn(worker)` and `let b = spawn(worker)`, would otherwise be one value on a node; a binding is a thing that exists, as a service is, and so holds its name where a type, which is a shape, does not. A group is one hash with positions, the strongly connected component in source order, since an order by hash ties where two members differ only in which other member they name. The scheme's version is mixed into every hash, so that hashes of two schemes are never equal, and it changes with any change to what runs before hashing, the canonical form and the checker among it. Names stay in the `.ern` files: a build resolves every name afresh and writes the table from name to hash, derived and never edited, so that no operation points a name at a hash and no source names one. What an abstract type's hash covers beyond its declaration, the types of its module's exported declarations or nothing, is the canonical form's document to decide, the milestone's second item.

**A type's hash covers its name.** Decided on the read-through of 2026-10-08. The first design hashed a type by its shape alone, its parameters by position and its constructors in declared order with their fields' names and the hashes of their types, so that a type renamed or moved between modules kept its identity across builds, and a kept state's file, written by one build, matched the old shape kept under another name in the next; with `compare` beside the hash as the type's identity, since a value ordered under one order must not be read back under another. Nodes of different builds went on 2026-10-08 and the kept state on its read-through, and nothing reads a type's identity across builds any more, so a type's hash covers its qualified name too, as the checker tells two declarations apart by name, and no member stands beside it; a renamed function still keeps its hash, since a function's own name is out of its body. Two words serve, defined once in the proposal: a definition's *hash* is the SHA-256 of its canonical form and nothing else, and its *identity* is what a reference names, a function's or a type's its hash, a binding's its qualified name with its hash.

## 3. The cookie and the build

**One build, and the cookie as MVP 3.0 has it.** Decided on 2026-10-08. The cookie is the digest of the protocol's version, `ern`'s version, OTP's version and the build's fingerprint, and two nodes of different builds never connect, as `nodes.md`'s section 6 argues; the first design's cookie without the build, with the runtime's surface named and versioned in its place, went with the two builds it let connect. A release of `ern` stops every node, as a new build does. What the hashes leave out agrees by the cookie: the runtime's functions and the standard library, which shipped code calls by name, and every foreign declaration, which a peer resolves by name and type.

**A bare node is given its build.** Proposed on 2026-10-08, with the rewritten proposal. A bare node has no load path to compute a fingerprint from, so its `ernest.conf` names the build, `build`, the fingerprint every node says on its standard error as it starts, pasted as a peer's public key is pasted; a wrong one is refused by the cookie as any build is, nothing is checked after the handshake, and no node learns its build from a peer. The alternative, a bare node of no build that takes the first connecting peer's, needs a check after the host's handshake, which `nodes.md`'s section 19 refuses, a frame the gateway holds every other behind, and a rule a reader would have to know, that the first peer wins; the paste is a line the operator's script writes between a stop and a start, beside the copy of the build it already makes. A node that both computes a fingerprint and is given one is refused at its start where they differ, so that a program node's configuration cannot lie about its build. A shell whose load path holds no program is a bare node with a prompt, and takes `build` the same way.

**A library's Erlang is where the library is.** To keep in mind, 2026-10-07. A library under `libs/` written in Ernest is hashed code: it crosses with a spawn, and a bare node receives it with the rest; a library's primitive in Erlang, `erl/json`'s for `libs/json`, is loaded from the installed tree on every machine that has `ern`, so a bare node has it; a library's shim over a module of its own that is not `ern`'s would be where that module is, and a bare node would lack it, which `NotLoaded` for a foreign declaration's module says. The standard library is `ern`'s, the same on every connected node by the cookie.

## 4. Messages, keys and bindings

**A message carries nothing, and a key its type's text.** As MVP 3.0 has them, `nodes.md`'s sections 7 and 14; set aside on 2026-10-08, the key that carried its type's identity, by which a find told a service at another version from one at its own. With one build a type's text says everything its hash would, and `OtherType` means what MVP 3.0 says, two services under one name with different types.

**Bindings, decided on 2026-10-08.** A node holds its bindings' values by identity and initializes nothing for a peer, since an initializer may spawn and the types do not tell a constant from a service. One rule for what a spawned function carries: a top-level binding it names is the peer's, resolved by identity and `NotLoaded` where the peer did not run it, and a value it is to carry from the spawner is bound to a local first, `let key = Counter.key`, and captured as any local is; so what crosses is read off the function's locals alone, and no binding's value travels by a rule a reader would have to guess from the example. The closure's list says which bindings a function reaches, so a peer answers `NotLoaded` for exactly those it did not run, where MVP 3.0's rule by module refused a function whose module held a binding the function never named (`nodes.md`, section 15); with one build what tells the nodes apart is which entry point each was started from. A service is one per node and key, a second offer faulting while it lives, so no second service is started unseen. A closure the peer cannot load fails the spawn with `Refused`, the peer's refusal with the peer's text, since none of the seven failures fit and a new constructor would break every match; `Refused` is that alone, since a connection the handshake refused is `Unreachable` to the dialer, the host telling it nothing of the reason.

## 5. A node's code, and the exchange at a spawn

**No module for each definition, and nothing unloaded.** Decided on 2026-10-07 and 2026-10-08. A module of the host for each definition cannot run on a node that lives long: OTP 29 lets a node load 65,536 module names in its life and exits at the limit, unloading gives none back, and fun and export entries live for ever. So the host's unit is the runtime's own grouping, invisible to the program and the protocol: what arrives in one exchange is one unit, the own build one unit per source module, and a table from hash to module and function is the code table; no module is named by a hash, which later lets names be reused from a pool, and a unit's functions are named by their position in it, so that the atom table, which the host never shrinks either, grows by the unit's name alone. Nothing is unloaded: unloading would free only the code bytes and not the names, a purge signals every process, and the VM does not track closures, so an unload would break a fun held in a value; a deploy restarts every node and bounds what it holds, and a node says when it nears a limit. The compiled code lives once, as loaded modules; a received definition's canonical form is kept beside it so that the node can ship it onward. A node with no `.erc` at all is a bare node, arriving for free: its entry process evaluates the standard library's bindings and waits, the node ending by termination. The memory of code is bounded, not reclaimed: the host's limits on module names, lambdas and atoms, with the node's warning at four fifths of any, and a node warned is stopped by its operator with `ern stop` and started again by its service manager. The host's embedded mode is not used, since a unit off the code path is loaded on demand in no mode, and the node loads otherwise as `ern run` does.

**No cache, and one occasion.** Set aside on 2026-10-08: the store on a node's disk of every form it received with the unit it compiled it into, by which a node restarted into a build it had been sent before a planned stop; it served the coordinator that told a node a root, the exchange's second occasion. A node holds its build directory on its disk and nothing else of code, and what its peers spawned on it in memory, so that a node restarted holds its build and is sent the rest again, which a spawn's exchange does for nothing more. A build directory is never changed under a running node, each build in a directory of its own, since a node reads its own forms from its `.erc` files when it ships them, and a copy over a running node would ship forms that fail their hashes.

**The exchange: the root first, the hashed form, quarantine and one load.** Decided on 2026-10-07. The root's hash goes first, so that the common case, a peer that has it, costs one round trip and no list; the list, the lacks and the code follow only where the peer lacks the root, as Unison does and as Git's negotiation over commits suggests ([`other_systems.md`](other_systems.md), section 6). The frame carries the hashed form, since by Nix's rule a content-addressed object verifies itself and a binary named by its source's hash can only be trusted; the peer compiles with its own back end. Arrivals wait in quarantine until the closure is complete and verified, then one atomic load, which Git's quarantine and Unison's temp entities both argue; what the peer said it has is pinned meanwhile, as Nix pins. A foreign declaration the peer lacks, and a binding it did not run, are `NotLoaded`, known from the list before any code moves. A faulty frame ends the connection, as in MVP 3.0.

**Risks.** Normalization, where an error costs most: two hashes for identical code or, worse, one hash for different code. And the time to compile when a node receives much code at once, a bare node's first spawn above all.

## 6. The shell

**A load on one node, decided 2026-10-07.** A client of one version and a service of another meet on one node across the shell's reload, as they would across nodes of different builds, which this milestone never connects. On one node there is no find. A client takes an address from a binding or from a value held since before the load, a local address is a pid alone, and constructors of one name in two versions are one term, so nothing at run time tells a message of the new version from one the old process matches, and `receive` would leave it in the mailbox for ever (§6.3). So the guard on one node is the checker: a type in the session's scope is its hash, a value keeps the hash it was checked under through a load, and a message of one version to an address of the other is a type error, whose diagnostic says which of the two is of the previous version. Two versions of a type are then two types in one scope, and claim 5 of the proposal holds on one node as one build holds it between nodes. The shell is where the rule shows, since `:reload` is the one load that puts two hashes of one name in one scope.

**No second version of a unit.** Decided on 2026-10-08. §11.2 ends a previous version's processes at a further reload with `Fault("its code was unloaded")`, which the host's limit of two versions of a module forces, and which claim 4, nothing a process runs is ever taken from it, and section 5's *nothing unloaded* forbid. The two agree once a load never gives a unit of the host's a second version: what one load brings to a node that holds the module's unit already is compiled into a unit of its own, as what arrives in one exchange is, from the forms its `.erc` or its source holds, and the table from hash to module and function points each version to its unit. The host's limit then never bites, and the fault goes from §11.2, and with it from §7.4 and §8.4, since nothing is unloaded anywhere, the shell's purge included: `:reload` is a load of the modules whose source changed, with nothing purged. A previous version's process runs on until it ends or is killed, reachable through the addresses of its version alone, its key offered again only once it has ended. The price is that a load counts against the host's lifetime limits of section 5, as an exchange does, which is what the four-fifths line is for. A load evaluates the closure's bindings in a fresh process at `Never` while the session waits, decided on 2026-10-08, since the soundness argument that an initializer at `Never` is safe rests on an empty mailbox, which a session's is not. A function typed at the shell has a hash as any definition has, and spawns on a peer with its code, which lifts MVP 3.0's refusals of `:load` and `:reload` in a shell that is a node (`nodes.md`, section 17).

**`Code` goes.** Proposed on 2026-10-08, with the rewritten proposal. The first design gave the standard library a module `Code` of two functions, `load`, which was `ern run`'s loading of a compiled module and its closure reached from Ernest, and `hashes`, a module's definitions as name and hash. `hashes` served `ern diff`, which went with the two builds it compared; `load` served the shell's `:load` and `:reload`, which are the session's today, reached from the shell's Ernest through a foreign declaration into the toolchain, and loading compiled code is what the host alone does, so no function of the standard library is missing for them (CLAUDE.md, *Shims*); and no program has anything to load by name, since it names every function it calls.

## 7. Termination told

**The planned stop and the kept state, set aside on the read-through of 2026-10-08.** Kept at first from the ordered rolling restart as the few sentences and the one primitive without which every program writes its own persistence, the four steps were read against what stop all and start all leaves them. Keys withdrawn existed so that a find during a rolling restart went to another of the key's peers rather than a node about to stop; with every peer stopping, and an offer ending with its process at the close, it buys nothing. Calls drained existed so that a rollout lost no request in flight before the next node was touched; with every caller stopping too, a call meets the close as it meets any loss, and the drain bought a courtesy to nobody at the price of a minute, a second termination and a walk of the table. Kept states written had value of its own, a service's total surviving `ern stop` and `ern run`; but it dragged in a loop the runtime owns, a member `migrate`, a state file with a format, `./.ernest/state/` for a program that is no node, and the identity of types by their shape, which after the trimming served the file and nothing else: five concepts for writing a value at the stop and reading it at the start, which every Erlang program does for itself with a file and an Ernest program does with `Fs` and `Json` (principle 5). What a program lacked was smaller: it could not act at its termination at all, since the node ended at once.

**One subscription, in the program's own type.** What a reader who knows Erlang expects at shutdown is OTP's `terminate/2`: each process is told, gets a bounded chance to clean up, and the system then ends (principle 1). Ernest gives it the shape `monitor`, `Clock.alarm` and `Process.faults` already have, a function from the message to the caller's mailbox type, delivered to the caller (E.0 shape rule 8): `Os.terminating(wrap)` subscribes the process, and at the end the runtime delivers `wrap(reply)`, which the process handles in its own `receive`, between two of its steps, writing what it keeps however it likes; it answers, and the program ends once every subscriber has answered or ended. Nothing is required of any mailbox: a process that did not subscribe gets nothing, and the one that did names the constructor itself, a sibling of §6.10's `Upgrade` in its type, which is the opposite of OTP's system messages, a protocol every `gen_server` must take and the behaviour handles unseen (principle 3); of OTP's `sys` requests, `change_code` is §6.10's `Upgrade`, which needs no suspend and resume since a tail call on a message handled in order has nothing run between the message and the switch, `get_state` and `replace_state` are the program's own requests, since the state is the loop's arguments and the runtime hides none, `get_status` is `Process.info`, and the debug set is the shell's. The reply is what makes the wait exact: the end waits as long as the writing takes and not a second more, a subscriber that ends without answering holds nothing up since the runtime watches it as it watches a callee, and no bound of the runtime's is needed, a second termination, the interrupt and the service manager's own patience being the bounds, each the operator's act or setting. The function is `Os`'s, since termination is the host's signal and `Os.exit` is already there; the constructor in the report's example is `Terminating`, present participle, since nothing has ended when it arrives and the process answers when it may, where style.md's past tense is for an event that has happened. The program's own end tells the subscribers too, the entry process returning or `Os.exit`, as OTP's `init:stop` runs `terminate/2` where `halt` does not, so that a service saves whichever way the program ends on purpose; the interrupt and a second termination are the quick ends, as today.

**Persistence is the program's.** A changed shape of what a program keeps is its own reading code, parsing the old file into the new value, with a version field where the program wants one: roughly the ten lines a `migrate` would have been, with no new concept and nothing invisible, and the way back is the program's too, where it wants one. The guide teaches a service that keeps its state as a process that subscribes, writes with `Json` and reads at its start. With the kept state went the type's identity by its shape, so a type's hash covers its name (section 2).

**The refusal.** Decided on 2026-10-08. A supervised process's restart runs the function the child was spawned with, so an upgrade in place of one vanished at its first fault in the supervisor experiment, and `Supervisor.child`'s function run again inside the child made the group count a fault that had not happened, since the inner function read the outer child's start cause. An operation by which a child replaces the function its restart runs was decided and withdrawn the same day with the change of logic in place ([`set_aside/deploy.md`](set_aside/deploy.md), section 15); what remains is to refuse the call, `Fault("a process runs one child function")`, the smaller of the two answers, since nothing of the deploy needs the other.
