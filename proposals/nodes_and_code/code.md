Status: the reasons for code and for termination told as [`mvp3.1.md`](mvp3.1.md) designs them, written on 2026-10-08 with the rewritten proposal and rewritten twice on its read-through the same day, when the kept state gave way to a program told of its end and the hash scheme to the module as the grain; in the order of the proposal's section 6, and kept in sync with the latest proposal that touches code; nothing here is normative, and the proposal states what this argues. The reasons for the first design, code by its hash, are [`set_aside/code.md`](set_aside/code.md), kept whole as the record beside the proposal it argued for, and its part two is the record of the thinking for a running process that takes new code in place, which stays out; the reasons for the kept state's first design, with the deploy around it, are [`set_aside/deploy.md`](set_aside/deploy.md). The reasons for nodes are [`nodes.md`](nodes.md)'s, the floor in its section 6, the spawn's digests in 13, the key's in 14, the bindings in 15, the shell in 17 and the end that tells its subscribers in 4; what other systems do is [`other_systems.md`](other_systems.md), sections 6 and 7.

## 1. The aim

MVP 3.0 holds every node to one build, proven whole at the handshake, which made the milestone simple and made every change a stop of all. MVP 3.1 asks what the floor beneath a build really is, so that a node may run any build above it, and answers with the least that must agree and the coarsest grain that tells the rest apart. What must agree is the host's major release, since the runtime calls OTP by name and compiled code is tied to its emulator; `ern`'s release, since compiled code calls the runtime's functions and the standard library by name, and nothing hashes that surface; and the protocol's version, what the frames mean. Above that a build is each node's own, and whether two nodes hold the same code is asked of the piece in question at the moment it matters: a spawn's function, with the modules it depends on and the bindings it names; a find's type, with the modules its definition reaches. Decided with the user on the read-through of 2026-10-08.

**The four steps.** Loading new code was four steps, of which MVP 3.0 is the first. On 2026-10-08 step D was set aside with the orchestration, and on the read-through step C with the hash scheme, leaving step B, which `code.md`'s first design had written down and never weighed, with two additions that have nothing to do with code: a program told of its end, and the `Standing` library.

| Step | What it gives | Where |
|---|---|---|
| A | one build on every node, and a deploy that stops them all | MVP 3.0, built |
| B | nodes of different builds connect; a spawn runs only where the peer holds the function's module and its closure unchanged, and a find answers only where the key's type is unchanged; no code crosses but a shell's | MVP 3.1, `mvp3.1.md` |
| C | a hash for each definition; code crosses by one exchange, at a spawn | set aside, [`set_aside/builds_side_by_side.md`](set_aside/builds_side_by_side.md) |
| D | a running system takes new code, as an ordered rolling restart | set aside, [`set_aside/ordered_rolling_restart.md`](set_aside/ordered_rolling_restart.md) |

What went, and why: a coordinator, a plan from the hashes, lockstep, `ern deploy`, `ern diff`, `ern status` and `ern state` order a rollout across machines, which Erlang leaves to release tooling and Go to the platform, so a reader who knows Erlang expects it outside the runtime (principle 1), and they add eight or nine concepts for a system of a few nodes listed by hand (principle 5). The definition's hash told two builds apart line by line, which pays only where the orchestration needs it; without that, it was a canonical form, an exchange and a code table in payment for nothing anyone asked, and the module, the host's own unit of code, tells builds apart for free. Replacing a module under running processes, as Erlang's `code` module does, is none of the steps: it changes code with nothing to check its types against.

## 2. The floor

**One release of `ern` on one major release of OTP.** Decided with the user on the read-through of 2026-10-08. The cookie digests the protocol's version, `ern`'s version and OTP's major release, `erlang:system_info(otp_release)`, in place of MVP 3.0's full version string of OTP and checksum of the build. The major is where OTP sets its own promise: the term format, the distribution protocol and a compiled module hold across the patch and minor releases of one major, so a floor set there is set where the host sets it, and a patch of the host rolls node by node with no help from Ernest; the full string split `29.0` from `29.0.1`, which would have split a system over a host patch. `ern`'s version stands for the runtime's surface, the standard library and the protocol, since all three ship with it, so two releases of `ern` never connect and a release of `ern` is a stop of all, as MVP 3.0 had it; the first design's named and versioned surface, by which two releases with one surface connected, went with the orchestration it served. The one risk is named as a limit: within a major the compiler may learn an instruction an earlier patch's emulator lacks, which OTP does not promise against, and under this design the only compiled code that crosses is a shell's modules, so the case is a shell on a newer patch spawning on a peer on an older one, answered `Refused` with the host's text, not a crash; a cookie that refused it at the handshake would do so by splitting every system at every patch, the worse trade. The report's sentence is written without the word "cluster", which `nodes.md` keeps for what Ernest refuses; "its peers" and "the nodes it lists" are the report's words.

**Nothing else is checked after the handshake.** A plain message goes straight into a mailbox, so a check made after the connection is open would race it (`nodes.md`, section 6); the floor is all the handshake proves, and everything above it is proven per operation, below, before any address crosses.

## 3. The module as the grain

**The host's digest, and nothing finer.** Decided with the user on the read-through of 2026-10-08. Whether two nodes hold the same code is asked of a module, and answered by the host's digest of its compiled code, `beam_lib:md5`, which leaves out documentation, line numbers and attributes, so that a fixed typo in a doc block changes no module; it is the list MVP 3.0's fingerprint already computes, kept now as a table on each node instead of digested into the cookie. The module is Erlang's own unit of code, what `code:load_binary` loads and `code:module_md5` names, so a reader who knows Erlang meets nothing new (principle 1); it costs nothing, since the digest exists; and it is coarse by exactly one thing, that an edit to any function in a module changes the module, so every type the module declares is another type to a find and every function in it another function to a spawn. The finer grain, a definition's hash over a canonical typed tree, told a renamed function from a changed one and a protocol from a helper beside it; that precision pays where two builds run side by side for long under an orchestrated rollout, and costs a canonical form that must be frozen, an exchange and a code table, which are the complicated half. With the module, the discipline the first design's section 7.4 already asked for does the work: a protocol's types in a module of their own, small and seldom edited, which the guide teaches with a number once programs are written on it. A version a program declares on a protocol, the fourth grain weighed, was refused since it lets a human say unchanged of a change, which a digest cannot.

**A spawn compares the closure.** The spawn frame carries, with the function's module and place as in MVP 3.0, the digests of every module in the function's module's closure, its dependencies transitively from the `.erc`, in name order; the peer compares them against its table and answers `NotLoaded` naming the first module it lacks or holds with another digest. The whole closure, not the module alone, since a function's module may be unchanged while a module it calls into changed, and the function would then run the wrong code or none; and the closure rather than the whole build, since that is MVP 3.0's rule again. The frame grows by sixteen bytes a module, measured when built.

**A find compares what the type reaches.** A key holds, with its name and its type's text as MVP 3.0 has it, the digests of the modules the type's definition reaches, through every field type to the modules that declare them, computed by the compiler where `Peer.key` is written; a find compares them against the peer's table and answers `OtherType` where one differs or is missing. The reach and not the declaring module alone, since a value of the type carries values of every type its fields name, and a changed one among them would cross unseen; the text stays beside the digests, since the digests say that the modules agree and the text says which type among them is meant. Claim 3 of the proposal, that no message of one version is read as another's, is MVP 3.0's induction with the digests in the handshake's place: every remote address came from a find, a spawn or an agreed message, and each of the three compared, or inherited, the digests of every module a value through that address can reach. The compiler refuses a key whose type reaches a module typed at the shell, since no two sessions hold one module, and a key of such a type could be found by nobody.

## 4. Bindings, and a node that runs no program

**Bindings, decided on 2026-10-08 and kept.** A node holds its bindings' values and initializes nothing for a peer, since an initializer may spawn and the types do not tell a constant from a service. One rule for what a spawned function carries: a top-level binding it names is the peer's, `NotLoaded` where the peer did not run it, and a value it is to carry from the spawner is bound to a local first, `let key = Counter.key`, and captured as any local is; so what crosses is read off the function's locals alone, and no binding's value travels by a rule a reader would have to guess from the example. The exact rule, by binding rather than by module, needs to know which bindings a function reaches through the calls it makes; the first design read that off the closure's list its exchange sent, and this one has the compiler write each definition's reach into the `.erc`, the cost `nodes.md`'s section 15 said the hashes would spare, now the cheap answer since the peer holds the `.erc` and nothing crosses for it. A service is one per node and key, a second offer faulting while it lives, so no second service is started unseen.

**A node that runs no program is a node of its load path.** Decided with the user on the read-through of 2026-10-08, the third of three answers. The first design's bare node held nothing of a program's and was sent code by its peers, which needed a cookie without the build and, once the build stayed in the cookie, a fingerprint pasted into the node's configuration, a line every node printed at its start, and a refusal where a node's two fingerprints differed; the second answer, a node that adopts the first connecting peer's build, needed a check after the handshake, refused in section 2. The third is MVP 3.0's node with no `main`: `ern run --config-dir dir --load-path dir...` with no `.erc` loads what its load path holds, as a program's build is loaded whole, and waits. The deploy's script already copies the build to every machine and starts every node, so the worker is one more machine in that loop, and a worker on a stale build answers `NotLoaded` naming the module, which the operator reads as any other. The rule by binding is what makes such a node useful at all: it ran no bindings, so under MVP 3.0's rule by module nothing could ever be spawned on it, and under the rule by binding anything that names none, or captures what it needs, spawns there.

## 5. The shell's modules cross

**The one place code crosses, and as compiled modules.** Decided with the user on the read-through of 2026-10-08. A session's inputs are modules in no build, so a spawn from a shell of a function it typed finds no peer that holds the module, and the shell as a node, which MVP 3.0 refused for that reason, needs code to cross exactly there. It crosses compiled: a spawn from a shell carries, in one frame beside the spawn's, the compiled code of every module of the session's in the function's closure, with each one's reach, and the peer loads what it lacks by `code:load_binary` before the process starts. The first design refused a compiled binary in a frame by Nix's rule, that a content-addressed form verifies itself where a binary can only be trusted; but the rule is for content nobody vouches for, and a listed peer is trusted completely, by MVP 3.0's bounds, to spawn anything on a node already, so a module it compiled is no more than it may do by name. The session's modules are named on the host after the session as well as the input, so that two sessions' seventh inputs never share a name on a peer, and a module the peer holds already with another digest, or one the host refuses to load, fails the spawn with `Refused` naming the module, nothing loaded; a module of the build's is never carried, and is compared by its digest as any.

**No second version of a module.** Decided on 2026-10-08 and kept with a cheaper means. §11.2 ends a previous version's processes at a further reload with `Fault("its code was unloaded")`, which the host's limit of two versions of a module forces, and which claim 4, nothing a process runs is ever taken from it, forbids. The first design compiled each load into a unit of its own under the code table; this one has `:reload` compile the module again into a fresh name of the session's own and bind the module's name to it, so that no module of the host's takes a second version, the host's limit never bites, and the fault goes from §11.2, and with it from §7.4 and §8.4, since nothing is unloaded anywhere. A previous version's process runs on until it ends or is killed, reachable through the addresses of its version alone, its key offered again only once it has ended. The price is a module name of the host's for each load and reload, which section 7's limits bound and the four-fifths line watches.

**A load on one node, decided 2026-10-07 and kept.** A client of one version and a service of another meet on one node across the shell's reload. There is no find; a client takes an address from a binding or from a value held since before the load, a local address is a pid alone, and constructors of one name in two versions are one term, so nothing at run time tells a message of the new version from one the old process matches, and `receive` would leave it in the mailbox for ever (§6.3). So the guard on one node is the checker: a type in the session carries the load it came from, a value keeps the type it was checked under through a reload, and a message of one version to an address of the other is a type error whose diagnostic says which of the two is of the previous version. A load evaluates the module's bindings in a fresh process at `Never` while the session waits, since the soundness argument that an initializer at `Never` is safe rests on an empty mailbox, which a session's is not.

**`Code` goes.** Decided on 2026-10-08. The first design gave the standard library a module `Code` of two functions, `load`, which was `ern run`'s loading of a compiled module and its closure reached from Ernest, and `hashes`. `hashes` served `ern diff`, which went with the orchestration; `load` served the shell's `:load` and `:reload`, which are the session's today, reached from the shell's Ernest through a foreign declaration into the toolchain, and loading compiled code is what the host alone does, so no function of the standard library is missing for them (CLAUDE.md, *Shims*); and no program has anything to load by name.

## 6. Termination told

**The planned stop and the kept state, set aside on the read-through of 2026-10-08.** Kept at first from the ordered rolling restart as the few sentences and the one primitive without which every program writes its own persistence, the four steps were read against what stop all and start all leaves them. Keys withdrawn existed so that a find during a rolling restart went to another of the key's peers rather than a node about to stop; with every peer stopping, and an offer ending with its process at the close, it buys nothing. Calls drained existed so that a rollout lost no request in flight before the next node was touched; with every caller stopping too, a call meets the close as it meets any loss, and the drain bought a courtesy to nobody at the price of a minute, a second termination and a walk of the table. Kept states written had value of its own, a service's total surviving `ern stop` and `ern run`; but it dragged in a loop the runtime owns, a member `migrate`, a state file with a format, `./.ernest/state/` for a program that is no node, and the identity of types by their shape, which after the trimming served the file and nothing else: five concepts for writing a value at the stop and reading it at the start, which every Erlang program does for itself with a file and an Ernest program does with `Fs` and `Json` (principle 5). What a program lacked was smaller: it could not act at its termination at all, since the node ended at once.

**One subscription, in the program's own type.** What a reader who knows Erlang expects at shutdown is OTP's `terminate/2`: each process is told, gets a bounded chance to clean up, and the system then ends (principle 1). Ernest gives it the shape `monitor`, `Clock.alarm` and `Process.faults` already have, a function from the message to the caller's mailbox type, delivered to the caller (E.0 shape rule 8): `Os.terminating(wrap)` subscribes the process, and at the end the runtime delivers `wrap(reply)`, which the process handles in its own `receive`, between two of its steps, writing what it keeps however it likes; it answers, and the program ends once every subscriber has answered or ended. Nothing is required of any mailbox: a process that did not subscribe gets nothing, and the one that did names the constructor itself, a sibling of §6.10's `Upgrade` in its type, which is the opposite of OTP's system messages, a protocol every `gen_server` must take and the behaviour handles unseen (principle 3); of OTP's `sys` requests, `change_code` is §6.10's `Upgrade`, which needs no suspend and resume since a tail call on a message handled in order has nothing run between the message and the switch, `get_state` and `replace_state` are the program's own requests, since the state is the loop's arguments and the runtime hides none, `get_status` is `Process.info`, and the debug set is the shell's. The reply is what makes the wait exact: the end waits as long as the writing takes and not a second more, a subscriber that ends without answering holds nothing up since the runtime watches it as it watches a callee, and no bound of the runtime's is needed, a second termination, the interrupt and the service manager's own patience being the bounds, each the operator's act or setting. The function is `Os`'s, since termination is the host's signal and `Os.exit` is already there; the constructor in the report's example is `Terminating`, present participle, since nothing has ended when it arrives and the process answers when it may, where style.md's past tense is for an event that has happened. The program's own end tells the subscribers too, the entry process returning or `Os.exit`, as OTP's `init:stop` runs `terminate/2` where `halt` does not, so that a service saves whichever way the program ends on purpose; the interrupt and a second termination are the quick ends, as today.

**Persistence is the program's.** A changed shape of what a program keeps is its own reading code, parsing the old file into the new value, with a version field where the program wants one: roughly the ten lines a `migrate` would have been, with no new concept and nothing invisible, and the way back is the program's too, where it wants one. The guide teaches a service that keeps its state as a process that subscribes, writes with `Json` and reads at its start.

**The refusal.** Decided on 2026-10-08. A supervised process's restart runs the function the child was spawned with, so an upgrade in place of one vanished at its first fault in the supervisor experiment, and `Supervisor.child`'s function run again inside the child made the group count a fault that had not happened, since the inner function read the outer child's start cause. An operation by which a child replaces the function its restart runs was decided and withdrawn the same day with the change of logic in place ([`set_aside/deploy.md`](set_aside/deploy.md), section 15); what remains is to refuse the call, `Fault("a process runs one child function")`, the smaller of the two answers, since nothing of the deploy needs the other.
