# Ernest: Code, the reasons

Status: the reasons for code and for termination told as [`mvp3.1.md`](mvp3.1.md), identity, and [`mvp3.2.md`](mvp3.2.md), code with a spawn, design them, written on 2026-10-08, split into the two on 2026-10-09, and kept in sync with them. Nothing here is normative; the proposal states what this argues. Each paragraph is one decision: the decision first, then its reason, then what was set aside for it. The path the design took that day is the log's once the proposal is built. The reasons for the first design, code by its hash with nodes of different builds working together, are [`set_aside/code.md`](set_aside/code.md), and its part two is the thinking for a running process that takes new code in place, which stays out; the reasons for the kept state and the deploy around it are [`set_aside/deploy.md`](set_aside/deploy.md). The reasons for nodes are [`nodes.md`](nodes.md)'s, the end that tells its subscribers in its section 4 and the standing address in its section 14. What other systems do is [`other_systems.md`](other_systems.md), sections 6 and 7.

## 1. The aim

Unison names every definition by a hash of its content. Two versions of a definition are then two things and never conflict, a rename costs nothing, and code can move between machines because its identity is exact. Ernest takes the idea for one use: code that crosses with a spawn. Two things want it, and neither is a deploy. The shell as a node spawns on a peer what was typed at it, which MVP 3.0 answers `NotLoaded`, since no peer has the shell's module. The bare node is a worker pool the program fills with code, a machine with `ern` on it and nothing else. The same hashes make `NotLoaded` exact, by binding rather than by module, and let nodes of different builds connect, since a key and a spawn say by hash what agrees.

**The four steps.** Loading new code was four steps. MVP 3.0 built the first. MVP 3.1 builds the second and the hash of the third; MVP 3.2 the rest of the third, the crossing. The fourth is set aside. The split, decided on 2026-10-09, puts identity before crossing: everything in the crossing needs the hash, nothing in the hash needs the crossing, and the hash alone already connects nodes of different builds.

| Step | What it gives | Where |
|---|---|---|
| A | one build on every node, and a deploy that stops them all | MVP 3.0, built |
| B | nodes of different builds connect, on one floor | MVP 3.1, `mvp3.1.md` |
| C | a hash for each definition, and two versions side by side on a node; then code crosses by one exchange, at a spawn | the hash MVP 3.1, `mvp3.1.md`; the crossing MVP 3.2, `mvp3.2.md` |
| D | a running system takes new code, as an ordered rolling restart | set aside, [`set_aside/ordered_rolling_restart.md`](set_aside/ordered_rolling_restart.md) |

Step D went because a rollout across machines is what Erlang leaves to release tooling and Go to the platform, so a reader who knows Erlang expects it outside the runtime (principle 1), and because its coordinator, plan, lockstep and four commands added eight or nine concepts for a system of a few nodes listed by hand (principle 5). A deploy is stop all and start all, by `ern stop` and `ern run`, ordered by an operator's script, as a balancer is a library and not a feature. Replacing a module under running processes, as Erlang's `code` module does, is none of the steps: it changes code with nothing to check its types against.

## 2. The hash

**The canonical form is the typed tree.** The hash is over the typed tree after checking, not an intermediate form. The toolchain has no other form of a program, and one kept only to hash would be a second representation of every program. `ern_interface:hash/1` already canonicalizes an interface the same way. Whatever runs before hashing, elaboration and how supplies are filled, is part of the form, so the scheme's version is mixed into every hash and changes with any change to it. Names stay in the `.ern` files: a build resolves every name afresh and writes the table from name to hash, derived and never edited.

**A reference is a hash, and a function's own name is out.** A reference is the hash of what it names and nothing else, so that a rename changes no dependent's hash, which is what hashing is for. A function's own name and positions are out, as in Unison: the spawn site travels in the spawn frame, and a trace names a hash by this build's name for it. A foreign declaration has no hash, so it is referred to by name and type, and each node resolves it for itself.

**A binding's identity holds its name.** A function's hash leaves out its own name, so `let a = spawn(worker)` and `let b = spawn(worker)` would be one value on a node. A binding is a thing that exists, as a service is, so its identity is its qualified name with its hash; a type is a shape and a function a body, and neither needs its name for that.

**A type's hash covers its name.** The checker tells two declarations apart by name, and a type renamed is another type to a reader. The first design hashed a type by its shape alone, so that a kept state's file matched the old shape under a new name; the kept state went, and nothing asks for less than the name.

**A group is one hash.** A hash cannot contain itself, so a mutually recursive group, the strongly connected component, is hashed as one, its members by position in source order. Source order and not an order by hash, since an order by hash ties where two members differ only in which other member they name.

**The typed tree is what crosses.** The peer runs its own back end over it, the emitter and the host's compiler, and links each reference through its table first. The emitter's own output, the host's forms with references by hash and variables numbered, was weighed as the thing to ship, so that a peer runs the host's compiler alone, `compile:forms`. It would spare the peer the emitter, milliseconds a module, and cost a second canonical form, made deterministic and name-free beside the tree that already is, and a second thing to verify against a hash. The emitter's time is a small share of the host's compile, which runs either way; a first spawn too slow for a spawn's time would not be saved by the forms, and the spawn's time and `Timeout` are the answer to it.

## 3. The cookie and the build

**The cookie holds the floor, and not the build.** The floor is one release of `ern` on one major release of OTP. The major is where OTP sets its own promise: the term format, the distribution protocol and a compiled module hold across one major's patch and minor releases, so a patch of the host rolls node by node. `ern`'s version stands for what the hashes leave out, the runtime's functions, the standard library and every foreign declaration over a module of OTP's or of `ern`'s, which shipped code calls by name. With the build out, nodes of different builds connect, and the hashes, computed anyway, say at a spawn and at a find what agrees. A release of `ern` is a stop of all, as a new build was under MVP 3.0; a new build is not. Two cookies were set aside for this one: the first design's, without the build but with the runtime's surface named and versioned in its place, and MVP 3.0's, with the build's fingerprint, under which nodes of different builds never connected and a bare node had to be given its build. `nodes.md`'s section 6 holds the rest.

**A bare node is of no build.** With the build out of the cookie there is nothing to give it. It is accepted on the floor, holds no definition until a spawn brings one, and runs whatever closures its peers spawn on it, of whichever builds. A fingerprint pasted into its `ernest.conf`, and a build learned from its first peer, served the cookie that kept the build and went with it.

**A library's Erlang is where the library is.** A library under `libs/` written in Ernest is hashed code: it crosses with a spawn, and a bare node receives it with the rest. A library's primitive in Erlang, `erl/json`'s for `libs/json`, is in the installed tree on every machine that has `ern`, so a bare node has it. A library's shim over a module of its own would be where that module is, and a bare node would lack it, which `NotLoaded` for a foreign declaration's module says.

## 4. Messages, keys and bindings

**A message carries nothing.** Every remote address came from a find or a spawn, where the hashes were compared, or inside a message whose type was agreed by one of the two, so nothing is checked on arrival (`nodes.md`, section 7).

**A key carries its type's hash.** Builds differ, so a name no longer says what a type is. The key carries the hash beside its text, and a find answers `OtherType` where the holder's differs: a service at another version. The key by its text alone served one build on every node (`nodes.md`, section 14).

**A binding is the peer's, and a value is captured.** A node initializes nothing for a peer, since an initializer may spawn and the types do not tell a constant from a service. So a top-level binding a spawned function names is the peer's, `NotLoaded` where the peer did not run it, and a value the function is to carry is bound to a local first and captured as any local is. What crosses is then read off the function's locals alone, and no binding's value travels by a rule a reader would have to guess. The closure's list says which bindings a function reaches, so the peer answers `NotLoaded` for exactly those, where MVP 3.0's rule by module refused a function whose module held a binding the function never named (`nodes.md`, section 15).

**`Refused` is the peer's refusal of a closure, and that alone.** None of the seven failures fit a closure the peer cannot load, and a new constructor would break every match. A connection the handshake refused stays `Unreachable`, since the host tells the dialer nothing of the reason.

## 5. A node's code, and the exchange at a spawn

**No module for each definition.** OTP 29 lets a node load 65,536 module names in its life and exits at the limit, and fun and export entries live for ever. So the host's unit is the runtime's own grouping, invisible to the program and the protocol: what arrives in one exchange is one unit, the own build one unit per source module, and the code table maps each hash to its unit and function. No unit is named by a hash, so names come from a pool and are reused. A unit's functions are named by their position in it, so the atom table, which the host never shrinks, grows by the unit's name alone. A module per definition was also weighed as the simplest shape and set aside for its cost: every call between two Ernest functions a cross-module call, on every program, nodes or not. The host's embedded mode is not used: a unit off the code path is loaded on demand in no mode, and the node loads otherwise as `ern run` does.

**A unit is made one way.** The own build's units are made by the same back end, from the same forms, through the same table as a unit that arrives. A build made otherwise would be a second way of making a module.

**A unit no process runs is let go.** References are by hash, so a fix to a definition many call makes every caller a new definition, up to the roots: a node that took three fixes to a leaf would hold four programs. With nothing unloaded, memory grew with every fix. Unison has the same cascade and feels nothing of it, since its codebase is on disk and a run loads what it reaches. The host gives the same with `erlang:check_process_code`, which says whether a process executes a module or holds a function of it, on its heap or in its mailbox, the check behind the host's own `soft_purge`. A unit no process runs or holds is unloaded when the node nears a limit, oldest first, its table entries with it, and comes again when a spawn asks for one of its definitions; not at every arrival, since a worker whose tasks end and are spawned again would then ship its code at every spawn. The build's own units never go, since the program is what the node is for. A purged name is reloaded by the host, so the name returns to the pool, which answers the lifetime limit on module names. Memory of code is then one program's worth once the old processes have been upgraded or have ended: Erlang's old and current code, generalised to as many versions as still run. The first design unloaded nothing, and bounded a node's life by the host's limits and a warning; that was set aside with the cascade.

**A table holds no function.** The host's check does not look into a table, and a table lives with its owner, not with the code's processes. So `Ets.Table(k, v)` is refused where `k` or `v` holds a function type, by §3.11's bound check's first case: one line in the checker and nothing at run time, and every holder of a function is a process the host sees. A scan of every table before a let-go is not sound, since a process may put such a function after the scan and before the unload. A count per table, kept at each `put`, is sound, and costs a walk of the value on a path that today costs the host's insert alone. What the rule costs a program is a dispatch table, handlers kept by key; such a program keeps its handlers in a process's state, or its data in the table and its dispatch in code. A table is for sharing and size, not for code.

**A caller crosses whole, and deltas wait.** The callers a fix renames differ from what the peer holds in their references alone, so the sender could ship, for each, the held hash and the references that changed, and the peer make the form. Deferred on 2026-10-09: the let-go answers the cascade's cost in memory, and what the delta saves is the wire, one program's worth of canonical forms per node per fix, a few hundred kilobytes, at the price of a second kind of code frame, a source name in the protocol as a hint, and a second way a form is made and verified. The compile of the callers on the peer is the same either way. What would bring it back is the measurement `mvp3.2.md`'s section 11 names.

**Nothing on disk but the build.** A node holds its build directory on its disk, and what its peers spawned on it in memory; a node restarted holds its build and is sent the rest again, which an exchange does for nothing more. A build directory is never changed under a running node, each build in a directory of its own, since a node reads its own forms from its `.erc` files when it ships them, and a copy over a running node would ship forms that fail their hashes. A store on disk of every form received served the coordinator of the rolling restart, and went with it.

**The exchange: the root first, the hashed form, quarantine and one load.** The root's hash goes first, so that the common case, a peer that has it, costs one round trip and no list; the list, the lacks and the code follow only where the peer lacks the root, as Unison does and as Git's negotiation over commits suggests ([`other_systems.md`](other_systems.md), section 6). The frame carries the hashed form, since by Nix's rule a content-addressed object verifies itself, and a binary named by its source's hash can only be trusted. Arrivals wait in quarantine until the closure is complete and verified, then one atomic load, as Git's quarantine and Unison's temp entities both argue; what the peer said it has is pinned meanwhile, as Nix pins. A foreign declaration the peer lacks, and a binding it did not run, are `NotLoaded`, known from the list before any code moves. A faulty frame ends the connection, as in MVP 3.0.

**`Code` goes.** The first design gave the standard library a module `Code`: `load`, which was `ern run`'s loading of a compiled module reached from Ernest, and `hashes`, a module's definitions as name and hash. `hashes` served `ern diff`, which went. `load` served the shell's `:load` and `:reload`, which are the session's, reached from the shell's Ernest through a foreign declaration into the toolchain; loading compiled code is what the host alone does, so no function of the standard library is missing for them (CLAUDE.md, *Shims*). No program has anything to load by name, since it names every function it calls.

**Risks.** Normalization, where an error costs most: two hashes for identical code or, worse, one hash for different code. The time to compile when a node receives much code at once, a bare node's first spawn and the callers of a fix above all. And the let-go's reliance on the host's check seeing every holder of a function, which the table rule secures: a new place a function could rest outside a process would have to be refused the same way.

## 6. The shell

**The checker tells the versions apart on one node.** A client of one version and a service of another meet on one node across the shell's reload, as they meet across nodes of different builds. On one node there is no find to compare hashes at. A local address is a pid alone, and constructors of one name in two versions are one term, so nothing at run time tells a message of the new version from one the old process matches, and `receive` would leave it in the mailbox for ever (§6.3). So the guard is the checker: a type in the session's scope is its hash, a value keeps the hash it was checked under through a load, and a message of one version to an address of the other is a type error, whose diagnostic says which of the two is of the previous version. Two versions of a type are then two types in one scope, and claim 5 of the proposal holds on one node as the hashes hold it between nodes.

**No second version of a unit.** §11.2 ends a previous version's processes at a further reload with `Fault("its code was unloaded")`, which the host's limit of two versions of a module forced, and which claim 4, that nothing a process runs is ever taken from it, forbids. The two agree once a load never gives a unit of the host's a second version: what one load brings to a node that already holds the module's unit becomes a unit of its own, and the table points each version to its unit. The host's limit then never bites, and the fault goes from §11.2, §7.4 and §8.4. A previous version's process runs on until it ends or is killed, reachable through the addresses of its version alone, its key offered again only once it has ended. A load evaluates the closure's bindings in a fresh process at `Never` while the session waits, since the argument that an initializer at `Never` is safe rests on an empty mailbox, which a session's is not. A function typed at the shell has a hash as any definition has, and spawns on a peer with its code, which lifts MVP 3.0's refusals of `:load` and `:reload` in a shell that is a node (`nodes.md`, section 17).

## 7. Termination told

**A program is told, and nothing is kept for it.** The planned stop's four steps were read against what stop all and start all leaves them. Keys withdrawn existed so that a find during a rolling restart went to another of the key's peers; with every peer stopping, and an offer ending with its process at the close, it buys nothing. Calls drained existed so that a rollout lost no request before the next node was touched; with every caller stopping too, a call meets the close as it meets any loss, and the drain bought a courtesy to nobody at the price of a minute, a second termination and a walk of the table. A kept state written had value, a service's total surviving `ern stop` and `ern run`; but it dragged in a loop the runtime owns, a member `migrate`, a state file with a format, `./.ernest/state/` for a program that is no node, and the identity of types by their shape: five concepts for writing a value at the stop and reading it at the start, which every Erlang program does for itself with a file and an Ernest program does with `Fs` and `Json` (principle 5). What a program lacked was smaller: it could not act at its termination at all, since the node ended at once.

**One subscription, in the program's own type.** What a reader who knows Erlang expects at shutdown is OTP's `terminate/2`: each process is told, gets a bounded chance to clean up, and the system then ends (principle 1). Ernest gives it the shape `monitor`, `Clock.alarm` and `Process.faults` already have: a function from the message to the caller's mailbox type, delivered to the caller (E.0 shape rule 8). Nothing is required of any mailbox. A process that did not subscribe gets nothing, and one that did names the constructor itself, a sibling of §6.10's `Upgrade` in its type; OTP's system messages are the opposite, a protocol every `gen_server` must take and the behaviour handles unseen (principle 3). Of OTP's `sys` requests, `change_code` is §6.10's `Upgrade`, which needs no suspend and resume since a tail call on a message handled in order has nothing run between the message and the switch; `get_state` and `replace_state` are the program's own requests, since the state is the loop's arguments and the runtime hides none; `get_status` is `Process.info`; and the debug set is the shell's. The reply makes the wait exact: the end waits as long as the writing takes and not a second more, a subscriber that ends without answering holds nothing up since the runtime watches it as it watches a callee, and no bound of the runtime's is needed, a second termination, the interrupt and the service manager's patience being the bounds, each the operator's act or setting. The function is `Os`'s, since termination is the host's signal and `Os.exit` is already there. The constructor in the example is `Terminating`, present participle, since nothing has ended when it arrives and the process answers when it may; style.md's past tense is for an event that has happened. The program's own end tells the subscribers too, the entry process returning or `Os.exit`, as OTP's `init:stop` runs `terminate/2` where `halt` does not, so that a service saves whichever way the program ends on purpose.

**Persistence is the program's.** A changed shape of what a program keeps is its own reading code, parsing the old file into the new value, with a version field where the program wants one: roughly the ten lines a `migrate` would have been, with no new concept and nothing invisible. The way back is the program's too, where it wants one. The guide teaches a service that keeps its state as a process that subscribes, writes with `Json` and reads at its start.

**The refusal.** A supervised process's restart runs the function the child was spawned with. In the supervisor experiment an upgrade in place of a child vanished at its first fault, and `Supervisor.child`'s function run again inside the child made the group count a fault that had not happened, since the inner function read the outer child's start cause. An operation by which a child replaces the function its restart runs was decided and withdrawn with the change of logic in place ([`set_aside/deploy.md`](set_aside/deploy.md), section 15). What remains is to refuse the call, `Fault("a process runs one child function")`, the smaller of the two answers, since nothing of the deploy needs the other.

## 8. Left out, with the reason

- *The rest of nodes of different builds: a type's identity by its shape, `ern diff`, a service offered at an old identity through a conversion or a forwarder, two builds for a changed protocol*: they exist so that an old node and a new one serve one protocol side by side during a rollout, which stop all and start all never needs; [`set_aside/builds_side_by_side.md`](set_aside/builds_side_by_side.md) is the design and [`set_aside/code.md`](set_aside/code.md) its reasons.
- *A deploy the runtime orders: a coordinator, a plan, lockstep, a node's restart inside its process, the `build` file, the cache, the way back, the generated test, `ern deploy`, `ern status`, `ern state`, `drain` and `coordinator`*: section 1; [`set_aside/ordered_rolling_restart.md`](set_aside/ordered_rolling_restart.md) and [`set_aside/deploy.md`](set_aside/deploy.md).
- *A state the runtime holds and writes, `kept`, `migrate` and a state file; the planned stop's keys withdrawn and calls drained*: section 7.
- *An upgrade in place, a change of protocol by translation, `become`, a rollback, the keeper*: [`set_aside/deploy.md`](set_aside/deploy.md)'s section 15 says what they would cost, and [`set_aside/code.md`](set_aside/code.md)'s part two is the record of the thinking.
- *`Code`, a module of the standard library*: section 5.
- *A bare node of a build, given it by its configuration or by its first peer*: section 3.
- *A module as the grain, compiled modules shipped whole under names that hold their digests*: a module per function was too slow and a module shipped whole too coarse, every type a module declares another type at a find when any function in it changed; the definition is the grain, and a unit is the runtime's grouping of definitions, invisible to the program.
- *A scan of tables, or a count per table, before a unit is let go*: section 5; the scan is unsound and the count a cost on every `put`.
- *Deltas on the wire*: section 5; the let-go answers the cascade, and the wire is the measurement's.
- *The emitter's forms as what crosses*: section 2.
- *A bound of the runtime's own on the end's wait*: section 7; a subscriber's answer is what it waits for.
- *A state moved to another of its key's peers, an election, a lease, a hot standby*: `nodes.md`, sections 4 and 14; one owner across a failure needs a lease in a store outside the nodes, a library's.
- *A compiled binary in a code frame*: section 5, the exchange; a content-addressed form verifies itself, and a binary can only be trusted.
- *A node that boots the platform over the network, and the key such a node receives*: a bare node has `ern` on its disk; the host's boot server has no TLS and checks only an address, and a diskless node would hand its identity to anyone on the network.
- *A project's name above a qualified name*: section 2; two codebases that agree on a type's name and definition agree on the type.
