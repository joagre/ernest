# Ernest: Code Update, the thinking for step D

Status: a thinking document, begun 2026-10-07, for step D of [`code.md`](code.md)'s section 1, *The four steps*, a running system that takes new code; nothing in it is decided, and no proposal is written from it yet. It starts from one recovery path and a matrix of the cases, and reads [`code.md`](code.md)'s part two, the thinking for one process that takes new code, against them; part two moves here when this document's shape is agreed, so that the subject has one owner. What other systems do is [`other_systems.md`](other_systems.md), section 7, read from the list section 6 once held. The reasons for code by its hash are `code.md`'s part one, and for nodes [`nodes.md`](nodes.md)'s.

## 1. The problem

**What MVP 3.1 leaves.** After MVP 3.1 a node holds versions of a definition side by side, a process keeps the code it was started with until it ends, a service is found by its key at whichever version it is, and a deploy is a rolling restart, node by node. That serves every process that can end and begin again without loss. It does not serve three kinds, and they are the ones a real system is made of: a service whose state lives in its loop's arguments and is worth keeping; a service that may not run twice on a node, because it holds a connection to a database, a listening socket, a file lock, a port or a table; and a process whose address, or whose connection, is what its clients hold on to, so that a successor at another address loses them.

**What the report has.** §6.10 is one process's mechanism: a message in its own type that carries the new loop, and a migration of its state by a function, switched by a tail call. It is right and it is not enough, since it says nothing of the system: who sends the message, in what order across a program, what becomes of the resources the process owns, of the clients that hold its address at the old protocol, of the messages in its mailbox at the switch, of its supervisor and of its restart function, of the other nodes, and of the way back when the new code is wrong. Those are the problem, and each is a fact the program, the tool or the runtime has to own.

**Erlang's answer, and why it is hell.** OTP upgrades a running system by an `appup` file for each application and a `relup` for the release, written by hand: which modules to load, which processes to suspend, which `code_change` to call with what `Extra` term, in what order, and from where there is no return. `code_change` is a function beside the process's `init`, written only for the upgrade, given the old state as an untyped term, and run only when a release is upgraded. The order of the instructions is the author's to get right across every dependency. The system that results is one where the upgrade is a second path through every process, hand-written, untyped, ordered by hand, and run seldom, so that it decays between releases; Elixir's releases left the mechanism out, and most Erlang systems are deployed by restarting, which section 6's reading is to confirm. The capability is real and the practice is not, and the gap is the second path.

**Where Ernest starts.** Three things are already better. The hashes say exactly what changed between two builds, down to each service's protocol and state type, which no `appup` author ever knew. Two versions of a type are two types, on one node as across nodes, so a message of one version never reaches a process of the other unchecked (`mvp3.1.md`, section 4, claim 5). And a process's state is a value of a declared type in its loop's arguments, not a term, so a function from one state to the next is checked like any function.

**The aim.** A deploy is planned from the hashes and refused before it starts wherever it cannot be made safely. Everything a human writes for it is typed, and is run at every fault, not only at upgrades. A service that can be replaced is replaced, with its state and its resources handed over; one that cannot is upgraded in place, as the exception and not the rule. And the whole of it is told to the program in values it matches on, and to the operator in a plan it reads first.

## 2. One recovery path

**Every service already has a path from one run to the next.** A process ends for more reasons than an upgrade: it faults and `restarting` or a supervisor runs it again, afresh (§6.9); it is killed through its address; its node restarts, for a new `ern` or a new OTP (`mvp3.1.md`, section 5, limit 4), or for a fault of the host; its node is lost. So a service whose state is worth keeping already has a way from the state of one run to the state of its successor, or the program loses that state by design. The ways there are today are three: the state is lost and the successor begins afresh; the state is outside the process, in a keeper process that seldom changes, in a table, in a file, in a database, and the successor reads it; or the state is handed from the old process to the successor, which only a planned end allows, since after a fault there is nobody to hand it.

**The migration is on that path already.** State that outlives a process outlives a build. A keeper of the previous build, a table written by it, a file on disk, is read by the new build's service, and where the state's type changed between the builds, the new build must hold a function from the old state to the new, or it cannot read what it finds. That function is Erlang's `code_change`, but it is not a second path: it is what a restart after a node's stop needs, and the first deploy that changes a state type and does not write it loses the state at the next restart, upgrade or none. So `migrate : (State1) -> State2` is written for recovery, typed against both builds' state types, and run wherever the old state is met.

**An upgrade is a recovery the operator chooses the moment of.** This is the idea the document is built on. The successor of a service starts as it would after a fault, from a state of its own type. What an upgrade adds is only that the old process is still alive to give its state, so the state need not have been outside: the old process hands it over, through `migrate` where the type changed, and ends. The code path from a state to a running service is then one, exercised at every restart, and the upgrade is that path with a handover in front of it. What the appup author writes by hand is either derived by the tool from the hashes, where modules load and in what order, or is the program's own typed function that a restart runs anyway, or is made unnecessary by the design, since nothing is suspended and nothing is swapped under a process.

**What a replaceable service is.** A service written for this has a shape, and the shape is small: it begins from a `State`, and it can be asked, at a planned end, for its `State` and for what it owns. `State` is the service's contract with its own future, as part two's *The state as a schema* has it. Behind an unchanged protocol a new loop holds inside whatever it likes and hands over a `State` when asked. The asking is a message in the service's own type, so that the type says the service can be replaced and the checker holds the reply to its rule (§6.6); whether that message is one constructor every replaceable service carries, from a library type, is section 7's. A service that cannot be asked is not replaceable: the tool says so, and what remains for it is a restart.

**The handover.** Replacing a service that runs is a dance of four steps, and the library writes it once. The successor is started, on the new code, waiting. The old service is asked to hand over, and gives the successor what it owns and its `State`; the successor begins from `migrate(state)`. The key moves: the successor offers itself under the service's key, and the latest offer holds (`mvp3.0.md`, section 6), so a client that finds the service from then on finds the successor; where the protocol changed, the successor offers the old key as well, through the translation, as section 3 says. Then the old service drains: it forwards what is in its mailbox and what still arrives at its address to the successor, in order, through the translation where the protocol changed, for a drain period the operator sets, and ends. A client that holds the old address meanwhile is served, and one that monitors the service sees it end at the end of the drain and finds it again.

**The binding on the service's node.** The key serves a client on a peer; a client on the service's own node reaches it by its binding (§6.5), and a replace must move that too, or local code of the new build starts a second service, as §11.2's reload does today. Two shapes are in sight, and part two's 7.3 weighed both. The tool adopts: the new build's binding is given the successor as its value instead of running its initializer, which keeps the program's text plain and puts the fact in the plan alone. Or the program says it: a replaceable service's binding is written with the library's start, `Service.start`, whose contract is that where a predecessor of this service is being replaced it begins from the predecessor's state, so that the binding's text says the service can be replaced and the tool only tells the runtime which services are. The second reads better by the principles, since a binding then holds what its text says, and the thinking leans to it; what loading a new build on a live node then is, its bindings evaluated in §8.5's order with the replaces among them, is section 7's.

**The forwarder returns, written once.** Part two's 7.2 settled that no forwarder is written, since it was a loop kept by hand around the one thing that cannot be avoided, the translation. The drain is that forwarder, and the objection does not reach it: it is the library's, written once for every service, it runs for the drain period and not for the service's life, and it carries the translation that the program writes anyway. What was wrong with the forwarder was its being each program's and for ever.

**The singleton is a service that owns a resource.** The service that may not run twice is the sharp case, and the language already has the shape for it. A socket, a file, a port and a table have an owner, the process that opened them or was given them (E.18), and on the host each can change owner in one act. So a singleton is not duplicated: in the handover the old service gives the successor its resources before it answers its `State`, and at no instant are there two owners. A connection to a database is a socket with a protocol over it and a state the driver keeps, and the handover moves both; a listening socket moves the same way, and the successor accepts the next connection on it. Nothing is reopened, and nothing is held twice. Whether the runtime gives every resource a `State` holds in one act, as the handover's rule, or the program gives each, is open (section 7); a forgotten give is a dead resource in the successor, which weighs for the rule.

**In place is the exception.** The handover gives the successor a new address, and a client that holds the old one is served only for the drain. Where what the clients hold is the address itself, a process that thousands of values point at, or a connection, a process that is a telephone call, a game session or a chat connection, a successor at another address is a loss, and §6.10's upgrade in place is the right mechanism: the same process, the same address, the new loop by a tail call, the state through `migrate`, and the protocol through `become` with a translation (part two, 7.2). The recovery path does not replace it; it bounds it. In place is for the process whose identity is its value, and everything else is replaced, so that the one mechanism that cannot be tested by a restart is used where nothing else serves.

**The way back.** While the old process drains it still holds its own state as it was at the handover, so a rollback within the drain period is the handover reversed: the key moves back, the resources are given back, and what the successor did since is lost, which is said. After the drain the old process is gone, and the way back is forward: a deploy of the previous build, with a `migrate` from the new state to the old, which that build must then hold. In place, the way back is part two's 7.3: the new loop runs again from the state as it was at the switch, and going back to the old protocol is a later build whose translation runs the other way.

**Across nodes.** A successor on another node is started by `Peer.spawn` and handed the state by a message, so the state crosses as values cross (§3.11): no function, no bound type, no resource. A resource does not cross nodes; a successor on another node reopens it, and the handover says so by the type, since a socket is not a value that crosses. So a node's stop, for the platform or a fault, is the one case where a singleton's resources are not handed over, and its state is, before the stop, to a successor elsewhere, or is outside. MVP 3.1a makes the platform's upgrade rolling by node, and this is what each node's services do before their node's turn.

## 3. The matrix

**The dimensions.** Two decide the mechanism, and the document keeps every case honest with a program for it. What changed is read from the hashes by `ern diff`, and is one of seven. What kind of process meets the change is read from what its build holds and what it owns, and is one of five, with the supervisor and the node beside them. The other dimensions, one node or a rolling deploy, forward or back, and who sends, are paragraphs of section 2 and not of the table: the handover is the same on one node and across two, but for the resources, and the way back is the drain period.

What changed, from `ern diff`:

- **C1, the logic**, behind an unchanged protocol and an unchanged state type: the loop's hash changed, the identities of `Msg` and `State` did not.
- **C2, the state's shape**: `State`'s hash changed, `Msg`'s identity did not.
- **C3, the protocol, every old constructor kept in form**: `Msg`'s identity changed, and the translation from the old type to the new maps each constructor to its namesake, which a tool can write.
- **C4, the protocol, a request retired or changed**: `Msg`'s identity changed, and the translation must answer an old caller whose request the new service does not take, in the old answer type's failure (part two, 7.2).
- **C5, a type many protocols carry**: one definition's change rippled into the identity of several services' protocols at once.
- **C6, a supervisor's tree**: a child added or removed, or a restart limit changed.
- **C7, the platform**: `ern`, OTP or the standard library, which is `ern`'s.

C6 and C7 are not rows of the table, since each is one case whatever the process: a supervisor is a P3 whose state is its children, replaced through a `migrate` that starts the added and ends the removed, the kept children taken over; and the platform's change ends every process on the node, so a P2 is restarted, a P3 or P4 hands its state to a successor on another node, as values, before the stop, and reopens its resources there, and a P5 loses what it held, one node at a time once MVP 3.1a makes it so.

What kind of process meets it:

- **P1, a worker**: short-lived, ends on its own.
- **P2, a service that can run twice**: stateless, or its state outside it.
- **P3, a service with state in its loop**: worth keeping, and nowhere else.
- **P4, a singleton**: a P3 that owns a resource, a connection, a listening socket, a file, a port, a table.
- **P5, a holder of identity**: a process whose address is held in values, or whose connection is its state.

| | P1 worker | P2 runs twice | P3 state in its loop | P4 singleton | P5 identity held |
|---|---|---|---|---|---|
| **C1 logic** | nothing | replace: successor, key moves, drain | replace, the state handed over as it is | replace, the resources and the state handed over | in place: `Upgrade` with `migrate` the identity (§6.10) |
| **C2 state's shape** | nothing | nothing of its own; its keeper is a P3 or P4 | replace, through `migrate` | replace, through `migrate`, with the resources | in place, through `migrate` |
| **C3 protocol, additive** | nothing | replace; the successor offers the new key and the old one through the translation | the same, with the state | the same, with the resources | in place, through `become` with the translation |
| **C4 protocol, a request retired** | nothing | as C3, and the translation answers each old caller | as C3 | as C3 | as C3, in place |
| **C5 a shared type** | nothing | C3 or C4 of every service that carries it, at once, listed by the tool | the same | the same | the same |

**The cells, read down the columns.** A worker is never touched: it ends on its code, and the next spawn runs the new, which is claim 4 of `mvp3.1.md` and the whole of Erlang's practice for short processes. A service that can run twice is the ordinary deploy, and it is what MVP 3.1's rolling restart already gives on another node; on the same node it is the handover without a state, which is the key moving and a drain, and the state it reads from outside is some keeper's C2. A service with state in its loop is the handover of section 2, with `migrate` where C2 made the state another type. A singleton is the same with its resources given first. A holder of identity is in place, §6.10 as the report has it for C1 and C2, and `become` for C3 and C4, which is what part two thought through, now bounded to this column.

**The cells, read across the rows.** C1 is the common case of a fix and costs the program nothing: the handover and the drain are the library's, and `migrate` is the identity. C2 costs one function, which the recovery path needs anyway. C3 costs a translation that a tool can write, and the successor serving two keys for as long as the build holds both; it is where a feature most often lands, since a feature is a new message. C4 is C3 with the translation answering for a retired request, which the old answer type's failure allows and which a service's answers therefore hold from the start; it is the one row where a protocol's past constrains its future, and the discipline of small, own protocols is what keeps C4 rare. C5 is not a mechanism but a bill: the tool lists every service the ripple reaches, and the guide's rule that a protocol's types are its own, not shared across a program, is what keeps the bill short. C6 is the supervisor as a P3 whose `State` is its children, and what a successor supervisor does with the children it keeps, monitor them anew and keep their places, is to be read against `Supervisor` (section 7). C7 is the row no upgrade in place saves, and the reason the recovery path is the default: a node's stop ends every process on it, so a service that is to outlive one has its state outside or hands it elsewhere, and that path, once written, is the upgrade's.

**What the program writes, in all.** A `State` type, and a service that begins from one and gives one when asked; `migrate` where `State` changed; `translate` where `Msg` changed, by hand where C4, by the tool where C3; and the give of its resources where it is a singleton, unless the handover's rule gives them. Nothing else. A service that writes none of it is restarted, which the tool says before the deploy, and a program that is content with that writes nothing.

**One program for each cell.** The matrix stays a claim until each cell runs. Under `experiments/code_update/` a program for each distinct cell, run by the tests: a counter for C1 and C2 of a P3; a store over a listening socket for C1 and C2 of a P4, the socket handed over with a client connected across the handover; the counter with `Reset` for C3 and with `Get` retired for C4; a program whose three services share a record for C5; a supervisor over two of them for C6; a chat server holding connections for C1 to C4 of a P5, the connections kept across the upgrade; and the store on two nodes for C7, the state crossing before the first node's stop. Each is written twice, as the program must write it today and as the proposal has it, so that what the design saves is measured in lines and in what can go wrong.

## 4. What the tool computes

**The plan from the hashes.** `ern diff` grows into a deploy plan: for each service of the program, by its binding's name and its key, which row it is in, from the hashes of its loop, its `State` and its `Msg`, and which column, from what its build holds, a handover message, a `migrate`, a translation, and from what the runtime shows of the running process, the hash of the function it was started with and the resources it owns. For each, the plan says what will be done, replace, in place, restart or nothing, and what the build must hold for it. Where the build lacks it, the deploy is refused before it starts, with the function named: `Counter: State changed and no migrate from the previous one`. Where a service holds no handover, the plan says it will be restarted and what state that loses.

**The order of a rollout is free.** `relup`'s ordering exists because an old client and a new service, or the reverse, cannot meet. Here the successor serves both protocols, the old through the translation, for as long as the build holds both, and an old client finds it by the old key; so services can be replaced in any order, and nodes restarted in any order, and the plan has no order to get wrong. What remains ordered is the retirement of an old protocol, which the deletion of its type and translation from the source does (part two, 7.3), and which the plan shows with the count of messages still translated from it.

**What is refused, and when.** Everything that the two builds decide is refused at planning: a missing `migrate`, a missing translation, a translation that is not total, which the checker refuses as it refuses any `match`, a singleton that cannot be asked for its resources, a `State` that holds what cannot cross where the successor is on another node. What only the running system decides, a service that does not answer its handover within its time, a resource the host will not give, is a failure the handover answers as a value, and the plan is stopped there with the service as it was, since nothing was taken from the old process until it answered.

## 5. What is to hold

What a proposal written from this would claim, each to be tested:

1. **A process keeps its code unless it acts.** Nothing is swapped under a process; it takes new code by a message in its own type, or ends (`mvp3.1.md`, claim 4; §6.10).
2. **No message of one version is read as another's**, on one node as across nodes (`mvp3.1.md`, claim 5).
3. **State crosses a version through one typed function**, `migrate`, written in the build and checked against both state types, and through nothing else.
4. **A resource has one owner at every instant**, and a handover moves it in one act.
5. **An upgrade runs the recovery path.** What a restart runs from a kept state, an upgrade runs from the handed-over state, and the handover is the one thing an upgrade adds.
6. **Every version in flight is listed**, by the tool, from the hashes: the processes on each code, the protocols each service serves, and the messages translated from each.
7. **What the hashes can refuse is refused before the deploy.** Nothing fails during a deploy that the two builds could have shown.
8. **The way back is the drain**, and after the drain it is forward.

## 7. Open questions

- Whether the handover message is one constructor every replaceable service carries, from a library type `Service(Msg, State)`, or each service's own in its protocol; and what the tool matches to know a service can be asked (part two, 7.6).
- Whether the runtime gives every resource a `State` holds in one act, as the handover's rule, or the program gives each (section 2).
- What `Supervisor` does with the children a successor supervisor keeps: monitor them anew, and whether a join from a process the group holds keeps the child's place (part two, 7.6).
- The order of a client's messages across the drain: a client that re-finds the service during the drain sends through the new address while its earlier messages go through the old and the forwarder, and §6.4's order for one sender may not hold across the two; whether the forwarder's hop is bounded so that it does, or the drain says it may not.
- What loading a new build on a live node is: its bindings evaluated in §8.5's order, a replaceable service's binding beginning from its predecessor's state, and the rest run as at a start; and whether the binding says so, by `Service.start`, or the tool adopts (section 2).
- How the tool reaches a service to ask it: by its key, through an address narrowed by `via` so that clients cannot ask (part two, 7.3), or by its binding on its node.
- What the plan does with a service whose process is on old code and whose binding the new build no longer holds.
- How long a drain is, who sets it, and what the forwarder does at its end with what is still arriving.
- What `restarting` and a supervisor's child run after a replace: the successor states its own, as part two's 7.2 has it for `become`.
- Whether `migrate` for a stored state runs at the deploy or when the state is next read.
- How an upgrade is a test: `ern test` with the previous build started, the plan applied, the state checked, on every commit.
- What of part two's thinking for in place changes under the recovery path beyond its bounding to P5, read once this document's shape is agreed.

## 8. What this changes in part two

Part two of `code.md` thought through one process taking new code, in place, and settled seven things for a change of protocol. This document keeps them for the column they belong to, P5, and changes the frame around them: in place is the exception and the handover the rule; the forwarder it refused is the drain, the library's and written once; and the upgrade case it wanted every service to carry becomes the handover message, which a service that is to be replaced without loss carries and the tool checks for. Its open questions move to section 7 as they are answered or stay open here. When the shape is agreed, part two moves here whole, and `code.md` goes back to the reasons for code by its hash.
