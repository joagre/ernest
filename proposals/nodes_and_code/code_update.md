# Ernest: Code Update, the thinking for step D

Status: a thinking document for step D of [`code.md`](code.md)'s section 1, *The four steps*, a running system that takes new code. Begun 2026-10-07 from one recovery path and a matrix of cases, read by four readers the same day ([`other_systems.md`](other_systems.md), section 7), rewritten under what they found, and its sections 2 to 4 rewritten again under six experiment programs ([`experiments/code_update/`](experiments/code_update/README.md)). Nothing in it is decided, and no proposal is written from it yet. `code.md`'s part two, the thinking for one process that takes new code, moves here when this document's shape is agreed.

## 1. The problem

After MVP 3.1 a node holds versions side by side, a process keeps its code until it ends, a service is found by its key at whichever version it is, and a deploy is a rolling restart. That serves every process that can end and begin again without loss, and not the three a real system is made of: a service whose state is in its loop's arguments and worth keeping; a service that may not run twice on a node, since it holds a database connection, a listening socket, a file lock or a table; and a process whose address or connection is what its clients hold.

§6.10 gives one process a way to take new code, by a message in its own type and a tail call. It says nothing of the system: who sends the message, what the resources, the clients, the mailbox, the supervisor and the other nodes do, and how to come back.

OTP's answer is the `appup`: a second path through every process, written by hand, untyped, ordered by hand, and run seldom, so that it decays. OTP's own applications mostly restart, Elixir left the mechanism out as unviable in practice, and the field loads modules by hand and skips it (*U6*, *U7*, *U9*).

Ernest starts with three things OTP lacks. The hashes say exactly what changed between two builds, down to each service's state and protocol. Two versions of a type are two types, so no message of one version reaches a process of the other unchecked. And a process's state is a value of a declared type, so a function from one state to the next is checked like any function. The aim is a deploy planned from the hashes, refused before it starts wherever it cannot be made safely, with everything a human writes typed and run on every commit.

## 2. The concept

**A service is a step function, and the library runs it.** The shape the field converged on is one function from a state and a message to the next state, the loop that calls it holding the state and owning the mailbox: `gen_server` beneath its callbacks, Akka Persistence's handler, Elm's `update` (*U3*, *V9*, *S7*). Every message boundary is then a safe point, since no frame of the old code is live when the next message is taken, the condition the dynamic-updating field proved and found by hand in each loop (*D1*, *D2*, *D13*). Ernest takes the shape as a library over the language it has: `Service.start(init, step)` spawns the library's loop, which holds the state, calls `step : (State, Msg) -> State` on each message, and takes one message of its own that carries new code. The experiments' library is 65 lines ([`experiments/code_update/`](experiments/code_update/README.md)). The language's process, a function that loops with its state in its arguments, stays for a worker, a connection and whatever a service is not.

**A change of logic is one message, in place.** The loop takes `Upgrade` as any message: when the step in progress returns, it goes on with the new step, in the same process, at the same address, with the same mailbox and everything the process owns. It is §6.10 written once for every service, and OTP's suspend, `code_change` and resume without the suspend window, since the mailbox queues what arrives (*U3*, *U4*). The counter kept its total, the store its items and its listener, and the chat server's connections, loops upgraded by their own case, kept their sockets. What it costs is the step in progress, which it waits for.

**Any other change is a change of the mailbox type, so in place it needs `become`.** The library's loop runs under `Envelope(Msg, State)`, which names both the protocol and the state; a new `State` or a new `Msg` is another mailbox type, which the running loop's type refuses, and the checker says so exactly (the counter's version 3). A loop whose upgrade case names its state or its protocol stands the same (the chat server's version 3). Rows C2 to C5 in place therefore need `become`, the gate through which a process's mailbox type changes under a translation (code.md, part two, 7.2), and it is the one addition to the language step D would make. With it, the library's loop changes its mailbox type and translates old clients' messages on intake. Without it, the change is a replace, which runs today.

**A replace is one message too, and a forwarder serves the old clients.** `Service.replace(old, forward, successor, migrate, step)` has the old loop hand its state through `migrate` to a successor of the new version and go on as a forwarder: each message at the old address is given to the program's `forward` with the successor's address, which sends the translated message, or, for a request retired or one whose answer's type changed, asks the successor and answers the old caller itself, so that no adapter for replies is needed. The counter went through two changes of protocol with clients two versions deep served, and three services through a change of a record they share. The costs: a new address, which old clients reach only through the forwarder; a forwarder process and a hop for each version still held, chaining until the old type and its `forward` are deleted; and what the process owned, which the successor opens again. The store's listener came back on another port, since Appendix E.18 gives a socket to another owner and not a listener.

**The envelope tells the versions apart, for an upgrade in place.** A local address is a pid alone, and a constructor of one name in two versions of `Msg` is one term on the host. Under a replace each version has its own loop, and an old address reaches the forwarder. In place, one loop takes both, so the library never hands out its loop's raw address: a client gets `via(self(), fn(m) = Message(identity, m))`, an adapted address whose function tags each message with the protocol's identity, and the loop applies the translations the tag calls for before the step sees the message. The cost is one tag on every message and every client's address an adapted one, which §6.5 makes free to cross, the tag put on at the service's node.

**A supervised process's restart follows its upgrade.** A restart runs the function its process was spawned with, so an upgrade in place of a supervised process vanished at its first fault in the supervisor experiment, and calling `Supervisor.child`'s function again inside the child made the group count a fault that had not happened. Decided with the user on 2026-10-07: `Supervisor` gains an operation by which a child replaces the function its restart runs, which the library's `Upgrade` calls for a supervised service, so that a fault restarts the new step from the state at the switch. Its name and shape are section 8's.

**Every long-running process of a module holds its version.** The chat server's readers, spawned by each connection and never upgraded, ran the old code until the shell's purge ended them, and the store's acceptors the same. An upgrade reaches every long-running process of a module, helpers among them, or leaves them listed as on old code by the hash they run (section 6, claim 6). Under MVP 3.1 nothing is purged, and a helper left behind runs its old code until the node restarts.

**The node that stops is a replace onto another node.** A new `ern` or OTP, or a fault of the host, ends every process on the node. A service's state leaves before the stop as a replace whose successor is started by `Peer.spawn`, the state crossing as a value, or is outside the process; a resource is opened again there, since no system moves a connection, and a listening socket alone can be handed (*U12*). The drain is of the node, minutes long, graded, and ending by a close (*U13*). A process that is a connection loses it. Every remote client has its waiting calls answered `None` and finds the service again through a standing address, a forwarder on the client's node that holds the key and finds again when told, which nodes.md's section 14 left to a library and which every client of a singleton on another node needs. What no library hides is the call itself: a `None` may or may not have run (nodes.md, section 11), so the retry is the program's and a request must be harmless when run twice. A change of code in place restarts no node, so this cost is paid for the platform's change alone.

**Two versions of a type are two types, at a price paid at the boundary.** The field chose to transform every value at an update and rejected coexisting versions as disastrous with side effects (*D3*). Ernest's choice is sound because values are immutable and a message is a copy, and its price is a translation wherever versions meet: a forwarder, a second key, a node of another build. A value of a new type is refused by its hash before any frame is decoded, which is where Orleans's rolling upgrade broke (*V5*).

## 3. What the program writes

**Nothing, for a change of logic.** `Upgrade(step)` behind an unchanged `State` and `Msg` is the plan's to write; in every experiment it was one line at the shell. It is the commonest deploy and the one the field makes in place (*U9*).

**A `migrate`, where the state changed.** It is derived by the one rule every system shares: match fields by name and type, a default for a field the new type adds, drop a field it removes, promote a number's width (*S1*, *V6*, *V11*, *D4*). A rename reads as a removal and an addition, and is told by one word in the new declaration, `was`, as Avro's and Orleans's aliases do (*S2*, *V6*). Where the rule stops, the derived `migrate` is written out with a hole the checker refuses as it refuses a partial `match`, never with a default (*D4*). A program may give a `migrate` for a `State` whose hash did not change, since a changed meaning behind an unchanged type is invisible to any diff (*D5*). The counter's was one line, and the catalog's a `Map.map` over the item's conversion.

**A `forward`, where the protocol changed.** Where every old constructor is kept in form it is the namesake map, 5 lines for the counter's `Reset`, which a tool writes. A retired request, or one whose answer's type changed, is answered by the forwarder asking the new service, 7 lines for the counter's retired total and 2 for the catalog's item converted back. A protocol is of independent requests; a conversation has no safe point between its messages and is a process of its own (*D12*).

**The new declaration takes a module of its own; the old stays where it is.** A type's qualified name is in its identity, so the old declaration moved would be another type, which no running client holds (`mvp3.1.md`, section 5, limit 1). Two types in one module cannot share constructor names, so the new one goes in a module of its own, `catalog2.ern`, whose clients write its name. Deleting the old declaration with its `migrate` or `forward` retires the version; a process or a stored value still of it refuses the deletion, and the plan lists it.

**A type many protocols carry costs each of them.** Changing the item three services' protocols carried cost a copy of each service, retyped at the new item, and a `forward` for each: 84 lines, of which 46 copied, against 37 where each protocol owned its types and only the catalog's carried an item. A protocol's types are its own, small, and of independent requests, which the guide is to teach with that number.

**A state outside the process is the store's, and its row type is Ernest's.** A database's schema is not in the hashes; the type a service reads a row into is. A stored value migrates when it is next read, through `migrate` from every shape still stored, and is written back in the new form at the next write (*V12*, *D9*). A schema change is therefore expand then contract (*S3*): additive in the database while both versions of the service run against it, the old shape gone when no row of it remains, which the deletion of the old row type from the source marks. The plan checks the service's side and says it cannot check the database's.

**The way back ships with the new build.** A previous build cannot hold a function from a type written after it (*V11*, *S11*, *V13*). The reverse `migrate` and the reverse `forward` are derived and holed like the forward ones; where either has a hole the plan says the change is forward-only for that service. Otherwise the way back from an upgrade in place is one more `Upgrade`, and from a replace a replace the other way.

## 4. The matrix

What changed is read from the hashes by `ern diff`; what kind of process meets it is one of three. Each cell says what ran on 2026-10-07, in [`experiments/code_update/`](experiments/code_update/README.md), and what needs `become`.

| | a worker | a service, `Service.start` | a loop, a process of its own |
|---|---|---|---|
| **C1 the logic** | nothing | `Upgrade(step)` in place: the counter, the store | its own upgrade case in place: the chat server, 15 lines |
| **C2 the state's shape** | nothing | a replace with `migrate`, at a new address: the counter, the store; in place with `become` | its upgrade case names its state, so a successor today and in place with `become`, as a service; not run |
| **C3 the protocol, every constructor kept** | nothing | a replace with the namesake `forward`, 5 lines; in place with `become` | in place only with `become`: the chat server's version 3, refused |
| **C4 a request retired or changed** | nothing | a replace with a `forward` that answers it, 7 lines; in place with `become` | as C3 |
| **C5 a type many protocols carry** | nothing | C2 to C4 for each service that carries it: 84 lines, against 37 for a protocol of its own | the same |

A worker ends on its code and the next spawn runs the new. A supervisor is not a service whose state is its children: its state is the children themselves, which stay where they are, and a count of recent faults. A tree is upgraded child by child, each child's restart made to run its new code; a child joins a running group at any time; and a change of strategy or limit is a new group, whose children begin afresh. The platform's change is the node that stops, section 2.

**The restart is the baseline, and the experiments measured what it loses.** The alternative to step D is to update no code in place: a deploy is MVP 3.1's rolling restart with a drain, as Orleans, Elixir, WhatsApp and the cloud do (*V2*, *U7*, *U9*). It removes the `Upgrade`, the envelope and `become`, and nothing else: `ern diff`, `migrate` for every state that outlives a process, a translation where an old client is to be served during a rollout, and the test stay owed. What it lost in the experiments: the counter's total, the store's items, and every connection the chat server held, which nothing softens. A replace, which runs today, lost none of the first two and kept old clients served; only `become` keeps a process's address and connections through a change of state or protocol.

## 5. The plan and the test

**The plan is computed from a baseline.** `ern diff` grows into the deploy's planning step. It needs the previous release's hashes and canonical forms without a running system, which the kept build directory of the last release gives, as Dapr's shipped file does (*V13*). For each service it names the row, from the hashes of its `State` and `Msg`, and the column, from how its binding is written; what the build must hold; and what is derived, holed or told. Everything the two builds decide is refused at planning, with the function named: `Counter: State changed and migrate has a hole at Reset`.

**The order of a rollout is free one way.** An old client meets the upgraded service through the translation. A new client meeting a service still on old code, on a node not yet reached, finds `OtherType` by MVP 3.1's rule and waits, as for `Unreachable` (*V4*, *S3*). A stored state migrates when next read and is written back in the new form at the next write (*V12*, *D9*); a `migrate` pure by its effect row pays nothing for being lazy (*D8*). A service's own state migrates once, at its `Upgrade`.

**What the running system decides is answered per service.** A service that does not take its `Upgrade` within its time is left as it was and named; the services before it stand upgraded; the plan prints what stands at which version and the way back for each. Nothing is suspended, and there is no point of no return, since no node restarts for a change of code (*U5*).

**The upgrade runs as a test on every commit.** The shape half runs with nothing started: each row from the baseline, each hole and each untold rename refused. The run half starts the previous build, writes a state into each service through its protocol, applies the plan, reads the state back, applies the way back and reads it again (*U11*, *D14*). The oracle is identity for a change of logic and the round trip for a changed state; a property a human writes is asked for only where the round trip is not total, which is the one piece no system has automated (*D14*, *V14*). The cost of testing by hand is the stated reason Ericsson's divisions, Elixir and WhatsApp restart instead (*U7*, *U9*), and the generated run is the answer to it.

## 6. What is to hold

What a proposal written from this would claim, each to be tested.

1. **A process keeps its code unless it acts.** It takes new code by a message in its own type, or ends (`mvp3.1.md`, claim 4; §6.10).
2. **No message of one version is read as another's**, on one node as across nodes, refused by hash before any frame is decoded.
3. **State crosses a version through `migrate` alone**, written in the build, derived where the diff decides, holed where it does not, and checked against both types.
4. **An upgrade in place keeps the process**: its address, its mailbox, what it owns and what it asked the runtime for. A replace keeps its address's meaning, through the forwarder, until the old version is retired.
5. **An upgrade runs the recovery path's function.** What a successor would begin from after a stop, `migrate` of the kept state, an upgrade begins from in place.
6. **Every version in flight is listed** by the plan: the processes on each code, the protocols each service serves, the stored states of each shape.
7. **What the hashes can refuse is refused before the deploy**, and what the running system decides is answered per service, nothing suspended.
8. **The way back is the new build's**, one `Upgrade` with the reverse `migrate` or a replace the other way, or forward-only, said so.

## 8. Open, for the experiment programs

- Whether `become` is built: everything else of step D runs today as a library over the language, and an upgrade in place beyond a change of logic needs it. Its measure is the processes that cannot pay a replace's new address, a loop holding connections first; where none must, the replace is the answer and this document records why.
- Whether replay replaces `migrate` for a service: the library keeps a snapshot and the messages since, and an upgrade folds the new step over the translated log, so that no `migrate` is written, only the translation; the rollback is the old step over the same log, and the test is deterministic (*S9*, *V12*). Its costs, to be measured against `migrate` in the counter and the chat server: a log per service, the replay's time at the upgrade, and a step split into what changes the state and what has effects, since a replayed send would send again, which is why Akka and Elm split the two.
- The `Upgrade` message's exact shape, and who may send it: the address the service keeps, clients being given one narrowed by `via`, as the experiments' `Handle` does.
- How a listener is handed to a successor on one node, which Appendix E.18 does not offer, `Tcp.give` taking a socket alone.
- The name and shape of `Supervisor`'s operation by which a child replaces the function its restart runs (section 2, decided 2026-10-07), whether a plain `restarting` gains the same, and what becomes of a call of `Supervisor.child`'s function inside a child, which today is miscounted as a fault (the plan's standing gaps).
- What a step that blocks costs an upgrade, and whether the plan should refuse a service whose step may not return.
- The form of the baseline: the kept build directory, or a file of hashes and forms.
- How the test writes a state into a service through its protocol, and reads it back, without a message the protocol does not have.
- Whether `migrate` for a stored state in a keeper or a table runs at the read, as every system read does, or the keeper is upgraded like any service.

## 9. What this changes in part two

Part two of `code.md` thought through one process taking new code in place, and settled seven things for a change of protocol. This document keeps them for the loop column, and changes the frame: the step function is the service, so the upgrade case part two wanted every service to carry is the library's `Upgrade`; the handover it weighed is a replace, the library's one message, onto the same node or another; the forwarder it refused returns for a replace, written once in the library with the program's `forward`; its question of how a process tells an older protocol's message from its own is answered by the library's envelope; and `become` is the one addition to the language the step function does not remove, which an upgrade in place of anything but the logic needs. Part two moves here whole when the shape is agreed.
