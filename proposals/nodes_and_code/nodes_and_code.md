# Ernest: Nodes and Code

Status: thinking for MVP 3.0 and 3.1, all of it tentative.

The thinking about nodes, code distribution and code change, before MVP 3.0 decides any of it. Nothing here is a decision, nothing is built, and nothing flows from it into the report, the plan or the log until the thinking is covered. Then each decision goes to its owner, the report for a rule and the log for the why, and this note, its tentative marks gone, is the design note for nodes, code and code change.

The peer protocol proposed for MVP 3.0 is [`mvp3.0.md`](mvp3.0.md)'s, and section 2 holds the reasons for it. Sections 3.1 to 3.4 hold the design of the two notes this one replaced, in this note's words and not yet weighed. The rest is this note's thinking. The open questions stand with their subjects, in sections 2.8, 3.6 and 4.6, and what is left out in section 5. *P n* and *D n* are a question's number in the protocol note and in the distribution note, which commit `3fa6b42` keeps. The plan's MVP 3.0 and 3.1 hold further questions: when a module's top-level bindings run on a peer, where a node's configuration and its key are read, which tree the normalized definition is and what becomes of its effect variables, and what a foreign function's hash compares.

## 1. The aim

Unison names every definition by a hash of its content. Builds become incremental, two versions of a definition are two things and never conflict, a rename costs nothing, since code refers to a definition by its hash and a name is a label on the hash, and code can move between machines because its identity is exact. Ernest takes that idea openly (the plan's MVP 3.1), all but the rename: as the design stands a name is part of what is hashed, and a rename is a change (section 3.5). The aim is to do what it promises soundly and realistically:

- **Sound.** What holds across nodes is argued, as [`soundness.md`](../../docs/soundness.md) argues the core, before it is built (MVP 3.0's first item). Failure is part of the language: a peer's loss puts its processes out of reach and tells their monitors so, with `Unreachable` (section 2.3), a message is sent at most once, a call waits with a deadline, and a reply is checked.
- **Typed processes as the unit of distribution.** Shipping code is spawning a typed process on a peer, its protocol's hash checked.
- **Realistic.** Source stays text files under git, edited and reviewed as any code; the compiler computes the hashes. The runtime is the BEAM, with its decades of production behaviour, on machines a program's owner runs, listed in `ernest.conf` and authenticated by mutual TLS, with no platform to depend on. What hash modules cost on the BEAM, atoms and code memory, is measured before anything is promised.

Unison has shipped for years, and Ernest has a design, so "better" is true only when MVP 3.0 and 3.1 run and their numbers hold. Unison's codebase is a database rather than text files, and its distributed promise lives largely in its hosted cloud; what is said of its internals is said from the outside, and modestly.

## 2. The peer protocol

What is proposed for MVP 3.0 is [`mvp3.0.md`](mvp3.0.md)'s, the proposal: what a program sees, what holds and what does not, how it works, and what is unsolved. This section holds the reasons for it, in section 2.3 and at each question of section 2.8, and in section 2.9 the order to build it in. How other systems treat the same questions is [`other_systems.md`](other_systems.md)'s. The reasons here were first written for a protocol of Ernest's own over TLS. The proposal now rides on Erlang's own distribution, so what these reasons say of a handshake, a detector, a delay before a dial and a checker over a played network is said of what is now the host's.

### 2.1 Nodes

In the proposal's section 6, *Nodes*.

**A node's peers change while it runs.** A configuration read only at start was weighed first and left, since adding a node is not a change to one node's list: every node that is to talk to the new one gets an entry, so adding a machine would restart the whole system, a deploy's cost for a change that touches no code. On this carrier the change is cheap. The rule that accepts a peer and the table that gives a peer's address read a table the runtime fills, and a removed peer is dropped with the host's own disconnect. Three ways for `ern` to reach the running node were weighed. Over the distribution, `ern` would be a node with a key the running node lists, which would have to be in the file about to be reloaded. A local socket or pipe is a second listener and a second protocol to say "read your file again". A signal needs no new channel: the host delivers it, the runtime has a signal handler, only the process's owner can send it, which is the right permission for a node with one owner, and `kill -HUP` works where `ern` is not at hand. So `SIGHUP` is the mechanism and `ern reload --config-dir dir` the convenience, by a process number the node writes in the directory it owns, as every daemon does. What cannot change while running is the node's own key and address, its name and its listener; the rest is a table's rows. A signal carries nothing back, so the node reports on its standard error, and the command's status says only that the signal was delivered.

**Two nodes with one key are not told apart.** The experiment tried a second node with the first one's key and name: to their peer the two are one node, and each one's dial ends the other's connection, with the host's `wait_pending`. The peer cannot refuse the second, since a connection from a name it already holds is exactly what a restarted node looks like, and asking the old connection whether it lives before accepting the new one would refuse every restart within the detector's 45 to 75 seconds. The node cannot refuse to start either, a copied directory on another machine being the original's twin. So the quarrel is stated as a limit and made visible: the peer says on its standard error each time a living connection is replaced by another from the same name, once for a restart and again and again for the mistake. And the mistake is made hard: `ern config` makes a key for one machine and prints the public key for the others' lists, and a configuration directory is never copied.

**The cookie is the build's fingerprint, and there is no hello.** The proposal first had a hello of Ernest's after the host's handshake, comparing the protocol's version, `ern`'s, OTP's and the build's checksum. Once a plain message went straight into the mailbox, that was a race: the host's handshake ends before the hello begins, and a message from a node of another build could reach a process first. The check has to be inside the host's handshake, where nothing passes before it. Two ways were weighed. Folding the four into the node's name, with the host told which names to accept, works but makes a node's name change with every build, against the rule that a name on the carrier is the key's identity and nothing else. The cookie is the other: the host's handshake proves both sides hold it before anything passes, and ours proved nothing. So each node computes it at its start from the four, nothing is written or copied, two nodes of one build arrive at the same one by themselves, and two of different builds fail the handshake with nothing sent, which the experiment showed. The cost is that the dialling side learns only that it was refused, so `Refused`'s text says what it can know, not listed there or another build, and the refusing side, which knows which, says so on its standard error. Erlang's cookie was a pain because it was the secret that said who may connect and had to be distributed; here that is the key's, and the cookie keeps no secret.

**Neither of a node's names holds an address.** The carrier wants a name for each node, and TLS a name in each certificate, and a host name is what both expect. Ernest gives neither one. A node is its key: its name on the carrier is the key's hash with a constant after it, and its certificate's name is a constant that nothing reads. So every node computes the same name for a peer, a node that moves keeps its name, and no name has to resolve: the configuration gives the address. The experiment ran with certificates that name another host and another address, and once with nodes named by a name that resolves nowhere, and a peer was accepted by its key in each. The host did not refuse the foreign name even where it was not told to accept it, which was not looked into, so the runtime turns the host's check of the name off and does not rest on that. The name a program writes is a third thing and is untouched: the name one node's `ernest.conf` lists a peer under, which is also what the runtime prints.

### 2.2 Connections

In the proposal's section 6, *Connections*, *The hello* and *What passes*.

**A sender waits, as the host has it.** The rule that a sender never waits was made for a protocol of our own, where blocking would have been code of ours. On the host's distribution it is the other way round: a sender that waits where the buffer is full is what the host does, and not waiting is what would be built, a `nosuspend` on every send, a disconnect where it is refused, and a limit to argue over. The host's way gives back-pressure, a program that sends faster than the network carries being slowed to the network's speed instead of losing the connection and every monitor and call on it; a bound, since the detector gives the peer up within 45 to 75 seconds and the send then returns; and nothing to build. Its costs are stated as a limit: a `send` across nodes returns at once only while the network keeps up; a process that waits in a send serves nothing from its mailbox, so a stalled peer stalls the processes that send to it, which Erlang programs live with by supervision and timeouts; and a call's time runs from the moment its request is sent. Akka drops the message where its queue overflows, which would break the claim that no message is dropped alone; ending the connection, which was weighed before, is the harshest answer to a stall. The buffer's size is the host's own 1 MB and says only when slowing begins.

**An operation with a time keeps its time.** With a sender that waits, a call's request could wait in the buffer, so a call to a stalled peer took the wait and then its time, as Erlang's `gen_server:call` does, where the timeout runs only in the receive after the send. Akka never waits and drops the message, which breaks the claim that no message is dropped alone; gRPC's deadline covers everything, connecting, sending and the answer, because the client owns its socket and can abandon a pending write. Erlang cannot give that promise for one process, since a process suspended in a send is not woken by its own timer, but it can for two: the call sends without waiting, and only where the buffer is full a process of the runtime's takes the request and does the waiting send, while the caller waits by its time. The common path costs nothing more; the helper is ended where the time runs out first, so that a stale request is not sent after its caller gave up. A plain `send` still waits, since back-pressure is what a sender without a time should feel. So the exception in the proposal's first rule, where the network is behind, applies to `send` alone. `answer` goes the same way as a call's request, since the one place the waiting sender punished the wrong process was a service answering a client whose node is stalled: the service blocked in the answer and served nobody else, held by one bad link to one remote client. An answer is small and one-shot, so the helper costs nothing on the common path. A service that pushes to many remote clients, subscriptions and the like, does it through a process for each, as Erlang programs always have, which the guide's peer chapter is to say.

**No delay before a dial.** The host dials again at the next operation that needs the connection, with no delay, and Ernest adds none. Measured, a send with no connection open returns in microseconds; where the peer's port refuses, each send makes one dial of about 90 microseconds; and where nothing answers, every send waits behind one dial, which the host gives up after 7 seconds. So a peer that is gone costs a node little, and only as fast as its program sends. A delay of Ernest's own would show: a peer that is back would stay out of reach for as long as the delay. It would also take the dial from the host and keep a clock for each peer. Akka's fixed second, and a delay that grows, protect a node that comes back from hundreds of peers that dial it at once, which a few nodes with one owner are not. A delay changes when and never what, so it can enter later and break no program.

**Two fields for two things: `listen` and `network-address`.** One field held where a node listens and where a peer is dialled, which are different things: the first is an interface, `0.0.0.0` among them, the second a destination. So the node's own is `listen`, and a peer's is `network-address`, `host:port` with a name or an address. A name is allowed for a peer because deployments name machines, and a rule of numbers only would be worked around; it is resolved at each dial, not at start, so that a changed address under a stable name is followed. The host runs distribution over one family of addresses per node, so the family is the listener's, and a peer of the other family is refused when the configuration is read rather than at a dial that would fail later.

**One side may be unable to dial.** Behind a translated address a node reaches its peer and the peer does not reach it. One connection carries both ways, so the node that can dial opens it and the other then sends, answers, spawns and monitors over it; a system with a connection for each direction, as Akka's, cannot send to such a node at all. What is left is the time after a loss, when the node that cannot dial has no way to open the connection again. Two answers were left: a node that dials again in the background, which was refused for every node (section 2.3), and a message carried through a third node. So nothing is added, and the limit is stated: the node that can dial watches, and opens the connection again. The configuration follows the fact. A node with no network address of its own does not listen, and a peer listed without one is never dialled, so that no dial is made that can only hang until the host gives it up. The experiment tried it with a node that does not listen: its peer could not connect to it, reached it and spawned on it once it had dialled, lost it at a loss, and reached the same process by the same address once it had dialled again. The host calls a node that does not listen hidden, and leaves it out of its plain list of nodes and its plain notices, so the runtime asks for nodes of every kind.

### 2.3 Loss and reconnection

The rules are in the proposal's section 6, *A loss*, *The detector* and *Connecting again*. The reasons follow.

**Both ends run a loss.** A loss is the end of a connection, and each end runs it for itself: no frame says it. The end that tears the connection down runs it then. The other runs it when it sees the close, when its own heartbeat timeout passes, or when a hello arrives from a peer it holds an established connection with: that hello is the loss of the old connection, run whole before the new one carries a frame. The rule of the lower `NodeId` chooses only between two connections both still in their handshake. Were a loss one end's alone, the other would wait on monitors the first has dropped and on calls it has ended, and nothing would tell it. A network that stays silent is the plain case: both ends hear nothing, and both time out. Erlang's distribution does the same: each end closes on its own tick timeout, and its handshake answers `alive` to a node it believes connected, which then confirms that the old connection is broken.

**An address outlives a loss.** An address reaches its process again once the two nodes connect again, for as long as the process lives and its node has not been started again. A loss ends what was in flight and nothing else: what waited to be sent, each monitor with its one `Down`, and each waiting call. The first answer to *P5* had an address die with its connection and stay dead, by a number each node gave its connections and marked what it held with. That kept a stream from ever going on after a hole. It also made every program that keeps an address of another node's process write for a loss: notice it, get the address again, monitor again. Each way round that was more machinery, a relay that finds a named service again, an operation that renews an address, a rule for a dead address that travels, and a process known by its address alone could not be found again at all. With an address that outlives a loss a program writes nothing for one, which is what a reader who knows Erlang expects (principle 1), and what Akka and Swift do at an ordinary loss; the capability systems keep a reference broken ([`other_systems.md`](other_systems.md)). The price is a hole: what one process sent another during a loss is gone, and what it sends after arrives. Both nodes run the loss, so whoever monitors is told that a hole may be there, and a protocol that must have none numbers its messages or calls. A restart of a node ends its addresses, which the incarnation tells, and the reason of a loss is `Unreachable` (*P6*), as Erlang's `noconnection` says that the process may still be alive.

**A monitor ends with its connection.** A monitor on a peer's process is among what a loss ends. The watcher's node makes its `Down`, the one message its `monitor` call gives (§6.9), and nothing sets the monitor again when the connection returns. A program that wants to go on watching calls `monitor` again. The `Down` holds the process, so `monitor` on it watches the same process over the next connection. Set again by the runtime, a monitor would say nothing at the loss, its watcher waiting for ever on a peer that never returns, or it would give two messages for one call. The node would dial in the background to set it, where a connection opens only on demand, and would keep each `wrap` for as long as the peer stays away. Erlang's monitor is the same: it is triggered once, the loss of the connection among what triggers it. A client finds its service again after a loss in any case (below), and monitors it again there; whether a library does both is section 2.8's question. A `monitor` called while the peer is still out of reach answers a `Down` with `Unreachable` once the dial has failed, so that a program that monitors again in a loop is paced by the dial's delay.

**The weaknesses, worked one at a time.**

1. *A full outgoing queue is a loss* (section 2.5, *P1*). Overload then costs every conversation with the peer, the innocent among them, and what they do to recover, finding, monitoring and sending again, adds to the load that caused it. The sender that filled the queue is told nothing. *Worked:* the teardown stays. Of what else a full queue could do, a sender made to wait stalls a server that answers one slow node for all its other clients, and §6.2 has `send` return at once; one message dropped breaks the unbroken prefix; a fault of the sender falls on whoever meets the limit, a server at its `answer` among them; and no limit lets a slow link take the node's memory. The teardown alone keeps the prefix, keeps `send` from waiting or faulting, and stops the harm at one peer. Two things go with it. The limit is generous, since reaching it costs every conversation with the peer, and a constant of the protocol. And the delay before a connection is opened again counts losses, which weakness 4 settles. A program is not given the queue's size to read: backpressure in Ernest is an acknowledgement, a call or a message back, and a number to poll would be a second way (principle 2). The innocent conversations with the peer still end at an overflow, and nothing cheap that keeps the prefix spares them.
2. *A large frame delays the heartbeat* (*P14*), and a delayed heartbeat is a false loss. *Worked:* a sign of life is bytes arriving, read from the socket's count of them, and not a heartbeat frame. The heartbeat is sent only when the connection is otherwise idle. A large frame in the middle of crossing is then itself a sign of life, and causes no false loss. No payload is sent in chunks: a frame crosses whole. The queue's limit is the largest frame, one number for both: a value that cannot fit the queue at all faults the operation that would transport it, as a foreign value does (§3.8), so the sender is told. Code goes a frame for each definition, so it needs no large frame, and other senders' frames pass between. What stays is delay: one large value holds up what waits behind it on the connection for as long as it crosses, and a call's deadline can pass meanwhile. That is stated, and measured before more is built. Erlang splits a large message into fragments that other traffic passes between, which needs a count for each sender in the connection's process; it waits with the separate connection for code (*P21*).
3. *The detector is a fixed timeout* (*P3*): what counts as a sign of life, how long the silence is, and what a node that is itself stalled concludes of its peers. *Worked:* the timeout stays fixed. A detector that adapts keeps a history of delays and a threshold to set, which buys little for a few nodes listed by hand; measured false losses would change that. Its default is Erlang's, 60 seconds in four intervals, so a silence is found in 45 to 75 seconds. A peer that crashes or exits is seen at once, its host closing the socket. The timeout governs a dead machine and a partition alone, and a program that must know sooner has the deadlines of its calls. The detector counts the intervals it has seen and not the time gone: a timer every quarter of the timeout, and four in a row with no bytes arrived are a loss. A node that was itself stalled then sees one silent interval as it wakes, and does not lose every peer at once. It watches both ways: a peer is silent too where bytes wait to be sent and none have left in four intervals, since it has stopped reading. The timeout is a constant of the protocol, as the queue's limit is. Each end sends its idle heartbeat every quarter of it, so the ends must agree, and a constant leaves nothing to negotiate in the hello and nothing to set wrong. A number becomes a key of `ernest.conf` when a deployment shows that it must differ. No detector tells a slow peer from a dead one, which is what `Unreachable` says.
4. *The delay before a connection is opened again has no random part* (*P4*), so after a wide interruption many nodes dial in step. And it grows with failed attempts alone, where a link that comes and goes, or a queue that fills again, loses a connection as often as it opens one. *Worked:* each wait is drawn evenly between nothing and the delay as it stands, so nodes that lost one peer at one instant spread out. The delay counts losses as well as failed attempts: it doubles after a dial that fails and after a connection lost young, and returns to its start only when a connection has lived as long as the heartbeat's timeout. A link that comes and goes is then damped, and so is a queue that fills again (weakness 1). A demand that comes while the delay runs waits for the dial at its end, and is not refused at once: refused, a program that tries again, by a restart or by a `monitor` called again, would turn at full speed, and waiting lets the runtime pace it. The numbers stay, doubling from 100 ms to 30 s, as constants of the runtime: they are a node's own, and a wrong one costs no conversation. A connection is still opened only on demand. How long a spawn waits in all (*P2*) meets this, since a spawn that waits 5 s can give up before a dial delayed 30 s is tried, and it is settled with *P2*.
5. *A dead address comes alive by travelling.* It no longer arises: no address dies of a loss (above).
6. *The races are argued and not tested*: a dial again against two nodes dialling at once; a loss during a handshake, during a spawn's exchange of code, and while a `spawned` is awaited; a hello of a new incarnation over an established connection; and a loss one end has run and the other not yet. *Worked:* the protocol is written as a state machine and nothing beside it: one function from a connection's state and an event, a frame, a timer, a close or a dial's result, to the new state and what to do, with the sockets, the timers and the processes at its edge. A checker in the test tree runs those machines themselves, two nodes and then three, over a network it plays: every order of events up to a bound, and long runs drawn from a seed that a failure prints and that runs again. It holds what the soundness argument states, one list for both. Each end has at most one established connection with a peer, and the two ends come to agree. Every monitor gets one `Down`, and every call ends once. An address reaches its process again when the nodes connect again. What a connection delivers of what one process sent another is a prefix of what was sent over it. No frame of a lost connection is handled after its loss was run. Each race named here is a case of its own beside the checker, run by name. A few tests over real sockets cover what the played network leaves out, TLS, the socket's counts and how a close is seen. A relay in the test tree that stalls a connection or cuts one way is written when a named case needs it. A model checker outside the code would check a second description, which drifts; it is the next step, for the handshake alone, if the bound proves too small. The checker meets what is still open and has it answered before it passes, *P18* first.

**Not solved, and not a heartbeat's to solve.**

- *Two processes where one was meant.* A watcher told `Unreachable` that starts a replacement has two where the first lives on. What must exist once needs more than a monitor: a lease whose holder the resource checks, or agreement among nodes, a library's work. The guide says that `Unreachable` is not death. *Worked:* nothing is added to the language or the runtime for it. An election and a lease are engines, a library's work, and the language stays small (principle 5). The guide teaches three rules that what there is already carries. A program replaces at `Unreachable` only work that may run twice. A process spawned on a peer watches whoever it works for and ends when it is told `Unreachable`, which it is, since both ends run a loss; so no worker runs on unwatched after a partition, by `spawn` and `monitor` alone. And what must exist once lives on one named node and is found there with `Peer.find`: out of reach it is unavailable, nobody else starts it, and moving it is the operator's act in `ernest.conf`. The standard library makes no second one itself, a supervisor's children running on its own node. A thing that must exist once and move by itself needs a lease its resource checks, or agreement among nodes, a library written when it is wanted. Between the two ends' timeouts a worker and its replacement can both run for a while, which the first rule makes harmless.
- *Whether a call that ended without an answer ran.* `None`, or the fault of a loss, says only that no answer came. A request that may be sent again is written so that running twice does no harm. *Worked:* nothing is added. The runtime gives a request no identity, sends none again and remembers none: a send is at most once, and a call says what it knows. The guide teaches two rules. `None` means that no answer came, and never that the request did not run. And a request that may be sent again is written so that twice does no harm: it states the result, set the level to 5, and not a change, add 1, or it carries an identity the service remembers. A service whose requests must each take effect once keeps its own record, which is the program's work.

### 2.4 Addresses

In the proposal's section 6, *Addresses*.

**An address is the permission to kill, across nodes too.** On one node an address lets its holder send to a process and kill it, inside one program. With peers the permission travels: every node that finds a service holds its address and can end it for the others. Two other rules were weighed. An address that only sends, which a find would give, is a second kind of address beside the one the language has, and the carrier cannot keep its promise: a connected node can end anything on the other, so it would guard against a peer's mistake and not against a peer. And a `kill` refused across nodes takes from a spawner the means to stop the worker it started on a peer. The rule kept is the one a process already knows, so that it need not know where an address leads, for `kill` as for `send`. Erlang has the same rule: whoever holds a pid can send it an exit signal. The capability systems have the other, a reference that conveys messaging alone ([`other_systems.md`](other_systems.md), *T6*), and there an address that only sends is a process in front of the service, which a program can write today: it forwards what it is sent, and a `kill` of it ends the forwarder. An address that only sends can enter later and break no program.

### 2.5 Messages

In the proposal's section 4 and its section 6, *The gateway*, *Messages* and *Calls*.

**A key carries its type's text, and no hash is in MVP 3.0.** With one build on every node a type's name says everything a hash would: one build has one definition for each qualified name, so two keys name one type exactly where their types print the same. A key therefore holds the message type's text as the compiler prints it, and a find compares the texts, which still catches two services under one name with different types, at a string comparison once per find. The compiler still takes the type where `Peer.key` is written and refuses one not fully known there; printing a type is the simpler half of hashing it. MVP 3.1 puts a hash in the text's place, where builds differ and a name no longer says what a type is; the proposal's third rule for what comes after compares a type's identity and never asks how it was made, and its fourth lets the wire change. The one hash left in the milestone is the build's, a checksum of files, and is called so, so that the word first appears in MVP 3.1 where it carries meaning. The note's rule for a type's hash (section 3.1) stays there.

**What cannot cross is refused by the compiler, and nothing is walked.** The proposal first had the runtime look through every value before it was sent, for a function, a foreign value or a resource, which is a walk in Erlang over the whole value and can cost a multiple of the host's send. A walk only where the type can hold such a thing was weighed, and then the walk went altogether, since the check is a type's. A type is bound to its node where it holds a function type, a foreign type, a resource, or an address or reply whose message type is bound; and a bound value has only two ways to start towards another node, a key of its type and a spawn that captured it, both of which the compiler sees and refuses. Every other way follows: an address of a remote process came from a find or a spawn, so its message type is unbound, and so is everything sent to it or answered through a reply in it. Testing at run time what the type checker knows is wrong, as the user put it. A spawn whose captures have a type variable in their type is refused for now, by the proposal's first rule for what comes after, and `needs`, which already carries a property of a type variable to its use, is the way to relax it. One check stays at run time: an adapted address crosses with its function's captured values, which its type does not show, so they are checked as it crosses, a few values and never a message.

**The build's hash does the work, and a message carries none.** A spawn on a peer names its function as a module and a place in it, which means the same on both nodes only where both run one build; a node of yesterday's build would run another function, or one with another closure, and nothing else would catch it. So the hello compares a hash of the build, taken over every compiled module on the load path by name and content, which costs reading the files once at start and 32 bytes at each connection. It cannot follow the entry point, since three nodes of one program start from three modules, so it covers the whole build and every node carries the whole build. A manifest written at `ern build` was left, since it goes stale when one file is rebuilt alone; a hash per module, compared where a message or a spawn meets it, is step B of the proposal's section 11 and relaxes this later. The standard library is left to `ern`'s version. The checksum is over what runs, since a `.erc` holds the module's documentation as well, and a checksum over the file would part two nodes over a fixed typo in a doc block: each module counts as its name and the host's own digest of its code, `beam_lib:md5`, which is what Erlang's release handling asks whether a module's code changed and leaves out documentation, line numbers and attributes. With one build made sure of, a hash of the mailbox type on each message does no work: every `send` across nodes is typed by the compiler as a local one is, and the types are the same at both ends by construction. What it would catch is a peer that sends a wrong value on purpose, which can do anything else as well. So a message carries no hash, and does not pass through the gateway: the host puts it in the mailbox, and a `send` across nodes costs the host's send and nothing of Ernest's. The gateway keeps what needs a process on the receiving node, a spawn, a find and a message to an adapted address. The price is one corner of order: a message to an adapted address made on the receiver's node takes a step more there, and a plain message sent after it can pass it, where on one node the function is applied in the sender. MVP 3.1 puts the hash back on messages when builds differ, which the proposal's fourth rule allows.

**A fault in an adapted address's function faults the sender, on a peer as on one node.** On one node the function runs in the sender and a fault in it is the sender's. Across nodes it runs in the gateway of the node that made the address, and the proposal first gave the fault to the process the address leads to, which was a second meaning for one construct. Charging the target was weighed, the function being the target side's adapter, but the report charges the process a function ran in, not its author, and the target would die for a message it never saw. Dropping the message and saying so is a silence the sender never learns of. So the frame carries the sender's address and the gateway ends the sender with the function's cause through the host's exit signal, which crosses nodes; the one difference is when, after the send returned rather than in it, the same shape as a `kill` from another node.

**A remote call ends at a restart, by a note.** The runtime keeps a table on the caller's node of who waits on whom, which a restart reads to tell each caller. A callee on another node cannot read it, so without more a remote call would not end at a restart, a `callForever` never, against the claim that every call ends. Saying that a restart does not end a remote call was weighed and left, `restarting` being the ordinary shape of a service. So a call across nodes sends the callee's node a note that it waits, one frame on the same connection, kept as a row until the callee answers, restarts or ends, with a second note where the caller's time ran out and a loss dropping every row of the peer. The other half of the gateway's question, a function of an adapted address that never finishes, is left as it is on one node, where it holds the sender: across nodes it holds that peer's gateway, and a process for each adapted address would hold only that address but could never end, nobody knowing when a remote holder drops the address.

**A call's `None` has one meaning.** Across nodes a call ends without an answer in four cases: its time ran out, the callee ended or restarted, the callee's node went out of reach while the caller waited, or no connection could be opened. In the last the request was never sent and did not run, and in the others it may have run. A program is not told which, for five reasons. `None` on one node already covers a time that ran out, where the request may run later, and a callee that ended, so other nodes add nothing new in kind. That a request was never sent is known only where no connection could be opened: once one exists, the caller's node cannot know what arrived. A request that may be sent again must be harmless when run twice whichever case it was, so the difference would spare a program one duplicate, seldom, and none of its code. Telling them apart would change `Address.call`'s type on one node too, or give other nodes a call of their own, and a process would then have to know where an address leads, which an address is there to hide. And the reason is to be had: a monitor's `Down` says `Unreachable`, how the process ended, or `Unknown`. Erlang's `erpc` merges the same two: a connection lost and one never established are one error, under which the function may or may not have run.

### 2.6 Serialization

In the proposal's section 2, *What may cross*, and its section 6, *Serialization*.

**Atoms.** An atom crosses as the text of its name: the external term format writes a tag, a length and the name's bytes, and between two nodes the host sends the text once for a connection and a one-byte index after that. The receiving node looks the name up and makes an atom only for a name it has never had. In an Ernest value only a constructor's name is an atom, a `String` being a binary, and with one build every node has every constructor's atom from its own compiled modules. So a correct program's traffic makes no atom: decoding one value with four constructors 100,000 times made none. An atom is made only for a name a faulty peer invents, and on this carrier that peer can do anything else as well, so the proposal promises nothing against it and says so among its limits. Constructors sent as binaries and turned back on arrival were weighed and left: Ernest would rebuild every value at both ends, in Erlang where the host works in C, against the value's type, since a `String` is a binary too; and the host's own signals, which carry atoms, would stay as they are. Where builds differ, in MVP 3.1, a peer can send a constructor a node lacks, which adds as many atoms as that peer's code has names, and never as many as it sends messages.

**The other encoding.** A format of Ernest's own, a constructor written as its position in its type, would put no atom on the wire and owe the host nothing. It would be written in Erlang, value by value against the type, where the external term format is the host's own and written in C. It is left out; a runtime on another host, or a measured need, would change that. Wikipedia's [comparison of data-serialization formats](https://en.wikipedia.org/wiki/Comparison_of_data-serialization_formats) lists the formats such an encoding would be weighed against.

### 2.7 Processes on a peer

In the proposal's section 6, *A spawn*, *A service and its key* and *Bindings*.

**A service is found by a typed key.** The proposal first found a peer's service by shipping a function that read one of the peer's top-level bindings. Three things were wrong with that. Naming the binding made the client's program depend on the service's module, so the client's node ran that module's bindings and started a service of its own, and no arrangement of modules avoids it, since the client needs the module for the message type. A function crossed to look something up, which needs the same function on both nodes and is the first thing to break where builds differ. And every binding of a peer was open to every peer. A key is a value that starts nothing, holds a name and a message type's hash, and crosses in place of code; a node offers what its peers may find, and nothing else is found. The compiler holds an offer to one message type, and the peer compares the hash at a find. It is a registry of a kind, which Ernest has otherwise refused: it holds what a program chose to offer, to peers alone, and on one node a service stays a top-level binding. It is what a reader who knows Erlang expects, a registered name on a node, with a type. Its price is a name the program chooses, so that two services under one name on one node clash.

**A later offer takes the earlier one's place.** Three answers were weighed for an offer under a name that is taken. Refusing it, as Erlang's `register` does, gives `Peer.offer` a failure every program must handle, and races: a service that restarts can offer itself before its node has noticed that the old process ended. A set of addresses under one key, as Akka's and Swift's receptionists keep ([`other_systems.md`](other_systems.md), *A-15*, *T-8*), makes a find answer a list the finder must choose from, which is the beginning of a cluster. Replacing cannot fail, has no race, and lets a new process take a service over from an old one, which an upgrade later needs. Its price is that two services which take one name by mistake do not clash loudly: a find through the first key answers "another message type" where the types differ, and where they are the same the second silently wins. Nothing withdraws an offer: it ends with its process, which is what a program means by it. And only a process of the offering node may be offered. An address of a third node's process would reach a node the finder may not list, and the offering node would have to watch the process across a connection to know when the offer ends; by the proposal's first rule for what comes after, it is refused now and may be allowed later.

**Placement by load is two libraries and one function of `Peer`.** The plan had `Peer.nodes`, `Peer.runQueue` and `libs/balancer`. `Peer.nodes` stays in `Peer`, since only the runtime has the configuration, and answers the listed peers without the running node, which is no peer of itself. `Peer.runQueue` goes: how busy a node is has nothing to do with peers, and the host's measures, the run queue, the schedulers' utilisation, memory and disk, are a library of their own, `libs/load`, each a shim, the last two answering a failure where `ernest.conf`'s `measures` did not start the host's services. The balancer is a process, round robin unless given a measure, a measure a function to 1.0 that a program gives on each node by `Balancer.measure(f)`, which offers a measuring process under `Balancer.key`. Load is pulled, not spread: a pick draws two candidates at random and calls each, the two-choices rule, so a pick costs two calls whatever the number of nodes and nothing is ever stale or gossiped. The library's own type of a place, this node or a peer's name, is fine for a library where it was not for the prelude. All of it is in MVP 3.0, as its last items, because the two libraries need nothing the proposal does not give and are the first real programs on it.

**No standing address in `Peer`.** An address that finds its service again after the service's node is started again was weighed for `Peer` and left to a library. Every piece of it is a program's already: a process on the holder's node that forwards what it is sent, holds the peer's name and the key, monitors the service and finds it again when told, held through `via` so that the holder has an `Address(m)` like any other. What the runtime knows adds nothing to it. It is a policy, and policies differ: what to do with a message sent while the service is gone, how long to wait before finding again, whether to tell the holder; `Peer` would pick one for every program, a library picks one and can be replaced. And it hides a restart, which the building block makes visible, so a program should choose it. `restarting` is the counter-example, a fault hidden behind a kept address in the prelude, and differs in being the runtime's own capability, the process keeping its address, where a standing address is a second process that forwards. Where every program with peers turns out to need it, and one policy fits all, it moves to where `restarting` is.

**One failure type, with a text in `Refused`.** `Peer.Failure` serves a find and a spawn both, as `Io.Error` serves every operation on a file, though a find never meets `NotLoaded` nor a spawn `NotOffered`: two types would repeat four constructors, and a program writes `_` for what its operation cannot meet. `Refused` carries a text, since a program cannot act differently on which of the protocol, the build, `ern` or OTP differed, only report it, and a text leaves room for a later hello to refuse for more without a new constructor, which the proposal's second rule for what comes after asks. `OtherType` and `NotLoaded` are named for what they will also mean later: a service at another version, and code the peer does not have.

**A spawn and a find answer a value, and take a time.** A spawn on a peer first faulted its caller where the peer was out of reach, and waited with no clock of its own. Both are changed, for four reasons. A fault says that the program is wrong, and a peer out of reach is no mistake of the program's: it is what a program of several nodes is written to meet, by trying another node, by waiting, or by telling its user. A process that faults can do none of these, and only a process that monitors it could. A find answered a value for the same condition, so two operations that wait on one peer failed in two ways. With no time, a spawner waited the 45 to 75 seconds the detector takes to find a silent peer, and for ever on a peer that lived and did not answer, which a gateway held up behind a slow function of an adapted address can be. And every other wait on a peer has a time, which `Address.call` takes as its last argument too. What stays a fault is the program's own mistake: a function that captured a value that may not cross is wrong on every run, and its own node finds it before anything is sent. A function whose bindings the peer did not run is answered as a value, though the program is where the mistake is: the spawner cannot know which entry point its peer was started from, a program can choose another peer, and a later milestone may run the bindings, so that a failure becomes an answer and breaks no program. The price is a `match` at every spawn on a peer, where a local `spawn` has none. And a spawn whose time ran out may have started its process, as one that lost its connection may (the proposal's section 5, point 3). Erlang went the same way: its `spawn/4` gave a useless pid for a node out of reach, and `spawn_request/5`, which came later, answers with the pid or with an error, `noconnection` among them. It has the same hole: a request that its caller abandons may still create its process.

### 2.8 Open questions

**Limits, and where they are set**

- The limit of a connection's outgoing queue. Proposed: 64 MB. The thinking keeps the teardown at the limit, the limit a generous constant (section 2.3). (*P1*)
- How long a spawn waits for a connection and for the peer's answer, and what a timeout or a loss during the wait faults with. Proposed: 5 s for a first connection. It meets the delay before a connection is opened again, which can be longer (section 2.3, weakness 4). *Worked:* a spawn takes a time as its last argument and answers a failure as a value, and so does a find (section 2.7, *A spawn and a find answer a value, and take a time*). The wait ends in one of four ways: the peer answers, the dial fails, the connection is lost while it waits, or the time runs out. A dial that fails and a connection lost during the wait are one failure, that the peer is out of reach: the caller cannot tell the two apart and has no use for the difference. A spawn with no clock of its own was weighed first and left: a peer that lives and never answers held its spawner for ever, a program that wanted a bound had to spawn from a helper process and wait on it with `receive` and `after`, and Appendix E.0's shape rule 8 has a function that waits without a limit say so in its name, which `Peer.spawn` does not. (*P2*)
- The heartbeat's interval and timeout, when too short a timeout makes a brief interruption a loss, and a watcher that replaces a process still running then has two. Proposed: 5 s and 15 s. The thinking takes Erlang's instead, 60 seconds in four intervals, a loss costing more here, as a constant (section 2.3). (*P3*)
- The backoff of reconnection. Proposed: doubling from 100 ms to 30 s. The thinking keeps the numbers, draws each wait at random below the delay, counts a connection lost young as a failed attempt, and has a demand wait for the delayed dial (section 2.3). (*P4*)
- The largest frame. Proposed: a larger payload in chunks, never interleaved with another's, with heartbeats between them, so that a large frame causes no false loss. The thinking sends no chunks: a sign of life is bytes arriving, and a value that cannot fit the outgoing queue faults the operation that would transport it (section 2.3). (*P14*)
- Where these limits are set: constants of the runtime, documented with the wire format (§10), or keys of `ernest.conf`. The thinking makes them constants of the protocol, and a number a key when a deployment shows that it must differ (section 2.3). (*P16*)

**Loss, and a peer that returns**

- How a node keeps a loss terminal when the lost incarnation returns, directly or in an address a third node hands over: by refusing it until the peer restarts, or by keeping only the old addresses dead, which the wire form cannot tell from new ones. The thinking has left both: an address outlives a loss, and only a restart of its node ends it, which the incarnation tells (section 2.3). (*P5*)
- Whether a watcher must tell a lost peer, whose process may live on, from a fault by more than the cause `peer lost`; `Reason` would gain `Unreachable`. §10 requires the reason to be distinguishable from every other, which a process calling `fault("peer lost")` breaks as the report stands, so the answer changes §10 or §9.3. The plan's MVP 3.0 holds it. The thinking inclines to `Unreachable`, since a node can meet the process again (section 2.3). (*P6*)
- What `site` has the `Down` a watcher's node makes on a loss, for a process it did not spawn: one the peer sends when the monitor is set, or the empty string, which §6.9 gives `Unknown` alone. *Worked:* the empty string, always. With `Unreachable`, `site` is empty as it is with `Unknown`, by one rule: where the node that makes the `Down` does not have the process's own word, it says nothing of where the process was spawned. Nothing is sent when a monitor is set: an answer to every monitor, and a string kept for each, would serve a diagnostic alone. A program that must know which process it lost has `process` in the `Down`, which compares equal to the one it monitored. A watcher that spawned the process itself loses a line it wrote, and keeps it beside the process where it wants it. (*P7*)
- What a monitor of an address whose node is absent from the peer table answers, `Unknown` at once or `Fault("peer lost")`, and what a `send` to one does, which the report does not say. *Worked:* a node absent from the peer table is a peer out of reach, and behaves as one whose dial fails, only at once. A `send` and a `kill` do nothing, a `monitor` answers a `Down` with `Unreachable` at once, and a call ends at once. A fault of the sender would be loud, and would end a process for a line missing in a configuration; `Unknown` would say that the process is dead, which is not known. §6.2's list of the one silence, which has a message dropped whose peer is lost, says out of reach when this is decided, and so covers both. A `send` to such an address then vanishes though the cause is `ernest.conf` and not the network; a monitor or a call on the address shows it. Reaching such a node would take a network address carried in the address as a hint, which stays among what is left out (*P21*). No function tells a program that an address's node is absent. A `monitor` or a call on the address already answers `Unreachable` at once, and a check beside them would be a second way (principle 2); a program can do nothing with the difference between absent and out of reach, which is the operator's, read from the two nodes' `ernest.conf`. A program that must know which node an address's process runs on, to place work near it, would change that: a function from an address to its node's name would answer this too. (*P8*)
- What becomes of a process a peer starts after its spawner has stopped waiting. *Worked:* there are two cases. In the first the connection is lost while the spawner waits, and the peer had started the process. Nothing is added for it: a peer that killed a process whose answer it could not deliver would have to know whether the answer arrived before the loss, which it cannot. In the second the spawn's time runs out while the connection lasts (*P2*), and the answer arrives at a node where no one waits for it. That node kills the process the answer names: the spawner was told that no process came, and the node makes that true a moment later, instead of keeping a process that no one can reach or stop. Erlang does the same for an abandoned spawn request that was linked, with the exit reason `abandoned`. What it costs is a row the node keeps from the moment a spawner gives up until the answer arrives or the connection is lost. For both, three things are stated. A spawn that fails with the peer out of reach, or with its time run out, says only that no answer came, never that no process started, as a call that ended without an answer says nothing of whether it ran. Such a process runs as any other and belongs to no one (§6.9); the addresses it captured reach their processes again once the nodes connect again, so what it sends them then arrives. And a spawn frame not yet handled when the loss is run starts nothing, no frame of a lost connection being handled after it. The guide's rules for two processes where one was meant cover the rest (section 2.3): a spawn that may be tried again is of work that may run twice, and a worker watches whoever it works for. A worker that does not runs on, as any process nobody watches does. (*P18*)
- What a long-serving service's clients on other nodes do at a loss, and whether a library finds the service again for them and monitors it again (section 2.3). *Worked:* an address outlives a loss, so a client writes nothing for one. It finds its service again only where the service's node has been started again, which a monitor tells: `Unreachable` at the loss, and `Unknown` once the node is back at another start. A library does that for it, a standing address, which the proposal leaves out of `Peer` (its section 10).
- The six weaknesses of loss and reconnection, and the two things it does not solve, each worked in its turn. Section 2.3 lists them.
- What a `monitor` answers while its process's peer is still out of reach. *Worked:* a `Down` with `Unreachable` once the dial has failed, and at once where the node is absent from the peer table (*P8*), so that a program that monitors again in a loop is paced by the dial's delay (section 2.3).

**Calls, order and deadlock across nodes**

- How a `Reply` crosses, and how a caller learns that a callee on another node ended or restarted before it answered, since §6.9 tells no monitor of a restart. *Worked:* a `Reply` crosses as the caller's node and an identifier private to the call. The answer comes back in a frame addressed to that identifier, and the caller's node checks it against the answer's type, hands it to the waiting call, and discards it where no call waits, as §6.6 has a late answer discarded. The callee's node watches the call as it watches a local one: it enters it among the calls waiting on the callee, in the same table and under the same rule that ends a local call when the callee ends or restarts, and tells the caller's node when the call ends other than by an answer. So the caller learns of a death and of a restart in one way, and §6.9's rule stands, the watch being the call's own and no monitor. The answer's frame is the one new frame: the watch travels as the monitor, demonitor and down frames do, marked as a call's, so that its down may also say restarted. A loss ends the call as it ends any conversation: `Address.call` returns `None`, and `Address.callForever` faults with the peer out of reach. A call to another node then costs four frames where a send costs one, which is what Erlang's own call costs; the watch folded into the request's frame would halve it, and is measured before it is built. A request handed on is watched only where it was sent first (§6.6), and handed to a third node it is answered from there. (*P10*, *P20*)
- Which process applies an adapted address's function on the node that made it, when a peer's message arrives for it: whether a sender's order survives it, and what a function that does not finish does to the connection it arrived on. *Worked:* the connection applies it, in the order the frames arrived, and delivers the result to the target. Every sender's order then survives, whichever addresses it sent through, adapted and plain alike. A helper process for each adapted address would lose the order between two addresses of one target and cost a process for each; the target applying it as it takes the message would keep the order, but the host cannot put an adapted message back in its place in a mailbox. A fault in the function is the target's (§6.5), delivered in the message's place in the target's mailbox, as §8.4 delivers a bad message's fault. A function that does not finish is the detector's: where nothing has been delivered in four intervals while deliveries wait, the connection is lost and both ends run the loss, as where bytes wait to be sent and none leave (section 2.3, weakness 3). A slow function then delays everything from that peer, where on one node it delays its own sender alone: the connection stands in for all the peer's senders, a frame not saying which process sent it. The applying runs beside the reading, so that a slow function does not keep the connection from seeing bytes arrive: one more process for each connection, and never one for each address. (*P17*)
- Whether the unbroken prefix becomes a sentence of §6.4 before anything relies on it. The plan's MVP 3.0 holds it. *Worked:* it does, when MVP 3.0's rules go to the report. The design leans on it: the teardown at a full queue was kept to hold it, and a rule the design relies on is the report's to state. The wording to bring: "Between nodes a message is never dropped alone: where one is dropped, the connection is lost, with all that waited to be sent." Its unit is the connection: what is sent after the nodes connect again arrives, so a loss can leave a hole (section 2.3). It promises the sender nothing, as §6.2 says of `send`: the prefix is what the receiver relies on, no gap and only an end. The checker holds the same sentence as one of its invariants (section 2.3, weakness 6). The receiver is not told where the sequence ended. Monitoring the sender, it learns by a `Down` with `Unreachable` that it ended, and not at which message; a protocol that must know counts its messages or acknowledges them. (*P19*)
- How a node's deadlock check (§8.6) learns what peers can still deliver: that a process it spawned on a peer has ended, that no message is in flight to or from a peer, that no remote process holds one of its addresses or waits on one of its calls, and that no monitor waits on a remote process. By frames of their own, or does a node with a connected peer never declare a deadlock? *Worked:* a node that listens for peers declares no deadlock. Work can always reach it from outside: a process on a peer that holds one of its addresses can send at any time, and a peer can spawn a process on it whenever it likes. A worker node whose `main` only waits, so that peers can spawn work on it, is otherwise a deadlock while it is idle, and must not be ended. §8.6 already holds a listener with a pending accept to be something that can still deliver. A program started without a configuration has no peers and no listener, and keeps the check as it is. No frame is added to follow what peers hold: knowing that no remote process holds an address of this node's is the collection of garbage across nodes. §8.6 gets shorter when this is decided, its sentences on a connected peer, and on a process spawned on a peer counting as a computation, giving way to the one rule. A program spread over nodes whose processes all wait on one another then hangs, and nothing says so, as in Erlang; a program that must notice puts deadlines on its calls. (*P9*)

**The wire**

- How values in the external term format are decoded so that no peer creates an atom, when a safe decoding refuses an atom the receiver lacks, and a constructor the receiving code never names may be one. *Worked:* the host's safe decoding, which creates no atom. The worry does not hold. The runtime's description of a type, which the checks at the foreign boundary already use, names every constructor of the type, those the receiving code never names among them, and §8.7 has the type on the node before any of its values is decoded. So every atom of a well-typed value exists before the value is read, and an atom the node lacks proves the value ill-typed: the frame is faulty, and the connection is torn down as for any faulty frame. The decoded value is not checked further. The address's type hash was checked, and for the rest a peer is trusted, as it is for code (section 2.1); a full check of every value would about double what receiving costs. A faulty peer can then send a value of the wrong type made of known atoms alone, which is not caught as it arrives, and the receiving process faults where it meets it. The emitter has to make a process's mailbox type description reachable at run time, for this and for the hash in an address, which is MVP 3.0's work. On Erlang's distribution the host decodes and has no safe decoding, so an unknown name becomes an atom and is not refused (section 2.6, *Atoms*). (*P11*)
- Who draws a spawned process's `LocalId`: the spawner, or the peer in its answer, since the spawner waits for that anyway. *Worked:* the peer draws it. A node draws the `LocalId`s of its own processes and no other node's, by one rule: the peer draws a spawned process's as it does for any process whose address first leaves it, and sends it in its answer. Drawn by the spawner, a node would have the names of its own processes from two sources, and a duplicate from a faulty peer to refuse. The spawn frame carries a number of the spawner's node, which the answer repeats, to pair the two: a small count for the connection, as a call's identifier is. So no address of a process exists before the process does. Nothing is lost by it, the spawner waiting for the answer in any case (*P2*). (*P12*)
- What identifies a function between two nodes of one build in MVP 3.0, before content addressing, and how the hello carries the build's identity, so that a peer of another build is refused with an error naming MVP 3.1. *Worked:* in MVP 3.0 no code crosses. Every node is started from the same compiled program, and the hello proves it: it carries one hash of the build, over the compiled modules of the program and of the standard library, as the toolchain already hashes its own modules (§11.1), and a peer whose hash differs is refused with the error that names MVP 3.1. A function is identified as the host identifies it within one build, by its module, its place in the module and the values it captured; the same build has the same modules, so the reference means the same on both nodes. The have, want and code frames wait for MVP 3.1, with a hash for each definition, the hash modules and the loader. MVP 3.0 builds and proves the rest of section 2, connections, loss, addresses, messages, calls, monitors and the spawn frame, and MVP 3.1 puts a function's hash where its reference was and adds the code frames behind the same spawn. So the protocol is tested without the loader, and the loader comes onto a protocol that works. Two hashes exist in MVP 3.0: the build's, in the hello, and the one in an address, which is taken from the mailbox type's description at run time until MVP 3.1 makes it the type's own. Every node then needs the program on its own disk, and one that receives its program from a peer waits for MVP 3.1. The same build is strict: one changed line makes two builds that refuse each other, and a deploy stops and starts every node (section 4.3). The plan's MVP 3.0 speaks of a spawn that ships code, wording to correct when this goes to its owners. (*P15*)
- Which versions the hello carries and checks, the back end's, the runtime's and OTP's, and which differences between nodes are allowed. *Worked*, for MVP 3.0: the hello carries the `NodeId`, the incarnation, the protocol's version, the build's hash (*P15*), and the versions of `ern` and of OTP. No difference is allowed: two nodes connect only where the protocol's version, the build's hash and the two versions are all equal. The versions travel as fields of their own and are not folded into the one hash. The check is the same either way, and sent apart the refusal says what differs, another build of the program, another `ern` or another OTP, which costs a few bytes and saves an operator a search. Nothing is then upgraded node by node in MVP 3.0, an OTP patch included, as a deploy stops and starts every node. Which differences MVP 3.1 allows stays open and is section 3's: once code carries its own hashes, nodes of different builds cooperate through the hashes they share, the build's hash leaves the hello, and what must still be equal is what section 3.2 lists as outside the hashes. (*D15*)

**Processes and resources of another node**

- What `Process.info` answers for a process on another node, of which Appendix E.21 says nothing. *Worked:* `None`. The runtime answers for its own node's processes alone, from its own record of them, and no frame is added. E.21 gains the sentence when this is decided: `None` where the process has ended or is another node's. A program that wants the answer asks on that node: it spawns a function there that calls `Process.info` and sends the result back, a `Process` crossing as it does. `None` then means ended or elsewhere, and a program tells the two apart by the node it had the process from.
- Whether the address of a socket, of a listener or of a program the runtime started, a process the runtime started for a resource, crosses to another node, of which Appendix E.18 says nothing. *Worked:* it does not. A resource is bound to its node, as a foreign value is (§3.8): the address of a process the runtime started for one does not cross, nor does an address adapted around it, and transporting it faults the operation that would transport it, with a cause of its own, found where the address would first leave the node. Crossing, it would let a process on another node write to a socket by a call across nodes for every write, and own it, so that §6.9's rule that a resource ends with its owner would have to hold across a loss. A program that wants another node to use a resource puts a process of its own before it, which owns it and takes the peer's messages. A reader who knows Erlang expects as much, a port being of no use from another node. No input or output through a peer then comes for nothing, and who owns a resource stays one node's matter.

**The plan's decisions that the phases need**

- Where a node's configuration and its key are read, which the plan's MVP 3.0 holds. *Worked:* only where `--config-dir` names the directory. The default, `./.ernest`, goes. A directory someone else controls, a cloned repository among them, would name the peers a program trusts, and a trusted peer may start any function on the machine; and `ern config` wrote the node's key into a working tree, where a commit can take it. `ern config` requires the option as well. As a node starts it checks the directory and the key, and refuses to start where others can write the one or read the other, saying which, as `ssh` refuses such a key. Every node is then started with one more option. A default for each user would spare it, and one user runs several nodes, each with its own key and address.
- When a module's top-level bindings run on a peer, which the plan's MVP 3.0 holds with what §8.7 leaves open of a peer's initialization. *Worked,* for MVP 3.0: a node runs at its start what §8.5 says, the standard library and the modules its own entry point depends on, by one rule for every node. A function spawned on a peer runs there only where the bindings it depends on have their values there; otherwise the spawn faults its caller, with a cause that names the module, and `Peer.find`, which answers and does not fault, answers a failure of its own, named with `Peer`'s section. Nothing is initialized because a peer asked. On first use, as §8.7 has it, leaves open what two processes see that use a binding before it has a value, whether a fault is kept or run again, and which process runs the initializer; every module's bindings run on every node would open a listener, or start a service, on nodes that were never meant to. So a node that is to serve a module names it in its own program, and what a node starts is seen in that node's own text (principle 3). Nodes that run one entry point initialize the same modules and are not touched by this. The question returns in MVP 3.1, when a node can receive a module it never had, and the plan's list applies there; §8.7's sentence on first use is rewritten to match when this goes to the report.

## 3. Code by its hash

### 3.1 Identity

**What is hashed.** A definition's hash is the SHA-256, by `crypto:hash/2`, of its canonical form: the version of the format first; each external reference as its qualified name and the hash of what it names; local variables numbered by position; the hashes of the types it uses; named fields in declared order, and construction in source evaluation order (§8.7). Comments and layout are not hashed. Mutually recursive definitions are hashed as one group. The toolchain has no IR today: the emitter goes from the typed tree to Erlang's abstract format in one pass, and whether an IR is added or the typed tree made canonical is the first decision of the plan's MVP 3.1.

**Hash modules.** Each hash, and each group's, is compiled to a module of its own on the host, named `ern#` and the hash in base32. A hash module never changes.

**Types.** A type's hash covers its qualified name, its parameters by position, its constructors by name in declared order, each constructor's field names, and the hashes of its fields' types. An abstract type's hash also covers the types of its module's exported declarations. So renaming a type or a constructor, or moving a type to another module, is a change of protocol between processes. Two unrelated codebases with a type of one qualified name and definition share its hash.

**Names.** The `.ern` files are the source of truth for names. Each build resolves every name afresh and writes a table from name to hash, derived and never edited: no operation points a name at a hash, and no source names a hash. The build keeps every hash it has built in a store that only grows. A definition changes by editing and rebuilding. Its dependents get new hashes, and where a type changed they fail to compile until they are edited, so a build is never half migrated. At run time names serve entry points and debugging, and each node keeps a table from hash back to name. Names are local to a build, and nodes share hashes: nodes built from different commits cooperate through the hashes they share. Within one build a name has one meaning, and an old version still needed keeps a name of its own in the source.

### 3.2 What the hashes leave out

**What the hashes leave out.** Three things are not hashed and must agree across nodes: the hash scheme, checked in the handshake; the compiler's back end, on every node, whose version keys the cached binaries; and what hashed code calls by name, the host's built-in functions and Ernest's runtime, pinned for each deployment with the OTP version. The prelude's types and the standard library are hashed as a program's code is. Their foreign declarations are excepted, and are each node's own (§8.7).

### 3.3 A node's code

**One kind of node.** Each node has a cache of code keyed by hash: persistent, on disk and possibly filled at deployment, or volatile, in memory and empty at start. A program's code may be absent, and a node receives what it needs from its peers. The platform may not be absent: the host and its applications, Ernest's runtime and loader, and the compiler's back end. A diskless node can boot the platform over the network by `-loader inet` and `erl_boot_server`, which use no Erlang distribution and no TLS.

**The loader** stands beside the host's unchanged `code_server`, which keeps its table of loaded modules, its purging and its serialized loads. The loader's cache is ETS, from hash to code and compiled binary, and on a persistent node one file for each hash. It verifies first: the hash of incoming code is computed before anything else, and a mismatch rejects it. It compiles to a binary by `compile:forms` with `deterministic`, and caches the binary under the hash, the back end's version and OTP's. Every unit lists the hashes it references, so a fetched closure is known to be complete before any of it is loaded. The closure is loaded at once, all of it or none, by `code:prepare_loading/1` and `code:atomic_load/1`; the first does the heavy work in the calling process, so the one `code_server` should not become a bottleneck, which the plan's MVP 3.1 measures. Nodes run in the host's embedded mode, which loads nothing from the code path on demand, so a missing module is an honest failure.

**Have and want.** Only a spawn on a peer ships code (§8.7). Before a spawn frame's payload is decoded, the sender lists the hashes, of code and types, that the function references transitively, its captures included. The receiver answers with those it lacks, and the sender sends them. The receiver verifies, compiles and loads them. Only then is the payload decoded, since a value cannot be read before its types are loaded, and the process starts. So the whole closure is present before anything runs. A failed exchange is a resolution failure, which faults the caller of the spawn.

**Risks.** Normalization, where an error costs most: two hashes for identical code or, worse, one hash for different code. And the time to compile when a node receives much code at once, typically as it starts.

### 3.4 The memory of code

**Unloading.** A hash may be unloaded, and removed from the cache, when no name table on the node refers to it, no loaded hash depends on it, and `code:delete/1` followed by `code:soft_purge/1` succeeds, the host checking that no process runs its code or holds a function of it. It is tried after a configured idle time. The host's check sees the closures in each process's state, so nothing counts references.

**Atoms and lambdas.** Every module's name is an atom, and the host never collects atoms; its limit is about a million. The host's table of lambdas grows the same way, an entry for each lambda of each version loaded, up to 524,288, and unloading frees neither. So a long-lived node that receives many versions leaks both. The note's answer is that a node counts its atoms and, above a threshold, drains and restarts: every process on it dies, and every address to it is dead. In reserve it holds a hybrid: incoming code is interpreted first, and compiled to a hash module only when hot, so that cold code costs no atom.

### 3.5 Findings

What reading the two notes' design beside this note's thinking shows of the hashes and of a node's code. Each is a finding to weigh, not a verdict.

**A rename is a change.** Section 1 counts a rename that costs nothing among what Unison's hashes give. There code is kept as hashes: a definition refers to another by its hash alone, a name is a label on a hash, and a rename moves the label and changes no code. Ernest's source is text, so a rename edits the definition and every use of it. What it could spare is the hashes, and as section 3.1 and §8.7 stand it spares none. A type's qualified name is in its hash by decision, being what makes two types of one shape two types, so renaming a type, a constructor or a field is a change of protocol. A function's follows from the normal form, which keeps each external reference as its qualified name beside the hash of what it names: renaming a function, or moving it to another module, changes the hash of every definition that refers to it, and of all that refer to those. The deploy plan then reports each service that reaches the function as changed, an upgrade in place of each, where no code changed; for a function of the standard library, every service. Whether the renamed function's own hash changes is *D8*. The hash of what a reference names already says what is called, so what the name beside it is for is to be found before it is kept. Three things lean on it. A foreign declaration is found on a peer by its qualified name (§8.7). A top-level binding is evaluated once on a node for each hash of its definition (§8.7), so two service bindings of one initializer, `let a = spawn(worker)` and `let b = spawn(worker)`, are two services where the program starts and one on a peer, unless its name is part of what a binding is. And a spawn's site and a fault's trace name a declaration, which a node's table from hash back to name answers only while a hash has one name, as *D11* asks of two definitions that differ in a line. A build or a `:load` is the other act: the name stays and is given a new hash, the table from name to hash written afresh (section 3.1, *Names*), where a rename gives a hash another name.

**Positions in the hash.** The distribution note asks whether source positions are hashed (*D11*), since a spawn's site names its line. The deploy plan weighs on it: with positions hashed, a line added above a definition changes its hash, and the plan reports every definition below an edit as changed.

**The order in a type's identity.** The plan's MVP 3.1 asks whether a type's identity holds the hash of its `compare`. The state handed over at an upgrade weighs on it. With it, a new `compare` is a new state type, a change of protocol, and declared. Without it, an ordered set carried through the upgrade is misordered, and nothing says so.

**The platform is outside the hashes.** The deploy plan compares hashes, and the hash scheme, the back end, the runtime and OTP are not hashed: a hello whose versions differ is refused. So a new runtime, or a new OTP, is no upgrade in place. Each node restarts, every process on it ends, and state leaves the node first or is lost. The standard library is hashed as a program's code is, so a release that changes one of its functions changes the hash of everything that uses it, an upgrade in place of every such service at once; and a change to a library type that protocols carry is a change of each of those protocols.

**What holds old code.** Code is collected when nothing refers to it, and several things refer in ways the thinking added or the notes left open: the function `restarting`, or a supervisor's child, restarts into; the old loop a rollback keeps; a translation, which holds the old protocol's types for as long as its process lives or its view stands in the source; a binding's evaluation on a node; and an adapted address, whose `{hash, env}` a peer may still send to after the node that made it would unload the code (*D14*). Each needs its answer before "old code is collected" is true.

**A drain and restart ends the service that never ends.** An upgrade in place loads new hash modules: an atom, and its lambdas, for each definition whose hash changed, its dependents included. The node that upgrades without a stop is the one that never sheds them. The distribution note's drain and restart is then the very outage the upgrade was to avoid, on a schedule the leak sets, and the plan's MVP 3.1 already questions it by the rule that memory no collection reclaims is fixed at its cause. So the leak is the floor under the whole story. It wants a number first: how many definitions change hash in an ordinary deploy, and so how many deploys a node takes. Then its cause, in three directions, none tried against the host: whether a module's name must be the hash, or can be drawn from names reused once a module is unloaded, with the node's registry from hash to module; whether a closure in a hash module must be a lambda of the host's, since a function already crosses as `{hash, env}`; and the hybrid, which moves from a reserve toward the main road.

## 4. Code change in running processes

### 4.1 Loading and upgrade in place

**The objection.** A typed language, it is said, cannot have Erlang's code loading. Of the mechanism that is true. Erlang swaps a module under every process that runs it, a state takes a new shape in `code_change`, and messages of any shape keep arriving: the types of live data and of messages in flight change with nothing to check them against. Of what the mechanism is for it is not true. A running system upgraded without a stop, old and new code side by side, has a typed form, and §6.10 is a start of it: a process takes a message in its own type that carries the new loop, checked against its mailbox type before it arrives, and carries its state over by a typed function, Erlang's `code_change` checked. What a typed process cannot do is change its mailbox type silently, since its clients hold an address of the old type. In Erlang the same mismatch shows at run time, as messages nobody matches; Ernest would make a program say how old clients are served, as a function from the old messages to the new, and with that function the type may change in place (below).

**Loading never disturbs running code.** A hash module never changes, so loading only adds. A process keeps the code it runs until its own upgrade case moves it, or until it ends, so loading new code is as safe as starting a process. BEAM's limit of two versions of a module, which kills a process still in the old one on a third load, does not arise. The cost moves to unloading: code stays loaded while any process, message or value refers to it, and memory no collection reclaims is a defect, so code is collected.

**A load moves names, and compiled code holds hashes.** A name is resolved to a hash when code is compiled, never when it is called. A load is a build's result brought into a running node, by a deploy or by the shell's `:load` and `:reload`. It gives a new hash to each definition that changed, and to each definition that refers to one of those, in whatever module, since a definition's hash covers the hashes of what it refers to. The rest keep theirs, and nothing is loaded for them. A hash is a definition's or a group's, and a module has none. The table from name to hash, the build's and a shell session's, then gives each of those names its new hash. What is compiled from then on, a shell input or a module built against it, reaches the new code. What was compiled before holds the old hashes and runs the old code, a running process and a function held in a value among it. Erlang's call by a module's name finds the latest version at each call, and the shell's reload leans on that today: it compiles again a module that uses a reloaded one only where the interface changed (§11.2). Under hashes a definition that refers to a changed one always gets a new hash, linked again where its text did not change. A service binding is no exception: one whose loop changed is another binding, and code compiled after the load reaches a second service (section 4.3).

**An upgrade arrives as code does, by a spawn.** A function does not cross nodes in a message (§3.11). A process on another node is sent its upgrade by a process spawned on that node, to which the spawn gives the new function (§6.10).

**An upgrade in place is not a restart.** It is a tail call. Nothing the process asked the runtime for is cancelled, its alarms, monitors and subscriptions; its mailbox is kept; and the replies it holds go on in its state. A restart begins afresh (§6.9).

**The service that never ends.** A short-lived process ends on its old code, and its successor begins on the new. A long-serving service never ends, so it sees new code only through an upgrade case of its own; the runtime cannot migrate a state it cannot see, which lives in the loop's arguments. A process whose type has no upgrade case is replaced instead. A change of logic behind the same protocol upgrades in place with no outage: the address stays, and what arrives meanwhile waits in the mailbox. It is the common case of a fix, and not of a service that grows: a feature is most often a new message, so a change of protocol is ordinary and has to be as safe.

### 4.2 A change of protocol

**A change of protocol is an upgrade in place, with a translation.** Three answers were weighed and left. A forwarder, a second process that holds the old protocol and hands each message on, is a loop written and kept by hand around the one thing that cannot be avoided, the function from an old message to a new one. A rule that a type with one more constructor is accepted where the old one is needs a subtyping the language does not have (principle 5). And a service whose protocol may never change is too little. What is left is that function alone. The process stays, as in any upgrade in place: its identity, its state, what it holds and what it asked the runtime for. Its mailbox type changes through one gate, under the working name `become`: `become : ((old) -> new, () -> Unit with new) -> Unit with old`. It takes the translation and the new loop, and runs the loop in place of what called it. It is the one place a process's mailbox type changes, and it cannot be called without the translation. Its result type is `Unit` and not a type variable, though it never returns to its caller, so that §6.6 holds it to its replies (section 4.3). An `Upgrade` case of §6.10's shape carries it with no change to the old protocol: the `next` it hands over has the old mailbox type, and is a function that calls `become`.

**Old addresses keep their meaning.** An address made before the change is an address of the old protocol, and what is sent to it is translated by the service itself as it takes the message. So are the messages waiting in the mailbox at the switch, and what the service's own alarms and monitors deliver, whose `wrap` functions were written to make old messages: one rule, that what is addressed to an older protocol passes through the translation. A translation that faults is then the service's own fault, as a fault in its loop is. A process that has changed its protocol twice translates through both, for as long as the build holds both (section 4.3).

**The translation is total.** The inclination is that it answers a new message for every old one, and never nothing. The reply rule then does the rest (§6.6): the translation is pure and cannot answer, and a reply is consumed exactly once, so each old request's reply must go into a new message, and no old caller is dropped. Where the answer's type changed, the reply is adapted as an address is, by a `via` for replies of `via`'s own shape, `(Reply(old), (new) -> old) -> Reply(new)`: answering the adapted reply answers the old caller with the converted answer. A request the new protocol retires still has a reply to place, in a constructor the new service answers with the old answer type's failure; an old request whose answer type has no failure cannot be retired while an old client may ask, which is the promise the old protocol made. So a service's answers hold a failure from the start.

**Nothing dies, so nothing is told.** No monitor sees the change, as none sees a restart (§6.9); a call waiting on the service waits on, since its callee has not ended; a socket the service owns is still owned; `Process.fromAddress` gives one process for an old address and a new one; and `kill` through an old address kills the service.

**An additive change** is the translation that maps each old constructor to its namesake. It is written, and so seen (principle 3), and the deploy tool, which holds both builds, could write it.

**A forwarder written by hand** remains possible in the language as it is, and is what a program falls back on where a point of this proves wrong.

**A discipline around upgrade types.** An upgrade case each service writes by hand is forgotten, or written in a shape of its own, and then nothing upgrades services alike. A fixed shape lets a supervisor, the shell or a tool upgrade any service, as OTP's system messages reach every behaviour, but visibly, in each protocol's type (principle 3). One form is a library type over the language's own: a service's mailbox `Service(Msg, State)`, its messages and an `Upgrade` that carries the new loop as `(State) -> Unit`, which adds no concept (principle 5). A rule of the language that every service binding holds one would be stronger, and would bind services that never change.

**The state as a schema.** In that form, the state's type at the switch is the service's contract with its later versions: the new code is handed a `State`. What it does with it is its own. Behind the same protocol a new loop holds any state it likes inside and hands over a `State` at its next upgrade. With a change of protocol the new `Service` type names its own state, and the function that calls `become` carries the old state into it, as `migrate` does in §6.10.

**A restart after an upgrade.** `restarting(limit, f)` and a supervisor's child hold `f` by its hash. A service upgraded and then faulting would restart into the `f` it was spawned with, and the fix would vanish at the first fault. Erlang's restart calls the start function by name and finds the new module. An upgrade would have to replace what a restart runs, so the discipline reaches `restarting` and `Supervisor`, not the loop alone. After a change of protocol it is no longer a matter of keeping a fix: a restart into the old function would run a loop of the old mailbox type under addresses of the new one. `become` runs its loop in place of the old stack, the `restarting` function the old loop ran under included, so the new loop states its own: `become(translate, restarting(limit, fn() = loop(state)))`. That is written and seen (principle 3), and the runtime replaces no function behind the program. The count of restarts begins anew. A supervisor's child states its own the same way, through `Supervisor.child` again; a child is known to its group by its process, which `become` keeps, so a join from a process the group holds keeps its place.

**Clients of two versions.** Clients that share a protocol type share its hash, and the service sees one type from all of them, whatever their own code's version. A client built against another version of the protocol holds an address of another type, and an address carries its mailbox type's hash, so no message of one version is read as the other's. Nor does such a client reach the service through its binding as the rules stand: its own binding is another binding, which starts a second service on the peer (section 4.3). The price is strictness. A type's hash covers what it refers to, so a change to a record deep in a protocol is a new protocol, and a change to a type many protocols share means replacing every service that carries it. So the discipline has a second half: a service's protocol types are small, stable and its own, not built from types shared across a program, and most changes are then changes of logic behind a stable protocol.

**Compatible evolution.** A second version that adds a constructor and is accepted where the first is, as protobuf's systems allow, would be an exception to "two versions of a type are two types", and a subtyping. It stays out: the additive translation above does its work, written.

**Where the thinking stands on a change of protocol**, on 6 October 2026. Settled means the thinking no longer weighs it; it is no decision of the report's until it goes to its owner.

Settled:

- A change of protocol is an upgrade in place: the same process, with a total translation from its old messages to its new, through `become` alone. No forwarder is written, no subtyping is added, and no protocol is fixed for a service's life.
- What is addressed to an older protocol is translated by the service as it takes it. Every old reply is carried into a new message, by the reply rule, and adapted by a `via` for replies where the answer's type changed. A retired request keeps a constructor that answers its old callers with a failure.
- Nothing is told of the change: no monitor, no waiting call, no owner of a resource.
- The new loop states its own `restarting` function and its own place under a supervisor. Its closure holds the state as it was at the switch, so a fault in the new loop runs it again from that state. That is the rollback a change of protocol has (section 4.3).
- `become` has the result type `Unit`, so a reply held where it is called is carried into the new loop or is an error (section 4.3).
- An old protocol is served for as long as the build holds its type and its translation, and no longer (section 4.3).
- On a peer, an address's hash says which protocol it is of, and a node accepts each protocol its process serves. After a restart of the service's node the old name is a view of the new service in the source, a service binding is matched by its name and protocol, and a second service is never started unseen (section 4.3).

Open, each in section 4.6: how a process tells an older protocol's message from its own on the host, and what `receive` does on intake; the `via` for replies, its name and how it crosses nodes; whether a join from a process its group holds keeps the child's place, read against `Supervisor`; how the tool tells a service to drop a protocol; what makes a binding a service binding for the matching rule; and `become`'s name.

### 4.3 Across builds and nodes

What reading sections 2 and 3 beside sections 4.1 and 4.2 shows of code change. Each is a finding to weigh, not a verdict.

**A service across two builds.** §8.7 gives a top-level binding the hash of its definition, with everything the definition refers to. A service binding refers to the loop it spawns, so a fix to the loop gives the binding a new hash. §8.7 says what follows: a binding whose definition differs from the peer's by hash is another binding, and code of the new build that names the service starts a second one on the peer, running the new version, beside the first. That is versions side by side, as designed, and it is replacement with no handover: the new service starts empty, and the old one runs on for the clients of the old build, with nothing to end it. An upgrade in place needs the opposite, code of the new build reaching the service that runs. As the rules stand it cannot name it: its own binding is another binding, and no source names a hash. Two shapes of answer are in sight.

- *The binding's identity changes.* A service's identity across builds is its binding's qualified name and its protocol's hash, in place of its definition's hash, so that the new build's binding is the running service wherever the protocol is unchanged. That gives a binding an identity unlike every other definition's (principle 2), and lets new clients talk to old code until the upgrade lands, which nothing in their text shows (principle 3).
- *The deploy tool bridges the builds.* The language stays as it is, and the tool does what it alone can, since it holds both builds' name tables. It finds the running service with the old build's code. It sends the upgrade with the new build's, the address captured as a value. Then it has the node take the running process as the value of the new build's binding, so that later code of the new build finds it and starts no second one. That adoption is a new operation of the runtime, checked by the protocol's hash, and no change to the language.

**After the service's node restarts.** The protocols a process has had live in the process, and a restart of its node ends it. The new build starts a service of the new protocol alone. A client of the old build on another node that finds the service again does so by `Peer.find`, which ships a function that reads the binding, and that function names the old definition's hash. As the rules stand the node fetches the old code and starts a second service of the old version beside the new one, empty, with nothing failing and nothing said. That is the worst of the outcomes, and it stands whether or not a protocol ever changes in place. Nothing can keep what the restart ended: the old client knows the service's name, its old definition's hash and its old protocol's hash, and the definition is gone on purpose, so the name and the protocol are all there is to find it by. Two answers follow, which go together. The new build serves the old name: the new service takes a new name, as its protocol does, and the old name stays in the source as a view of it through the translation, `let counter : Address(CounterMsg) = via(counter2, translate)`. And a service binding that shipped code names is matched on the peer by its name and its protocol where the definition's hash is unknown there: the same name and protocol is the peer's own binding, the view; the same name and another protocol is a failure `Peer.find` answers, the service being at another version; and a second service is never started. This is the first shape above, kept to the one direction in which its cost is small: an old client reaches new code through a translation the new build states in a line, where the worry was a new client reaching old code with nothing in its text. With the tool's adoption, a running service is one process under both builds' bindings, each at its own protocol. A node restarts for more than a fault, a new runtime or a new OTP among the reasons (below), so the view is in the source wherever old clients are to be served, and `become` takes the function the view is made with: one translation, used twice.

**The hash in an address is its protocol's version.** Section 2.4's address carries the hash of its process's mailbox type, and the receiving node checks it. After a change of protocol every old client on a peer would fail that check, and lose its connection as a faulty peer. The check becomes that the hash is of a protocol the process has had; the message is then decoded with that protocol's types and translated, as a local old client's is. No peer needs new code, and none is told. An adapted reply that leaves the node crosses as an adapted address does, the conversion applied on the node that made it. On the host a local address is a pid alone, and constructors of one name in two protocols are one term, so an address made after a change has to carry which protocol it is of; a process that never changes its protocol pays nothing.

**A rollback across a change of protocol.** Section 4.4's rollback resumes the old loop. After a change of protocol the old loop has the old mailbox type, and addresses of the new protocol may already have left the service, through `self()` or a binding, so resuming it would need the opposite translation, from new messages to old. What a rollback is for is the state, which a fault in new code must not lose, and that is had without going back: the function the new loop's `restarting` runs is a closure over the state as it was at the switch (section 4.2), so a fault runs the new loop again from that state, under the same mailbox type, with no address made wrong. A loop that keeps faulting meets its limit and its supervisor. What it handled between the switch and the fault is lost, as at any restart (§6.9). Going back to the old protocol is going forward: a later build whose translation runs the other way.

**A reply held when the protocol changes.** §6.6 excuses a path that cannot return from answering its replies, since a fault ends the process and every call waiting on it. A function whose result type is a type variable is such a path. `become` ends nothing, so a reply dropped there would leave its caller waiting, and `become` is given the result type `Unit`: it is then no such path, and the reply rule holds as anywhere. A reply held where `become` is called is captured by the loop handed over, which the rule already counts as handing it on, or it is the error of a reply not answered on every path. What is written after a call of `become` is checked and never runs, as after a loop that does not end.

**How long an old protocol is served.** A service that changes its protocol ten times would hold ten, and translate the first one's messages nine times over. The source decides, as it does for names (section 3.1): a service serves an old protocol for as long as the build holds that protocol's type and its translation. A later build that deletes them retires it. The deploy tool sees the deletion, since it compares the two builds, and tells the service at that upgrade to drop the protocol. From then on a message to it is one to an ended process, and a client that looks the service up by it is answered that the service is at another version. So an old protocol ends by an act a reviewer sees, the deletion of code, taken with the count of messages still translated from it (section 4.4), and not by a timer. Until then only its own clients pay for the chain.

**A changed protocol takes a new name.** A translation names the old protocol and the new one in one build. A type's hash covers its qualified name, and within one build a name has one meaning. So the old type cannot be the one renamed: under another name it has another hash, and the old clients' addresses no longer fit it. The new protocol takes the new name, `CounterMsg2` beside `CounterMsg`, and the old type stays in the source unchanged, with every type it refers to, for as long as the translation serves it. A protocol whose service must outlive the change is then not edited: a new type is added beside it.

**An upgrade case is a permission.** An address is the permission to send, so whoever holds a service's address may send its upgrade. A service would hand its clients an address of its requests alone, made with `via`, and keep the address of its whole protocol for what deploys it; `via` gives that with no new concept. On the wire an adapted address holds its target's address, so between nodes this narrows nothing that the trust in a peer has not already granted.

**MVP 3.0 alone upgrades nothing.** MVP 3.0 ships code between nodes of one build, and a peer of another build is refused. Until MVP 3.1 a deploy stops every node and starts every node, and everything in section 4 waits for the hashes.

### 4.4 In practice

Most production systems, Erlang's among them, do not upgrade in place. They start the new version beside the old, move the traffic and drain the old, with the state kept outside the processes. An upgrade in place serves where reconnecting costs: a telephone call, a chat or game server holding many connections, a trading gateway. So the thinking is to make the ordinary path excellent and the upgrade in place safe.

- **A deploy planned from the hashes.** For each service binding, by its name in the two builds' name tables: its definition and its protocol unchanged is nothing to do; its definition changed behind the same protocol is an upgrade in place; its protocol changed is an upgrade in place with a translation, which the plan asks for and checks is there. Erlang's `appup` files say this by hand. A tool that prints the plan before a deploy, and refuses what it cannot do safely, is worth more than a feature of the language.
- **A keeper.** A service built as a process that holds the state behind a small protocol that seldom changes, with the logic that changes often in processes cheap to replace, or in functions the keeper upgrades. Most deploys are then changes of logic. The guide would teach it as the ordinary way to build a service.
- **Rollback by default.** Where the new loop faults within a limit, the old loop resumes with the state it handed over. Across a change of protocol the new loop is run again from that state instead (section 4.3).
- **A restart follows the upgrade**, as in section 4.2.
- **The code's hash in `Process.info`**, so that a deploy lists the processes still on old code.
- **A protocol change run by the tool.** The tool checks that the new build holds a translation from each protocol a running service speaks, writes the additive one, and sends the upgrade. The service counts the messages it translates from each older protocol, so that an operator sees when the old clients are gone and the view may leave the source.
- **An upgrade tested.** Each build tested against the last release's: the old started, the plan applied, the state checked. A path that runs once a quarter decays unless a machine runs it on every commit.

The order the thinking suggests: the plan from the hashes and the code's hash in `Process.info`; then the upgrade in place with its rollback; then the change of protocol by translation.

### 4.5 The story

Not "hot code loading, but typed": that promises the mechanism, the part that cannot be typed. The story is about deploys:

> Ernest knows exactly what changed between two builds, down to each process's protocol. Before a deploy, it tells you which services upgrade in place without a dropped connection, which change their protocol and by what translation, and which are untouched. And the compiler guarantees that a client and a service of different protocol versions never exchange a message.

It is told only once it runs: a demo, a chat server holding many connections upgraded in place with none dropped, then a protocol change carried by its translation, the old clients served on, with the plan printed before each step. Its limits are stated with it: a service cooperates; a protocol change needs a translation, and a retired request an answer; strict hashes make a shared type ripple; a new runtime or a new OTP restarts each node; and a client on another node finds its service again after a loss.
