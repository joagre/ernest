# Ernest: Nodes, the reasons

Status: the reasons for nodes as designed through MVP 3.1, in the order of [`mvp3.0.md`](mvp3.0.md)'s section 6, kept in sync with the latest proposal that touches nodes; nothing here is normative, and the proposals state what this argues. Where MVP 3.0 and MVP 3.1 differ, a paragraph says so. The reasons for hashing itself, the exchange that ships code, a node's code and `Code` are [`code.md`](code.md)'s; what other systems do is [`other_systems.md`](other_systems.md); what the host showed is the experiment under [`experiments/`](experiments/erlang_distribution/).

## 1. The carrier

**Erlang's own distribution, with what hurts turned off.** The design first had a protocol of Ernest's own over TLS: a handshake, a heartbeat, an address that died with its connection, a sender that never waited. Weighed against what the host already has, its connections, its handshake, its ticks, its order, its monitors across nodes and its one-shot replies, that protocol was Erlang's semantics reinvented one piece at a time, each piece a surprise to a reader who knows Erlang and each one less tried than the host's. What hurt in the host's distribution could each be turned off or replaced by a rule: the mesh by a setting, the port-mapper daemon by a table, the cookie as the only proof of a peer by a TLS rule that accepts a peer by its listed key, and the sender made to wait was kept after all. The experiment tried every one of these on real nodes before the carrier was chosen, and tries each decision since that bears on the host. Nothing a program sees names the carrier, so another could take its place.

## 2. A node

**Neither of a node's names holds an address.** The carrier wants a name for each node, and TLS a name in each certificate, and a host name is what both expect. Ernest gives neither one. A node is its key: its name on the carrier is the key's hash with a constant after it, and its certificate's name is a constant that nothing reads. So every node computes the same name for a peer, a node that moves keeps its name, and no name has to resolve: the configuration gives the address. The experiment ran with certificates that name another host and another address, and once with nodes named by a name that resolves nowhere, and a peer was accepted by its key in each. The host did not refuse the foreign name even where it was not told to accept it, which was not looked into, so the runtime turns the host's check of the name off and does not rest on that. The name a program writes is a third thing and is untouched: the name one node's `ernest.conf` lists a peer under, which is also what the runtime prints.

**A certificate's dates mean nothing.** A self-signed certificate has an end date, and the host refuses an expired one, "Certificate Expired", which the experiment showed with certificates re-signed to end in 2021. Were that left, every program would stop on some anniversary, which is the kind of failure nobody expects of a configuration that worked yesterday. The key is the identity, so the rule answers the host's `cert_expired` as it answers `selfsigned_peer`, by the key, and the experiment's certificates are all expired on every run. `ern config` still writes the longest validity the format allows, so that no other tool complains.

**Two nodes with one key are not told apart.** The experiment tried a second node with the first one's key and name: to their peer the two are one node, and each one's dial ends the other's connection, with the host's `wait_pending`. The peer cannot refuse the second, since a connection from a name it already holds is exactly what a restarted node looks like, and asking the old connection whether it lives before accepting the new one would refuse every restart within the detector's 45 to 75 seconds. The node cannot refuse to start either, a copied directory on another machine being the original's twin. So the quarrel is stated as a limit and made visible: the peer says on its standard error each time a living connection is replaced by another from the same name, once for a restart and again and again for the mistake. And the mistake is made hard: `ern config` makes a key for one machine and prints the public key for the others' lists, and a configuration directory is never copied.

**A configuration only where `--config-dir` names one.** The plan once had a default directory, `./.ernest`, the directory a program starts in, whose `ernest.conf` would name the node's peers. It goes, with the private key `ern config` would have written into a working tree, where a commit can take it, which a security reader found. A program started without `--config-dir` is no node, has no peers and listens to nothing, and a node refuses a directory others can write and a key others can read, as `ssh` refuses them.

## 3. Its configuration

**Two fields for two things: `listen` and `network-address`.** One field held where a node listens and where a peer is dialled, which are different things: the first is an interface, `0.0.0.0` among them, the second a destination. So the node's own is `listen`, and a peer's is `network-address`, `host:port` with a name or an address. A name is allowed for a peer because deployments name machines, and a rule of numbers only would be worked around; it is resolved at each dial, not at start, so that a changed address under a stable name is followed. The host runs distribution over one family of addresses per node, so the family is the listener's, and a peer of the other family is refused when the configuration is read rather than at a dial that would fail later.

**A node's peers change while it runs.** A configuration read only at start was weighed first and left, since adding a node is not a change to one node's list: every node that is to talk to the new one gets an entry, so adding a machine would restart the whole system, a deploy's cost for a change that touches no code. On this carrier the change is cheap. The rule that accepts a peer and the table that gives a peer's address read a table the runtime fills, and a removed peer is dropped with the host's own disconnect. Three ways for `ern` to reach the running node were weighed. Over the distribution, `ern` would be a node with a key the running node lists, which would have to be in the file about to be reloaded. A local socket or pipe is a second listener and a second protocol to say "read your file again". A signal needs no new channel: the host delivers it, the runtime has a signal handler, only the process's owner can send it, which is the right permission for a node with one owner, and `kill -HUP` works where `ern` is not at hand. So `SIGHUP` is the mechanism and `ern reload --config-dir dir` the convenience, by a process number the node writes in the directory it owns, as every daemon does. What cannot change while running is the node's own key and address, its name and its listener; the rest is a table's rows. A signal carries nothing back, so the node reports on its standard error, and the command's status says only that the signal was delivered.

**The measures in Ernest's words.** Which of the host's measures run on a node is the machine's own matter, so it is `ernest.conf`'s, a section `measures` read at start and at a reload, none running where it is absent; a function the program calls to set them was weighed against it, since a program is one build on every node and the host reads the parameters only when its services start. The entries are `cpu`, `memory` and `disk`, with the host's parameters under them by their meaning, since an operator's file speaks Erlang's module names no more than a program does; the `Load` library's page says which service each is.

## 4. Its start and its end

**Initialization, the shell and a program's tests, in short.** A node listens only once its bindings all have their values, so that no spawn from a peer meets a binding being evaluated; one that arrives earlier, over a connection the node dialled itself, since an initializer may find and call, is answered `NotLoaded`, which means not there yet. A shell with a configuration is a node like any other and the remote console people want at no cost; a function typed at it is in a module no peer has, so `NotLoaded`, and `:load` and `:reload` are refused there, since code the build does not have would be spawned on a peer by a reference the peer resolves to other code, which MVP 3.1's hashes make safe. A program's tests of two nodes need nothing new in `ern test`, since `--config-dir` makes a test run a node and `Os` starts a second one on a directory `ern config` made; the guide shows it once, and a library that wraps it is written when a program's tests want it more than once.

**A node's end is not a loss.** When a program ends, its processes die with `ProgramEnd`, and a peer's monitor on one of them should say so, not `Unreachable`, since the peer can then tell a program that ended from a network that failed. The experiment showed that this rests on how the node stops: a halt right after the processes end, with or without a disconnect of each peer first, loses the `Down`s still in the buffer, and the peer's monitor gives `noconnection`; the host's orderly stop lets them cross. So a node stops as the host stops a node, in order, and what `ern run` does today at a program's end is checked against it when it is built.

## 5. What it says

**The host's reports are off, and the node's lines name the alias.** The host prints its own reports of a lost node, in its own words, which the experiment's output shows; they say less than the node knows and name the node by its carrier name, which no program sees. So the node turns them off and says one line each, on its standard error, for a peer connected, lost, refused for its key or its build, or replaced by a second node of its name, and for what a reload did, naming the peer by the alias in `ernest.conf` and by the key's digest only where the peer is not listed. Nothing is said for a message, a call or a spawn, which are the program's.

## 6. Connections

**The cookie is the build's fingerprint, and there is no hello.** The proposal first had a hello of Ernest's after the host's handshake, comparing the protocol's version, `ern`'s, OTP's and the build's checksum. Once a plain message went straight into the mailbox, that was a race: the host's handshake ends before the hello begins, and a message from a node of another build could reach a process first. The check has to be inside the host's handshake, where nothing passes before it. Two ways were weighed. Folding the four into the node's name, with the host told which names to accept, works but makes a node's name change with every build, against the rule that a name on the carrier is the key's identity and nothing else. The cookie is the other: the host's handshake proves both sides hold it before anything passes, and ours proved nothing. So each node computes it at its start from the four, nothing is written or copied, two nodes of one build arrive at the same one by themselves, and two of different builds fail the handshake with nothing sent, which the experiment showed. The cost is that the dialling side learns only that it was refused, so `Refused`'s text says what it can know, not listed there or another build, and the refusing side, which knows which, says so on its standard error. Erlang's cookie was a pain because it was the secret that said who may connect and had to be distributed; here that is the key's, and the cookie keeps no secret.

**From MVP 3.1 the cookie leaves the build out.** Builds differ by design once code is named by its hash, so the cookie keeps the protocol's, the hash scheme's, `ern`'s and OTP's versions and nothing of a program's code; nodes of different builds connect, and an upgrade of `ern`, of OTP or of the scheme stops every node, which MVP 3.1a narrows to the runtime's surface. `code.md` holds the argument for what the hashes leave out.

**No delay before a dial.** The host dials again at the next operation that needs the connection, with no delay, and Ernest adds none. Measured, a send with no connection open returns in microseconds; where the peer's port refuses, each send makes one dial of about 90 microseconds; and where nothing answers, every send waits behind one dial, which the host gives up after 7 seconds. So a peer that is gone costs a node little, and only as fast as its program sends. A delay of Ernest's own would show: a peer that is back would stay out of reach for as long as the delay. It would also take the dial from the host and keep a clock for each peer. Akka's fixed second, and a delay that grows, protect a node that comes back from hundreds of peers that dial it at once, which a few nodes with one owner are not. A delay changes when and never what, so it can enter later and break no program.

## 7. The gateway and what passes

**The build's hash does the work, and a message carries none.** A spawn on a peer names its function as a module and a place in it, which means the same on both nodes only where both run one build; a node of yesterday's build would run another function, or one with another closure, and nothing else would catch it. So the hello compares a hash of the build, taken over every compiled module on the load path by name and content, which costs reading the files once at start and 32 bytes at each connection. It cannot follow the entry point, since three nodes of one program start from three modules, so it covers the whole build and every node carries the whole build. A manifest written at `ern build` was left, since it goes stale when one file is rebuilt alone; a hash per module, compared where a message or a spawn meets it, is step B of the proposal's section 11 and relaxes this later. The standard library is left to `ern`'s version. The checksum is over what runs, since a `.erc` holds the module's documentation as well, and a checksum over the file would part two nodes over a fixed typo in a doc block: each module counts as its name and the host's own digest of its code, `beam_lib:md5`, which is what Erlang's release handling asks whether a module's code changed and leaves out documentation, line numbers and attributes. With one build made sure of, a hash of the mailbox type on each message does no work: every `send` across nodes is typed by the compiler as a local one is, and the types are the same at both ends by construction. What it would catch is a peer that sends a wrong value on purpose, which can do anything else as well. So a message carries no hash, and does not pass through the gateway: the host puts it in the mailbox, and a `send` across nodes costs the host's send and nothing of Ernest's. The gateway keeps what needs a process on the receiving node, a spawn, a find and a message to an adapted address. The price is one corner of order: a message to an adapted address made on the receiver's node takes a step more there, and a plain message sent after it can pass it, where on one node the function is applied in the sender. MVP 3.1 puts the hash back on messages when builds differ, which the proposal's fourth rule allows.

**From MVP 3.1 a message still carries nothing.** MVP 3.0's section 11 planned a hash on each message once builds differed. The induction that lets a bound value go unchecked holds for a type's identity too: every remote address a program holds came from a find, where the peer compared the key's identity, from a spawn of the program's own function, or inside a message whose type was agreed by one of the two, and there is no fourth way. So a message goes straight into the mailbox across builds as well, and a per-message hash would guard only against a peer that means harm, which can do anything else.

**A fault in an adapted address's function faults the sender, on a peer as on one node.** On one node the function runs in the sender and a fault in it is the sender's. Across nodes it runs in the gateway of the node that made the address, and the proposal first gave the fault to the process the address leads to, which was a second meaning for one construct. Charging the target was weighed, the function being the target side's adapter, but the report charges the process a function ran in, not its author, and the target would die for a message it never saw. Dropping the message and saying so is a silence the sender never learns of. So the frame carries the sender's address and the gateway ends the sender with the function's cause through the host's exit signal, which crosses nodes; the one difference is when, after the send returned rather than in it, the same shape as a `kill` from another node.

## 8. A loss and the detector

**Both ends run a loss.** A loss is the end of a connection, and each end runs it for itself: no frame says it. The end that tears the connection down runs it then. The other runs it when it sees the close, when its own heartbeat timeout passes, or when a hello arrives from a peer it holds an established connection with: that hello is the loss of the old connection, run whole before the new one carries a frame. The rule of the lower `NodeId` chooses only between two connections both still in their handshake. Were a loss one end's alone, the other would wait on monitors the first has dropped and on calls it has ended, and nothing would tell it. A network that stays silent is the plain case: both ends hear nothing, and both time out. Erlang's distribution does the same: each end closes on its own tick timeout, and its handshake answers `alive` to a node it believes connected, which then confirms that the old connection is broken.

**An address outlives a loss.** An address reaches its process again once the two nodes connect again, for as long as the process lives and its node has not been started again. A loss ends what was in flight and nothing else: what waited to be sent, each monitor with its one `Down`, and each waiting call. The first answer had an address die with its connection and stay dead, by a number each node gave its connections and marked what it held with. That kept a stream from ever going on after a hole. It also made every program that keeps an address of another node's process write for a loss: notice it, get the address again, monitor again. Each way round that was more machinery, a relay that finds a named service again, an operation that renews an address, a rule for a dead address that travels, and a process known by its address alone could not be found again at all. With an address that outlives a loss a program writes nothing for one, which is what a reader who knows Erlang expects (principle 1), and what Akka and Swift do at an ordinary loss; the capability systems keep a reference broken ([`other_systems.md`](other_systems.md)). The price is a hole: what one process sent another during a loss is gone, and what it sends after arrives. Both nodes run the loss, so whoever monitors is told that a hole may be there, and a protocol that must have none numbers its messages or calls. A restart of a node ends its addresses, which the incarnation tells, and the reason of a loss is `Unreachable`, as Erlang's `noconnection` says that the process may still be alive.

**A monitor ends with its connection.** A monitor on a peer's process is among what a loss ends. The watcher's node makes its `Down`, the one message its `monitor` call gives (§6.9), and nothing sets the monitor again when the connection returns. A program that wants to go on watching calls `monitor` again. The `Down` holds the process, so `monitor` on it watches the same process over the next connection. Set again by the runtime, a monitor would say nothing at the loss, its watcher waiting for ever on a peer that never returns, or it would give two messages for one call. The node would dial in the background to set it, where a connection opens only on demand, and would keep each `wrap` for as long as the peer stays away. Erlang's monitor is the same: it is triggered once, the loss of the connection among what triggers it. A client finds its service again after a loss in any case (below), and monitors it again there; a library does both, the standing address of section 14. A `monitor` called while the peer is still out of reach answers a `Down` with `Unreachable` once the dial has failed, so that a program that monitors again in a loop is paced by the dial's delay.

**`Unreachable` is a reason of its own.** A watcher told that a process's node is out of reach must be able to tell it from a fault, since the process may live on and a replacement would make two; the report's older peer chapter gave both the cause `peer lost`, which a reader outside the project found indistinguishable. So `Reason` gains `Unreachable`, and a `Down` made at a loss carries it with an empty site, the watcher's node not knowing where the process was spawned.

**The detector stays fixed.** A fixed timeout: what counts as a sign of life, how long the silence is, and what a node that is itself stalled concludes of its peers. *Worked:* the timeout stays fixed. A detector that adapts keeps a history of delays and a threshold to set, which buys little for a few nodes listed by hand; measured false losses would change that. Its default is Erlang's, 60 seconds in four intervals, so a silence is found in 45 to 75 seconds. A peer that crashes or exits is seen at once, its host closing the socket. The timeout governs a dead machine and a partition alone, and a program that must know sooner has the deadlines of its calls. The detector counts the intervals it has seen and not the time gone: a timer every quarter of the timeout, and four in a row with no bytes arrived are a loss. A node that was itself stalled then sees one silent interval as it wakes, and does not lose every peer at once. It watches both ways: a peer is silent too where bytes wait to be sent and none have left in four intervals, since it has stopped reading. The timeout is a constant of the protocol, as the queue's limit is. Each end sends its idle heartbeat every quarter of it, so the ends must agree, and a constant leaves nothing to negotiate in the hello and nothing to set wrong. A number becomes a key of `ernest.conf` when a deployment shows that it must differ. No detector tells a slow peer from a dead one, which is what `Unreachable` says.

**Two processes where one was meant.** *Two processes where one was meant.* A watcher told `Unreachable` that starts a replacement has two where the first lives on. What must exist once needs more than a monitor: a lease whose holder the resource checks, or agreement among nodes, a library's work. The guide says that `Unreachable` is not death. *Worked:* nothing is added to the language or the runtime for it. An election and a lease are engines, a library's work, and the language stays small (principle 5). The guide teaches three rules that what there is already carries. A program replaces at `Unreachable` only work that may run twice. A process spawned on a peer watches whoever it works for and ends when it is told `Unreachable`, which it is, since both ends run a loss; so no worker runs on unwatched after a partition, by `spawn` and `monitor` alone. And what must exist once lives on one named node and is found there with `Peer.find`: out of reach it is unavailable, nobody else starts it, and moving it is the operator's act in `ernest.conf`. The standard library makes no second one itself, a supervisor's children running on its own node. A thing that must exist once and move by itself needs a lease its resource checks, or agreement among nodes, a library written when it is wanted. Between the two ends' timeouts a worker and its replacement can both run for a while, which the first rule makes harmless.

**One side may be unable to dial.** Behind a translated address a node reaches its peer and the peer does not reach it. One connection carries both ways, so the node that can dial opens it and the other then sends, answers, spawns and monitors over it; a system with a connection for each direction, as Akka's, cannot send to such a node at all. What is left is the time after a loss, when the node that cannot dial has no way to open the connection again. Two answers were left: a node that dials again in the background, which was refused for every node (section 6), and a message carried through a third node. So nothing is added, and the limit is stated: the node that can dial watches, and opens the connection again. The configuration follows the fact. A node with no network address of its own does not listen, and a peer listed without one is never dialled, so that no dial is made that can only hang until the host gives it up. The experiment tried it with a node that does not listen: its peer could not connect to it, reached it and spawned on it once it had dialled, lost it at a loss, and reached the same process by the same address once it had dialled again. The host calls a node that does not listen hidden, and leaves it out of its plain list of nodes and its plain notices, so the runtime asks for nodes of every kind.

## 9. Addresses

**An address is the permission to kill, across nodes too.** On one node an address lets its holder send to a process and kill it, inside one program. With peers the permission travels: every node that finds a service holds its address and can end it for the others. Two other rules were weighed. An address that only sends, which a find would give, is a second kind of address beside the one the language has, and the carrier cannot keep its promise: a connected node can end anything on the other, so it would guard against a peer's mistake and not against a peer. And a `kill` refused across nodes takes from a spawner the means to stop the worker it started on a peer. The rule kept is the one a process already knows, so that it need not know where an address leads, for `kill` as for `send`. Erlang has the same rule: whoever holds a pid can send it an exit signal. The capability systems have the other, a reference that conveys messaging alone ([`other_systems.md`](other_systems.md), *T6*), and there an address that only sends is a process in front of the service, which a program can write today: it forwards what it is sent, and a `kill` of it ends the forwarder. An address that only sends can enter later and break no program.

**The spawn site crosses with the spawn, and not with a `Down`.** The peer records the site from the spawn frame, one string sent once per process, so its faults and `Process.info` name where the process was spawned, which is in the peer's own source too, the build being one. A `Down` across nodes comes from the host's monitor, whose reason is what the process exited with; carrying the site in it would take a round trip at every monitor or a site in every exit reason, against what the report says a process exits with, and neither is worth a debugging aid. So a `Down` for a process of another node has an empty site, as the one with `Unreachable` has.

## 10. Messages

**A sender waits, as the host has it.** The rule that a sender never waits was made for a protocol of our own, where blocking would have been code of ours. On the host's distribution it is the other way round: a sender that waits where the buffer is full is what the host does, and not waiting is what would be built, a `nosuspend` on every send, a disconnect where it is refused, and a limit to argue over. The host's way gives back-pressure, a program that sends faster than the network carries being slowed to the network's speed instead of losing the connection and every monitor and call on it; a bound, since the detector gives the peer up within 45 to 75 seconds and the send then returns; and nothing to build. Its costs are stated as a limit: a `send` across nodes returns at once only while the network keeps up; a process that waits in a send serves nothing from its mailbox, so a stalled peer stalls the processes that send to it, which Erlang programs live with by supervision and timeouts; and a call's time runs from the moment its request is sent. Akka drops the message where its queue overflows, which would break the claim that no message is dropped alone; ending the connection, which was weighed before, is the harshest answer to a stall. The buffer's size is the host's own 1 MB and says only when slowing begins.

**Atoms.** An atom crosses as the text of its name: the external term format writes a tag, a length and the name's bytes, and between two nodes the host sends the text once for a connection and a one-byte index after that. The receiving node looks the name up and makes an atom only for a name it has never had. In an Ernest value only a constructor's name is an atom, a `String` being a binary, and with one build every node has every constructor's atom from its own compiled modules. So a correct program's traffic makes no atom: decoding one value with four constructors 100,000 times made none. An atom is made only for a name a faulty peer invents, and on this carrier that peer can do anything else as well, so the proposal promises nothing against it and says so among its limits. Constructors sent as binaries and turned back on arrival were weighed and left: Ernest would rebuild every value at both ends, in Erlang where the host works in C, against the value's type, since a `String` is a binary too; and the host's own signals, which carry atoms, would stay as they are. Where builds differ, in MVP 3.1, a peer can send a constructor a node lacks, which adds as many atoms as that peer's code has names, and never as many as it sends messages.

## 11. Calls

**A call's `None` has one meaning.** Across nodes a call ends without an answer in four cases: its time ran out, the callee ended or restarted, the callee's node went out of reach while the caller waited, or no connection could be opened. In the last the request was never sent and did not run, and in the others it may have run. A program is not told which, for five reasons. `None` on one node already covers a time that ran out, where the request may run later, and a callee that ended, so other nodes add nothing new in kind. That a request was never sent is known only where no connection could be opened: once one exists, the caller's node cannot know what arrived. A request that may be sent again must be harmless when run twice whichever case it was, so the difference would spare a program one duplicate, seldom, and none of its code. Telling them apart would change `Address.call`'s type on one node too, or give other nodes a call of their own, and a process would then have to know where an address leads, which an address is there to hide. And the reason is to be had: a monitor's `Down` says `Unreachable`, how the process ended, or `Unknown`. Erlang's `erpc` merges the same two: a connection lost and one never established are one error, under which the function may or may not have run.

**An operation with a time keeps its time.** With a sender that waits, a call's request could wait in the buffer, so a call to a stalled peer took the wait and then its time, as Erlang's `gen_server:call` does, where the timeout runs only in the receive after the send. Akka never waits and drops the message, which breaks the claim that no message is dropped alone; gRPC's deadline covers everything, connecting, sending and the answer, because the client owns its socket and can abandon a pending write. Erlang cannot give that promise for one process, since a process suspended in a send is not woken by its own timer, but it can for two: the call sends without waiting, and only where the buffer is full a process of the runtime's takes the request and does the waiting send, while the caller waits by its time. The common path costs nothing more; the helper is ended where the time runs out first, so that a stale request is not sent after its caller gave up. A plain `send` still waits, since back-pressure is what a sender without a time should feel; on one node it never waits, a mailbox having no limit. So the exception in the proposal's first rule, where the network is behind, applies to `send` alone. `answer` goes the same way as a call's request, since the one place the waiting sender punished the wrong process was a service answering a client whose node is stalled: the service blocked in the answer and served nobody else, held by one bad link to one remote client. An answer is small and one-shot, so the helper costs nothing on the common path. A service that pushes to many remote clients, subscriptions and the like, does it through a process for each, as Erlang programs always have, which the guide's peer chapter is to say.

**A remote call ends at a restart, by a note.** The runtime keeps a table on the caller's node of who waits on whom, which a restart reads to tell each caller. A callee on another node cannot read it, so without more a remote call would not end at a restart, a `callForever` never, against the claim that every call ends. Saying that a restart does not end a remote call was weighed and left, `restarting` being the ordinary shape of a service. So a call across nodes sends the callee's node a note that it waits, one frame on the same connection, kept as a row until the callee answers, restarts or ends, with a second note where the caller's time ran out and a loss dropping every row of the peer. The other half of the gateway's question, a function of an adapted address that never finishes, is left as it is on one node, where it holds the sender: across nodes it holds that peer's gateway, and a process for each adapted address would hold only that address but could never end, nobody knowing when a remote holder drops the address.

**A node with peers declares no deadlock.** On one node the runtime declares a deadlock where no process can be delivered a message any more (§8.6). A node with peers can always be reached from outside, by a message, a spawn or a connection, so nothing on it can be known to wait for ever; a program that waits on itself across nodes hangs, and a time on its calls is the program's answer.

## 12. Serialization

**The other encoding.** A format of Ernest's own, a constructor written as its position in its type, would put no atom on the wire and owe the host nothing. It would be written in Erlang, value by value against the type, where the external term format is the host's own and written in C. It is left out; a runtime on another host, or a measured need, would change that. Wikipedia's [comparison of data-serialization formats](https://en.wikipedia.org/wiki/Comparison_of_data-serialization_formats) lists the formats such an encoding would be weighed against.

**What cannot cross is refused by the compiler, and nothing is walked.** The proposal first had the runtime look through every value before it was sent, for a function, a foreign value or a resource, which is a walk in Erlang over the whole value and can cost a multiple of the host's send. A walk only where the type can hold such a thing was weighed, and then the walk went altogether, since the check is a type's. A type is bound to its node where it holds a function type, a foreign type, a resource, or an address or reply whose message type is bound; and a bound value has only two ways to start towards another node, a key of its type and a spawn that captured it, both of which the compiler sees and refuses. Every other way follows: an address of a remote process came from a find or a spawn, so its message type is unbound, and so is everything sent to it or answered through a reply in it. Testing at run time what the type checker knows is wrong, as the user put it. A spawn whose captures have a type variable in their type is refused for now, by the proposal's first rule for what comes after, and `needs`, which already carries a property of a type variable to its use, is the way to relax it. One check stays at run time: an adapted address crosses with its function's captured values, which its type does not show, so they are checked as it crosses, a few values and never a message.

**Another node's processes and resources.** `Process.info` answers for the running node's processes alone and `None` for another node's, since the runtime answers from its own record and asking a peer would be a call a program did not write. The address of a socket, a listener or a program the runtime started, and an `Ets.Table`, are the host's references and mean nothing on another node, so they are bound types and never cross; a supervisor's children run on its own node for the same reason.

## 13. A spawn

**A spawn and a find answer a value, and take a time.** A spawn on a peer first faulted its caller where the peer was out of reach, and waited with no clock of its own. Both are changed, for four reasons. A fault says that the program is wrong, and a peer out of reach is no mistake of the program's: it is what a program of several nodes is written to meet, by trying another node, by waiting, or by telling its user. A process that faults can do none of these, and only a process that monitors it could. A find answered a value for the same condition, so two operations that wait on one peer failed in two ways. With no time, a spawner waited the 45 to 75 seconds the detector takes to find a silent peer, and for ever on a peer that lived and did not answer, which a gateway held up behind a slow function of an adapted address can be. And every other wait on a peer has a time, which `Address.call` takes as its last argument too. What stays a fault is the program's own mistake: a function that captured a value that may not cross is wrong on every run, and its own node finds it before anything is sent. A function whose bindings the peer did not run is answered as a value, though the program is where the mistake is: the spawner cannot know which entry point its peer was started from, a program can choose another peer, and a later milestone may run the bindings, so that a failure becomes an answer and breaks no program. The price is a `match` at every spawn on a peer, where a local `spawn` has none. And a spawn whose time ran out may have started its process, as one that lost its connection may (the proposal's [`code.md`](code.md), section 4, point 3). Erlang went the same way: its `spawn/4` gave a useless pid for a node out of reach, and `spawn_request/5`, which came later, answers with the pid or with an error, `noconnection` among them. It has the same hole: a request that its caller abandons may still create its process.

**A spawn answer no one waits for ends the process it names.** Where the spawn's time ran out while the connection lasts, the answer reaches a node where no one waits for it. Letting the process run would keep a process no one can reach or stop; killing it makes true what the spawner was told, that no process came, a moment later. Erlang does the same for an abandoned spawn request that was linked, with the exit reason `abandoned`. Where the connection was lost instead, no answer arrives and neither node can know, so that process runs on, which is the limit the proposal states.

**From MVP 3.1 the spawn carries a hash, and code crosses.** The function's module and place, which one build made mean the same everywhere, become the function's hash, and a peer that lacks it is sent the closure; the reasons for the exchange are `code.md`'s. What stays is the spawn's shape: a value answered, a time, `NotLoaded` for what the peer cannot be sent, a binding's value or a foreign declaration's module.

## 14. A service and its key

**A service is found by a typed key.** The proposal first found a peer's service by shipping a function that read one of the peer's top-level bindings. Three things were wrong with that. Naming the binding made the client's program depend on the service's module, so the client's node ran that module's bindings and started a service of its own, and no arrangement of modules avoids it, since the client needs the module for the message type. A function crossed to look something up, which needs the same function on both nodes and is the first thing to break where builds differ. And every binding of a peer was open to every peer. A key is a value that starts nothing, holds a name and a message type's hash, and crosses in place of code; a node offers what its peers may find, and nothing else is found. The compiler holds an offer to one message type, and the peer compares the hash at a find. It is a registry of a kind, which Ernest has otherwise refused: it holds what a program chose to offer, to peers alone, and on one node a service stays a top-level binding. It is what a reader who knows Erlang expects, a registered name on a node, with a type. Its price is a name the program chooses, so that two services under one name on one node clash.

**A later offer takes the earlier one's place.** Three answers were weighed for an offer under a name that is taken. Refusing it, as Erlang's `register` does, gives `Peer.offer` a failure every program must handle, and races: a service that restarts can offer itself before its node has noticed that the old process ended. A set of addresses under one key, as Akka's and Swift's receptionists keep ([`other_systems.md`](other_systems.md), *A-15*, *T-8*), makes a find answer a list the finder must choose from, which is the beginning of a cluster. Replacing cannot fail, has no race, and lets a new process take a service over from an old one, which an upgrade later needs. Its price is that two services which take one name by mistake do not clash loudly: a find through the first key answers "another message type" where the types differ, and where they are the same the second silently wins. Nothing withdraws an offer: it ends with its process, which is what a program means by it. And only a process of the offering node may be offered. An address of a third node's process would reach a node the finder may not list, and the offering node would have to watch the process across a connection to know when the offer ends; by the proposal's first rule for what comes after, it is refused now and may be allowed later.

**A key carries its type's text, and no hash is in MVP 3.0.** With one build on every node a type's name says everything a hash would: one build has one definition for each qualified name, so two keys name one type exactly where their types print the same. A key therefore holds the message type's text as the compiler prints it, and a find compares the texts, which still catches two services under one name with different types, at a string comparison once per find. The compiler still takes the type where `Peer.key` is written and refuses one not fully known there; printing a type is the simpler half of hashing it. MVP 3.1 puts a hash in the text's place, where builds differ and a name no longer says what a type is; the proposal's third rule for what comes after compares a type's identity and never asks how it was made, and its fourth lets the wire change. The one hash left in the milestone is the build's, a checksum of files, and is called so, so that the word first appears in MVP 3.1 where it carries meaning. The note's rule for a type's hash ([`code.md`](code.md), section 2.1) stays there.

**From MVP 3.1 a key carries its type's identity.** Once builds differ a name no longer says what a type is, so the key carries the type's hash, and with it the hashes of the members the type declares, `compare` among them, so that a value ordered under one order never meets code that orders it under another; the members stand beside the hash and not in it, since a member's tree names the type and no hash may contain a hash that names it. `OtherType` at a find then means a service at another version, which is what MVP 3.0's section 11 kept the constructor for.

**No standing address in `Peer`.** An address that finds its service again after the service's node is started again was weighed for `Peer` and left to a library. Every piece of it is a program's already: a process on the holder's node that forwards what it is sent, holds the peer's name and the key, monitors the service and finds it again when told, held through `via` so that the holder has an `Address(m)` like any other. What the runtime knows adds nothing to it. It is a policy, and policies differ: what to do with a message sent while the service is gone, how long to wait before finding again, whether to tell the holder; `Peer` would pick one for every program, a library picks one and can be replaced. And it hides a restart, which the building block makes visible, so a program should choose it. `restarting` is the counter-example, a fault hidden behind a kept address in the prelude, and differs in being the runtime's own capability, the process keeping its address, where a standing address is a second process that forwards. Where every program with peers turns out to need it, and one policy fits all, it moves to where `restarting` is.

## 15. Bindings

**A node runs its own bindings, and nothing for a peer.** A node evaluates at its start the top-level bindings of the standard library and of the modules its entry point depends on, as a program on one node does, and listens only once they all have their values. A function spawned on it runs only where the bindings it depends on have their values there, and otherwise fails with `NotLoaded`: an initializer may spawn, send and call, and the types do not tell a constant from a service, so evaluating one because a peer asked would start processes nobody on that node asked for, the problem the key solved. A spawned function captures what it needs instead; captured values cross and bindings are the node's own. In spawned code a top-level binding is the peer's and a captured value the spawner's, so the system processes are the peer's and a spawned process's output is the peer's.

**From MVP 3.1 bindings are held by hash.** A spawned function finds a binding's value where the peer's own build ran that hash, which it did wherever the definition is unchanged between the builds, and `NotLoaded` otherwise; nothing changes in the rule. A service is one per node and key, the latest offer, so no second service is started unseen when builds differ. A node started with no `.erc` at all, a bare node, falls out of the same rules: it runs the standard library's bindings and nothing else, takes what its peers spawn on it, and offers what those processes offer.

## 16. Placement by load

**Placement by load is two libraries and one function of `Peer`.** The plan had `Peer.nodes`, `Peer.runQueue` and the library `Balancer`. `Peer.nodes` stays in `Peer`, since only the runtime has the configuration, and answers the listed peers without the running node, which is no peer of itself. `Peer.runQueue` goes: how busy a node is has nothing to do with peers, and the host's measures, the run queue, the schedulers' utilisation, memory and disk, are a library of their own, `Load`, each a shim, the last two answering a failure where `ernest.conf`'s `measures` did not start the host's services. The balancer is a process, round robin unless given a measure, a measure a function to 1.0 that a program gives on each node by `Balancer.measure(f)`, which offers a measuring process under `Balancer.key`. Load is pulled, not spread: a pick draws two candidates at random and calls each, the two-choices rule, so a pick costs two calls whatever the number of nodes and nothing is ever stale or gossiped. The library's own type of a place, this node or a peer's name, is fine for a library where it was not for the prelude. All of it is in MVP 3.0, as its last items, because the two libraries need nothing the proposal does not give and are the first real programs on it.

**A measure is installed from the program's side.** `Balancer.measure(place, f)` spawns the measuring process on any place, this node or a peer, rather than each node calling it for itself, so that one way installs a measure everywhere and a bare node, which runs no program of its own, is measured and placed on like any other; the measure's functions are the `Load` library's, the platform's, so they exist on every node.

## 17. The shell

**A shell is a node, and in MVP 3.0 loads nothing.** A shell with a configuration is a node like any other and the remote console people want at no cost. In MVP 3.0 a function typed at it is in a module no peer has, so a spawn of it answers `NotLoaded`, and `:load` and `:reload` are refused in a shell that is a node, since code the build does not have would be spawned on a peer by a reference the peer resolves to other code. From MVP 3.1 both refusals lift: a function typed at the shell has a hash and spawns with its code, and a load adds hashes and moves the session's names.

## 18. `Peer`'s shape

**One failure type, with a text in `Refused`.** `Peer.Failure` serves a find and a spawn both, as `Io.Error` serves every operation on a file, though a find never meets `NotLoaded` nor a spawn `NotOffered`: two types would repeat four constructors, and a program writes `_` for what its operation cannot meet. `Refused` carries a text, since a program cannot act differently on which of the protocol, the build, `ern` or OTP differed, only report it, and a text leaves room for a later hello to refuse for more without a new constructor, which the proposal's second rule for what comes after asks. `OtherType` and `NotLoaded` are named for what they will also mean later: a service at another version, and code the peer does not have.
