# Ernest: Nodes, the reasons

Status: the reasons behind [`mvp3.0.md`](mvp3.0.md), nodes as MVP 3.0 and MVP 3.1 design them; synced on 2026-10-08 to `mvp3.0.md` after the review of the three proposals, the decisions of that day dated where they stand. The sections follow the order of `mvp3.0.md`'s section 6, and a paragraph that begins *From MVP 3.1* says where that milestone changes the rule. Nothing here is normative: the proposals state the rules, and this document says why. Three things are elsewhere: the reasons for code by its hash are [`code.md`](code.md)'s; what other systems do is [`other_systems.md`](other_systems.md); and what the host showed is the experiment under [`experiments/`](experiments/erlang_distribution/).

## 1. The carrier

**Ernest's network carrier is Erlang's distribution.** It gives Ernest the connection between two nodes and its handshake, over TLS; the heartbeat that finds a silent peer; the order of messages between two processes; monitors across nodes; one-shot replies; and a sender that waits where the network is behind. Ernest turns off five things of it and puts a rule of its own in each one's place. The mesh, by which every node connects to every node a peer knows, is off: two nodes connect only where one dials the other, and that A knows B and B knows C connects A and C in no way. The port-mapper daemon is off: a node finds a peer's address in its configuration. The host's check of a certificate's name is off: a node accepts a peer by its public key alone, which its configuration lists, by a rule of Ernest's in the TLS handshake. The host's own reports of its nodes are off, but one, the handshake's refusal by the cookie, which nothing of the node's own sees (section 5): the node says on its standard error, in its own words, that a peer connected, was lost, was refused or was replaced. And the cookie is no longer the proof of a peer: it is the build's fingerprint, so that two nodes of different builds fail the handshake with nothing sent, and the key is the proof.

## 2. A node

**A node is its key.** A node's name on the carrier is the SHA-256 digest of its public key with a constant after it, and the name in its certificate is a constant. Neither is a host name, and nothing resolves either: a peer is accepted by its public key, which the configuration lists, and its address comes from the configuration. So every node computes the same name for a peer, and a node that moves to another machine keeps its name and its identity. The name a program writes is a third one: the alias this node's `ernest.conf` lists the peer under, which the runtime also prints.

**A certificate's dates mean nothing.** The rule that accepts a peer answers an expired certificate as it answers a self-signed one, by the key, since the key is the identity and a certificate that expired would otherwise stop every program on some anniversary. `ern config` still writes the longest validity the format allows, so that no other tool complains.

**Two nodes with one key are one node to their peers.** A connection from a name a node already holds is what a restarted node looks like, and asking the old connection whether it lives before accepting the new one would refuse every restart within the detector's 45 to 75 seconds; a copied directory on another machine is the original's twin, so neither node can refuse to start. The limit is stated and made visible: the peer says on its standard error each time a living connection is replaced by another from the same name, once for a restart and again and again for the mistake. The mistake is made hard: `ern config` makes a key for one machine and prints the public key for the other nodes' lists, and a configuration directory is never copied.

**A configuration only where `--config-dir` names one.** A program started without it is no node, has no peers and listens to nothing. Its directory is §11.3's default, `./.ernest`, which holds its startup file and, from MVP 3.2, the states its `kept` loops write at termination and read at the next start (`deploy.md`), and never a key or a peer: a key in a working tree would be where a commit can take it, so a node is made only by `--config-dir`, naming a directory of its own. A node refuses a directory others can write and a key others can read, as `ssh` refuses them.

## 3. Its configuration

**Two fields for two things: `listen` and `network-address`.** Where a node listens is an interface, `0.0.0.0` among them, and where a peer is dialled is a destination, so the node's own is `listen` and a peer's is `network-address`, `host:port` with a name or an address. A name is allowed for a peer because deployments name machines, and it is resolved at each dial, not at start, so that a changed address under a stable name is followed. The host runs its distribution over one family of addresses per node, so the family is the listener's, and a peer of the other family is refused when the configuration is read rather than at a dial that would fail later. `listen` may name port 0, at which the host picks a free port and the node says on its standard error which it bound, so that two tests on one machine, each running two nodes, collide on nothing; decided on 2026-10-08.

**A node's peers change while it runs.** Adding a node is an entry in every node that is to talk to it, so a configuration read only at start would restart the whole system for a change that touches no code. The rule that accepts a peer and the dial read a table the runtime fills from `ernest.conf`, and a removed peer is dropped with the host's own disconnect. `SIGHUP` tells the node to read the file again, and `ern reload --config-dir dir` sends it by the process number the node writes in the directory it owns, as every daemon does: a signal needs no new channel, only the process's owner can send it, which is the right permission for a node with one owner, and `kill -HUP` works where `ern` is not at hand. The node's own key and `listen`, its name and its listener, cannot change while it runs; the rest is a table's rows. A signal carries nothing back, so the node reports on its standard error, and the command's status says only that the signal was delivered.

**The measures in Ernest's words.** Which of the host's measures run on a node is the machine's own matter, so it is `ernest.conf`'s: a section `measures`, read at start and at a reload, none running where it is absent. Its entries are `cpu`, `memory` and `disk`, with the host's parameters under them by their meaning, since an operator's file speaks Erlang's module names no more than a program does; the `Load` library's page says which service of the host each is.

## 4. Its start and its end

**A node listens once its bindings have their values.** So no spawn from a peer meets a binding being evaluated; one that arrives earlier, over a connection the node dialled itself, since an initializer may find and call, is answered `NotLoaded`, which means not there yet. Since 2026-10-08 a node dials only once its bindings have their values too, so none arrives earlier (section 15). A shell with a configuration is a node like any other, the remote console people want at no cost. A program's tests of two nodes need nothing new in `ern test`: `--config-dir` makes a test run a node, and `Os` starts a second one on a directory `ern config` made; the guide shows it once, and a library that wraps it is written when a program's tests want it more than once.

**A node's end is not a loss.** When a program ends, its processes die with `ProgramEnd`, and a peer's monitor on one of them says so, not `Unreachable`, so that the peer can tell a program that ended from a network that failed. For that the node stops as the host stops a node, in order: a halt right after the processes end loses the `Down`s still in the buffer, and the peer's monitor would read a loss. What `ern run` does today at a program's end is checked against it when it is built.

**Hangup is a reload and termination an end.** A node is a daemon, and every daemon reads its configuration again at hangup and ends at termination; `ern reload` and `ern stop` send the two by `ernest.pid`, and `kill` does as well. For a program that is no node both end it, as the report has it. From MVP 3.1 a bare node, whose entry process runs the standard library's bindings and no `main`, ends by termination alone. From MVP 3.2 termination is the planned stop, four steps before this end, and the reasons are `deploy.md`'s; this document keeps the end as MVP 3.0 builds it.

## 5. What it says

**The node's lines name the alias.** The node says one line each, on its standard error, for a peer connected, lost, refused for its key or its build, or replaced by a second node of its name, and for what a reload did. Each names the peer by the alias in `ernest.conf`, and by the key's digest only where the peer is not listed. The host's own reports of its nodes are off, since they say less than the node knows and name a node by its carrier name, which no program sees; the one kept is the handshake's refusal of a peer's cookie, since that refusal happens inside the host's handshake, before the rule of Ernest's runs and where nothing of the node's own can see it, and without the host's line a wrong build would be seen on neither side (decided on 2026-10-08). Nothing is said for a message, a call or a spawn, which are the program's.

## 6. Connections

**The cookie is the build's fingerprint.** Each node computes the host's cookie at its start as the digest of the protocol's version, `ern`'s version, OTP's version and the checksum of its build; nothing is written or copied, and two nodes of one build arrive at the same one by themselves. The host's handshake proves both sides hold it before anything passes, so two nodes of different builds fail the handshake with nothing sent. The check is inside the handshake because a plain message goes straight into a mailbox, and a check after the handshake would race it. The dialling side learns nothing of why: the host reports a failed handshake as no connection, whatever the cause, a wrong key refused by the rule ending in a TLS alert the host swallows the same way, so a connection the peer refused is `Unreachable` to the dialler, as the experiment showed with a wrong cookie, and `Refused` is kept for MVP 3.1's refusal of a closure, which a peer answers over a connection that stands (decided on 2026-10-08). The refusing side, which knows which, says so on its standard error. The cookie keeps no secret: who may connect is the key's.

**From MVP 3.1 the cookie leaves the build out.** Builds differ by design once code is named by its hash, so the cookie keeps the protocol's, the hash scheme's, OTP's and the runtime surface's versions, the standard library's identity among the surface, and nothing of a program's code (`mvp3.1.md`, section 6); nodes of different builds connect, and a release that changes the surface, OTP or the scheme stops every node (`deploy.md`, section 12). `code.md` holds the argument for what the hashes leave out.

**The key is on prime256v1.** The experiment proved the handshake with the rule on prime256v1 certificates, so `ern config` makes the key there; whether ed25519 serves in TLS 1.3 with a pinning rule is untried, and is the build's first question, taken where it serves (decided on 2026-10-08).

**No delay before a dial.** The host dials again at the next operation that needs the connection, and Ernest adds no delay. A send with no connection open returns in microseconds; where the peer's port refuses, each send makes one dial of about 90 microseconds; and where nothing answers, every send waits behind one dial, which the host gives up after 7 seconds. So a peer that is gone costs a node little, and only as fast as its program sends. A delay of Ernest's own would keep a peer that is back out of reach for as long as the delay, and would take the dial from the host and keep a clock for each peer; what a delay protects, a node that comes back from hundreds of peers dialling at once, a few nodes with one owner are not. A delay changes when and never what, so it can enter later and break no program.

## 7. The gateway and what passes

**The build's checksum does the work, and a message carries none.** A spawn on a peer names its function as a module and a place in it, which means the same on both nodes only where both run one build, so the cookie carries a checksum of the build: every compiled module on the load path, in name order, each as its name and the host's own digest of its code, `beam_lib:md5`, which leaves out documentation, line numbers and attributes, so that a fixed typo in a doc block parts no two nodes. It covers the whole build, since three nodes of one program start from three modules, and every node carries the whole build; the standard library is left to `ern`'s version. With one build made sure of, every `send` across nodes is typed by the compiler as a local one is, and the types are the same at both ends by construction; a hash on each message would catch only a peer that sends a wrong value on purpose, which can do anything else as well. So a message carries no hash and does not pass through the gateway: the host puts it in the mailbox, and a `send` across nodes costs the host's send and nothing of Ernest's. The gateway keeps what needs a process on the receiving node: a spawn, a find, and a message to an adapted address. The price is one corner of order: a message to an adapted address made on the receiver's node takes a step more there, and a plain message sent after it can pass it, where on one node the function is applied in the sender.

**One gateway per node.** The frame that opens a connection, a find or a spawn to a peer with no connection open, arrives before anything on the accepting node has seen the peer come up, and the host drops a message to a registered name that does not exist on a remote node without a word; a gateway made for each connected peer would therefore miss the first frame, and the finder would wait out its time. So a node has one registered gateway, which exists from the node's start and takes every frame from every peer, and hands each to a worker for the sender's node (decided on 2026-10-08).

**From MVP 3.1 a message still carries nothing.** The induction that lets a bound value go unchecked holds for a type's identity too: every remote address a program holds came from a find, where the peer compared the key's identity, from a spawn of the program's own function, or inside a message whose type was agreed by one of the two, and there is no fourth way. So a message goes straight into the mailbox across builds as well.

**A fault in an adapted address's function is the target's, on a peer as on one node.** §6.5 has it so on one node: the process the address names dies of the fault and the sender goes on, since the function is the target's own, written by whoever made the address, and the sender knows nothing of it. Across nodes the function runs in the gateway of the node that made the address, which ends the target with the function's cause, on its own node or on another, and the sender goes on as before, told nothing, as on one node. The rule is the report's and the same everywhere; charging the sender would fault a process for a function it never wrote and make the rule differ across nodes (decided on 2026-10-08).

**An adapted address crosses whatever node its target is on.** Decided on 2026-10-08, as the report was rewritten from the proposal. The report's rule that an adapted address crosses only when its target is on the node that made it had its teeth in the run-time fault at transport, which this proposal removes, and where a target lives is not a type, so none of section 2's refusals can take its place. The gateway of the node that made the address applies the function and sends the result on to the target wherever it is, over a connection that node has, since it found the target there; a check at the gateway that dropped such a message would be a new silence, against the second rule. So the qualifier goes, and claim 4.1's corner is stated for an address made on another node than the sender's.

**An adapted address's captures cross as payload, and nothing is looked through.** The function runs only on the node that made the address, so the values it captured are touched nowhere else: they cross inside the address as inert payload and come home with every message sent to it. Nothing is therefore checked as the address crosses: finding an adapted address inside an outgoing value would mean walking every remote message, since the host encodes a message whole with no hook per part, a cost proportional to the message where the send costs the host's send. The price is stated as a limit: the address is as large as what its function captured, and carries it at every crossing. §6.5's requirement that the captured values can cross themselves goes, which the proposal's §9.5 names (decided on 2026-10-08).

## 8. A loss and the detector

**Both ends run a loss.** A loss is the end of a connection, and each end runs it for itself; no frame says it. The end that tears the connection down runs it then. The other runs it when it sees the close, when its own detector gives the peer up, or when a peer it believes connected dials it anew, which is the loss of the old connection, run whole before the new one carries a frame. Were a loss one end's alone, the other would wait on monitors the first has dropped and on calls it has ended, and nothing would tell it. A network that stays silent is the plain case: both ends hear nothing, and both time out. Erlang's distribution does the same.

**An address outlives a loss.** An address reaches its process again once the two nodes connect again, for as long as the process lives and its node has not been started again. A loss ends what was in flight and nothing else: what waited to be sent, each monitor with its one `Down`, and each waiting call. A program therefore writes nothing for a loss, which is what a reader who knows Erlang expects (principle 1). The price is a hole: what one process sent another during a loss is gone, and what it sends after arrives. Both nodes run the loss, so whoever monitors is told that a hole may be there, and a protocol that must have none numbers its messages or calls. A restart of a node ends its addresses, which the start's number tells, and the reason of a loss is `Unreachable`, which says that the process may still be alive.

**A monitor ends with its connection.** A monitor on a peer's process is among what a loss ends. The watcher's node makes its `Down`, the one message its `monitor` call gives (§6.9), and nothing sets the monitor again when the connection returns; a program that wants to go on watching calls `monitor` again, and the `Down` holds the process, so `monitor` on it watches the same process over the next connection. A monitor set again by the runtime would say nothing at the loss, its watcher waiting for ever on a peer that never returns, or would give two messages for one call, and the node would have to dial in the background and keep each `wrap` for as long as the peer stays away. A `monitor` called while the peer is still out of reach answers a `Down` with `Unreachable` once the dial has failed, so that a program that monitors again in a loop is paced by the dial. A client finds its service again after a loss and monitors it again there, which a library, MVP 3.2's `Standing`, does for it (section 14).

**`Unreachable` is a reason of its own.** A watcher told that a process's node is out of reach must be able to tell it from a fault, since the process may live on and a replacement would make two. So `Reason` has `Unreachable`, and a `Down` made at a loss carries it with an empty site, the watcher's node not knowing where the process was spawned. A one-node program pays an arm for it, a `match` on a `Down`'s reason listing a case it never meets; §9.3 states that `Unreachable` comes from a monitor on another node's process alone, and the arm is accepted, since a second `Down` for other nodes would make a process know where an address leads, which an address is there to hide (decided on 2026-10-08).

**The detector stays fixed.** Its timeout is Erlang's, 60 seconds in four intervals, so a silence is found in 45 to 75 seconds; a peer that crashes or exits is seen at once, its host closing the socket. The timeout governs a dead machine and a partition alone, and a program that must know sooner has the deadlines of its calls. The detector counts the intervals it has seen and not the time gone, so a node that was itself stalled sees one silent interval as it wakes and does not lose every peer at once. The timeout is a constant of the protocol: each end sends its idle heartbeat every quarter of it, so the ends must agree, and a constant leaves nothing to negotiate and nothing to set wrong. A detector that adapts would keep a history of delays and a threshold to set, which buys little for a few nodes listed by hand. The number becomes a key of `ernest.conf` when a deployment shows that it must differ. No detector tells a slow peer from a dead one, which is what `Unreachable` says.

**Two processes where one was meant.** A watcher told `Unreachable` that starts a replacement has two where the first lives on. Nothing is added to the language or the runtime for it, since an election and a lease are engines, a library's work (principle 5); the guide teaches three rules that what there is already carries. A program replaces at `Unreachable` only work that may run twice. A process spawned on a peer watches whoever it works for and ends when it is told `Unreachable`, which it is, since both ends run a loss, so no worker runs on unwatched after a partition. And what must exist once lives on one named node and is found there with `Peer.find`: out of reach it is unavailable, nobody else starts it, and moving it is the operator's act in `ernest.conf`; the standard library makes no second one itself, a supervisor's children running on its own node. Between the two ends' timeouts a worker and its replacement can both run for a while, which the first rule makes harmless. A thing that must exist once and move by itself needs a lease its resource checks, or agreement among nodes, a library written when it is wanted.

**One side may be unable to dial.** Behind a translated address a node reaches its peer and the peer does not reach it. One connection carries both ways, so the node that can dial opens it, and the other then sends, answers, spawns and monitors over it. After a loss the node that cannot dial has no way to open the connection again, so the node that can dial watches and opens it again, which is stated as a limit. The configuration follows the fact: a node with no network address of its own does not listen, and a peer listed without one is never dialled, so that no dial is made that can only hang until the host gives it up. The host calls a node that does not listen hidden and leaves it out of its plain list of nodes, so the runtime asks for nodes of every kind.

## 9. Addresses

**An address is the permission to kill, across nodes too.** On one node an address lets its holder send to a process and kill it. With peers the permission travels: every node that finds a service holds its address and can end it for the others. The rule is the one a process already knows, so that it need not know where an address leads, for `kill` as for `send`; the carrier could not keep a narrower promise, since a connected node can end anything on the other; and a `kill` refused across nodes would take from a spawner the means to stop the worker it started on a peer. An address that only sends is a process in front of the service, which a program can write today, and could enter the language later without breaking a program.

**The spawn site crosses with the spawn, and a `Down` from another node's process has none.** The peer records the site from the spawn frame, one string sent once per process, so its faults and `Process.info` name where the process was spawned. Decided on 2026-10-08 that the site crossed in every `Down` the process's node sends, as "the process's node, which recorded the site, gives it with that reason"; that was withdrawn the same day, decided with the user, as MVP 3.0's item 5 was begun, since the host's monitor gives the watcher the exit reason alone, and a process that returns exits `normal` while one killed or ended with its program takes its reason from outside, so none of them can add its site. A site where the process makes its own end would leave a `Down`'s field full or empty by how the process ended, which no reader predicts; a monitor of Ernest's own, a frame to the process's node that answers with the site, would add a message to an operation the host makes without one, which CLAUDE.md's cost rule refuses. So a `Down` from another node's process has an empty site, as one with `Unknown` or `Unreachable` has, §6.9 states the departure, and the node where a process faulted reports the fault with its site on its own standard error, where whoever debugs it reads.

## 10. Messages

**A sender waits, as the host has it.** A sender waits where the buffer to a peer is full, the host's own 1 MB, which says only when the slowing begins. That gives back-pressure, a program that sends faster than the network carries being slowed to the network's speed instead of losing the connection and every monitor and call on it; a bound, since the detector gives the peer up within 45 to 75 seconds and the send then returns; and nothing to build. Its costs are stated as a limit: a `send` across nodes returns at once only while the network keeps up; a process that waits in a send serves nothing from its mailbox, so a stalled peer stalls the processes that send to it, which supervision and timeouts answer.

**Atoms.** An atom crosses as the text of its name, which the host sends once for a connection and as a one-byte index after that, and the receiving node makes an atom only for a name it has never had. In an Ernest value only a constructor's name is an atom, a `String` being a binary, and with one build every node has every constructor's atom from its own compiled modules, so a correct program's traffic makes no atom. An atom is made only for a name a faulty peer invents, and on this carrier that peer can do anything else as well, so the proposal promises nothing against it and says so among its limits. Where builds differ, in MVP 3.1, a peer can send a constructor a node lacks, which adds as many atoms as that peer's code has names, and never as many as it sends messages.

## 11. Calls

**A call's `None` has one meaning.** Across nodes a call ends without an answer in four cases: its time ran out, the callee ended or restarted, the callee's node went out of reach while the caller waited, or no connection could be opened. In the last the request was never sent and did not run; in the others it may have run. A program is not told which, for five reasons. `None` on one node already covers a time that ran out, where the request may run later, and a callee that ended, so other nodes add nothing new in kind. That a request was never sent is known only where no connection could be opened: once one exists, the caller's node cannot know what arrived. A request that may be sent again must be harmless when run twice whichever case it was, so the difference would spare a program one duplicate, seldom, and none of its code. Telling them apart would change `Address.call`'s type on one node too, or give other nodes a call of their own, and a process would then have to know where an address leads, which an address is there to hide. And the reason is to be had: a monitor's `Down` says `Unreachable`, how the process ended, or `Unknown`.

**Every message a process sends goes from that process, and order holds.** A request, a find, a spawn and an `answer` are sent as a plain send is, by the process that makes them, since the host keeps order per sender and receiver: a message sent by any other process on the caller's behalf could be passed by one the caller sends after it, against the first claim of section 4; and a process for each message a stalled peer holds back would be as many as those messages, which no limit bounds, a service answering twenty thousand a second into a stalled peer reaching the host's process limit in under a minute. So a sender to a stalled peer waits in its send, at most the detector's time, and a call's time bounds the wait for the answer and nothing before it, as §6.6 already has it; the exception in the proposal's first rule, where the network is behind, applies to every send, a request and an answer among them. Back-pressure is what a sender should feel, and on one node a send never waits, a mailbox having no limit. A service that pushes to many remote clients does it through a process for each, which the guide's peer chapter says (decided on 2026-10-08).

**A remote call ends at a restart, by a note.** The runtime keeps a table on the caller's node of who waits on whom, which a restart reads to tell each caller, and a callee on another node cannot read it. So a call across nodes sends the callee's node a note that it waits, one frame on the same connection, kept as a row until the callee answers, restarts or ends, with a second note where the caller's time ran out and a loss dropping every row of the peer; without it a remote call would not end at a restart, a `callForever` never, against the claim that every call ends. Since 2026-10-08 the gateway records the notes itself and a restart asks it, as it asks the reaper, since a request that faults its callee could otherwise be read before the note; and the second note goes wherever a call ends otherwise than by an answer on the callee's node, a restart or an end, since a reply answered on another node, or a caller ended while it waited, would leave a row for as long as the callee lives. A `Reply` is the host's alias, which takes one answer; a second answer from another node crosses the wire before the alias drops it, a message's cost and no more, stated so that "takes one answer" is not read as costing nothing. A function of an adapted address that never finishes holds that peer's gateway, as on one node it holds the sender, since a process for each adapted address could never end, nobody knowing when a remote holder drops the address.

**A node with peers declares no deadlock.** On one node the runtime declares a deadlock where no process can be delivered a message any more (§8.6). A node with peers can always be reached from outside, by a message, a spawn or a connection, so nothing on it can be known to wait for ever; a program that waits on itself across nodes hangs, and a time on its calls is the program's answer. `--config-dir` tells the deadlock detector so, since it otherwise counts a monitor on a process it did not start as a source and looks for the deadlock, and the host's lost connection reaches it as a reason of the host's, which it gives as `Unreachable` and never as a fault (decided on 2026-10-08).

## 12. Serialization

**The host's external term format.** Values cross in the host's own encoding, written in C. An encoding of Ernest's own, a constructor written as its position in its type, would put no atom on the wire and owe the host nothing, and would be written in Erlang, value by value against the type; a runtime on another host, or a measured need, would change that.

**What cannot cross is refused by the compiler, and nothing is walked.** A type is bound to its node where it holds a function type, a foreign type, a resource, or an address or reply whose message type is bound. A bound value has two ways to start towards another node, a key of its type and a spawn that captured it, and the compiler refuses both. Every other way follows: an address of a remote process came from a find or a spawn, so its message type is unbound, and so is everything sent to it or answered through a reply in it. So no value is walked before it is sent, which would cost a multiple of the host's send; testing at run time what the type checker knows is wrong. A spawn whose captures have a type variable in their type is refused for now, by the proposal's first rule for what comes after, and `needs`, which already carries a property of a type variable to its use, is the way to relax it. No check stays at run time: an adapted address's captured values cross inside it as payload touched only on the node that made it (section 7), so nothing is looked through at a send.

**The function a spawn on a peer starts is written where the compiler sees it.** Decided on 2026-10-08, as MVP 3.0's item 2 was built. The checker sees what a function captured only where its lambda is written: a function that arrives as a parameter, in a message or from a call carries its captures in no type, and §0 gives a function type one mark, its mailbox. Three ways were weighed. A mark on function types for captures that may cross, as Swift's sendable closures have, would break that one mark and add a concept, against principles 2 and 5. A check at run time of a closure's captures cannot tell an address of a bound mailbox type from any other, the types being gone, and tests at run time what the checker knows. So the rule is on the expression: a declaration's name, which captures nothing, or a lambda written in the definition, at the spawn or bound by a `let` the spawn names, as §6.6 already reads a lambda and the name bound to it; anything else is refused, and `Peer.spawn` is not taken as a value, which would let a call escape the check. The same holds a key's and a spawned mailbox's type to being known whole where they are written, since a type variable there could be made bound by a later instance. The cost fell on `Balancer`, section 16.

**A spawn whose mailbox type is bound is refused too.** Otherwise a function could cross through it: the spawner would hold a remote address of a bound type and send a function through it. The third refusal closes the one way the first two left.

**Another node's processes and resources.** `Process.info` answers for the running node's processes alone and `None` for another node's, since the runtime answers from its own record and asking a peer would be a call a program did not write. The address of a socket, a listener or a program the runtime started, and an `Ets.Table`, are the host's references and mean nothing on another node, so they are bound types and never cross; a supervisor's children run on its own node for the same reason.

## 13. A spawn

**A spawn and a find answer a value, and take a time.** A peer out of reach is no mistake of the program's: it is what a program of several nodes is written to meet, by trying another node, by waiting, or by telling its user, and a process that faults can do none of these. A find answers a value for the same condition, so a spawn does too, and two operations that wait on one peer fail in one way. Without a time a spawner would wait the 45 to 75 seconds the detector takes to find a silent peer, and for ever on a peer that lives and does not answer, which a gateway held up behind a slow function of an adapted address can be; every other wait on a peer has a time, which `Address.call` takes as its last argument too. What stays a fault is the program's own mistake: a function that captured a value that may not cross is wrong on every run, and its own node finds it before anything is sent. A function whose bindings the peer did not run is answered as a value, though the program is where the mistake is, since the spawner cannot know which entry point its peer was started from, a program can choose another peer, and a later milestone may run the bindings, so that a failure becomes an answer and breaks no program. The price is a `match` at every spawn on a peer, where a local `spawn` has none. A spawn whose time ran out may have started its process, as one that lost its connection may.

**A spawn answer no one waits for ends the process it names.** Where the spawn's time ran out while the connection lasts, the answer reaches a node where no one waits for it; the process is killed, which makes true a moment later what the spawner was told, that no process came, where letting it run would keep a process no one can reach or stop. Where the connection was lost instead, no answer arrives and neither node can know, so that process runs on, which is the limit the proposal states.

**From MVP 3.1 the spawn carries a hash, and code crosses.** The function's module and place, which one build made mean the same everywhere, become the function's hash, and a peer that lacks it is sent the closure; the reasons for the exchange are `code.md`'s. What stays is the spawn's shape: a value answered, a time, `NotLoaded` for what the peer cannot be sent, a binding's value or a foreign declaration's module.

## 14. A service and its key

**A service is found by a typed key.** A key is a value that starts nothing, holds a name and a message type's identity, and crosses in place of code; a node offers what its peers may find, and nothing else is found. The compiler holds an offer to one message type, and the peer compares the identity at a find. A function shipped to read one of the peer's bindings would do three things wrong: naming the binding makes the client's program depend on the service's module, so the client's node runs that module's bindings and starts a service of its own, and no arrangement of modules avoids it, since the client needs the module for the message type; a function crosses to look something up, which needs the same function on both nodes and is the first thing to break where builds differ; and every binding of a peer is open to every peer. A key is a registry of a kind, which Ernest has otherwise refused: it holds what a program chose to offer, to peers alone, and on one node a service stays a top-level binding; it is what a reader who knows Erlang expects, a registered name on a node, with a type. Its price is a name the program chooses, so that two services under one name on one node clash.

**An offer under a held key faults, and the table is by name and identity.** Two services under one key on one node are a program's error, so an offer under a key a living process holds faults the caller, as Erlang's `register` fails on a taken name: the mistake is loud where it is made, not seen later at a find that answers the wrong one. A deploy and a restart need no silent replacement: a `restarting` loop keeps its address, so its offer stands through its faults; a supervisor's new child offers again because the old process has ended, and the offer ended with it, so there is no race. The table holds one address for each key's name and type identity, so that a node offers one key at two identities, the new protocol and the old through a conversion, which MVP 3.2's rollout needs (`deploy.md`); a find compares the identity anyway, and answers the one its key asks for. A set of addresses under one identity would make a find answer a list the finder must choose from, the beginning of a cluster. Nothing of the program's withdraws an offer: it ends with its process, which is what a program means by it; MVP 3.2's planned stop withdraws a node's offers before it ends, its reasons `deploy.md`'s (decided on 2026-10-08). Only a process of the offering node may be offered, since an address of a third node's process would reach a node the finder may not list, and the offering node would have to watch the process across a connection to know when the offer ends; by the proposal's first rule for what comes after, it faults the caller now and may be allowed later.

**In MVP 3.0 a key carries its type's text.** With one build on every node a type's name says everything a hash would: one build has one definition for each qualified name, so two keys name one type exactly where their types print the same. A key holds the message type's text as the compiler prints it, and a find compares the texts, which catches two services under one name with different types at a string comparison once per find. The compiler takes the type where `Peer.key` is written and refuses one not fully known there.

**From MVP 3.1 a key carries its type's identity.** Once builds differ a name no longer says what a type is, so the key carries the type's hash, and with it its `compare`'s hash and no other member's, so that a value ordered under one order never meets code that orders it under another, and a change to any other member changes no protocol; `compare` stands beside the hash and not in it, since a member's tree names the type and no hash may contain a hash that names it. `OtherType` at a find then means a service at another version.

**A key's peers, and the one find.** Decided on 2026-10-07 with MVP 3.2's deploy, and narrowed to one find on 2026-10-08. `ernest.conf` lists, for a key, the peers that may offer it, and `Peer.find(key, ms)` asks them in the list's order; it is the one find, and no find names a node. Where a service lives is the configuration's and not the program's: the operator moves a program to another machine by editing `ernest.conf`, and a client with a node's name in its source would be rebuilt for a move that touched no code; a service on one node is an entry of one peer, and a key with no entry answers `NotListed`. `Peer.spawn` names a node, and should, since placing work is the program's decision; asking for a service someone else placed is not. Each peer is given the time left, and the find passes over `Unreachable`, `Refused`, `NotOffered` and `OtherType`, answers the first address, and otherwise the last failure met, or `Timeout` where the time ran out. The peers are asked in order and not at once, so that the list's order, which is the operator's preference, decides which of two peers offering by mistake is found, where asking all at once would let the faster answer decide. The costs are stated as limits: a silent peer early in the list can take the whole time, the host's dial of 7 seconds being longer than many a find's `ms`; a find may dial several peers where the operator has moved a program, bounded by the list; and two of a key's peers offering at once is possible by mistake. No election follows and at a failure nothing moves by itself: a service whose node is lost is unavailable until the node returns or an operator edits the configuration, since one owner across a failure needs a lease in a store outside the nodes (*O3*, *A5*), a library's.

**A standing address is a library's, not `Peer`'s.** Decided on 2026-10-08. A process the runtime spawns and the program never sees breaks the rules the report states for an address: `kill` through it would kill the forwarder and not the service, `Process.fromAddress` would name the forwarder, a call through it would have the forwarder as its callee and not notice a dead service until its time ran out, the forwarder would belong to no one and never end, and it would find again at a cadence the runtime chose, against the first rule that the runtime retries nothing; every repair adds a special case to the report's rules for one kind of address. Written in Ernest, as `Standing.start(key, ms)` of a library of MVP 3.2's over `Peer.find` and `monitor`, the whole thing is an ordinary process the program spawned, and every rule holds without a word added: `kill` kills the process the program started, `Process.fromAddress` names it, a monitor on it says when it ends, a call through it ends by its time where the service is away, and the forwarder's one extra hop is what any process in between costs. The gap keeps a loss's semantics, which the program already knows: a send during it is dropped as a send during a loss is, and a call waits by its own time and answers `None` where the service is not back; holding sends through the gap would need a bound and a rule for what the bound drops, which dropping needs not. The library always answers an address, so a client written before its service is up needs no loop of its own, and it monitors its caller and ends with it, so nothing is left finding. A program that wants the service's own `Process`, to monitor it directly, holds the address `Peer.find` gives; the two are different tools and say so. What no library hides is the call itself: a `None` may or may not have run (section 11), so the retry is the program's.

## 15. Bindings

**A node runs its own bindings, and nothing for a peer.** A node evaluates at its start the top-level bindings of the standard library and of the modules its entry point depends on, as a program on one node does, and listens only once they all have their values. A function spawned on it runs only where the bindings it depends on have their values there, and otherwise fails with `NotLoaded`: an initializer may spawn, send and call, and the types do not tell a constant from a service, so evaluating one because a peer asked would start processes nobody on that node asked for. A spawned function captures what it needs instead; captured values cross and bindings are the node's own. In spawned code a top-level binding is the peer's and a captured value the spawner's, so the system processes are the peer's and a spawned process's output is the peer's. The rule is one, whatever a binding's value: a top-level binding named in the function is the peer's, and a value the function is to carry from the spawner is bound to a local first, `let key = Counter.key`, and captured as any local is, so that the text alone shows which names are locals and nothing is read off a binding's type (`mvp3.1.md`, decided on 2026-10-08).

**Read by module, decided on 2026-10-08 as MVP 3.0's item 8 was built.** The runtime knows a function's dependencies by its module, which §8.5 initializes whole and after the modules it depends on, so a function spawns on a node where its module and every module that module depends on have their bindings' values there. A function that names no binding is refused with a module that has one the node never ran, and a program keeps a function it spawns on a peer in a module the peer's program also depends on, or in one without bindings. A table of each declaration's dependencies would make the rule exact at a cost every compiled module and every spawn would pay, where MVP 3.1's hashes make it exact for nothing more. **A node dials after its bindings, as it listens**: its carrier starts once they have their values, so a find or a spawn in an initializer answers `Unreachable`, and no spawn reaches a node before its bindings have theirs.

**From MVP 3.1 bindings are held by hash.** A spawned function finds a binding's value where the peer's own build ran that hash, which it did wherever the definition is unchanged between the builds, and `NotLoaded` otherwise; nothing changes in the rule. A service is one per node, key name and type identity, an offer under a held key faulting, so no second service is started unseen when builds differ. A node started with no `.erc` at all, a bare node, falls out of the same rules: it runs the standard library's bindings and nothing else, takes what its peers spawn on it, and offers what those processes offer.

## 16. Placement by load

**Placement by load is two libraries and one function of `Peer`.** `Peer.nodes` is `Peer`'s, since only the runtime has the configuration, and answers the listed peers without the running node, which is no peer of itself, and without a peer marked `coordinator`, which runs no program and would otherwise be placed on (`mvp3.2.md`, decided on 2026-10-08). How busy a node is has nothing to do with peers, so the host's measures, the run queue, the schedulers' utilisation, memory and disk, are a library of their own, `Load`, each a shim, the last two answering a failure where `ernest.conf`'s `measures` did not start the host's services. The balancer is a process, round robin unless given a measure, a measure a function to 1.0 that a program installs on each node by spawning there a process running `Balancer.serve(measure)`, which offers itself under `Balancer.key`; since 2026-10-08, decided with the user, the process runs `Balancer.serve(balancer, place, measure)` and registers with the balancer, since one find names no node and could not reach the two places a pick draws. The balancer picks a place and the program spawns its work there: a balancer handed the program's function could not spawn it on a peer, since a spawn on a peer starts only a function written at it (section 12, decided on 2026-10-08), and a place this node or a peer's name lets the program write the two spawns over one `let` of its lambda. Load is pulled, not spread: a pick draws two candidates at random and calls each, the two-choices rule, so a pick costs two calls whatever the number of nodes and nothing is ever stale or gossiped. The library's own type of a place, this node or a peer's name, is fine for a library where it was not for the prelude. Both libraries are in MVP 3.0, as its last items, because they need nothing the proposal does not give and are the first real programs on it.

**A measure is installed from the program's side.** The program spawns the measuring process on any place, this node or a peer, rather than each node calling it for itself, so that one way installs a measure everywhere, and from MVP 3.1 a bare node, which runs no program of its own, is measured and placed on like any other; the measure's functions are the `Load` library's, the platform's, so they exist on every node.

## 17. The shell

**A shell is a node, and in MVP 3.0 loads nothing.** A shell with a configuration is a node like any other and the remote console people want at no cost. In MVP 3.0 a function typed at it is in a module no peer has, so a spawn of it answers `NotLoaded`, and `:load` and `:reload` are refused in a shell that is a node, since code the build does not have would be spawned on a peer by a reference the peer resolves to other code. From MVP 3.1 both refusals lift: a function typed at the shell has a hash and spawns with its code, and a load adds hashes and moves the session's names.

## 18. `Peer`'s shape

**One failure type, with a text in `Refused`.** `Peer.Failure` serves a find and a spawn both, as `Io.Error` serves every operation on a file, though a find never meets `Refused` or `NotLoaded` nor a spawn `NotOffered` or `OtherType`: §4.2 lets no two types of one module share a constructor, so two types would need two modules or three constructors renamed, which is more than the arm costs; the proposal states which constructors each operation answers, and a program writes `_` for what its operation cannot meet, the one cost (weighed again on 2026-10-08). `Refused` carries a text, since a program cannot act differently on why a peer could not load what was sent, only report it, and a text leaves room for a peer to refuse for more without a new constructor, which the proposal's second rule for what comes after asks; the handshake's own refusal reaches the dialler as `Unreachable` (section 6). `OtherType` and `NotLoaded` are named for what they will also mean later: a service at another version, and code the peer does not have.
