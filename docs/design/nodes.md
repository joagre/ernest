# Ernest's Nodes: Design

Status: the nodes' design note, which changes when the carrier, the gateway, the peers' workers, the notes or the processes kept for addresses do; the code table and the exchange are [`code.md`](code.md)'s. It is not a proposal, and not authoritative: the report states what a program is promised of nodes, in §6.5, §8.3, §8.7, §11.2, §11.3 and Appendices C and E.27, and this note states the shape the runtime keeps those promises by, as it stands. A line here is a shape a reader must know to change the component without breaking a promise, never what one function does, which is the code's; the module map and the tables are [`architecture.md`](../architecture.md)'s, the runtime's own bookkeeping is [`runtime.md`](runtime.md)'s, and the reasons are the log's, named at each line. How the design was weighed is the log's, *The Nodes' Reasons, Kept* and *What Other Systems Taught the Nodes* among its entries; the proposals it came from stood under `docs/proposals/nodes_and_code/` until 2026-10-24. Where the code and this note differ, the code is what is built and this note is corrected.

## The rule

Two nodes are two files and one connection, and what passes between them is the host's distribution carrying the host's terms: a message between nodes costs what the host's send costs, and the runtime adds a frame of its own only where the receiving node must do something a message cannot, start a process, apply a function, record a wait, carry code (§8.7, *What passes*). Nothing is initialized, evaluated or loaded because a peer asked, beyond the code a spawn or a compute carries: a binding is its node's own, and a bare node runs what it is sent and nothing else (§8.7; the log's *The Module Peer*, *What the Outline Asked*). A node trusts a listed peer whole and no one else: the list of peers is the whole of the trust, and a peer that may spawn may run anything (the log's *The Carrier*).

## A node

A node is a running runtime with a configuration directory, whose key is its identity (§8.3, §11.3). Its name on the carrier is a constant at the digest of its public key and names no network address: a peer's address is the configuration's alone, resolved by the host at each dial and not when the file is read, and the node's own port map, `ern_epmd` in place of the host's, answers a dial from the configuration, so that no port mapper runs and connections are never transitive (§8.7, *Its configuration*, *Connections*; the log's *The Carrier*). A node runs over one family of addresses, its listener's, or IPv4 where it has none, and refuses a peer of the other family when the file is read. The carrier is the host's distribution over TLS 1.3, each side with the certificate it signed itself, whose subject is the same for every node and whose dates mean nothing, with what hurts in the host's distribution turned off: the handshake's verification accepts a peer by its listed key under the name that key gives, and on a dial under the name dialed, and refuses every other, saying why; the cookie is the digest of the floor, the protocol's version, the form's version, `ern`'s major and minor and OTP's major release, or of a development build's own code, so that two nodes of different floors never pass the handshake, and nothing of the program's build is in it (§8.7, *Connections*; `ern_carrier:verify/3`, `cookie/0`). The flags the host boots with are the carrier's, asked of it by the launcher before the host starts, so that `ern config`, `ern reload` and `ern stop`, which make no node, start the host once (`ern_carrier:boot_flags/1`; the log's *Two Nodes on One Machine, Built*).

A node writes its process number to `ernest.pid` and holds the file locked for its life, which the host ends with the process however it ends, so that a second start finds the lock and refuses, and `ern stop` waits on the lock for the node's end (§8.7, *Its start and its end*; §11.2). It starts the host's measures its file names, and its listener once its bindings have their values, so that nothing of a peer's arrives before them (§8.5, §8.7; the log's *The Carrier*, *The Module Peer*). Each start of a node has a number the host draws into every address, so that an address of an earlier start is dead on arrival (§8.7, *Addresses*). Its end is told: it stops in order, every `Down` already on its way crossing before its connections close, and sends each connected peer the frame that it ends, so that the peer says `ended` and not `lost` (§8.6, §8.7; `ern_carrier:depart/0`). A reload, which the hangup signal asks of the carrier, reads `ernest.conf` again and changes what the file may change, a peer added, removed or renamed, the measures and the utilization's entries, and never the node's own key or `listen` (§8.7, *A reload*; `ern_signals`). The lines a node says of its peers, one each on its standard error, are the carrier's (`ern_carrier:say/1`), written as a fault's line is, to the launch's standard error process while it takes such lines and to the job's error device while none does (§8.7, *What it says*; §11.2).

## The gateway and its workers

A node has one gateway, a registered process that takes every frame of the runtime's from every peer from the node's start, so that the frame which opens a connection finds it. It reads some frames itself and hands the rest to a worker for the sender's node: a call's two notes it records, a compute's frame it records as the call's first note and hands on, a utilization it answers with the node's measure, or the number the program set where one is, a telling it holds with the moment it came and the teller's interval, a node's end it records against the loss to come, and the exchange's four frames it hands to the exchange's process (§8.7, *What passes*, *Calls*, *A utilization*). A worker is one process for one peer across the losses of that peer's connection: it applies the frames in the order they came, runs the loss once it has read every frame that came before it, reads those that come after the connection is opened again, and asks the gateway to end it, `{idle, Node, Worker, Taken}`, once it has run one loss and holds no frame and no process kept for an address, `Taken` the count of the frames the gateway handed it, so that no frame handed meanwhile is lost; the worker ends at the gateway's `stop` (§6.4, §6.5; the log's *The Runtime's Own Processes*, *Kill Darlings* on the kept process). A frame the gateway cannot read is faulty, and the node ends the connection; a message to the gateway that names no process of a peer names no connection, and is dropped and said. The gateway is the teller too: one timer of its own, armed from the interval, and a telling sent to every connected peer with no dial, so that a telling never opens a connection; it keeps the measure's one reading for asks and tellings alike, since the host keeps the schedulers' time for the one process that turned it on (the log's *Placing Work by Name*).

The frames are fifteen, listed in the runtime's note and in §8.7's *What passes*, and a test holds both lists to the modules that read them (`test/ern_docs_tests.erl`, `runtime_frames_test`). Everything else that crosses is the host's: a message straight into the mailbox, a monitor and its `Down`, an answer through an alias, a sign of life, the handshake. A `kill` of a process of another node is a frame to that node, which carries it out as its own kill, suspending the victim, reading its call and ending it (§6.9; the runtime's note, *A call, a restart, a kill*).

## A loss

A connection is lost when the network breaks it, when the host's detector finds the peer silent, a tick where nothing else was sent for fifteen seconds and four such intervals without an answer, so between 45 and 75 seconds, or when a frame is faulty (§8.7, *A loss*); the tick, the dial's seven seconds and the buffer's size are boot flags `ern` sets the same on every node, none in `ernest.conf`, since the two ends must agree. Each node is told by its own host, as `nodedown`, the gateway watching nodes of every kind since a node without a listener is hidden to the host, which the gateway hands the peer's worker as `{lost, Order}`, `Order` the place among the node's moments at which the gateway learned of it, and the worker runs the loss after the frames that came before it: a `Down` with `Unreachable` for each monitor on the peer's processes, the end of each call waiting on one of them and of each wait on the peer that began before the loss, a spawn's, a find's, a compute's and a utilization's, which the gateway's ordered table of spawns tells apart by the moment each was written (`ern_spawns`), and the drop of what waited to be sent, the peer's notes and its utilization (§8.7; the log's *The Nodes' Reasons, Kept*, *The Runtime's Own Processes*). A node whose peer dials it anew while it believes the old connection alive runs the loss of the old one first. No connection is opened again in the background: the next operation towards the peer dials, a refused dial failing at once and one that nothing answers given up after seven seconds, and until then what the other node sends vanishes and its monitors say `Unreachable`. What waits to be sent to a peer waits in the host's buffer for that peer, 1 MB, and a sender that finds it full waits in the send until it drains or the detector gives the peer up (§8.7, *Messages*).

## Addresses

An address names its process for as long as the process lives, on whichever node, and is as good on a third node as on the one that made it; a loss does not end it, and an address of an earlier start of its node is dead (§6.5, §8.7, *Addresses*). An adapted address holds its function, its target, its maker and the launch it was made in, `{adapted, Function, Target, Maker, Launch}`: the function is applied on the node that made the address, never where the message is sent from, so that a function never crosses in a message and a type that holds one stays bound to its node (§3.11, §6.5). A message to it from another node is a frame to the making node, whose worker for the sending peer keeps one process for each address that peer sends to, a `#kept{}` with the process, the worker's monitor of it and the messages waiting, hands it each message in the order the frames came, `{apply, Message}`, and tells it to stop once none waits; a kept process acts for the maker, so that what the function opens is the maker's and `Process.current` in it is the maker (§6.5, §6.9, §8.7; `ern_rt:kept/1`; the log's *The Runtime's Own Processes*). The launch's tag ends the address with the launch, so that a later run of the same node, the next run of `ern test` over a directory among them, drops what is sent to it wherever its function would be applied (§6.5, §11.2; the log's *The Sitting on §8.6's Bookkeeping*). An address exposed to foreign code has a checker in front of it, which is the runtime's note's.

## Calls and computes across nodes

A call's reply is the host's alias, which takes one answer and drops any other; the caller monitors the callee while it waits, so the callee's end and a loss both end the call (§6.6, §8.7, *Calls*). A call to a process of another node sends that node a note that this caller waits, a row of `ern_notes` beside the call's row of `ern_callees`, keyed by the caller's node so that a loss drops a peer's notes together; a restart in place reads every note that came before it and tells each caller `restarted`, and a note comes before its request but for one through an adapted address made on a third node; a call that ends otherwise, its time run out, answered from another node or its caller ended, sends the second note, by which the node lets the first go (§6.6, §6.9, §8.7; the log's *Calls Across Nodes*). A compute's frame is the call's first note: the peer starts a process, the compute's callee, a row beside a call's, records the compute's site for it, and the function's value or its fault crosses back through the alias, the fault whole with its trace so that the caller faults as if `f()` had faulted in it; the call's second note kills the callee where the caller gave up first, and a fault once the note has gone is the process's own, reported on the peer (§8.7, *A compute*). The value crosses back at the type the compiler checked at the compute, which the peer holds too, in `f`'s form.

## A spawn

A spawn's frame carries the function's identity, its captures in the order its body first names them, a reply among them crossing as in a message, its site and its time, and for `restarting` the limit and the inner function's identity (§8.7, *A spawn*; §11.1; `ern_peer`'s `spawned()`). The peer's gateway finds the identity in the node's code table and starts the process through the node's runtime, recording the site as a local spawn's with the peer whose spawn started it in the process's row, or answers `NotLoaded` where a binding of the function's reach has no value there or a foreign declaration's module is missing, or, where it lacks the function, hands the spawn to the node's exchange; the answer goes back through the spawner's gateway, which kills a process no one waits for any more, its spawner's time run out while the connection lasted (§8.7, *A spawn*; the log's *The Spawn by Hash, Built*). What the peer lacks of the function's reach the exchange brings, which is the code note's ([`code.md`](code.md)). A function typed at a shell has a hash as any definition has, and crosses the same way (§11.2).

## Services and the pick

A service a peer may find is an offer, a row in `ern_offers` under the service's name and its message type's hash, and a row in `ern_offered` for the process whose address is offered, kept while that process lives and never withdrawn; a second offer under a held name answers the holder, so that the caller may monitor it and offer again at its end (§8.7, *A service and its name*). A find asks the peers `services` lists under the name, in order, each given the time left, through their gateways, each comparing the hash and answering the address, `NotOffered` or `OtherType`; it ships no code (the log's *The Nodes' Reasons, Kept*, *The Service Named*). A node tells each connected peer how busy it is every `utilization-interval`, and once as the peer connects, the telling carrying its interval, in place of the host's own idle tick where one would go; the gateway holds each peer's last telling with the moment it came, in `ern_utilizations`, one row per peer by its name on the carrier, so that a peer a reload renames keeps its row, each telling replacing it and a loss dropping it, so that the table is bounded by the configuration; a compute that names no peer draws two of the peers whose telling is no older than two of its intervals, at random, and takes the less busy, the first drawn where they are equal (§8.7, *A utilization*; the log's *Placing Work by Name*, *The Numbers Across Machines*). The node's own measure is the processes running or ready to run, the one measuring left out, over its schedulers, or its schedulers' time since the last reading, read from the host's counters with no scan; the number a program set with `Peer.setUtilization` is a row of the launch's, told and answered in the measure's place until it is set again, and gone with the run (`ern_rt:set_utilization/1`). A pick is a read of the held rows and a draw, a few microseconds and no frame.

## Costs

A message between nodes is the host's send. A spawn on a peer that holds the function is a frame and an answer, a few milliseconds on one LAN; the first spawn that carries code to a bare node is the slow one, about 250 milliseconds on a machine of eight cores and 650 on one of two, most of it the host's compiler starting, and every spawn after it that carries code pays the exchange's own cost, under a hundred milliseconds for a definition of ordinary size (the deployment guide's §3.4; the log's *The Numbers Across Machines*, *What MVP 3.1 Costs, Measured*). Three idle nodes exchange about 1.2 packets a second at the default telling interval, the tellings in place of the host's idle ticks and not beside them (the deployment guide's §3.2). A process kept for an adapted address costs its peer's messages one hop more on the making node, and nothing to any other process (§6.5; the log's *The Sitting on §8.6's Bookkeeping*). A correct program's traffic makes no atom on a node but in three bounded cases, a spawn's or a compute's captures, which the host decodes before the identity is looked up, an adapted address made in a unit the receiver lacks, and the name of a node not yet met; a faulty peer can make any atom, which the trust in a listed peer admits (the log's *The Spawn by Hash, Built*).

## What the nodes' machinery does not do

It opens no connection in the background and sends nothing a second time: a message arrives once or not at all, and where one is dropped the connection is lost with everything that waited (§8.7, *Messages*). It connects no third node through a second: that A knows B and B knows C connects A and C in no way. It evaluates no binding, runs no initializer and loads no module because a peer asked, beyond the reach a spawn or a compute carries, so a bare node's offers are what the processes spawned on it offer and nothing of its own. It looks for no deadlock on a node, since a peer can reach it (§8.6). It keeps nothing for a peer it has lost but what §8.7 names, a node's end recorded against the loss and a worker that lives until it holds no frame and no kept process. And it names no node to itself: a program that must say where it runs is given the name by whoever spawned it (the log's *What the Feedback Left*).
