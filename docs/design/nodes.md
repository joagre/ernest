# Ernest's Nodes: Design

Status: the nodes' design note, which changes when the carrier, the gateway, the peers' workers, the notes or the processes kept for addresses do; the code table and the exchange are [`code.md`](code.md)'s. It is not a proposal, and not authoritative: the report states what a program is promised of nodes, in §6.5, §8.3, §8.7, §11.2, §11.3 and Appendices C and E.27, and what the carrier does, in §12.5, §12.6 and §12.8, and this note states the shape the runtime keeps those promises by, as it stands.

A line here is a shape a reader must know to change the component without breaking a promise, never what one function does, which is the code's; the module map and the tables are [`architecture.md`](../architecture.md)'s, the runtime's own bookkeeping is [`runtime.md`](runtime.md)'s, and the reasons are the log's, named at each line. How the design was weighed is the log's, *The Nodes' Reasons, Kept* and *What Other Systems Taught the Nodes* among its entries; the proposals it came from stood under `docs/proposals/nodes_and_code/` until 2026-10-24. Where the code and this note differ, the code is what is built and this note is corrected.

## The rule

Two nodes are two files and one connection, and what passes between them is the host's distribution carrying the host's terms: a message between nodes costs what the host's send costs, and the runtime adds a frame of its own only where the receiving node must do something a message cannot, start a process, apply a function, record a wait, carry code (§12.6, *What passes*).

Nothing is initialized, evaluated or loaded because a peer asked, beyond the code a spawn or a compute carries, among it the shell's of a build other than the node's, whose own the node holds from its start: a binding is its node's own, and a bare node runs what it is sent and nothing else (§8.7, §12.7; the log's *The Module Peer*, *What the Outline Asked*, *The Shell Attaches as a Program Spawns*, *A Node Holds the Shell*). A node trusts a listed peer whole and no one else: the list of peers is the whole of the trust, and a peer that may spawn may run anything (the log's *The Carrier*).

## A node

A node is a running runtime with a configuration directory, whose key is its identity (§8.3, §11.3). Its name on the carrier is a constant at the digest of its public key and names no network address: a peer's address is the configuration's alone, resolved by the host at each dial and not when the file is read, and the node's own port map, `ern_epmd` in place of the host's, answers a dial from the configuration, so that no port mapper runs and connections are never transitive (§12.5, *Its configuration*, *Connections*; the log's *The Carrier*). A node runs over one family of addresses, its listener's, or IPv4 where it has none, and refuses a peer of the other family when the file is read.

The carrier is the host's distribution over TLS 1.3, each side with the certificate it signed itself, whose subject is the same for every node and whose dates mean nothing, with what hurts in the host's distribution turned off: the handshake's verification accepts a peer by its listed key under the name that key gives, and on a dial under the name dialed, and refuses every other, saying why; the cookie is the digest of the floor, the protocol's version, the form's version, `ern`'s major and minor and OTP's major release, or of a development build's own code, so that two nodes of different floors never pass the handshake, and nothing of the program's build is in it (§12.5, *Connections*; `ern_carrier:verify/3`, `cookie/0`).

The carrier's distribution module is the node's own, `ern_tls_dist`, whose acceptor is the node's and whose every other function is the host's TLS one (`inet_tls_dist`), over the node's family of addresses. The acceptor takes each connection itself before it makes the connection's process, so that a spawn it cannot make closes that connection and leaves the acceptor accepting. Each later step that needs room, the host's TLS, its handshake and the handshake's timer, closes the connection the same way, and the node says so, by the address before the TLS handshake gives the key and by the peer after (§12.5; the log's *The Carrier's Acceptor at a Full Table*).

At the limit of open files the acceptor tries again once a dial's time has passed, since the host signals no file freed. A dial is the host's alone, so a dial from a full table is not the module's to refuse.

The acceptor speaks `net_kernel`'s side of a connection as the host's guide to a carrier states it, the ERTS User's Guide's *Alternative Carrier*. It rests on three things of the host's that the guide does not promise. The first is `inet_tls_dist`'s exported functions over a family of addresses and its server's options. The second is the messages the host's TLS acceptor and its handshake trade, `{Acceptor, controller}` among them. The third is `net_kernel` passing the answer of `accept_connection/5` to the acceptor unread, which lets the module answer `limited` where the guide asks for a process. A new OTP is read against the three, and the acceptor's tests at a full table hold them.

The flags the host boots with are the carrier's, with the limits of processes and ports `limits` names, asked of it by the launcher before the host starts, so that `ern config`, `ern reload` and `ern stop`, which make no node, start the host once (`ern_carrier:boot_flags/1`; the log's *Two Nodes on One Machine, Built*, *A Node's Limits*). That reading checks the directory as the start does, its modes among it, and makes a missing `certificate.pem` from the key, since the TLS options name the file on the host's command line; `ern reload` and `ern config --peer-dir` read it making none (§11, §12.5; `ern_node:read/2`).

A node writes its process number to `ernest.pid`, and the runtime's helper holds the file locked until the node's process has ended, however it ends. It then removes the file, where the path still names it, before it lets the lock go. So a second start finds the lock and refuses, and `ern stop` waits on the lock for the node's end. The helper watches the process by the operating system's own call for it, and a host that has none refuses the start (§12.5; §11.2; the log's *A Lock Held to the Process's End*). It starts the host's measures its file names, and its listener once its bindings have their values, so that nothing of a peer's arrives before them (§8.5, §8.7, §12.5; the log's *The Carrier*, *The Module Peer*).

A carrier that cannot start ends the node there, before `main`, as a job that cannot start, its line the job's, once the end has told the subscribers of `Os.subscribeTermination` and waited for them, as at any end (§12.5, §8.6, §11.8; `ern_rt:refused/1`; the log's *The Shell's Own Node*, *The Release Review Before 0.7.0*). Each start of a node has a number the host draws into every address, so that an address of an earlier start is dead on arrival (§8.7, *Addresses*).

A node's end is told: it stops in order and sends each peer connected when it begins to stop the frame that it ends, after what is placed for that peer, so that the peer says `ended` and not `lost`. It waits for no exit that still places a message or a `Down`, which the host calls gone at once, so the halt drops what is not yet placed, and a peer that connects after the list is read is told nothing (§8.6, §8.7, §12.6; `ern_carrier:depart/0`; the log's *A Node's End Waits for No Send*).

A reload, which the hangup signal asks of the carrier, reads the configuration directory again as the start reads it, the directory the node started with whatever the working directory is since, a doc example's run setting it (§11.2), and changes what the file may change, a peer added, removed or renamed, the measures and the interval of the tellings, and never the node's own key, `private-key.pem`'s, or `listen`; a missing certificate is made once the key is found the running node's, and a changed `limits` is checked, and holds from the node's next start, which the node says (§12.5, *A reload*; `ern_signals`; the log's *A Node's Limits*).

The lines a node says of its peers, one each on its standard error, are the carrier's (`ern_carrier:say/1`, and `say_later/1` for the gateway, the checks of a peer and a reload, which wait on no stream, the runtime's note's *The process model*), written as a fault's line is, to the launch's standard error process while it takes such lines and to the job's error device while none does (§12.5, *What it says*; §11.2). An attached shell's own node says no line of the end or the loss of the node its session runs on, which the shell's own line says; the shell's job puts that node's name on the carrier once, as the node starts (§11.2 *The attached shell*; `ern_carrier:attaching/1`; the log's *The Attached Shell's Own Node, Quiet*).

## The gateway and its workers

A node has one gateway, a registered process that takes every frame of the runtime's from every peer from the node's start, so that the frame which opens a connection finds it. It reads some frames itself and hands the rest to a worker for the sender's node: a call's two notes it records, a compute's frame it records as the call's first note and hands on, a utilization it answers with the node's measure, or the number the program set where one is, a telling it holds with the moment it came and the teller's interval, a node's end it records against the loss to come, and the exchange's four frames it hands to the exchange's process (§12.6, *What passes*; §8.7, *Calls*; Appendix E.27, *A utilization*).

A worker is one process for one peer across the losses of that peer's connection, made as the connection opens, which the host tells the gateway before any frame over it, so that no frame waits on a spawn; a connection the full table leaves no room for a worker is closed as it opens, and the node says so (§12.5, *Connections*).

A worker applies the frames in the order they came, runs the loss once it has read every frame that came before it, reads those that come after the connection is opened again, and asks the gateway to end it, `{idle, Node, Worker, Taken}`, once it has run one loss and holds no frame, no process kept for an address and no restart's deliveries, `Taken` the count of the frames the gateway handed it, and of the connections opened again it was told of, so that no frame handed meanwhile is lost; the worker ends at the gateway's `stop` (§6.4, §6.5; the log's *The Runtime's Own Processes*, *Kill Darlings* on the kept process).

A frame the gateway cannot read is faulty, and the node ends the connection; a message to the gateway that names no process of a peer names no connection, and is dropped and said. The gateway is the teller too: one timer of its own while the node lists peers, armed from the interval, and a telling sent to every connected peer with no dial, so that a telling never opens a connection (the log's *Placing Work by Name*).

The gateway waits on no peer: what it sends a peer itself goes by the host's `nosuspend`, and what the host would hold, the peer's buffer being past its limit, is not sent: a telling is stale by the next one, so one not sent is the right answer, where every other process that serves the whole node sets `async_dist` (Appendix E.27; §8.7, *Messages*; the log's *What a Full Buffer Holds*).

A node ends a connection at three places: a frame it cannot read, a reload that removes a peer, and the refusal at a full table. Each asks the host by `net_kernel:async_disconnect/1`, which sends the connection's process its exit and waits for nothing. The host's `erlang:disconnect_node/1` waits for that process's end in the host's process of the node's connections, which a process that stands in a send to a full socket holds without limit ([`otp_bugs.md`](../otp_bugs.md), report 26). The connection ends when the host closes it, and until then the peer's frames are served (§12.5, *A reload*; the log's *The Disconnect Waits for Nothing*).

The processes of the runtime's that serve the whole node and send a peer a signal of their own wait on no peer either: the killer, the reaper and the exchange's process each set the host's `async_dist`, so that what one sends a peer is placed in that peer's buffer whatever it holds, and is taken by the peer or dropped at the loss. The host counts nothing they place against the buffer's limit, so a program's `send` waits as §8.7 has it.

Each of the three sends a peer one signal for one operation of a program's or one frame of the peer's, and never a stream of its own making: the killer a call's second note; the reaper a monitor, a demonitor, a call's second note and, to a compute's caller, how the compute's process ended; the exchange its frames, each answering a frame of the peer's. A test holds the list to the code (§6.9, §8.7, §12.7; the log's *The Runtime's Processes Wait on No Peer*).

A peer's worker sets the flag around one send alone: the fault it sends an adapted address's process where the full table left no room for the process kept for the address (`ern_rt:kept/1`). That process may be on a third node, whose full buffer would hold the worker, and its own peer's frames behind it. Every other send of a worker's that leaves the node goes to its own peer (§6.5, §12.5; the log's *What a Peer's Worker Waits On*).

The frames are seventeen, listed in the runtime's note and in §12.6's *What passes*, and a test holds both lists to the modules that read them (`test/ern_docs_tests.erl`, `runtime_frames_test`). Everything else that crosses is the host's: a message straight into the mailbox, a monitor and its `Down`, an answer through an alias, a sign of life, the handshake. A `kill` of a process of another node is a frame to that node, which carries it out as its own kill, suspending the victim, reading its call and ending it (§6.9; the runtime's note, *A call, a restart, a kill*).

## A loss

A connection is lost when the network breaks it, when the host's detector finds the peer silent, a tick where nothing else was sent for fifteen seconds and four such intervals without an answer, so between 45 and 75 seconds, or when a frame is faulty (§8.7, *A loss*, §12.6); the tick, the dial's seven seconds and the buffer's limit are boot flags `ern` sets the same on every node, none in `ernest.conf`; the dial's time is stated once, which the shell asks (`ern_carrier:dial_ms/0`).

Each node is told by its own host, as `nodedown`, the gateway watching nodes of every kind since a node without a listener is hidden to the host, which the gateway hands the peer's worker as `{lost, Order}`, `Order` the place among the node's moments at which the gateway learned of it, and the worker runs the loss after the frames that came before it.

The host says `nodedown` once it has closed the connection: at once after the detector's decision where the socket holds nothing the peer has not taken, and about ten seconds after it, a time of the host's own TLS, where the socket is full (§12.6; the log's *A Connection That Cannot Drain*).

The loss is a `Down` with `Unreachable` for each monitor on the peer's processes, which the reaper gives as the host ends its monitor of each with `noconnection`, ending first each delivery of `Restarted` for that process not yet placed, so that no `Down` follows the loss's (*A restart*), the end of each call waiting on one of them and of each wait on the peer that began before the loss, a spawn's, which the gateway's ordered table of spawns tells apart by the moment each was written (`ern_spawns`), and a find's, a compute's, a utilization's and a restart's wait for the peer's answer, each by its waiter's watch of the peer's gateway, and the drop of what waited to be sent, the peer's notes and its utilization (§8.7; the log's *The Nodes' Reasons, Kept*, *The Runtime's Own Processes*).

A node whose peer dials it anew while it believes the old connection alive runs the loss of the old one first. No connection is opened again in the background: the next operation towards the peer dials, a refused dial failing at once and one that nothing answers given up after seven seconds, and until then what the other node sends vanishes and its monitors say `Unreachable`.

What waits to be sent to a peer waits in the host's buffer for that peer, whose busy limit `ern` sets to 1 MB (`+zdbbl 1024`), or waits to be placed there. A program's `send` is the host's plain send. That send places a message above 64 KB in fragments of 64 KB while less than the limit waits, and then suspends its sender, with any fragments not placed. By the host's code the sender goes on once less than half the limit waits, which no probe has shown. So the wait of §8.7 is the host's and nothing of the runtime's (§8.7, *Messages*; the log's *The Outside Reviews Read* and *A Message Is Placed in Parts*).

A process's exit is the host's too. It tells the monitors of its own node, then finishes a send the process had begun, waiting at the buffer as the send did, and then tells the monitors of other nodes one after another, each `'DOWN'` waiting at a busy buffer as a send does. Where the exit's reason is an immediate term, an atom among them, the host tells the monitors of other nodes before it finishes the send, and the peer gets the `'DOWN'` before the rest of the message. Every end the runtime gives a program's process but a return has a tuple for its reason (§12.2). A call's answer rests on that: it is not overtaken by its callee's `Down` (§6.9), and `ern_nodes_tests`' two tests of a killed callee's answer hold it (§8.7, *Messages*; the log's *A Down Follows the Send*; `docs/otp_bugs.md`, report 25).

Every socket of the carrier has a linger of no time from its start: each dialed one by the boot flag `inet_dist_connect_options`, which the host reads at each dial, and the listener by `inet_dist_listen_options`, whose linger each accepted connection takes. It is kept for a loss: a socket closed at a loss drops what it still holds, as a loss drops what waited, where one that lingered would keep its queue and the peer would take messages after both nodes ran the loss (§8.7, *A loss*; `ern_carrier:boot_flags/1`; the log's *A Connection That Cannot Drain*). The boot flag sets it before a connection is up, so it costs a refusal its last bytes, which a reset can drop before the refused peer reads them.

The job halts without the host's flush, so a node's end waits for no socket, a peer's or a program's (§12.6, *A node's end*; Appendix E.18; the log's *The Job Halts Without the Host's Flush*).

## Addresses

An address names its process for as long as the process lives, on whichever node, and is as good on a third node as on the one that made it; a loss does not end it, and an address of an earlier start of its node is dead (§6.5, §8.7, *Addresses*). An adapted address holds its function, its target, its maker and the launch it was made in, `{adapted, Function, Target, Maker, Launch}`: the function is applied on the node that made the address, never where the message is sent from, so that a function never crosses in a message and a type that holds one stays bound to its node (§3.11, §6.5).

A message to an adapted address from another node is a frame to the making node, whose worker for the sending peer keeps one process for each address that peer sends to, a `#kept{}` with the process, the worker's monitor of it and the messages handed to it and not yet applied, its `handed`, hands it each message in the order the frames came, `{apply, Message}`, and tells it to stop once none waits; a kept process acts for the address's target where the target is on this node, so that what the function opens is the target's and `Process.current` in it is the target, and for none where the target is on another node (§6.5, §6.9, §12.6; `ern_rt:kept/1`; the log's *The Runtime's Own Processes*).

Where it acts for none, a monitor its function makes is its own, and a fault in that monitor's wrap is sent it as to a program's process, which it meets at its next wait in the function, or, where the function has returned first, at its wait for the next message: a fault in the function, and so the target's, which takes it as a message, and one met between messages takes no message's place (§6.5, §6.9; `ern_rt:faulted/3`, `ern_rt:kept_loop/2`; the log's *A Wrap's Fault Met in the Function Is the Target's*, *A Wrap's Fault After the Function Is the Target's*).

The launch's tag ends the address with the launch, so that a later run of the same node, the next run of `ern test` over a directory among them, drops what is sent to it wherever its function would be applied (§6.5, §11.2; the log's *The Sitting on §8.6's Bookkeeping*). An address exposed to foreign code has a checker in front of it, which is the runtime's note's.

## Calls and computes across nodes

A call's reply is the host's alias beside the caller's process, which `Process.fromReply` answers; the alias takes one answer and drops any other; the caller monitors the callee while it waits, so the callee's end and a loss both end the call (§6.6, §8.7, *Calls*, §12.6).

A call to a process of another node sends that node a note that this caller waits, a row of `ern_notes` beside the call's row of `ern_callees`, keyed by the caller's node so that a loss drops a peer's notes together; a restart in place reads every note that came before it and tells each caller `restarted`, and a note comes before its request but for one through an adapted address made on a third node; a call that ends otherwise, its time run out, answered from another node or its caller ended, sends the second note, by which the node lets the first go (§6.6, §6.9, §8.7, §12.6; the log's *Calls Across Nodes*). So a note goes at an answer given on its node, the callee's restart or end, the second note, or the loss of the caller's node.

A compute's frame is the call's first note: the peer starts a process, the compute's callee, a row beside a call's, records the compute's site for it, and the function's value or its fault crosses back through the alias, the fault whole with its trace so that the caller faults as if `f()` had faulted in it; the call's second note kills the callee where the caller gave up first, and a fault once the note has gone is the process's own, reported on the peer (§8.7 and Appendix E.27, *A compute*). The value crosses back at the type the compiler checked at the compute, which the peer holds too, in `f`'s form.

A restart of a process tells each other node with a process that monitors it when the restart reads them, a watcher's node and a caller's whose call's end has not reached it, which the restart reads as the host lists the processes that monitor it, by a frame from the restarting process carrying an alias of its own, and waits for each answer as it waits for a delivery on its own node (§6.9, §8.7, *A restart*, §12.6).

The node's worker for the peer asks the node's reaper to deliver `Restarted` through the service monitors it holds of the process, and answers by a frame to the restarting node's gateway once every delivery has ended, which it waits for in its own state, watching each, so that a wrap that does not finish holds up that restart and no frame of the peer's, and the wait needs no process (§7.4, §12.5); the answer goes over the connection that stands and opens none, and the restarting node's worker hands it to the alias, which takes one answer.

The process's end, as the host ends the reaper's monitor of it, a loss among the ends, ends each delivery of `Restarted` not yet placed before its `Down` is given, and the answer then reaches no alias (the runtime's note's *A call, a restart, a kill*; the log's *The Release Review Before 0.6.0*, its decision K3, and *No Restarted After a Death*).

The alias is let go when the wait ends, so that a late answer is dropped. The restarting process watches the peer's gateway meanwhile, so that a loss, or the peer's end, which ends its gateway, ends its wait; a node that holds no service monitor of the process, its processes monitoring it otherwise or waiting for its answer, answers at once (the log's *A Restart Told Across Nodes*, *A Restart Told Across Nodes, Built*).

## A spawn

A spawn's frame carries the function's identity, its captures in the order its body first names them, a reply among them crossing as in a message, its site and its time, and for `restarting` the limit and the inner function's identity (§12.6, *A spawn's frame*; §11.1; `ern_peer`'s `spawned()`). A compute's frame says the same of its function.

The peer's gateway finds the identity in the node's code table and starts the process through the node's runtime, recording the site as a local spawn's with the peer whose spawn started it in the process's row, or answers `NotLoaded(text)` where a binding of the function's reach has no value there or a foreign declaration's module is missing, `text` the words the gateway says of it, or, where it lacks the function, hands the spawn to the node's exchange; the answer goes back through the spawner's gateway, which kills a process no one waits for any more, its spawner's time run out while the connection lasted (§8.7 and Appendix E.27, *A spawn*; the log's *The Spawn by Hash, Built*).

A spawn's row in `ern_spawns` goes when its answer comes, when the spawner gives up, or at a loss of the peer's connection that the gateway learned of after the row was written. A monitored spawn's process waits on the peer until its spawner has made the monitor or has ended.

What the peer lacks of the function's reach the exchange brings, which is the code note's ([`code.md`](code.md)). A function typed at a shell, and the shell's own session, has a hash as any definition has, and crosses the same way, but that a node of the shell's build holds its session from its start and lacks none of it (§8.7, §11.2).

## Services and the pick

A service a peer may find is an offer, a row in `ern_offers` under the service's name and its message type's hash, and a row in `ern_offered` for the process whose address is offered, both kept while that process lives, whose end the reaper sees for a process the runtime started or opened and watches for in any other, and never withdrawn; a second offer under a held name answers the holder, so that the caller may monitor it and offer again at its end (Appendix E.27, *An offer and a find*). A find asks the peers `services` lists under the name, in order, each given the time left, through their gateways, each comparing the hash and answering the address, `NotOffered` or `OtherType`; it ships no code (the log's *The Nodes' Reasons, Kept*, *The Service Named*).

A node tells each connected peer how busy it is every `utilization-interval`, and once as the peer connects, the telling carrying its interval, in place of the host's own idle tick where one would go; the gateway holds each peer's last telling with the moment it came, in `ern_utilizations`, one row per peer by its name on the carrier, so that a peer a reload renames keeps its row, each telling replacing it and a loss dropping it, so that the table is bounded by the configuration; a compute that names no peer draws two of the peers whose telling is no older than two of its intervals, at random, and takes the less busy, the first drawn where they are equal (Appendix E.27, *A utilization*; the log's *Placing Work by Name*, *The Numbers Across Machines*).

An attached shell's own node tells no peer, so that no compute that names no node runs on the operator's machine, and answers an ask as every node does (§11.2, Appendix E.27; `ern_carrier:tells/0`; the log's *The Attached Shell's Own Node, Quiet*).

The node's own measure is the processes running or ready to run, the one measuring left out, over its schedulers, read from the host's counters with no scan; the number a program set with `Peer.setUtilization` is a row of the launch's, told and answered in the measure's place until it is set again, and gone with the run (`ern_rt:set_utilization/1`). A pick is a read of the held rows and a draw, a few microseconds and no frame.

## Costs

A message between nodes is the host's send. A spawn on a peer that holds the function is a frame and an answer, a few milliseconds on one LAN; the first spawn that carries code to a bare node is the slow one, about 250 milliseconds on a machine of eight cores and 650 on one of two, most of it the host's compiler starting, and every spawn after it that carries code pays the exchange's own cost, under a hundred milliseconds for a definition of ordinary size (the deployment guide's §3.4; the log's *The Numbers Across Machines*, *What MVP 3.1 Costs, Measured*).

Three idle nodes exchange about 1.2 packets a second at the default telling interval, the tellings in place of the host's idle ticks and not beside them (the deployment guide's §3.2). A process kept for an adapted address costs its peer's messages one hop more on the making node, and nothing to any other process (§6.5; the log's *The Sitting on §8.6's Bookkeeping*). A correct program's traffic makes no atom on a node but in three bounded cases, a spawn's or a compute's captures, which the host decodes before the identity is looked up, an adapted address made in a unit the receiver lacks, and the name of a node not yet met; a faulty peer can make any atom, which the trust in a listed peer admits (the log's *The Spawn by Hash, Built*).

## What the nodes' machinery does not do

It opens no connection in the background and sends nothing a second time: a message arrives once or not at all, and where one is dropped the connection is lost with everything that waited (§8.7, *Messages*). It connects no third node through a second: that A knows B and B knows C connects A and C in no way.

The nodes' machinery evaluates no binding, runs no initializer and loads no module because a peer asked, beyond the reach a spawn or a compute carries, so a bare node's offers are what the processes spawned on it offer and nothing of its own. It looks for no deadlock on a node, since a peer can reach it (§8.6). It keeps nothing for a peer it has lost but what §8.7 names, a node's end recorded against the loss and a worker that lives until it holds no frame and no kept process. And it names no node to itself: a program that must say where it runs is given the name by whoever spawned it (the log's *What the Feedback Left*, 2026-10-20).
