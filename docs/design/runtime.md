# The Ernest Runtime: Design

Status: the runtime's design note, which changes when the runtime does. It is not a proposal, and not authoritative: the report states what a program is promised, in §6 to §9 and Appendix E, and what every runtime must give and how this one gives it, in §10 and §12, and this note states the shape the runtime keeps those promises by, as it stands. A line here is a shape a reader must know to change the runtime without breaking a promise, never what one function does, which is the code's; the module map is [`architecture.md`](../architecture.md)'s, and the reasons are the log's, named at each line. Where the code and this note differ, the code is what is built and this note is corrected.

## The rule

What the runtime adds to an operation of the host costs a fraction of it, and nothing on a call that answers at once (CLAUDE.md's *Design*, §10). Its bookkeeping follows one rule: what the deadlock look needs of a process, the process marks in its own state, and the look reads it when the program seems idle; no operation writes a shared row for the look's sake. A shared row exists only where a process other than its owner must read it, and each such row names that reader below. The log's *The Sitting on §8.6's Bookkeeping* argues the rule.

## The process model

A program's processes are the host's, spawned by the runtime, which keeps a row for each (§6.9, §8.5). The reaper, one process, monitors every process the program spawns and every resource a system module opens, delivers each `Down` through a process of its own, and makes the deadlock look (§8.6).

The system processes, stdout, stderr, stdin, the clock, the file system, the terminal, TCP and the host (§8.2), are foreign processes the runtime starts at a launch and stops at its end, the standard streams in order, after what was sent them, so that a line of the toolchain's own a stream did not take its sayer writes; each counts what it holds that can still deliver. The entry process runs the initializers in dependency order and then `main` (§8.5). A launch is one run of the runner, tagged by a reference the adapted addresses carry (§6.5, §11.2); the log's *The Numbers Across Machines* and *The Rows That Grew* measure what a spawn, a monitor and a restart cost.

A listener and a socket are processes TCP's process starts, each holding the host's socket, `gen_tcp`'s or, over TLS, `ssl`'s, whose functions the code calls alike; a socket `accept` answers on a listener over TLS shakes hands in its writer, a process of the socket's own, before the first write it takes, while the socket's process answers the rest. TCP's process starts the host's `ssl` application at a launch's first request over TLS where nothing has started it, a node among them, whose carrier runs without it, and the host loads its modules each at its first call (E.18, §12, §12.5; the log's *TLS in `Tcp` and a Terminal in `Os`*, *Lean at the Limits*).

A program `Os.start` started is a process that owns a port to its run of `ern_exec`, the one helper in C, the two talking in frames the helper's header lists. The command's variables and its directory are frames ahead of the command: the helper sets each variable over the environment it inherited, and enters the directory before it forks, answering itself where it cannot. A signal is a frame the helper sends the program alone, answered by whether the program had already exited. A write and a signal each wait in a queue of the process's for their answers in order, and the program's exit answers what remains. The helper takes the program's input until the program exits, past the end of its outputs, and its kill ends the program's process group (E.23; the log's *A Program's Environment, and a Signal Named Built*).

A program `Os.startTerminal` started has the process, the frames and the reads of one `Os.start` started; its helper holds the pseudo-terminal's master, which is both the program's input and its output, its end of input the terminal's hangup, and a resize a frame the helper applies to the master, which the program's process answers without waiting on the helper. The program is its own session's leader, and so its process group's, which the helper's kill ends with it (E.23; the log's *TLS in `Tcp` and a Terminal in `Os`*).

A process whose root has a screen is a session's: what it writes to standard output and standard error goes to that screen, but while a capture of its chain runs, which takes it first (E.24), standard input and the terminal refuse it as a shell's terminal does, and its `Os.exit` faults it, while any other process's `Os.exit` ends the run as the launch's row says, `ern run`'s ending it and the shell's and `ern test`'s faulting every caller, but a process of the shell's own in the shell's own run, whose row says so, which ends the shell (§12.1, §11.2, E.23).

Everything the end uses is there before the end: the reaper, the launch's killer, the sayer of the lines said later and the system processes from the run's start, and the terminal's holder, a shell that keeps the settings the program found and gives them back when told or as its input ends with the host, from the first subscription to keys. A full table of the host's so stops no end, and a node's limit is the one `limits` states (§12.1, §12.5; the log's *A Node's Limits*).

At a full table, a spawn the runtime makes for a request faults its asker with the host's class and reason, the process that took the request living on; one on a message's way, a delivery, a teller of the end or a process kept for an adapted address, faults the process the message is for at its next wait, as a fault in an adapted address's function does (§6.5, §7.3, §7.4). A process the host's TLS makes for a request, a connection's own or a listener's tracker, is such a spawn: the host raises where the table refuses it, and the request faults its asker (`docs/otp_bugs.md`, 15; the log's *A Program's TLS at a Full Table*).

A socket's closer, which lingers over what it has not sent, is made as the socket ends, once its writer has ended, so that it takes the writer's room; where the table refuses it, the socket closes with a linger of no time (E.18, §12.5; the log's *Lean at the Limits*). A read of standard input opens its input for the read alone, so that nothing is read ahead, and one whose input cannot be opened faults its reader as a request; a subscription whose holder cannot be opened answers the host's refusal (§12.1, §12.5).

What the runtime calls is loaded before the operating system's limit of open files can refuse it. A run's start loads the toolchain's own Erlang of the run's side, `ern_tree:run_code/0`, with the host's modules their import tables name and the few a report reaches through the host's own; a unit loads with the modules its import table names, its foreign functions' among them; the host's TLS loads as the host loads it, so a handshake at the limit can fail (E.18). A load after that which the host cannot make faults its call as a module the host lacks does, the host's loader giving no reason (§12, §8.4; `docs/otp_bugs.md`, 13; the log's *The Runtime at the Limit of Open Files*).

A load's evaluator ends once every binding has its value, unless it owns what a binding opened, which would end with it: a listener, a socket or a running program, each of which watches its owner from before its address is given out until it is given to another, a table it made that it still owns, and a process it started to end with it, a proxy's (E.18, E.23, G.1, G.7).

A running program's process whose program has exited, or a socket's whose connection has closed, is *spent*: it marks itself so in `ern_held`, tells an evaluator that owns it, and keeps it alive no longer (E.28). So the evaluator asks the host what watches it and reads the tables it made and the processes it started so, its own state, and no other process's; its caller waits for its end, so a load answers once its evaluator has gone (E.28; the log's *Sites, Sessions and Their Names*).

An evaluator that lives on reads what it owns again at each end or spending among them, and ends once none lives unspent, a table being ended by nothing but the program's end or a kill of the evaluator.

A `Code.load`'s evaluator is spawned by a settler, a process of the runtime's own that watches the caller from before the spawn and makes the load whole or undoes it however the caller ends. A caller killed while it waits, or meeting a fault or a restart asked for at that wait, leaves the load undone as a binding's fault does. The evaluator is killed first and its end taken from the reaper's notice, which comes after every spawn the evaluator asked for, so that the withdrawal finds each process the evaluation started (E.28, §6.9; `ern_rt:evaluate_load/2`; the log's *The Release Review Before 0.7.0*, *The round*).

A line of the toolchain's own that a program's own process says waits until standard error has taken it, so that it stands in order with the program's output. A line said where a wait would hold up others waits on no stream: the gateway's, which routes every frame, the check of a certificate's inside the host's TLS, the port map's on a dial, the host's log filter's and a reload's in the host's signal handler. It goes to one process of the runtime's own, `ern_say_later`, started with the first run and kept for the host's life, which says each line in the order its caller said them as a waiting line is said; a launch's end and the job's end wait for it to have said what it was given (`ern_rt:say_later/2`, `wait_for_later/0`; §12.5, §11.2).

## What the runtime keeps, and where

A process's own, in its dictionary, dying with it, read by the process and by the look, and by another process where a line says so:

- the mark that it is inside foreign code, put by the boundary's wrapper while a function given to foreign code runs, and by each slow wait of the runtime's own around its receive (§8.4, §8.6);
- the mark that it is in a receive with a deadline (§6.3);
- its call, the callee and the reply, while a call waits (§6.6), which the look, `Process.status` and a kill read;
- on a socket's process, its own processes, neither with a row: the one that does its writes, which holds what it wrote until it runs again, and the one that does its close, so that `Process.status` counts both as the socket's (E.18, E.21);
- while a restarting function runs, its outermost's start cause and the alias a supervisor asks the process to restart through, which a supervisor reads of the process as it asks (§6.9, E.22);
- the evaluator a load's caller waits for, which a deadlock faults in the caller's place (§8.6, E.28), and what a process of the runtime's own acts for, its recipient, or none where the recipient is on another node (§6.5, §6.9);
- the tables it made, which `Ets.new` tells the runtime of, and the processes it started to end with it, a proxy's, which `Proxy.start` tells, each a list that drops what the process no longer holds once it has doubled, so that it stays within twice what the process holds; a load's evaluator reads its own at its end, and `Process.owned` and `Ets.owned` read another's, with what watches it as its owner (E.21, E.28, G.1, G.7).

The compiler writes a receive with an `after` as a fun applied where it stands, which it enters again until the deadline has passed. The fun's frame is its definition's to `Code.running` and writes the receive's line in a trace, and a fun in a lambda's body is named apart (E.21, E.28). A receive without an `after` is the host's `receive`. The log's *Nothing at the Wait Built* argues it.

Shared rows, in the runtime's tables, each with the reader outside its owner that needs it (`ern_rt:tables/0`):

- a process's row (`ern_processes`): its spawn site, order, root and the peer whose spawn started it, read by a fault's report, the program's end and `Process.current` (§6.9, §8.6), its root by the screens' readers below; the fault it ended with, its cause, its trace, the site of the callee or the name of the peer it was carried from and the moment it was met, which the process writes as it ends and the reaper reports beside the host's term of the end, which carries the cause and the trace alone, or, for a compute's process, that the fault went to its caller, which the reaper reports to no one (§6.6, §8.7, §12.2, E.21);
- in a process's row (`ern_processes`) too, the mark that its fault is expected, which the process `Process.run` starts for `Test.faults` sets as it begins, through a function of the runtime's its library declares, and a load's evaluator is given as it is spawned, its fault the load's answer, and by which the reaper reports its fault to no job and no subscriber (E.21, E.24, E.28);
- in a process's row (`ern_processes`) too, whose own it is: the shell's, the session and the processes the shell runs to serve it, which the session sets, and whose `Os.exit` ends the shell's run; an input's, one that runs or one that bound a name, which marks itself; or the runtime's, a load's evaluator, given the mark as it is spawned; `Process.live()` reads it, leaving all three out and any process the host says has ended, since a row stands until the reaper has taken its process's end, and `Process.status` knows no evaluator, so that the set of a session's own is its processes' rows and goes with them (§11.2, E.21, E.23, E.28);
- the callees' rows (`ern_callees`), one for each pending call, keyed by the callee, a process of this node or another or a compute's peer's gateway, read by a callee's restart to end every call waiting on it, dropped by the caller's end of the call or its kill, and read by the reaper for a caller the host ended, whose call it drops and whose peer it tells, a read of every row that such an end alone pays (§6.6, §6.9, §8.7); the one shared write a call makes, on a table with the host's write concurrency, an ordered set since the restart reads its own rows by prefix (the log's *Measured 2026-10-22, the callee's table under eight writers*);
- the sources and the opened resources (`ern_held`), few rows, read first by the look (§8.6);
- the deliveries (`ern_deliveries`), each with the process whose `Down` it carries, read by a recipient's restart and its end, by a `demonitor`, which ends the `Down`s of its process on their way, and by the shell's end, which waits for those on their way to the shell as it begins to end (§6.9, §11.2);
- the fault subscriptions (`ern_faults`) and the termination subscriptions (`ern_terminating`), read by a fault and by the end (E.21, E.23);
- the checkers (`ern_checkers`) in front of exposed addresses (§8.4);
- the launch's row (`ern_launch`), the runner, the tag, the reaper, the killer, the standard error process while it takes the toolchain's lines, the reporter, the arguments, how `Os.exit` ends the run and whether the run is a node's, read by every process of the launch, and beside it a row for each of a few facts of the run, its entry process, how the terminal is read, the process a deadlock faults, the runner the end tells a late subscriber to while it looks for its subscribers, that the end's wait is over, and the utilization the program set, all gone with the table at the end (§8.6, §8.7, §11.2, E.27);
- a node's offers (`ern_offers`), each process's own offers (`ern_offered`), the initialized modules (`ern_initialized`), and the notes of calls from other nodes (`ern_notes`), keyed by the caller's node so that a loss drops a peer's together (§8.7, E.27);
- the screens (`ern_screens`), a row for each root a session heads, its own, which its inputs are chained to, and each evaluator's its chain started, with the sink its chain's writes go through, written by the session and by such an evaluator as it begins, kept past the evaluator's end while the session lasts, dropped by the session as it detaches, every row of its sink, and by a load withdrawn, and read by the standard streams at each write, by standard input and the terminal at each request, and by `Os.exit`: the writer's row for its root and the root's screen, two lookups, about a tenth of a microsecond against a write's two to ten, the writer being the process a process of the runtime's own acts for (§12.1, §11.2, E.28; the log's *The Session's Screen and the Toolchain's Units, Built*, *The Argument's Four Decisions*).
- the captures (`ern_captures`), a row for each `Test.capture` that runs, keyed by the head of the chain whose writes it takes and the order the captures began in, with its collector, a process of the runtime's own and of no chain's, which no kill of the chain's reaches: written as a capture begins, deleted by its collector as the capture ends or as its caller does, and read by the standard streams at each write before the screens, by one step back from the head's last key (E.24; the log's *A Case's Standard Error*);
- the collectors (`ern_collectors`), a row for each that has not ended, written as its capture begins and deleted by the collector as its last act, once it has answered or written back what it took, which the run's end reads once every process of the run has ended, telling each collector that the run ends, at which it writes back as at its caller's end, and waiting for each before it flushes the streams (E.24, §8.6; the log's *A Capture Written Back at the End*).

Beyond the runtime's tables, the gateway keeps two for a node's life, the spawns it waits on and its peers' utilizations (`ern_spawns`, `ern_utilizations`), and the code table two for the host's, the units and their sums (`ern_code`, `ern_code_sums`) (§8.7, §11.1, E.27).

The host's persistent terms, few, small and set at a job's start, a launch or a reload: the build of `ern` that every `.erc` records, its version and the compiler's digest, which a run compares before anything runs (`ern_build`, §11.1, §11.2), the system processes' pids and the process that holds the terminal for a shell (`ern_rt`), the file mode mask the host's facts gave (`ern_os`), a node's peers and services, `names`, `nodes`, `named` and `services` (`ern_peer`), the node an attached shell's session runs on, on the shell's own node (`ern_carrier`'s `attached`), and a top-level binding's value, which a ground binding needs no read of (§8.2, §8.5, §8.7, §11.1, §12.1); beside them the toolchain's own modules, a map put once in a host's life (`ern_rt`'s `own_modules`).

## The look

A deadlock is quiescence (§8.6; the log's *Deadlock Is Quiescence*): nothing in the program can deliver a message, and every process waits. The runtime can decide it because it owns every source of a message. The look runs in the reaper after a while without a message, and never on a node or while a shell holds the terminal. It reads the cheap facts first, the sources, the terminations, the system processes' quiet; only where nothing can deliver does it read every process, its status and reductions, twice, and in the second read each waiting process's top frame and three marks in one `process_info`.

A host module on top of a waiting process is a host receive inside foreign code; the foreign mark is a callback inside foreign code; the timed mark and the call's mark are theirs; anything else is Ernest's wait. A module is Ernest's where it exports `'$code'/0`, as every unit does, or it is one of the toolchain's own beams, never by a prefix. Every slow wait of the runtime's own that a program process can be inside marks itself, which a test holds for every `receive` of the toolchain's Erlang by the module's `-receives` attributes (docs/code_style.md's *Erlang*).

The second read asks the waiting processes one by one, a `process_info` each, until one cannot be a deadlock's, so a look of a program at rest whose one timed wait is in its last process asks every process; the look comes seldom while something can deliver.

Once the look has found a deadlock, it reads the waiting processes' marks of a load's evaluator: where a load's caller waits for one, it faults the evaluator spawned last of those waited for, which refuses that load, the load's answer the fault's one report (§8.6, E.28; the log's *The Argument's Four Decisions*). Otherwise, before it faults the entry process or the test that runs, it reads each other waiting process's stack, while every process still waits, and keeps a line for each group of one spawn site and one waiting frame, the first of the program's frames, with their count, in the order of the sites, in the launch's table beside the process it faults; the fault's report takes the lines and writes them beneath the trace (§12.4, §11.2). Nothing of it is read before the verdict, and nothing of who waits for whom.

## A call, a restart, a kill

A call is the host's monitor with an alias, a send, a receive with its deadline and the answer (§6.6); its reply is the alias with the caller's process beside it, which `Reply.process` answers; it writes its callee's row and marks itself, and its wait reads the caller's mailbox so that a restart asked for is taken there (§6.9, §10). A `callForever` reads its callee's spawn site as it begins, while the row stands, so that a fault of the callee's it ends with names the site after the cause (§6.6, §7.4).

A restarting function entered in a process of the runtime's own that applies a function for another, a wrap's delivery, the terminal's courier or a kept process, faults before anything of a restart begins, a fault the recipient meets as it meets any fault there (§6.9, §7.4; the log's *The Argument's Four Decisions*).

A restart runs in the restarting process, in four steps (§6.9). The clock and the terminal cancel what the old run asked of each, with the deliveries each started to it, and answer, as the gateway does; then the reaper cancels the process's own monitors and its subscriptions, with every delivery to it, and answers, so that a monitor a delivery of the clock's or the terminal's asked for is canceled with the rest. No restart asks an end's teller: a teller's delivery reads its subscriber's subscription once its own row is written, and delivers nothing where the row no longer holds the end's telling, telling the teller of the restart instead; the reaper deletes the subscription before it reads the deliveries, and the check rests on that order (the log's *The Teller's Late Delivery, Built*).

The process empties its mailbox. It reads its own callees' rows and tells each caller `restarted`, asked or with the cause. Last, it tells its service monitors, here and on other nodes, and waits for each answer before the new run begins. Whether a fault is one met as the program ends, which ends the process with the program unreported, the process that meets it asks as it meets it (§8.6, §11.2).

The reaper tells each service monitor of the process, a monitor it keeps marked, a `Down` with `Restarted` through a delivery of its own, the monitor standing. Each other node with a process that monitors the restarting one when the restart reads them, once its calls have ended, is told by a frame: a watcher's node, whose reaper holds the watcher's monitor, and a caller's whose call's end has not reached it, which the restart reads as the host lists the processes that monitor it. That node's reaper takes the frame as this one's takes the restart, the `Down` of a process of another node having an empty site, and a node whose processes hold no service monitor of the process answers at once.

Each answer comes once every delivery has ended, from a process of the runtime's own where one is under way, through an alias of the restarting process's, which takes one answer and is let go when the wait ends; the process waits for each, or for its watch of the reaper or of the node's gateway to end, a loss and the node's end among the ends.

A loss ends the watching node's side too: as the host ends the reaper's monitor of a peer's process with `noconnection`, the reaper ends each delivery of `Restarted` for that process to a caller with a service monitor of it, read by the caller's prefix as a `demonitor` reads them, before it gives the loss's `Down`, and the answer the deliveries' end lets go reaches no alias (§6.9, §8.7, *A restart*, §12.6; the log's *A Restart Told Across Nodes* and *A Restart Told Across Nodes, Built*).

Every end the runtime gives a process from outside it but the program's end goes through one kill: the launch's killer, a process no program can name, made with the reaper at the run's start, suspends the victim, reads its call's mark, drops the callee's row and the peer's note, ends it and lets it go, one kill after another, so that a kill needs no room in a full table (§6.9, §10). A kill of a process of another node is a frame, which that node carries out as its own kill (§12.6).

An end the host gives a caller, foreign code's kill, leaves no mark to read, and the reaper finds its call among the callees' rows as it learns of the end. A fault in an adapted address's function reaches a process the runtime started as a message it takes at its next wait, and ends one it did not start as an exit signal (§6.5).

A call from the runner to a process that ends with the program waits for the program's end, so the runner calls none but through an alias under a monitor, as its flush of the shell's screen and its lines on standard error do. A process of the runtime's own that kills the process it acts for ends at the kill, as that process would had it killed itself, and a monitor it asks for is that process's, made only while both live (§6.5, §6.9; the log's *A Wrap's `self` Is Its Recipient's*). The reaper keeps such an asker beside the monitor and watches it until it ends; one that ends otherwise than it returns, a delivery ended with its recipient's run among them, takes its monitors with it.

A fault's trace is the host's stack as it stood, twelve of the program's and the host's frames of the sixty-four the host keeps, the runtime's own left out but where a host error was met in its code, a frame of a unit that names no definition of the program's among the runtime's (§7.3, §7.4, E.21). A host function is written as the host writes it, quoted where the host quotes it, in a trace and in a cause alike. A fault a compute carries back is the peer's cause and trace, the cause naming the peer and the trace ending in the compute's site (§8.7).

## The boundary

What crosses between foreign code and the program is checked where it enters the program: a foreign function's return, a reply foreign code gives, a message to an address exposed to foreign code through a checker process, and each argument foreign code calls an Ernest function with (§8.4, §12.3). The standard library and the system processes are the runtime's own and are not checked. A function given to foreign code runs inside a wrapper that marks the process and turns a raise into the fault §12.3 names; a function value foreign code gives is a foreign function, named as the host names it. The foreign call itself is the host's call inside one `try`, and writes nothing; a call of the standard library's foreign function is that call at the call site, the declaration's own function left out (§11.1; the log's *The Emitter's Calls Against the Host's*).

## Nodes

Two nodes are two files and one TLS connection, the host's distribution as the carrier runs it (§8.3, §12.5). Seventeen frames are the runtime's own, which the gateway takes from each peer, reading some itself and handing the exchange's four to the exchange and the rest to that peer's worker: a message to an adapted address, a spawn and its answer, a compute, a find, a utilization and a node's telling, that a call waits and that it is over, a kill of a process the runtime started on this node, that a node ends, a restart of a process that a process of this node monitors or calls and that its watchers there have been told, and the exchange's four, the request for a reach, the reach, the lacks and a code frame; a test holds this list, and §12.6's, to the code that reads them.

The exchange carries to a peer the definitions its spawn's reach names and the peer lacks, verified by hash and loaded whole before the process starts ([`code.md`](code.md)). A node detects no deadlock, since a peer can reach it.

## Addresses and code, owned by the nodes' and the code's notes

Two shapes this note only points at are [`nodes.md`](nodes.md)'s and [`code.md`](code.md)'s. An adapted address applies its function on the node that made it, a process kept for it there applying a peer's messages in order, and an address exposed to foreign code has a checker in front of it (§6.5, §8.4, §8.7). A unit is a compiled module of the host's holding definitions each named by its hash; a module a load brings is placed as a unit the node already holds, as its file or as its forms, and an arrival is the unit one exchange's definitions make (§8.7, §11.1, §12.7, Appendix H).

## What the runtime does not do

It makes no scan on an operation's path that grows with other processes' work: a restart reads its own rows, a kill reads its victim, the look reads every process only when nothing else can deliver, and only an end the host gives reads every row of its kind, a caller's every pending call and a delivery's every delivery. It keeps no cache without a rule for letting go: a launch reads the host's facts again (E.23). It routes around no defect of the host: what the host does not signal, a port's queue emptied, is waited for through the host's own busy state and not polled (§12.1; the log's *Built* paragraphs on the fixed waits).
