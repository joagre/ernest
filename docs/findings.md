## To decide

- D1 [decided 2026-10-17 as recommended, the remote target's case added; planned before the tag], §6.9, §6.5, E.18, E.23, E.28, §11.2. A wrap, and an adapted function applied on arrival, run in a process of the runtime's own, and every rule that names "the process that" then meets that process. §6.9 says "A fault in it is the fault of the process it delivers to", and a reader expects everything else in the wrap to act for that process too. The code does otherwise, and four cases a program can reach show it.
  1. `Os.start` or a socket opened in a wrap is owned by the delivery (ern_os.erl:72 monitors the caller), so it is killed as the delivery ends, at once.
  2. A process a wrap spawns heads a chain of its own, since the delivery has no row (`root/2`), so a refused `:load` or `Code.load` does not kill it, though its monitor came from the load's evaluation.
  3. `Code.load` called in a wrap finds no row to mark (`rooting/0` answers `none`), so a refused load kills nothing it started, against E.28.
  4. `Process.current()` in a wrap answers the delivery, which E.21's `status` already allows for. On one node an adapted function runs in its sender, and on arrival in the kept process, so one function answers differently by where it was sent from.

  Recommendation: state in §6.9 that what such a function opens, spawns and asks of the runtime is the recipient's: for a wrap the process it delivers to, and for an adapted function on arrival the address's target. The delivery's row then names that process for ownership and the root, and `Process.current()` answers it. Principle 1 decided: the report already gives the recipient the fault. The other way, stating that the runtime's process owns what it opens, adds a rule a reader must learn and makes a resource opened in a wrap useless. Principle 5: no new concept either way.
- D2 [decided 2026-10-17 as recommended; planned before the tag], §8.6 and E.15; ern_rt.erl `alarm/4`, `fired/2`. An alarm whose process has ended stays a source of the deadlock count until it fires. `source_begin()` at `alarm/4` is ended only in `fired/2` or `alarms_canceled/2`, and the clock learns of no end. §8.6 counts a timer only where its completion would deliver a message, and E.15 now says one that fires after its process has ended delivers nothing. So a program whose last setter of a `Clock.alarmAt` an hour away has ended is found deadlocked an hour late. alarm_after_its_process_ended_test_ moves the clock past the alarm to see the deadlock at all. Recommendation: the code follows §8.6, and the clock forgets an ended process's alarms as it forgets a restarted one's. Shape: the clock monitors a recipient while it holds an alarm of it, one monitor for each process with alarms, gone as the last one fires; the clock is a system process, which may cost a message by design. Principle 1 decided: the reader of §8.6 and E.15 together predicts the deadlock now.
- D3 [decided 2026-10-17 as recommended; §11.1's sentence written], §11.1 (toolchain.md:42) and §11.2 **What a node holds** (:200); ern_code.erl `forms/1`. A build's forms are read from its `.erc` at the first request that needs them, not at the start. A build written into the directory under a running node therefore leaves every earlier definition the node has not shipped yet without a form: `forms/1` answers `none`, and a spawn of one on a peer that lacks it fails with `Other`, "no longer holds". §11.1 says such a build "reaches it at its next start and nothing before", and §11.2 says the form "is kept beside the code". Recommendation: state it in §11.1, in one sentence beside "a new build goes in a directory of its own": the node then cannot ship a definition of its build that it has not shipped before, and such a spawn fails with `Other`. Principle 1 (the departure stated) and principle 5 (reading every form at the start would hold memory docs/memory.md avoids) decided. The other way is to read the forms at the start.
- D4 [decided 2026-10-17 as recommended; §11.2's sentences written, the code planned before the tag], §11.2 (toolchain.md:88, :200) and soundness *Code that crosses*. Under `ern test --config-dir` over a directory, "the runs are one node", but "a unit, once loaded, is held for the node's life" is not kept: `ern_cli:loaded_unit/3` purges an earlier program's code of a name before a later one loads that name. ## Notes for the longer lines

**C27.** In `ern_rt:tell/4` the order is: `watched(Address)`, then `monitor(Subscriber, fun(_) -> Ended end)`, then `Way = adapted_way(Address, Reply)`, which runs `wrap(Reply)` here, then `pending/2`, `sent/1` and the `receive`. A wrap that spins or waits never reaches `pending/2`, so a restart's word to the callers in `?CALLEES` misses it. The subscriber's end does reach it, as `Ended` through a delivery to the teller, but the message sits unread. The runner's `waited/5` waits on `{said, ...}` or the teller's DOWN, and neither comes. `cut_short/2`, a second termination or the interrupt ends the program. The killed teller test covers foreign code killing a spinning teller, not the subscriber ending under it.

**D1.** A wrap's type is `(Down) -> m` with no mark (§9.5), so a wrap may call anything that carries none. That includes `spawn`, `Os.start`, `Code.load`, `Address.callForever`, `Process.current` and `Os.exit`. E.0 shape rule 5 says the wrapping function "receives nothing, as `adapted`'s does". So the language means it to run anywhere, and only these rules that name the process are open. The kept process for an adapted address raises the same questions for `f`, with the target or the maker as the candidate actor. The recommendation is the target, since the target already takes `f`'s fault (§6.5). One example a program can reach: a service's binding at `:load` monitors a worker with a wrap that spawns a helper and then faults. The refused load kills the service and the worker, and the helper runs on.

**D2.** `alarm/4` runs `source_begin()` in the clock, and `fired/2` and `alarms_canceled/2` alone end it. `look/0`'s `nothing_delivers/0` reads `sources()`. The clock has no monitor of a recipient and the reaper tells it nothing at an end. So an ended process's pending alarm keeps `look/0` answering `delivering` until the timer fires.

**D4.** `kept/1` answers `none` only where no reaper runs, between runs. In run 2 the reaper runs, so a message to run 1's adapted address starts a kept process whose `deliver/2` sees the maker as of this start (`is_of_this_start/1` compares the start's number, which run 2 shares). Run 1's fun is old code after one later load of its module and gone after two, and calling it then raises, which `adapted_way/2` sends as a fault to `process_of(Target)`.
