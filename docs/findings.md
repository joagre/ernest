# Findings: the review of the three proposals, 2026-10-08

Six readers read `proposals/nodes_and_code/mvp3.0.md`, `mvp3.1.md` and `mvp3.2.md` whole on 2026-10-08, before anything is built from them: *C* for consistency across the three, *P* for the five principles, *R* for the report and the soundness argument, *F* for feasibility against the runtime, *O* for operations through a list of scenarios, and *W*, who wrote a paper program across all three. Each section is a reader's report as given, lightly cut. A finding is something to weigh, worked with the user one at a time; its verdict is written beside it when taken, and the file goes when every finding has one, as CLAUDE.md has it. The proposals change with the verdicts; nodes.md, code.md and deploy.md are synced after; the plan last.

## Verdicts taken

Each verdict names the findings it closes; a finding not named is open.

- **2026-10-08, a kept state.** A service whose state is to outlive a deploy runs `kept(key, init, step)`, a function of `restarting`'s family whose loop the runtime owns, so the runtime holds the state between steps and asks for it between two, as a supervisor asks for a restart (§6.9); it composes with `spawn` and `restarting`, and the report's service, a binding holding an address, is unchanged (mvp3.2.md §2, §3, §6). A process that is not a `kept` loop begins afresh at its node's restart. Closes P1, O2, W1, C1, R1, R-soundness 1, F2.
- **2026-10-08, the move dropped.** A kept state is written to the file at every planned stop and read by the `kept` loop under the key at the next start; nothing moves a state to another node, and a service is away for its node's restart. A moved state made two owners at the restarted node's own `kept`, and could not close the race of two nodes starting with a third out of reach; a hot standby is a lease's, a library's over a store outside the nodes (mvp3.2.md §1, §5, §6, §10, §11). Closes O1 and the judgment's move half, W4, W13, C8, and F11's first half, the standing address asking the key's next node; F11's second half, what a standing address sees, stays open under finding 3 of R.
- **2026-10-08, the node restarts itself.** A build is an entry point's closure, named by its root, the hash of the entry point's definition; the configuration directory's `build` file names the build the node runs, which `ern run` with an `.erc` writes and `ern run` without one runs, a bare node where it names none; a planned stop that carries a next build writes it there and restarts the runtime inside the same host process, so the coordinator starts nothing and any start from outside lands on the planned build; a restart whose initializer faults goes back to the previous build once; a node up but not offering its keys in time is sent a planned stop carrying the previous build; the state files are removed once the node listens, not at their read (mvp3.2.md §1, §2, §6, §7, §9). Closes O3, O4, W5, C4, F1; the release of `ern` stays open under F14 and O12.
- **2026-10-08, the standing address is a library's.** `Peer.standing` is withdrawn from mvp3.0.md and mvp3.2.md; `Standing.start(key, ms)`, of a library under `libs/`, spawns an ordinary Ernest process over `Peer.find` and `monitor`, with the mailbox `Message(m) | Went(Down)`, that always answers an address, finds again at the service's `Down` and with `ms` between failed finds, and ends with its caller; every rule of the report holds of its address as of any process's. A service is away from its state's handing to its first offer, and a node's end gives `ProgramEnd` (mvp3.2.md §2, §3, §4, §5, §6, §8). Closes P2, O24, W14, C5, R3, R-soundness 10, F11.

## P. The principles

Read: `language.md` §0 whole; the three proposals in full.

1. **The planned stop reads a service's state from behind the program** (mvp3.2.md §2, §6 *The state file*). "A node writes, at its planned stop, the state of each service it alone may offer to `state/` ... A program sees nothing of it but the directory." Principle 3. The proposal never says how the runtime obtains a service's state; in its own example the state is the argument of `count(total)`, held by that process alone, and nothing a service writes hands it over. Any way the runtime reads it without a line of the program's text is a value taken from behind the program, and the successor "started by `Peer.spawn` ... with the state as a captured value" requires the runtime to know which function starts the service. A reader who knows Erlang expects the process to be asked, as `terminate` asks it. Fix: the hand-over is a request of the service's own protocol, or a function the program offers with the key, `Peer.offer(key, address, handOver : () -> State with m)`, so the service's text shows what crosses a restart; a service that offers nothing writes nothing, and the plan says so.
2. **`Peer.standing` is the runtime finding again, through a process the program did not spawn** (mvp3.2.md §2, §6). Principle 3, principle 2, and mvp3.0.md §1's own rule, "nothing is retried, and a policy, finding a service again, placing work, is a library's", with its §10 leaving out "a second attempt by the runtime at anything". Three surprises follow, and "Nothing else differs from an address `Peer.find` gives" does not hold: `kill(standing)` kills the forwarder and not the service; `Process.fromAddress(standing)` names the forwarder, so the monitor "through the address found" cannot be made, the caller never holding that address; and a message to it takes `via`'s extra step and can be passed (mvp3.0.md §4.1). It widens the one silence, an act on what has ended, to a send to a service that is only restarting, and says neither when the standing process ends nor what reclaims it. Fix: a library function, `Standing.start(key, ms)`, spawning a visible process whose address the program holds; or drop it and let the board's monitor-and-find stand as mvp3.0.md §3 writes it.
3. **Which references a spawned function captures and which it resolves on the peer is a rule the text does not show** (mvp3.1.md §2, §3 *A bare node*; mvp3.0.md §6 *Bindings*). "The function captures `Counter.key`, a value, and names no binding of the store's": `Counter.key` is a top-level `let` written inside the lambda exactly as `count` is; one is called a captured value and the other a named definition, and mvp3.0.md says "In spawned code a top-level binding is the peer's", which would make `Counter.key` the peer's and `NotLoaded` on a bare node. Principles 3 and 1. Fix: state the rule in §8.7, for example "a top-level `let` of a type that crosses is captured at the spawn as its value; a service binding and a `foreign` binding are the peer's", and have the compiler refuse a spawned function that names a binding of the third kind rather than a run-time `NotLoaded`.
4. **A derived `migrate` or `forward` is a top-level binding no text shows, and `forward` is a second concept for `via`** (mvp3.2.md §2, §6 *What is derived*). Principles 2, 3 and 5. Ernest's one mechanism for code the program names but does not write is `derives compare` (§3.5); `forward : (OldMsg, Address(NewMsg)) -> Unit with n` is what `via(addr, f)` already is, an address seen through a translation; where `via` cannot serve, a retired request that needs a call, the program already writes a process. Fix: `derives migrate(Counter.State)` on the new state type and `derives forward(Counter.Msg)` on the new protocol, holed where the diff stops; the old protocol offered by `Peer.offer(Counter.key, via(counter2, forward))`; a retired request a process the program spawns.
5. **A tool-chosen default and a widened number are what §4.5 forbids** (mvp3.2.md §6 *What is derived* against §4.5). "a default for a field the new type adds ... a number promoted to a wider width" against "never with a default the program did not write". Ernest has no declared field defaults (§3.5), so the example's `adds = 0` is the tool's default, and an `Int` into a `Float` field is a coerced value no line shows (§0's host paragraph). Fix: strike both; a field added and a field whose type changed are holes the program fills.
6. **One failure type makes a clause the text shows cannot run** (mvp3.0.md §2). "a program writes `_` for what its operation cannot meet": `Left(NotOffered)` in a spawn's match is a clause that cannot run, which principle 3 has the compiler refuse. Fix: `Peer.FindFailure` and `Peer.SpawnFailure`, each holding what its operation meets, the shared constructors named alike.
7. **A later offer silently replacing a living service is a failure made invisible** (mvp3.0.md §6 *A service and its key*, §9.2). Principle 3, and the Erlang reader's `register` fails on a taken name. Fix: `Peer.offer` answers `Either(Peer.Taken, Unit)`, or faults, while a living process holds the key; a supervised service's new process may offer again because the old has ended.
8. **`Peer.find` with two arities is two spellings of one job** (mvp3.0.md §2). Principle 2, and no other Ernest name has two arities. Fix: one `Peer.find(key, ms)` over the configuration's `keys`, a `keys` entry of one node being the named form; or a second name, `Peer.findOn(name, key, ms)`.
9. **Two ways to end a node, and the service manager's gets the worse one** (mvp3.2.md §2 against mvp3.0.md §6). `ern stop` is the planned stop and `SIGTERM` the quick end that drops the keys without a drain and writes no state; the Erlang reader expects `SIGTERM` to be the orderly stop, as `init:stop` is. Fix: termination is the planned stop with the default drain, one end; the quick end is `SIGINT` or a flag.
10. **`was` is a reserved word for one line of `migrate`** (mvp3.2.md §2, §6). Principles 5 and 2; it puts a dropped field's name in a type declaration for the tool's reading alone, and whether it is in the type's hash is unsaid. Fix: no new word; a renamed field is a hole the program fills in `migrate`.
11. **The coordinator putting a failed node back is the runtime's second attempt** (mvp3.2.md §6 *Lockstep* against §1 and mvp3.0.md §10). The operator's yes covered the new build, not a return to the old. Fix: at a node that does not answer, the coordinator stops and prints what stands; a second `ern deploy` of either build, with its yes, is the way on or back.
12. **The old service forwarding to its successor is the runtime changing what a process does behind its text** (mvp3.2.md §6 *The planned stop*). Principle 3 and mvp3.0.md §1's "A process changes its code only by its own act". Fix: the old service ends with its keys withdrawn, and a client reaches the successor by its next find, which is what the key is for.
13. **A new module per protocol change renames the service in every client** (mvp3.2.md §6). Two names and two keys stand for one service for the length of a rollout; the Erlang reader changes a module in place. The rule follows from "a type's hash covers its qualified name", a decision not weighed against this cost. Fix: let the old declaration live in the tool's cache, which holds every build's canonical forms by hash, named in `forward` and `migrate` by the build, `Counter.Msg of build 2`, so the new declaration keeps its module and name.
14. **`Unreachable` costs a one-node program an arm** (mvp3.0.md §2, §4 against principle 5). The Erlang reader's `noconnection` makes it the right design, so it is a departure to state, not remove. Fix: state in §9.3 that `Unreachable` is a reason only a monitor on another node's process gives, and accept the arm.
15. **A `send` that may wait 7 seconds is control flow the text does not show** (mvp3.0.md §5.4, §6 *Messages*). §6.5 says `send` "returns at once". Fix: state it as a rule in §6.5, "a `send` to a process of another node may wait for the network".
16. **Claim 4.1 cannot be true as written** (mvp3.2.md §4.1 against mvp3.1.md §6). "refused by its hash before any frame is decoded" against "A message carries nothing of its type"; what holds is mvp3.1.md §4.5's argument through the find. Fix: restate 4.1 as mvp3.1.md §4.5 states it.
17. **Three notions where §8.7 has one** (mvp3.1.md §6 *The hash*). A definition has a hash, a binding an identity of name plus hash, a type a hash and a separate identity, a key "carries its type's identity, hash and members". Fix: one word, identity, defined once per kind of definition, and "hash" kept for the SHA-256 alone.

Checked and not found against the principles: the typed address and failures as values, departures mvp3.0.md states and principle 3 justifies; the refusal of a function inside a message and of a bound type crossing; the bare node, a runtime mode and no concept of the language; `ern diff` and `ern deploy` printing a plan and waiting for a yes.

## O. Operations

Read in full: the three proposals, and `other_systems.md` sections 1 and 7.

1. **Two owners after the first restart, in the proposal's own example** (mvp3.2.md §6 *The planned stop*, *Lockstep*). The store's `main` runs `Peer.offer(Counter.key, counter)` with `count(0)` unconditionally, so the restarted store offers a fresh counter at 0 while the backup holds the moved one; `Peer.find(key)` asks the store first and every client sees the total reset; when the backup is later stopped its counter moves back onto the store as a second process. Claim 4.3 does not hold. Fix: say what a node's start does for a key whose state another node holds, the successor staying and the restarted node's offer refused or deferred until the state is moved back; or drop the move and always restart from the state file, accepting limit 5.1's gap, as Orleans and Akka do (*V2*, *V8*).
2. **How the runtime gets a service's state out of a running process is unstated** (mvp3.2.md §2, §6). §3's service is `count(total)`, a receive loop whose `total` nothing outside the process can read; the plan cannot find a "state type" in the hashes. Fix: state the service shape the deploy requires, a declared state type and the operation by which the runtime obtains the value, which the survey argues must be the loop's argument and nothing on the stack (*S7*, *V8*, *D7*), and rewrite §3's counter in it.
3. **Who starts a node after its close is unstated** (mvp3.2.md §6 *Lockstep*). The coordinator can send nothing to a machine whose node has closed; under systemd the unit restarts the node with its old command line, naming the old build directory, and `ernest.pid` settles the race at random; a machine that dies mid-stop comes back on the old build with fresh state. Fix: the node records in its configuration directory, before step one, the build it is to run next, and `ern run --config-dir dir` with no `.erc` runs the build the directory names, so any restart lands on the planned build; the coordinator's "starts that node" is a frame to a living node or a printed instruction.
4. **The state file is removed at its read** (mvp3.2.md §6 *The state file*). A service that reads and then faults, or a new build killed after the one-minute wait, has lost the state; every system read keeps the old form until the next write (*V12*, *V13*). Fix: the file stays until the next planned stop's rename replaces it, and a start that finds one reads it.
5. **Two operators run `ern deploy` at once**: silent in all three. Both plans succeed, both get a yes, and nodes take stop frames from both. Fix: a node that takes a planned-stop frame marks itself with the coordinator's key and target build until it has restarted and been checked, answers the mark with its hashes, and refuses a frame from another coordinator; the plan refuses where any node is marked by someone else.
6. **A node is down when the plan is made**: silent. If skipped, the drop rule is unsound, the down node returning on the dropped protocol. Fix: the plan refuses when a listed node does not answer, naming it, and continues only with an explicit `--without node` whose line says that node must be deployed by hand before any build that drops a protocol.
7. **A rollout is cancelled half way** (mvp3.2.md §2). A cancel during a node's stop leaves the four steps running with no coordinator to restart it; the node closes and stays down. Fix: a cancel is caught by the coordinator, which lets the current node's stop finish and restarts it into the new build if the state step passed and the previous one if not; a node whose coordinator's connection is lost before its state step offers its keys again and stays.
8. **A node whose start takes longer than a minute is rolled back while starting** (mvp3.2.md §7). A large state file is read at start; at 61 s the coordinator acts. The move as a `Peer.spawn` captured value serializes the whole state as one term and crosses the one connection in pieces (mvp3.0.md §5.5). Fix: separate the start wait from the drain, drive it by the node's own report of its start phases, give the state step its own bound, and have the plan print each service's state size.
9. **The disk is full when the state file is written**: silent; the write fails and the close proceeds, losing the state. Fix: a failed state step ends the stop before the close with the node still serving and the keys offered again, and the coordinator stops and prints the error; `ern deploy` compares free disk against each state's size before the yes.
10. **The network partitions during a rollout.** A coordinator parted from a healthy node cannot tell it from a dead one and, when the partition heals, rolls back a node that is up on the new build; a move whose `Peer.spawn` fails with `Unreachable` may have started its process, and the stop writes no file since the key has another node. Fix: the state step always writes the file and moves in addition; a coordinator that loses a node mid-rollout stops and prints without acting on it.
11. **A node is added to or removed from `ernest.conf` during a rollout**: silent. Fix: the coordinator reads each node's configuration at planning and before each stop and stops where any differs.
12. **The same build deployed twice is a no-op, which a release of `ern` as a rollout contradicts** (mvp3.2.md §6, §4.11). The program's hashes are equal, so nothing restarts a node to pick up the new `ern`; nothing says who installs the binary. Fix: the plan compares each node's `ern` release and surface version as it compares hashes, restarts a node whose release differs, and names the installation of the release on each machine as the operator's precondition.
13. **The coordinator on another `ern` release**: sound at the handshake, not in the hashes. A compiler fix in a release with the same scheme version makes the coordinator's hashes of unchanged source differ from the nodes'. Fix: bump the scheme version with any change to what runs before hashing, which mvp3.1.md §11.5 half says, and print every node's release and scheme first.
14. **A node's cache is corrupted or deleted** (mvp3.1.md §6, mvp3.2.md §6). Verification is stated for arrival, not for a load from disk; a deleted cache leaves no way back; a rebuilt machine gets a new key and, being bare, runs no entry point, and nothing may copy a build to it. Fix: a node verifies every definition against its hash when it loads from disk and refuses to start naming the hash; the coordinator ships what a node lacks for both the next build and the way back before the yes; a machine's first start is by hand with a build directory, stated.
15. **The first deploy ever**: silent on a cold start; nodes of an MVP 3.0 build refuse the coordinator; and "where a build names the previous one" says not how. Fix: `ern deploy` plans over running nodes alone, a stopped node is started by hand into the build its directory names, and how a build names its predecessor is stated.
16. **No way to see what runs.** The plan is kept nowhere, the state file is readable by nothing, `Peer.nodes()` gives names, and a build has no name. Fix: `ern status --config-dir dir`, printing for each node its build, `ern` release, surface version, the keys it offers and any rollout mark; and `ern state path`, printing a file's type and value as Ernest literals.
17. **The hot fix at three in the morning.** The plan does not say how long the rollout will take, what clients see meanwhile, how to go back, whether the given build is older than what runs, or that it will restart nodes whose code did not change: in §3's first example desk and board do not depend on `count`, yet all four are restarted. Fix: print the estimated time, the way back as a command, a rollback line where the target is older, what a standing address drops meanwhile, and skip a node whose entry point's closure is unchanged, saying so.
18. **A rollback after the drop**: answered and sound (§4.7, §5.9, §6 *The way back*), resting on knowing every node's build (finding 6); the cache lets a build go at the drop and the operator is never told which builds remain reachable. Fix: the plan prints the builds the way back can reach, and the cache keeps a build until the plan has printed that it is unreachable.
19. **Two nodes on one developer machine**: answered; two tests in parallel pick colliding ports. Fix: `listen` takes port 0 and the node answers the port it bound.
20. **A node's clock is wrong**: nothing depends on wall time. Sound; keep it so.
21. **The check after a restart is liveness, not health** (mvp3.2.md §6 *Lockstep*). A build that leaks after ten minutes is on every node before anyone sees it; a client node that offers no keys is checked by nothing stated. Fix: `--pause ms` between nodes and `--only node` for a canary, and a stated check for a node without keys.
22. **Any listed peer can stop any node**: the desk can stop the store, by mvp3.0.md §5.9. Fix: name it as that limit's consequence, and let a node accept a planned stop only from peers its configuration marks as coordinators.
23. **Three builds in flight**: deploy.md says the plan checks each pair, mvp3.2.md does not. Fix: state in §6 that every check runs against every build any node runs or any state file holds.
24. **`Peer.standing`'s lifetime and first find** (mvp3.2.md §6). It never says when the process ends, so a caller that ends leaves it finding for ever, memory no collection reclaims; and it answers `Left` where the first find fails. Fix: the standing process monitors its caller and ends with it, and standing succeeds with a waiting address when the service is not yet there.
25. **Unlisted changes to mvp3.0.md.** mvp3.2.md withdraws keys where mvp3.0.md says nothing withdraws one, and makes `ern stop` the planned stop where mvp3.0.md makes it `kill -TERM`'s equal; neither is in mvp3.0.md's status line. Fix: list both, and say the standing address learns of a stop through the `Down`, not through withdrawal.

Judgments. **The drain's minute** is right for calls of seconds, since Ernest holds no connections of its own; but "mailboxes are empty" is wrong, a busy service never being empty and emptiness being a moment, so keep "no call waits on any of its services" alone. **The planned stop's steps** are the field's order; the state step has no failure path (9, 10) and the move's half makes two owners (1): make the file the rule and the move an addition, and a failed state step abort the stop. **The plan's printed form** says more than Orleans or Akka print; missing against practice: the direction of compatibility per service (*S3*), the builds in flight and which the way back reaches (*S4*), the time, the nodes skipped, the drain, and what the plan cannot check, in the plan and not only in the proposal; and nothing persists the plan. **`Peer.standing`** is honest where Orleans and Akka queue, consistent with the loss's semantics; its lifetime (24) and its re-find on `Unreachable`, which automates the two-owner mistake mvp3.0.md §5.1 warns of, should be stated as limits.

## W. The paper program

The writer wrote an accounts system of five nodes and a coordinator through five builds and a rollback, in Ernest as the report has it plus the three proposals; the program is [`proposals/nodes_and_code/experiments/paper/accounts.md`](../proposals/nodes_and_code/experiments/paper/accounts.md). Where a proposal left a form unsaid the writer wrote the smallest form that let the program go on and recorded the gap.

1. **A service's state is nowhere a thing the runtime can reach.** In the report a service is a binding that holds an address over a loop whose state is its arguments, and nothing can read a loop's arguments; mvp3.2.md names `forward`, `migrate` and `was` and no declaration a service takes; deploy.md says "A library service hands its state on by default" and names no library; and nothing says how the coordinator learns a key's state type. Fix: add to mvp3.2.md §2 the one declaration a service takes to be deployed, `Service.start(key, init, step) : Service.Handle(m, s)`: the loop is the library's, it offers the key, its handle's type names the protocol and the state type the plan reads, it reads `state/<key>` at its start, and the planned stop asks it for its state.
2. **Two keys of one name on one node cannot both be offered.** Build 3 must offer the new key and the old, both `Peer.key("accounts")`, but mvp3.0.md says a later offer under the same name takes the earlier's place. Fix: a node keeps one offer for each key by its name and its type's identity; a later offer under the same name and identity takes its place, and a find answers the offer whose identity is the finder's.
3. **Nothing spawns the forwarder.** `forward` sends and answers rather than returning a message, so it is a process, and no sentence says who starts it or offers the old key under it. Fix: when a service starts under a key whose module declares a `forward` from an older protocol, the library spawns a forwarder beside it and offers the older key under its address; the forwarder ends with the service.
4. **After the move the restarted node's own binding starts a second service.** The store's build 2 evaluates `let accounts = Service.start(...)`, a fresh empty service offering the key, while `backup` holds the moved one; the clients' order finds the empty one. Fix: a service started under a key one of the key's nodes offers at that moment does not run `init`: it takes the state the move hands it, and the moved process ends; the coordinator moves a service back as part of its node's restart, before the check.
5. **No one can start a stopped node.** Step four ends the node, and a node that has ended has no process the coordinator can reach. Fix: a planned stop that carries a next build does not end the host process: `bin/ern` stays and, once the runtime has stopped in order, starts it again from the cache with the build the stop named; `ern stop` with no build ends the process.
6. **The derived `migrate` is stated three ways, and only one can be written.** "never with a default the program did not write" against "a default for a field the new type adds" against "derived: adds = 0", which implies a field default Appendix A has not; and from a non-record state the rule has nothing to match. Fix: a field a new type adds has a hole; where the old state is no record, `migrate` is written whole; drop `derived: adds = 0` from §3.
7. **The reverse `migrate` has no name**, and two functions `migrate` in one module are an error. Fix: `migrateBack : (NewState) -> OldState`, declared beside `migrate`.
8. **Which `keys` the coordinator reads, and a node cannot list itself** as a key's node, the running node being no peer of itself; `ern stop` by hand has no coordinator to name the move's target. Fix: the coordinator's `ernest.conf` is the `keys` the plan and the stops go by; a node run by hand goes by its own, and writes the state to its file where its own lists no other node.
9. **After a deploy, a machine's reboot runs the wrong build.** The only `store.erc` on the machine is build 1's. Fix: `ern run --config-dir dir` with no `.erc` on a node whose cache names a current build runs that build's entry point; the cache records the entry point with the build.
10. **A one-shot client is no node a rollout can reach**, yet mvp3.2.md §3 lists `desk` in every order. Fix: a program that is not running is not in the order; its machine's cache takes the build at the next `ern run`, or one-shot programs are built and copied as before, stated.
11. **Nodes whose code did not change are restarted.** Fix: a node whose entry point's closure has one hash in both builds is not in the order.
12. **The next build's root for each node is unnamed**, nodes running different entry modules of one build. Fix: a node's root in the next build is the entry point of the qualified name it runs; a build without it refuses the plan.
13. **The move with an older next build has no reverse step**: an older build has no `migrate` from the newer type. Fix: where the next build is older, the stopping node applies `migrateBack` before the state moves or is written.
14. **A standing address that fails at first forces every client to write the retry loop it exists to remove.** Where no node offers the key yet, the client gets `Left(NotOffered)` and loops. Fix: `Peer.standing(key, ms)` answers `Right` whenever the key is listed, its process finding the service within `ms` and again as it goes; `Left(NotListed)` is its one failure.
15. **The example's `Left(Timeout)` is not the language's**: `Peer.Failure`'s constructors are neither the module's nor the prelude's. Fix: `Left(Peer.Timeout)` in the examples, or `Peer.Failure` in the prelude.

Acknowledged in the proposals' own section 9 and so not findings: the JSON shape of `keys`, the syntax of `was`, and the report's §8.3, §6.2 and §10 still carrying the older peer chapter.

## C. Consistency across the three

Read in full: the three proposals.

1. **Nothing in the three says what a service's state is to the runtime or how the runtime gets it** (mvp3.2.md §2, §6). In mvp3.0.md §3 the counter's state is the argument of `count(total)` inside a `restarting` function, and a service is "a top-level binding that holds an address"; no declaration, library shape or operation lets the runtime read `total`, hand it to a successor, or let build 2's `main` read it instead of running `count(0)`. ## F. Feasibility against the runtime and the host

Read: the three proposals, the distribution experiment's README, `run.sh` and `ern_probe.erl`; `ern_rt.erl`, `ern_os.erl`, `ern_exec.c`, `ern_cli.erl`, `ern_build.erl`, `ern_fs.erl`, `ern_emitter.erl`; OTP 29's `erlang.erl`, `code.erl`, `net_kernel.erl`, `init:restart/1`. Most important first.

1. **Nothing can start a node after its planned stop, nor put one back after a failed start.** The coordinator acts only on a connected node, and after the close no process of Ernest's runs on the machine; a node cannot leave a successor behind through `Os.start`, since a program's process group is killed when its owner ends, and mvp3.0.md §6 refuses a start that finds `ernest.pid` living. The host offers `init:restart/1`, a restart inside the same OS process from the same boot arguments, which can carry a node into its cache; but a new build whose initializer faults ends the node, and the OS process is then gone. Fix: the node restarts itself by the host's restart into the build a file in its directory names, which the coordinator wrote; a node whose new build does not come up falls back to the previous build by its own launcher before it ends, or the machine's service manager starts it; say which.
2. **The runtime cannot read, drain, move or forward a service's state.** A loop's state is an argument on its stack, which the host gives no way to read, and the mailbox is the host's, so nothing of the runtime's can make the old process forward. deploy.md §7's "a library service hands its state on by default" presupposes a `Service` shape with a hand-over request, which mvp3.2.md §2 does not list. Fix: a service that is drained, moved or written is a process of the library's `Service` shape, which answers the runtime's request for its state; a plain receive loop is restarted with nothing; the counter example rewritten in that shape.
3. **An adapted address cannot be found in a message without looking through the message, and today's representation runs its function on the sender.** The host's send encodes the whole term with no hook per subterm, so finding a `via` inside an outgoing value is a traversal of every remote message, which CLAUDE.md's cost rule forbids and mvp3.0.md §6 denies. The address is `{via, Function, Target}` with an Erlang fun applied by the sender's `deliver/2`; a fun crosses callable on a peer of the same build, so "f runs on the node that made it" needs a representation carrying the maker's node, and the receiving runtime must send to that node's gateway. Fix: an adapted address carries the node that made it; a send to one from another node goes unconverted to that node's gateway; the check of captured values is made where `via` is written, the compiler refusing a `via` whose function captured a bound value when the address's type may cross. Or state the traversal and its cost.
4. **The dialer cannot tell `Refused` from `Unreachable` at the host's handshake.** The dialer's host reports a failed connection as `noconnection` with nothing of the handshake's reason; a key refused in the verify function ends in a TLS alert the controller swallows the same way; the experiment's step 10 saw a wrong cookie as a silent timeout. Fix: a connection the peer's handshake refused is `Unreachable` to the dialer; the acceptor says on its standard error that it refused a key it does not list; a build refused by the cookie is seen on neither side but in the host's log; `Refused` is the peer's refusal of a closure.
5. **The drain's condition is not observable as written.** Mailbox lengths are readable for local pids. The table of calls is written by the caller, so a remote caller writes no row on the callee's node; the note frame fills it, but the note goes to a process other than the service, and the host orders per sender-receiver pair only, so an empty mailbox and no row can be seen while the request is still in flight. A service computing, or waiting on a call of its own, shows in neither measure; a call through a standing address names the standing process as callee. Fix: define the drain as the services' mailboxes empty and no row against them, seen twice with a pause between, and say the request in flight and the one in hand are what the drain's bound covers.
6. **The helper process breaks the order claim, and its number is bounded by the host's process limit.** The host keeps order per sender-receiver pair; a request a helper sends is another sender's, so a later plain send can pass it; the same for an answer. A process is spawned per request or answer that finds the buffer full, for up to the detector's 45 to 75 seconds; a service answering 20,000 a second into a stalled peer reaches the process limit, 1,048,576, in under a minute. Fix: add to §4.1 that a message sent after a request or answer that waited for the network can pass it, and the process limit to §5.4; or one helper per peer that takes every later message of a sender while it holds one, with that cost stated.
7. **The cache fetch is not mvp3.1.md's exchange as written, and the coordinator must serve forms from a build it does not run.** The exchange is defined from a spawn frame and ends in a load and a start; the cache's asker is a node told a root hash, its server the coordinator reading canonical forms from the new build's `.erc` directory, and the receiving side must stop at verified and written. The node must also persist what to start: the entry's hash, and what `ern_cli` checks today, the interface and the standard library's identity. If the cache holds forms alone, a restart compiles the whole program inside the drain's bound. Fix: the exchange has two askers, a spawn and a node told a root hash, which asks the node that told it; the coordinator serves a build's forms from its directory; what a root brings is verified and written to the cache with its compiled units and not loaded; the cache names the entry.
8. **A gateway per connected peer cannot take the first frame.** A find or spawn frame to a peer with no connection open is what opens it, so it arrives before the acceptor has seen the node up; a message to a registered name that does not exist on a remote node is dropped without a word, and the finder waits out its ms. Fix: one registered gateway per node takes every frame and hands each to a worker for the sender's node.
9. **§5.4's sentence that a plain send waits for the dial contradicts the experiment and §6.** The experiment's step 8 saw three sends return in under 10 microseconds and wait behind one dial; the kernel queues behind a pending connection and suspends the sender only past the busy limit, 1,048,576 bytes here; the dial's time is the kernel's 7,000 ms setup time. Fix §5.4: a plain send to a peer with no connection open returns at once and its message waits behind the dial; the sender waits only where what waits exceeds the buffer.
10. **A find by the key alone over several peers does not fit one ms with one dial each.** A dial nothing answers takes 7 seconds, so a find of 5,000 ms over two peers with the first silent answers `Timeout` before the second is asked; the §3 example works only because a stopped node's port refuses at once. Fix: a find by the key alone gives each peer the time left and moves on at `Unreachable`, `NotOffered` or `OtherType`, and a silent peer early in the list can take the whole ms; or dial the key's peers at once.
11. **A standing address cannot see a withdrawal, and the example's `Down` is the wrong one.** The standing process monitors its process, which lives through steps two and three, and nothing withdraws an offer unasked, so the standing address learns nothing until the close and forwards to the old service meanwhile, which step three's forward covers. Say so, or add a notice to every finder with the table of who found each key. And a node that ends is no loss: a monitor on one of its processes gives `ProgramEnd`, as the experiment's step 13 confirmed, not `Unreachable` as §3 says.
12. **The coordinator's knowledge of each node's build needs a frame and a definition of "build".** None of the seven frames answers it; §9 lists it as unsolved. A node holds the closures of the builds it has run and processes spawned from other builds; a bare node runs none. Fix: a node's version is the root hashes it started from; the coordinator's frame asks a node for them, for the keys it offers with their identities, and for what its cache holds.
13. **`ern stop` by `ernest.pid` is a signal, which cannot carry `--drain`, and the two proposals disagree on what TERM is.** `ern stop` has no key and cannot connect, so it is a signal; it must then be a signal other than TERM, and a signal carries no ms in. Fix: name the signal (USR1), say TERM is the quick end in both documents, and that `--drain` for `ern stop` is written to a file in the directory the node reads at the signal, or is the default.
14. **`ern deploy` cannot carry a release of `ern`, and today's checks refuse a cached build after one.** What crosses by hash is Ernest code; the runtime, the compiler and the helper are loaded from the installed tree and never cross. The compiler build's identity and the interface checks refuse an `.erc` built by another compiler build; a node restarting into a cached build after a release must recompute or waive them. Fix: the operator installs the release on each machine; `ern deploy` then restarts each node into it.
15. **Embedded mode changes how the runtime loads everything.** In embedded mode `code:ensure_loaded` does not load, and today every process's error handler loads on first call, the standard library by `ensure_loaded` over the code path, the shell by `load_binary`, the emitter by `ensure_loaded` of the host module, and the compiler, `ssl` and `crypto` lazily. Units off the code path are never autoloaded in interactive mode either, so the sentence costs the loading rewrite and buys nothing. `code:atomic_load/1` itself is fine. Suggest dropping "embedded mode".
16. **The atom table is missing from mvp3.1.md §7.** Every unit's name and every function name in it is an atom, never reclaimed, limit 1,048,576 here; with hundreds of functions per unit the atom table ends thousands of units before the module table does. Add it to §7 and to the warning at four fifths, and name a unit's functions by position so the names are reused.
17. **The state file has two gaps.** Neither the write nor the rename syncs, so a completed stop and a power loss can leave an empty file after a successful rename; and decoding the value fails where the old type's constructor atoms are not yet made on the node, so a service that holds no `migrate` for the hash must read the hash and never decode the value. Add "written, synced and renamed" and "the hash is read before the value is decoded".
18. **Smaller points.** `ern config` generates ed25519 keys while the experiment pinned prime256v1 certificates; ed25519 in TLS 1.3 with a pinning verify function is untried. A node that does not listen is hidden, and the loss notice needs the node monitor with all node types, which §6 should say. The call's reply is made with alias and demonitor, not reply-demonitor, so a second answer crosses the wire before it is dropped. The reaper counts a monitor of a process it did not start as a source and looks for deadlock, so §5.6's "declares no deadlock" is a flag set when `--config-dir` is given, and the reaper must map `noconnection` to `Unreachable` rather than a fault.
