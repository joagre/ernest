# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, an item of a milestone, or a line in the log saying it was dropped and why. An entry keeps its number, which the plan, the log and the code cite; the next is 262.

260. **`Fs` has no way to make a write reach the disk before it answers.** `Fs.write` is the host's `file:write_file`, which calls no sync, and E.17 promises of `rename` what a reader of the path sees, not what a power loss leaves. A program that keeps data across a power loss cannot be written in Ernest. The host has `file:sync/1` and `file:datasync/1`, so E.0 rule 1 admits the operation and rule 4 does not refuse it: the question is its shape. Two facts for it: `Fs` has paths and no open file, where the host's sync takes an open file; and a write that survives needs the file synced and, after the rename, its directory. Found 2026-11-17 by a reading of the guide's kept count (the log's *The Outside Reviews Read*); the plan's MVP 4.16, item 96.

261. **`Tcp` hands no listener to another process, and no second listen stands beside a live one.** `Tcp.give` moves a connection's socket and nothing moves a listener's, and `Tcp.listen` answers that the port is taken while a listener holds it (E.18). A program that takes new code while it serves therefore closes its old listener before the new one listens, and connections are refused between. The host has both: `gen_tcp:controlling_process/2` takes a listening socket, and the kernel's option to share a port lets a second listen stand. Found 2026-11-17 by ernest-httpd's session, asked what new code under traffic would take (the log's *The Server's Answers*); the plan's MVP 4.5, item 4.
