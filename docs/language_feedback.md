# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, a "Later" entry in the log, a question in the plan, or a line saying it was weighed and left alone. An entry keeps its number, which the plan, the log and the code cite; the next is 103.

97. **A previous version's values are made only by what was kept from before the reload** (2026-10-10, MVP 3.1's item 5, `test/ern_shell_tests.erl`'s `reload_keeps_the_type_checked_under`). After a `:reload` changes `Counter.Msg`, a binding of the previous version's type takes only a message of that version, whose constructors are `Counter$1.Inc`, a name no input writes, since `$` marks a name the session made (§11.2). So a message for the previous version's process is made by a function kept from before the reload, `let inc = Counter.Inc`, or one an input declared then; a user who kept none cannot make one, though the process runs and its constructors print. Two versions as two types is the rule (claim 3 of `mvp3.1.md`); what feels against principle 3 is a type whose values the session shows and cannot write. Weighed for: a previous version's constructors writable at the prompt alone. Stands as MVP 4.3's decision.

98. **`:processes` shows two versions' processes alike** (2026-10-10, MVP 3.1's item 5). A reload's service runs beside the previous version's, and both are listed by their spawn site, `Counter.service:5`, the spawner's words, which are the same in both versions; which version a process runs is invisible at the prompt, where the session tells the versions' types apart by `Counter$1`. Weighed for: `:processes` naming the version of the unit a process runs, which the host's report of its current function gives. Half decided 2026-10-10 with MVP 3.1's read (W17): a reload's version's spawn sites carry the number, `Counter$2.service:5`, so the end's lines tell the versions apart; `:processes` naming the version in a column of its own stands as MVP 4.3's decision.

102. **A reply a function took to `Peer.spawn` cannot be answered where the spawn fails** (2026-10-10, a draft of `examples/typed_channels.ern` whose `squareOn` handed a request's reply to a function spawned on a peer; the example as kept spawns nothing on a peer). The function a spawn on a peer starts is consumed by the spawn whatever it answers (§6.6), so where `Peer.spawn` answers `Left(NotListed)` or `Left(Unreachable)` at once, the reply its function captured is gone with it, and the caller learns of the failure only as `None` when its own time runs out, though the spawner knew at once. Against principle 3, a failure visible where it happens: the spawner holds the failure as a value and cannot hand it on. The way around it, a function that sends its result to the spawner, which answers, gives up the reply's crossing that §8.7 decided today; the draft kept the crossing and said in its comment that a failed spawn drops the reply. Planned 2026-10-10: MVP 3.2's item 1 decides it, a named decision of that item, where the spawn frame is written anew for the code it carries: whether a reply that crossed with a function a failed spawn dropped ends the caller's call at once, as a callee's death does, or waits out its time.

103. **Two declarations whose forms are one term are one definition** (2026-10-13, MVP 3.2's item 6, `erl/cli/test/ern_code_load_tests.erl`). `Code.running(waiter)` listed the processes of `idle`, a function of another name with the same body, since Appendix H hashes a definition by its form and the form holds no name, so the two are one definition and a reference to either is to the first declared. A reader who knows Ernest predicts that two names are two functions. The gain is content addressing itself, a renamed function staying the same definition on every node; the surprise is stated in Appendix H and E.28, and shows only where two top-level functions are written verbatim alike, which a program rarely wants.

104. **A message type that carries `Upgrade` is bound to its node** (2026-10-13, MVP 3.2's item 6, `test/ern_nodes_tests.erl`'s `code_upgrade_test_`). §6.10's `Upgrade(migrate, next)` puts two functions in the process's own message type, and §3.11 binds a type that holds a function to its node, so the counter could not be offered as a service nor its loop spawned on a peer, which a reader adding an `Upgrade` clause to a working service does not predict. Decided 2026-10-13: the service is offered through an adapted address (§6.5) of a type without `Upgrade`, its upgrade sent on its own node over `Code.running`, stated in §6.10; a second type with the public constructors is the cost. What would lift it: a function value that crosses by its declaration's identity, the log's *Later*, shape C.

105. **A program cannot time anything under a millisecond** (2026-10-13, MVP 3.2's item 7, the measuring programs of `test/bench/`). `Clock.monotonic` answers milliseconds (Appendix E.15), so a program that measures a spawn, a pick or a raise, which take microseconds, declares `erlang:monotonic_time/1` as a `foreign fn`, which CLAUDE.md forbids a program to do for a gap in the library. The host answers any unit exactly (E.0 rule 1). To decide: a function beside `monotonic` in microseconds, `Clock.monotonicMicros`, under E.0's admission rules, the measuring programs then written over it. Decided 2026-10-13: `Clock.monotonicMicros`, E.15, built with MVP 3.2's item 7.

106. **A placement rule of the program's own cannot wrap the compute** (2026-10-13, MVP 3.2's item 8, `proposals/placement/push.md`'s first example and the guide's `least.ern`). A helper `leastLoaded(f, ms)` that picks a name over `Peer.utilisations()` and then computes `f` there is refused, since §3.11 admits as the function of a compute a declaration or a lambda written at the call and not a function that came as a parameter; so the rule answers a name and the compute is written where the lambda is, two lines in place of one call. Against principle 2's one way, mildly: the restriction is §3.11's own, which keeps a function value from crossing, and the two lines are the honest shape; what would change it is a function value that crosses by its declaration's identity, the log's *Later*, shape C.

107. **No `List.minimumBy` or `maximumBy`** (2026-10-13, MVP 3.2's item 8, the guide's `least.ern`). The least busy of `Peer.utilisations()` is a `List.sort` with a comparator over a tuple's field and the head taken, where a reader who knows the type looks for the smallest by a key in one call. To decide under E.0's admission rules: `List.minimumBy(list, key)` and `maximumBy` beside `List.sort`, or the sort kept as the one way.
