# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, a "Later" entry in the log, a question in the plan, or a line saying it was weighed and left alone. An entry keeps its number, which the plan, the log and the code cite; the next is 81.

64. **A record of operations cannot hold a polymorphic operation** (2026-09-28). An operations record, `SetOps(s, a)`, cannot hold `Set.foldLeft`: the field `fold : (s, b, (b, a) -> b) -> b` is refused, `type variable b is not a parameter of the type`. An effect variable may be a parameter of the record, but one record value then fixes one effect for all its operations. A Haskell class method and a Java generic method are polymorphic in such a variable, and nine of `Set`'s twenty functions mention one besides the set and its element, so it bites principle 1 where the contract is to stand for a library type. The choices: a field's type quantifies the variables the type does not take, as OCaml's polymorphic record fields do, checked where the record is built and instantiated where a field is selected, so that inference stays Hindley-Milner's; or the verdict that a contract holds what its types close over, the rest written over its `toList`. The first is much smaller than type classes, with no instance resolution, no constraint in an inferred type and no hidden argument, and it still puts a type scheme inside a type declaration, where the log's *Dropped from Unison* drops rank-n types. A field's own variable carries no inferred restriction, since none is written, so a value that needs one, `==` on it, does not fit the field. `map` and `filterMap` need a representation for the result's element, which neither choice gives, as neither Haskell's `Data.Set` nor Java's `Set` has one. MVP 2.99b takes it first, after the first release; [`operations.md`](operations.md) proposes the second choice, a record of the primitives.

69. **`T.compare` may be declared at an instance of its type** (2026-09-29). §4.8 gives a member named by an operator, `compare` among them, the type `(T, T) -> Ordering`, with `T` "the type applied to any arguments", so `Pair.compare` may be declared at `(Pair(Int), Pair(Int))`. The ordering constraint `operations.md` proposes cannot then reduce `Ord Pair(a)` to a constraint on `a`, since the instance's head is not the type over its own parameters. The choices: `T.compare` declared over `T`'s own parameters, any other shape refused at its declaration; or the freedom kept, with predicates on types that are not variables deferred, as Haskell's flexible instances do. Maybe: the first, which the note proposes. MVP 2.99b's item 4 decides it.

70. **The standard library's rules meet operations records** (2026-09-29). Three rules stand against the shape `operations.md` proposes. E.0's admission rule 4 refuses a function that is one call of another, which `Set.union`, a call of `Set.Operations.union` with `Set`'s record, is. E.0's shape rule 1 puts a callback last, where the note's rule 5 puts the record last: `map(set, f, from, to)`. And §9 makes a type the prelude's when the module of its operations is named after it, so `OrderedSet` would be declared in the prelude, where `ordered_set.ern` cannot see its constructor (§4.4); E.0's shape rule 7 also refuses the name `OrderedSet.OrderedSet`. Maybe: rule 4 admits a representation's own call of a generic function, which requirement 1 asks for; the record goes last and the callback before it; and a standard library type written in Ernest is declared in its own module, as §9 then says. MVP 2.99b's item 4 decides them.

71. **A type's order is not part of its identity** (2026-09-29). §8.7's type hash leaves out member bodies, so a value built under one `T.compare` can be read under another: at a node with another version of the module, in code shipped with a spawn, after an `Upgrade` (§6.10), and across `:reload` and the shell's later inputs (§11.2). An ordered set read under another `compare` is misordered, and its `contains` answers wrongly. The same holds for any value whose invariant rests on a member's behaviour. The choices: a type's identity includes the hash of its `compare`, or of every member its values' invariants rest on; or the misordering stated as the price of versions. Maybe: `compare`'s hash in its type's identity, since the order belongs to the type. MVP 2.99b's item 4 decides it for the ordered set, and MVP 3.0 where versions meet over the network.

73. **The note's rule 3 refuses a top-level function that is not a `fn`** (2026-09-29). `operations.md`'s rule 3 generalizes no top-level `let` over an ordered variable, since an initializer may spawn and send and must run once (§8.5). It also refuses `let lt = fn(a, b) = a < b` and `let insert = OrderedSet.put`, which compute nothing and repeat no effect, while a block `let` of the same lambda is generalized (§4.6, the log's *A Lambda Bound by `let` Is Generalized*), and §3.9 lets such a lambda name its own type variables only where the binding is generalized. The choices: an initializer that is a lambda or a name exempt, as ML's value restriction exempts values (Wright 1995); or the rule kept whole. Maybe: exempt them. MVP 2.99b's item 4 decides it.

76. **A nested record update spells every constructor on its path** (2026-10-01, the release review's N-C8). §5.6's `C(..p, f = v)` updates one level, so a field two levels down is `Pool(..pool, stats = Stats(..pool.stats, indexed = pool.stats.indexed + 1))`: the path written twice, and each constructor on it once. The newcomer passed an update function down instead. The choices: a path in the update, `Pool(..pool, stats.indexed = pool.stats.indexed + 1)`, a second spelling which principle 2 admits where the first would nest where the reader reads a sequence, as a path is read, each type on it having one constructor, as `..` already requires; or the form kept, each construction written where a value is built (principle 3). Maybe: the path form, which builds nothing the path does not name. The attack plan's phase 5 decides it with the family *Which forms enter the language*.

77. **`let me = self()` before a spawn** (2026-10-01, the principles review's W-13). `self()` inside a spawned lambda is the child's address (§6.2), so a parent that wants replies binds `let me = self();` first, nine times in the guide, with two warnings explaining it; Erlang's reader writes `Self = self()` the same way. The choices: a spawn whose function takes the spawner's address, `spawn(fn(parent) = ...)`, a second shape of spawn (principle 2); or the line kept, one binding that says what it does (principle 3). Maybe: kept, the guide teaching it once. Weighed again by a milestone that touches §6.2.

78. **`let _ = e` for a value discarded** (2026-10-01, W-31). A statement that is not the last has type `Unit` (§5.4), so a value an effectful call answers, `Tcp.write`'s `Either`, is discarded with `let _ = e`, eleven programs, and a `foreach` body is a block for it. The choices: `List.foreach` and its kin taking `(a) -> b with e` and discarding the result, which makes the common body one expression and hides nothing, the callback's result being the caller's to ignore; a statement of any type accepted, which principle 3's sentence refuses as a value dropped; or the form kept. Maybe: `foreach` over any result, decided with the library family's edits or after 0.2.0.

79. **An ask that answers into the mailbox** (2026-10-01, W-34). A `Reply` is made only by `Address.call`, which waits, so a process that must send a request and keep receiving spawns a helper to wait for it (the guide's §4.4). E.0 shape rule 8 has the form already: a function that delivers later takes a function from the message to the caller's mailbox type, as `monitor` does. `Address.ask(addr, mk, wrap)` would make the reply, send `mk(r)`, and deliver `wrap(answer)` to the caller's mailbox, without a limit, an alarm being the caller's. The choices: the prelude function, which §9's criterion admits since the runtime alone makes a `Reply`; or the helper kept. Maybe: the function. Decided by a milestone after 0.2.0 that touches §6.6.

80. **A `Down` after the dead process's messages** (2026-10-01, W-38). §6.9 says a `Down` has no order with the messages the ended process sent, so a result that must not be lost to a `Down` comes as a call's answer, and the guide's §5.6 routes workers' results through `main`, each count crossing two mailboxes. The host's monitor keeps that order, a `DOWN` arriving after every message the dead process sent to the monitoring process; Ernest's reaper delivers the wrapped `Down` from a process of its own, which loses it. The choices: the monitoring process taking the host's monitor itself, the runtime applying the wrap as the process receives, so that §0's host paragraph takes a seen outcome; or the rule kept and stated, as it is. Maybe: the host's order. Decided with the runtime's monitor design, after 0.2.0.
