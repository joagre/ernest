64. **A record of operations cannot hold a polymorphic operation** (2026-09-28). An operations record, `SetOps(s, a)`, cannot hold `Set.foldLeft`: the field `fold : (s, b, (b, a) -> b) -> b` is refused, `type variable b is not a parameter of the type`. An effect variable may be a parameter of the record, but one record value then fixes one effect for all its operations. A Haskell class method and a Java generic method are polymorphic in such a variable, and nine of `Set`'s twenty functions mention one besides the set and its element, so it bites principle 1 where the contract is to stand for a library type. The choices: a field's type quantifies the variables the type does not take, as OCaml's polymorphic record fields do, checked where the record is built and instantiated where a field is selected, so that inference stays Hindley-Milner's; or the verdict that a contract holds what its types close over, the rest written over its `toList`. The first is much smaller than type classes, with no instance resolution, no constraint in an inferred type and no hidden argument, and it still puts a type scheme inside a type declaration, where the log's *Dropped from Unison* drops rank-n types. A field's own variable carries no inferred restriction, since none is written, so a value that needs one, `==` on it, does not fit the field. `map` and `filterMap` need a representation for the result's element, which neither choice gives, as neither Haskell's `Data.Set` nor Java's `Set` has one. MVP 2.99b takes it first, after the first release; [`operations.md`](operations.md) proposes the second choice, a record of the primitives.

68. **A restart keeps the old run's messages (2026-09-28)**. restarting and a Supervisor's restart run f() again in the same process, which keeps its address and its mailbox (§6.9). What waits in that mailbox belongs to the run that faulted:
      - Requests whose callers were ended with "callee was restarted" (§6.6). The new run answers them to replies no one waits for, or acts on them twice when the caller asks again.
      - What the old run asked the runtime for: alarms, Downs and events (Clock.alarm, monitor, Terminal.subscribe). They arrive wrapped in the mailbox type, and the new run cannot tell them from its own.
      - Plain sends, the only ones that still mean what they meant.

      A reader who knows that a restart begins f() afresh would predict an empty mailbox (principle 1). A message from a run that no longer exists acts unseen (principle 3). In Erlang, a restarted process is a new one with an empty mailbox.

      The same invisibility loses a service's subscribers: the new run has forgotten them, and no monitor tells them (§6.9).

      The choices:
      - the mailbox emptied at a restart, and what the old run set up with the runtime (its alarms, monitors and subscriptions) cancelled with it, so that a restart is a new run in all but its address;
      - the rule as it stands, stated in §6.9, and taught with RestForOne for subscribers;
      - a restart made visible to the process's watchers, so that a subscriber can subscribe again.

      Maybe: the first. Plain sends are lost as Erlang loses them, and a sender that needs delivery uses a call.

69. **`T.compare` may be declared at an instance of its type** (2026-09-29). §4.8 gives a member named by an operator, `compare` among them, the type `(T, T) -> Ordering`, with `T` "the type applied to any arguments", so `Pair.compare` may be declared at `(Pair(Int), Pair(Int))`. The ordering constraint `operations.md` proposes cannot then reduce `Ord Pair(a)` to a constraint on `a`, since the instance's head is not the type over its own parameters. The choices: `T.compare` declared over `T`'s own parameters, any other shape refused at its declaration; or the freedom kept, with predicates on types that are not variables deferred, as Haskell's flexible instances do. Maybe: the first, which the note proposes. MVP 2.99b's item 1 decides it.

70. **The standard library's rules meet operations records** (2026-09-29). Three rules stand against the shape `operations.md` proposes. E.0's admission rule 4 refuses a function that is one call of another, which `Set.union`, a call of `Set.Operations.union` with `Set`'s record, is. E.0's shape rule 1 puts a callback last, where the note's rule 5 puts the record last: `map(set, f, from, to)`. And §9 makes a type the prelude's when the module of its operations is named after it, so `OrderedSet` would be declared in the prelude, where `ordered_set.ern` cannot see its constructor (§4.4); E.0's shape rule 7 also refuses the name `OrderedSet.OrderedSet`. Maybe: rule 4 admits a representation's own call of a generic function, which requirement 1 asks for; the record goes last and the callback before it; and a standard library type written in Ernest is declared in its own module, as §9 then says. MVP 2.99b's item 1 decides them.

71. **A type's order is not part of its identity** (2026-09-29). §8.7's type hash leaves out member bodies, so a value built under one `T.compare` can be read under another: at a node with another version of the module, in code shipped with a spawn, after an `Upgrade` (§6.10), and across `:reload` and the shell's later inputs (§11.2). An ordered set read under another `compare` is misordered, and its `contains` answers wrongly. The same holds for any value whose invariant rests on a member's behaviour. The choices: a type's identity includes the hash of its `compare`, or of every member its values' invariants rest on; or the misordering stated as the price of versions. Maybe: `compare`'s hash in its type's identity, since the order belongs to the type. MVP 2.99b's item 1 decides it for the ordered set, and MVP 3.0 where versions meet over the network.

72. **An ambiguous restriction that carries evidence** (2026-09-29). An ambiguous equality constraint is harmless, since `==` needs nothing at run time: `fn f() : Bool = [] == []` is accepted. An ambiguous ordering constraint is an error, since no `compare` can be chosen, so `fromList([], Set.setOperations())` is accepted and `fromList([], OrderedSet.setOperations())` is refused, and changing a program's representation changes whether it compiles (principle 1). The shown restriction of MVP 2.99b's item 7 meets every type, so the same rule would refuse `Io.show([])`, Haskell's `show []`. The choices: refuse, as Haskell does where it does not default; or, for a restriction every type meets, write the value by its representation, as E.1 says for a type variable. Maybe: refuse for ordering, and the representation for `shown`. MVP 2.99b's items 1 and 7 decide them.

73. **The note's rule 3 refuses a top-level function that is not a `fn`** (2026-09-29). `operations.md`'s rule 3 generalizes no top-level `let` over an ordered variable, since an initializer may spawn and send and must run once (§8.5). It also refuses `let lt = fn(a, b) = a < b` and `let insert = OrderedSet.put`, which compute nothing and repeat no effect, while a block `let` of the same lambda is generalized (§4.6, the log's *A Lambda Bound by `let` Is Generalized*), and §3.9 lets such a lambda name its own type variables only where the binding is generalized. The choices: an initializer that is a lambda or a name exempt, as ML's value restriction exempts values (Wright 1995); or the rule kept whole. Maybe: exempt them. MVP 2.99b's item 1 decides it.
