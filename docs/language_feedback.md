# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, an item of a milestone, or a line in the log saying it was dropped and why. An entry keeps its number, which the plan, the log and the code cite; the next is 146.

140. **A top-level `let` that is no ground term has no value on a bare node** (2026-10-23, the tour's outline, `Tally.empty` and `Counter.service`). A spawn carries a function's reach to a peer that lacks it, but a binding's value is made where its module was loaded, and a bare node loaded nothing, so a reach that names `let empty = Tally(Map.empty)` or `let service = Peer.service("counter")` fails there with `NotLoaded` (report §8.7, §11.1). The tour writes both as functions, where E.0 writes a value, and nothing tells the writer before the spawn fails; a reader who knows the rest of Ernest writes the `let`. Whether the exchange should evaluate a module's bindings on arrival, as `Code.load` does, is a design question. Principle 1.

141. **Taking the `Right` of an `Either` at the prompt is a `match` with a `fault` clause** (2026-10-23, the tour's outline, chapter 2). `let far = match Peer.spawn("foo", fn() = Counter.count(0), 5000) { Right(a) -> a | Left(e) -> fault(Io.show(e)) }` is the shortest honest line, ninety columns, where the guide's `<-` works in a block alone and a Gleam reader predicts `let assert`. A second form that only shortens is what principle 5 refuses; this line is evidence to weigh against it, not a new claim. Principles 1 and 5.

142. **Two nodes on one machine take two `ern config` and edits of two files by hand** (2026-10-23, the tour's outline, chapter 2). Each node's key is pasted into the other's `ernest.conf` as one JSON string, the ports changed so that they do not collide, `listen` removed from the one that only dials, and a `services` entry written for a service to be found; a second bare node doubles it. A tour's reader meets it before the second claim. `ern config` makes a directory and a key, and could list a peer from that peer's directory on the same machine, the one case a reader trying Ernest is in. Principle 1, for the operator's day.

143. **`restarting` after an `Upgrade` runs the loop it was given** (2026-10-23, the tour's outline, chapters 6 and 8). A process under `restarting(limit, fn() = count(empty()))` that was moved to `count2` by its `Upgrade` runs `count` again at its next fault, the old code, with nothing in the program or the report naming it (report §6.9, §6.10). The tour spawns its long-lived counters plain for it. A program that needs both carries a trap nothing shows; a sentence in §6.9 would show it, and whether `restarting` could do better is open. Principle 3.

144. **A computed function cannot say where it ran** (2026-10-23, the tour's outline, the compute chapter). The tour wants to show that `Peer.compute` placed work on one of two bare nodes, and the function has no name for its node (report §8.7), so it prints a line and the peer's terminal shows where. Entry 117 decided on 2026-10-20 that `compute` means anywhere and a program that cares names the peer; the tour is the first program that wants to show the pick and not to use it. Evidence for the record of that decision, not a new claim. Principle 3.

145. **One host question costs a `Foreign.atom` beside its declaration** (2026-10-23, the tour's outline, `schedulers`). `erlang:system_info(schedulers)` is asked as `foreign fn systemInfo(what : Foreign.Term) : Int` and `systemInfo(Foreign.atom("schedulers"))`, two declarations for one question, since a foreign declaration names a function and cannot fix an argument (the guide's §8.3, report §4.7). The one foreign call a tour shows is this one, and a reader sees the atom before the check that is the point. Evidence to weigh, not a new claim: a second form of declaration is what principle 5 refuses. Principles 1 and 5.
