# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, an item of a milestone, or a line in the log saying it was dropped and why. An entry keeps its number, which the plan, the log and the code cite; the next is 269.

260. **`Fs` has no way to make a write reach the disk before it answers.** `Fs.write` is the host's `file:write_file`, which calls no sync, and E.17 promises of `rename` what a reader of the path sees, not what a power loss leaves. A program that keeps data across a power loss cannot be written in Ernest. The host has `file:sync/1` and `file:datasync/1`, so E.0 rule 1 admits the operation and rule 4 does not refuse it: the question is its shape. Two facts for it: `Fs` has paths and no open file, where the host's sync takes an open file; and a write that survives needs the file synced and, after the rename, its directory. Found 2026-11-17 by a reading of the guide's kept count (the log's *The Outside Reviews Read*); the plan's MVP 4.5, item 96.

261. **`Tcp` hands no listener to another process, and no second listen stands beside a live one.** `Tcp.give` moves a connection's socket and nothing moves a listener's, and `Tcp.listen` answers that the port is taken while a listener holds it (E.18). A program that takes new code while it serves therefore closes its old listener before the new one listens, and connections are refused between. The host has both: `gen_tcp:controlling_process/2` takes a listening socket, and the kernel's option to share a port lets a second listen stand. Found 2026-11-17 by ernest-httpd's session, asked what new code under traffic would take (the log's *The Server's Answers*); the plan's MVP 4.5, item 4.

262. **E.18 does not say when the far end sees the close of a socket that ended while its host held bytes.** E.18 has the bytes a socket has taken sent while the far end takes them, by a process the socket makes as it ends, and says that the host's socket then closes. A probe on 0.10.0 over plain TCP on the loopback: after 1 MiB or less, which the kernel's buffer took whole, the close came with the last byte. After 4 MiB the client had every byte within 9 ms, and its read answered `Left(Closed)` 1001 to 1004 ms after the server's close.

     So a client that reads to the close and is slower than the server's write waits up to a second past a response. Principle 1: a reader predicts that the close follows the last byte. Found 2026-11-17 by ernest-httpd's session, its feedback line 31 (the log's *Two Lines on a Close*); the plan's MVP 4.16, item 100.

263. **A write that answers `Left(Closed)` loses what had arrived and no read had taken, and E.18 does not say what a read answers after the far end's close.** E.18 says that after a connection closes each `Tcp.read` answers `Left(Closed)`. A probe on 0.10.0: a client writes a byte the server never reads, and the server writes `hello` and closes, which resets the connection. A client that then reads twice is answered `hello`, then `Left(Closed)`. One that writes a byte first is answered `Left(Closed)` by the write and by both reads, and `hello` is gone.

     A client that still writes when its server answers 413 or 408 and closes meets it. Principle 1: a reader predicts that what has arrived is read before the close is answered. Found 2026-11-17 by ernest-httpd's session, its feedback line 32 (the log's *Two Lines on a Close*); the plan's MVP 4.16, item 100.

264. **A program that waits for a peer's telling reads `Peer.utilizations` in a loop with a sleep.** Four sites do, all in the tests: `test/fixtures/peers/placing.ern` and three programs in `test/ern_nodes_tests.erl`. A telling is the runtime's frame, so nothing delivers it and no message shows that one came. The wait is a time, the teller's interval, where `CLAUDE.md` has a process wait on what it means. No program outside the tests waits so: one that places work reads what the table holds and acts on it. Found 2026-11-17 by the read-back of MVP 4.16's item 97 (the log's *What a Full Buffer Holds*); the plan's MVP 4.5, item 5.

265. **An address given to foreign code keeps a process until its target ends, one for each distinct address.** §8.4 has one check for each distinct address that has crossed, lasting until the process the address names ends, and an adapted address is distinct by its function and by what the function captured. A server that gives a foreign function a fresh `adapted(self(), fn(v) = Got(id, v))` for each request keeps a process, with what the function captured, for each request while it lives. §10 states the process. Read from the code and not measured. It questions §8.4's life of a check: memory that grows with a server's requests and goes only at the server's end. Found 2026-11-18 by the cold reading of item 111's sentences (the log's *A Checker Acts for the Target*); the plan's MVP 4.5, item 113.

268. **No function can run a lambda on a peer or here.** §3.11 has the function a spawn or a compute on a peer runs be a lambda written in the same definition, and refuses one that came as a parameter. A program that runs one piece of work on a peer or on its own node, as a value says, writes the choice at each site. Item 133's probe repeats one form at 12 sites: `let there = fn() = …;` and then `if where == "two" then remote(Peer.computeAt("b", there, limit())) else local(Process.run(there))`. The refusal's help names what to write. Only a probe that compares two nodes with one has shown it, and no program outside the tests. Found 2026-11-20 by item 133's showing (the log's *An Address Given Back, on Another Node*).
