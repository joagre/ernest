What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). 91. **A listener opened in a top-level binding lives under `ern run` and dies under `:load`** (2026-10-07, the chat server under `proposals/nodes_and_code/experiments/code_update/`). §8.5 evaluates a module's bindings in the entry process, which lives through `main`, so a listener a binding opens serves the program; §11.2 evaluates them in a process of the shell's own, which ends with the load, so the same listener ends with its owner (Appendix E.18) before the first input, and the acceptor finds it ended. The report states both, and the program is better with the acceptor owning its listener; what feels against principle 3 is that one source behaves two ways and nothing says so at the `:load`. Weighed for: the shell's binding process living on as the entry process does, or the load reporting a resource its process will end.

93. **A test of two nodes must write the second node's `ernest.conf`, which is JSON** (2026-10-08, MVP 3.0's item 10). `ern config` makes a directory with no peer, and a program's own test of two nodes lists each node in the other's file, so the test, in Ernest, must add a peer and a key to a JSON file. Splicing text into the file would write a data format by hand, which CLAUDE.md keeps out of Ernest code; the standard library has no JSON, and `ern config` writes the file through the host's formatter (the log's *The Node's Directory*). The need is a JSON library under `libs/`, which the same entry foresaw for when Ernest code first meets JSON; this is that meeting.
