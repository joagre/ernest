# Language feedback

What writing Ernest has felt against the principles, and what a reader found that questions a rule of the language rather than showing a defect (CLAUDE.md, *Defects and gaps*). An entry stays until a plan item decides it: a report change, a "Later" entry in the log, a question in the plan, or a line saying it was weighed and left alone. An entry keeps its number, which the plan, the log and the code cite; the next is 101.

91. **A listener opened in a top-level binding lives under `ern run` and dies under `:load`** (2026-10-07, the chat server under `proposals/nodes_and_code/experiments/code_update/`). §8.5 evaluates a module's bindings in the entry process, which lives through `main`, so a listener a binding opens serves the program; §11.2 evaluates them in a process of the shell's own, which ends with the load, so the same listener ends with its owner (Appendix E.18) before the first input, and the acceptor finds it ended. The report states both, and the program is better with the acceptor owning its listener; what feels against principle 3 is that one source behaves two ways and nothing says so at the `:load`. Weighed for: the shell's binding process living on as the entry process does, or the load reporting a resource its process will end.

94. **A table may not hold a function, for the runtime's sake** (2026-10-09, MVP 3.1's proposal, `proposals/nodes_and_code/mvp3.1.md`, section 6, *What a node lets go*). A unit of code is let go when no process runs it or holds a function of it, which the host's `check_process_code` sees; the host does not look into a table, so `Ets.Table(k, v)` is to be refused where `k` or `v` holds a function type, by §3.11's bound check's first case. The rule is visible, a type error, and sound; but it is a rule of the language made for the runtime's bookkeeping, and the program it costs is a dispatch table, handlers kept by key, which keeps its handlers in a process's state instead. A reader of G.1 meets the rule before its reason. Weighed against a scan of tables before a let-go, unsound, and a count per table at each `put`, a walk of every value on a path that today costs the host's insert alone (`code.md`, section 5). Stands until the item that builds the let-go decides it. Decided by the principles review of 2026-10-09 (S7, §0's principle 5): the refusal goes, and a unit a table's function holds is never let go, a limit the proposal states.

96. **An error type grown for one module grows every exhaustive `match` on it** (2026-10-09, the principles review's S24, `shell/shell.ern`, `examples/file_sync.ern`, `examples/web_server.ern`). `Io.Error` gained `NotListed`, `NotOffered`, `OtherType`, `NotLoaded` and `Unreachable` when `Peer.Failure` went into it, so that a block reading a file and finding a peer converts nothing; three programs that use no peer matched `Io.Error` whole and each gained five arms. One error type for every system module is the trade principle 2 and E.0 shape rule 8 made, and its cost is that a program that names every case names every module's; a program that wants only its own cases writes a last `_` arm, which loses the compiler's word on a constructor added later. Decided by the review; listed for the next time an error type is weighed.

97. **A previous version's values are made only by what was kept from before the reload** (2026-10-10, MVP 3.1's item 5, `test/ern_shell_tests.erl`'s `reload_keeps_the_type_checked_under`). After a `:reload` changes `Counter.Msg`, a binding of the previous version's type takes only a message of that version, whose constructors are `Counter$1.Inc`, a name no input writes, since `$` marks a name the session made (§11.2). So a message for the previous version's process is made by a function kept from before the reload, `let inc = Counter.Inc`, or one an input declared then; a user who kept none cannot make one, though the process runs and its constructors print. Two versions as two types is the rule (claim 3 of `mvp3.1.md`); what feels against principle 3 is a type whose values the session shows and cannot write. Weighed for: a previous version's constructors writable at the prompt alone. Stands as MVP 4.3's decision.

98. **`:processes` shows two versions' processes alike** (2026-10-10, MVP 3.1's item 5). A reload's service runs beside the previous version's, and both are listed by their spawn site, `Counter.service:5`, the spawner's words, which are the same in both versions; which version a process runs is invisible at the prompt, where the session tells the versions' types apart by `Counter$1`. Weighed for: `:processes` naming the version of the unit a process runs, which the host's report of its current function gives. Stands as MVP 4.3's decision.

99. **A constructor with a named field is no wrap** (2026-10-10, MVP 3.1's item 6, `proposals/nodes_and_code/mvp3.1.md`'s section 3). The proposal wrote `Terminating(reply : Reply(Unit))` and `Os.terminating(Terminating)`, which the checker refuses, `Terminating has named fields; write Terminating(reply = value)`, since a named constructor is no function value (§5.6); the example now declares `Terminating(Reply(Unit))`, positional. A message that carries a reply names it `reply` everywhere else, `Get(reply : Reply(Int))`, so a reader who writes the end's message as the rest of a protocol meets the refusal at the one place a constructor is passed as the function that wraps, `Os.terminating`, `Process.faults`, `monitor` and `via` alike, and writes `fn(reply) = Terminating(reply = reply)` or drops the field's name. What feels against principle 1 is that a constructor of one named field reads as a function of one argument and is not one. Weighed for: a constructor of one field, named or not, as a function of it. Stands as MVP 3.1's item 9's question, for its reader of the principles.

100. **The end's lines are said wherever a program has a subscriber** (2026-10-10, MVP 3.1's item 6). §8.6 has the runtime say on standard error that the end waits, for how many, and each subscriber's answer, for every program; `mvp3.1.md`'s section 6 had the node say it when termination arrives, for the operator who waits on a stop. A program run at a prompt that keeps its state through `Os.terminating` writes two lines on standard error at every end, of a wait its own subscriber made and answered at once, which §11.2's measure, what a program cannot learn and an operator must, does not ask for. Weighed for: the lines on a node alone, as the proposal had them. Stands as a decision of MVP 3.1's item 9, with the user.
