97. **A previous version's values are made only by what was kept from before the reload** (2026-10-10, MVP 3.1's item 5, `test/ern_shell_tests.erl`'s `reload_keeps_the_type_checked_under`). After a `:reload` changes `Counter.Msg`, a binding of the previous version's type takes only a message of that version, whose constructors are `Counter$1.Inc`, a name no input writes, since `$` marks a name the session made (§11.2). So a message for the previous version's process is made by a function kept from before the reload, `let inc = Counter.Inc`, or one an input declared then; a user who kept none cannot make one, though the process runs and its constructors print. Two versions as two types is the rule (claim 3 of `mvp3.1.md`); what feels against principle 3 is a type whose values the session shows and cannot write. Weighed for: a previous version's constructors writable at the prompt alone. Stands as MVP 4.3's decision.

98. **`:processes` shows two versions' processes alike** (2026-10-10, MVP 3.1's item 5). A reload's service runs beside the previous version's, and both are listed by their spawn site, `Counter.service:5`, the spawner's words, which are the same in both versions; which version a process runs is invisible at the prompt, where the session tells the versions' types apart by `Counter$1`. Weighed for: `:processes` naming the version of the unit a process runs, which the host's report of its current function gives. Half decided 2026-10-10 with MVP 3.1's read (W17): a reload's version's spawn sites carry the number, `Counter$2.service:5`, so the end's lines tell the versions apart; `:processes` naming the version in a column of its own stands as MVP 4.3's decision.

101. **One subscriber to the program's end keeps every deadlock from being found** (2026-10-10, a draft of `examples/typed_channels.ern` whose counter subscribed with `Os.terminating`; the example as kept has no subscriber). §8.6 counts a subscription to the end among what can still deliver a message, so a program with one living subscriber is never found deadlocked: its entry process, waiting for a message that cannot come, waits until a person sends termination, where the same program without the subscription faults with `Fault("deadlock")`. A scratch copy of the draft whose `main` waits at its end for a `Died` that never comes did both: it hung while its counter was subscribed through `Os.terminating`, and faulted at once without that line. The rule is stated and argued (the log's *MVP 3.1 Read*, E2: a program that waits for its termination message is no deadlock); what feels against principle 1 is that one process's subscription changes what the detector says of every other process, so that the draft's sentence on the deadlock needed a second sentence beside it.

102. **A reply a function took to `Peer.spawn` cannot be answered where the spawn fails** (2026-10-10, a draft of `examples/typed_channels.ern` whose `squareOn` handed a request's reply to a function spawned on a peer; the example as kept spawns nothing on a peer). The function a spawn on a peer starts is consumed by the spawn whatever it answers (§6.6), so where `Peer.spawn` answers `Left(NotListed)` or `Left(Unreachable)` at once, the reply its function captured is gone with it, and the caller learns of the failure only as `None` when its own time runs out, though the spawner knew at once. Against principle 3, a failure visible where it happens: the spawner holds the failure as a value and cannot hand it on. The way around it, a function that sends its result to the spawner, which answers, gives up the reply's crossing that §8.7 decided today; the draft kept the crossing and said in its comment that a failed spawn drops the reply.
