# Ernest Toolchain: Architecture Notes

How the toolchain's code is arranged: its stages, its modules and what each does, the runtime, and the kinds of tests. The code wins any conflict with this document. The language is the report's; the layout of the repository and the commands are [`development.md`](development.md)'s; the reasons are the [decisions log](decisions.md)'s; the roadmap is the [plan](implementation_plan.md)'s. The Erlang follows [`style.md`](style.md).

## The pipeline

One Ernest module goes through these stages, each an Erlang application under `erl/`:

| Stage | Modules | In | Out |
|---|---|---|---|
| lexer | `ern_lexer` | source text | tokens |
| parser | `ern_parser`; `ern_ast`, a node's span and the walks later stages share | tokens | AST, records of `ern_ast.hrl` |
| format | `ern_format` and its printer `ern_pretty` (§11.6), which `ern_docs` lays a type declaration out with (§11.4) | source, tokens with comments, AST | the text laid out |
| typer | `ern_typecheck`, with `ern_types`, `ern_prelude`, `ern_exhaust`, `ern_reply`, `ern_scope` (§5.4), `ern_bitspec` (§5.11), and `ern_interface`, the interface chunk | AST, dependency interfaces | typed AST, interface, environment |
| emitter | `ern_emitter`, with `ern_descriptor` (§8.4) and `ern_docs`, the `Docs` chunk | typed AST, environment | Erlang forms, then BEAM with the `ErnI` and `Docs` chunks |
| runtime | `ern_rt`, `ern_boundary`, `ern_show`, the system processes `ern_fs`, `ern_tty`, `ern_tcp` and `ern_os`, the standard library's shims, `ern_tty_signal`, the terminal's resize handler, and `ern_exec`, the one helper in C | | what compiled code calls |
| diagnostics | `ern_diagnostic`, in `utils`, beneath every stage | a `#diagnostic{}`, the source | the text of §11.5 |
| chunks | `ern_chunk`, in `utils`, which reads the term a compiled module's chunk holds: plain data and nothing else, its new names within the room the host has for names (§11.1), so that a crafted `.erc` is refused and never run or let to fill the host | a chunk's bytes | the term, or `error` |
| namespaces | `ern_namespace`, in `utils`, the one mapping between a path's components and a namespace's segments (§4.2, §11.1), which the build, the emitter's module names and the shell's `:load` share | a component or a segment | the other |
| cli | `ern_cli`; `ern_build`, the build every job reaches; `ern_shell`, the shell's front end; `ern_page`, §11.4's renderer; `ern_signals`, the handler of termination and hangup; `ern_out`, a job's standard output and standard error | command lines, shell inputs | `ern`'s jobs, a session |

The Makefiles pass `VERSION` to `erlc` as a macro, which `ern_cli` prints. The Emacs mode calls the toolchain only as `ern format -` ([`emacs_mode.md`](emacs_mode.md)).

`bin/ern` finds its tree, refuses a working directory whose name is not UTF-8, tells the host to write no crash dump (§10), and starts the host with `-noinput`, with `erl/*/ebin`, `build/stdlib` and `build/shell` on the code path, with `ern_signals:install/0` and then `ern_cli:start/0`; [`install.md`](install.md) lays out the installed tree. `start/0` installs `ern_signals` again, for a caller that is no launcher, and runs `ern_cli:ern/2`, a run writing to the node's own descriptors. Every job but the shell writes its own text through `ern_out`, ports on descriptors 1 and 2 in place of the host's `user`, which halts the host when a stream's reader has gone; `ern_out` ends `ern` with 141 then (§11). The shell keeps `user`, which is its terminal, and `ern_tty` asks `user` whether a stream is a terminal and what size it is, whatever device a job writes to. `ern` then ends with the job's status, with 70 after a failure of the toolchain itself, or by the signal that ended a run. `ern_signals` takes `SIGTERM` and `SIGHUP` from OTP's default handler: during a run it ends the run through `ern_rt:signal/1` (§8.6), and otherwise ends `ern` at once; `die/2` restores the signal's default action and sends it again (§11.2).

## Tokens and AST

`ern_lexer:tokenize/1` returns `{ok, [Token]}` or `{error, #diagnostic{}}`. A token is `{Category, Position, Value}` for a literal, an `ident`, a `typename` or a `doc` block, and `{Symbol, Position}` for an operator, a delimiter or a reserved word. `Position` is `{Line, Column, End, PreviousEnd}`, `PreviousEnd` being the end of the token before. `tokenize/2` with `comments` adds each comment as `{comment, Position, Text}`, for the formatter.

`ern_parser:parse/1` takes tokens; `parse_string/1`, `parse_expr/1`, `parse_type/1` and the shell's `parse_statement/1` are conveniences. The diagnostic of an unfinished input carries `expected`, which completion reads, and `within`, the innermost call and the argument's index, which `Shift-Tab` reads (§11.2).

Every node is a record of `erl/parser/include/ern_ast.hrl`, one per production of Appendix A, `span` first, which `ern_ast:span/1` reads. A `fn` declaration's requirement is a list of `#member{}`, and in its body the parser makes `a.compare` and `a.negate` of a type variable of the signature an `#e_member{}`, as `a.+` is wherever it stands (§4.9); the declaration binds no name that is one of its type variables, so the two readings never meet. Expressions and patterns end in a `type` field the checker fills. A name, `#e_var{}`, carries a `referent`, what §4.2's lookup resolved: `var`, `#own_declaration{}`, `#remote_declaration{}` or `{prelude, QualifiedName}`. The emitter reads it and never resolves a name again, as it reads the order of the top-level lets from `ern_typecheck:let_order/1` (§8.5). Declarations carry `doc` and `export`. The parser rewrites twice: parentheses make no node, and `x |> f(a)` is the call `f(x, a)` with its `pipe` flag set, so that `x` is evaluated before a callee that is not a name (§5.1). A clause's `or` alternatives are one `#p_or{}` (§5.9). `prune_docs` keeps a doc block only where §2.2 attaches it, and the module's is `#module_doc{}`, first in the list.

Expressions are parsed by one precedence-climbing loop, patterns by a second small one, and declarations by recursive descent. Nothing backtracks: where the first token does not decide, the parser reads the later token that Appendix A's last paragraph names.

## The type checker

`ern_typecheck:check(Namespace, Declarations, Interfaces)` returns `{ok, Typed, Interface, Env}` or `{error, [#diagnostic{}]}`, `Interfaces` being the `#interface{}` records of the modules referred to. `infer/2` gives an expression its type, and `ern_typecheck:check_expr/5` checks one against an expected type, pushing it through branches, clauses and blocks, which gives a diagnostic §11.5's labels.

Types are the terms of `erl/typer/include/ern_types.hrl`: `{tcon, QualifiedName, Args}`, `{tvar, Id}`, `{ttuple, Elements}` and `{tfn, Params, Effect, Result}`, `Effect` being `pure` or a type. Each variable has a `#type_variable{}` entry with its level, its restrictions (`equality`, `process_only`, `not_reply_carrying`, §3.9) and its annotation's name, in a `#type_state{}`. `ern_types` owns this state: unification with the effect rules, generalization by levels, instantiation, and the printer that diagnostics and `ern doc` share.

`ern_prelude` holds §9 as tables, each entry documented: the built-in types, the declared types as Ernest source, the values with their type text, and the process-only values. `ern_typecheck:prelude_env/0` builds the starting environment from them and from the standard library's interfaces, `ern_prelude:stdlib_interfaces/0`. `ern_prelude:docs/0` makes of the tables a `Docs` term, which `ern_page:prelude_page/0` renders for `ern doc` and `ern_page:prelude_declaration/1` for `:doc` and `Shift-Tab`.

A module is checked in this order:

1. `declare_types`: every type, its constructors with their fields in declared order (§3.5), reply-carrying computed (§6.6); `mark_abstract` marks an abstract type, whose constructor `lookup_constructor` refuses elsewhere (§4.4). Its third pass, `check_recursive_groups`, takes the cyclic strong components of the module's types over the names in their fields and refuses a group's type named at other than the declaring type's parameters (§3.9).
2. `check_values`: the value declarations in dependency groups, from a `digraph` of references by name (§4.2). `run_group` checks a group when the fold reaches it, or when `demand` asks for one of its names during another definition's inference (§4.8). `check_group` gives each member a monomorphic placeholder, unifies the annotations first, infers the bodies in order and generalizes. `alternatives_differ` and `alternatives_agree` check pattern alternatives (§5.9). After each group, `let_cycles` reports a cycle of top-level lets (§8.5).
3. `post_checks`, per definition: `<-` resolved to `Either` or `Optional` (§5.5); operators left open by `operator_result/4` (§4.8); what each requirement is supplied with, `supplied/2` (§4.9, below); rigid annotation variables (§3.9); the local-fn use order (§5.4); undetermined block bindings (§4.6); exhaustiveness by `ern_exhaust`, Maranget's algorithm with a witness (§5.9); that a top-level `let` holds no reply and the reply discipline by `ern_reply` (§6.6), which also gives each variable of the definition's type its not-reply-carrying restriction (§3.9); and the restrictions an instantiation carries, `check_pending_restrictions`. A lambda a block's `let` binds has no post check of its own, so `let_binding` asks `ern_reply:restrict/4` for its restrictions before it generalizes it.
4. `check_abstract` and `check_exports`: §4.2's and §4.4's visibility rules.
5. `interface_of`: the exported types and values.

**Requirements** (§4.9). A declaration's requirement rides on its `#scheme{}`, `[{Id, Member}]` over the scheme's variables, so that it travels with the name through the globals, a block's locals and a compiled interface, and `ern_types:format_scheme/2` prints it after the type wherever a declaration's type is printed; `ern_types:instance/2` instantiates it beside the type. `signature_shape` puts it on a definition's placeholder, so that a recursive use is supplied as a later one is, and `publish` and `release` carry it over generalization. The members in force, the enclosing declarations', are the environment's `requirement`, and an operator on a type variable among them resolves to its member. Each use of a declaration with a requirement leaves a `#pending_member{}` in its `#e_var{}`'s `supplies`, as an operator does in its node's `member`, `Io.show` does for its descriptor, and `Foreign.from` does for the type its value crosses at (§8.4), under a member of its own, `exposed`, which no requirement supplies; at the definition's end `supplied/2` replaces each by a `#known_member{}`, a known type's member with its own requirement supplied in turn, a `#required_member{}`, the enclosing requirement's, or a `#shown_type{}`, the records of `ern_types.hrl`, or reports the error §4.9 names. A local fn's are resolved at its own end, with its own requirement in force. `derived_members/2` makes each `derives compare` an ordinary `fn T.compare` declaration before the values are checked, with the requirement its fields' comparisons reach, read to a fixpoint over the module's derived types; and `filled/7` reads `Ops(..Set)` as the construction that names each field's declaration in the namespace (§5.6). A path in a record update, `Pool(..pool, stats.indexed = e)`, is `updated_through_paths/7`: the base and each value are bound once, in source order, to names no program spells, and the construction over them nests an update per first segment, whose constructor is the one of the type the field reaches (§5.6, §5.1); the typed tree holds the block, and the emitter sees only bindings and constructions.

A block's local `fn`s get placeholders from their annotations before any statement is checked, and one is generalized once every later local fn it references is checked (§5.4). An initializer is checked as a body of mailbox type `Never` (§4.6), and one that calls a process-only function, noted in `effectful_lets`, is not generalized. `builtin_operators/2` reads `fn Float.+` in a built-in type's module as that module's `+` (§4.8).

The environment is opaque outside the module. The compiler reads it through functions of its own, `type_state/1`, `resolve_type/2`, `lookup_type/2`, `lookup_constructor/4`, `node_type/1` and `foreign_implementation/1` among them; the shell also through `declared_scheme/3`, `fields/2` and others, and through `ern_ast:pattern_bindings/1` for the names a pattern binds.

## The compiler

`ern_emitter:forms(Namespace, Typed, Env)` builds Erlang forms with `erl_syntax` in one traversal, threading a record `#emit_context{}`: the namespace, the variable map, a counter, the local-fn table and the lifted functions. It has a clause for each record of the AST, and a value's representation is §8.4's ABI.

- Every binding is a fresh Erlang variable `Name_N`.
- A local `fn` is lifted to a module function `'name$N'`, whose leading parameters are the variables it closes over, its own and those of the local fns it references (§5.4). A call passes them; a use as a value is a closure.
- `let p <- e` is a `case` on `Left`/`Right` or `None`/`Some`, the rest of the block in its second clause.
- A selected field (§3.5) is `erlang:element/2` where every constructor holds it at one place, and a `case` on the tag otherwise.
- A clause with alternatives is one Erlang clause per alternative, each calling a fun that holds the body (`alternatives/3`). A guard that is not an Erlang guard falls through by a continuation.
- A top-level `let` is a getter over `persistent_term`, filled by `'$init'/0`. A module lists its dependencies in `'$deps'/0` and its tests in `'$tests'/0`.
- `spawn` passes its site as a third argument (§6.9).
- A requirement's members are parameters after the written ones, in the order it writes them (§4.9); `#emit_context{}`'s `members` holds each one's variable by its type variable and member. A call appends what the checker supplied, `supply_form/2`: a known type's member as a function value, its own members bound into a closure, the enclosing requirement's parameter, or `show`'s descriptor; a declaration with a requirement as a value is a closure that supplies them. A lifted local fn closes over the enclosing requirement's parameters its body uses (`enclosing_members/3`).
- A `Float` operation is inline (`float_operation/5`): it adds `0.0`, so that a negative zero is `0.0` (§3.1), and makes its own `badarith` §7.4's fault. A float segment's variable is `{zero, V}` in the variable map, read as `V + 0.0` (`variable_form/1`).
- A type's descriptor is a function `$type_N`. A function type's holds a maker (`built_descriptor/1`), with which `ern_boundary` wraps a function value.
- A module that exports a function exports `'$fun'/2`, and another module's function as a value is `M:'$fun'(f, N)`, not `fun M:f/N`, so that it keeps its version across a reload (§11.2).

`compile/5` runs `compile:forms` with the chunk `ErnI`: a format number, the canonical interface, and what §11.1's recompile rule compares, the hashes of the source, of each dependency's interface and of the standard library's, and the build of `ern`. `ern_interface` owns the chunk: `encode/2`, `read/1`, which refuses another format, and `hash/1`, which leaves variable names out. `ern_docs:build/4` builds the EEP 48 `Docs` chunk in the same compile, an entry per declaration §11.4 renders, with its signature, its doc block, and, in its metadata, parameter names, constructors and fields; its `BeamLanguage` is `ernest`. `erl_source/4` is `--emit-erl`.

A module's atom is its Erlang name, `ern@` and its path (report §11.1), and a type member keeps its prefix, `'Stack.push'/2`. `module_info` and `record_info`, which the host gives every module, compile as `'module_info$'` and `'record_info$'`; `ern_emitter:function_atom/1` is that mapping, and the runner and the shell call through it.

## The runtime

`ern_rt` is what compiled code calls for processes, and the runner. It keeps nine tables:

- `ern_processes`: `{Pid, Site, Timers, Foreign, SpawnOrder}` per process the runtime started or adopted, `Timers` and `Foreign` counting its timed receives and foreign calls, and `SpawnOrder` its place in the order of spawns, which `RestForOne` reads.
- `ern_calls`: `{Caller, Callee, Reply}` per pending call, keyed by the caller, which makes one call at a time; `Reply` is the alias of the caller's monitor of the callee, and the reply's.
- `ern_callees`: the same calls by callee, `{{Callee, Caller}, Reply}`, ordered, so that a restart reads its own callers.
- `ern_faults`: `{Subscriber, Address}` per subscription to faults.
- `ern_held`: `{{source, Holder}, Count}` for each holder of a source: a system process, a socket or a running program, the reaper for a watched process it did not start, a counted delivery process (`counted_link/2`), and `Tcp`'s connect and accept workers; and `{{opened, Pid}}` for each process a system module opened.
- `ern_deliveries`: `{{Recipient, Starter, Pid}}` for each delivery a process started, ordered, so that a restart of the recipient reads its own deliveries and its starter can end them.
- `ern_restarts`: `{Pid, Alias}` for each restart a process may be asked (§6.9).
- `ern_proxies`: `{{proxy, Key}, Proxy}` for each checking proxy of §8.4, and `{{behind, Proxy}, Pid, Address, Key}` for what it stands in front of.
- `ern_launch`: how the terminal is read, `{reading, Kind}`, and the process a deadlock faults, `{deadlock_victim, Pid}`.

Its parts:

- **An address** is a pid, `{via, F, Target}` (§6.5), or `{foreign, Pid, D, B}` for an address foreign code gave that names no process of the program (§8.4); `send` applies the functions in the sender, and a fault in one ends the target, and a message to a foreign address is exposed as a foreign function's argument is. `process_of/1` is the pid behind an address, and `held/3` how the boundary holds one foreign code gave. **`Reply`** is the call's monitor's alias, which the call's end deactivates, dropping a late answer; one foreign code gave back is `{foreign_reply, Reply, D, B}`, `D` its answer's descriptor.
- **A call** (§6.6) monitors the callee and writes its `ern_calls` row, so that it ends when the callee ends, by the monitor, or restarts, by a notice to each alias noted against it. Ernest answers `{Reply, answered, V}` and foreign code `{Reply, V}`, the form §8.4 gives it, and so does Ernest to a `{foreign_reply, Reply, D, B}`, its answer exposed; a program's call checks only the second form, against the reply's descriptor the compiler passes it (`call/4`, `call_forever/3`), and the runtime's own calls (`call/3`, `call_forever/2`) check nothing.
- **`restarting/2`** (§6.9) runs the function in a `try`, and on a fault within the limit begins a fresh run and runs it again; past the limit the fault goes on to `run/1`. `fresh_run/0` asks the reaper, the clock and the terminal to cancel what the process asked of them, its waits and fault subscription, its alarms, its keys, each ending the deliveries it started to the process (`cancelled/1`), then empties the mailbox, and then ends the pending calls. For a restart asked for (E.22), the outermost one keeps an alias made with `priority` in the `{restart, Pid}` row, to which `Supervisor`'s private shim `ask_restart/1` sends `'$ern_restart'`; every emitted `receive`, and every call's wait (`call/4`, `call_forever/3`, which `call/3` and `call_forever/2` reach), take it first and call `restart_now/0`. `start_cause/0`, another shim, answers `First`, `AfterFault` or `Asked`, and `spawn_order/1`, the third, a process's place in the order of spawns, which `RestForOne` reads.
- **A time** (§6.3) is a deadline on the monotonic clock (`deadline/1`); `remaining/1` caps a wait at the host's longest timer, and the wait is taken again in slices. The clock holds an alarm after milliseconds so, and an alarm at a time by the time itself, read against the host's clock (E.15): the host's timers count monotonic time, so the clock's process monitors the host's time offset and, at each change, sets every alarm at a time again (`set_again/1`).
- **The reaper** `spawn_monitor`s every process a program spawns, and monitors every listener, socket and running program a system module opens (`opened/2`), writing each one's row, and holds the monitors of them (§6.9), and those of a `monitor` of a process it did not start. Each `Down` is delivered by `wrapped/3`, in a counted process of its own. `spawnMonitored`'s monitor, and the runner's of the entry process, are made with the spawn.
- **The one proxy** is the foreign boundary's, one per address and mailbox type, living as long as the process behind it, so that a compiled `receive` never sees a foreign message.
- **A deadlock** (§8.6) is found by the reaper's look, which comes after 100 ms without a message, and again after 100 ms while nothing can deliver but a process still runs; while something can still deliver it comes once a second, since a deadlock can begin only once that has ended and a program at rest pays a wake-up of the host for each look (the log's *The Reaper's Look at Rest*). Where nothing can still deliver, by `ern_held`'s `{source, Holder}` rows, the calls in `ern_calls` on a system or an opened process, the system processes' status and mail, and the counts in `ern_processes`, it takes two snapshots of every live process's status and reductions; equal snapshots, all `waiting`, with nothing able to deliver between them, make the runner fault the entry process with `deadlock`. The check is off while the shell holds the terminal. A module loaded on its first call counts as a foreign call, since `ern_rt` is the `error_handler` of every process the runtime starts and loads inside `in_foreign/1`.
- **Sources** (§8.6) are counted, not asked about: the clock counts an alarm until it is delivered, `stdin` a request until its answer, the terminal its subscriptions, and the reaper a monitor on a process the runtime did not start, until its `Down` is delivered. A call to a system process, a listener, a socket or a running program counts from its `ern_calls` row, written before the request is sent. A timed `receive` and `Address.call` count themselves in and out, and a foreign call runs inside `in_foreign/1`, but for a standard library function without a mailbox type, which waits on no process. The compiler writes a foreign call in place, its exception turned into a fault by `ern_boundary:raised/6` and its return checked as its type needs: `any` not at all, `int`, `bool`, `bytes` and `float` in place, a value with no function, float, address or `Reply` in it by `check/3`, and any other, `char` and `string` among them, by `value/3`. The standard library's own return is not checked, and its own arguments are not exposed (§8.4).
- **Standard input** is a port on descriptor 0, opened per request and closed at its answer; the terminal reads keys through it, in `stty`'s raw mode. For a run, `run_main` sets standard output and standard error to `latin1`, so that they take bytes (§8.2).
- **Faults** are reported by the reaper (E.21), at a process's end with a fault and at a restart. `report/4` builds the `FaultReport`, gives it to the run's `faults` function, and delivers it to each subscriber in `ern_faults` in a counted process. `Process.info` reads `ern_processes`, the host's status and `ern_calls`.
- **`run/1`** wraps every process body, so that an exception is a fault: `badarith` is `Fault("division by zero")`, and a thrown `{ern, fault, Cause}` is `Fault(Cause)`.

### The runner

`run_main(EntryPoint, Site, Options)` makes the tables, starts the reaper and the system processes `stdout`, `stderr`, `stdin`, `fs`, `terminal`, `tcp`, `os` and `clock`, and binds each under `persistent_term`, where `ern_rt:system_process/1` reads it. In the entry process it runs the standard library's initializers, then `Opts`' `init`, then `Main` (§8.5); the runner's `init` is `ern_rt:init_modules/1` over the modules it loaded, the shell's own among them for `ern shell`, each set ordered by its `'$deps'/0`. It waits for the entry process, a deadlock, `Os.exit`, a stream gone, or a signal; ends every live process with `ProgramEnd` and flushes `stdout` and `stderr`, each answering whether its stream took what was pending; and returns `{gone, Stream}` where one did not (§8.6), and otherwise `ok`, `killed`, `{fault, Msg}`, `{fault, Msg, Trace}`, `{initializer_fault, Site, Msg}` for a top-level binding that faulted before `Main` ran (§8.5), `{exit, Status}`, `{gone, Stream}` or `{signal, Signal}`. A deadlock, and a fault a system process finds, are made the entry process's fault. A reference tags each launch, and the reaper's late notices of it are flushed.

The options are `faults`, the runtime's own subscriber; `stdout` and `stderr`, a function or `{fd, N}`, a port that learns when a write fails (§8.2); `stdin` and `keys`, a function answering each read, and `time`, the clock the `Clock` process reads, for tests; `init`; `arguments`; and `exit => fault`, for the shell and `ern test` (§11.2). A `Write` is answered once the function or the port has taken the bytes.

### The system processes

- `ern_fs`, `ern_tty` and `ern_tcp` are the processes behind `Fs`, `Terminal` and `Tcp`, speaking their modules' message types. A socket's and a listener's process traps exits, so that however it ends it closes its host socket itself; a socket with bytes the far end has not taken hands its host socket to a closer of its own, `lingering/4`, since the host's close would hold it open for as long as the far end takes nothing. `Fs.removeAll` is `ern_exec`'s second job, `remove`, which walks a tree by the directories it has opened, since Erlang's `file` has no operation relative to an open directory. `ern_tty_signal`, added to OTP's signal server at the first subscription, sends the terminal's process each `SIGWINCH`.
- `Tcp`'s reference answers `Listen` and `Connect`, and each socket is a process over its `gen_tcp` port speaking `Tcp.SocketMsg`, alive until `Tcp.close`. A waiting request carries its milliseconds, and the socket, the listener's worker or the connect's decides the timeout, so that a request that timed out took nothing. A waiting request is a source against its holder, and listeners and sockets are recorded as opened.
- `ern_os` (E.23) answers `Start` with the program's process, linked, opened, and a source until the program ends. That process owns a port of `ern_exec` (`erl/runtime/c_src/ern_exec.c`), which runs the program in a process group of its own, speaks frames of a length and a tag for the input, the output, standard error, the acknowledgements and the exit status, and kills the group when the port closes. The program's process speaks `Os.ProgramMsg` and holds the time limit; `Os.run` is Ernest over it. Run with no program, the helper writes back the user it runs as and its environment, which `ern_os:host/0` reads once as the program starts, for `Os.user` and `Os.environment`. The environment is the one `ern` was started in (E.23): the launcher keeps what it and the host's start change ([`install.md`](install.md), *The launcher*), and the helper puts each back before it answers or runs a program. A program it runs starts with every signal at the host's default, since an ignored signal stays ignored in a program started.

### The standard library

Appendix E is one Erlang module per namespace, `ern@list` and so on, compiled by `make` from `stdlib/` into `build/stdlib`; the standard library is every `ern@` module in a `stdlib` directory on the code path. `ern build` lets its source root take prelude namespaces (`is_stdlib_root/1`, §4.2). `ern_prelude` holds §9 alone: a module declares its own types, and a prelude operation in a type's namespace, `Int.compare`, is in that type's module. Every contract is Appendix E's. `erl/runtime/test/ern_stdlib_tests.erl` calls each module by the ABI. `prelude_targets_test`, in `erl/emitter/test/ern_emitter_tests.erl`, holds every name of `ern_prelude:values/0` exported by its module with its type's arity, and `stdlib_targets_test`, in `erl/runtime/test/ern_doc_tests.erl`, does the same for the standard library.

- **The shims.** A shimmed module's Erlang helper is named `ern_` and the module's name. `ern_char` reads E.6's predicates above ASCII from the host's `unicode_util` tables, the ones `string` follows (the log's *Char Reads the Host's Tables*). `ern_map`, `ern_set`, `ern_string` and `ern_path` hold the primitives their sections name, and `ern_list` the one `List.zip` is, and `primitives_test` holds each module's `foreign fn`s equal to them. `ern_float:text/1` writes a `Float` for `Float.toString` and `ern_show`. A `Set` is `{set, S}`, `S` a version 2 `sets:set`, so that it is not a `Map`.
- **Printing.** `ern_io:show/2` and `ern_io:debug/2` write through `ern_show`, which reads a value by the descriptor the compiler passes for its type, `ern_boundary`'s with field names and abstract types added; the `any` descriptor falls back to §8.4's representation (E.1). The shell prints through `ern_show` with a depth and a length.
- **The bit syntax's checks**, those of §5.11 and §7.4 that the host's bit syntax does not make, are `ern_bits`, which the compiled bitstring code calls.
- **The foreign boundary** is `ern_boundary` (§8.4). `expose/2,3` replaces each address in a foreign function's argument, a message to a foreign address, or an answer to a `Reply` foreign code gave, with a proxy that checks each message foreign code sends it, and in place of one that fails sends the receiver `{'$ern_fault', Cause}`, which every wait the emitter writes, and `ern_rt`'s waits for an answer, take before any other clause but the restart. The compiler writes the call in place; `raised/6` turns its exception into a fault, and `check/3` or `value/3` checks its return. `value/3` also checks a reply foreign code gave and wraps each function value so that its result is checked at every call. `zeroed/2` makes a negative zero from outside `0.0`.

## The tools

`ern_cli:ern/2` takes the job from the first word, each job's options a getopt spec of its own; `no_job/1` and `old_option/2` refuse an old spelling with the new one. `ern_build` holds the build and what every other job takes from it, a module's source and namespace, an interface, a file written whole, and it alone of the jobs is in the compiler's hash (`compiler_modules/0`, §11.1), so that a change to another job recompiles nothing. `write_whole/2` and `write_whole/3` write every file a job writes: to a dot-name beside it, the writer's own, made there or not at all, so that a name another planted is never written through, its mode set before its data, then renamed into its place, a link followed. `write_output/2` and `write_output/3` write so in the place itself, a link replaced: a build's outputs, and the configuration directory's files, which `ern config` writes into a directory it made, closed, and found empty. `ern run`, `ern test` and `ern shell` also install `ern_signals`, for a test that calls the job, and lower the host's logger to warnings.

- **`ern build`**, in file or directory mode: modules from paths (§11.1, §4.2), with `namespace_clash` refusing a module namespace that is a type namespace of its parent; dependencies from a parse-only scan of qualified names; a `digraph` for order and cycles. Per module, the dependencies' interfaces from the build directory, §11.1's recompile rule over the `ErnI` hashes and `stdlib_hash/1`, then check, compile, and write. Directory mode sweeps stale `.erc` files.
- **`ern run`** reads the `.erc`, derives the root from its namespace's depth, puts the root and the `--load-path` roots on the code path, loads the dependencies by namespace, and calls `run_main`. `reporting/2` gives the run `report_fault/2` as `faults`, writing through standard error's process, and, from the launcher, `{fd, 1}`, `{fd, 2}` and the stamp §11.2 describes; a test calling `ern_cli:ern/2` gets standard error on its own device. `outcome/2` gives §11.2's status.
- **`ern shell`** loads a file and names its entry point, which the shell spawns beside it, or none (`shell_entry/4`); see *The shell* below.
- **`ern test`** is `run_tests/4`: it calls the module's `'$tests'/0` and runs each test in a monitored process of its own. The running test is recorded before it starts, in a table of `run_tests/4`'s own, so that its fault is its line and not a report, and `ern_rt:deadlock_victim/1` names it to the reaper (§11.2).
- **`ern format`** is `ern_format:format/1`: it lexes with the comments, parses, walks the tree into a template of the layout, a function per production, and walks the template in source order with a cursor over the tokens, placing each comment beside its token; `ern_pretty` prints it in 100 columns. `ern_format:markdown/1` lays out a CommonMark text's Ernest blocks.
- **`ern doc`** renders a page with `ern_page:page/1` from the two chunks, compiling a source in memory first; `doc_dir/2` writes a directory's pages and index. With `--man`, `ern_page:manual/1` renders it through the `roff` of `libs/markdown`, which `make` copies into `build/shell` with `libs/ansi`, which it uses. `ern(1)` is `tools/manual.ern`'s, which `make man` runs to render §11 of the report.
- **`ern config`** writes Appendix C's file and an Ed25519 key pair (§11.3).

### The shell

The shell is an Ernest program over `Terminal`: `shell/shell.ern` and its six modules under `shell/shell/`, compiled by `make` into `build/shell` with `libs/markdown` and `libs/ansi` beside it. [`shell/README.md`](../shell/README.md) guides a reader through the code, and [`shell_design.md`](shell_design.md) holds the design. `ern_cli:shell/3` starts it.

`ern_shell` is the front end the shell reaches through `foreign fn`. It holds the session and checks an input with `ern_typecheck:check/4`, the session being a scope of its own. A `let` with a pattern is checked as the block `{ let p = e; #(names) }`, and its names are held by a module with a getter each. `Shift-Tab` is `documentation/1`, a name's page, or `signature/1`, a call's signature printed by `ern_types:format_call/4` in three parts, the argument at the cursor the middle one. `:doc` is `ern_page`'s `declaration/2`, `session_declaration/3` or `module_head/1`.

## Tests

`make test` runs every kind below; the targets are [`development.md`](development.md)'s.

- **Unit tests**: EUnit under `erl/*/test`, one function per behaviour, each citing what it tests; `make sections` lists the report sections none cites. The emitter's tests run a program as the runner does with `ern_emitter_tests:run/3`, which `ern_supervisor_tests`, `ern_restart_tests`, `ern_reaper_tests` and `ern_system_module_tests` share, the tests of a supervisor's group, a restarting function, the reaper and the system modules.
- **Golden files**: `test/golden` holds the Erlang emitted for the programs of `test/programs`, `hello` and `services` (`golden_names/0` in `erl/emitter/test/ern_emitter_tests.erl`), compared as text. The hand-written modules of `test/target`, for `hello` and `counter`, are the two expectations the emitter did not write.
- **Programs**: `test/ern_integration_tests.erl` builds and runs the programs of `test/programs`, and the examples `hello`, `services`, `word_count` and `shout`, comparing their output with `test/expected` as a multiset of lines. `repl`, `file_sync`, `web_server` and `tally` run under tests of their own; `test/programs/echo.ern`, a measurement, is only compiled, `snake` is run without a terminal for its refusal, and `test/ern_terminal_tests.erl` plays `snake`. The file also tests the signals, the streams, `Os`, the manual pages against §11 (`manual_pages_test_`), the installation and the release archive (`installation_test_`), each library's `Test` values (`libs_test_`), and the three programs under `docs/operations/` against `test/expected/operations/` (`operations_test_`).
- **The corpus**: `ast_coverage_test` holds that the examples, the programs of `test/programs`, the standard library and the libraries use every AST record, and the checker's tests type-check every example and every such program.
- **Generated programs**: `test/ern_grammar_programs_tests.erl` derives programs from Appendix A, read by `test/ern_grammar.erl`, and holds the parser and the formatter to them and their near misses; `test/ern_typed_programs_tests.erl` generates well-typed programs and changes that the checker must refuse, the reply discipline's among them; and `erl/runtime/test/ern_laws_tests.erl` holds the standard library's functions to their laws on drawn cases ([`soundness.md`](soundness.md) names the three).
- **Documentation**: the CLI's tests hold `docs/module_doc_template.md` equal to `ern doc`'s page for `test/programs/template.ern`. `erl/runtime/test/ern_doc_tests.erl` checks the documentation of the template, `stdlib/` and `libs/`: its examples, which type-check and, ending in `// => v`, print `v`; its `since` lines against `VERSION`; that every export is documented and every exported function but an operator called by an example; and its `See also`.
- **Style**: `test/ern_style_tests.erl` checks `docs/style.md`'s line limit, tabs, module names and blocks of more than one statement, `ern format`'s layout over every module and every Ernest block of the report and the guide, and the Emacs mode's word lists and operator table against the lexer and the parser. It and the citations' tests read the repository's files through `test/ern_repository.erl`, which leaves an editor's files out.
- **Citations**: `test/ern_docs_tests.erl` (`make xref`) resolves every section citation of the live documents, the examples and the modules, holds the report's and the guide's contents lists equal to their headings, and checks the backticked paths of the documents that say where things are, the README's list of what Ernest adds against the guide's (`what_ernest_adds_test`), `THIRD_PARTY_LICENSES` (`third_party_test`), and the fault causes against §7.4 (`fault_causes_test`).
- **The guide and the report**: `test/ern_guide_tests.erl` compiles every `ernest` block, runs every program a console shows, checks every `ernest-rejected` block's error, and replays every shell session, by the marks its header describes, in the guide, the report and the README (`readme_examples_test_`). It checks `test/diagnostics.md`, the front end's errors, the same way. An example and a rejected example are built in the test's node through `ern_cli:ern/2`; a session and a program given input each run in a node of their own; the groups run in parallel.
- **The shell**: `test/ern_shell_tests.erl` runs sessions in line mode and drives the shell under the pseudo-terminal harness. `test/ern_terminal_tests.erl` drives §8.2's keys and the terminal's restoration. Both call the harness through `test/ern_pty.erl`, and make what they need under one directory per run, which `make test-shell` removes.
- **The Emacs mode**: `make test-emacs` runs the tests under `emacs/test/` ([`emacs_mode.md`](emacs_mode.md)).

Outside `make test`, `make load` runs [`memory.md`](memory.md)'s loads: `test/ern_load.erl` runs each program under `test/load/`, and the shell under a session it writes, through `ern_cli:ern/1` in a node of its own.
