## A Node's Schedulers, 2026-11-04

ernest-httpd's line 24, Ernest's 231. The server is a VM that reports 32 possible processors and 2 online. The host makes a scheduler, and a dirty CPU scheduler, for each processor the machine could have, bringing online those it has, so each node there held about 80 threads and 47 MiB, where 2 of each take 20 threads and 35 MiB. The visitor's container of two nodes then needed about 167 threads and peaked at 145 MiB, past its `--pids-limit 128` and `--memory 128m`, and the host failed to make its threads. *A Node's Limits* measured 37 MB a node on a machine whose possible and online counts agree, which hid it.

A node now sizes both by the processors online, through the flags `ern_carrier:boot_flags` already makes for `limits`. Putting the schedulers under `limits` was weighed and refused: its right value is always what the machine has, so a setting would only be a way to get it wrong (principle 5), and a node sized to the processors it can use is what a reader expects (principle 1). The cost is that a processor brought online later is used after a restart, which §12.5 is to say. Built in MVP 4.15's item 1, the runtime at the host's limits.

The container's caps and CPU share wait on ernest-httpd measuring again after the fix. Its times from start to the example's answer were 8.9 s at half a core, 4.3 s at one and 3.4 s uncapped, and part of them is likely the threads made and woken that the fix removes.

**Built, 2026-11-04.** The plan put the sizing in a node's flags, where it was found, but every host the launcher starts makes the same threads, a plain `ern run` and the shell's own among them, so the launcher sizes them all: `+S n:n` and `+SDcpu n:n`, `n` being `nproc`'s count of the processors the process may run on, online and within its CPU set, or `getconf`'s where there is no `nproc`. That is one fork of a small program a run, against a second start of the host, which computing it in Erlang for a plain run would have cost. §12 says it once for the runtime. A test runs a program under `taskset` on one processor and counts its host's scheduler threads by their names in `/proc`; on this machine of eight processors it counted eight of each before.

## An `or` Stands Between Patterns, 2026-11-04

Feedback 232, felt as the site's generator was written. `#(Paste or Load, _) ->` is refused as a tuple of one, `a tuple has two components or more`, with the help to write the component itself or add another, since the parser reads `Paste` as the tuple's one component and stops at `or`. The message names a problem the code does not have, which is a defect of the diagnostic (principle 1).

The language stays as it is. An or-pattern stands at a clause's level by principle 2's rule on a second spelling, since two clauses would otherwise repeat one body (*When a Second Spelling Enters*). An `or` inside a pattern says nothing a clause's own does not: `#(Paste or Load, _)` is `#(Paste, _) or #(Load, _)`, so nesting would be a second spelling of the same clause, which principle 2 refuses. Erlang has no or-pattern; OCaml and Rust nest theirs, and their readers would try it. So §5 is to say in one sentence that an `or` stands between a clause's whole patterns and nowhere inside one, beside "Patterns nest to any depth", which a reader could take to include it. The parser then names the `or`, and its help writes the alternatives out whole. Planned as MVP 4.15's item 17.
