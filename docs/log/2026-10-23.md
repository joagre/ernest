## What the Outline Asked, 2026-10-23

Decided with the user on 2026-10-23: the six entries the tour's outline left in `docs/language_feedback.md`, 140 to 145, each weighed. Two become the items of MVP 3.296, built before a chapter of the tour is written, and four are dropped with their verdicts here. The outline stays under discussion in `docs/proposals/tour/`, and nothing of it is decided by this entry.

**A binding has no value on a bare node (140), dropped.** §8.7 says a spawned function runs on a peer only where every binding its reach names has its value there, and that nothing is initialized because a peer asked. The entry asked whether the exchange should evaluate an arriving module's bindings, as `Code.load` evaluates a loaded one's. The two are not alike. `Code.load` is called by the node's own program, which decided to run that code. A code frame arrives because a peer asked, and a binding may offer a service to every peer of the node or open a resource, which the types do not tell from a value. Evaluating on arrival would make a bare node offer and hold what no program of its own started, visible to third nodes through `Peer.find`.

Three narrower rules were weighed and not taken. Evaluating only a binding whose reach is pure needs a purity walk the language does not have, a second mechanism beside the ground term. Widening the ground term to a name of a ground binding does not reach the entry's case, since `Map.empty` is a foreign call, `emptyMap()`. Starting a binding that spawns only where the node's `ernest.conf` names it needs the toolchain to know which bindings are services, which the type does not say, a name for each that a configuration can write, which a binding has not, and it moves which of a module's bindings run out of the program into the operator's file.

Principles 3 and 5 decided. The rule costs a writer a pair of parentheses per non-ground value a spawned function reads from its own module, or a parameter passed into the loop at its start, and both readers the tour is written for live by it already: Erlang has no module-level value, and Gleam's `const` admits literals, constructors of them, tuples and lists, which is §11.1's ground term almost to the word. What remains is principle 1's surprise, that the standard library's `Map.empty` is a `let` that works on every node where a program's `Tally.empty` cannot, since every node holds the library at its start. That is said where the writer reads, the guide's §8.1, as part of MVP 3.296's item 1.

**The `Right` at the prompt (141), dropped.** The `match` with its `fault` clause is the honest line, and a form that only shortens it, Gleam's `let assert` the one weighed, is the second way principle 5 refuses. The tour writes the line at its spawn and at its compute, and wraps every later take in a function of the program.

**Two nodes on one machine by hand (142), MVP 3.296's item 2.** Of what two `ernest.conf` need, the port and the `services` line are typable JSON, and the key is not: a three-line PEM folded into one JSON string with `\n`, copied between terminals, is the one step a reader gets wrong and cannot see wrong until the handshake refuses. `ern config` already writes the file, and a peer's directory on the same machine holds the peer's certificate and its `listen`, which is everything the peer's entry needs. So `ern config` gains `--listen host:port` and `--peer dir`, and writes the entry a hand writes worst from what it already reads, with no new job and no new file. The `services` line stays a hand edit, so a reader sees the file once. Principle 1 decided, for the operator's day; principle 5 holds, since the file stays the one description of a node and the tool writes it as it did.

**`restarting` after an `Upgrade` (143), MVP 3.296's item 1.** A process under `restarting` that moved itself to new code by its own send runs the function `restarting` was given at its next fault, the old code, and §6.9 did not say so. The runtime could do better only by tracking which loop a process runs, a mechanism beside the one rule, so the report states the rule, and the deployment guide says beside its §5.3 that a service under `restarting` takes new code by the reload of its binding, which §11.2 already says starts a service of the new version. No program in the repository had met it. Principle 3 decided.

**Where a compute ran (144), dropped.** *What the Feedback Left* decided on 2026-10-20 that a node has no name for itself and `compute` means anywhere. The tour is the first program that wants to show the pick rather than use it, and shows it where it is visible, the line the function prints on the peer's own terminal. Recorded as evidence beside that decision, which stands.

**A `Foreign.atom` beside a declaration (145), dropped.** A foreign declaration names a host function and fixes no argument (§4.7), so a host question with an argument costs its atom, one line, and a declaration that fixed one would be a second form. The tour keeps `schedulers`, since its chapter's point is the check on the host's answer, and a count of schedulers is the host question a tour about processes asks. Principle 5 decided.

## The Hash's Parents, 2026-10-23

Moved from `faq.md`'s answer on Unison on 2026-10-23, as history a FAQ's reader in a hurry does not need; the answer keeps what Ernest took and left.

The idea of a function known on its own, apart from any module, has an older parent on this runtime. Joe Armstrong asked the Erlang list in May 2011 [why modules are needed at all](https://erlang.org/pipermail/erlang-questions/2011-May/058768.html): "all functions have unique distinct names", and "all functions go into a global (searchable) Key-value database".

At the Erlang User Conference in 2012, in *A Few Improvements to Erlang*, he said "I don't like modules. It's a sort of love/hate relationship. The problem with modules is the classification problem", and "If you look at something like git, the way you deal with time is checksum, timestamp".

Unison names Erlang among its influences, and stands on parents of its own: a thing known by the hash of its content is Git's and Nix's, and its abilities are Frank's, Eff's and Koka's, from the last of which Ernest takes one rule, that a function that receives nothing stands wherever one receiving `M` is expected (the guide's §3.5).
