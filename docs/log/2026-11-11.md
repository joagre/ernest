# The decisions log, 2026-11-11

## One Copy of the Pages, 2026-11-11

Decided with the user on 2026-11-11, MVP 4.16's item 13: the library's pages as CommonMark are `make doc`'s alone, written under `build/`, the one copy a checkout holds. `docs/man/` is gone, and `make man` with it. *The Pages Written From `main`* had `make man` write `docs/man/` from `main` and a release commit it. Between releases the tracked copy was what the last `make man` wrote, stale against the doc blocks with nothing to say so, and a reader of the checkout met it beside the sources it was written from and could not tell which to trust (principle 1). One copy, written from the sources by the build, is the one way to have the pages (principle 2), and principle 2 decided. ernest-template made the same change the day before, from the finding in ernest-httpd (its log's *One copy of the pages*).

Two other shapes were weighed. A test holding `docs/man/` equal to the sources would keep it current, but every change to a doc block would carry its page in the same commit, the same text twice in every diff. A rule sending a session to the source instead of `docs/man/` would leave the stale copy where a reader finds it, a workaround in prose. A reader on the web browses the pages at ernest-lang.org/man/, and an installation has them as manual pages. The release archive already carried them as man3 files written by its own `ern`, so it does not change.

`make doc` writes every page: the standard library's under `build/stdlib/`, each library's under `build/libs/<name>/`, and two indexes beside `ern(1)`, `build/man/README.md` and `build/man/libs/README.md`, which link the pages where `ern doc` wrote them. `make site` runs it in the tag's export, and the site's generator reads the build's pages (docs/design/site.md). `make` does not write them; `make test-docs` and `make test-site` run `make doc` first, about 2 s where nothing changed, the hosts' starts. `make version` no longer writes the pages: the next `make doc` does, since a page is older than the toolchain built anew (§11.4). The prelude's page names no source in its footer, as a contents page does, since its source is no file. A tag before this one still builds its site, since its generator reads its own tracked `docs/man/`.

**ernest-httpd's 29, feedback 250, a decision for the user, item 18.** G.11 said `parseRequest` admits the visible ASCII characters "RFC 3986 writes a target in", which was false, since RFC 3986 writes none of `"`, `<`, `>`, `\`, `^`, `` ` ``, `{`, `|` and `}`, and `[` and `]` only in an IP literal; the clause is fixed. The probe ran here: `parseRequest` reads `GET /?a[]=1 HTTP/1.1` and eight more such targets, and `target` answers `None` for each, since `Uri.parse` is RFC 3986's. Chromium sends the nine raw in a query and the brackets raw in a path, as the WHATWG URL standard has a browser encode a query, so a server over `Http` answers 400 to a link a browser follows (principle 1).

The recommendation: `Http.target` reads such a target with each such character percent-encoded, the brackets left alone in an absolute form's authority, so that `Uri.decode` gives the character back and `Request.target` stays the text as written. `Uri` stays RFC 3986's exactly, since a published specification is a library's whole work. Against it: `Uri.parse` admitting the nine, which would make `Uri` neither RFC 3986's nor the WHATWG's, whose parser itself encodes some of them and not others; and leaving the 400, which Go's, Python's and nginx's readers do not, so that a reader who knows servers predicts the parse. Where a reader predicts the component as the browser wrote it, `{x}` and not `%7Bx%7D`, the decode gives it, and the rule says so.

**250 decided and built, 2026-11-11.** Decided with the user as the build began, on a sentence of the RFC the recommendation had missed. RFC 9112 §3.2 has a recipient of an invalid request line answer a 400 or a 301 "with the request-target properly encoded", and goes on: "A recipient SHOULD NOT attempt to autocorrect and then process the request without a redirect, since the invalid request-line might be deliberately crafted to bypass security filters along the request chain." The recommendation had named the 301 as its ground. What it builds is the autocorrection the sentence advises against, so it is taken as a departure, which G.11 states as a rule. It is the first of RFC 9112's rules for a server that `libs/http` does not take; a folded header in a request, for one, is refused as the RFC allows.

The bypass the sentence guards against needs a reader in the chain to see other components than the server does. None of the eleven parts a path's segments, its query or a fragment, so encoding them moves no boundary, and `Uri.decode` gives each character back: the server's program reads what a lenient filter reads. Cowboy reads them raw, its reader of a request line parting a target at a space, `?` and `#` and taking every other byte as written, and principle 1's reader knows servers as Erlang has them. The RFC's 301 would leave every server over `Http` a branch to write, and a browser following a 301 may turn a POST into a GET (RFC 9110 §15.4.2), so a `fetch` to `/api?q={x}` would lose its body. Keeping the 400 refuses the link a browser follows. Principle 1 decided.

Two smaller decisions came with it. The encoding reaches the path and the query alone, the whole of an origin form and what follows an absolute form's scheme and authority, and every authority is read as written: `CONNECT [::1]:443` keeps its literal's brackets, which "outside an absolute form's authority" had left unsaid, and a host holding a `{` is refused. A `%` before no two hexadecimal digits is read as `%25`, since a browser sends `/100%` raw as well, and such a `%` begins no encoding, so one before two digits keeps its meaning.

The walk takes each character once and conses it, three for an encoded one, and `String.fromList` makes the text at the end. Measured on nike, `target` costs 1.2 µs on a target of 16 characters where `Uri.parse` alone costs 0.8 µs, about 25 ns a character, and `parseRequest` reads a browser's head of nine lines in 6 µs, so the plain walk stays. A first form that wrote the text with `Char.toString` and `<>` a character at a time cost twice that. The tests, written with the code, hold the eleven in a path and a query, the three targets the feedback named and their decoding, an IP literal in an absolute form and in `CONNECT`'s, an absolute form with no authority, and the `%` cases; they do not cover a target a program builds with a character outside ASCII, which `parseRequest` never reads.

**ernest-epx's `++`, feedback 251, taken, item 19.** `Io.println("a" ++ "b")` is refused at the second `+`, which the message says no expression stands at, with no help. §11.5 already gives `<-` where a delimiter is expected a help naming `a < -1`; `++` is Erlang's and Haskell's concatenation, the languages principle 1's reader comes from, Ernest took `<>` for it on 2026-09-15, and no expression of Ernest begins with `+`, so the second `+` means one thing.
