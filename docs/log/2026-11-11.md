## One Copy of the Pages, 2026-11-11

Decided with the user on 2026-11-11, MVP 4.16's item 13: the library's pages as CommonMark are `make doc`'s alone, written under `build/`, the one copy a checkout holds. `docs/man/` is gone, and `make man` with it. *The Pages Written From `main`* had `make man` write `docs/man/` from `main` and a release commit it. Between releases the tracked copy was what the last `make man` wrote, stale against the doc blocks with nothing to say so, and a reader of the checkout met it beside the sources it was written from and could not tell which to trust (principle 1). One copy, written from the sources by the build, is the one way to have the pages (principle 2), and principle 2 decided. ernest-template made the same change the day before, from the finding in ernest-httpd (its log's *One copy of the pages*).

Two other shapes were weighed. A test holding `docs/man/` equal to the sources would keep it current, but every change to a doc block would carry its page in the same commit, the same text twice in every diff. A rule sending a session to the source instead of `docs/man/` would leave the stale copy where a reader finds it, a workaround in prose. A reader on the web browses the pages at ernest-lang.org/man/, and an installation has them as manual pages. The release archive already carried them as man3 files written by its own `ern`, so it does not change.

`make doc` writes every page: the standard library's under `build/stdlib/`, each library's under `build/libs/<name>/`, and two indexes beside `ern(1)`, `build/man/README.md` and `build/man/libs/README.md`, which link the pages where `ern doc` wrote them. `make site` runs it in the tag's export, and the site's generator reads the build's pages (docs/design/site.md). `make` does not write them; `make test-docs` and `make test-site` run `make doc` first, about 2 s where nothing changed, the hosts' starts. `make version` no longer writes the pages: the next `make doc` does, since a page is older than the toolchain built anew (§11.4). The prelude's page names no source in its footer, as a contents page does, since its source is no file. A tag before this one still builds its site, since its generator reads its own tracked `docs/man/`.

## A Deadlock of the Whole Program, 2026-11-11

MVP 4.16's item 1, the documents of the deadlock proposal's Part 2 (`docs/proposals/deadlock/`), whose nine questions were answered with the user on 2026-11-09 (*MVP 4.16, the Proposals Before the Launch*). This entry argues the proposal whole. Items 2 and 3 build its Parts 4 and 3.

**What the check is.** §8.6 finds quiescence, not a cycle: every live process waits in a `receive` without `after` or in `callForever`, nothing is in flight, and nothing the runtime counts can deliver. A computing process is not waiting, so a long computation is no false alarm. Everyone in `callForever` is always a deadlock and always holds a cycle, since each waits on one live callee. A cycle is still neither necessary nor sufficient. Why's first program has no call, `main` waiting for `Done` and the worker for `Go`: the communication deadlock of Chandy, Misra and Haas. And a reply handed on (§6.6) ends a cycle of calls. A calls B, B gives A's reply to C and calls A, C answers A, and A answers B.

**Types play no part.** The look reads no type, and Go's runtime makes the same check over its goroutines. Types answer what may arrive, and a deadlock asks whether anything will. Who holds which address does not matter either, since everyone is asleep. Ruling a deadlock out statically takes session types and a restricted topology, a third concept against §0's two (principle 5). So the typed mailbox leaves the argument for why the check is decidable, in *The Sitting on §8.6's Bookkeeping* and in Why.

**What it promises.** When the fault comes, nothing could ever have delivered again, but in §8.6's one case: a delivery foreign code arranges once its call has returned, by a host timer or a host process no monitor watches. It does not promise a stuck part of a program, two workers in a cycle while a listener is open or a timer pending. Nor does it promise anything on a node, or a livelock. It serves tests, scripts and learners, and barely a server.

**The claim given its scope.** "A deadlock is found" reads as any deadlock. It becomes "A deadlock of the whole program is found", and its first sentence names a program that is no node, since the homepage sets it beside the distribution built for a WAN and a node never looks. Principle 1 decided the scope. The word stays, since the fault, Appendix F, the guide and the tour use it, and a second name for one concept is a second way (principle 2). The rewording moves Why's anchor. The site is not live, and its check catches every link inside.

**It stays among the four.** *What Ernest Adds Stays at Four* refused the claim on principle 1, on two legs. A reader told of deadlock detection expects any deadlock, which the scope answers. And the claim held only in a program that has stopped waiting on the world. That is true of a deployed server, but every program has tests, and under `ern test` a case that waits for a message nobody sends faults while the run goes on; the tour's chapter 5 shows it. That entry's way to change the verdict, a fault from the calls in flight, is unsound, since a reply handed on makes a cycle that ends.

**The limit is the guide's.** Why and guide §5.4 say that a process stuck while another can still run or deliver is not found. §8.6 does not. Principle 1 has the report state a departure from what a reader who knows Erlang predicts, and for a stuck part that reader predicts a wait, which Ernest gives. The limit is the contrapositive of §8.6's "every live process", and §6.6 states it where a cycle is written.

`Fault("deadlock")` keeps its name, on Appendix F's term, whose scope is the whole program. A cause that stated the fact, "every process waits", would be true in the false alarm and of an idle server too.

**The status premise.** The two reads prove that nothing is in flight only if a process with a message on its way never reads as `waiting`. In OTP 29.1.2 a local send marks its receiver active in the sender's own call (`erts_proc_notify_new_sig`), and its status then reads `runnable` (`erts_process_state2status`). Erlang's documentation does not promise it, and no program shows it, so `docs/design/runtime.md` names it as what the look rests on.

**A stuck part gets a report, never a fault.** An operator who sees `calling` predicts being able to ask on whom (principle 1), and a report that called a legal cycle a deadlock would surprise, so it states facts. `Process.Calling` gains its callee, whether a limit ends the wait and when the call began, and `Process.peer` names a process's peer. `:processes` writes them, with a line for each cycle of calls without limit whose calls all began before the listing did (item 3). A deadlock's lines name each group's callee (item 2). The runtime never tells unasked: a time for it could only be chosen, and `callForever` says none applies.

**Weighed and not taken.** A name without the word, "A program that can never go on is ended", which a retry loop and a server whose client never comes also fit. A sentence of the limit in §8.6, which would restate "every live process". A deadline in place of `limited`, which nothing asks for (principle 5). A second command beside `:processes` (principle 2). A tree of chains, or a count of callers. A line `calling a foreign process`, which the shell cannot tell from a callee that has just ended. A line from the runtime once a cycle has stood, which only a condition could make true, and with one the answer would be a fault.

Nor a status read over the network or a walk across peers (principle 3; *MVP 3.0's Findings Decided*, a node no peer of itself). Nor the host's reductions in `Status`, for the shell's sake alone. Nor, in the fault's report, a cycle line, an age or the faulting process's own callee, which would make the reaper a second cycle finder.

**A sound partial check, not taken.** Addresses cannot be forged, so a process whose address and replies no running process can reach can never wake. That is the one link between types and detection, and it is sound even with a hand-off. It is the idea of Pony's actor collector, whose cycle detector collects a group of blocked actors that no live actor can reach (the Pony tutorial's *Garbage Collection*). It is also that of Go 1.27's goroutine leak profile, which marks a blocked goroutine leaked when no live goroutine reaches what it is blocked on (the Go blog's *Goroutine Leak Profiles*, 2026-09-02). The proposal wrote both from memory, and both hold against those documents. The check needs a reading of every process's heap, which the host does not appear to offer.

Four questions came up as the item opened and were decided with the user the same day.

**A limit the callee keeps.** The proposal read `limited` from the caller's timed mark, which `Address.call` alone puts. But `Tcp.accept`, `read`, `write`, `connect` and `connectTls`, and `Os.read` and `write`, give their milliseconds to the callee in the request and make a `callForever`. The listing would then write `without limit` beside every wait of a server, a read that ends in five seconds among them (principle 1). So the limit goes into the call's mark, each call form putting its own, and those seven requests go through a call private to their modules whose wait is limited (E.18, E.23). E.0 shape rule 8 already names the waits that take a time, so the field has one rule behind it.

A fourth field of the mark measured 51.0 ns against 51.0 ns for three, best of five runs of five million, where the timed mark put and erased would add 17 ns to every such wait. Dropping `limited`, the smaller language (principle 5), was weighed and not taken: it loses the one fact that tells a stuck call from a slow one.

**A wait on a peer.** `Peer.find`, `Peer.spawn`'s wait for the peer's answer and `Peer.utilization` read `Receiving`, which E.21 gives a `receive` and `Clock.sleep` alone. Each waits on a peer for an answer within a time, as a compute does. So each is `Calling`, its callee `None` and its wait limited, its moment in a mark of its own.

**The listing's form.** The age is the whole seconds, `for 41 s`, every age counted to the moment the listing read its last process, so that a cycle's line and its processes' lines agree. A cycle's line begins at the process the listing writes first, so that two listings of one cycle write one line. A socket's site stays the library's, `Tcp.accept`, as §6.9 names every process by the spawn that started it. The fourth decision, a defect, follows below.

**The cold reading.** One reader read the report's sentences before the build, and its `fix` lines were made. `since` is the moment the call was made, where §6.6 starts its clock, and not the later moment the wait began. `status` answers `None` for a process a program's foreign code started, which E.21 did not say and the listing leans on. E.18 and E.23 name the private call among their primitives, by its own name, `callLimited`, as E.5 names `around`, since several functions make it. The order of one site's processes is stated, the words' and then memory's, the least first, and the order of two that tie is unspecified, since `Process.live` gives none. A callee on a peer is `a process of the peer b`, as the toolchain's other lines name a peer.

The reader's question of a restart's wait was decided by the rule *Where the report is silent*: a restarting process read `Receiving` while its restart waits for the wraps that tell its service monitors and for the other nodes' answers, and E.21 now says so. `Running` would say the host works in it, and `Calling` that it waits for an answer it asked for, and neither holds. The glossary's `ms` line takes `since`.

**A defect beside it.** A process waiting for a load's evaluator read `Receiving`, though E.21 has said `Calling` since 0.8.0: `Process.status` never read the load's mark. A probe showed it. The load's mark now holds the moment its wait began, which `status` reads.

**The tests.** Each is a regression test, written after the code but for the listing's five, which were written with it. `process_status_test` holds a call's callee, a system process's as `None`, each call form's limit, the moment and the peer's mark; `compute_caller_test` a waiting compute; `load_caller_calling_test` a load's wait; `restart_wait_status_test` a restart's. `processes_on_peers_test` runs a shell that is a node, with a callee on a bare peer and a wait on a peer whose gateway is suspended. None covers `Os.read`'s and `Tcp.read`'s limit through their modules, the waits of `Peer.find` and `Peer.spawn`, or a cycle's line written by a running shell, which the listing's own tests hold.

**The cost.** `make bench` left the call's rows within their noise: neither `Address.call` nor `Address.callForever` moved by a fifth from the last run or the release's. The bench's row of the call's key alone read 26.6, 44.6 and 37.3 ns in three runs, its range 33.8 to 53.2 ns, so a probe measured it, best of five runs of five million: the record put and erased costs 29.4 ns against 27.1 for the two-element key it replaced. The one new cost is `callForever`'s read of the clock, 23 ns alone against the host's round trip of 1165 ns, since `Address.call` read it already for its deadline and now reads it once for both.
