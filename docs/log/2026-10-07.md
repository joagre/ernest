## A Binding of a Previous Version Is Forgotten, 2026-10-07

Reading `mvp3.1.md` back for a load on one node showed that the rule it adds, two versions of a type are two types in one scope, is broken by today's shell before any hash exists. An experiment held it: a counter module loaded, its address bound to `c`, a constructor `Reset` added to `Counter.Msg`, `:reload`, and `send(c, Counter.Reset)` accepted without a diagnostic, the message then sitting unmatched in the old process's mailbox, where §6.3 leaves it. The checker names a type by its qualified name, the session's scope holds one meaning for the name, and a local address is a pid alone, so nothing in the checker or at run time told the versions apart. Three answers were weighed. The real one is MVP 3.1's, a type's identity its hash in the session's scope as everywhere, which keeps the binding of its own type and refuses only a message of the other version; it is items 2 and 7 of that milestone and not an afternoon. Refusing each use of the binding while leaving it in scope needs a scan of the typed tree for its references after the check, and leaves a binding that nothing can use standing in `:browse`. Forgetting the binding at the reload, listing it as the reload lists what holds a previous version, and answering a later use with why, reuses what `:forget` and the purging reload already do, and is what §11.2 now says. Which bindings: those whose type names a type whose declaration the reload changed, compared by the hash of each type alone in §11.1's canonical form, an abstract type of a module compiled again counted as changed since its representation is not in its interface, and every type of the session that names one of these, to a fixed point, since a session type declared at the prompt over `Counter.Msg` carries the old version as the binding does. The price, stated: a binding that could still be used soundly, killed through or watched by `Process.fromAddress`, is forgotten with the rest, and a binding of an abstract type is forgotten where its module was compiled again for a dependency alone. The refusal names MVP 3.1, `docs/development.md`'s table lists it, and the plan's standing gaps hold the defect with its fix.

## An Abstract Type's Private Fields Travel in Its Interface, 2026-10-07

The supervisor experiment under `proposals/nodes_and_code/experiments/code_update/` bound an address of `Supervisor.Msg` at the shell, and the shell stopped with an internal error; a program that printed such an address stopped `ern build` the same way. §4.2 lets an exported abstract type's fields name a private type, and `Supervisor.Msg`'s `Join` names `WatcherMsg`; the interface carried the abstract type's constructors but not the private types they name, so the descriptor builder, describing the abstract type's representation for printing or for the boundary's check, met a type it could not look up. Two answers were weighed. Describing such a type as unchecked, as a foreign type is, would leave a representation §8.4 checks unchecked from every dependent, an unstated approximation. Carrying the private types an exported abstract type's fields name, and those theirs name, in the interface, where the descriptor builder reads them and no name resolves to them, keeps §8.4's promise and §4.2's privacy both; it is what §11.1 now says. The interface's format went from 5 to 6, so every module compiled before is stale and compiled again, and the private types are in the interface's hash, since a change to them changes how a dependent describes the abstract type's values. The checker's own lookup is unchanged; the builder's is `ern_typecheck:described_type/2`.
