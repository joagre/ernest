## The Code Table, Built, 2026-10-10

MVP 3.1's item 3 as narrowed (*Positional Names Wait for Code That Arrives*). What the building decided:

- **The table is an ETS table, made once for the host's life**, since units outlive a run under `ern test` over a directory; a `persistent_term` would make every process collect at each load, and a load writes the table. A row is read in one lookup, a fraction of the spawn it serves (§10). It is a bag, since two definitions with one body share a hash and may sit in two units.
- **The table is filled from a function each unit carries, `'$code'/0`**, a literal list of each declaration's name, hash and function, which the emitter writes from the same canonical hashes as the forms' chunk, so `ern_canonical` remains their one owner. Filling it from the forms' chunk was measured first: decoding it took 88 ms over 35 units against their 38 ms to load, past §10's fraction, and the interface chunk 19 ms; the literal costs 2.6 ms over 26 units against their 24 ms. The host keeps a module's literals with its code, so nothing is read from disk again. A full build costs three percent more for compiling the literal.
- **The host has a fourth limit**, its export table, 524,288 entries in OTP 29, which a unit's exported names fill and at whose end the host exits (`export.c`). It is counted with the module names, the lambdas and the atoms, from `erlang:system_info(info)`'s index tables, the one place the host reports the three that are not atoms, at about a millisecond and a half, read once at a run's start and once for each unit the shell loads; the line at four fifths of any, once per limit for the runtime's life, is §11.2's rule for what the runtime writes unasked.
- **"Limit", not "bound"**, since the glossary's Bound is §3.11's bound type.
- **A defect found beside it**: `ern_node` called `ern_build:refused/2`, which was never exported, so a configuration directory the host could not read as one made `ern` fail with an internal error; exported, with a regression test.

## Positional Names Wait for Code That Arrives, 2026-10-10

MVP 3.1's item 3 had the build's units name their functions by position and be made from the canonical forms, so that one way would make every unit before MVP 3.2's code arrives. Reading its reach as the build began, every caller by name, the entry point, a test, the shell, a binding's initialization and `ern doc`'s calls into `Markdown`, would route through the code table, a fault's trace would map a position back to a name, and the golden files would be rewritten; and each buys MVP 3.1 nothing. Positional naming exists so that names a peer's build invents do not become atoms on a node without bound, and making a unit from forms so that a unit is compiled from what arrived; MVP 3.1 ships no code, and a load in its shell brings function names that are the program's atoms already. Decided with the user: both move to MVP 3.2's item 4, where code first arrives and needs them, and MVP 3.1's item 3 builds the code table, from hash to unit and function and from a binding's identity to its value, which item 4's spawn by hash reads, and the limits' line. One way makes a unit at each point in time: MVP 3.2 changes it for every unit at once (CLAUDE.md, *Prefer minimal, direct implementations over speculative abstraction*).
