## The Ownership Test Built, 2026-11-14

MVP 4.16's item 27, built on 2026-11-14. The rule is *A Package and Its Manifest*'s **The group's bits**. This entry holds what the build did, what it found, and what was decided over it.

**What was built.** Three places applied the older test, which counted a group's write bit as the world's: a node's configuration, the shell's startup files and `ernest.pid`. Under a umask of 002 a node refused an `ernest.conf` its group may write. Each now reads the owner and the bit for others. Where the tested path is a link, each link is followed in turn, and the directory that holds what it reaches is tested.

The walk is written twice, in Erlang for the node and in Ernest for the shell, since the shell's work is Ernest's. The Erlang stands in the toolchain's `cli`, as `ern_ownership`, where item 5's jobs can call it. Every test is a regression test, and none covers a path of another user's, which a test run as one user cannot make.

**One answer for a path.** A directory of the chain that fails is the tested path's failure, and the refusal names the path given, as §11.9 names `lib/epx` (principle 2). What the path reaches is judged first, then each directory in the order followed, the owner before the mode in each. The node says `may be written by every user`, as `ern stop` does. The shell's lines take the same words, where it said `could be changed by another user`: `F may be written by every user, and is not run` of the file, and `D is another user's, and F is not run` of its directory.

**`ernest.pid` follows no link.** The report was silent on a link there, and the code refused one at a node's start and at a signal. §11.2 and §12.5 now say so. The plan's item had the pid file take the chain. The narrower promise was chosen: a node writes its number through no link, so a link names no node's file, and following one in `ern stop` alone would be a second rule (principle 2). So the pid file's test is the open file's owner and mode.

**The superuser at `ernest.pid`.** The helper let the superuser signal by another user's file, and refused an ordinary user a file of the superuser's. No entry decided either. Another user's file holds the number its owner writes, and a process of that owner's can hold its lock. So the superuser's `ern stop` would signal a process of that user's choosing. The helper now applies the report's test, the user's own or the superuser's, as a node refuses the superuser another user's directory (principle 2). The cost is that the superuser stops another user's node as that user, or by `kill`. No test holds the change.

**A target that is not UTF-8.** No `Path` names a link's target that is not UTF-8, so the shell cannot test the directory that holds what it reaches. The shell reports the file and does not run it, and §11.2 says so. The node's Erlang reads any name. Nothing was added to `Fs`, whose `NotUtf8` is Appendix E's answer for such a name.

**What the sentence already decides.** A target that ends in `.` or `..` is held by the directory above what it reaches, which the host's `..` finds, and not by the directory its text names last. §11.2 says "the directory that holds what a link reaches", so no sentence was added, and a test holds the case. The root has no directory above it and is judged as itself.

Two points stay in the code. Both walks stop at forty links, the host's limit for one path: the host followed the chain to reach what the path reaches, so only a chain changed during the walk is longer, and the read after the test meets that chain too. A path given with a trailing separator loses it before its link is read, since the host would follow the link there.

**The read-back.** The walk in Ernest writes `match first { None -> next | failure -> failure }` twice, to judge the next thing only where the first passed. A search of the tracked Ernest for an arm that hands its value through finds eight sites, and only these two are over an `Optional`. Two sites in one walk are no form repeated at site after site, so nothing goes to the language's feedback, and `orElse` stays out (*The Library Family's Rules*).

## A Library's Function in a Program, 2026-11-14

Decided with the user on 2026-11-14, while MVP 4.16's item 28 was built. This entry says why CLAUDE.md gained a rule, what the sweep it plans reads, and one verdict.

**The gap in the rule.** CLAUDE.md had a function the library lacks said at once, where the writer felt it missing. Nobody writes a sort in a program without feeling it. A helper over a list of segments is written as the program's own, and the rule never fires. E.0 counts no programs: a function enters when a rule admits it, whether or not a program has asked (principle 5). So a function written once, in one program, may still be the library's.

**The test.** A private function whose type names no type of its program's own is read against E.0 before it is written. The trigger is the function's type, which a search runs over the sources. The verdict stays a reading: rule 4 refuses a composition, and rule 3 a buried policy.

A general function written over a program's type, one that never looks inside it, names that type and passes the test. The rule stays that narrow, since a wider one brings the feeling back as its trigger. The sweep's readers look for the shape.

**The sweep.** The Ernest outside the standard library is about 42,000 lines, 21,800 here and 20,100 in the three applications. All of it is read in one item, MVP 4.16's item 37, before the full review, so that the review reads the library with what the sweep admits in it. The Ernest here holds 880 private functions, about 430 of which name no type of their program's own by a rough count. A script lists them, which costs cycles, and three readers judge the list from the candidates' bodies and not from the code whole.

**The applications are swept from here.** The clean room keeps an application's session from Ernest's checkout and keeps this session from writing there. It lets this session read, and the sweep only reads. So the same script and two more readers list the applications' functions, under each program's name. One judge then reads one list by one reading of E.0, and the user opens no three sessions for it. An application's session is told which of its functions the library takes, and drops each at its floor's rise.

**Who judges.** A reader gives each line its verdict by E.0, and the session judges a line its reader hesitates over. The user is brought only what the session wants to discuss, so that a long list costs the user no evening. Every verdict stands in the item's report all the same.

With the test of the type, the line is written where a reading of E.0 admits the function, and for no other, so the feedback gains no noise.
