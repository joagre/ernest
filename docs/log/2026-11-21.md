## A Failed Write Loses What Had Arrived, 2026-11-21

The second question of MVP 4.16's item 100, feedback 263, decided with the user. A first user meets it, less often than the first: a client that still writes when its server answers and closes.

**Shown.** A client wrote a byte that the server never read, and the server wrote `hello` and closed, which reset the connection. A client that then read twice was answered `hello` and `Left(Closed)`. One that wrote a byte first was answered `Left(Closed)` by the write and by both reads. The same held after an orderly close, where the server had read the client's byte: the first write after it answered `Right(Unit)`, the next `Left(Closed)`, and both reads `Left(Closed)`. Each in 5 runs of 5, the client acting once a monitor said the server's socket had ended.

**The host drops the bytes.** `hello` was in the kernel's buffer for the client's socket when the write failed, and the kernel alone still gave it to a read after a failed send. The host's driver closes its descriptor at a failed send (`tcp_send_or_shutdown_error` in `inet_drv.c`), and the bytes go with it. Twelve options of the host's were tried with OTP alone, its other socket engine among them, and none keeps the bytes for a read after the failed send. Over TLS the probe lost nothing: the host's `ssl` reads one record ahead, so nothing was reset and every write answered `Right(Unit)`. Whether a write over TLS that answers `Left(Closed)` loses bytes was not run.

**Decided: a narrower sentence.** Since *What One Read Answers* E.18 said that what had arrived before the far end closed is read before a read answers `Left(Closed)`. The probe shows that false where a write fails first, so it is mended before the launch (*The Line Before the Launch*). E.18 now excepts a write answered `Left(Closed)` first, and says that such a write closes the host's socket and that what had arrived and no read had taken is lost. Principle 1 decides: a reader who knows Erlang predicts that a `recv` after a failed `send` answers `closed`. It keeps what *A Close, an Exit and a Write* and *What One Read Answers* decided, a write as the host's send and a read as the host's receive.

**The mechanism set aside.** A socket that takes what has arrived before each write does not hold the promise, since bytes that arrive between that take and the failing send are still lost. It also breaks the pull of *Sockets Are Read by Pulling*: the host takes a piece only for a read, and a program that writes and never reads would grow a buffer without bound.

**What a program does.** A client that wants the answer reads before it writes again. A server that wants its answer read keeps reading what the client still sends until the client closes or a time passes, and closes then. ernest-httpd's session is told with the item's verdicts.
