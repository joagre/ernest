## §0 Read Again, 2026-10-16

MVP 3.26's item 0, decided with the user on 2026-10-16, before its items 1 and 2 are built. Three sentences of §0 change, as the proposal's section 5 asked.

The sentence that defined *pure* goes. §0 said a function that sends, receives or asks for its address names its mailbox in its type, and that one which does not is pure and affects nothing; after the change a sender names no mailbox and a function without a mark may print, so both were about to be false. §0 now says that a function which receives from its mailbox, gives out its address or asks for a message to be delivered into it names the mailbox, `receiving M`, and that one whose type names no mailbox receives nothing and runs in any process. The word *pure* appears nowhere in the report; "functional language" stays, by what it has meant here, functions as values over immutable values. CLAUDE.md's first line changes with it.

Principle 3 says what visible means: where it happens, a send at the line that sends, a fault at the line that faults, a receive at the line and in the type around it. That is how the principle already read failure, and it is the sentence that lets a forgotten answer be a run-time outcome, the loss the proposal's section 2 names.

Principle 5 says what a type carries: what keeps values and messages safe, the type of what a function receives among it, and nothing of what a function does. It stands under smallness because it is the measure that decided both subtractions and the measure the next mark on a type must meet; under principle 3 it would read as a claim about visibility, which it is not. The cost is a sentence in §0, which had not said what the type system is for.

## The Runtime's Own Processes, 2026-10-16

Two defects the read-back of MVP 3.26's item 2b found, fixed the same day. The reaper was linked to the processes it starts for the runtime's own work, a `Down`'s wrap and the process kept for an adapted address, and trapped no exit, so one of them ending abnormally ended the reaper and the run with it; the clock was linked to each alarm's delivery the same way. A probe before the fix showed it: a refused `:load` of a module whose binding monitors with a wrap that never finishes purged the unit, the purge killed the spinning delivery, the reaper died with it, and the session answered nothing more. The reaper now traps exits and holds these processes, and so does the clock; a process of theirs that ends abnormally is taken out of the deadlock count's sources and its row of deliveries goes, by a read of the deliveries in flight that only such an end pays, since the purge that makes one reads every process of the host already. Rows of their own for these processes were the other shape, and lost: rows protect the run only from the ends the checks foresee, a purge of code reached through a function value, a kill from foreign code or a raise at the boundary among what they miss, and `Process.live` and `status` would have a kind of row to leave out. Principle 1 decided: §6.9 says a wrap that does not finish holds up no other delivery, and §8.7 that a kept process holds its messages and nothing else, so a reader expects such a process's end to end nothing else, however it ends. Each delivery's end now reaches the reaper as a message after the delivery has ended, so the memory test of its waits reads its words once it has taken every one, which a full run showed when it read them too soon.

The gateway started a new worker for a peer whose connection was lost and opened again while the old worker could still hold frames, and now processes kept for addresses whose functions wait: a message sent after the loss could pass one sent before it, against §6.4's order to one address, and `ern_peer:lost/1` took every spawn row of the node, so a spawn made after the reconnection could be taken by the old worker's loss and answered `Unreachable`. A node now keeps one worker across a loss: the gateway hands it the loss with the order it read it in, counts what it hands it, and the worker runs the loss in order, keeps its kept processes until none waits, reads the frames that come after the reconnection itself, and asks to end once it has run a loss and keeps no process, which the gateway grants only when the worker has taken every frame handed to it. A spawn's row carries the order it was written in, and a loss takes the rows written before the node ran it, which §8.7 says now: the node cannot see the moment the host dropped the connection, so a wait that began in the gap before the gateway read the loss ends as the loss ends every wait that began before it.
