## The Watcher Holds Who Waits, 2026-11-17

MVP 4.16's item 73, widened with the user before its build and built by one agent. *Two Orders Stated* decided its first form.

**The held child is not asked again.** *Two Orders Stated* has the child at whose fault a group gave up run again once each other child has restarted or ended. Asked last, it would restart a second time. A call made to it after its fault would then end with its mailbox, where the same call after a strategy's restart is answered. So it is not asked: it restarted at its fault and has run nothing since. Principle 1 decides, one answer for both restarts. A service monitor of that child now gets one `Restarted`, where *The Nested Group's Third Restart* counted two.

**One cause, four ways.** Only the supervisor's current run knew which children wait to run again. An ask from a run, or at a moment, that did not know restarted a waiting child at its wait, and it ran `f` at once. The group's giving up was the first way. A sibling's fault was the second: under `OneForAll`, `a` faults and waits for `b` and `c`, `b` faults before it takes the restart, and `b`'s fault asked `a`. A probe had `a` answer 31 to 49 ms after its fault, 3 of 3, while `c` computed for 1.1 s more.

The third was the parent asking the supervisor to restart, whose new run asked the waiting child: 51 ms, 3 of 3. The fourth is a fault the supervisor has not yet counted when it asks. It was read from the code and not shown, since it needs two faults within two messages of each other.

**The narrower promise was not taken.** It would have excepted a second fault and a parent's restart. A cascade makes both, and there a program needs the group whole most (principle 1).

**The rule.** The watcher holds who waits, and the supervisor decides when each goes. After every restart a child asks through the watcher whether it may run. Its call sends the question before the wait at which an ask is taken, and `Process.status` before it is no wait. So the supervisor has a child's fault before that child's later question. The watcher keeps each child's latest question until the supervisor lets it go or the child ends.

Each run reads who waits as it begins, asks every other child, and lets each waiting child go once those have restarted or ended. The first run finds none, so no run reads its start cause, and E.22's sentence of primitives has `startCause` beneath `child`. `Hold`, `Release` and the `Bool` answer are gone.

**What the build added.** A question passed on before a restart in place may reach the new run, which has read it from the watcher already (§6.9). So the watcher numbers its questions, and a run drops those at or below the last it read. A let-go names its question. One that named the child could answer a question that has since replaced the one it was meant for, and the child would run before its next fault is counted. A second fault waits for a sibling already asked and does not ask it again.

**The fourth way's edge.** A child asked before its supervisor has counted its fault takes the restart. Its service monitor gets a second `Restarted`, and a call made to it meanwhile ends. It waits on all the same, and E.22 says so.

**The fourth way's test.** The item's first commit left the edge untested, on the belief that only a hold inside the module could show it. The host holds the supervisor from outside. Main suspends its process with `erlang:suspend_process/1` while `b` and then `a` fault and wait for its word. It makes `a` fault only once `ern_waits:queued/2`, a new wait on a mailbox's count, shows `b`'s question in the supervisor's mailbox, so the order of the two questions rests on no race.

Resumed, the supervisor takes `b`'s fault and asks `a` before it has counted `a`'s, and `a` answers only once the computing `c` has restarted. With the clause that keeps an asked child waiting for its own fault taken out, it answered `0 not restarted`, 13 of 13. It is a regression test, written after the code, and takes 0.3 s.

**Left as they are.** A fault the supervisor never takes, because its parent restarts it first, is counted by no run. The run that would have counted it lost its count at the restart, and the new run counts afresh, so no program can tell, and E.22 gains no sentence. A child asked by one run and again by the next may restart twice. E.22 has each run ask each child, so both are restarts the report states.

**The tests.** Three tests, one for each of the first three ways, were written before the code and were red on the old module with `0 not restarted`. Each reads, as the waiting child answers, that the `Restarted` of the computing sibling is in main's mailbox, which §6.9 places before the sibling's new run. Killing the socket's port at the decision removed the wait, and holding the receiver 12 s made it 22 s.

**The node's end is the host's `halt`.** The receiver's end closes the port with 1.6 to 5.3 MB still queued, and the host keeps such a port until its queue drains. `halt` waits for it with no limit. gdb on the hung node showed one port left and every scheduler idle. A termination does nothing to a node there, since no Erlang process runs to take it; the interrupt ends it.

**With OTP alone.** Two plain `erl` nodes show both. Over TLS distribution `nodedown` came 10.002 to 10.004 s after the ticker's end in every run, and over plain TCP in the same millisecond, so the wait is ssl's alone. It is the code of OTP's issue 12212, `docs/otp_bugs.md`'s report 10, entered from the ticker's end where that report enters from `ssl:close/2`. It is report 24. The hang shows over TCP and TLS alike: neither `halt(0)` nor `init:stop()` ended a node within 15 s while its peer stood still. No report is written for the hang, since OTP documents that a halt flushes without a limit and documents the setting that bounds it.

**The ten seconds: a sentence, and no mechanism.** Decided with the user. A time the host decides is stated as the host's, and a number stands in the report only where Ernest's own code keeps it. Principle 1 decides: its reader knows processes as Erlang has them, and the loss comes when the host says so. §12.6 says that the loss is run once the host has closed the connection, and that the host closes it later where more was sent to a silent peer than its connection took. It states no number, since the ten seconds are two of ssl's constants. The deployment guide gives the measured 85 seconds, and its unit's 90 stand.

The mechanism set aside: kill the socket's port at the detector's decision. It removes both symptoms. On the dialing side Ernest reaches that port only through the process structure of OTP's TLS, which no document promises, so it would be a reliance to defend at every release of OTP for a number the host never gave.

**Three kinds of promise at a limit.** The verdict rests on a sorting made in the same discussion. A rule of Ernest's own semantics holds at the limits or principle 3 means nothing. Liveness, that a node ends and a wait is ended, cannot be narrowed and stay useful. A time, an order or an amount the host decides is the host's, and the narrower promise is weighed first there (`CLAUDE.md`, *A hole is answered first by a narrower promise*). The late loss is of the third kind and the node's end of the second.

**The node's end: a linger of no time.** Decided with the user: a close drops what the socket still holds, as §8.7 has a loss drop what waited. It chooses no time. A limit on the halt's flush is a time chosen, and was not weighed further.

The first build set the linger on each connection as it came up, by `net_kernel:setopts/2` at the gateway's `nodeup`. It raced the host. The host sends `nodeup` from `erlang:setnode/3`, before the connection's owner tells `net_kernel` that the connection is up, and a call made then answers `{error, noconnection}`. With OTP alone it did so for 40 of 1,000 connections and 49 of 2,000, and every node whose call lost hung as before. The test passed inside the nodes' suite, where the call won, and failed alone.

The host's other documented way, `net_kernel:setopts(new, ...)`, answered `{error, enotsup}`: it sets the options through the distribution module's `setopts/2`, which neither `ern_tls_dist` nor the host's `inet_tls_dist` exports. So `ern` gives the host the linger as it boots: `inet_dist_connect_options`, read at each dial, and `inet_dist_listen_options`, whose linger each accepted socket takes. A probe read `{linger, {true, 0}}` on the dialed socket, the accepted one and the listener.

That is wider than the first build: the linger reaches a close before a connection is up, a refusal's among them, where a reset could drop a refused peer's last bytes. Decided with the user on the condition that no refusal's line changes. Fifteen tests that read a refusal's line, or a peer's line at such a close, each passed ten times of ten alone, and eleven tests of an orderly end did the same. The node ended 8 to 12 ms after its loss line in five runs of the test alone, its peer still stopped.

**A green run that showed nothing.** The session ran the first fix by hand before it was built, saw the node end, and reported the fix as shown. The run showed the fix where the call takes. The build's test, run alone, found the race.

**`ern stop` and a node in its halt.** `ern stop` answered at once, status 1, `no such file: no node runs from the directory`, of a node hung in its halt. The node removes `ernest.pid` before the halt, and the halt closes every port, the lock helper's among them, so the lock is let go while the process still runs. A change of order does not fix it: the helper must hold the lock until the node's process has ended. It is MVP 4.16's item 102, with the tests' cleanups that find a node by the same file.

**Not shown.** The end, while its peer stands still, of the node that was dialed. An end by termination meanwhile. The options on a real IPv6 listener's sockets, where a test holds the flag's text alone.

**What it cost.** The diagnosis 36 minutes of an agent, the two builds 52, and the reproduction with OTP alone 36. `make test-full` ran once at the close.
