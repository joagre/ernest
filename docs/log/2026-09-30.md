# The decisions log, 2026-09-30

## The Runtime's Own Is Not Checked, 2026-09-30

A foreign function's return and a call's reply were checked in the standard library as in a program. There they guard against our own defects, at every program's cost. `Set.put` walked the whole set it returned, so it was linear where the host's is logarithmic, since `==` compares a set's representation. Checking `Map.get`'s `Optional` took more than half its time. §8.4 already left the system processes' messages unchecked, because the runtime delivers the declared types, and the standard library is the runtime's in the same way. Now a return of one of the library's foreign functions and the reply to a call the library makes are not checked. What holds their contracts is what holds the rest of the library's: its tests and its documented examples, which run. A program's foreign functions, and the libraries under `libs/`, keep every check, since their host code is not ours and the type checker never saw it. The `try` around a library call stays, so an exception the host raises still faults with the text §7.4 gives, naming the implementation. `Map.get` went from 63 ns to 24, against Erlang's 19. The question this leaves for a program is the next one: whether a reply between two Ernest processes, which only Ernest code answered, needs a check.

## A Value Is Checked Where It Crosses, 2026-09-30

Every `Address.call` checked its reply, because the caller could not tell whether foreign code had answered. Between two Ernest processes the check paid for nothing, since the type checker had already seen both sides. It cost 6% of a call with a one-string reply and 190% of a call answering 1,000 strings, on top of the copy of the message. Decided with the user, a value is now checked where it enters from foreign code, and code the checker has seen never checks its own values.

An answer now says who gave it. Ernest's `answer` sends `{Alias, answered, v}`, and foreign code answers `{Alias, v}`, the form §8.4's ABI gives it, since a foreign server must answer and the report had called a `Reply` an opaque handle. The caller checks only the second form, against the reply's type, which the compiler passes to the call. A `Reply` that foreign code gives back, in a return or a message, is held as foreign, and Ernest answers it in foreign code's form. So a `Reply` handed back retyped, whose answer Ernest would give as the new type, still reaches its caller checked. The runtime's own calls, the standard library's and the system processes', pass no type and check nothing.

Two designs came first. A checking proxy for each `Reply` that crossed into foreign code needed a process whose life must end with its call, and a call that timed out left it waiting for an answer that might never come. A mark on the caller's row in the table of calls needed no process, but reading the mark as the call ended took the row out of the table. That cost 100 to 140 ns a call, more than the check it replaced for a small reply, and no other way of reading the table was cheaper. The answer's form costs nothing an Ernest call did not already pay. What it does not guard is foreign code that sends the runtime's own form on purpose. That is foreign code impersonating the runtime, as sending `'$ern_restart'` would be, which no check can stop.

Measuring the first decision's check found a defect beneath this one. Only a foreign function's arguments crossed. An address sent inside a message to a foreign process reached it raw, and a bad message it sent back was delivered unchecked: `Go(<<"x">>)` matched `Go(n)` with `n : Int` bound to a binary, and faulted far away in `Int.toString`. An address that comes from foreign code, in a return, a reply, a message or a callback's argument, is now held as foreign, unless it names a process of the program. A message sent to a foreign address crosses as a foreign function's argument does. The same holding undoes a proxy that comes back: an address the program gave out and foreign code returned is the process again. The standard library's own arguments are not exposed, since its shims are ours, which also ends the proxy `Process.fromAddress` spawned for every address it was given.

## Supervision Stays in the Reaper, 2026-09-30

`spawn`, `monitor` and a call's row go through the reaper and a table, where Erlang's `spawn` and `monitor` make no message and keep no row, and the question was whether they should. Decided with the user, they stay. The round trip at a spawn is the supervision itself, not bookkeeping around a native call. The reaper holds a monitor on every process from its start, so one place sees every end, whatever caused it: a return, a fault, a kill, the program's end, an exit foreign code sent, a host limit. That place reports a fault, delivers `Down`, and keeps the rows the deadlock check and `Process.live` read. A process that registered and removed itself would cost about 1.8 µs a spawn, but an end it cannot see would be seen by nobody: its row would need a sweep, and its fault would go unreported. A `monitor` waits for the reaper so that a kill after it is seen as `Killed`. A call's row, 200 ns of a call of 1.3 µs, is what lets a restart end the calls waiting on its process (§6.9). Measured beside them, Erlang's `proc_lib:spawn`, which reports a crash, costs 1.7 µs, and `supervisor:start_child` 6.1 µs. The same protocol written in plain Erlang costs 4.2 µs. Ernest's `spawn` now costs 4.9 to 5.1 µs. The reaper takes a process's row in one step rather than a read and a delete, builds a `Down` only for a process something waits for, and skips its maps of waits when the process was in none of them.

## Three Scans on a Value, 2026-09-30

Measuring found three places where the work grew with more than the value asked about, or where a general engine answered a fixed question. `String.trimEnd` split the whole string into a list of graphemes to drop the last few: 11 ms for 100 KB, 34 times the host's trim. The host's trim cannot stand in for it, since it compares whole graphemes with its separators, where §E.5 removes a grapheme by its first code point, a space that a combining mark joins among them. Now only the tail is split. No ASCII code point extends a grapheme or is prepended to one, so the tail after the last ASCII byte that is not White_Space holds every grapheme that could go, and ordinary text trims in microseconds. A string with no such byte is still split whole by the host, 8.6 ms for 100 KB of accented letters, since telling where its graphemes break needs properties the host does not publish. `String.toFloat` checked the literal form of §2.5 with a regular expression. A scan of the form's few parts says the same thing more plainly. `Char`'s predicates did the same for a code point beyond ASCII, 0.6 to 3 µs a call, which *Char Reads the Host's Tables* decided. And the shell read every persistent term of the node to find the few a purged input had stored. The host copies each term it returns, so a session holding a large value copied it again at every purge. The shell now keeps each input's keys beside what the input needs, and reads those alone.

*Superseded in part 2026-10-04 by "What Erlang Held, Moved": the tail's argument now finds the last grapheme, beneath `trimEnd` in Ernest.*

## Char Reads the Host's Tables, 2026-09-30

`Char`'s predicates read a code point beyond ASCII with a regular expression, `\p{Nd}` and its kind, 0.6 to 3 µs a call even with the pattern compiled once. `String.trimEnd` tests a character with `Char.isSpace`, so it paid that too. Decided with the user, they now read the host's own tables, `unicode_util:category/1` and `is_whitespace/1`, at 1 to 30 ns. Those are the tables the host's `string` module is built on, `uppercase`, `next_grapheme` and `to_graphemes` among its functions, so `Char` and `String` now follow one version of Unicode. PCRE carried its own, older one: over every code point, 4,644 letters and a few digits, all added in Unicode 17, were letters to `String`'s tables and not to `Char`'s. White_Space agreed everywhere. Against it, the host's documentation hides `unicode_util`, and a shim is written from its manual page (CLAUDE.md). There is none to write from, and a host release could change the module without notice. The library's tests pin what each predicate answers, a code point new in Unicode 17 among them, so such a change fails where it is seen. §E.6's rule, the Unicode property of the code point, is unchanged, and so is its version: the host's.

## `RestForOne` Reads the Order of Spawns, 2026-09-30

`RestForOne` restarted the children that joined after the one that faulted, in the order they joined, and a child joins when it first runs. So children a program spawns in one order join in the order the scheduler runs them. The program cannot choose that order, and the strategy it chose was at the scheduler's mercy. `examples/services.ern` spawns a store, a source of ids and an audit log, in that order, and relies on the store's fault restarting the other two. Once the library's calls grew faster, the three joined in reverse, nothing joined after the store, and nothing restarted. OTP has no such race, since its supervisor starts children one at a time and waits for each. Decided with the user, the order `RestForOne` reads is now the order of spawns, which is the program's own. Every spawn passes through the reaper, so the reaper numbers each process as it starts or adopts it, from the host's monotonic counter, in the row it already writes. A private shim, `spawnOrder`, reads the number, as `startCause` reads why a restart began (E.0 rule 1): it is the runtime's knowledge. The watcher keeps its members in that order, so the reverse in which a dead supervisor's children are killed follows it too. Taking a place when `Supervisor.child(sup, f)` is called was the other way. It needed no shim, but it would have turned `child` into a call with an effect, and a place taken for a function never spawned would have been held with nothing to let it go. A child that runs `child`'s function in its own process, rather than spawning it, stands where its process was spawned.

## `Clock.monotonic` Is In, and `Udp` Is Placed, 2026-09-30

Both had waited since 2026-09-18 for "a later MVP", with no milestone and no verdict. Judged on E.0, `Clock.monotonic` is admitted by rule 1: the host's monotonic clock lives in the runtime, and Ernest cannot compute it. It passes rule 3, being general and burying no policy, and rule 4, since the difference of two `now`s is not a duration when the clock is set between them. `Clock.now` is the wall clock (E.15), and a program that measures time by it measures wrong once the clock is stepped. Our own `make bench` did, and `Supervisor` counts its faults by alarms for that reason. It is a shim over the host's monotonic time in milliseconds, the unit of every other time in the library, and makes no call to the clock's process, since Erlang reads it without a message. Its value alone means nothing, so it is named for what it is, not `elapsed` or `ticks`. `Udp` is admitted by rule 1 as well, a system module beside `Tcp` over the host's sockets. Nothing we build needs it, so it waits with the libraries that are written as they are wanted (MVP 3.2), as a module of Appendix E and not a library under `libs/`. Its shapes are `Tcp`'s: a socket is an address, a read is pulled and takes a time (E.0 shape rule 8), and a datagram is `Bytes`. What would bring it forward is our own work needing it, or someone asking.

*Reason restated 2026-10-01: `Udp` is admitted by E.0 rule 1 and dated to the libraries' milestone, MVP 3.4 since 2026-10-07, as a module of Appendix E, a schedule and not an admission ("The Library Family's Rules"); our work needing it or someone asking was a count, which no longer decides.*

## Make Runs `ern build` Every Time, 2026-09-30

The Makefile kept a stamp file for each Ernest tree, `build/stdlib/.built` and the others, and ran `ern build` only when a source's modification time was newer than the stamp. A time says when a file was touched, not what it holds. A source restored with an older time, by a checkout or an editor, a stamp left behind a deleted `.erc`, or two trees built in a different order all leave the stamp saying "done" over a tree that is not. `ern build` already decides what to compile again by content: the source's hash, its dependencies' interfaces, the standard library's, and the build of `ern` (§11.1). The stamps were a second rule, beside the toolchain's own, guessing at its answer (principle 2). Decided with the user, make keeps no stamp: `stdlib`, `libs`, `shell`, `tools` and `man` run the toolchain every time, and the toolchain decides. A copy of a module under its Erlang name is written only where its content differs. The price is measured: a `make` with nothing to do takes about 5 seconds, for the virtual machine each run starts, where it had taken nothing. A change to a source dated before the last build, which the stamps missed, is now built.

## A Load Samples a Node at Rest, 2026-09-30

About one run of `make load` in ten failed a load that leaks nothing (the plan's MVP 2.98, item 7). Each process's memory was written at each sample, beside the kinds of `erlang:memory()` read at the sample and a moment after. That showed three causes, none of them a growth.

The caller of `mark` sampled the node while it was itself at work. It collected its own heap partway through collecting the others, then took the answer to each later collection as a message. Those messages sometimes forced a minor collection that moved its whole heap into a new old heap just before the reading, a swing of about 340 KB.

The host sizes a heap after a collection by what the process held before it, garbage included, and grows it a size at the next collection when what lives fills most of it. So the same data sat in a heap of 28,690 words at one sample and of 46,422 at another, in the shell's own process and in `code_server` alike. A second collection straight after the first did not settle it.

The host keeps the structures of ended processes for processes to come, and trims them when it likes. In the `supervisors` load they rose by about 300 KB over the first eleven rounds and fell by 100 KB after, while what the processes used held flat. The host also counts a freed heap a moment after the collection that frees it.

The sample now measures what a leak grows, and nothing the host decides. A process of the harness's own samples while the caller waits in `receive`, as the plan's shape of the fix said, so the caller is at rest and collected as every other process is. A heap is counted by the words it holds, from the host's own figures for each process (`garbage_collection_info`), not by the block the host keeps for it. The node's memory is what is in use: what the processes use and what the system uses, less the unused words of every heap. The sampler waits 100 milliseconds after the collections before it reads. The reaper's column reads what the reaper holds the same way.

Nothing a leak grows is left out: a message kept, a heap's live data, a table's rows and a binary all count. A leak planted in the harness, a process keeping 48 KB more each round, showed at exactly that and failed the load. The loads now vary by about 15 KB where they varied by several hundred. The bound stays at 128 KB, the size that shows a leak of a hundred bytes an operation. The median of three, tried on 2026-09-29, hid the swing while its cause was unknown; this removes the causes instead.

## A Check at the Boundary Lasts as Long as Its Process, 2026-09-30

An address that crosses into foreign code is replaced by a proxy that checks what foreign code sends it (§8.4). There is one proxy for each address and mailbox type, and it lives until the process behind it ends. For `via(f, addr)` the address holds `f`, so a function that captured other values is another address. The shell exposed `via` over a fresh closure at each input and kept a proxy for each for as long as the session lived, 679 of them in one load, until its function stopped capturing the run's number.

Decided with the user, the proxy keeps that lifetime, and §8.4 now states it. The runtime cannot tell when foreign code lets go of an address, since the host keeps no weak reference to a process. A proxy ended earlier, when the call that exposed it returns, would drop what foreign code sends later, without a fault anywhere (principle 3); the shell's own `spawnInput` sends after its call has returned. One proxy for each process, with each `via`'s function in its table, grows by a table entry where it now grows by a process, and it cannot tell which function a message was meant for, since a process does not see which alias a message came through. Refusing a `via` whose function captures values judges the program's text where the growth is its run's: a `via` that captures a constant grows nothing. What is kept is bounded by what the program does. The same `via` exposed again, a constant function or a function capturing the same values, reuses its proxy. That is `docs/memory.md`'s rule that something is kept as long as a program holds what it stands for, the holder here being foreign code.

The runtime makes no such proxy of its own. The standard library's arguments are not exposed (*The Runtime's Own Is Not Checked*), and a system process is not a foreign address. The shell exposes three addresses, its own for the terminal, the screen through `via(Wrote, screen)`, and the session through `via(Done, self())` at each input. Each is the same address every time, and a session holds three proxies after a hundred inputs as at its start.

Reading the path found a defect of the same promise. An answer given to a `Reply` foreign code gave went to foreign code as it was, so an address in it crossed with no proxy, and a bad message foreign code sent there was taken unchecked. §8.4 now names that answer among what crosses. The foreign `Reply` keeps its answer's descriptor, and the answer is exposed as a message to a foreign address is. A function in the answer crosses as one in a message does: §8.4 checks the arguments of a function given to a foreign function, and of no other.

## Scheduling Hints Are the Host's, 2026-09-30

The first plan put "`process_flag(priority, ...)` and scheduling hints" among the optimizations of a later MVP, and the plan since said they "wait for a program that needs them", a count, which decides nothing. Decided with the user, they are out of the language and the standard library.

The host offers three kinds: a process's priority, `low` to `max`; the memory options of a spawn, `min_heap_size`, `fullsweep_after` and `message_queue_data`; and the node's schedulers and their binding to the processors. None changes what a program computes. The node's schedulers are how a node is started, not a program's.

A priority breaks a rule the report states. §10 says a process cannot prevent others from running, and a busy process at `high` or `max` does: it starves every process below it, and one that calls a process at `normal` waits on it while it is starved. It is invisible too (principle 3): a priority set in one process changes when every other process runs, and none of their code shows it. E.0 would admit a `Process.setPriority`, by rule 1, since only the host can make one, and rule 3 refuses none, since the level is an argument. §10 is what refuses it.

The memory options change no meaning. Each would be a second way to spawn, or a setting beside one, for a cost on one host (principles 2 and 5). The runtime may set them on its own processes when a measurement shows the need, which is its implementation and needs no sentence in the report.

A program that must have either reaches the host through `foreign fn`: `processFlag(Erl.atom("priority"), Erl.atom("high"))` over `erlang:process_flag/2` runs today. That is where it belongs, the host's alone and marked foreign where it is written, and §10's rules, as §8.4's checks, do not reach foreign code. What would change the verdict: a rule of the report that promises time, a bound on how late a process runs, which a priority would be how to keep; or a measurement that shows the runtime's own processes need an option, which changes the runtime and not the report.

## A Library Is Fetched by Its URL, 2026-09-30

The fetcher of MVP 3.1, `ern fetch name url`, takes a library's source from a git URL and records the hashes of its definitions (*MVP 2.7, the Fetcher, and No Server*). Finding a library by its name alone, through a registry, was left as "a tooling question for later" since *Packages*. Decided with the user, it stays out of the toolchain.

Where code comes from is visible now: the user writes the URL, and it is recorded beside the hashes. A registry puts an index between a name and a source, and whoever keeps the index decides what the name fetches, a trust the user does not see (principle 3); registries have lost names to squatting and to hijacking. Content addressing does not need one: what the code is, is its hashes (§8.7), checked after the fetch, and a registry adds a party to trust and nothing to that check. A name a registry resolves would be a second way to say where a library comes from, beside its URL (principle 2), and a registry is a service to keep, which nothing in the language asks for (principle 5).

An index of libraries is others' to publish, as a page or a list that gives the `ern fetch` line to run, and `ern` does not change for it. What would change the verdict is a registry that hides nothing, whose answer can be checked, as a name signed with the hashes it stands for. Even then it would stand beside `ern`, and `ern fetch` would take the URL it gives.

## A Cycle Through a Function Stays One, 2026-09-30

A reader of our Ernest code found `libs/markdown`'s block starters written `fn starts() = [headingStart, ...]` and rebuilt for every line, since `let starts = [...]` is a cycle: `quoteStart` reaches back through `quoted` and `blocks` to `block`, which reads the list. §8.5 names the case: a binding depends on what every function it names depends on, "called or not", and `let handlers = [f]` is a cycle when `f` names `handlers`. Building `[f]` calls nothing, so that cycle would do no harm at run time. But the rule cannot tell a function kept from one called, as `List.map([1], f)` calls `f` and `Map.fromList([#("a", f)])` might. Go's rule is the same, and so is its error.

Decided with the user, §8.5 stays. A finer rule exists, OCaml's for `let rec`: an initializer that calls nothing, built of constructors, lists, tuples and lambdas, depends only on the `let`s it names. It would take the literal list, and not the dispatch table a program most often writes, `Map.fromList([...])`, which is a call. And `let xs = [f, g]` would compile where `let xs = List.reverse([f, g])` would not, a line a reader could not predict (principle 1), drawn by a clause more in §8.5 (principle 5).

What was missing was the way out, which the lambda's cycle already had in its help line. The diagnostic of a cycle through a function now says that the function reads the value when it is called, and that a `fn handlers() = ...` builds the value when it is asked for. Both are true whether or not the initializer calls the function. Where it does, the `fn` recurses as the `let` would have, which the help does not hide.

## `kill` and `monitor` Keep the Address, 2026-09-30

A reader of our Ernest code found `Supervisor`'s children joining with two closures each, `stop = fn() = kill(me)` and `watch = fn(wrap) = monitor(me, wrap)`, and asked for `kill` and `monitor` on a `Process`, which has one type for every process. Decided with the user, they keep the address, each principle weighed.

Killing is authority, and an address is the authority over a process (§6.5). `Process.live()` answers the `Process` of every process the runtime started, which is safe because a `Process` grants nothing (*A Process's Identity Is a `Process`*); a `kill` on one would let any code end any process it found there, by power no code handed it (principle 3). Monitoring a `Process` was refused in *The Live Processes Are a Library Function* as a second `monitor` (principle 2). The closures are the design *The `Supervisor`'s Shape* recorded, standing for an address whose mailbox type the supervisor cannot name: a function that captures a value is how Ernest holds a value whose type it cannot write, and a reader who knows the language reads them so (principle 1).

A function that forgets an address's mailbox type, `Address(m)` to `Address(Never)`, was weighed. It is sound, since nothing can be sent to an `Address(Never)` and it can still be killed and monitored, and it would let the supervisor hold one address a child for two closures. It is a concept more for one module's convenience (principle 5), where closures already say it, and today it is written as a `via` over a function from `Never` whose body can never run, one that recurses or faults, a trick no reader predicts (principle 1). Nothing of the grammar changes either way (principle 4).

*Superseded in part 2026-10-02 by "MVP 2.99b's Questions, One by One": `monitor` takes a `Process`, §6.5's address being the permission to send; `kill` keeps the address.*

## No Limit Is `Unlimited`, 2026-09-30

A reader of our Ernest code found `Supervisor`'s child restarting under `RestartLimit(restarts = 1, within = 0)`, named `unlimited` privately, a limit of no limit that reads as one restart. §6.9 made it so in one sentence, "A time of 0 sets no limit". Reading its two users found them apart. A group checked the time first and restarted for good, as §6.9 said. `restarting` counted restarts first, so that `RestartLimit(restarts = 0, within = 0)` never restarted, against it. The stdlib's `restarts = 1` was the count that made the two agree.

Decided with the user, no limit has its name: `type RestartLimit = RestartLimit(restarts : Int, within : Int) | Unlimited`, and `restarting(Unlimited, f)` runs `f` again after every fault. The sentence of the time of 0 goes, and a time below 1 is 1, so that a window of no time is not a second, unwritten spelling of no limit (principle 2). The use site says what it does (principles 1 and 3). The price is a constructor, and what goes is a special sentence, the private binding, and the group's branch on its time (principle 5); the grammar is untouched (principle 4). Fixing `restarting` alone was the other way, and it kept a count beside a time of 0 that means nothing there.

The runtime keeps no time of a restart under `Unlimited`, and a group under it counts nothing. `restart_unlimited_test` holds both halves: a process under `Unlimited` restarts through fifty faults, and one under a time of 0 that faults at once ends, its window a millisecond. Before, it restarted for good.

## `Other` Says the Host's Words, 2026-09-30

A reader of our Ernest code found the same `errorText` in `filesync` and `webserver`, a third table in the shell, and none of them able to word `Other`, which held the host's code for a reason, `eaddrinuse`. Decided with the user, the tables stay, and `Other` changes.

The words for an error are the program's. A library function that worded every `Io.Error` would choose a wording for every program, which E.0 rule 3 refuses as it refuses a format or a locale, and the guide's §2.9 teaches the `match` in the program's own words since the newcomer's N7 (2026-09-29). Two examples with the same seven lines are two programs that chose alike.

`Other(text)` held two kinds of text: a sentence of the runtime's for a case `Io.Error` does not name, `"not a regular file"`, and for every other reason the host's term as printed, a code a program can only pass on. The host has words for its codes, `file:format_error/1` and `inet:format_error/1`, documented, "address already in use" for `eaddrinuse` and "no space left on device" for `enospc`. `Other` now holds them, and a program's `Other(text) -> text` shows words with no change of its own. A reason with no description keeps its printed form: the host answers "unknown POSIX error" for an atom it does not know and raises for a term that is no atom, so the runtime asks only for an atom and takes no answer that begins so. `Other("exists")` stays the runtime's own, since `Fs.create` and `Fs.makeDir` promise it and a program matches on it.

## A Group Restarts Whole, 2026-09-30

A reader of our Ernest code found `examples/services.ern` waiting 500 milliseconds after corrupting its store, since nothing told a program that its supervisor's restart had finished; the guide's `pair.ern` waited the same way. Under E.22 a child's fault restarted the child at once, while the siblings its strategy restarts were asked to and restarted at their next wait (*A Sibling Restarts at Its Next Wait*). The group came back a piece at a time, with no moment at which it was whole, where E.22's first sentence says a supervisor restarts its children together. An Erlang reader expects the group whole after the restart, as OTP's supervisor makes it before it does anything else (principle 1). The sleep hid it, and an example may not route around a gap.

Decided with the user, the child that faulted runs again once each sibling its fault restarts has restarted or ended. The supervisor holds its answer; a sibling that takes its asked restart tells the supervisor so, and the watcher tells it of a child that ended, so that one gone first leaves nothing waiting. A call to the faulted child after its fault is then answered by the group restarted whole, and every call made after that answer finds each sibling restarted too. Nothing is added that a program calls (principle 5), and the end of a restart shows through the call a program already makes (principle 3).

A `Supervisor.settle(sup, ms)` that answered once no restart was pending was weighed. It is a function more, and it races on its own: called before the fault has reached the supervisor, it answers at once, so a program would first need a call that proves the fault happened, the call this rule already answers.

The price is named. A sibling that computes when the fault comes delays the faulted child until it next waits, and one that never waits keeps the faulted child from running again, where before only the sibling missed its restart. A call waiting on the faulted child when it faults still ends (§6.6), so `services.ern` asks its store again when a call ends, as the guide teaches a client to.

## `closeListener` Names What It Closes, 2026-09-30

## A Restart Begins Afresh, 2026-09-30

Language feedback 68, of 2026-09-28. A restart ran `f()` again in the same process with its address and its mailbox, so the new run took what the old one had left: requests whose callers §6.6 had already told the call had ended, so that an ended call could still be carried out, and done twice when the caller asked again; the old run's alarms, `Down`s and terminal events, wrapped in the mailbox type, which the new run could not tell from its own; and plain sends. A reader who knows a restart begins `f()` afresh predicts an empty mailbox (principle 1), and a message from a run that no longer exists acts unseen (principle 3). *Names, Restarts and Supervision* kept the address, as Akka Typed does, and the mailbox came with it unweighed.

Decided with the user, a restart is a new run in all but its address. The mailbox is emptied, and what the old run asked the runtime for is canceled, its alarms, its monitors and its subscriptions, with the deliveries of them already under way, so that a call a restart ended was not done, and asking again is safe. A message that arrives while the process restarts is dropped or taken by the new run, since a send in flight cannot be caught in either, and so the request of an ended call still on its way at the restart can reach the new run; a plain send is lost at a restart as Erlang loses one to a process that dies, and a sender that must know uses a call, which tells it.

Two other shapes were weighed. Keeping the mailbox and ending only the call whose request was being handled keeps a call honest, but it needs the mailbox searched at every restart for each waiting call's reply, and the alarms and `Down`s already delivered stay, which the new run still cannot tell from its own. Keeping the rule and stating it makes a double effect the rule, which no program can guard against, since it cannot tell an old request from a new one.

The price is named. The supervisor restarted in place found its watcher through a message it had left in its own mailbox, so `Supervisor.group` now spawns the watcher when it is called and keeps it in the function it answers, and its type gains the effect; one process runs a group's function, and a second faults. A plain send that arrives just before a restart is lost.

## Names Are the First Documentation, 2026-09-30

Most of the toolchain's variables are a letter or two: in `erl/*/src` alone `T`, `N`, `D`, `E`, `A`, `R`, `V`, `X`, `P`, `C` and `L` each stand for something several hundred times, and not always for the same thing. Some function names are as short: the parser's `w/1`, the boundary's `chk`. So are records, which a reader meets in every clause that matches one: the pretty printer's `#p{}`, the formatter's `#ctx{}` and `#cur{}`, the emitter's `#cx{}` beside the formatter's `#ctx{}` for the same idea, the type engine's `#st{}` and `#tv{}`, and two unrelated `#env{}`, the checker's and the shell's. The Ernest sources have the same fault in a type's constructors: the shell's `K(Terminal.Event)` is a key. The meaning of such a name is in its writer's head, so every other reader rebuilds it from the code around it, which is the work a name exists to save. Code is read far more often than it is written, and mostly by someone other than its writer. A name that says what its value is documents the code where no comment is kept up to date, and a name used for one concept everywhere lets a reader carry what one module taught into the next. A long name costs only where it becomes very long. Longer names make the code longer, and that is accepted: the line stays at 100 characters in Erlang and in Ernest (`style.md`, §11.6), which leaves them room.

The pass waits until after the release so that it does not mix with the release's fixes, and it covers the Ernest sources too, since they are read as examples of the language. It was planned in MVP 2.99d, what the release review left, and that milestone became MVP 2.99b's first item the same day: the pass touches nearly every file, and the operations records that follow it rewrite `set.ern` and add to the checker and the emitter, so renaming first means that work is written once, in the agreed names, and a rename's commits never meet a feature's. The compiler guards the renaming: with `-Werror` a name renamed on one side only is an unbound or an unused variable, and a record field misspelled does not compile. What it cannot catch, a name that compiles and says the wrong thing, is why each area's commit is read back. The rules went into `style.md` at once, so that the code written before the pass keeps them and does not add to it. Consistency also needs a list: a glossary of the recurring names comes first in the pass, in `style.md`, and the renaming follows it area by area. The exported names of the standard library are the report's, so the pass renames them only where the report changes first. The report is the glossary's authority too: it names the language's concepts, so a code name for one of them follows the report's, and each place where the two differ, or where the report's name seems wrong for the code, is a question for the user, since a rename there changes what the report teaches.

## The Release Review's Questions, 2026-09-30

The review's questions, decided with the user one at a time before the tag.

**`Io.show` through a type variable (R-1).** A generic function shows an abstract type's value by its representation, `Seed(42)` where `Io.show` at the type writes `<abstract>`, and E.1 said so while §4.4 promised that another module does not see the constructors. What leaks is text: no module can build the value or match it by it. The fix is decided (*`Io.show` Follows Its Type*) and needs the hidden argument that the operations' decision brings, weeks after the release, and the runtime cannot close the leak alone, since it cannot tell an abstract type's value from any other tuple. Holding the release for it was weighed and left. The release ships with the behavior stated where the abstraction is: §4.4 says that through a type variable a value of an abstract type is written by its representation, pointing to E.1, so that a reader of §4.4 is not surprised (principle 1), and MVP 2.99b's item 13 removes the sentence when it closes the leak.

**A foreign function's type variables (R-2).** §4.7 promises that a value of another shape than the declared one faults at the boundary, and §8.4 settled a result variable that no parameter names, which matches no value. A variable a parameter names matched any value, unsaid: `foreign fn weird(x : a) : a` answering `2` for `weird([1, 2])` reached the program as a `List(Int)`, which faulted later, elsewhere, in the host's words, and so did an argument foreign code called a function with at such a variable. Refusing the declarations would refuse ordinary shims, Appendix D's `rawLookup` among them. The wrapper cannot check, since it is generic and only the caller knows the type, and a check at each call site would miss a foreign function passed as a value into generic code, a partial fix. The whole fix is item 13's: a foreign function takes its caller's description of each variable and checks there, at the cost of a description passed and a check the size of the value, as for a concrete type. Until then §8.4 says what the boundary does (principle 1); trusting foreign code at a variable for good was weighed and left, since it would give up the boundary's promise for a cost that fits "a fraction of the call".

**`Prelude.` past a member of the module's own (R-3).** A dotted name `T.name` is the module's own member where its type `T` declares one, and the namespace `T`'s name otherwise. The build did not follow the second half: it left a module `T` out of a source's dependencies wherever the source declared a type `T`, so `Stack.other` was an unknown name beside a local type `Stack` without that member. It now leaves out only a reference to a member the type declares. Where a member does hide a namespace's name, `Prelude.List.size` reached the standard library's past it and nothing reached `Io.println` past a member `Io.println`, since `Io` is no prelude namespace: a line between two standard library modules, both always in scope and neither renamable by the program, that a reader cannot predict (principle 1). Its reason was that `Prelude.Io.println` would be a second way to write `Io.println`, and §4.2 has since allowed `Prelude.` only where the module's own declaration hides the name, so that it is never a second way (principle 2). `Prelude.T.name` now reaches every namespace of the prelude or the standard library, past the module's own member only. A module of the program's own stays out of its reach: the program named both, and renaming one is its way out. Keeping the line was weighed and left, and so was removing `Prelude.T.name`, which would have put `List.size` out of reach again. §4.2 no longer calls `List.size` the prelude's.

**`as` and `or` in a pattern (R-5).** §5.10 said that `as` binds loosest, and Appendix A, which rules, has `or` between a clause's whole patterns and `as` inside one, so `Some(1) or Some(2) as x` binds `x` in the second alternative alone and is refused. What it asks for is written already, `Some(1) as x or Some(2) as x`, each alternative naming the value. Parenthesized patterns, or an `or` inside a pattern, would be a second way to write it (principle 2), and were left. §5.10 now says what the grammar does, and the refusal's help line shows the form that works.

**E.0 rule 4 and the vocabulary (R-6).** Rule 4 refused a function that is one call of another or a pipe of two, above rules 1 to 3, and kept four; the listing held more, by the log's own reading of a composition: `Map.contains` and `String.contains` are `isSome` of `get` and `indexOf`, `List.any` of `find`, `Set.union` one fold over `put`, `Map.merge` a `mergeWith`, `Map.keys` a `map` over `toList`, and `Io.println` a `print`. Most of them are the vocabulary, shape rule 2's container operations and rule 2's words, which exist so that a reader guesses a name in every module that has the operation (principle 1), and a word that composes two others is still the word guessed. The report never said which of the two wins. The vocabulary does: rule 4 refuses a composition outside it, rule 2 names a set's words, `union`, `intersection`, `difference` and `isSubset`, and a map's, `keys`, `values` and `merge`, and the kept list is `Io.debug`, `Io.println`, `Io.printlnError`, `Optional.isNone` and `Either.isRight`, `String.trim` being text's word. Applying rule 4 as written would have taken the first words a reader reaches for from every module, and a longer list of exceptions would have said which without saying why. Nothing in the library changed.

**A pipe into a construction (R-12).** §5.7 fills a call and applies any other operand, and did not say which a construction is; the toolchain refused `x |> Some(2)` as a callee that is no function and `x |> W(b = 2)` as a missing field. Appendix A decides, and so this was no question for the user: a constructor followed by its argument is consumed in `QName`, a value and no call. §5.7 now says that the pipe applies a construction and never fills it, `x |> Some` being `Some(x)`, and the checker refuses a construction on a pipe's right in those words, since a construction is always of its type and never a function.

**A bitstring literal that does not fit (R-13).** §5.11 made a violation the compiler can see a compile-time error and one that depends on a dynamic size a fault, and then made a value that does not fit its width a fault, "a literal included": `<<1:size(4)>>` was refused and `<<-1>>`, `<<256>>` and `<<300:size(8)>>` compiled and faulted, `<<-1>>` having been kept so on purpose, as one value like any other. The report's own test was applied to one violation and not to the other, and `<<-1>>`, the likeliest slip in an unsigned byte, surprised a writer who had just seen the other refused (principle 1). The test now holds for both: a numeric literal, negated or not, that does not fit a segment of constant width is a compile-time error, in a construction and in a pattern, where it would never match, and a computed value faults at construction or fails to match, as a dynamic size does. Keeping the fault was weighed and left. The message names the segment's range, not the literal, which the span marks: the checker writes a `Float` in the host's form, `7.0e4`, and not as the program wrote it.

**`Foreign` and a foreign type's equality (R-21).** `Foreign` has no `==` and a `foreign type` has the runtime's exact equality, two rules for values Ernest does not inspect. They stay two. `Foreign.from` makes a `Foreign` of any value, a function and an address among them, so its equality would compare what §3.10 refuses (*What a Foreign Function's Variables Carry*); a foreign type's values are made by foreign code alone, a handle whose identity is its meaning, and its parameters carry the equality they need (*A Foreign Type States the Equality It Needs*). Each rule is stated where its type is, and the report is unchanged.

**`fn f` beside `let f = fn` (R-22).** Both name a function, and they differ in that a `let` does not see its own name, so a lambda it binds cannot call itself. They stay both: `fn` declares a function, named, of fixed arity and recursive, and `let` binds a value, of which a lambda is one among `compose(g, h)` and `List.map`, and the difference is §4.6's general rule and no special one. Refusing a `let` whose initializer is a lambda would key a rule on the right-hand side's syntax and take from the shell and the guide the plainest way to show a function as a value; principle 2 is about one operation spelled two ways, and binding a value and declaring a recursive function are two operations. §4.6 now says that a function that calls itself is declared with `fn`.

**The inferred restrictions (R-23).** §3.9 infers equality, process-only and not-reply-carrying and never lets them be written, so a signature in the source does not show them, and a printed type shows two: `a=` and `a!`. A process-only effect variable prints unmarked; alone in a type it prints only because it is process-only, but one a callback's type shares prints as `List.map`'s does, and the restriction appears first in the message that refuses a pure call. The release keeps the rule as §3.9 and §11.5 state it. How a printed type marks every restriction, this one among them, and whether a restriction may be written in an annotation, a change to the grammar and a second way beside inference, is decided in MVP 2.99b's item 4, beside the ordering restriction's mark and item 13's shown one. Making the marks writable before the tag was weighed and left, since it would change the grammar and every signature on the eve of the release.

**`via` runs its function in the sender (R-24).** A send through `via(f, addr)` applies `f` in the sender, and a fault in it is the target's. It stays so, for the reasons *`via` Is a Value* gives: a process per adapted address leaked one per alarm and lost a faulting wrap's message silently; running `f` in the target would need a mailbox of the runtime's own that runs code as it takes a message, refused for receive guards; and a fault the sender's would let any program's wrap bring down the clock. `f` is pure by its type, so what runs in the sender costs it time and does nothing else. The report is unchanged.

**`Os.start`'s milliseconds (R-25).** Shape rule 8 reads a system function's milliseconds as how long the call waits, and `Os.start`'s are that and then its program's life: when they pass, the program is killed and its `read` answers `Left(Timeout)`, as E.23 said. The one time bounds the whole conversation with the program, which is why `Os.read` takes none, and it is what `Os.run`'s time already is. It stays, and rule 8 now says it. A time per read, with the lifetime left to the caller's alarm and `kill`, was weighed and left: three signatures and the program's process changed on the eve of the release, and a program could outlive every read meant to bound it. A lifetime field in `Command` would say twice what `Os.run`'s time says once.

**A local helper over an operator (R-26).** `fn add(a, b) = a + b` in a block is refused, though the block calls it at `Int`: an operator is resolved when its definition is inferred and before it is generalized (§4.8), and a local `fn` is a definition of its own, generalized before the block's later calls are read. The rule stays, and the helper says its type, as the error asks. Resolving such an operator with the enclosing definition, and then not generalizing the helper, was weighed and left: whether a local function is generic would depend on whether its body uses an operator, which nothing in the declaration shows (principle 1). §4.8 did not name a lambda a block `let` binds, which the checker treats as a local `fn`, since §4.6 generalizes it so; it now does.

**The built-in operators as shims (R-27).** §9.6 declares each built-in operator with itself, `fn Int.+(a, b) = a + b`, and says the body names the runtime's operation and is no recursive call, and the `compare`s written with `<` the same; the checker carries the case. On 2026-09-29 shims were left as a second form beside the members a user's type declares (*A Member Is Written `T.name`*). That verdict is reversed. The operation is the host's alone, which is what E.0 rule 1 and the repository's rule for `foreign` say a shim is for, as `String.toUpper` is one; a user's operator is Ernest and a built-in's the host's, two kinds and not two ways to write one; and the present form is a shim in disguise, a body that reads as a call of itself and is not, which two exceptions explain (principle 1). The operators, their `negate` and the `compare`s become `foreign fn`s in MVP 2.99b's item 14, over the host's operation or a helper of the runtime's where the host has none of the shape, and the exceptions go. Not before the tag: it touches the checker, the standard library and every operator's page. *Reversed again 2026-10-03, once built, by "The Operators Stay Ernest".*

**`Fs.removeAll` walks by open directories (C1-3).** `removeAll` was Ernest over `readLink`, `stat`, `list` and `remove`, and between checking that a path was no link and listing it, another process that could write the tree could put a link in the directory's place, and `removeAll` emptied the link's target, a directory the program never named, with the program's permissions: Rust's CVE-2022-21658. No check in Ernest closes it, since each check and the use of the path after it race. The walk now opens each directory refusing a link and lists and removes inside it by its handle, `openat` and `unlinkat`, so that a name swapped under it is never followed; Erlang's `file` has no operation relative to an open directory, so it is the host's work (E.0 rule 1), the second job of the runtime's helper, `ern_exec remove`. `removeAll` is one request, and waits its milliseconds once for the whole removal where each step waited them before. Stating the race and fixing it after the release was weighed and left: it destroys data, the pattern is published, and the fix is contained.

**`Foreign.from` past the proxy (C1-4).** An address in a foreign function's argument crosses behind a proxy that checks what foreign code sends it, and a function behind a check of its arguments, by the argument's declared type; `Foreign.from` gives foreign code a value as the runtime holds it, and a parameter of type `Foreign` carries no type to expose it by, so an address in it crossed bare. The runtime cannot expose it where it crosses, since the type is gone and an address and a `Process` are one term there, and `Foreign.from` knows its value's type only where its caller's type is concrete; a check there alone would protect a call by where it is written. The whole fix is R-2's: with MVP 2.99b's item 13, `Foreign.from` takes its caller's description and exposes at it. Until then §8.4 says what crosses. The boundary catches mistakes and is no sandbox, since foreign code runs with the runtime's powers, so what the gap loses is where a wrong message is caught.

**Who owns a socket (C1-2).** A socket lived until `Tcp.close`, so one whose handler faulted before closing it kept its descriptor and its process until the program ended, one for each fault, where a running program is killed when the process that started it dies (E.23). The same rule for the opener alone would not help, since the process that accepts lives for the whole run and hands each socket to a handler. A socket now has an owner, as `gen_tcp`'s controlling process: the process that opened it, killed with it when it dies, and `Tcp.give(socket, process)` makes another the owner, so an acceptor gives each socket to its handler and a handler that faults takes its connection with it. A socket given to a process that has ended is killed at once, and a restart is no death. Keeping E.18 and having every server watch its handlers was weighed and left, the same bookkeeping in every server; a change of contract is cheapest before the first release. A listener keeps its rule, one to a server and as long-lived as it. At the prompt an input's process ends with the input, so a socket or a program it opens ends with it unless given on; whether the session owns them instead is MVP 3.3's decision.

**An address retyped by foreign code (C1-6).** An address that crosses into foreign code goes out behind a proxy that checks what foreign code sends, and the runtime undid the proxy when foreign code gave the address back, whatever type it came back at: an `Address(Int)` returned as an `Address(String)` took the program's `String`s to a process of `Int` unchecked. The proxy is now undone only at the type it went out at; at another the address stays foreign, so what is sent through it meets the proxy's check against the process's own type, which faults the process on a mismatch as any bad message from foreign code does. It cannot fault a correct program, which gets its own address back at its own type and at worst pays a hop for a retyped one. Faulting the return instead was weighed and left: it asks whether two type descriptions are one type, generic and recursive ones among them, and a wrong answer would fault a correct program.

**`:load` of a compiled module (C3-9).** `ern run` refuses a module compiled against another interface of a module it uses or of the standard library, and a file at a module's path that holds another; `:load` of a module with no source took its compiled form without either check, and the module faulted later where the two differed. §11.2 was silent, and this needed no choice: the shell refuses as the runner does, in its words, and loads nothing.

**An alarm is not canceled (N-C1, N-B4).** A coordinator that set a deadline per job and did not match the deadlines of jobs done early grew its mailbox by one message a job. A cancel would not remove the need to drop a stale deadline: an alarm that fires as it is canceled has delivered already, and no cancel takes a delivered message back, so a process matches stale deadlines with a cancel or without one, and with one it is rarer and so forgotten. What a cancel adds is freeing the clock's pending alarm early, which without it lasts until the alarm fires, at the price of `Clock.alarm` answering a handle at every call. E.15 stays; the guide's §5.5 now says that an alarm cannot be canceled and shows a deadline carrying its job's id, matched and dropped once the job is done.

**The order of a `Down` (N-B5).** Erlang delivers a `DOWN` from the dying process itself, after every message it sent; Ernest's runtime delivers a `Down`, applying the wrap as it delivers, so it is another sender's message and §6.4 promises no order with the ended process's own. §6.9 now says so, since an Erlang programmer assumes the opposite, and names the ordered way to a result: the callee's own answer to a call, which reaches the caller before the callee's end does. Erlang's order would take the receiving process turning the host's `DOWN` into `wrap(d)` in its `receive`, a mailbox of the runtime's own, refused before for receive guards and for `via`.

**`type Word = String` (N-C3).** The newcomer wrote it for an alias and got a type whose one value is a nullary constructor named `String`, and met it first as "expected Word, found String". Ernest has no type aliases: an alias is a second name for one type (principle 2), and the case that asks for one in Elm, a record, is a named-field constructor here; a wrapper, `type Word = Word(String)`, is the way, and a type of its own. Refusing a nullary constructor named as a type would forbid an enumeration of type names, `type Kind = Int | Float | String`. So the mistake is told where it shows: a mismatch between a type whose one constructor is nullary and the type that constructor is named as gains a help line saying there are no aliases and what a wrapper is, and the guide's §2.3 says it.

**The line `C-c` abandons (C3-23).** `C-c` on a line being typed abandons it: it stays in the transcript, runs nothing, and ends an input that runs. The shell keeps it in the history, to recall and mend, and §11.2 did not say so. It stays and §11.2 says it: the usual reason to abandon a long input is a mistake seen in it, and the history gives it back. Dropping it, as Bash and GNU Readline do, was weighed and left, since an abandoned long input would be lost.

## The Principles Review, 2026-09-30

After the first release the question was whether the language had grown by exceptions: a `receive` guard that is the BEAM's, E.0's shape rules with lists of functions outside them, and thousands of decisions each argued at the time and never read as a set. The repository agreed. The principles reader's count of concepts went from 79 at the full review of 2026-09-28 to 89 at the release review two days later; that reader's list of rules that buy little stands in `findings.md` unworked, parked for the next full review; and the log holds about five hundred entries in three weeks that no reader reads, by design, since a reader is given nothing that argues for the rules.

The two examples show that what is missing is seldom a verdict and usually a sentence. The guard was argued on all five principles (*Receive Guards Are Guard Expressions*) and is remembered as pragmatic, and both hold, because §0 says nothing about when the host's visible semantics are the language's; E.0 rule 1 says it for the library alone. With such a sentence the guard, message order, unbounded `Int`, `after`, monitors and the bitstring size are one rule's instances; without it, six pragmatic calls. Shape rule 8 states a rule, then three kinds and twelve functions outside it: a rule with a growing list is stated at the wrong level, and restated at the right one the list falls out, leaving at most the one exception the report keeps with its reason here. So the review's product is sentences that make families of exceptions into instances, and verdicts that remove a rule where the smallest program that shows it reads better without it. A stated exception is visible and no wart; a list of them is.

The shape follows. Not the full review, which does not run while `findings.md` is open and is the wrong size after a release, but four readers in five sessions. P, the principles reader, over the report and what MVP 2.99b proposes, told that it is proposed. K, the cold reader, over the report, since a rule another contradicts and a list of exceptions inside a rule are what inconsistent means, and in Appendix E each function against E.0 and each rule against its functions, which is where the shape rules and the library have drifted. W, a new reader of the guide, since a rule the guide must explain, warn about or route around is evidence about the rule, which the guide's truth check, U, cannot give. And L, a new reader of the log, the one reader that sees the arguments, since a principle cited after the fact shows only there, and a family of decisions that one sentence would decide is visible only in the set. Peers are left out as unbuilt. The principles themselves are in scope, and that is the point: a principle changes where the readers show it did not decide, by a sentence that decides, and never to admit a rule the rest of §0 refuses. The sentences are decided before the families, since they are the measure. A decided family is closed and not reopened before 1.0 but by a program that shows a new case: much of the unease came from decisions taken and never closed, and the closing is part of the product.

It runs after MVP 2.99b's item 3 and before its item 4, which adds an inferred restriction with a hidden argument, the largest addition to the type system since the release, and should be judged under principles that have just been sharpened; the operations decision moves back by the review's week, which is the right order. It runs now rather than at MVP 3.9 since every milestone until then builds on the released shape, and the price of removing a rule rises with each program written against it. Not taken: a full review, for its size; and leaving R's list to the next full review, which would have parked it through the milestones that build on what it questions. With three reviews, each document is named for what it is: `review.md` became `release_review.md` the same day.
