## A Pure Function Stands for One With a Mailbox, 2026-09-26

The cold read's 1.1. The report said an effect variable binds to a mailbox type or to pure, and nothing about pure meeting a concrete mailbox, and the checker unified plainly while generalization turned a lone effect variable into pure. So `Up(next = fn(n) = Unit)` was accepted and `Up(next = done)`, with `fn done(n : Int) -> Unit = Unit` above, was refused: whether a program compiled depended on whether a function had a name (principle 3), and a reader from any language with inferred effects expects a function that does nothing to fit anywhere (principle 1). Plain unification throughout, which would refuse the lambda as well and `spawn(Local, fn() = Unit)` with it, was the other consistent reading and was rejected. Subeffecting was taken in the form Koka gives it: an expression whose type is a pure function type takes a fresh effect variable in its outermost arrow, which the context binds, so no subtyping enters the checker, and the order of two arguments that share an effect does not matter. Only the outermost arrow opens; a pure function type inside another, a parameter's or a field's, keeps its effect, since opening there would let a function that sends reach a place that promised pure. The converse stays an error: a function with a mailbox type never stands where a pure one is expected. §11.5 already printed a lone effect variable as pure in a scheme, and now does in every printed type, so an opened type reads as it did. The guide's §3.6, which taught that a pure callback cannot be spawned, now teaches that it can, its mailbox being what the address is used as.

*Reason restated 2026-10-01: a pure function standing for one with a mailbox stands as §6.2 and §3.9 state it; the reader of a language with inferred effects was a neighbor's, which no longer decides.*

## Names, Restarts and Supervision, 2026-09-26

Feedback item 53, a direction and not yet a decision; the plan's MVP 2.65 step 5 holds the questions it leaves, and nothing is built before they are decided.

*No Registry* (2026-09-13) left two things to every program: threading a service's address from `main` to every function that sends to it, and, once services restart, a supervisor that is also a name service, since a restarted child has a new address and whoever held the old one must be sent it. Each program writes the same forwarding and the same threading, a little differently. That is the churn *Ambient Sys, Five Principles* removed for the runtime's own processes: `Sys.stdout` is a named, typed address that nobody hands on, and it is visible because its name is at the use site. A program cannot declare one of its own. Against principle 2 the hand-written variants are many ways to do one job, and against principle 1 a reader must read each to know which variant it is.

The knot is Erlang's identity model, kept when Erlang's registry was refused: an address names one execution of a function, so a restart makes a new address, and a name bridges the gap. The cousins were surveyed on this day. Outside the BEAM, a restart keeps the reference: Akka Typed and Pekko restart a behavior inside the same actor, its mailbox kept and the message being handled lost; Proto.Actor, Ray and Spritely Goblins keep it too; Orleans and Akka's sharding keep a logical key instead. Every BEAM language documents the gap between a death and a registration again: a call exits with `noproc` in Erlang, `send` panics in Gleam, and Elixir's `Registry` may return a process already dead. Where names survive, they are typed: Akka's `ServiceKey[T]`, Swift's reception keys, Gleam's `Name(message)` since its 1.0 of 2025, whose documentation gives the threading as its reason, and Unison's `ServiceName a b`. The registries keyed by strings, Erlang's, Lunatic's, Cloud Haskell's and Ray's, return the type the caller asserts. The capability literature, Miller's *Robust Composition* above all, refuses a mutable global namespace and admits a fixed top-level binding that designates something. Akka Typed moved supervision from the parent to a wrapper the child declares, stopping by default, since a parent's verdict cost a round trip and restart loops went unnoticed; Orleans has no supervision and is criticized for grains that run on with inconsistent state. A restart limit is universal; strategies across siblings are the BEAM's alone.

The direction. A process spawned through `restarting(f)` keeps its address and its mailbox across a fault and runs `f` again from its start; a fault is not catchable (§7.3), so the wrapper is the runtime's, and `spawn` stays one. A service is a top-level binding, `export let service : Address(M) = spawn(Local, restarting(...))`: typed by its declaration, reached by its name as `Sys.stdout` is (principle 3), and granted by `export`, so the capability discipline holds with module visibility as the permission. Nothing re-registers, since the address never changes. What `restarting` leaves out, a group of children, strategies across them and the order they stop in, is a library's, and whether the standard library has one is weighed again against E.0 rule 3, since every program would otherwise write it. The cost is one prelude function and one revoked rule, §4.6's pure initializer (principle 5).

This revises two entries. *No Registry* keeps its verdict, no table from names to addresses, and loses "threaded arguments from `main` for the rest". *Against OTP as a Language Feature* loses its first cost, no canonical supervisor, if the standard library gains one, and gains one mechanism in the language, the restart that keeps an address.

*Superseded in part 2026-09-30 by "A Restart Begins Afresh": a restart keeps the address and empties the mailbox.*

## A Call Ends When Its Callee Faults, 2026-09-26

The first question *Names, Restarts and Supervision* left. A fault loses the message being handled, and a restart resets the loop's state, so every `Reply` the process held is lost with it: the one in the current message, and any it kept, a queue of waiting callers or a lock's waiters. What was open is what the caller learns. Until now, nothing: `Address.callForever` is a bare wait on the reply's alias, so a caller whose callee died waited until a deadlock of the whole program, and `Address.call` until its time ran out. Death at least let a caller that thought of it monitor the callee; a process that restarts never dies, so restart in place would have made a silent wait an unobservable one. Principle 3 refuses a failure the one party waiting on it cannot see.

Delivering the lost message again was refused: a message that faulted the process usually faults it again, so the process loops to its restart limit, and it would rescue the current message and not the replies held in the state. Akka and Proto.Actor refuse it for the first reason. Leaving it as it was, Akka's `ask` timing out, was refused on principle 3.

Taken: when the process a call's request was sent to faults or dies before it answers, `Address.call` returns `None` at once and `Address.callForever` faults the caller with the same cause. It is what `gen_server:call` does through its monitor, and what §6.7 already says of `remote`, a fault faulting the caller with the same cause. It needs no redelivery and no record of who holds a `Reply`: the runtime notes each pending call against the process it was sent to. It closes the wait on a dead callee as well as on a restarted one.

Its costs, accepted. A call whose request was still queued, not lost, ends too; the request runs after the restart and its answer is discarded as late, which is the ambiguity `None` already has after a timeout. A request handed on to a second process under §6.6 is watched only at the first, so a fault in the second leaves the caller to its time limit. And `callForever` to a service that faults faults its caller: a caller that must outlive the service uses `Address.call` with a limit, and now learns at once. A message without a `Reply` is lost silently, as in every system surveyed; the fault itself is made visible by the third question.

*Superseded in part 2026-09-30 by "A Restart Begins Afresh": the mailbox is emptied at a restart, so a call the restart ended is not carried out after it.*

## A Restart Has a Limit and No Strategy, 2026-09-26

The second question *Names, Restarts and Supervision* left. A restart guarantees a known initial state, not a retry: a fault in the start itself, a missing file or a port in use, comes back at every restart, and without a limit the process spins, and floods whatever reports its faults. Every system surveyed has one: OTP one restart in five seconds by default, Elixir three, Gleam two, Akka `withLimit`, Proto.Actor a count in a window, Ray `max_restarts` at zero. A limit the runtime chose would be a policy the program cannot see (principle 3) and a choice made for it, which E.0 rule 3 refuses in the library; so the limit is written in the call, with no default, since it is part of what the process means. It is a constructor, `Limit(restarts = 3, within = 5000)`, and not two `Int`s, for the reason E.0 rule 9 gives against a `Bool`: the call says what it means only to a reader who knows the signature. Past the limit the process dies with the last fault's cause, so the loop becomes a death its monitors see and the first question's rule ends its calls.

Only a fault restarts. `Returned` is the function choosing to stop; `Killed` must stop a restarting process, or nothing could; `ProgramEnd` ends everything. That is OTP's transient child; its permanent child, restarted after a return too, would be a second behavior of one wrapper (principle 2).

No strategy: `one_for_all` and `rest_for_one` are relations among siblings, and a wrapper around one function has none to see. Akka Typed's per-child supervision has none either, a group's failure reaching its parent through `watch`. No backoff: it is policy, it matters for outside resources, and a function that needs it waits at its own start. Both are the group's, the sixth question's `Supervisor`. Processes spawned before a fault run on, since nothing owns a process (§6.9), and the address they hold still reaches the restarted one.

## Every Fault Reaches Standard Error, 2026-09-26

The third question *Names, Restarts and Supervision* left, and feedback item 9. A program run by `ern` printed a fault only when it was the entry process's own (§11.2): a worker that divided by zero ended in silence, `main` finished, and the exit status was 0. The shell, under §11.2, prints every fault. A process that restarts never dies, so even a monitor would not see its faults, and a service could fault and restart under its limit for weeks with nothing said; restart loops that went unnoticed are what Akka Typed's stop-by-default answered. Taken: `ern` prints every fault of every process to standard error, in the shell's form, the spawn site and the cause, with `restarted` after a fault the limit allowed. Erlang's runtime logs every abnormal exit, monitored or not, and `ern` and the shell stop differing without a stated reason. `monitor` stays one message, at death (§6.9). A restart is not a death, and a second kind of message would give `monitor` two jobs (principle 2). A `Supervisor` that restarts a group, the sixth question's, restarts its children as new processes and sees each fault as a death, so it needs nothing here.

## A `Supervisor` in the Standard Library, and `fault`, 2026-09-26

The sixth question *Names, Restarts and Supervision* left, and the last. `restarting` restarts one process; a group, strategies across it and the order it stops in were left to a library, and every program would write that library again, a little differently, which is the churn the direction was taken to end. So the standard library has one, where every program looks, and not `libs/`, which is not on the load path by default.

E.0 admits a function by one of four rules, and rule 3 is the one that can admit this: a general operation whose definition is the obvious one and in which no policy is buried. A supervisor is almost all policy, but none of it need be buried: the strategy, the group's limit and each child's are arguments without defaults, and the definition is the one OTP settled and every BEAM library copies, Gleam's among them, start in order, stop in reverse, three strategies. Rule 3 gains a sentence, that a policy the program passes as an argument is not buried. *Against OTP as a Language Feature* named no canonical supervisor as a cost; that cost is paid, and the supervisor is still a library's, not the language's.

How it restarts a group decided whether it fits the direction. Children as new processes behind forwarders need nothing from the language, but put back the knot the direction untied, inside the library: a hop on every message, and a supervised child's mailbox lost where a `restarting` one's is kept, two restarts that behave differently (principle 1). Taken instead: its children are `restarting` processes, and for a group strategy the supervisor restarts a sibling in place, its address and mailbox kept. Only the host can restart another process, so that is a shim internal to the module by the `foreign` rule, and the language gains no `restart(address)` that any holder of an address could call. (The premise was wrong in part, as *A Sibling Restarts at Its Next Wait* records: not even the host can restart another process at an arbitrary point.) The supervisor learns that a child restarted from a notice the module's wrapper sends at every start, a second from one child meaning a fault, in Ernest; `monitor` keeps its one job. `Supervisor.spawn` returns the child's typed address, and the supervisor holds its children as functions whose message types it does not see, the first form of the guide's §7.3, so children of any types share one supervisor. With service bindings the tree is a set of top-level bindings, started in dependency order. `RestForOne` means the children spawned after, and two independent children have no order and no reason to use it against each other.

The supervisor's own end, past the group's limit, found a gap: a process cannot fault on purpose, `todo` meaning unfinished, and a supervisor that gave up and returned would look to its watcher like one that finished (principle 3). `fault : (String) -> a` enters the prelude: a deliberate fault with its cause, uncatchable as every fault is, and reported as every fault is. Gleam has `panic` beside `todo`, Erlang `exit` and `error`. The risk is that it is used where `Either` belongs; E.0's rule that a partial operation returns `Optional` or `Either` governs the library, and the guide teaches `fault` for an invariant broken beyond recovery (principle 5 pays one function).

*Reason restated 2026-10-01: `Supervisor` stands by E.0 rule 3, its policy passed as an argument without a default, and its shape is Appendix E.22's stated rule ("The Reader Family's Rules"); OTP's settled definition was a neighbor's, which no longer decides. ## A Process's Identity Is a `Process`, 2026-09-26

Feedback item 24. An address had no equality and printed as `<address>`, so `:processes` showed three processes spawned by three inputs as `input:1` three times, and a program that removed a subscriber or kept state per client carried an id in its protocol beside the address it already held, two ways to say which process (principle 2). §3.10 refuses equality on an address because an adapted address holds a function, `{via, F, Target}` in the runtime.
