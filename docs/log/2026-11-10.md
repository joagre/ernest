# The decisions log, 2026-11-10

## A Compiled Module the Host Cannot Load, 2026-11-10

MVP 4.15's item 43, found by item 42's read-back. A `.erc` whose code chunk is gone, empty or zeros, every other chunk sound, was refused by `ern run` and `ern test` as `cannot load top.erc: badfile`, in the host's word, and `ern doc` wrote its page. A probe found more. `ern build` found such a module current. The shell's `:load` took it, beside its source or not, and faulted, ending with status 70. `Code.load` answered `Left(Other("… the host did not load it, badfile"))`, where E.28 says `Left(Invalid)`. Where the host held a unit of the module's name, `Code.load` faulted its caller, since `ern_code:is_held/2` took the host's digest of the bytes for granted, and `ern test` over a directory reaches the same.

**Decided with the user: the build checks its own modules' code.** Two rules were weighed. (A) Each job reads only the chunks it needs, and a load finds code the host will not load. It costs nothing, and a reader who knows Erlang predicts it: `make` keeps a damaged `.beam`. (B) The build also asks the host's loader of each `.erc` it would keep. Principle 1 decided for (B). Told by a run that a file is no compiled module, the reader who knows Ernest runs `ern build`, which §11.1 says compiles such a module again. Under (A) the build kept the file and the run refused it again, a loop no line shows the way out of; a help that said "remove it" would be a workaround in an error's text.

**The cost.** The host's own check is `erlang:prepare_loading/2`, which prepares the code and loads nothing. On the three shapes, and on a module of another name, it gave the load's answer each time. It takes about 10 ms a megabyte of compiled code: 17.5 ms over the 18 `.erc` of `build/shell` and `build/libs`, 1.8 MB, where reading one chunk of each takes 0.03 ms. That is about 13 ms for ernest-httpd's 1.3 MB, and about 30 ms for the toolchain's 3.2 MB. A `make` with nothing to do took 1.31 to 1.65 s before and 1.31 to 1.39 s after, the check inside the spread. A run pays nothing. *Lean at the Limits* refused a hold every run pays for a rare coincidence, where the alternative left an outcome the report states; here (A) left a loop.

**Decided: a job that loads no code takes only what it reads.** `ern doc` writes its page from the documentation, as the plan's paragraph recommended, since a page needs no code. A build reads a dependency's interface alone; a run then refuses the dependency by its name, and building the dependency's own tree compiles it again. `Code.hashes` answers the definitions its forms give. §11 states the rule for the jobs, and E.28 for its two functions.

**The sites.** The check is `ern_chunk:is_loadable/2`. The build asks it in `current/6`, of a module's own `.erc`. The runner answers the load's `badfile` as §11's refusal: the file the program was given as `top.erc is not a compiled module`, and another as a chunk it cannot read is, `lib/dep.erc: not a compiled module`. The runner loads every unit from its file, so it asks nothing more. `is_held/2` takes bytes whose digest the host cannot take, through `ern_chunk:md5/1`, as code it does not hold.

The shell and `Code.load` ask the check as they read each file, before the unit is placed. Both may make a unit from the file's forms where the host holds another unit of its name, and then never load the file's code; asked at the load alone, the same file would be refused on one node and loaded on another, by what the program does not see. In the shell, a form that fails it does not qualify beside its source, which is compiled, and with no source the load refuses the file before anything is installed. The check costs 3.2 ms for Markdown's 280 KB, of a `Code.load` of 36 to 37 ms. The shell's help for an unknown name asks it in place of the digest, so that it proposes no `:load` the load refuses, as item 42 decided for unreadable atoms; a host's `.beam` at a module's path is no longer proposed either.

**The host's report.** The check writes the emulator's report of the code it refused, as a load does. Item 42's filter drops it, but only a job that started the runtime installed the filter, and the build wrote the report. The filter states §11's rule for every job, so every job installs it, in `job/6`.

**Found: a load past the host's atoms.** A probe gave a module of 20,000 new atoms to a host whose limit was 20,000 and which held 10,269. The host ended, `no more index entries in atom_tab`, status 1, whether it loaded the code or only checked it. §11.2 says a load that would pass one of the host's limits fails as one the node cannot load; for atoms the host ends instead, at a run's load, the shell's, `Code.load`'s, and now at the build's check. *Lean at the Limits* decides the shape: where the host fails worse, the report states it. It is the plan's item 44. The check brings it to the path where `Code.load` and the shell make a unit from a file's forms, whose names the chunk reader bounds, but a load of the same file under a name the node does not hold met it already.

**The tests**, written before the fix, each failing on the code before it. `ern_cli_tests`'s `code_not_loadable_test` gives the three shapes to `ern run`, `ern test` and `ern doc`, and `code_not_loadable_build_test` holds the build's two paths, the run's refusal of the dependency and nothing of the host's written; `cannot_load_named_test` holds the new line. `held_without_code_test` holds `is_held/2`. `ern_code_load_tests`'s `code_not_loadable_test` holds `Code.load` on a fresh name and beside a held unit, and `Code.hashes`. `load_code_not_loadable_test_` holds the shell's `:load` beside the source and without it, and its help. Not covered: the shell's `:reload` and a node's start, which read a file as the shell's `:load` and the runner do.
