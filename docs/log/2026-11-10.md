# The decisions log, 2026-11-10

## A Compiled Module the Host Cannot Load, 2026-11-10

MVP 4.15's item 43, found by item 42's read-back. A `.erc` whose code chunk is gone, empty or zeros, every other chunk sound, was refused by `ern run` and `ern test` as `cannot load top.erc: badfile`, in the host's word, and `ern doc` wrote its page. A probe found more. `ern build` found such a module current. The shell's `:load` took it, beside its source or not, and faulted, ending with status 70. `Code.load` answered `Left(Other("… the host did not load it, badfile"))`, where E.28 says `Left(Invalid)`. Where the host held a unit of the module's name, `Code.load` faulted its caller, since `ern_code:is_held/2` took the host's digest of the bytes for granted, and `ern test` over a directory reaches the same.

**Decided with the user: the build checks its own modules' code.** Two rules were weighed. (A) Each job reads only the chunks it needs, and a load finds code the host will not load. It costs nothing, and a reader who knows Erlang predicts it: `make` keeps a damaged `.beam`. (B) The build also asks the host's loader of each `.erc` it would keep. Principle 1 decided for (B). Told by a run that a file is no compiled module, the reader who knows Ernest runs `ern build`, which §11.1 says compiles such a module again. Under (A) the build kept the file and the run refused it again, a loop no line shows the way out of; a help that said "remove it" would be a workaround in an error's text.

**The cost.** The host's own check is `erlang:prepare_loading/2`, which prepares the code and loads nothing. On the three shapes, and on a module of another name, it gave the load's answer each time. It takes about 10 ms a megabyte of compiled code: 17.5 ms over the 18 `.erc` of `build/shell` and `build/libs`, 1.8 MB, where reading one chunk of each takes 0.03 ms. That is about 13 ms for ernest-httpd's 1.3 MB, and about 30 ms for the toolchain's 3.2 MB. A `make` with nothing to do took 1.31 to 1.65 s before and 1.31 to 1.39 s after, the check inside the spread. A run pays nothing. *Lean at the Limits* refused a hold every run pays for a rare coincidence, where the alternative left an outcome the report states; here (A) left a loop.

**Decided: a job that loads no code takes only what it reads.** `ern doc` writes its page from the documentation, as the plan's paragraph recommended, since a page needs no code. A build reads a dependency's interface alone; a run then refuses the dependency by its name, and building the dependency's own tree compiles it again. `Code.hashes` answers the definitions its forms give. §11 states the rule for the jobs, and E.28 for its two functions.

**The sites.** The check is `ern_chunk:is_loadable/2`. The build asks it in `current/6`, of a module's own `.erc`. The runner answers the load's `badfile` as §11's refusal: the file the program was given as `top.erc is not a compiled module`, and another as a chunk it cannot read is, `lib/dep.erc: not a compiled module`. The runner loads every unit from its file, so it asks nothing more. `is_held/2` takes bytes whose digest the host cannot take, through `ern_chunk:md5/1`, as code it does not hold.

The shell and `Code.load` ask the check as they read each file, before the unit is placed. Both may make a unit from the file's forms where the host holds another unit of its name, and then never load the file's code; asked at the load alone, the same file would be refused on one node and loaded on another, by what the program does not see. In the shell, a form that fails it does not qualify beside its source, which is compiled, and with no source the load refuses the file before anything is installed. The check costs 3.2 ms for Markdown's 280 KB, of a `Code.load` of 36 to 37 ms. The shell's help for an unknown name asks it in place of the digest, so that it proposes no `:load` the load refuses, as item 42 decided for unreadable atoms; a host's `.beam` at a module's path is no longer proposed either.

**The host's report.** The check writes the emulator's report of the code it refused, as a load does. Item 42's filter drops it, but only a job that started the runtime installed the filter, and the build wrote the report. The filter states §11's rule for every job, so every job installs it, in `job/6`.

**Found: a load past the host's atoms.** A probe gave a module of 20,000 new atoms to a host whose limit was 20,000 and which held 10,269. The host ended, `no more index entries in atom_tab`, status 1, whether it loaded the code or only checked it. §11.2 says a load that would pass one of the host's limits fails as one the node cannot load; for atoms the host ends instead, at a run's load, the shell's, `Code.load`'s, and now at the build's check. *Lean at the Limits* decides the shape: where the host fails worse, the report states it. It is the plan's item 44. The check brings it to the path where `Code.load` and the shell make a unit from a file's forms, whose names the chunk reader bounds, but a load of the same file under a name the node does not hold met it already.

**The tests**, written before the fix, each failing on the code before it. `ern_cli_tests`'s `code_not_loadable_test` gives the three shapes to `ern run`, `ern test` and `ern doc`, and `code_not_loadable_build_test` holds the build's two paths, the run's refusal of the dependency and nothing of the host's written; `cannot_load_named_test` holds the new line. `held_without_code_test` holds `is_held/2`. `ern_code_load_tests`'s `code_not_loadable_test` holds `Code.load` on a fresh name and beside a held unit, and `Code.hashes`. `load_code_not_loadable_test_` holds the shell's `:load` beside the source and without it, and its help. Not covered: the shell's `:reload` and a node's start, which read a file as the shell's `:load` and the runner do.

**Read back.** The runner keeps its other refusal, `cannot load x.erc: reason`, for what else the host refuses of a load, said in the host's word. Only a forged `.erc` reaches it, one whose `-on_load` function fails, since the runner purges a unit's old code first and no `.erc` the build writes has an `-on_load`. The check took a word the shell used for another thing, a module of a name that `:load` could load. That is `is_unloaded_module/2` now, and the glossary's **Loadable** is the host's.

**Found: a flake.** The first `make test-full` of the item failed `ern_system_module_tests`'s `os_signal_after_an_unread_exit_test`, `Right(Unit) started` where it holds `Left(Io.Closed) started`, and the second passed it. The test signals a program whose shell has exited while the shell's child holds its output open, once the child has said `gone`, which it says on reading the end of a pipe the shell held. The cause is not found. It is the plan's item 45.

## A Load Past the Host's Limits, 2026-11-10

MVP 4.15's item 44, found by item 43's probe (*A Compiled Module the Host Cannot Load*). §11.2 said that a load or an arrival that would pass one of the host's limits fails as one the node cannot load. The decision of 2026-10-11 said so, and that the node runs on (*The Report for Code with a Spawn*). It was never built: nothing measures a load against the limits before it.

**The probes.** Each of the host's four limits was passed by loads, with OTP alone. Each ended the host with status 1 and a line of its own: `no more index entries in module_code (max=65536)` after 65,536 modules, `export_staged_index (max=524288)` and `fun_staged_index (max=524288)` after modules of 2,000 exports or 2,000 funs each, and `atom_tab` as item 43 found. Through `ern run`, a `Code.load` past the atoms ended the run with status 1, standard error holding the host's line alone, and so did `Foreign.atom` past them. So the sentence was false for every limit, not for the atoms alone.

**Decided: the report states the end**, the shape *Lean at the Limits* gives where the host fails worse than a refusal. A load or an arrival past a limit ends the node at once, as exhausted memory does (§10), with status 1 (§11.8).

A check before each load was weighed and refused. Only the atoms are counted cheaply. The host gives the other three counts only in its system information, a text of its whole state, which the runtime reads at four fifths alone. Read at each load, it would be a scan that grows with the host and not with the load, which §10 refuses. The runtime's sums leave out what the host loads on its own, and a foreign function and the host's own work make atoms beside a load's. So a check on the sums would refuse a load the host could make, or let the host end: a rule by estimate.

Principle 1 decides as well. The reader who knows Erlang knows that the emulator ends at its atoms, which OTP's *Common Caveats* states, and reads §11.2 for the rest. The line at four fifths stays the warning, and a restart the cure (the deployment guide's §4.2).

**The sweep.** §11.2 states the end, the host's line its example, and §11's list of where the host ends a job and §11.8's status 1 cite it. §11.8 names any job whose host would pass a limit, so a build's is among them: its compile makes an atom of each name, and item 43's check adds each module's code. E.28 no longer counts a limit among the reasons `Code.load` answers `Left(Other(text))`, and points at §11.2. E.12's `atom` says that an atom past the host's number ends the node.

The deployment guide's §4.2 said the node runs on past a limit, and its §4.3 counted a limit passed among an arrival's reasons; both now say the end. `docs/memory_checks.md` and the code's design note say it too, the note that nothing measures a load first. The comments in `ern_code_load` and its tests say it.

**OTP.** The end at the atoms is documented, so it is no defect. The other three limits are named nowhere in OTP's *System Limits*, and a load past one ends the emulator where `spawn` at the process limit raises `system_limit`. That is `docs/otp_bugs.md`'s 19, whose filing is the user's.

**The test.** `ern_integration_tests`'s `load_past_atoms_test_` is a regression test, written after the sentence, since the end is the host's. A run fills the host's atoms but for room for 100, the names of a module's 500 definitions among them, and then loads that module. A unit names its functions by their places, `$1` to `$500`, and a bare run's units name none past `$52`, so the module's code brings atoms that no chunk the load reads names. The test holds status 1, the line written before the load, and the host's line alone. It does not cover the other three limits, which no test reaches within its time, nor an arrival, the shell's loads or a build.

**Read back.** The host ends its line with a carriage return, `\r\n`, which the test holds as the host writes it. §11.8's "one of its limits on what it loads" read loosely for a build, whose atoms come of its compile, so it names the four limits of §11.2 instead. The test checks its premise first, that the module's code names `$500`, so that a change to how a unit names its functions fails there and not as a load that answered. No Ernest the item wrote felt against a principle, so `docs/language_feedback.md` is unchanged.

## The Flake of `os_signal_after_an_unread_exit_test`, 2026-11-10

MVP 4.15's item 45, found by item 43's `make test-full` (*A Compiled Module the Host Cannot Load*). The test signals a program whose shell has exited once the shell's child says `gone`, which the child says on reading the end of a pipe the shell held. It held `Left(Io.Closed)`, and one full run in two saw `Right(Unit)`.

**The cause.** The host closes an exiting process's files before it reports the exit: Linux's `do_exit` closes them before `exit_notify` makes the process one its parent can wait for. So the child can read the pipe's end and say `gone` while the shell is still exiting. The helper's `waitid` then finds no exit, and sends the signal to a shell that takes none any longer.

A probe in C ran the test's shell and asked `waitid` on reading `gone`, as the helper asks. Idle, it found the exit not yet reported in none of 2,000 runs. Beside 48 busy loops on nike's 24 threads it did so in 3 of 3,000. The test itself failed none of 50 runs idle, and one of 2,000 beside the loops, with the flake's output.

**The runtime did what the report says, and the fault was the test's.** E.23 answers `Left(Closed)` once the program has exited, and the helper asks the host whether it has, as *The signal* (2026-11-07) has it. The test took the end of a pipe the program held for its exit.

**Decided: no sentence in the report.** "Has exited" is the host's exit, as the host reports it to the program's parent. A signal sent as a program exits races the exit on every host, and Ernest answers as the host does. Principle 1 decides: the report states a departure from what the reader predicts, and here Ernest departs from nothing.

**The fix.** The test sends the signal until it answers `Closed`. Each one sent before reaches the exiting shell, which takes none, and the shell's status of 0 shows it. No read asks for the exit meanwhile, so none takes it.

A copy that counts the signals before `Closed` ran 2,000 times beside the 48 loops, in four hosts, and passed every run with no signal before `Closed`. So that run shows the test passing under the load, not the window crossed. A probe held the window open: the shell trapped the interrupt, closed the pipe itself and exited 0.3 s later. The copy then sent 25,700 to 31,900 signals before `Closed`, about 10 µs apiece, and held the test's output in three runs of three.

**Found: a write and a resize after the exit.** A probe of the same shape found that E.23's two other answers to an exited program are not built where a process the program started holds what they reach. Where a child holds the program's input, a write once the shell has exited answers `Right(Unit)`, its bytes taken by the pipe the child holds. Where a child holds its terminal and ignores the hangup, a resize answers `Right(Unit)`. Each was seen in three runs of three, after `signal` had answered `Closed`.

E.23 answers `Left(Closed)` to both, and *The signal* says that `write` does. The helper learns of the exit only once both outputs have ended, but at a signal, and the shim answers a resize without the helper. It is the plan's item 46.
