# The decisions log, 2026-09-27

## No Remote Computation in the Language, 2026-09-27

Feedback items 14 and 25, decided. `remote(f)` came from Unison, where the evaluation of a function somewhere else carries the whole of distribution. Ernest already has that in another form: a process spawned on a named peer takes its code with it, runs there, and reports its failure through monitors. What `remote` had of its own was three things. It waited for its answer, which a spawn and a `receive` do. It answered a failure as a value, `RemoteError`, a type that existed only for it. And the runtime chose the peer by load, a policy the program could not see (principle 3). The guide's own example showed what the waiting cost: to run several computations at once, `inParallel` wrapped each `remote` in a local process, so the program wrote the processes anyway and `remote` inside them. It is removed, with `RemoteError`, the `"remote-peer"` flag of `ernest.conf`, and its section's content (principles 2 and 5). §6.7 keeps its heading and says that work on a peer is a process spawned there.

Item 25's `spawn(Remote, f)`, a place where the runtime chooses the node, was weighed as the asynchronous form and refused with it. On a node that has no peer to choose, it must either fault, so that a program written for peers dies on one node, or run the process here, the fallback principle 3 refuses. Counting this node among the candidates, `Anywhere`, answered that, but it kept the policy in the runtime. A measure of load is a policy, and the right one depends on the work: a node with an idle processor may have its pool of database connections full. A policy belongs in a function the program can read and replace, so no placement by the runtime enters the language. Erlang's `pool:pspawn`, which spawns on the node with the lowest run queue, has been in its standard library for decades and is rarely used; programs build their own pools, for the same reason.

What a program needs to place work on a lightly loaded node is two facts only the runtime has: which nodes there are, and how busy one is. They enter with `Peer` in MVP 3.0, `Peer.nodes` and `Peer.runQueue`, by E.0's first admission rule. Reading another node's number is a process spawned there, ordinary Ernest. The policy over them is a library, `libs/balancer`, and not the standard library, since sampling, ties and a silent peer are choices E.0's third rule refuses to bury in one. It draws two nodes at random and takes the less busy, the power of two choices, which needs no process of its own and does not send every caller to the node that stale numbers call the least busy. A program's own measure is a function given to it, and nothing is installed globally: a chooser registered once would make every `spawn` elsewhere depend on code a reader of it cannot see, and two libraries registering one would collide (principle 1).

The asynchronous call item 25 asked for is a spawned process, whose address is what a task or a future is elsewhere; *Remote Ergonomics* refused a `Task(a)` beside it, and that holds. `Peer.find` stands, as *`Peer.find` Stands* left it for this outcome, and answers its failure with `Peer`'s own type, `Peer.Failure = NoSuchPeer | Lost`: the two ways a lookup finds no service, a name `ernest.conf` does not list and a peer lost before it answers, named for what the caller does next, and `NoSuchPeer` rather than `Unknown`, which the prelude's `Reason` has.

## A Program's Command Line Is `Os`'s, 2026-09-27

Feedback item 16, decided: a program could not read its arguments. Two shapes were weighed. An entry point `main(args : List(String))` shows the input in the entry's type, but either every entry point takes a list that most ignore, or there are two entry shapes (principle 2); the environment would need a second parameter, so the signature grows with every fact of how the program was started; and a module deep in the program that needs a setting would have it threaded down from `main`, the threading *Ambient Sys, Five Principles* ended for the standard devices. The other shape is §8.2's: what only the runtime has is a top-level binding of a system module, visible where its name is written (principle 3). The arguments and the environment are fixed for a run, so they are values, `Os.arguments` and `Os.environment`, not processes. The environment is a `Map`, since a lookup function beside it would be a composition (E.0 rule 4). An argument that is not UTF-8 refuses the run, since it was given to this program; a variable that is not UTF-8 is left out, since refusing to run over a variable the program never reads would be the greater surprise (principle 1), and the report states it.

`Os.run` joins them: starting a host program is what only the host can do (E.0 rule 1). Erlang's `os:cmd` was the model weighed and not taken. It answers standard output alone, so the exit status and standard error are lost and a command that failed reads as one that printed nothing (principle 3); and it passes one string to `sh -c`, so quoting is the caller's and a name with a space or a `;` in it does what the program did not mean (principle 1). `Os.run` starts the program itself, each argument as it is, and a shell is one program it can start, so there is one way (principle 2). A status other than 0 is the program's answer and not a failure of the call. The output is `Bytes`, as standard input's is since item 57, and the fields are `stdout` and `stderr`, `Io`'s words: §8.2 says standard error is a second sink, not a level of severity, so a name like `errors` would contradict it. The request is a record read by its field names, and the milliseconds are the last argument and the failures `Io.Error`'s, as `Tcp`'s are. A command never reads the terminal, which the terminal's claim for keys or for lines would contest; its standard input is what the request gives.

*Superseded in part 2026-10-01 by "The Silence Family's Rules": `Os.environment` asks by name, and a value that is not UTF-8 faults its asker.*

## A Program Ends With `Os.exit`, 2026-09-27

The last question of MVP 2.66's opening, decided. A program exited 0 when `main` returned and 1 on a fault, and could say nothing else, where a tool that distinguishes "no match" from an error needs to. An entry point that returns an `Int` would make every entry point return one or give two entry shapes (principle 2), and a status decided deep in the program would be threaded back to `main`, the threading *A Program's Command Line Is `Os`'s* refused. A function that records a status for the end is state any process sets and the last one wins, invisible where the program ends (principle 3). `Os.exit(status)` ends the program where the decision is made, as §8.6 ends it, and its type `a` says it does not return, as `fault`'s does. The default stays for a program that does not call it. A status outside 0 to 255 faults, since the host would keep its low byte without a word. In the shell it ends the input and not the shell, answered `exited with status n` as an interrupted input is answered `Killed`; under `ern test` it fails the test and the run goes on. A reader from Erlang knows `exit` as a process's end, which Ernest spells `kill` or a return, so its module page says in a line that it ends the program.

*Superseded in part 2026-09-27 by "The Environment Read Through the Helper": in the shell and under `ern test`, `Os.exit` faults its caller with `exited with status n`.*

## A Sibling Restarts at Its Next Wait, 2026-09-27

MVP 2.66, before the build, decided. *A `Supervisor` in the Standard Library, and `fault`* took children as `restarting` processes and had the supervisor restart a sibling in place through a shim, on the ground that only the host can restart another process. The host cannot either. `restarting` restarts in place because the fault is raised inside the process, where its loop catches it; BEAM has no way to raise one in another process, and an exit signal either ends the process, losing its address, or, trapped, arrives as a message it reads at its next wait.

So a sibling is restarted at its next wait. The supervisor sends a priority message, which OTP 28 places before the mailbox's other messages; every `receive` the emitter writes, and the runtime's waits in a call, has one clause for it, and `restarting`'s loop runs `f` again. A restart the supervisor asks for is not the child's fault, so it counts against no limit and is reported as no fault. The child runs on until it next waits, as an OTP `gen_server` reads its system messages between callbacks, and a child already waiting restarts at once; a child that waits while it handles a message, in a nested `receive` or a call, restarts there, and the message is lost as at a fault. The rule was first written as finishing the message in hand, and the build showed that a handler's own wait comes first. A child that computes without waiting is not restarted; it already serves nothing, and killing it, as OTP does after a timeout, would lose the address the restart exists to keep, and a timeout would be a policy argument more. With mailboxes kept, a group needs no order to restart: a message sent to a sibling that has not yet restarted waits for it. A supervisor is itself a `restarting` process, so a tree restarts in place level by level and its service bindings keep their addresses.

Two other shapes were weighed. Children as new processes, as OTP has them, are simple inside the supervisor and leave every service binding holding a dead address; Erlang answers that with a registered name, which §6.5 refuses, and the other answers are a forwarder, a hop on every message, or a handle that `send`, a call, `monitor`, `kill` and `Process.fromAddress` would each look up, the mailbox lost at every restart and a `Down` told of a process whose address still works (principle 1). `OneForOne` alone needs no signal and gives a thin supervisor that stops at one level, since a supervisor restarted as a new process brings its children back at new addresses. The signal is about forty lines in the emitter and the runtime, and nothing about an address changes.

The service binding is also why Ernest needs no registered name in a tree. In Erlang a child registers a name so that its replacement is found; in Ernest the binding is the name, typed, scoped by `export`, with no window in which a send to it fails, and it names the process in a fault line (§6.9's site). Names made at run time, one process per user, are a service holding a `Map`, as *No Registry* decided.

*Reason restated 2026-10-01: a sibling restarting at its next wait stands as §6.9's rule ("The Reader Family's Rules"); the OTP reader was a neighbor's, which no longer decides. Superseded in part 2026-09-30 by "A Restart Begins Afresh": the mailbox is emptied.*

## The `Supervisor`'s Shape, 2026-09-27

MVP 2.66's questions on the module's interface, decided one at a time.

**Children added at run time.** OTP has `simple_one_for_one`, and Elixir a `DynamicSupervisor`, for children started while the program runs, one per connection or per user. In Ernest a child can join a supervisor at any time, from a service binding's initializer or from any process later, so a pool is the same supervisor and not a second kind (principle 2); whoever starts a child holds its address, and the restart in place keeps it. A child that returns or is killed leaves the group and is forgotten: `restarting` restarts only a fault, so every child is what OTP calls transient, and no per-child restart type is needed; and a pool that kept its ended children would grow with nothing to reclaim it. `RestForOne` means the children that joined after, in the order they joined. `OneForAll` over a pool, which OTP refuses, is left to the program, which chooses it by an argument and reads what it means in the module's documentation.

**The caller writes the `spawn`.** A fault line and a `Down` name the declaration in which `spawn` is written (§6.9), so a `Supervisor.spawn` that spawned inside the module would name `Supervisor.spawn` for every child of every program (principle 1). The compiler could pass the caller's position into the function, as Rust's `#[track_caller]` does, but that is a feature of the language for one module, or a special case the reader cannot see (principle 3). `restarting` already has the shape that needs neither: it answers the function a process runs, and the caller spawns it. `Supervisor.child` does the same, `spawn(Local, Supervisor.child(sup, f))`, so the site is the caller's binding, the placement the caller's, a peer included, and `spawnMonitored` works as it does with any function. The child joins the group before `f` runs, waiting until the supervisor has it, so the order `RestForOne` reads is the order children joined, with no race between a new child and a sibling's fault. A program that calls the answered function rather than spawning it makes its own process the child, as calling `restarting(limit, f)()` runs `f` in place; nothing forbids it.

**A group, and one limit.** A supervisor is spawned as a child is, `spawn(Local, Supervisor.group(strategy, limit))`, so its own fault line names its binding too, and its message type is abstract, as a system module's is. *A `Supervisor` in the Standard Library, and `fault`* gave each child a limit beside the group's; the two overlap, a fault counting against both and the reader left to work out which gives up first and what each then does. OTP has the group's alone, its intensity, and it has sufficed, so the group's is the only one (principles 2 and 5), and `Supervisor.child(sup, f)` takes none: a child restarts in place after each fault until the group passes its limit. The group then faults with a cause naming the limit, which is what `fault` entered the prelude for. A supervisor under a parent is a child, so it restarts in place, whether it gave up or its parent restarted it with a sibling, and it asks each of its children to restart, so a subtree restarts with its root as in OTP; its children keep their order: the watcher holds the order, and outlives the restart because its address waits in the supervisor's kept mailbox. The group counts its faults by alarms, one per fault expiring when the limit's window has passed, since `Clock.now` is the wall clock, which a stepped clock would move under a sliding window. An alarm carries the number of the run that set it, which the watcher hands out, so one set before a restart in place is ignored and does not lower the new run's count; the build found that defect, and a test holds it. At the root the supervisor dies, its watcher kills the children, and `main` decides what follows, since only its end ends the program (§8.6).

**Stopping is `kill`.** A supervisor that dies of a defect of its own, not by `fault`, would leave its children running, since nothing owns a process, so the module spawns a watcher beside it that kills them on its `Down`. A `kill` is one more way for the supervisor to die, so the watcher stops a group too, and a `Supervisor.stop` would be a second way to do what `kill(sup)` does (principle 2). `kill` is asynchronous, so the watcher kills in the reverse of the order the children joined and waits for each to end before the next, so that a child that may use an earlier one is gone first. A child that must finish its work, a file to flush, is sent a message of its own protocol and answered before the program kills the group: the module knows no child's message type, and no process can catch a kill, where OTP traps the exit and waits a shutdown time (§6.9, "There are no other links"). The watcher is a process of its own in `Process.live`, its site in the module; it is real, and the module's page names it.

**What the build and its readers found.** Two readers who took no part read the result, and found four defects in the code, each now held by a test. A child joined inside its restart loop, so a child of a supervisor that had ended faulted on its join and restarted without end, and children asked to restart as their root gave up joined the dead supervisor and reported that as faults of their own. A child now joins once, before its loop, by a call with a limit, made again when it ends unanswered while the supervisor lives, and faulting with `the supervisor has ended` when it does not; after a fault it tells the supervisor by a `send`, which to a dead supervisor does nothing. A supervisor restarted by its parent left its children running, where OTP restarts the subtree, which is what a reader from Erlang predicts (principle 1): at each start that is not its first it asks its children to restart, so giving up is only a fault. And a `restarting` nested in a child's function took the restart meant for the child: the outermost restarting function of a process is the one asked (§6.9). Telling a fault from a restart asked for needs the runtime, since only the restart loop knows why it ran the function again: `startCause`, a second private shim, reads it, and E.0 rule 1 names it. A child's own limit is none, `RestartLimit(restarts = 1, within = 0)`, which §6.9 now states rather than leaves to be worked out, and the module names it `unlimited`.

**A supervisor and its children run on one node.** A child's `Join` carries two closures, its `stop` and its `watch`, which stand for an address whose type the supervisor cannot name, and *Code Travels Only With a Spawn* keeps a function from crossing nodes. A child spawned on another node than its supervisor would fault as it joined, with `function cannot cross nodes`, a cause that names nothing the program wrote. Carrying the child's `Process` with private shims to kill and watch it would have made the join plain data and let supervision cross nodes. It was refused on OTP's reason, which holds more strongly here: a restart in place is a mechanism of one node, since only the runtime that holds a process can interrupt it at its next wait, and across nodes every restart, fault notice and ordered kill would be a network message, so a lost connection would read as the group failing and a partition would count against its limit. When a peer is lost, every process on it faults (§10), which is network failure, not the failure a supervisor exists to restart. Between nodes a process watches another with `monitor`. So each node has its own trees, and `Supervisor.child` faults with `a child runs on its supervisor's node` before it joins, a check MVP 3.0 builds once there are peers, through a private shim that says whether a process is on this node.

**When a restart is over, left as it is.** Feedback item 61, decided: after a fault, a call to a sibling may be answered from its old state, end, or be answered from its new one, and nothing tells a client which, so `examples/services.ern` and the guide's §6.6 wait before they ask again. A `Supervisor.settled(sup)` that answered once no asked restart was pending would not close it: the faulted child's notice and the client's request come from different senders, which §6.4 does not order, so the request can arrive first. The window is what an asynchronous fault is, and OTP has it too. A client that relies on a service's state after a fault takes the state as lost and asks again, with `Address.call`; the example and the guide wait only so that their output is the same on every run, and say so.

*Reason restated 2026-10-01: one limit and a subtree restarted with its root stand as Appendix E.22's stated shape ("The Reader Family's Rules"); the OTP reader was a neighbor's, which no longer decides. Superseded in part 2026-09-30 by "No Limit Is `Unlimited`" and "A Restart Begins Afresh": no limit is `Unlimited`, and the mailbox is emptied at a restart.*

## Code Travels Only With a Spawn, 2026-09-27

*Superseded in part 2026-10-07: the walk and the run-time fault were replaced by the compile-time refusal of a bound type (§3.11; *The Nodes' Reasons, Kept*); code still crosses with a spawn and a compute alone.*

Decided from §3.11's sentence that every value can be sent, a function included, and that its code travels with it. §8.7 shipped code with three operations: a spawn on a peer, a `send` to a remote address, and an answer to a caller on another node. For a message the design did not hold together. A `send` returned at once, and a peer that failed to resolve the code faulted the sender later, at no line of its code (principles 1 and 3). The fetch was traffic the code did not show. And the report never said when a message's code was resolved. Resolving a function in a message lazily, at its first call, looked like the answer until the three things a shipped function depends on were told apart. Its captured values are part of the message and travel with it. Its code is content-addressed and can be fetched at any time. The top-level bindings it names are the question. If they meant the sender's values, a lazy fetch would have to return to the sender for state, which may be gone, and an eager one would walk the whole program at every send. §8.7 had avoided that by making a binding the peer's, which is why `fn() = send(counter, x)` and `{ let c = counter; fn() = send(c, x) }` meant different processes once shipped.

A function is now bound to its node, as a foreign value is (§3.8), and a value that holds one faults at the operation that would take it to another node, `Fault("function cannot cross nodes")`, in the process doing it, found by the same walk. A message between nodes is values, and it needs no code on the node it reaches. Its types are those of the receiving process's mailbox type, which that process's node holds, since the process runs code that names them. So a message fetches nothing, a `send` faults only at the call, and no fetch pauses a connection to keep order. Code travels one way, with `spawn(Peer(name), f)`, where the program asks for it: `f`, its captures, and the code of every function among them are resolved before the process starts, and a failure faults the caller at the call. There the binding rule stays, since `Peer.find` needs a service binding to be the peer's, and §8.7 states it in one sentence beside the rule for captures. Code replacement on another node is the same composition: a process spawned there brings the new function and sends the upgrade on that node.

Forbidding functions in messages altogether was weighed and refused. On one node a function in a message costs nothing, and code replacement (§6.10), `via`, the subscriptions of the system modules, the `Supervisor`'s `Join` and records of functions all rest on it; what went wrong happened only at the node boundary, so the rule is drawn there. An adapted address is a function inside an address, and the boundary rule alone would keep one from crossing, so that a client could not hand a remote service `via(Wrap, self())` and a service would have to speak each client's message type. It crosses without its code: its function is applied on the node where the address was made, which holds that code, the value crossing to it and being wrapped on delivery. What crosses is a reference to the function and the values it captured, and a message to the address carries them back, so the making node keeps no table of the addresses it handed out, which would grow with every copy and have nothing to reclaim it; the captures are values, and a foreign value among them faults. A spawn ships every function its captures hold, through data and other functions' captures alike, since the spawn is where the program asked for code to go. §6.5 already made a fault in the function the target's, so the fault lands where it did. An adapted address made around another node's process would need a hop through the node that made it, or its code shipped, and it faults when it would cross, since one adapts one's own address to hand it out. Erlang's rule, a fun sent as a reference that the receiving node must already have, was the nearest precedent; Ernest faults at the send instead of at a later call, since the sender is where the program can see it.

## `Os.run` Runs Through a Helper in C, 2026-09-27

`Os.run` was agreed as a program run to its end, its standard output and standard error apart, its input given and then ended, and the program killed when the time runs out. Built with the manual page of OTP 29's `open_port` open, none of the last three can be done with a port. A port gives a program's standard error either merged into its output or to the emulator's own standard error; `port_close` closes both directions, so a program that reads its input to the end, `sort`, waits for ever; a port that only reads leaves the program the emulator's own standard input, so that `cat` read the running program's input; and closing a port does not end the program, and OTP has no way to kill one. Three ways were weighed. A shell to wire the redirections, `exec "$0" "$@"` with temporary files, needs no compiler but leaves files behind a crash, cannot tell a failure to start from the program's own exit status 126 or 127, and kills its group through a detail of how OTP starts a program that no page documents. A contract cut to what a port can do, the output merged and an input that never ends, is not the `Os.run` agreed. A helper in C does all four, and it is what the ecosystem does where it meets the same limits, MuonTrap and goon for Elixir, erlexec for Erlang, OTP itself through `erl_child_setup`. So `ern_exec` runs the program in a process group of its own, with pipes for its input, output and error, closes the input once it is written, reports the reason a program did not start from `execvp`'s own error, and kills the group when the port closes, which is also how the program dies with the process that called `run`. The helper is what only the host can do, by the rule for `foreign`, and it is C99 over POSIX.1-2008 alone, built by `make` on the hosts Ernest runs on, Linux and macOS.

What the runtime keeps is Ernest's rule for a shim: a run is a process that owns the helper's port and answers `Next` with what the program sent, in order, and `Os.run` gathers the pieces in Ernest. Those primitives are private, so that exporting them, a process reading a program's output as it runs, is a decision of its own, placed in MVP 2.7. A run is a source from its start to its end (§8.6), so a caller that only waits for a program is in no deadlock. A name or argument holding U+0000 cannot reach `execvp`, and `run` says so rather than answering the host's `badarg`; `Fs` had answered a path with U+0000 with that same term, and now names it too (E.17). The run ends when the program has exited and both its outputs have ended, as other languages' `run` with captured output does, so a process it started that keeps them open holds it, which E.23 states.

## A Running Program Is a Process, 2026-09-27

`Os.run` waits for a program to end and holds all its output, so a program that does not end or ends late and matters as it goes, `tail -f` or a build that reports its progress, output larger than memory, and a conversation with a program through its input and output are all out of its reach. ## Back Pressure, Again, 2026-09-27

The question came back because back pressure is what Erlang lacks, and the answer is the same as on 2026-09-13 for a sharper reason. Two things were found wanting beside it, neither a mailbox. ## Running as a Service, 2026-09-27

What remains is what only `ern` can do. ## Layout for the Reader, 2026-09-27

The style guide's layout rules are judged by how the code reads, and a formatter applies them, so what they leave open is settled by the tree and a line's length and never by the writer (principle 2, one way; principle 1, the code that results). A function's body begins on the line after its head, one step in, however short it is. The head then reads as a signature alone, a match or a receive that is a body stands at the same step in every function, and one rule needs no exception for bodies that fit. A `foreign fn`'s string is its body and stands there too. Keeping it on the head's line made long heads break inside their signatures, which read worse than the string on a line of its own. A blank line stands between top-level declarations, with a declaration's comment directly above it, so that no comment stands between two declarations without saying which is its own. A block holds more than one statement, since braces around one expression say nothing.

A bracket that does not fit holds one item a line, aligned under its first, and closes on the last item's line. The rule first written the same day broke a bracket after its opening, stepped its items in and closed it on a line of its own. A head's parameters then stood at the step its body stands at, and where the head ended showed only in the closing line; aligned, they stand apart from the body, and the closing parenthesis needs no line of its own. Alignment is a second model beside the step, and renaming a function moves every line aligned under it. It is admitted for a bracket's items alone, and for every bracket alike, a call, a head, a constructor where it is declared and where it is built, a list and a tuple, so that it is one rule rather than a list of the brackets that align. Filling each line with as many items as fit was weighed and refused: the break then falls inside a record's fields wherever the length runs out, which tells a reader nothing, while one item a line reads as a table and lets a diff touch one item. Where alignment runs out of room there is no second shape, a break after the opening bracket stepped in: the formatter splits further, and a writer names a part of the expression where the split reads worse than a name. A last item that opens a brace, a lambda above all, stays on its bracket's line, since `spawn(Local, fn() = {` broken one item a line would cost four lines at every spawn.

A brace runs over lines, a `match` and a `receive` as a block does, so a match is always read as a table of arms. The body after `then`, `else`, an arm's `->`, a lambda's `=` or a `let`'s `=` stays on that line when it fits, and otherwise begins the next line, one step in; an `if` that does not fit breaks at every `then` and `else`, so that a long `else if` ladder reads down its conditions. An arm's body goes to the next line rather than splitting beside its pattern, since an aligned bracket beside a long pattern drifts right, and one arm of the shell had no layout within 100 characters that way. Breaking after every such word was weighed. It is the most uniform rule, but it doubles every match and puts a conditional of two words on four lines, and the code written by hand before any of this, with its one-line matches, its tables of arms and its one-line `if`s, is what a reader who knows Ernest predicts (principle 1). The mix first decided, `then` and `else` always ending their lines while arms broke by length, gave one job two rules, which principles 2 and 5 refuse. The measure of what fits is the formatter's, so it is no longer the writer's judgment, which is what the always-breaking `if` was chosen to avoid. A head's `=` still always ends its line: a head is a declaration, read as a signature, not a body inside an expression. A lambda has no rule of its own.

The rules were tried by hand on `shell/shell.ern` before they were written, and reading it settled four details: one item a line; a part named where a split reads badly; an `else Unit` on a line of its own after a block, since keeping it beside the brace would take the whole-`if` rule's ladder away; and `else` returning to the start of the line its `if` began on, whether that is the `if`, a `let`, a pattern or a lambda's `fn`. The rules for heads, `foreign fn` strings, blank lines and blocks were applied by rewriting the code, since each moves or adds lines and nothing else. The first run found four places where the layout of *Layout for the Reader* had said too little. Of two brackets on a line the first breaks, so a head's parameters break before its return type; but a later `if`, operator chain or pipe may end the line at its first break, as Prettier's printer lets it, so a pattern before `= if` stays whole. A comment or a doc block before a bracket's first item puts that item on a line of its own and the items a step in, a shape the content decides and not the length, so it is no second shape where alignment runs out of room. A brace's contents step in from the line its construct began on, the `match` of a scrutinee broken over lines and not the line its brace ended. And a line an operator opens carries on the operand of a more loosely binding operator a step further than the operator chain above it, which shows how the expression groups; the Emacs mode knows it from a table of how tightly each operator binds, held equal to the parser's by a test, as its word lists are held to the lexer's.

The Emacs mode indents as the formatter lays out, and `reindent` holds it to every source. One rule needs it to look past the line: a brace in the first item of a bracket steps from that item's column when the bracket holds a further item, and from the line when it is the only one, which hugs it. Where nothing follows yet, the mode takes the hug, and the formatter sets it right on save. The first run asked the writer for three names where no layout fit in 100 columns and for two comments to move above their arms, and the generator of `Terminal.columns`' table now writes the table as the formatter lays it out. A `let`'s value became a body too, decided with the user after the first run: a value that did not fit had stayed on its `let`'s line, its brackets aligned far to the right, where on the next line, a step in, it reads as the source had it and aligns half as far; a table and a test's `Test(...)` begin their own line, and a value whose first line ends in a brace, `let readers = match keys {`, stays. One cost was accepted: a long table of short entries takes a line an entry, 647 for the width table.
