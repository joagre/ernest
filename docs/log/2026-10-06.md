# The decisions log, 2026-10-06

## No Mark Lifts a Foreign Function's Restriction, 2026-10-06

*A Foreign Function Marks Its Equality* left open whether a second mark should let a foreign function's signature lift §4.7's not-reply-carrying restriction from a variable, so that a library function whose type carries a reply could stand on the host. Decided with the user: no mark. §4.7 stays as it is, and those functions stay Ernest.

What the mark would buy is small. Of `List`'s functions that carry a reply, `foldLeft`, `foldRight` and `foreach` already measure 1.0 to 1.1 times the host's, and `map` has a host function whose page states no order, so it stays Ernest whatever the mark. Four would gain: `reverse` at 2.4 to 4.6 times `lists:reverse/1`, `indexed` at 1.4 to 3.0, `unzip` at 1.3 to 1.9, and `<>`. The emitter's work, MVP 2.99d's item 3, can narrow the last three; `reverse`'s gap is a built-in of the host's, written in C, against a loop, and only the host closes it.

What the mark would cost is a kind of trust the language has not taken. The equality mark narrows what a scheme admits, so it is sound whatever the foreign code does. A mark that lifts a restriction widens it on the foreign code's word: where that word is false, a reply is dropped and its caller waits for ever, the failure §6.6's discipline is there to rule out, and nothing reports it. It is also a second mark a program writes, which principle 5 counts, and one that removes a restriction where the only other adds one, against what principle 1's reader predicts.

The *Later* list holds it, with what would change the verdict.

## The Shell Shows a Bracket's Match, 2026-10-06

Decided with the user, who missed it at the prompt: a `)` typed shows the `(` it closes for a moment, and a bracket that closes another kind, or none, shows nothing; `]` and `}` the same. Three choices made it small.

**The cursor moves, as Readline's `blink-matching-paren` moves it.** The shell keeps Readline's Emacs keys, and Readline shows a match by standing the cursor on it. That needs no color, so it is the same where `NO_COLOR` is set, and the region draws as it did, told only where the cursor stands. A highlight would have needed the region to draw one grapheme styled, the style carried beside the text, since the region draws a control character in the input as its picture.

**The compiler's lexer finds the bracket.** A scan in the shell would be a second lexer, of strings, characters, raw strings, nested comments and `#(`, to disagree with the first, as counting brackets would have been a second parser beside `needsMore`. `ern_shell:opening/1` reads the text before the cursor with the lexer, comments as tokens, and pairs the brackets back from the last: a stray bracket before the pair hides nothing, and a bracket of another kind between the two shows nothing. Text the lexer cannot read, a string or a comment left open, shows nothing, which is what a bracket typed inside one should show.

**Typing is never held.** The reader waits for the next key with an `after` of 500 ms, Readline's half second. A key that comes first puts the cursor back and is read at once. A paste and a search's key answer as before, so a pasted `)` moves nothing.

## Path Read as the Runtime Reads It, 2026-10-06

E.14 says a `Path` is in the runtime's syntax, and its functions were Ernest over `String`, whose searches match whole graphemes. The two part where a combining mark follows a separator: `"/\u{301}"` is one grapheme, so `Path.split(Path("dir/\u{301}x"))` was `["dir/\u{301}x"]` and `Path.name(Path("dir") <> Path("\u{301}x"))` was `Some("dir/\u{301}x")`, where the file system, and `filename`, see the directory `dir` and the name `"\u{301}x"`. A dot followed by a mark was no dot, and `Path.extension(Path("a.\u{301}"))` was `None`. The name a program took from a path was not the name the file system gives the same file: a defect, found while making `Path` faster. E.14 now says that a path is read by its code points, as the runtime reads it.

**Two primitives of the path syntax.** E.0 rule 1 admits a primitive that reaches the runtime's path syntax, and the `filename` pages, which state none of E.14's edge cases, admit no shim. `parts` is the text between each occurrence of a separator or a dot, `binary:split/3` with `global`, through `ern_path` since its option is an atom: it reads bytes, and UTF-8 never holds one code point's bytes inside another's, so its parts are UTF-8 and a separator is one wherever it stands. `split`, `join`, `extension`, `withExtension` and `withoutExtension` are Ernest over it, and a name's stem and extension come from its parts between dots, the empty ones before the first part being the dots that begin it. The second, `lastPart`, is the text after the last separator, read from the text's end, for `name`: what it costs is the name's length, where `filename:basename` grows with the path.

**Measured,** against the host's `filename` at 10, 100 and 10,000 graphemes. `name` from 9.7, 41 and 48 times to 0.7, 0.3 and 0.0, never growing; `extension` from 11, 82 and 5,950 to 1.4, 1.4 and 1.5; `parent` from 5.4, 33 and 20 to 1.6, 1.4 and 1.1. `split` at 100 from 44 us to 1.5 us. What `parent`, `join` and `withExtension` still cost grows with the path, as what they answer does.

The laws of `Path` drew only ASCII names, which is why they had not found it; they now draw names with a combining mark after a dot or at a name's start and a prepended mark at a name's end, and read a name's leading dots by bytes, and six of them failed on the old `Path` before the change.
