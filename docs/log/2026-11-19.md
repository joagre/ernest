## What a Peer's Worker Waits On, 2026-11-19

MVP 4.16's item 108: an agent read a peer's worker whole, with everything it runs for a frame, a loss, a connection opened again and its own end. It found two holds. The session read the sites against the code and ran the four probes again, with the same results. Nothing was fixed, and the fixes were decided with the user.

**The list.** Six of the worker's sends leave the node. Four go to its own peer, by a guard or by the gateway's name on the peer's node: a spawn's answer, a compute's failure, the kill at an `answer` frame, and `restarted`. Every other signal of the worker's stays on the node. It sends no monitor, link or exit to another node, makes no call there, and writes to no group leader there.

**No send waits for a dial.** On OTP 29 a send to a node that is not connected is queued, and the dial runs beside it (`dist.c`, `erts_dsig_prepare` and `erts_auto_connect`). Only the buffer's limit holds a sender. The brief had assumed that a dial holds one too.

**A fault for a third node.** At a full process table the worker cannot start the process kept for an adapted address (`ern_rt:kept/1`). It then sends the fault to the address's process, wherever that is. The frame's clause checks the maker's node alone, so the process may be on a third node: B makes `adapted(q, f)` with `q` on C, and gives the address to A.

With C's connection held as item 104's tests hold one, and B's table full, the host held A's worker in that send. A's `find` answered `Left(Io.Timeout)` after 3 s, and within 1 ms once C's connection was let go. Three runs of three.

**A `find`'s alias.** The `find` frame answers to the alias it names and checks no node, where the `compute` frame does. `Peer.find` makes the alias on the asker's node, so only a faulty frame names another node, and the harm stays on that peer's own worker. Read, not shown.

**The host's disconnect waits for the controller.** The worker waits on three processes of its own node. The reaper and the code server wait on no other node. `net_kernel` can. `erlang:disconnect_node/1` is a call to it. It sends the connection's controller an exit and waits for the controller's end, with no limit. Over TLS the controller is ssl's sender, which traps exits and reads nothing while it stands in a send to a full socket. It is the sender of `docs/otp_bugs.md`'s report 24, met from another side.

A node calls the disconnect at three sites: a frame it cannot read, from the worker or the exchange; a reload that removes a peer; and the gateway's refusal at the peer limit.

**What it holds, with a connection held back.** With C's connection held, B's reload removed C, and A sent B a frame it cannot read. `net_kernel` stood in its disconnect, the signal server behind it in the reload, and A's worker behind both. A's `find` timed out, while the gateway answered its utilization at once. A termination sent then waited in the signal server, and B ended 8 to 11 ms after C's connection was let go. Three runs of three for the reload, and three of three for the termination.

**What it holds, with a node really stopped.** C was stopped with 16 MB waiting for it. B had not removed C 100 s after the reload, where the host gives such a connection up within 85 s (*A Connection That Cannot Drain*): `net_kernel` held the ticks it never passed on. A's `find` got no answer while that lasted, and A's own termination waited in its departure's ping to B. B removed C 2 to 3 ms after C ran again, and A ended within 13 ms. Five runs of five.

**Who meets it.** It takes a disconnect of a peer whose connection cannot drain, made before the host gives the connection up. An operator who removes a hanging peer and reloads does that. By a reading, a listed peer does it alone: it sends a frame the node cannot read and stops reading. Such a peer can already start code on the node, so that case is robustness and no defense.

**Decided: the host's `async_disconnect`.** The three sites call `net_kernel:async_disconnect/1`, which sends the same exit and does not wait. Principle 3 decides as it did for the killer: a loss that is never decided and a termination that does not end the node are rules of Ernest's own failing at a limit. The function is the host's own, which `CLAUDE.md`'s *Design* puts before anything cleverer. Its documentation is hidden, so a later OTP may change it. The probes, kept as tests, would show that at once.

**Set aside for the disconnect.** Killing the controller, found by `system_info(dist_ctrl)`: the calls are documented, and they rest on how TLS is built, which *A Connection That Cannot Drain* set aside. A process for each disconnect: it frees the caller, and `net_kernel` is held all the same. Waiting for a fix in OTP: no narrower promise is worth making of a node that decides no loss.

**Decided: the flag around the fault's send.** The worker sets the host's `async_dist` around that one send. The flag for the worker's whole life was set aside: it would also change how a worker waits on its own peer, which nothing found asks for. The `find` frame takes the `compute` frame's guard.

**Planned.** Item 125 holds the disconnect and its report to OTP, number 26. Item 126 holds the fault's send and the guard.

**Not shown.** The `find`'s alias. The fault's send against a node that is really stopped. The gateway's own disconnect at the peer limit under the hold: the nodes' note says the gateway waits on no peer, and item 125 shows whether that holds there.
