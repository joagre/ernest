## The Detach Keeps What Declares a Function, 2026-10-30

MVP 4.0's item 13, decided the same day (*The Attached Shell, Tested*) and stated in §11.2's `:detach` sentence before it was built.

**The rule.** At a detach, each of the session's units that declares a function or builds a function value stays for the node's life, as a load's units do, with every unit it needs. The rest go as before: deleted, and purged where no process runs one. OTP 29's `erlang:check_process_code/2` counts no function value as code a process holds, so no purge can find the process that holds one. Principle 1 decided: a service left at a node runs on, whatever holds its functions.

**Which units.** A unit builds a function value where its interface chunk says `builds_functions`, as the emitter marks it. It declares a function where its `'$code'/0` lists a `function` or a `foreign` row; a member a type derives, `compare`, is such a row. An input that declares types alone, an expression's unit without a lambda and a holder declare none. An input that hands a declared function on, `Keep.Hold(applied = tripled)`, builds no function value of its own: the value is a function of the declaring unit, which stays.

**What they need.** A unit the session keeps recorded the units its code calls and those its interface names. Writing the test found a third kind: a type that a function's body alone names, which no import shows. A peer's compute of the function after the detach then fails, the peer saying the compute `was not loaded: the spawner's node no longer holds the function's reach`, since the type's form went with its unit. A kept unit's needs now take in the session units its forms reference, the interface chunk's `references`. While the session runs this changes nothing: those units are declaring inputs, kept anyway, or holders and units of `it` that its calls reach already.

**Values.** The values of a unit a lasting unit needs stay, its getter called by code that stays. A lasting unit that none needs loses its values, the last expression's `it` among them, since no code that stays reads them.

**The purge's bookkeeping stays.** *The Attached Shell, Tested* expected it to go. §11.2 still keeps a unit a process runs while it does, and the rest are still let go by `code:soft_purge/1`, so the node's `detached` row and `collect_detached/0` stay. A unit of the rest makes no function a value can hold, so only a process in the middle of its code keeps one.

**The test.** `attached_functions`, written before the code. A session declares two types, a type that derives `compare`, a `foreign fn`, and a function whose body alone names the first type. It starts a process of the program's loop holding a lambda that computes the function on a bare peer, and a `restarting` service whose function is a lambda, and hands the function and both addresses to the program. It binds `let x = 1`, types `x + 1`, lists the session units the node holds, and detaches. A second session calls each through the process that holds it, makes the service fault and calls it after its restart, and lists the units again.

On the old code the holder faulted with `error:undef` at the declaring input's function, `'ern@$input1_1':'$1'/1` in the test's first form, and the step waiting on the next answer failed after its 30 s. With the rule but without the references, the type's unit was let go and the peer's compute failed as above. It passes in 5.2 s alone: six lasting inputs, the first type's input and the holder that the call of the service reads stay; the unused type's input, two holders, the unit of `x + 1` and the input that listed them go. The nodes tests took 3 min 23 s for 93 tests and take 3 min 31 s for 94, on one machine of eight cores.

**Not covered.** A unit kept in the `detached` row for a process mid-way through its code, which the tests before this one did not make either.

## An Expression's One Unit, and an Input's Cost Flat, 2026-10-30

MVP 4.0's items 11 and 12, decided the same day (*A Line-Mode Input's Cost*). A thousand inputs
of `1` in line mode took 12.0 ms an input and take 6.0; `let _ = 1` took 7.9 and takes 5.8. After
a thousand declarations `fn fN() : Int = 1` an input of `1` took 25.0 ms and takes 9.8, each the
median of three sessions less a session's time without the inputs. One session that times two
hundred inputs of `1` at its start and again after a thousand declarations `fn fN() : Int = N`,
by the clock it reads at the prompt, took 13.5 and 46.9 ms an input in one run, 3.5 times, and
takes 5.9 and 9.0, the median of three, 1.5 times; that session, 1,402 inputs, took 31.2 s and
takes 7.4. On one machine of eight cores.

**One unit.** An expression's unit holds the value `it` names. The emitter writes a getter of it
after the unit's definitions and foreign functions where the build asks it (`ern_compile`'s
`held`, `ern_emitter:held_position/1`), the interface gives its position, and the unit's
`'$code'/0` lists it as a binding of the input's entry, as a holder lists one. The input's process
puts the value under the getter's key once it has it. The session joins an interface of `it`
under the input's namespace, so a later input reads `it` with the call it makes for any
module's value. The unit is let go once a later expression binds `it` and no unit the session
keeps reads it; one whose code builds a function value keeps its code, and its value goes. Of
item 7's 10.0 ms of the host's work on two units, a holder's compile, load, delete and purge
are gone.

**What such a unit needs.** An expression's unit the session does not keep needs none of what its
code called, which runs no more, and holds what a holder holds, the units whose types its
interface names. Kept as the earlier holder of `it` was, `it + 1` typed again and again would
have chained every expression's unit to the one before it, and the unit test asks for that case.

**The record stays in its process.** Of the five places item 7 found the session's record
crossing, the check writes no row now. The input's process is given its unit, its entry, the
names it binds with their schemes and what its holder is named by, all made in the session's
process, and not the session. It answers what it bound, an interface, which the session joins
in its own process (`collect/2`), so the outcome and the checker in front of its address carry no
session. The row is written once, after the join. The highest holder's number is a row the
input's process takes, since it no longer answers a session.

**The environment kept.** The session holds the checker's environment over its interfaces
between inputs (`session_env/1`, `ern_typecheck:seeded/2`). An expression adds one interface and
lets one go. Each is the session's own, under a namespace no other interface shares, so the
change is the one taken out (`ern_typecheck:without_interface/2`) and the one added; a change to
any other interface, a load's, a reload's or another session's, makes it again. The node's
modules are read only where their version has moved (`synced/1`). The cache's argument: it holds
what the interfaces fix and goes with them or with the session, and the row holds none.

**The collection reads what it may let go.** Each unit is a row of its own. Two small rows hold
the units that hold a value or that the session does not keep, and of them those a kept unit
needs. A collection reads those alone, each reached by a name of its own in scope or needed by a
kept unit, where it read every unit and every name of the scope; the binders go by the same
reading. The printed names the checker is given are the declaring inputs', kept in the session.
A unit is recorded before it is made, so that an interrupted input's own unit, where the session
does not keep it, and a holder it began, are let go at the next collection; an interrupted
input's unit stayed loaded for the session's life before, taken for a kept input's.

## The Attached Shell's Own Node, Quiet, 2026-10-30

MVP 4.0's items 9 and 10, decided and stated in §11.2's *The attached shell* and Appendix E.27
the same day: an attached shell's own node tells no peer how busy it is, and says nothing of the
end or the loss of the node its session runs on.

**Item 9's cause.** The gateway told every listed peer that connected how busy the node is, the
node the shell attaches to among them. So at that node's prompt `Peer.utilizations()` held the
operator's node, and a `Peer.compute` that names no node could run there. The nodes test's
session showed it before the fix: `[#("ops", 0.375, 635)]`, and `Right(["node"])` for a compute
that named no node, `["node"]` being the operator's node's peers.

**Item 10's cause.** The shell's own node said `the peer b ended` through the launch's standard
error, whose sink is the session's screen, on `b`. That screen had ended with `b`. While the
stream's process stood the line was sent to it and lost; once the launch's end had stopped the
process, the line went to the job's own standard error, before or after the runner's `the node
b ended`. Held to the line alone, the line-mode test was red in 1 run of 16 and the terminal test
in 8 of 8.

**The fix.** The shell's job puts the node its session attaches to, by that peer's name on the
carrier, once the node's configuration is listed and before anything dials:
`ern_carrier:attaching/1`, a persistent term set once in the job's life. The gateway arms no
telling and tells no peer as it connects where the term is set (`ern_carrier:tells/0`). The
carrier's line for that node's end answers none, ended, lost or replaced, since the session ends
with the connection and the shell's line says it. `the peer b connected` stays, said before the
screen is named, as the guides show it. An ask by name, `Peer.utilization("ops", ms)`, is still
answered: E.27's telling is the frame the node sends unasked, and an ask is answered by every
node. A spawn or a compute that names the operator's node runs there, as the test's
`Peer.computeAt` shows.

**Why a persistent term.** The node's `#configuration{}` would lose the fact at a reload, which
replaces it. The term is read at each telling armed and each connection, set before the gateway
starts, and never changed, the runtime note's rule for the host's persistent terms.

**The tests.** `attached_utilization`, written before the fix and red on it. The end tests'
assertions were made strict before the fix, red as above; after it the line-mode test passed 16
runs of 16 and the terminal test 8 of 8. `ern_carrier_tests`' `attached_said`, a regression
test of the carrier's two answers. The deployment runbook's `ended/3` held standard error to the
line alone already, and met the race.

## The Rest Stays First, 2026-10-30

The record update's form was questioned: in `State(..state, session = e)` the base stands among the fields and reads as one, where OCaml writes `{ state with session = e }` and Erlang `State#state{session = E}`, the base first and apart. Weighed and kept as it is.

**The position is OCaml's own.** For a constructor with named fields OCaml writes `State { state with session = e }`, the constructor first and the base first inside, which is Ernest's order with `..` where OCaml writes the base and `with`. Standard ML has no update at all; Haskell, F#, Elm and Erlang put the base first with a token after it; Rust puts `..state` last by rule and Gleam first, as Ernest does. The reader of §0 predicts the shape (principle 1).

**The token serves three forms.** `..` means "the fields not given come from here" in the update, in the path, `Pool(..pool, stats.indexed = e)`, and in the fill, `Operations(..Set)`, where no value stands to put a `#` or a `with` after; a keyword would serve two of the three and leave the fill a second spelling (principle 2). `#` already marks a tuple, and `state#State(...)` would be Erlang's reading alone, as `with` would be OCaml's. Base first inside the parentheses is the order §5.6 evaluates in (principle 3). Rust's order, `State(session = e, ..state)`, was the one change that adds no spelling, and it costs that match; not taken. The report names the forms and not the token; in prose it is "the rest from `state`", since it gives the fields not named and spreads nothing.

## The Attached Shell's Last Row, 2026-10-30

MVP 4.0's item 8: where an attached shell's node ended or was lost, the runner's line, `the
node b ended` or `the node b is lost`, landed after the `> ` the screen last drew. At a
terminal the line also followed whatever was typed after the prompt, `> abcthe node b ended`.

**The cause.** The screen runs on the node and ends with the session, so at any end but a
detach nothing takes the region away: the operator's terminal keeps the region as last painted,
the cursor after the prompt. A detach is the session's own end, whose `finish` takes the region
away first. In line mode the prompt has no line feed until the next line is read.

**The fix.** The screen sends with each `Write` the bytes that end its drawing where that write
leaves it, and the local half keeps the last. At a terminal they are the region's `ending`:
what was typed after the prompt and the rows under it go, the tail and the prompt stay where
they stand, and the cursor goes to a fresh line, or to the start of the input's row where no
prompt stands. In line mode they are a line feed after a write that leaves its line unended.
At every end but a detach the local half writes them before it gives the runner its line. The
ending is nine bytes a write at a prompt, and costs 9 µs beside a paint's 110 µs, measured over
a hundred thousand of each.

**Not `finish` itself.** `finish` leaves a region later writes are drawn on, its rows 0, since
in a plain shell a subscriber may write after the session ended; the local half's end need not,
since nothing is drawn after it. `finish` also leaves an empty row after a prompt already ended,
at `C-d` and after `:quit` or `:detach` is entered at a terminal; the ending leaves none. Both
stay as they are: the empty row is no rule the report states, and no reader has asked.

**The tests.** Two nodes tests, written before the fix and red on the shell before it: in line
mode the prompt's line is ended before the line, and at a terminal, through the
pseudo-terminal's harness, the prompt's row holds the prompt alone and the line a row of its
own, for a node ended and one lost. The region's `Test` values hold its `ending`. The

## The Pun, 2026-10-30

A field given or matched by the variable of its own name is written `Desk(local = local)`, and
the repository's own Ernest writes that pair at 190 sites, half in patterns and half in
constructions, 42 of them with three fields or more: `Desk(local = local, size = size, color =
color, attached = attached)`. Whether the repeat could go was weighed on the principles. Decided: a
*pun*, `=local`, stands for `local = local` in a construction and in a pattern, `Desk(=local,
=size)`, mixing with the other forms, each field once; the word is the one the reader of Standard
ML, OCaml and Haskell has for it; built after MVP 4.0 as the plan's *The pun*.

**Two families, by the bracket.** Every language that puns a field bare gives its records a
bracket of their own, so the bare name can be nothing but a field: OCaml's `{x; y}`, Haskell's
`C {x, y}`, Standard ML's `{x, y}` in a pattern, Rust's `P { x, y }` beside its positional
`P(x, y)`, Elm's, PureScript's, Lean's and JavaScript's. Every language that writes named fields in
the call's parentheses, as Ernest does, has no shorthand, Erlang, F#, Scala, Kotlin and Swift among
them, or marks the pun as a trailing label with its value left out: Gleam's `C(x:, y:)` since its
1.4 and Ruby's `f(x:, y:)` since its 3.1. Python's PEP 736 proposed the trailing form with Python's
own token, `f(x=)`, and its steering council rejected it in 2025 as costing more in reading than it
saved. Haskell's `C {..}`, every field at once, is the form its style guides warn against.

**The bare name and the trailing mark.** The bare name is the first family's and collides in
Ernest: `Desk(local)` has the shape of `Some(x)` and of a call, the one-field string derives two
ways in Appendix A with the declaration deciding, and `Append(path, bytes, reply)` reads as
positional, which Ernest has no form for (principles 3 and 4). The trailing mark is the answer of
Ernest's own family, but with Ernest's `=` it is the spelling Python rejected: `local =` reads as
a value forgotten, the reader waiting at the hole.

**The other marks.** `?local` is Erlang's macro to the reader of §0, `local?` asks a question
where a pun asserts, and `~local` is OCaml's label with a token Ernest lacks; each of `?`, `@`,
`&` and `~` is free and means nothing here, so any would be learned for this job alone (principle
5). `Desk(..)`, every field by its name, puts no name at the use site, which principle 3 refuses
as it refuses a fill from the scope. A bracket of records' own would change every constructor in
every program. The dot, `.local`, was the first choice, Ernest's own word for a field in
`desk.local`; it gives the dot a second role, prefix beside postfix, and sets `Desk(..d, .local)`
beside an update that means something else.

**The leading `=`.** `=local` is the pair's own form with the repeated name left out, so a reader
who knows `Desk(local = l)` reads it untold, which principle 1 decides, the reader who knows Ernest
first; it is the family's answer, Gleam's and Ruby's `x:`, in Ernest's token; the value stays in
view and the name it carries is left out, where the trailing form leaves the reader waiting;
nothing in Ernest begins with `=`, so the parser reads it on its first token (principle 4); and it
stands clear of `..`. No language writes it, so §5.6 states the departure, which §0 allows.

**Principle 2's sentence gains the scope.** A second spelling "that only shortens stays out", and
the pun shortens; but the same sentence admits the fill, which pairs each field with the
declaration of its name in one namespace, and the pun is that pairing one scope down, with the
local of its name, as visible as the fill since every name stands at the use site. The sentence
gains the scope beside the namespace rather than being overridden, and the style guide says a
field whose variable bears its name is written as a pun, so one site has one spelling.

`=f` is `f = f` read textually, so it gives whatever `f` names where the construction stands, a top-level
function among them, and stands in a record update and a fill as in a plain construction. A pun
names a field, so a single-positional constructor takes none: `Some(=x)` is refused, its error
naming `Some(x)`, since a pun there would shorten nothing (principle 2).

**Weighed beside it and left out.** Function clauses, `fn len([]) = 0 | len(x :: r) = ...`, which

comprehensions, Erlang's and Haskell's: the reader of §0 knows Erlang for its values and
processes, not its expression forms, and the pipe of `List.filter` and `List.map` is the one way.
Composition, `f >> g`: it serves point-free style, which a language without currying does not
write, and the pipe covers the value. Currying, operators as values and string interpolation stood

## `Test.until`, Built, 2026-10-30

MVP 3.96's item 8, decided from feedback 166 (*What the Newcomer's Feedback Left*): `Test.until(run, ms)` runs a test again until it passes or the milliseconds end, and answers the last `Result`. Three shapes were decided as it was built.

**The last `Result`, not `Left(Timeout)`.** E.0 shape rule 8 has a function that takes milliseconds answer `Left(Timeout)` when they pass. `until` answers the last run's `Result` instead, since a test's finding is its `Failed` text, `expected 3, got 2`, which a `Timeout` would hide; its milliseconds bound how often the test is run and no one request. Rule 8 names the exception, and E.24 states it.

**No wait between runs.** Between a `Failed` and the next run, `until` waits for nothing: the test runs again at once. A pause would be a number no one can derive, since what the test waits for, the runtime's delivery of a `Down` and the recipient's handling of it, has no measure, and *No fixed sleep* refuses a chosen one. A test that calls a server is paced by the server's answers; one that reads a table alone spins for at most `ms`, in a test. The plain form is kept and its cost named here.

**`run`, not `test`.** The callback has the type of a `Case`'s `run`, `() -> Result receiving m`, and takes its name; `test` is the glossary's predicate asked of each element, which this is not. It runs in the caller's process, so a fault in it is the caller's, as a direct call's; `faults` alone runs its call apart, since what it tests is the end.

**Built** in Ernest alone, `until` over a helper that carries the deadline, with its page and three tests of `ern test`'s output. The test of a server counting the `Down`s it is told of, run without `until`, was red in each of twenty runs, the server answering before the death reached it; with it, green.
