## What a Lambda's Reach Finds on a Peer Built, 2026-11-08

*Superseded in part 2026-11-08 by "A Top-Level Binding Stays the Node's" and "The Shell Attaches as a Program Spawns": the load of a unit for a binding of the reach goes, the two bindings being constants, and item 27 takes the recommendation under What it leaves widened to every binding the node holds, not the rows under The fix.*

MVP 4.15's item 15, built by an item session on the decision of *What a Lambda's Reach Finds on a Peer* (§8.7, §11.2, §12.7).

**The shape.** One finder, `ern_peer:unvalued/1`, answers for a binding of the reach without its value. It gives the unit of the toolchain's own that holds the binding, found by its hash in the tree's index (`ern_code:own_unit/1`), or what the node lacked. It is called at the two sites the plan names: where the exchange reads the reach (`reach_lacked/2`), and where a function the node holds is started (`frame/2`, on the run's answer).

The load is the one a spawned function of the toolchain's own already had, run in a process of its own. What follows it differs by site, so the plan's one function is two. The runtime cannot call the nodes, so the held path's frame goes back to the gateway, which hands it to the exchange (`ern_exchange:lacking_value/4`). The exchange path keeps its exchange and its time, and reads the reach again when the load answers, asking the spawner nothing more.

**The reading ends.** A unit is loaded at most once for one exchange or one frame. A binding still without its value after the load answers `NotLoaded`, as where the node holds other code under the unit's name. A load that fails answers `Other(text)`, as §12.7 says.

**The held path's test.** The plan's sketch, a second spawn of a function the node then holds, does not reach the held path's load. On a bare node the first spawn's load has given the unit its values, and the held spawn finds them. The held path needs a runtime whose marks have gone since the arrival, which a run of `ern test` over a directory makes, each module in a runtime of its own. So a second test runs three such modules on the peer, and spawns and computes in each run. With the held path's load disabled, its second run answered `NotLoaded`, so the test covers it. Both tests were written before the code.

**A defect the probe found.** A lambda whose reach names no binding, spawned first on a bare node, brings its enclosing definition whole. The arrival links the definition's other reads of `Ansi.clearBelow` and `Ansi.clearScreen` to faults, since the node holds them without values then (§12.7). The arrival's code still calls `libs/ansi`'s unit, for `Ansi.styled`. Once a load had given that unit its values, a held spawn of the lambda that reads `Ansi.clearBelow` found the binding valued in a unit its code calls. It started, and faulted on the link, and a compute faulted its caller. Before the item the spawn answered `NotLoaded`, the unit having no values. A shell's attach, which loads the toolchain's own units, could reach the fault the same way.

**The fix.** The arrival gives the code table the bindings it linked to a fault (`ern_code:loaded/4`), in rows that go with the unit. A spawn's check reads them before it asks the run (`ern_code:lacked/2`). Where a unit the function's code calls reads a binding of the reach from a fault, the spawn answers `NotLoaded`, and the node says the binding had no value here when its code arrived. That is the reading *MVP 3.1 Read* decided: a binding read through several units has its value only where each does. The text is the foreign case's, which says a module was not here when its code arrived (*The Report for Code with a Spawn*).

Nothing is loaded for such a binding, since no load changes the link. The check costs one lookup per binding of a held spawn's reach, and the walk over the called units only where a row is found. A regression test of the probe's case was written before the fix, and failed on the fault.

**What it leaves.** Which spawn comes first decides whether the bare node runs `fn() = Io.show(Ansi.clearBelow)`: first, it runs; after a sibling lambda of its definition, it answers `NotLoaded`. That is §12.7 as written, since the binding lay beyond the first spawn's reach. But it surprises (principle 1), and no program can avoid it short of the node's restart. Changing it changes §8.7 and §12.7, so it is a decision for the user, in a design session, and stands as MVP 4.15's item 27.

The recommendation is that an arrival links a binding of the toolchain's own beyond the reach to its unit, as it would link a valued one, and leaves the fault for a program's binding. A later spawn whose reach names the binding then finds it without its value and loads the unit, by the check this item built. The arrival loads nothing it does not need.

## A Top-Level Binding Stays the Node's, 2026-11-08

*Superseded in part 2026-11-08 by "The Shell Attaches as a Program Spawns", the same day and before anything built it: a bare node evaluates the standard library's bindings alone, the two bindings being constants; the rule and item 27 stand.*

Decided with the user on 2026-11-08, in a design session the item session briefed after item 15's build raised item 27, when the user asked whether the nodes were drifting from KISS. The rule stands: in a spawned function a top-level binding is the peer's (§8.7), a constant crosses as code (§4.6) and a capture crosses as a value (§3.11). The exception for the toolchain's own units shrinks back to the shell's code: a bare node evaluates the libraries' bindings at its start, as it evaluates the standard library's (§8.5, §12.7), and the load of a unit for a binding of the reach, decided 2026-11-07 and built the next day, goes. Item 27 is decided as recommended and widened: an arrival links any binding the node holds without its value to its holder, a program's among them, since the defect's other form is a program's binding and a toolchain binding is no longer a class of its own once its unit is evaluated at the start (§12.7).

**What other systems do.** The question is forty years old and has three answers. Emerald and Obliq keep a moved closure's free names pointing at the site where they live, each read a round trip. Unison, Cloud Haskell's static pointers and Spark's `object`s take a top-level definition as code, fetched by hash or by class and evaluated once where it runs. Erlang's funs over modules, Scala's spores, Akka's `Props` and Gleam's `const` make a top-level name the receiving node's, a local an explicit capture and a constant part of the code. Ernest's rule is the third, §4.6's constant being Erlang's macro and Gleam's `const`, and §3.11's lambda a spore whose captures the compiler reads.

**Unison's answer, and why Ernest cannot take it.** A top-level term in Unison is pure unless its type names an ability and the term is delayed, so evaluating one on the receiving node starts nothing the sender did not write a fork for, and that is in the type. Ernest's top level is where a program starts its processes: §4.6 makes an initializer a body at `Never` that may spawn, send and call, §6.5 makes a service a binding, and §0 keeps a send out of every type. *What the Outline Asked* refused evaluation on arrival for that reason, and the purity walk that would make it safe as a second mechanism beside the ground term. The log's standing sections on Unison keep what Ernest took and left.

**The roots weighed.** Evaluating a binding on the peer, Unison's way, is refused as above and for a second surprise: a service binding evaluated on a bare node gives the spawned function a fresh service there, where today the spawn answers `NotLoaded`; principle 3. Refusing at compile time every spawned function whose reach names a non-constant binding would make a static refusal of a run-time value, but whether the peer holds the value is a fact of the deployment, which principle 3's own sentence makes a value or a fault when it runs; it would also refuse the deployment the guide's §8.1 teaches, a function on a peer running the same program reaching that peer's service, and let a library's private binding decide which of its functions can be spawned.

**A binding's value crossing with the code**, the item session's lean, is lexically right for a reader of ML and was refused on three grounds, the last decisive. Principle 1's reader has values and processes as Erlang has them, where a module-level value is a function evaluated on the remote node or a macro in the code, so the rule as stated is that reader's prediction, and §8.2's system processes are an instance of it rather than an exception. *A binding belongs to its node* already argues that a value to carry is captured so that the text shows what crosses; under this root every binding in the transitive reach crosses with every spawn, which Spark's users meet as the reason `broadcast` exists.

And the root cannot be built as a rule of the exchange. Compiled code reads a binding through its unit's getter, and a peer that runs the same program holds that code in its own unit, whose getter answers the peer's slot. For the code to read the spawner's value on every peer, every binding read on every node would consult a per-process environment inherited through spawn chains, and a bare node would hold two spawners' values of one binding: the code table's design, a binding found where it was evaluated, rebuilt, and every program's binding reads taxed for a case nothing in `examples/`, the tour or the nodes tests writes but to show `NotLoaded`. Principle 1 decided for the rule, with 3 and 5 beside it.

**The exception's shape.** What a developer must know to predict `Peer.spawn` is three sentences of the rule, a capture crosses, a binding is the node's, a constant crosses, and four of the toolchain exception, *The Shell's Own Node* extended to bindings by item 15: that a binding of four units is loaded from the peer's tree, that a peer of another build answers `NotLoaded` for it, that which sibling lambda crossed first decides between running, `NotLoaded` and a fault, and the guide's line that a restart of the node clears it. Item 27 is that extension's defect. A bare node already holds the toolchain's libraries, which §11.2 puts on its load path, and their bindings are two strings in `libs/ansi`, test cases in `libs/markdown` and none in `libs/ets`. Evaluated at the node's start they have their values before any arrival, so the order dependence goes, the split between `Ansi.clearScreen` and a program's `let cls = Ansi.clearScreen` is the one the guide's §8.1 teaches for `Map.empty`, and a peer of another build falls under the general rule, a binding held or lacked by hash.

The two grounds *What a Lambda's Reach Finds on a Peer* set this aside on are answered. "Charges every program for what it does not use" was weighed for every node's start; a bare node has no program, and a program node changes nothing: one that runs another program and lacks the library answers `NotLoaded` by the general rule, where the load would have served it. "Leaves the shell's load as a second mechanism": the shell's unit is a program's and on no load path, so its load on attach stays under either shape, and the load of 2026-11-08 made it serve two things. The mechanism decided on 2026-11-07 is reversed and its result kept, the lambda serving on a bare node. Principle 1 decided, the reader predicting a bare node's libraries from its standard library.

**Item 27.** The defect predates item 15 in a rarer form: an arrival that names a load-path module's binding beyond its reach, held without value, links a fault; a shell's `:load` of that module gives the binding its value; a later spawn of a sibling lambda passes the check and faults on the link. Recording the faulted bindings per unit refuses a later function whose reach names the binding and whose code calls the arrival for anything else, though it reads the binding through a valued getter elsewhere, and per definition needs a second reach. So the arrival links a binding the node holds without its value to the unit that holds it, as it links a valued one, and the fault stays for one held in no unit; the check reads the holder where the code does, valued or not. Soundness section 7 says so.

**The cold reading**, one reader over the sentences before the build, as CLAUDE.md asks of a rule of §3 to §9: eight lines fixed as read, nine decided. §12.7 names the unit a link reaches among several, the latest loaded with its value or the latest loaded of all where none has, and so states for the first time where a valued binding is linked too. §8.7's check points at §11.2's form, the unit the code reads a binding from, since the two sentences decided a case differently. §11.2 keeps its pointer to §12.7's load for a function of the toolchain's own, whose units the node evaluates first, a case that stands. The soundness sentence for a toolchain binding went, §8.5's evaluation being §8.5's. §4.2's hiding of a toolchain library by a program's module of its name, on a bare node's load path, is the build's to state in §8.5.

**Built by the item session**, named in the plan's items 15 and 27: the binding half of the 2026-11-08 build reverted, the bare node's start evaluating the three libraries' units it holds after the standard library's, item 27's link, the held-path test's expectation the general rule's, and the design notes, the deployment guide and the architecture map following the code.

## The Shell Attaches as a Program Spawns, 2026-11-08

Decided with the user on 2026-11-08, the same day as *A Top-Level Binding Stays the Node's*, whose §8.5 clause it removes before anything built it. The toolchain's own units are no class of the exchange: the shell's definitions cross to the node it attaches to as any program's do, by hash, and `libs/ansi`'s two bindings, `clearBelow` and `clearScreen`, become the string literals they are, constants (§4.6) that cross with the code, and four bindings of the shell's own become functions or captures (below). §12.7's *The toolchain's own units* goes, with the spawn frame's mark of whose unit a function is, Appendix F's term, §8.5's and §8.7's clauses, E.27's third cause of `NotLoaded` and the attach's refusal of another build (§11.2). A bare node evaluates the standard library's bindings and no other, and nothing is initialized because a peer asked.

**The reason, and what the shell gives.** *The Attached Shell's Cut* made the load from the tree because "the first attach would have carried the whole shell as forms whose bindings had no value on the node". The reach of the shell's session half names six such bindings today. `libs/ansi`'s `clearBelow` and `clearScreen` are `"\u{1b}[" <> "J"` and its like, and become the literals they are. Four are the shell's own, `Ernest.Shell.localMs`, a sum over a call, `Ernest.Shell.defaults`, a record whose field names a constant, `Ernest.Shell.Command.settingsAbout`, a call, and `Ernest.Shell.Command.commands`, a list whose entry names it; they become functions or captures, as the guide's §8.1 has every module meant for a bare node write such a value. The shell's other bindings, `colorAllowed` and the history's three paths, are the local half's and cross nowhere; `libs/markdown`'s are test cases and `libs/ets` has none.

Item 15 then extended the load to a binding of the reach, item 27 was that extension's defect, and this morning's decision moved the libraries' values to the bare node's start, which still named four units in the language report. The shell follows the rule every program follows, and the side door goes.

**Why it is right, and not only possible.** The shell is the one program of ours that starts a process on another node every day, and it did so through a side door. Under the exchange it lives by the rules every program lives by, the hash, the floor and the foreign module whose doing is the node's (§8.7); where those rules fail the shell they fail ernest-httpd, and that is a finding to meet before the launch. The floor, not the build, is Ernest's unit of compatibility, so that a fleet rolls patch by patch, and the attach was the one operation that demanded an exact build. Principle 5 decided, a class, a frame's field, an index and a loader going for two literals; principles 2 and 1 hold beside it, code reaching a node one way and the shell being a program.

**Whose shell runs on the node.** The operator's. Its Ernest half, the editor, the completion and the commands, crosses from the operator's build; its Erlang half, the checker and the emitter that compile each input and some fifty foreign declarations of the shell's, `version()` among them, runs on the node and is the node's. That is the right split, since code that runs on a node is compiled by that node's toolchain. The local half, the terminal and the files on the shell's own node, and the session speak the shell's own typed messages and must be one build, and they are.

A node of another release on the floor runs the shell where it answered `NotLoaded`, and the start line names the node's release, which the session's `version()` answers there (principle 3). The patch rule holds every foreign declaration's type and, from today, the protocol's version (§8.7), and the release review's patch check names the shell's declarations with the library's. Erlang's `-remsh` runs the remote node's shell; a node of Ernest's has no shell of its own, and the tool comes to it.

**Costs.** The first attach to a node ships the shell's own definitions as forms, once per node per shell build, where the tree's load took 0.27 seconds; the libraries' code ends every job's load path already (§11.2) and crosses nowhere, so the exchange carries the shell alone, and the build measures it. A node holds an arrival of the shell for each shell build that attaches, bounded by the builds. An attach measured in seconds would be a slow exchange, fixed at its cause and never by a path around it.

**The cold reading**, one reader over the sentences: the entry's count of the shell's bindings was wrong and is corrected above; §11.2's list of what crosses between the shell's two nodes gained the shell's definitions; the start line's `v` is the shell's version text, since two toolchains are in play; and §8.7's patch rule, which the cookie's protocol version could break silently, now names that version, §12.5 pointing at it where it restated the rule.

**Built by the item session**, the plan's item 15: the two bindings as literals and the shell's four as functions or captures; the own-unit index, loader and frame mark removed with the exchange's branch, the protocol's version moving before the release; item 27's link; the attach tests, `attach_other_build` among them, its other build changing a function's body and expecting the run and the start line; and the design notes, the deployment guide's lines on the attach and on a binding without a value, and the architecture map following the code.
