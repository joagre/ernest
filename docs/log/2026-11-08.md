## What a Lambda's Reach Finds on a Peer Built, 2026-11-08

*Superseded in part 2026-11-08 by "A Top-Level Binding Stays the Node's" and "The Shell Attaches as a Program Spawns": the load of a unit for a binding of the reach goes, the two bindings being constants, and item 27 takes the recommendation under What it leaves widened to every binding the node holds, not the rows under The fix.*

**The shape.** One finder, `ern_peer:unvalued/1`, answers for a binding of the reach without its value. It gives the unit of the toolchain's own that holds the binding, found by its hash in the tree's index (`ern_code:own_unit/1`), or what the node lacked. It is called at the two sites the plan names: where the exchange reads the reach (`reach_lacked/2`), and where a function the node holds is started (`frame/2`, on the run's answer).

The load is the one a spawned function of the toolchain's own already had, run in a process of its own. What follows it differs by site, so the plan's one function is two. The runtime cannot call the nodes, so the held path's frame goes back to the gateway, which hands it to the exchange (`ern_exchange:lacking_value/4`). The exchange path keeps its exchange and its time, and reads the reach again when the load answers, asking the spawner nothing more.

**The reading ends.** A unit is loaded at most once for one exchange or one frame. A binding still without its value after the load answers `NotLoaded`, as where the node holds other code under the unit's name. A load that fails answers `Other(text)`, as §12.7 says.

**The held path's test.** The plan's sketch, a second spawn of a function the node then holds, does not reach the held path's load. On a bare node the first spawn's load has given the unit its values, and the held spawn finds them. The held path needs a runtime whose marks have gone since the arrival, which a run of `ern test` over a directory makes, each module in a runtime of its own. So a second test runs three such modules on the peer, and spawns and computes in each run. With the held path's load disabled, its second run answered `NotLoaded`, so the test covers it. Both tests were written before the code.

**A defect the probe found.** A lambda whose reach names no binding, spawned first on a bare node, brings its enclosing definition whole. The arrival links the definition's other reads of `Ansi.clearBelow` and `Ansi.clearScreen` to faults, since the node holds them without values then (§12.7). The arrival's code still calls `libs/ansi`'s unit, for `Ansi.styled`. Once a load had given that unit its values, a held spawn of the lambda that reads `Ansi.clearBelow` found the binding valued in a unit its code calls. It started, and faulted on the link, and a compute faulted its caller. Before the item the spawn answered `NotLoaded`, the unit having no values. A shell's attach, which loads the toolchain's own units, could reach the fault the same way.

**The fix.** The arrival gives the code table the bindings it linked to a fault (`ern_code:loaded/4`), in rows that go with the unit. A spawn's check reads them before it asks the run (`ern_code:lacked/2`). Where a unit the function's code calls reads a binding of the reach from a fault, the spawn answers `NotLoaded`, and the node says the binding had no value here when its code arrived. That is the reading *MVP 3.1 Read* decided: a binding read through several units has its value only where each does. The text is the foreign case's, which says a module was not here when its code arrived (*The Report for Code with a Spawn*).

Nothing is loaded for such a binding, since no load changes the link. The check costs one lookup per binding of a held spawn's reach, and the walk over the called units only where a row is found. A regression test of the probe's case was written before the fix, and failed on the fault.

**What it leaves.** Which spawn comes first decides whether the bare node runs `fn() = Io.show(Ansi.clearBelow)`: first, it runs; after a sibling lambda of its definition, it answers `NotLoaded`. That is §12.7 as written, since the binding lay beyond the first spawn's reach. But it surprises (principle 1), and no program can avoid it short of the node's restart. Changing it changes §8.7 and §12.7, so it is a decision for the user, in a design session, and stands as MVP 4.15's item 27.

The recommendation is that an arrival links a binding of the toolchain's own beyond the reach to its unit, as it would link a valued one, and leaves the fault for a program's binding. A later spawn whose reach names the binding then finds it without its value and loads the unit, by the check this item built. The arrival loads nothing it does not need.

## A Top-Level Binding Stays the Node's, 2026-11-08

*Superseded in part 2026-11-08 by "The Shell Attaches as a Program Spawns", the same day and before anything built it: a bare node evaluates the standard library's bindings alone, the two bindings being constants; the rule and item 27 stand.*

Decided with the user on 2026-11-08, in a design session the item session briefed after item 15's build raised item 27, when the user asked whether the nodes were drifting from KISS. **What other systems do.** The question is forty years old and has three answers. Emerald and Obliq keep a moved closure's free names pointing at the site where they live, each read a round trip. Unison, Cloud Haskell's static pointers and Spark's `object`s take a top-level definition as code, fetched by hash or by class and evaluated once where it runs. Erlang's funs over modules, Scala's spores, Akka's `Props` and Gleam's `const` make a top-level name the receiving node's, a local an explicit capture and a constant part of the code. Ernest's rule is the third, §4.6's constant being Erlang's macro and Gleam's `const`, and §3.11's lambda a spore whose captures the compiler reads.

**Unison's answer, and why Ernest cannot take it.** A top-level term in Unison is pure unless its type names an ability and the term is delayed, so evaluating one on the receiving node starts nothing the sender did not write a fork for, and that is in the type. Ernest's top level is where a program starts its processes: §4.6 makes an initializer a body at `Never` that may spawn, send and call, §6.5 makes a service a binding, and §0 keeps a send out of every type. *What the Outline Asked* refused evaluation on arrival for that reason, and the purity walk that would make it safe as a second mechanism beside the ground term. The log's standing sections on Unison keep what Ernest took and left.

**The roots weighed.** Evaluating a binding on the peer, Unison's way, is refused as above and for a second surprise: a service binding evaluated on a bare node gives the spawned function a fresh service there, where today the spawn answers `NotLoaded`; principle 3. Refusing at compile time every spawned function whose reach names a non-constant binding would make a static refusal of a run-time value, but whether the peer holds the value is a fact of the deployment, which principle 3's own sentence makes a value or a fault when it runs; it would also refuse the deployment the guide's §8.1 teaches, a function on a peer running the same program reaching that peer's service, and let a library's private binding decide which of its functions can be spawned.

**A binding's value crossing with the code**, the item session's lean, is lexically right for a reader of ML and was refused on three grounds, the last decisive. Principle 1's reader has values and processes as Erlang has them, where a module-level value is a function evaluated on the remote node or a macro in the code, so the rule as stated is that reader's prediction, and §8.2's system processes are an instance of it rather than an exception. *A binding belongs to its node* already argues that a value to carry is captured so that the text shows what crosses; under this root every binding in the transitive reach crosses with every spawn, which Spark's users meet as the reason `broadcast` exists.

And the root cannot be built as a rule of the exchange. Compiled code reads a binding through its unit's getter, and a peer that runs the same program holds that code in its own unit, whose getter answers the peer's slot. For the code to read the spawner's value on every peer, every binding read on every node would consult a per-process environment inherited through spawn chains, and a bare node would hold two spawners' values of one binding: the code table's design, a binding found where it was evaluated, rebuilt, and every program's binding reads taxed for a case nothing in `examples/`, the tour or the nodes tests writes but to show `NotLoaded`. A bare node already holds the toolchain's libraries, which §11.2 puts on its load path, and their bindings are two strings in `libs/ansi`, test cases in `libs/markdown` and none in `libs/ets`. Evaluated at the node's start they have their values before any arrival, so the order dependence goes, the split between `Ansi.clearScreen` and a program's `let cls = Ansi.clearScreen` is the one the guide's §8.1 teaches for `Map.empty`, and a peer of another build falls under the general rule, a binding held or lacked by hash.

The two grounds *What a Lambda's Reach Finds on a Peer* set this aside on are answered. "Charges every program for what it does not use" was weighed for every node's start; a bare node has no program, and a program node changes nothing: one that runs another program and lacks the library answers `NotLoaded` by the general rule, where the load would have served it.
