# The decisions log, 2026-10-05

## The Library Stands on the Host, 2026-10-05

E.0 rule 1 had the standard library written in Ernest wherever Ernest could express the work, `foreign` only for what the host alone can do, and a primitive beneath an Ernest function only where the Ernest form cost more than three times the host's (*The Full Review's Questions, One by One*). MVP 2.99d's first measurement put numbers on it: the `Path` functions 20 to 90 times the host's, `List.sort` 7, `List.reverse` and `Bytes.toList` 5, `List.unique` quadratic where the host has `lists:uniq`. Decided with the user: the line goes, and the rule with it. Where the host has the function, Ernest stands on it, so that wherever the host can do the work an Ernest program is as fast as Erlang.

**Why the cost is acceptable.** A pure standard-library shim is light: its return is the runtime's own and not checked, and the `try` around it is free on the host; `Map.get` over `maps:find` measured 1.0 to 1.1. What the change gives up is named and accepted: less of the language tested by writing the library in it, more code trusted by its type where the soundness argument argued Ernest's, and a library whose behavior follows the OTP pinned for a deployment, as the runtime's already does.

**The form, the sharper of two.** One reading shimmed every function the host maps to or almost maps to, its adapter in Erlang inside the shim. The other, taken, is the same speed with the adapter where the compiler sees it: where a host function does exactly the work, the Ernest function is its shim; where it almost does, the gap, an index from 0, a `None` where the host raises `badarg`, another set of white space, is closed in Ernest around a shim that is the host function exactly. That is where the bugs of such code live, and Ernest types them, shows them on the page, and lets the laws machine hold them. Where an Ernest adapter measurably costs, in a loop the host runs for it, the adapter is Erlang, and the measurement decides. Where no host function does the work, the function stays Ernest, and its speed comes from the emitter, MVP 2.99d's item 3.

**The rule written, and the callback.** E.0 rule 1 now admits an operation that a host function does exactly as a primitive, and the glossary's *primitive* and CLAUDE.md's *Shims* say the same. Two consequences were found in writing it. A primitive calls the functions it is given, as `lists:sort` calls a comparison, where the old rule had a primitive call none but a wrap it delivered through. A fault raised in such a function already passes through a shim as itself, and the library's shims already give a function to the host unwrapped and take its return unchecked. But the emitter counted a standard shim with an effect as foreign code while it ran, and for a higher-order primitive the effect is the callback's: a callback that waited for what no one sends was counted as foreign code, and the deadlock was not found. A standard library function whose effect is only a function's it is given is no longer counted, since what waits is Ernest and is watched as Ernest. And exactly is by the host's own documentation: `lists:map`'s says its order of evaluation depends on the implementation, where `List.map` promises its function is applied in order, so `lists:map` is not exact for `List.map`, and each conversion reads the page for such a difference.

## A Foreign Function Marks Its Equality, 2026-10-05

Converting `List` to the host's functions under the new E.0 rule 1 found that a primitive's type is its signature alone, and a signature could not state what a body's inference gives. A type variable a body compares with `==` takes the equality constraint (§3.10); a `foreign fn` has no body, its signature could write the mark only on a foreign type's parameter, and §4.7 gives each of its variables the not-reply-carrying restriction, since foreign code may copy or drop a value. So `List.contains` over `lists:member` would type as `(List(a!), a!) -> Bool`, the constraint lost, and `List.contains([f], g)` would compile, the host comparing two closures where §3.10 says there is no answer. Nothing of this is a check at run time: both restrictions are the scheme's, checked at each instance, and a shim costs nothing for them.

Decided with the user: a foreign function's signature writes the mark, `a=`, the one a foreign type's parameter writes, and the checker puts the constraint on the scheme as the inference would put it on a body's. The mark only narrows the instances a scheme admits, so it is sound whatever the foreign code does, and it is a promise of the foreign code's as its types are: one that compares values at an unmarked variable breaks it, as one that answers another type does. `docs/soundness.md` says both.

**Where it is written.** The first form put `[ "=" ]` after every type variable, the mark taken where the token after the `=` may follow a type, so that `fn f() : a = x` keeps its body. The generated programs found the hole at once: `needs` is an identifier read by its place, so in `fn f(needs : a) : a = needs` the token after the `=` follows a type and begins a body alike. The mark stands in a list of types instead, Appendix A's `ListedType`: a type's arguments, a tuple's components, a function type's parameters, and a foreign function parameter's whole type. There `=` follows nothing else, so the parser decides by the `=`, and no `=` that ends a type is ever read as a mark. What it gives up is the mark on a function type's result, `(Int) -> a=`, which a variable that occurs elsewhere does not need, and on a bare variable in parentheses, `(a=)`, which is refused with what to write.

**Written once.** The mark is the variable's, as `k=` is a foreign type's parameter's, so it is written once, on any of the variable's occurrences in the parameters; a second mark is refused, and so is one in the result type or in any annotation outside a foreign function's parameters, where a body's `==` says it. Writing it at every occurrence, as a type prints, was weighed: a function type's result cannot carry it, so the rule would need an exception, and the result type would carry it too, where the parameters already decide the variable. Writing it at the first occurrence alone was weighed and not taken for the same exception.

**Not-reply-carrying stays.** §4.7's restriction is what keeps a reply out of foreign code that stores or drops it, and the library's primitives keep it. A function whose Ernest type carries a reply, `List.reverse`, `List.foreach`, `List.foldRight`, `List.indexed`, `List.unzip` and `List.<>`, would take the restriction as a primitive, and the supervisor's own `List.foreach` over the replies it holds would no longer compile; so by E.0 rule 1 the host's function is not exact for it, and it stays Ernest. Lifting the restriction would take a second mark a program writes. Measure first: `List.reverse` costs 3 to 4.5 times the host's, the others 1.0 to 3, and the mark is decided, or not, with the numbers of the next measurement.

## String Stands on the Host, 2026-10-05

E.5 promises that every search matches whole graphemes, and the `string` module's page says that its `find`, `replace`, `split` and `trim` leave grapheme clusters of `prepend` code points and of decomposed Hangul unhandled, for speed. Agreed with the user first: take that rule of the host's and state it in E.5, so that the searches could be its shims. Probed before writing the sentence, the host does not keep its page. A match must end where a grapheme ends, but may begin inside one: `string:find` finds `"\u{301}"` inside `"a\u{301}"`, the second emoji of a joined sequence, and the line feed of `"\r\n"`, which the same page calls one grapheme, so `string:split("a\r\nb", "\n", all)` cuts the carriage return off; `string:trim` with `"\n"` takes the line feed out of a final `"\r\n"` too. No sentence of E.5 can take that rule honestly: it is not the page's, it breaks E.5's own example, and a release of OTP that keeps the page would change it under the program. So E.5 is as it was, and the searches stay ours, over the host's segmentation. The report of the defect to OTP's maintainers is the user's.

**What stands on the host.** `repeat` is `binary:copy/2` around a count below 0. `join` is `lists:join/2` and `erlang:iolist_to_binary/1`. `toInt` and `toIntBase` are `binary_to_integer/2`, whose forms are E.5's but a leading `+`; it raises where E.5 answers `None`, which Ernest cannot catch, so the two are closed in `ern_string:to_integer/2`, the `+` refused beside the raise. At 10,000 characters `toInt` went from 42 us to 0.35 us, its growth gone.

**What stays Ernest, and why.** `startsWith` has `string:prefix/2`, which keeps whole graphemes in every case probed, prepend, Hangul, `"\r\n"` and flags among them; but it answers the rest of the string or the atom `nomatch`, no Ernest value. Through an adapter it measured 1.2 to 1.5 times the host's, where the Ernest over the host's `string:length` and `string:slice` measures 1.0 to 1.1, so the Ernest stays: the host does its work already. `trim` and `words` have `string:trim` and `string:lexemes`, whose whitespace is Pattern_White_Space where E.5's is White_Space, and which compare whole graphemes where E.5 reads a grapheme's first code point. `padStart` and `padEnd` have `string:pad`, which pads with one grapheme where E.5 pads with a string's copies cut to fit. `endsWith` and `lines` have no host function.

**`split`, read once.** `split` asked `indexOf` for the next separator, then `drop` and `slice` for the parts, each walking the graphemes from the part's start: three walks. A primitive of the same kind as `indexOf`'s, `around`, answers the string before the first match and the string after it in one walk, and `split` is Ernest over it. And the walk measured each grapheme by converting it back to UTF-8; `string:next_grapheme/1` answers the rest of a binary as a binary, so the grapheme ends where the rest begins, which the walk now reads, measuring a grapheme only where the rest comes back in another form, as it does at the end of a string after a prepend code point. The laws machine found that case on the change's first run. Measured: `split` from 2.6 to 3.8 times the host's `string:split` to 1.3 to 2.6, `replace` from 2.7 to 4.2 to 1.4 to 2.0, `contains` from 2.0 to 2.4 to 1.3 to 1.7, each still matching whole graphemes where the host's does not. `Path`, Ernest over `String`, followed: `parent` at 100 graphemes from 33 times `filename`'s to 10, `name` from 41 to 22, `extension` from 82 to 44.

**`Path`.** The `filename` pages state none of E.14's edge cases, the empty segments, a separator at the end, the root's name, the dots that begin a name, so no host function is exact for a `Path` function, and `Path` stays Ernest under E.0 rule 1. What remains of its cost is its own: `name`, `extension` and `parent` split the whole path to read its last segment. They are to read it from the path's end instead.

## List Stands on the Host, 2026-10-05

The first module converted under the new E.0 rule 1, each function read against its upstream page. Ten of `List`'s functions now stand on the host. `size` is `erlang:length/1` and `unique` is `lists:uniq/1`, each exactly. Six close a small difference in Ernest around a private primitive: `contains` and `remove` take their arguments in the other order from `lists:member/2` and `lists:delete/2`, whose match is the `=:=` that `==` compiles to; `last` answers `None` where `lists:last/1` raises; `take` and `repeat` make a count below 0 into 0, which `lists:sublist/2` and `lists:duplicate/2` raise on; `range` answers `[]` where `lists:seq/2` raises. Their types are E.2's as they were, the equality marked where it was inferred (*A Foreign Function Marks Its Equality*), and the laws machine holds them as it held the Ernest. Measured at 10, 100 and 10,000: each at 1.1 to 1.5 times the host's function, where `size` was 2.2; `unique` at 10,000 from 776 ms to 3.2 ms, its growth from quadratic to the host's.

**`sort`.** `lists:sort/2` promises no stability on its page, and wants an ordering function that calls two elements equal only where they are one. So each element is paired with its index by `lists:enumerate/2`, two that the program's `compare` calls `Equal` are ordered by their indexes, and `lists:unzip/1` takes the indexes off: the host sorts, and Ernest keeps the promise. On 10,000 random integers with `Int.compare`, the new sort takes 3.1 to 3.4 ms, the old merge sort 3.6 ms, and the host's sort through the same `compare` 2.1 ms; on a sorted list, which the host's sort finds as one run, 0.55 ms against the old 1.95 ms and the host's 0.10 ms. The same decoration written in Erlang took 3.1 ms, as the Ernest did, so no adapter: what costs is the pairing, and Erlang would pay it too. E.2 said a function that is no order gave a result arranged some way; the host's page states nothing for one, so E.2 now states nothing either, as §3.10 already did of what holds of a sorted list.

**`zip`.** `lists:zip/3` does the work with the atom `trim`, which Ernest makes only through `Erl.atom` at each call: 160 to 200 ns a call, two to two and a half times the host's zip of ten pairs, where the Ernest loop had been level with it. A binding of the atom at the top of `List` was tried and fails, since the toolchain calls `List` from Erlang, writing the manual pages, where no program has bound it. So `zip` is a primitive of its own, `ern_list:zip/2`, the atom written in Erlang, as E.0 rule 1 allows where the Ernest measurably costs.

**What stays Ernest, and why.** `reverse`, `foreach`, `foldRight`, `indexed`, `unzip` and `<>` carry replies, and a primitive's variables do not (*A Foreign Function Marks Its Equality*). `map`, `filter`, `any`, `all`, `find`, `partition` and `flatMap` call a function in an order, or stop calling it at a point, that their pages do not state, where E.2 states both. `filterMap`'s page calls its function on successive elements but defines it through `lists:map`, and the function answers `{true, V}` or `false`, where E.2's answers an `Optional`, a difference closed only element by element. `span` is `lists:splitwith/2`, whose page defines it by `takewhile` and `dropwhile`, which call the test twice on the prefix. `foldLeft` carries replies. `get` and `drop` would walk the whole list to find what the host's `nth` and `nthtail` raise on, where the Ernest walks to the index. `isEmpty`, `dropLast`, `tryMap` and `tryFold` have no host function.

**What the machine measured wrong.** MVP 2.99d's first pass drew `sort`'s comparison as a function that answers `Less` whatever it is given, over a list of equal elements: no order, and an input the host's sort reads as one run. Its 8.2 times was that, before the change and after; the numbers above are from inputs a program meets. Before this item's last measurement the machine draws varied elements and gives a comparison the type's `compare`, so that its row for every function that takes one says what a program pays.

## A Fault at the Program's End, 2026-10-05

§8.6 had every live process die with the reason `ProgramEnd` when the entry process dies, and the runtime let one slip: a process whose call waited on something the entry process owned, a listener, faulted as that owner's death closed it, and the reaper reported the fault before the program's end reached the process. `examples/shout.ern` printed `callee had ended` now and then on a loaded machine. Nothing in the program faulted; the program had ended, and the line was its ending, out of order.

The report keeps its rule and says the case: a process that faults once the entry process has died, at what the program's end ended, dies with `ProgramEnd` too, and its fault is not reported, and §11.2's reporting runs until the entry process has died. The other reading, reporting every fault however late, would print a line for a cause the program did not have. The check is the reaper's, as it handles a fault: whether the entry process is still alive. A fault that the entry's end caused comes after that end, so the check holds whatever order the two signals reach the reaper in, which the host does not promise across senders. What it gives up is a fault that comes, unrelated, in the same instant the entry process ends, which a program cannot tell from its ending either.

## The Manual Pages Teach, 2026-10-05

The pages `ern doc` writes are what a user of the standard library and the libraries reads: at the prompt through `:doc` and `Shift-Tab`, with `man`, and in `man/`. Their doc blocks were written as the report is, every rule stated and none ordered. `libs/ets` opened with one paragraph of seven facts, two of them the project's own, why it is a library and that Appendix D shows it, and the one thing a new user must do first, the load path, last. A declaration had one sentence, because shape rule 6 asked for one: `Fs.read` was "The file's octets." The guide's disease, a construct's ordinary use and its every finer rule in one breath, with a rule that made it so.

**The form is shape rule 6's.** The rule owns what a doc block contains, and the template page states none of its own, so the form went into the rule. A page is written for the programmer about to use the module: it says what holds, gives no reason for the design, and states a fact before it cites the report, so that it is read without the report. A module's opening is one sentence that says what the module is, which the manual page's NAME line and the shell show alone, and then paragraphs in one order: when a program uses it and what serves better elsewhere, what a program does to use it, and what a caller must know, one behavior a paragraph.
