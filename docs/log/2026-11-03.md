## A Node's Limits, 2026-11-03

Decided with the user on 2026-11-03, while the site's homepage was given a second node in each visitor's container, so that a visitor starts a process on another node as the page's heading says (the site proposal's *The live shell*). A probe measured what a node costs: a bare `ern shell` held 85 MB, the shell as a node 101 MB and a node with no program 102 MB, which put two nodes past the server's 128 MB a visitor.

Most of it was not Ernest's. By the host's own count a bare shell holds 53 MB: 12 MB of process table, reserved for 1,048,576 processes, 12 MB of port table, 7 to 9 MB of loaded code in 181 modules, and about 1 MB for its 63 processes. With tables for 65,536 processes and 4,096 ports a bare shell's anonymous memory went from 63 MB to 29 MB and a node's from 67 MB to 37 MB, the first prompt at the same time; one scheduler took 6 MB more.

The host's flags cannot reach it, since the launcher clears `ERL_FLAGS` so that nothing outside the command changes a program. Three ways were weighed. `ern` lowering the host's defaults for every job saves the most, but a program that spawned 300,000 processes would fault where it ran before, with nothing in its files saying why: principle 1 refuses a silent limit in a language whose subject is processes. An option of every job's would be visible, but puts a fact about a node in each command that starts it. A member of the node's configuration states the node's limits where §12.5 keeps its listener, its peers and its services, and changes nothing for a program without one: principle 2 decided.

`limits` takes `processes` and `ports`, each from 1024 to 67108864, and the node gives the host the least power of two at or above the number. The host rounds to a power of two only up to 2^26 and its page calls its rounding "often, but not always", so the node rounds itself and the rule has no exception. The host's own port limit is 65536, or the least power of two at or above the open files the system allows where that is more, 1048576 on the development machine, and §12.5 says so. A change holds from the next start, since the host takes its tables only as it boots, and a reload says so rather than read it silently. One scheduler is left out until a number says the tables are not enough.

Building it found the runtime at a full table. `Tcp.listen` and `Tcp.connect` answer `Left(Other("a system limit was hit, probably not enough ports"))`, as §12.5 says; `Os.start` faulted as a helper failure where E.23 has it answer `Left(Other(text))`, now fixed. A spawn past the limit of processes kills the reaper and the system processes that spawn for a request, and the first read of standard input at a full port table faults with the host's term: they predate `limits`, which makes them cheap to reach, and the plan's MVP 4.15 item 10 fixes them under one rule.

**A full table and the runtime's end, decided 2026-11-04.** A full process table faults a program, and the runtime must still end it: report the fault, flush its streams, stop. Room kept below the limit for that end was weighed and refused. It would make a node's limit smaller than the one `limits` states by a figure no one chose, and keep a number right as the runtime changes. Instead everything the end uses exists from the run's start, the reaper, the reporter and the streams, standard input's among them, so a full table cannot stop it and the limit means what it says (principles 1 and 5). A step of the end that cannot move to the start comes back to the user with its reason.

**Built, 2026-11-04.** At a full table every spawn the runtime makes for a request answers its asker with the host's class and reason, `Fault("error:system_limit")`, and the process that took the request lives on. That covers the reaper's spawn, the per-request processes of `Fs`, `Tcp` and `Os`, a listener's accept, a listener's and a socket's own processes, which are now made before the address is given out, and the terminal's courier and reader. A spawn on a message's way is a delivery, the end's teller or a process kept for an adapted address. There the process the message is for faults at its next wait (§7.4). A peer's spawn or compute that the node cannot start answers `Other("error:system_limit")` (E.27). The host's own report of each refused spawn went to the program's standard output, and it is dropped now (§12.5).

The end's steps were read for what they open. Three needed something new. The first was a kill, a deadlock's fault given to the entry process and a delivery ended with its recipient among them. Every kill, the prelude's included, now goes to one killer, made with the reaper at the run's start, which carries the kills out one after another. No process can name it, so two processes can never suspend each other, and a kill needs no room. So at a full table a kill makes room, which is the moment a program reaches for one (§10). The second was the sayer of the lines said later, which now starts with the run. The third was the terminal's `stty` at the end. The first subscription now opens one shell, the holder, which keeps the settings it found. It gives them back when the end tells it to, or when its input ends with a host that was killed, so the end opens nothing and a `kill -KILL` leaves the terminal as it was. A subscription whose holder cannot be opened answers the host's refusal.

Standard input keeps its port per read, as *The Build's Fourth Group* decided, so that nothing is read ahead. A read whose port cannot be opened faults its reader, and keys that cannot be read fault the entry process (§12.1). Nodes of 1024 processes and of 1024 ports hold these rules, and so do two runs under a terminal, one whose host is killed and one at a full table of ports.

**The reporter's hold, 2026-11-04.** `faults_before_the_end_are_reported_test` deadlocked itself. Its reporter held the reaper in the first fault's report until the entry process ended.
