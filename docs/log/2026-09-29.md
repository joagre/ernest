## Sockets Are Read by Pulling, 2026-09-29

The newcomer who wrote a chat server found two things of `Tcp` against expectation, and both stay, decided with the user. **A socket is read by pulling** (N-L1): `Tcp.read` answers what has arrived, and nothing a socket receives comes to a mailbox, so a connection that must also receive has a reader of its own, a process that pulls and sends. Every read in Ernest pulls, `Io.readLine`, `Io.read`, `Os.read` and `Tcp.read`, and a process waits on two sources by composing processes; a socket that delivered to the mailbox, Erlang's active mode, would be a second way to read one (principle 2). A pull also holds a sender back that a reader does not keep up with, since the host takes bytes only while a read waits (E.18), where a delivering socket would need a credit scheme of its own, Erlang's `{active, once}` armed again after each message, or fill a mailbox without bound. **A socket's waits take a time** (N-L2): a network peer may never answer, so every function of a system module that waits on the world takes one (E.0 shape rule 8), and the turn of an accept loop after a timeout is where a server looks at what else it must; a time has no upper bound, so a program that wants fewer turns gives a longer one. What misled was the guide: §5.5 said the system modules deliver wherever something arrives later, which is true of `Clock.alarm`, `Terminal.subscribe` and `monitor` and not of reads. §5.5 now says so, and §8.7, which was missing (N1), teaches a server: the accept loop, a reader for each connection, the framing of lines over pieces, and a socket read by one process and written by another.

## What Ernest Adds to a Host Call, 2026-09-29

The newcomer measured the standard library's calls at up to 120 times a bitstring pattern (N-L4): `Bytes.get` 1.2 µs, `Bytes.size` 0.4 µs, `Map.get` 0.6 µs. What Ernest adds to a host operation should cost a fraction of it, never a multiple, and should be found by measuring rather than guessed. `make bench` now prints each of a few operations beside the same operation as Erlang writes it, the loop's own cost included on both sides. Its first honest run also corrected an earlier table, whose send and receive had timed the growth of a stack that was not a tail call, in the Erlang baseline as well.

**A foreign call is written in place.** Every call went through `ern_boundary:foreign/6`. That zipped the arguments with their descriptors, counted the call in the process table twice, applied the function, and then walked the result's descriptor twice to decide whether anything needed arming or zeroing. The compiler knows all of that when it compiles the declaration. So it now writes the call itself inside a `try`, exposes only an argument that holds an address or a function, and chooses the return's check: an integer, a boolean, bytes or a float is tested in place; a value with no function or float in it is checked alone (`check/3`); any other goes through `value/3`, as before. A result whose type is a variable that a parameter names matches any value and is not checked.

**A type variable a parameter names is checked by the shape around it.** The check folded over every entry of a `Map(k, v)` result, so `Map.put` into 100,000 entries cost 3.2 ms, linear where the host's is logarithmic. A map of such keys and values is now checked as a map, and a list of them as a proper list. An improper list, which had crashed the check with `function_clause`, now faults with the report's text. A `Set`'s check still walks the set, since `==` compares its representation, and a set of free elements is the case the question below decides.

**A standard library function without a mailbox type is not counted.** The deadlock check must know a process waiting inside foreign code, because foreign code can still deliver (§8.6). Counting every foreign call cost two table updates, 118 ns. The sentence first proposed for §8.4, "a foreign function without a mailbox type does not wait on a process", is false of our own code: the shell's `forget` is declared without one and waits on the code server. A writer who broke such a promise would get a false deadlock. So the report is unchanged. The runtime skips the count for its own library's functions without a mailbox type, each of which was read and waits on no process, and every other foreign call keeps the count. Reading where a waiting process waits, its `current_function`, would cost nothing on the call. It was rejected because the read costs the process one reduction, and the deadlock proof rests on reductions standing still; compensating by arithmetic would be a trick.

**A call's monitor is its reply's alias**, as `gen_server`'s call makes one, instead of an alias of its own beside the monitor. That saves 140 ns a call. **The table of calls is keyed by the caller.** A process makes one call at a time, since a message's function and `via`'s are pure. So a process's end deletes its row by key, instead of scanning the table for rows where it was the caller, which cost 2.15 µs at every end and was the reaper's largest cost. A restart now scans the pending calls for its own: a rare event paying a small linear cost, where every call would otherwise pay. A table ordered by callee, which would serve both, measured 614 ns a call against the set's 209. **Fault subscriptions have a table of their own**, so a fault reads the subscriptions and not every process's row.

**`Bytes.get` is one pattern**, the octet at the index, instead of a `slice` of one. A negative or too large index fails to match, as §5.11 says a dynamic size does.

The numbers, before and after in ns an iteration, Erlang's in parentheses: `Map.get` 534 to 63 (19), `Map.put` 715 to 153 (183), `String.size` 322 to 104 (90), a call answered 1,800 to 1,660 (1,220), `spawn` 7,300 to 5,300 (1,500 bare, 4,200 for the same protocol written in Erlang). The newcomer's `Bytes.size` and `Bytes.get`, 0.4 and 1.2 µs in their loop, are 16 and 48 ns in ours, against 18 for their pattern. Send and receive were at parity already.

What stays measured and undecided is the plan's: whether the standard library's own foreign functions are checked at all, whether a reply between two Ernest processes is, and whether `spawn`, `monitor` and a call's row go through the reaper and a table as they do. Two measurements are no decision of ours. `List.size` is written in Ernest over the list, twice `length`, which the host writes in C (E.0 rule 1). `List.map` costs 1.5 times `lists:map` only because its list comes before its function: the host's compiler moves registers around a fun's call less well that way round, 1,130 ns against 810 for the same code with the order reversed.
