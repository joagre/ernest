## A Module That Does Not Load Is Named, 2026-11-28

ernest-epx filed the tracker's first issue, issue 1: a foreign call into a module that stands on the load path and does not load faults with `raised error:undef`. epx meets it where its NIF is not built. It was reproduced on `main` with a module whose `on_load` function fails. A second case showed beside it, a `.beam` that is no module, with the same cause and no report of the host's. The verdict, decided with the user: taken, and built for 0.11.1. It sharpens *The Runtime's Lines*, which named a missing module or function in place of the raise. Principle 3 decides.

**The causes.** §12.3 gains `m's on_load function failed` and `the host cannot load m.beam`. The reason of an `on_load` failure is not in the cause. The host gives it through no documented call, and only its reports hold it, which a run writes already. §11 says those reports are written. The host writes none where the function answers an atom, and two where it raises, so §12.3 says "where it writes any".

**No further load.** One call ran the `on_load` function four times, where the host runs it once. The unit's load loads the modules its code calls, on purpose (*The Runtime at the Limit of Open Files*), and that stays. The host's handler loads at the call. The boundary loaded again to word the cause. It now asks `code:prepare_loading/1`, which loads nothing and runs no `on_load` function. The fourth was the runtime's error handler, which loaded every module before it handed the call to the host's handler, which loaded it again. It now loads the toolchain's own units alone. So a failing `on_load` function runs twice in a program, at the unit's load and at the call.

**What the host refuses.** The host answers the same for bytes that are no module and for a file that holds another module's code, and the cause is worded by its answer. A node that takes a foreign module as code arrives loads it once more, a first load there, and that stays.

## An Os.exit After the Wait Gives Its Status, 2026-11-28

MVP 4.18's item 7, the third of its faults, was item 140. On a node, a process kept for an adapted address outlives the end's wait. An `Os.exit` it called during the end's flush was read by nothing, so the node ended with status 0, against §8.6. It is built in the shape *Item 140 Stands After the Launch* kept: the exit's status is the job's, the flush goes on, and the status stands through a later termination. §8.6 is unchanged.

**Built.** The runner reads such an exit from its mailbox once the flush is over, before it drops what the run sent it, and its status replaces what began the end. A termination that ends a stalled flush meanwhile changes nothing. As during the wait, the first exit read gives the status, and none is read after one that cut the wait. So two `Os.exit` calls that reach the runner before it reads either, with no subscriber, now give the second's status where they gave the first's, as they already did where a subscriber waited. By §8.6 the second is an `Os.exit` once the end has begun, and two senders have no order.

**The tests.** Two, on a pair of nodes, each stream stalled in turn. The peer sends 7 to the adapted address once the wait is over. The node ends with 7 when the reader is released, the megabyte whole, and with 7 after a termination. Both ended with 0 before the fix. The word that the exit was called comes back through the peer, since the host writes both streams through its one async thread, which the stalled one holds (*The Sitting on §8.6's Bookkeeping*, its paragraph *Found beside it: one async thread*).

**Found beside it.** In the agent's first test, the address's function called `Tcp.connect` with its target ended, and the call did not return in 30 seconds. It is not diagnosed, and item 136's showing takes it up, since it reads the same process.

## A Wrap's Fault Met in the Function Is the Target's, 2026-11-28

MVP 4.18's item 7, the second of its faults, was item 136. Where an adapted address's target is on another node than the one that applies its function, a `monitor` in the function is the kept process's, and a fault in its wrap is that process's, met at its next wait (§6.5, §6.9). The kept process has no row, so `faulted/3` took it for a foreign process and sent it an exit signal, which ended it, and the target was never told. An agent showed it on two nodes. §6.5 and §6.9 are unchanged.

**Built.** The kept process marks itself as it starts, and `faulted/3` sends it the fault as it sends one to a program's process. Its next wait in the function raises it, a fault in the function and so the target's, which takes it as a message. A test on two nodes, the function waiting in a call never answered as the wrap faults, failed before the fix and passes after it: the target faults with the wrap's cause, and its node writes the line.

**What stays.** The two runs of 2026-11-19 were the other case: the function's call was answered as the wrap ran, and in two of three runs today the function returned before the fault reached the kept process. The fault then waits in the kept process's mailbox, which its loop between messages does not read, and goes with the process; a later message's function meets it at its first wait, in that message's place. §6.9 has the fault met at the process's next wait, and does not say whether the kept process's wait for its next message is one, nor what a fault met there is. So the known issue's line narrows to that case, and the plan's item 7 names it a decision. A wrap whose kept process has ended never runs, since a delivery to a process that has ended ends with it (§6.9). With the target on the maker's node the monitor is the target's, and the target faults, as before.

**Found beside it.** The `Tcp.connect` of *An Os.exit After the Wait Gives Its Status* waits on the reaper, which takes no resource's adoption once the end's wait is over, and is answered `Left(Closed)` as the node ends. It has a line of the known issues. In a run that is not ending, a connect for a target that has ended answers at once, and the socket closes, since its owner has ended. In the checker that §8.4 puts in the kept process's place, the wrap's fault goes to the target directly, so a checker and a kept process differ where the fault comes after the function.
