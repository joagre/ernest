# The decisions log, 2026-11-16

## A Purge Needs Sight, 2026-11-16

MVP 4.5's item 2, added with the user in a discussion. Nothing was built, and no sentence of the report changed.

**The question.** Why a node cannot let go code that no one uses. OTP's report 8, a purge that costs the process limit, is not the reason: it made a purge slow and never stopped one.

**The cause.** Since ERTS 9.0 `erlang:check_process_code/3` reads only a process's direct references to old code, as its own documentation says. A function value is not counted, and one used after a purge raises an exception. So no purge can find who holds a function of a unit, and a unit that declares a function or builds a function value is kept (*The Detach Keeps What Declares a Function*). A peer may name a definition by its hash besides, which no node can see.

**How it is weighed.** A first reading called the gain small: a kept unit for each such input, and the host's counts of module names, export entries, function entries and atoms never fall, so a purge lengthens no node's life. That reading was set aside. Code no one uses is garbage as a dead value is, and memory that no collection reclaims is a defect. It stands today because its cause is the host's, with its cost stated. Lean decided: what would let it go is worth asking for.

**What a purge needs.** One answer for the whole node: no function value of this module's code is alive. With the host's check of the processes that run the code, a purge is then safe on one node. The answer may err on the safe side, saying alive until the holder's next collection, and must never say none while one lives. `code:soft_purge/1` as it stands does not give it: it refuses only while a process runs the old code, the check Ernest makes already.

**What the emulator keeps.** Its source was read the same day, `erl_fun.h`, `erl_fun.c` and `beam_bif_load.c`. A function value is a plain object on a heap that points at its function entry. An entry holds no count of the values that point at it, and is never freed. A purge points each entry of the old code at a stub that raises. So there is no count to expose, and OTP would have to build one of two things.

**A count.** Every place that makes, copies or collects a function value would keep it. The collector's part is the costly one: it would have to visit dead function values, which it does not today. Every program on every node would pay, so a refusal is expected.

**A scan when asked.** An option on `erlang:check_process_code/3` that counts function values again, as the check did before ERTS 9.0. It is code OTP has had, and only the caller pays. It sees a process's heap and its message queue, and no table and no persistent term. Ernest would then keep its own books for the function values in its own tables, as a session does for its values, and one that foreign code puts in a host table would stay unseen.

**The choice.** The second is the more surgical request, and the likelier granted. It gives less. The item chooses between the two and drafts the one chosen for the user to file. OTP may refuse either. Asking costs one issue.

**What it leaves out.** The four counts that never fall are not asked for: that is a larger request, and it would make a refusal of this one more likely.

**Two decisions the item holds.** The documentation of `erlang:check_process_code/3` contradicts itself: its `true` case names funs that reference old code, and its change note says they are ignored since ERTS 9.0. Whether that is filed as a report of `docs/otp_bugs.md` is the user's. Where OTP refuses, the runtime could give each function value of a unit a token whose end the host reports. That costs a word in each function value and C in the runtime, and is cleverer than the plain form, so whether it is weighed at all is the user's too. A node that let a definition go would also need it again when a peer names it, which the item's design would have to answer.

## A Sender That Outlives Its Run, 2026-11-16

MVP 4.16's item 51, the flake of `delivery_foreign_code_arranges_test`, diagnosed by one agent under `make flakes`.

**The cause.** The test's second program monitors a host process that sends `Done` and ends. `Done` and the `Down` reach `main` by two ways. `Foreign.term(self())` crosses as an exposed address, so the host process sends to the checker in front of `main`, which passes the message on (§8.4). The host process then ends, and the reaper's delivery sends the `Down`. A `Down` has no order with the messages the ended process sent (§6.9; *MVP 2.99b's Questions, One by One*). So the runtime was right, and the test read an order nothing promises.

**Shown.** A probe held the checker from before the send until the reaper had looked twice more. All 20 runs then printed `the sender ended first`. Traced beside 24 busy loops, the checker passed the message on 21 to 55 µs after the send, and the delivery sent the `Down` 34 to 137 µs after that. No load raised the natural rate above the hunt's: 1 run in 560 across the loads tried.

**The fix.** The host process lives until the reaper has ended, after the run, so no `Down` of it comes while the program waits. No runtime code changed. With the hold, all 20 runs printed `done`. The changed test still fails where the monitor is no source: with `source_begin()` taken out of `monitor_stood`, it reads `deadlock`. The test's comment names what it no longer covers, a sender that ends while the program waits.

**The hunt.** Beside 15 loops, the hunt met the flake in 5 of 549 rounds in two hours before the change. After it the hunt was ended at 45 minutes and 207 rounds, with none. At the rate before, that many rounds meet none about one time in seven, so the run shows only that nothing else broke. The hold is the proof.

**What is left.** Receiving `Done` alone would have fixed the test too, and the probe showed what that leaves open. Where the sender has ended and its message still waits at the checker, the look reads a deadlock: 10 of 10 runs with the checker held. The look reads no checker's queue, and §8.6 counts a message in flight. Without the hold it needs a checker unscheduled for the look's quiet time, and no record shows it. It is the plan's item 70. Decided with the user: the look reads the checkers' queues, and §8.6 stands as it is. A fault that ends a program which could go on is the surprise principle 1 refuses.

**What the hunts met besides.** The flakes of items 57 and 58 showed again, and their lines hold the sightings. Two tests the plan did not name showed: `supervisor_counts_before_the_restart`, now in item 57, and `node_limit_flags_test`, canceled twice with a crash dump of its host, now item 71.

**What it cost.** The item took over three hours, two of them a hunt before the change that met the flake in its round 18, and the brief had stated no bound in time (*Two Hours for a Hunt*). A build with nothing to do took 1.6 s and 16 s of processor time, reading each library's `.erc` again; it is the plan's item 72. `make test` passed after the change.

## Two Hours for a Hunt, 2026-11-16

Decided with the user, over item 51.

**The rule.** A flake is hunted for two hours at most, under what it was seen under, and the hunt ends at its first sighting. One that does not show is closed as not reproducible. Its log entry names the test and what it wrote, and the item is opened again where the flake shows again. Where a probe makes the failure at will, it shows the cause and the fix, and no hunt follows. Where none can, the hunt runs to its third sighting, and the hunt after the fix runs three times the rounds one sighting took.

**Why a bound.** A hunt must cost less than its flake does. A flake that two hours of hunting cannot make is almost never met in real work. A line kept open with nothing to act on is a decision left pending. Closing loses nothing: a new sighting is searched in the log first, and finds the entry.

**The budget is chosen.** Two hours is the most a flake nobody can make is worth, and no measurement gives it. On item 51's part it is about 550 rounds, so a flake it misses fails less than about once in 180 rounds.

**The rest is derived.** One sighting gives the record and shows that the hunt is the place, so the hunt ends there. A probe that makes the failure at will shows more than any hunt, and the tests show that nothing else broke. Where the hunt alone must show the fix, three sightings give a rate, and three times the rounds of one sighting, run clean, leave about one chance in twenty that the flake still stands.

**What item 51 showed.** Its brief asked for a hunt before and after the change, long enough to meet the flake several times, and gave no bound. The agent ran two hours before, though the flake showed in the fourth minute, and began two hours after, with the cause already shown at will by a probe. Under the rule it would have hunted for four minutes.

**What it replaces.** The plan had a flake seen once or twice hunted to a bound its brief states, and its line kept where it did not show. The plan's paragraph over MVP 4.16's flakes now states the rule.

**The first closed under it.** Item 67, `shell_reload_terminal_gone`. It ended with the status 0 where 129 was expected, its output whole, seen 2026-11-14 once over item 6's runs. Item 40's hunt did not meet it in 2,304 runs (*The Shell's Last Line*). It is closed as not reproducible.

**Where it stands.** The rule is every repository's. It went to the template first, tagged `v0.10.7`, then to `CLAUDE.md`'s *Tests* and to both copies, the same day.

## Three Orders the Supervisor Tests Read, 2026-11-16

MVP 4.16's item 57, the flakes of three tests of `ern_supervisor_tests`, diagnosed by one agent with probes and two short runs under the hunt's load.

**The causes.** Each test read an order nothing promises, and the runtime was right in all three. `limit_reports_only_real_faults_test` read the fault reports once the `Down`s had come and the deliveries had ended. A report comes through the subscription's own process (E.21), and so has no order with a `Down`, which comes from the runtime (§6.4, §6.9). The wait covered the deliveries alone.

`supervisor_counts_before_the_restart` took whichever came first of the supervisor's `Down` and its child's. The runtime delivers each `Down` through a process of its own, and the report states no order between two.

`count_survives_restart_in_place_test` read a sibling's count to learn that a nested group gave up. The group asks its children in turn, and each takes its restart at its next wait (§6.9). So the child that faulted can answer main before its sibling has its ask, and the sibling answers main's next call from its old run.

**Shown.** Each failure was made at will in a fresh host, so no earlier round is needed, and no hunt followed. With main's reports held from after the first, the first test wrote `division by zero`, even where they were let go as main began its wait. With the supervisor's `Down` held in its wrap, the second wrote `kept`.

For the third, main first waited until the sibling had taken the group's first restart, which in the common order comes after main's calls. A copy of the supervisor held between its asks then wrote `2` in 3 of 3 runs. Beside 15 busy loops in 9 hosts, an instrumented copy met the flake once in 1,876 runs. The group had reached its limit there, and main ran on time. A logged copy showed the two asks 46 µs apart, where they take 7 µs at rest.

**The fix.** No runtime code changed. The tests that count reports wait through `ern_rt:wait_for_deliveries/0`, which covers the reports as the shell's wait for its session does (§11.2). Two tests beside the first had the same wait and took the same change: a late report could only pass them falsely. The second test takes the child's `Down` only where the child returned. The third has one child, and reads the nested group's own report of its limit, once the earlier run's alarm is due twice over. With each hold the changed tests pass.

**What the count test could not see.** It was written for alarms of an earlier run lowering the new run's count. Over a supervisor whose alarms outlive its restart the old test passed every run, since the sibling's late first restart had set the count to 0. The new test ends in a deadlock there. Neither checked that the new run counts afresh: a run that kept the earlier count gives up one fault early, and its report answered the last read. The test now reads each report by its process, and looks for the group's once the child has answered after the new run's first fault. Over a copy that keeps its count it fails there, 3 of 3.

**Read back.** The stale alarm now comes before the new run's two faults, where the old test placed it between them behind a quarter window's margin. So the test rests on a count that can go below zero, as `supervise`'s does, and reads no margin of time. `limit_reports_only_real_faults_test` expects the child's second report before its group's. The two reach the reaper from two processes, which the host does not order, and on one node they come in the order they were caused. It was never seen otherwise, and is left. The module takes 3.1 s, from 2.3 s, the count test waiting two windows. The two searches found nothing: the test's functions are receives on its own mailbox, in one program.

**What is left.** Two orders the report does not state, each met by a program, the plan's item 73. E.22 has a faulted child run again once its siblings have restarted, for a strategy's restart, and says nothing of a group restarted in place. `nested_group_restarts_in_place_test` read the same order on 2026-10-26 (*The Nested Group's Third Restart*). §6.9 says nothing of an order between two `Down`s.

**What it cost.** About five minutes under load, against the hunt's two hours, and no `make flakes`. The agent took 47 minutes in all. `make test` takes 26 s.

## Two Orders Stated, 2026-11-16

MVP 4.16's item 73, decided with the user the day item 57 found it (*Three Orders the Supervisor Tests Read*).

**Two `Down`s have no order.** §6.9 now says that where two processes die, their `Down`s have no order with each other, whichever died first. The runtime stands. §6.9 already had a `wrap` that does not finish hold up no other delivery, so each `Down` goes its own way, and the new sentence states what follows. An order would have one `Down` wait on the `wrap` of the one before it, against that rule. Erlang orders no two processes' `DOWN`s either, so the reader of principle 1 predicts none.

**Read cold.** The sentence first spoke of the `Down`s of two processes. That covered a `Restarted`, which §6.9 does order: it is placed before the new run takes a step, so before the `Down` of a process that run kills. The sentence now speaks of two deaths, and stands after the call's answer, the exception to the sentence before it. It says nothing of one process's `Down`s. There the reading found a hole, read from the code and not shown: a process killed while its restart waits on a service monitor's `wrap` may give that monitor `Killed` and then `Restarted`. It is the plan's item 74. Two monitors of one watcher on one process give two `Down`s of one death in no order, which no program reads, and nothing is said of it.

**What the sentence finds.** `kill_stops_in_reverse_order_test` monitors three children, kills their supervisor and reads `c b a` from the order of their `Down`s. E.22's rule stands, each child killed once the one before has ended, and the test reads it through an order §6.9 does not give. It was never seen to fail. Item 73's build changes it to read what the rule promises: at a child's `Down`, each child spawned after it has ended.

**A group restarted in place comes back whole.** E.22 has a faulted child run again once each sibling its fault restarts has restarted or ended (*A Group Restarts Whole*). A group that gave up and is restarted in place asks each child to restart, and lets the child at whose fault it gave up go on once each is asked. That child can then answer a call while a sibling's old run still stands. Two tests read the group whole there, on 2026-10-26 and in item 57, each written by a reader who knows the rest of Ernest. That is the surprise principle 1 names.

Decided: that child runs again once each of the others has restarted or ended, as after a strategy's restart. The supervisor waits on the messages it already has, a child's word that it restarted and the watcher's that one ended, and reads no clock. A sentence saying that a restart in place gives no order was the narrower promise. It was not taken: it would leave one rule for a fault that restarts siblings and another for a fault that restarts the group, where a program asks the same question of both. A restart in place that the parent asks for holds no child, so nothing waits there. E.22's sentence is written with the build.

## A Listener Closed Before Its Accept, 2026-11-16

MVP 4.16's item 59, the flake of `ern_tcp_tests`' `write_given_no_time_test`, diagnosed by one agent.

**The cause.** The test's far end accepts on a listener of the host's and sends the test what it reads. The test closed the listener once the run had ended, and nothing in the run waits for the far end's accept. The host ends an accept in the accepting process, which reads the listener's options once the driver has taken the connection. Where the close came first, that read answered `einval`. The far end then died of a failed match, and its answer never came. The test waited five seconds for it, past EUnit's limit.

So the test waited on what never comes. The loops starved nothing past the limit: they delayed the far end by a third of a millisecond. The runtime was right, and its own accept already reads `einval` as the close under way.

**Shown.** A probe held the far end still once it waited in its accept, and let it go once the test, its run ended, waited in a receive. All 10 runs of the test as it stood were canceled at five seconds, each far end's read of the listener answering `einval`. All 100 runs of the fixed test passed under the same hold. Unheld, the far end won by 144 to 571 µs at idle. In nine hosts at once beside 15 loops it lost in 2 of 81,000 runs, its accept refused with `einval` as under the hold.

**The fix.** The test closes the listener once the far end has answered. No runtime code changed. No other test closes a listener before a far end it waits on has accepted: `ern_tcp_tests` and `ern_rt_tests` were read whole, and the accepts of `ern_browser_tests`, `ern_nodes_tests` and the benchmark site by site.

**The hunt.** None ran: the probe made the failure at will (*Two Hours for a Hunt*).

**What it cost.** The diagnosis took 26 minutes. The probe's first nine hosts made 45,000 connections in 20 seconds and spent the loopback's ephemeral ports, so a listen answered `eaddrinuse`. The later batches waited for the closing sockets to expire. `make test` passed in 26 s.
