## A Purge Needs Sight, 2026-11-16

MVP 4.5's item 2, added with the user in a discussion. Nothing was built, and no sentence of the report changed.

**The question.** Why a node cannot let go code that no one uses. OTP's report 8, a purge that costs the process limit, is not the reason: it made a purge slow and never stopped one.

**The cause.** Since ERTS 9.0 `erlang:check_process_code/3` reads only a process's direct references to old code, as its own documentation says. A function value is not counted, and one used after a purge raises an exception. So no purge can find who holds a function of a unit, and a unit that declares a function or builds a function value is kept (*The Detach Keeps What Declares a Function*). A peer may name a definition by its hash besides, which no node can see.

**How it is weighed.** A first reading called the gain small: a kept unit for each such input, and the host's counts of module names, export entries, function entries and atoms never fall, so a purge lengthens no node's life. That reading was set aside. Code no one uses is garbage as a dead value is, and memory that no collection reclaims is a defect. It stands today because its cause is the host's, with its cost stated. Lean decided: what would let it go is worth asking for.

**What a purge needs.** One answer for the whole node: no function value of this module's code is alive. With the host's check of the processes that run the code, a purge is then safe on one node. The answer may err on the safe side, saying alive until the holder's next collection, and must never say none while one lives. `code:soft_purge/1` as it stands does not give it: it refuses only while a process runs the old code, the check Ernest makes already.

**What the emulator keeps.** Its source was read the same day, `erl_fun.h`, `erl_fun.c` and `beam_bif_load.c`. A function value is a plain object on a heap that points at its function entry. An entry holds no count of the values that point at it, and is never freed. A purge points each entry of the old code at a stub that raises. So there is no count to expose, and OTP would have to build one of two things.

**A count.** Every place that makes, copies or collects a function value would keep it. The collector's part is the costly one: it would have to visit dead function values, which it does not today. Every program on every node would pay, so a refusal is expected.

**A scan when asked.** An option on `erlang:check_process_code/3` that counts function values again, as the check did before ERTS 9.0. It is code OTP has had, and only the caller pays. It sees a process's heap and its message queue, and no table and no persistent term. Ernest would then keep its own books for the function values in its own tables, as a session does for its values, and one that foreign code puts in a host table would stay unseen.

**The choice.** The second is the more surgical request, and the likelier granted. It gives less. The item chooses between the two and drafts the one chosen for the user to file. OTP may refuse either. Asking costs one issue.

**What it leaves out.** The four counts that never fall are not asked for: that is a larger request, and it would make a refusal of this one more likely.

**Two decisions the item holds.** The documentation of `erlang:check_process_code/3` contradicts itself: its `true` case names funs that reference old code, and its change note says they are ignored since ERTS 9.0. Whether that is filed as a report of `docs/otp_bugs.md` is the user's. Where OTP refuses, the runtime could give each function value of a unit a token whose end the host reports. That costs a word in each function value and C in the runtime, and is cleverer than the plain form, so whether it is weighed at all is the user's too. A node that let a definition go would also need it again when a peer names it, which the item's design would have to answer.

## Two Hours for a Hunt, 2026-11-16

Decided with the user, over item 51.

**The rule.** A flake is hunted for two hours at most, under what it was seen under, and the hunt ends at its first sighting. One that does not show is closed as not reproducible. Its log entry names the test and what it wrote, and the item is opened again where the flake shows again. Where a probe makes the failure at will, it shows the cause and the fix, and no hunt follows. Where none can, the hunt runs to its third sighting, and the hunt after the fix runs three times the rounds one sighting took.

**Why a bound.** A hunt must cost less than its flake does. A flake that two hours of hunting cannot make is almost never met in real work. A line kept open with nothing to act on is a decision left pending. Closing loses nothing: a new sighting is searched in the log first, and finds the entry.

**The budget is chosen.** Two hours is the most a flake nobody can make is worth, and no measurement gives it. On item 51's part it is about 550 rounds, so a flake it misses fails less than about once in 180 rounds.

**The rest is derived.** One sighting gives the record and shows that the hunt is the place, so the hunt ends there. A probe that makes the failure at will shows more than any hunt, and the tests show that nothing else broke. Where the hunt alone must show the fix, three sightings give a rate, and three times the rounds of one sighting, run clean, leave about one chance in twenty that the flake still stands.

**What item 51 showed.** Its brief asked for a hunt before and after the change, long enough to meet the flake several times, and gave no bound. The agent ran two hours before, though the flake showed in the fourth minute, and began two hours after, with the cause already shown at will by a probe. Under the rule it would have hunted for four minutes.

**What it replaces.** The plan had a flake seen once or twice hunted to a bound its brief states, and its line kept where it did not show. The plan's paragraph over MVP 4.16's flakes now states the rule.

**The first closed under it.** Item 67, `shell_reload_terminal_gone`. It ended with the status 0 where 129 was expected, its output whole, seen 2026-11-14 once over item 6's runs. Item 40's hunt did not meet it in 2,304 runs (*The Shell's Last Line*). It is closed as not reproducible.

**Where it stands.** The rule is every repository's. It went to the template first, tagged `v0.10.7`, then to `CLAUDE.md`'s *Tests* and to both copies, the same day.

## Two Orders Stated, 2026-11-16

MVP 4.16's item 73, decided with the user the day item 57 found it (*Three Orders the Supervisor Tests Read*).

**Two `Down`s have no order.** §6.9 now says that where two processes die, their `Down`s have no order with each other, whichever died first. The runtime stands. §6.9 already had a `wrap` that does not finish hold up no other delivery, so each `Down` goes its own way, and the new sentence states what follows. An order would have one `Down` wait on the `wrap` of the one before it, against that rule. Erlang orders no two processes' `DOWN`s either, so the reader of principle 1 predicts none.

**Read cold.** The sentence first spoke of the `Down`s of two processes. That covered a `Restarted`, which §6.9 does order: it is placed before the new run takes a step, so before the `Down` of a process that run kills. The sentence now speaks of two deaths, and stands after the call's answer, the exception to the sentence before it. It says nothing of one process's `Down`s. There the reading found a hole, read from the code and not shown: a process killed while its restart waits on a service monitor's `wrap` may give that monitor `Killed` and then `Restarted`. It is the plan's item 74. Two monitors of one watcher on one process give two `Down`s of one death in no order, which no program reads, and nothing is said of it.

**What the sentence finds.** `kill_stops_in_reverse_order_test` monitors three children, kills their supervisor and reads `c b a` from the order of their `Down`s. E.22's rule stands, each child killed once the one before has ended, and the test reads it through an order §6.9 does not give. It was never seen to fail. Item 73's build changes it to read what the rule promises: at a child's `Down`, each child spawned after it has ended.

**A group restarted in place comes back whole.** E.22 has a faulted child run again once each sibling its fault restarts has restarted or ended (*A Group Restarts Whole*). A group that gave up and is restarted in place asks each child to restart, and lets the child at whose fault it gave up go on once each is asked. That child can then answer a call while a sibling's old run still stands. Two tests read the group whole there, on 2026-10-26 and in item 57, each written by a reader who knows the rest of Ernest. That is the surprise principle 1 names.

Decided: that child runs again once each of the others has restarted or ended, as after a strategy's restart. The supervisor waits on the messages it already has, a child's word that it restarted and the watcher's that one ended, and reads no clock. A sentence saying that a restart in place gives no order was the narrower promise. It was not taken: it would leave one rule for a fault that restarts siblings and another for a fault that restarts the group, where a program asks the same question of both. A restart in place that the parent asks for holds no child, so nothing waits there. E.22's sentence is written with the build.

## A Terminal's Echo Beside Its End, 2026-11-16

MVP 4.16's item 64, the flake of `ern_os_tests`' `terminal_test`, diagnosed by one agent with a loop of the test. The report's sentences, the test's form and the kernel's report were decided with the user.

**The cause.** The test ran an interactive `sh` under a terminal and wrote `stty size` and then `exit 3`. It held each line's echo as one span, and the echo of `exit 3` before the end. Two things broke that, and neither is the runtime's.

The test typed ahead. Linux echoes a line as it takes it, and what the program writes meanwhile lands inside the echo. The test wrote each line without waiting for its prompt, so a prompt stood inside an echo now and then, as in `e$ xit 3`.

The host ends the output before the last echo. Linux wakes the program at a line's end before it writes that line's echo. `sh` exits on `exit 3` without writing again, so it could close the terminal first. The master then answered its end, the helper stopped reading, and the echo came after.

**Shown.** In 24 hosts at once the test failed 115 times in 72,000 runs, 94 at the echo of `exit 3` and 21 at the echo of `stty size`. A copy of the test that kept each run's output gave 112 failures, each with the status 3. In 76 a prompt stood inside an echo, and in 36 the echo of `exit 3` was missing.

A C program with no Ernest in it, running a terminal as the helper does, lost the echo at the end 12 times in 480,000 runs. A later read of the master found it each time. The order was read in `n_tty.c` of Linux 6.12: a line's end wakes the reader before the echoes are written, and a write by the program writes the waiting echo before its own bytes.

**The report.** E.23 said only that the terminal echoes what is written to it. A program that drives a shell meets both cases, and our own test was written expecting neither. So principle 1 asks for the rule. E.23 now says that an echo comes among what the program writes, and that the echo of a line the program exits on, writing nothing after it has taken the line, may not arrive. The paragraph of `Os.startTerminal` in `src/stdlib/os.ern` says the same.

**The narrower promise.** A mechanism that kept every echo was weighed first, and none is sound. Nothing marks that the echo has come, so a read past the end would wait a chosen time. A helper that held the terminal open itself would change when the output ends, against E.23's terminal that no process holds open any longer.

**The fix.** No runtime code changed. The test's program is `sh -c` over `stty size; read line; echo "took $line"; exit 3`. It writes nothing while its line is taken, so the echo comes whole. It answers after the line, so the echo arrives. One assertion holds the whole exchange. In 24 hosts at once the test passed 72,000 of 72,000 runs.

An interactive `sh` with its prompt set, each line written after its prompt, was weighed and passed the same loop. Its exact match holds only where `sh` writes nothing but its prompt, which a `sh` with a line editor does not. That was reasoned and not run.

The test covers neither an interactive shell's prompts nor the two cases the new sentences state. The second cannot be held by a test, since the echo arrives nearly every time.

**The hunt.** None ran: the loop made the failure in 20 s (*Two Hours for a Hunt*). The record came from the loop's hosts and not from `make flakes`. The sightings of 2026-11-15 left no record, and both causes fit them.

**No report to the kernel.** Dropped. E.23's sentence must stand for the kernels in use, whatever a later one does.

**What the read-back found.** `Os.resize`'s example in `src/stdlib/os.ern` reads the echo of a line its program exits on, writing nothing to its terminal after it. Its program runs `stty` between the line and its exit, so the echo has longer to arrive than under `exit 3`. It was not run under load. It is the plan's item 76.

`ern_integration_tests`' `terminal_program_test` reads an echo that its program answers after, which arrives. The tests under the pseudo-terminal harness were not read for an echo held at a program's end. They are left: the harness sends only after an `expect`, the shell paints its own line with the terminal's echo off, and a test that holds such an echo fails as this one did, where this entry is found.

**What it cost.** The diagnosis took 17 minutes, with five runs of 24 hosts at 20 to 22 s each, and the build 3 minutes. `make test` passed in 28 s, `make test-library` in 9 s, `make test-integration` in 11 s and `make test-guide` in 12 s.

## A Subscriber That Ends Beside Main, 2026-11-16

MVP 4.16's item 63, the flake of `subscribed_while_the_end_waits_test`, diagnosed by one agent with a probe.

**The cause.** The test's `main` spawned two subscribers and returned at once. The first subscribes and ends, and the test read that it was gone before the end. The second subscribes and waits, and the test read that the end found it. Nothing orders either before main's end. `spawn` starts a process and promises none of its acts before the spawner's next (§6.2), and nothing a program reads orders two deaths (§6.9). The end reads the subscriptions once the entry process has died, and a subscription stands until its process has died (E.23). So the runtime was right, and the test read an order nothing promises.

**Shown.** A probe held the subscriber that ends, once it had subscribed, until the end's first read of the subscriptions had returned. All 20 runs wrote `the end waits for 2 subscribers: M.main:25, M.main:26`. With the waiting subscriber held before its subscription until the end's last read, all 20 runs wrote no line of the wait. The session ran both again, with the same counts.

Unheld, one host met none in 2,000 runs, and nine hosts at once met it in 5 of 9,000, each as `2 subscribers`. A copy of the runtime that stamped each end met it 14 times in 13,500. There the subscriber's body returned within 20 µs of main's, on either side, and the end read 28 to 60 µs after main's return.

**The fix.** Before it returns, main waits for the `Down` of the subscriber that ends, through `spawnMonitored`, and for the `Ready` the other sends once it has subscribed, as the module's other programs wait. A `Down` says its process has died, so its subscription has ended, and the `Ready` says the other's stands. No runtime code changed. Under each hold, and under both, all 20 runs of the changed test passed, and nine hosts at once passed 13,500 of 13,500. The test's comment names what it no longer covers: an end that races a subscription or a subscriber's end.

**The hunt.** None ran, since the probe made the failure at will (*Two Hours for a Hunt*).

**The report stands.** §8.6 does not say when the end reads its subscribers, and the diagnosis asked for a sentence there: a subscription made, or a subscriber's end, beside the entry process's end may be found or not. It is left out. Each outcome is one that an order of the two deaths, or of the subscription and the end, gives, and §6.2, §6.9 and E.23 leave those orders open. The sentence would say again what they say. A subscriber found ended holds nothing up, and is said as `ended without answering` (§11.2).

**What is left.** `test_told_of_the_end_test` and `shell_told_of_the_end` end beside their subscriber's subscription in the same way, with a wider margin. Neither was seen to fail. They are the plan's item 79.

**What it cost.** The agent took 24 minutes, the probe's runs about six of them. `make test` passed after the change.
