# The decisions log, 2026-11-16

## A Purge Needs Sight, 2026-11-16

MVP 4.5's item 2, added with the user in a discussion. Nothing was built, and no sentence of the report changed.

**The question.** Why a node cannot let go code that no one uses. OTP's report 8, a purge that costs the process limit, is not the reason: it made a purge slow and never stopped one.

**The cause.** Since ERTS 9.0 `erlang:check_process_code/3` reads only a process's direct references to old code, as its own documentation says. A function value is not counted, and one used after a purge raises an exception. So no purge can find who holds a function of a unit, and a unit that declares a function or builds a function value is kept (*The Detach Keeps What Declares a Function*). A peer may name a definition by its hash besides, which no node can see.

**How it is weighed.** A first reading called the gain small: a kept unit for each such input, and the host's counts of module names, export entries, function entries and atoms never fall, so a purge lengthens no node's life. That reading was set aside. Code no one uses is garbage as a dead value is, and memory that no collection reclaims is a defect. It stands today because its cause is the host's, with its cost stated. Lean decided: what would let it go is worth asking for.

**What a purge needs.** One answer for the whole node: no function value of this module's code is alive. With the host's check of the processes that run the code, a purge is then safe on one node. The answer may err on the safe side, saying alive until the holder's next collection, and must never say none while one lives. `code:soft_purge/1` as it stands does not give it: it refuses only while a process runs the old code, the check Ernest makes already.

**What the emulator keeps.** Its source was read the same day, `erl_fun.h`, `erl_fun.c` and `beam_bif_load.c`. A function value is a plain object on a heap that points at its function entry. An entry holds no count of the values that point at it, and is never freed. A purge points each entry of the old code at a stub that raises. So there is no count to expose, and OTP would have to build one of two things.

**A count.** Every place that makes, copies or collects a function value would keep it. The collector's part is the costly one: it would have to visit dead function values, which it does not today. Every program on every node would pay, so a refusal is expected.

**A scan when asked.** An option on `erlang:check_process_code/3` that counts function values again, as the check did before ERTS 9.0. It is code OTP has had, and only the caller pays. It sees a process's heap and its message queue, and no table and no persistent term. Ernest would then keep its own books for the function values in its own tables, as a session does for its values, and one that foreign code puts in a host table would stay unseen.

**The choice.** The second is the more surgical request, and the likelier granted. It gives less. The item chooses between the two and drafts the one chosen for the user to file. OTP may refuse either. Asking costs one issue.

**What it leaves out.** The four counts that never fall are not asked for: that is a larger request, and it would make a refusal of this one more likely.

**Two decisions the item holds.** The documentation of `erlang:check_process_code/3` contradicts itself: its `true` case names funs that reference old code, and its change note says they are ignored since ERTS 9.0. Whether that is filed as a report of `docs/otp_bugs.md` is the user's. Where OTP refuses, the runtime could give each function value of a unit a token whose end the host reports. That costs a word in each function value and C in the runtime, and is cleverer than the plain form, so whether it is weighed at all is the user's too. A node that let a definition go would also need it again when a peer names it, which the item's design would have to answer.
