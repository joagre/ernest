## What Erlang Held, Moved, 2026-10-04

MVP 2.99c's item 5 is built, its three decisions taken with the user as *What Erlang Holds, Measured* recommended them.

**The line in E.0 rule 1.** A primitive beneath an operation Ernest could write is admitted only where the Ernest form's cost grows with something the host's does not, and a cost within a bounded multiple of the host's admits none. The rule said "a multiple", which nearly every Ernest form over a host's operation costs, and so decided nothing. Growth is what a program meets as its input grows, and it is the line `trimEnd` and `toIntBase` fell on either side of; the rule gives `trimEnd` as its example.

**`String`.** `trimStart` is Ernest over `slice` and `drop`, and `trimEnd` over the private `lastGrapheme`, the string without its last grapheme and that grapheme, found from the string's end. Unicode's segmentation looks back across no ASCII code point, but a line feed's to the carriage return before it, so of the host's graphemes of the tail from an ASCII byte, every one after the first is the string's own; a tail of one grapheme is split again from the ASCII byte before. `toInt` is `toIntBase` in base 10, which reads its digits in Ernest, in halves past forty of them. `trim_start`, `trim_end` and `to_int_base` are gone from `ern_string`, and E.5's list of primitives names in their place the last grapheme `trimEnd` takes off, as it names `slice` for its private slice. Before the shims went, the Ernest forms agreed with them on thirty thousand random texts, hard at the graphemes, and as many numerals, long ones among them.

**`:output` in Ernest.** `Fs.append` writes a device as well as a regular file, a terminal among them (E.17), since a write to a device ends. A named pipe stays refused, since its open waits for a reader that may never come. The shell's `:output` is then the session's: it tries the path with an append of nothing, which creates a file that is not there and refuses what is neither a file nor a device, and sends the screen where output goes. The screen holds it and appends each program's write there. The front end's open device, its persistent term and its check of the path's type went. Two things change for a person, and §11.2 says both. The file holds what the live region would show, a byte that is not UTF-8 as U+FFFD, where it held the bytes. And a write that fails sends output back to the live region with a line that says why, where the front end dropped the error. A path whose directory is missing is said so, since the append creates the file and only the directory can be missing.

**Its cost, weighed** when it was built, as the plan asked. An append opens the file each time, in a process `Fs` starts for the request: 113 µs a line, against 10 µs for a write to a file held open. Ten thousand lines a program prints take 1.97 s to a file through `:output` at a terminal, against 0.77 s in the live region, which repaints at each write; in line mode, 1.8 s against 0.14 s. About five thousand lines a second is more than a person reads in the other terminal `:output` exists for. Kept: the cost is `Fs`'s, a module of paths that holds no file open, and the only other way is a file the front end holds open, the Erlang the item moved. What would change the verdict is a program whose output at `:output` outruns that, or `Fs` gaining a file held open.

**The terminal's key decoding stays in `ern_tty`.** It reads ECMA-48's sequences into `Terminal.Event`s inside the runtime's process for the terminal (§8.2, E.16). E.0 rule 1 names a process of the runtime's among what is the runtime's, and what crosses into Ernest is the event. Decoding in Ernest would move a published specification's reader into a module, which is a library's work by CLAUDE.md, for no program's gain.

The line drawn is that one: a primitive beneath where the Ernest form's cost grows with what the host's does not.
