# The decisions log, 2026-11-09

## A Program's TLS at a Full Table, 2026-11-09

MVP 4.15's item 33, found by item 31 (*The Carrier's Acceptor at a Full Table*). A program's `Tcp.connectTls` at a full table of processes, with one process free, did not answer within its three seconds.

**The wait.** The host's TLS starts processes of its own: a connection's supervisor and its two children in `ssl:connect/4` and in `ssl:transport_accept/2`, and a listener's trackers in `ssl:listen/2`. It matches each start's answer as `{ok, _}`, and at a full table it raises the failed match (`docs/otp_bugs.md`, 15). A probe that left from none to eight processes free reached each start in turn. The connect's worker caught the raise and handed it to the host's `ssl:format_error`, which raises on a tuple it does not name (`docs/otp_bugs.md`, 16). The accept's worker did not catch it at all, and a listen's worker ended as the connect's did. Either way the worker ended unanswered. The caller's call is to the TCP process, which lived, so it waited for ever, and the emulator wrote the worker's end as an error report.

**Decided.** Each of the three faults its caller with `Fault("error:system_limit")`, as a request whose own worker or socket's process the table refuses does. §12.5 already says so, by §7.4, so the report needs no sentence. The runtime reads the raise as the full table where the start's reason is the refused spawn's `system_limit`, the supervisor's own or one of its children's. The match is on that reason and not on the failed match alone, since the host's accept fails the same match on a socket closed under it.

Any other raise answers `Left(Other(text))`, the reason as the host prints it where `ssl:format_error` cannot write it, so that no request goes unanswered. The accept over TLS now catches the host's raise, as the connect and the listen did. With the fix, the probe's runs said the fault's line alone, the host's reports of the refused spawns dropped as item 31 drops them.

**The handshake.** The item expected a program's handshake to meet the host's `{dtls_upgrade, notsup}`. It never does: only `ssl:handshake/3` on a TCP socket answers that, which the node's acceptor calls and a program's TLS does not. Once a connect or an accept has made a connection's processes, the probe's handshake made no other, over TLS 1.2 and 1.3, with no process free. So the handshake needs no change.

**The first request at a full table, found.** A run's first request over TLS starts the host's TLS, and at a full table that start can end the host's own kernel (`docs/otp_bugs.md`, 17). With no process free the application controller ended, and the run with it, status 1. With one the start never answered. With two the host's logger ended, status 70. With three or four it answered `Left(Other(text))`, the host's term over many lines, with the host's reports written beside it. OTP alone does the same. Plan item 35 takes it.

Starting the host's TLS at a run's start, which item 35 weighed and refused (*Lean at the Limits*), was measured. It costs a bare run 9.7 ms and a node 4.5 ms, medians of nine and of three runs on nike, the node's less since it has loaded the host's crypto for its keys. It makes 22 processes, and takes about 1.5 MB in a bare host. No count of the table before the start is sound, as item 31 found for the dial, since the host's own processes fill it beside the program's.

**The tests.** `tls_at_a_full_table_test_` is a regression test, written after the fix. Eight runs fill a node's table of 1024 processes but for one, two or three, and hold that a `connectTls`, an `accept` over TLS and a second `listenTls` each fault their run with `error:system_limit`, with nothing else written. A host's process may end between the count and the request, which a probe showed, so a run can leave one more free than it asked; at every count the test asks, one more still faults. On the old code the test's first run was still waiting when its step's time had passed. It held five runs of five. It does not cover the first request at a full table, nor a reason `ssl:format_error` cannot write, which no request was found to give once the full table is read.

## Lean at the Limits, 2026-11-09

Decided with the user on 2026-11-09, as item 33's report brought item 35. Item 1 had what the runtime's end uses exist from the run's start, so that a full table leaves the program able to end (*A Node's Limits*). That is the line. Any other request at a host's limit may fail, and fails as §8.4 and §12.5 say, its caller faulted or answered. Where the host fails it worse, by ending the run or never answering, the report states it and the defect goes to OTP. Nothing is held in every run for a request a limit might meet.

Memory weighs as much as time. A start that holds code, processes or tables for a rare case costs every run that never meets it, and a node holds it for its whole life. Principle 1 decides, as the reader who knows Erlang predicts the runtime: the host starts an application at its first use, and a full table can end the host's own processes.

**Item 35.** E.18 states that a run's first request over TLS at a full table of processes may end the run, or never answer and hold every later `Tcp` request, the host's defect (`docs/otp_bugs.md`, 17). Starting the host's TLS at each run's start was weighed and refused. It would hold about 10 ms and 1.5 MB in every run, nearly none of which use TLS, for a coincidence of two rare things: a program at its limit, and its first request over TLS.

**Item 32, turned.** Its recommendation, the node's own `net_kernel` borrowed for each major release of OTP, builds around the same kind of coincidence, a dial from a full table, whose fix is OTP's. Its alternative, §12.5 stating that the dial ends the node, is now the recommendation, and the design session decides it.

**What was held already, read again.** Item 20 has every run load at its start its run side's Erlang with every host module their import tables name: a bare run went from 180 to 199 ms and from 7.8 to 8.7 MB of code (*The Runtime at the Limit of Open Files*). The modules that answer a refusal and report a fault are on the line, since without them an accept at the limit neither answered nor ended. The rest is item 35's reasoning, a call the limit refuses being one that faults as a module the host lacks does (§8.4).

TLS loaded whole at its first request holds 6 MB of code, about half of which a handshake never loads, so that a handshake at the limit of open files finds its code. Without it the handshake answered `Left(Closed)`, a request failing at a limit. The socket's closer is on the line, a close being the socket's end, but at a process and 2.6 KB a socket it is the largest hold inside it. Plan item 36 brings the three to the design session, each measured in time and in memory, a bare run's and a node's.
