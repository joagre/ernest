## One Namespace at the Root, 2026-11-13

MVP 4.16's item 30, decided with the user on 2026-11-13. The code and §4.2 differed on how a module is found at the root (*A Package and Its Manifest*). The report changes, and the code changes in one place.

**What differed.** §4.2 said that the first root that holds a name's first segment finds it. Every finder in the code takes a module by its own path, at the first root that holds its file: the build's lookup, its read of a dependency, `ern run`, `Code.load` and the shell. So a program's `time/zone.ern` left `Time.toCivil` the library's, and a probe showed the same between a program and a `--load-path` root. The clause was a reader's, added in the round of 2026-11-10 without a probe (*The Release Review Before 0.10.0*). §11.1 and §11.2 found a module by its namespace before it and after.

One finder took the roots in another order. The shell's `:load` looked for a compiled form on the load path first and under the source root last, where the build and the run take the source root's first. So a `greet.erc` with no source beside it, and another on a `--load-path` root, gave the run one `Greet` and `:load` the other. `:load` now takes the source root's first, and §11.2 says so.

**The root is one namespace.** Two roots hold parts of one name, so there is nothing to choose between until both hold the same module. At depth it is otherwise: `Top.Time` and `Time` are two names, and the nearer wins. A reader who knows that a file is a namespace predicts that `time/zone.ern` provides `Time.Zone` and takes nothing away (principle 1). The rule is one for the lookup and every loader, and it is the host's own, one module for each name (principle 2).

**What a root that owned a namespace would cost.** It would hide the library's `Time` behind a directory, with no `time.ern` in the tree to show it. The refusal of a hiding module would reach every module under a library's namespace again, the third round's form, since `Http` could not load its `Time`. Each loader would scan a root to learn whether it holds a segment. It would buy a namespace from one tree, which a package has by §11.9's refusal and the standard library by its taken namespaces. So the narrower promise stands: a root holds modules and owns no namespace.

**The cost.** A program may put a module under a library's namespace, and `Time.Zone.name()` reads as the library's until the reader opens the tree. A program's module at the name of a library's type shares that type's namespace (§4.2), so a later release's new member may clash with it, at the program's file.

**Item 26's refusal.** It follows in one step. A module hides the module of its namespace under a later root, and it is refused where a module of a library or of a named package depends on the hidden one. §11.1 states that already, so item 26's build waits no longer.

**A source root's module is the source root's.** A build that was not given a module's source read a later root's module where the source root's had no `.erc`. With `time.ern` uncompiled, `ern build main.ern` took the library's `Time` and `ern build .` the program's, so one tree gave two programs (principle 1). The build now refuses, `compile Time first, which Main uses`, as it did where no later root held one. §11.1 states the rule and the refusal, which it had not.

**An edited dependency.** A build that is not given a module's source reads its `.erc` as it stands, one whose source was edited since among them, and says nothing. That stays, as the narrower promise: a build compiles the sources it is given and no other. The other answer was a digest of each dependency and one more refusal.

**`:reload`.** A source that appears under the source root, at the name of a module loaded compiled from a later root, is that module's source from then on, as `:load` in a new session finds it. The reload compiles it where it differs from the source the loaded form records. The code did so, and §11.2 says it now. §11.2 also states a refusal the code made and the report did not: a loaded module that uses what the reload changes, and has no source, refuses the reload.

**The cold reading.** One reader read the sentences before the build, probing with `ern`. It found four points, each with a sentence or a probe behind it, and each changed a sentence the same day. The first is the shell's order above. A type's members are still read from their module's source (§11.1), so the rule of the `.erc` as it stands is said of a module another depends on. A build compiles a named package's sources too (§11.9), so "no other" is said of the source root's modules. A file at a taken namespace, `list.ern`, is no module's source, and `:reload` passes it over, as the code does.
