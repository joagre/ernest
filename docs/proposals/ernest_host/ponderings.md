# A host of Ernest's own: ponderings

Begun 2026-10-12. Pondering, not a proposal: nothing here is decided, planned or built, and the plan's MVP 4.4, a BEAM back end, stays the nearer step. These notes keep the thinking so that it is not thought twice.

## 1. What brought it up

MVP 3.2's item 4 met the BEAM's limits in two places on one day.

The report let a node let go of a unit when no process ran it or held a function of it, "which the host tells". The host does not tell: since OTP 20, `erlang:check_process_code` sees the code on a process's stack and nothing of the function values a process holds, and a function value of a purged module is simply dead. The rule had to go, and a node now holds every unit for its life (§11.2). The BEAM's own tables then bound that life: module names, export entries, fun entries and atoms are counted for the host's life and never fall, so a node that is sent code without end nears a limit and is restarted. On this machine the counts are 65,536 module names, 524,288 export entries, 524,288 fun entries and 1,048,576 atoms.

The same day, exporting every function of every unit, so that a received definition could call a private one the node already held, cost 19.5% on the bench's operator scenario, because the BEAM's compiler narrows a private function's argument types only where it sees every caller. Ernest's type checker knows those types exactly, and throws them away at the host's door.

Behind both stands a wider observation: Ernest uses a part of the BEAM and pays for all of it. The OTP behaviours are not used at all (CLAUDE.md forbids them in the toolchain). The distribution is used only as a carrier under Ernest's own peers, keys, TLS and frames (§8.7), with Ernest's own `epmd`. Hot code loading's two versions and its purge that kills are set aside for content addressing by hash. Reductions count work the scheduler could instead measure by time, since every operating system Ernest targets reads a clock in a few nanoseconds. And the emitted code uses a small part of the instruction set, in known types, where the BEAM's instructions are generic over terms.

A host built for Ernest alone would answer each of these. Whether it is worth building is the question these notes are for.

## 2. What such a host would gain

- **The let-go, for free.** A host whose heap owns function values knows which code is reachable: a function value is a reference to a definition, and a definition no process, no table and no other definition references is garbage like any other. Code is data. The question the BEAM cannot answer becomes the collector's ordinary work.
- **No tables that never fall.** Definitions loaded by hash, with no modules, need no module table, no export table and no fun table; and constructors need no atom table at all, since the checker knows every type's constructors and a constructor can be a small number under its type. The limits §10 states as the host's disappear, and §11.2's four-fifths line with them.
- **Definitions as the unit of loading.** Content addressing wants a definition loaded, kept and let go on its own. On the BEAM a definition rides in a module, hence the units, the positional names and the pool. A host of Ernest's own loads a definition by its hash, as Unison's runtime does, and the exchange's code frame is its loader's input directly.
- **Types kept to the metal.** The checker knows every value's type at every point. A typed instruction set, which is MVP 4.4's thought too, adds an integer without asking what it is, matches a constructor by a number and reads a field by an offset. The host's compiler would have nothing to infer, since the checker already did.
- **The runtime's bookkeeping native.** §10 prices a spawn and a monitor at a message to the runtime and its answer, by design, since the runtime keeps rows the host does not: a process's site, its root, its peer, its monitors' wraps. `make bench` has a spawn at 7,275 ns against the host's 1,579. In a host of Ernest's own those rows are fields of the process, and the message goes.
- **Faults and traces in Ernest's words.** A trace today is the host's stack with Ernest's names read back through the code table (§11.2). A host of our own knows a frame by its definition's hash and its site, and the trace is Ernest's from the start.

## 3. What Ernest uses of the BEAM, from the code

Counted on 2026-10-12 as calls into host modules, so that the size of the undertaking is read from the code and not guessed.

**The runtime, `erl/runtime/src`, 7,574 lines of Erlang.** `erlang` 229 calls, `lists` 131, `ets` 116, `maps` 64, `persistent_term` 50, `file` 45, `unicode` 37, `sets` 37, `binary` 25, `queue` 18, `string` 16, `gen_tcp` 14, `inet` 13, `code` 9, `io_lib` 8, `filename` 7, `proplists` 6, `io` 6, `unicode_util` 5, `math` 3, `gen_event` 3, `filelib` 3, `os` 2, `error_handler` 2. The standard library's `foreign fn` declarations name these runtime modules almost alone, `ern_rt`, `ern_string`, `ern_set`, `ern_char`, `ern_peer`, `ern_foreign`, `ern_float`, and the host's `erlang`, `maps`, `math`, `lists` and `binary` directly for the operations that are the host's own (E.0 rule 1). So the surface Ernest stands on is the runtime's modules, and beneath them the host modules above.

**The node side, `erl/cli/src`.** The carrier, the gateway, the exchange, the arrival and the node's start add `public_key` 14, `crypto` 7, `json` 5, `net_kernel` 3, `net_adm` 1, `inet` 4, `beam_lib` 2 and `code` 13. The carrier runs on the host's distribution, started by `net_kernel` under Ernest's node names and allowed peers, over TLS with Ernest's keys; nothing else of the distribution is used.

**The helper, `erl/runtime/c_src/ern_exec.c`.** C99 over POSIX.1-2008, what the host's ports cannot do: a program's standard error apart from its output, the end of its input, a kill of its process group, the node's lock on `ernest.pid` and a signal to the node that holds one.

**The toolchain, 36,609 lines of Erlang in all**, the compiler, the build, the shell's front end, `ern doc`, `ern format`. None of it would run on a host of Ernest's own, which runs Ernest. See section 7.

**What is not used.** No OTP behaviour but two `gen_event` handlers OTP's own signal server calls; no supervisor, no application of our own, no release handling; no hot code loading's two versions, no purge that kills; no tracing, no debugger, no observer; no distribution but as the carrier's transport; no `rpc`, no global name registry; no records in the runtime's data (plain tuples and maps); no `receive` with a timeout but Ernest's own `after`; no process dictionary; no `erlang:hibernate`; no NIFs but the one C helper, which is a port.

## 4. What the host would have to implement

The list a host must satisfy is §10's, with the rest of the report behind each line; this is the implementation's reading of it, grouped by subsystem, each with the hard part named.

**Terms.** A fixed, documented representation of every value (§10): integers of arbitrary precision, so small integers tagged in a word and bignums beside them; floats as IEEE doubles with Ernest's rules at the boundary; constructors, which need no atoms once the checker numbers them under their type, though `Foreign.Term` and `Erl.atom` (E.19) need an interned symbol table for what crosses the foreign boundary; tuples and records; lists; maps, which are Erlang's today, a flat map under 32 keys and a hash array mapped trie above, with structural equality and the host's total order over keys (G.1 compares keys as the runtime compares its terms, and `compare` sorts); sets, which are `sets` of version 2, maps underneath; binaries and bitstrings with the bit syntax whole (§5.11): sizes, signedness, endianness, floats, UTF-8 segments; references; addresses carrying the node's start number (§8.7) and process-local aliases, which `Reply(a)` is (§6.6: an alias takes one answer and drops any other); function values as a definition's hash and lambda position with captured values, which is what a spawn's frame already names (§8.7). The hard part is equality and ordering over all of it, which every `match`, every `Map` and every `sort` leans on, and which must agree with the BEAM's wherever a value's text or order is observable.

**Memory.** Processes share no memory (§10), so the proven shape is the BEAM's: a heap per process, a generational copying collector, messages copied at send, large binaries reference-counted off the heaps, literals in an area of their own. Ernest's values are immutable, so a shared heap with no copying at send is possible in principle, as Pony's ORCA does for actors, but it needs a concurrent collector, which is the one piece of a runtime that takes years to get right; KISS says copy. A top-level binding's value is immortal once evaluated (§8.5), as `persistent_term` makes it today, and since no unit is let go nothing need ever be erased from that area. Memory exhaustion ends the program at once with the host's message (§10, §11.8).

**Processes and the scheduler.** Preemptive scheduling (§10) at safe points: every call and every `receive`, which in a language whose loops are recursion is every back edge, so a slice ends by comparing a cheap monotonic clock, or by a flag a timer thread sets, at a call. Reductions go. One scheduler per core with a run queue each and work stealing, or a single queue first; timers for `after`, `Clock.alarm` and every deadline the report states, a wheel per scheduler; monitors with reasons distinguishable from every other (§9.3, §10); a kill; the process row the runtime keeps today in `ets`, its site, its root and its peer (§6.9, §11.2), as fields of the process; the entry process and the end's protocol (§8.6), the subscribers waited for, the system processes (§8.2) as native services or Ernest processes; deadlock detected (§8.6, §10), which is the scheduler noticing that every process waits with nothing in flight, natural in a host of our own and a search over the process table today.

**Mailboxes.** Unbounded queues (§10); `receive` takes the first message that matches a clause's pattern and guard and leaves the rest (§6.3), so a selective receive over a typed queue, with the BEAM's trick of a mark where a reply is awaited to keep a long queue from being scanned twice; a `Reply`'s single answer; the boundary check on what foreign code sends (§8.4), which is Ernest's own code already, `ern_boundary`.

**Code.** A loader that takes a definition's canonical form (Appendix H) or a compiled definition by its hash, links its references to definitions already held, and makes it callable; the code table (§8.7, §10) as the loader's own index; function values that survive the definition's unloading only by keeping it alive, which is the collector's work; a compiled form on disk in place of the `.erc`, the canonical forms kept beside the code so that a node ships a definition onward (§11.2); the interpreter, threaded code dispatched by computed goto over a typed instruction set designed from what the emitter emits today, which `ern_emitter` already writes from the canonical forms alone and nothing else, the position MVP 3.2's item 4 put it in. No JIT: the BEAM ran without one until OTP 24, and Ernest's time goes where Erlang's does, to messages, scheduling and the host's own operations, not to tight arithmetic. The bench's `operator` and `loop` scenarios would show the cost, three to ten times; the rest little.

**The carrier.** TLS between named peers with keys, certificates and the node's name as its key's digest (§8.7), which is `ssl`, `public_key` and `crypto` today; the handshake with the floor's cookie; the thirteen frames; the loss detected within 45 to 75 seconds where a peer falls silent (§10); the external term format on the wire (§8.4, §10), or a format of the host's own, since a host of Ernest's own is a floor of its own and connects to no BEAM node. TLS is the one component that is a library the size of the host: it would be linked, OpenSSL or a smaller one, never written. Linux's kernel TLS could carry the bytes once a library has done the handshake.

**The world.** Files, directories, modes and the listing's errors (E.17), over POSIX; TCP sockets (E.18), over `epoll` or `io_uring`; the terminal in raw mode and its signals (`ern_tty`, `ern_tty_signal`), which the shell needs and a program may; `Os.start` as `ern_exec.c` does it today, which stays as it is; signals for termination (§8.6); the environment, the user, the clock; standard output and error as the system processes write them (§8.2).

**Unicode.** The categories, the cases, the graphemes and the widths are the host's tables of the version it ships (§10, E.5, E.6, E.16). A host of our own ships its own tables, generated from the Unicode data files as `unicode_util`'s are, with the version named.

**Hashing.** SHA-256 for the definitions' identities (§8.7, Appendix H), which is `crypto` today; and JSON (Appendix G.6), a library over the host's `json` module today, would stand on Ernest's own or a C library's.

**What stays as it is.** The checker, the canonical forms, the hashes, the exchange's protocol, the boundary check, the standard library's Ernest, the shell's Ernest, the report. The host is beneath §10, and §10 is written to be beneath.

## 5. What other systems do

- **The BEAM.** Per-process heaps, generational copying, messages copied, binaries over 64 bytes reference-counted off-heap, literals in a shared area; one scheduler per core with run queues, work stealing and reductions as the slice; a threaded interpreter by computed goto until OTP 24 and BeamAsm since; modules as the unit of code with two versions and a purge that kills. Thirty years of staying up. What we have, and what we pay for whole.
- **AtomVM.** A BEAM in C for microcontrollers, a subset of the instruction set, running real `.beam` files in a few hundred kilobytes. The strongest evidence that a subset BEAM is a bounded undertaking, and a possible first road (section 6).
- **Unison.** Its own runtime; definitions by hash with no modules; closures serializable, their dependencies enumerable by the runtime, so a node receiving a computation asks for the hashes it lacks, which is the exchange; code cached once per node. Solved the let-go by owning the heap. The price: a young runtime and nothing beneath it.
- **Pony.** Actors with a heap each and ORCA, a protocol that lets actors share immutable data without copying and collects across heaps by message counting. The one design that keeps isolation and skips the copy; also the one that took a research group.
- **Go.** M:N goroutines on a shared heap with a concurrent collector; preemption by safe points at calls and, since 1.14, by signals for tight loops. Shows time-based preemption at safe points works at scale, and shows what a shared heap costs in collector complexity.
- **Lua, CPython, wasm3.** Threaded interpreters by computed goto or tail calls, fast enough that their users rarely ask for more. The dispatch loop is the easy part.
- **Erjang, Lumen.** A BEAM on the JVM and a BEAM in Rust with ahead-of-time compilation; both abandoned. A reimplementation that must run all of Erlang chases a moving target; one that runs Ernest alone does not.

## 6. Roads a first host could take

- **A BEAM subset in C, running our `.erc` files as they are.** Everything above the host unchanged: the compiler emits Erlang, the `.erc` holds BEAM code. The host implements the instructions our emitted code uses and the host functions the runtime calls, and nothing else. Tests the thesis cheaply: whether Ernest's programs run, how fast an interpreter of our own is, what the GC and the scheduler cost to write. Keeps modules, so the tables stay, though the host decides how they are counted. AtomVM is the precedent and possibly the starting code.
- **A typed instruction set from the canonical forms, definitions as the unit.** The real thing: MVP 4.4's typed registers as the host's instructions, the emitter a function from a definition's form to its code, the loader by hash, no modules, the let-go by the collector. A new file format in place of the `.erc`. Everything in sections 2 and 4.
- **Linux alone, first.** `epoll` or `io_uring`, `timerfd`, `signalfd`, `eventfd`, futexes, the vDSO clock, `mmap` for heaps; no portability layer until there is a second system to port to. The helper is POSIX already and stays.

The first road is the one to take first, if any: it measures before it commits, and what it learns about the heap and the scheduler carries into the second.

## 7. The hard questions, honestly

- **The toolchain is Erlang.** 36,609 lines: the compiler, the build, the shell's front end, the documentation, the formatter. A host of Ernest's own runs Ernest, so the toolchain stays on the BEAM and compiles for the new host, two runtimes installed where one is today, until the compiler is written in Ernest, which is a milestone of its own and a long one. The shell's front end, `ern_shell.erl`, is foreign code to the shell's Ernest; a shell on the new host needs that part in Ernest or in the host.
- **Speed.** Without a JIT the host loses on compute against BeamAsm, three to ten times on the scenarios that measure dispatch, and wins back only what the runtime's native bookkeeping saves on spawn, monitor and call. The shims stop being the host's C and become the host's C again, written by us. Where the standard library stood on `lists`, `maps`, `binary`, `string` and `unicode` for the host's speed, it would stand on ours.
- **The three things that are hard once and impossible to retrofit.** The heap and its collector; binaries shared without copying; a scheduler fair under SMP with IO woven in. The dispatch loop, the instruction set and the loader are the easy and pleasant parts and would be done first, which is the wrong order.
- **TLS and Unicode.** Two libraries one does not write. Linked, with their versions named, as the host's are named today.
- **Who it is for.** Ernest's programs today run on the most proven concurrent runtime there is, and `make bench` holds every Ernest operation to a fraction of the host's. A host of our own trades that for control over exactly the places where the BEAM's shape shows through: the let-go, the tables, the types at the door, the runtime's messages. Whether those places matter enough is a measurement, which MVP 3.2's item 7 begins, and a question of what Ernest wants to be.

## 8. What would make this a proposal

A measured answer to section 7's last question; the first road built far enough to run `test/programs` and `make bench`; and a design for the heap and the scheduler read back against §10 line by line, before a line of the interpreter is written. Until then this stays a pondering, and MVP 4.4 the next step toward the metal.
