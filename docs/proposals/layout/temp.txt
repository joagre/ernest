A proposal: the repository's directory hierarchy by least surprise (2026-11-04)

Agreed with the user as a direction; tentative until the user says it is
ready, then planned as an item of its own.

The rule
--------
A directory holds one kind of thing, named for it. A program or a library
stands in one place, its host half beside its Ernest, so a reader who opens
it finds all of it. Every directory of source is named by its role, never by
its language.

The changes
-----------
1. The Ernest programs leave tools/ for src/tools/, a source root beside
   src/shell:
     tools/site.ern, tools/site/  ->  src/tools/site.ern, src/tools/site/
     tools/manual.ern             ->  src/tools/manual.ern
     tools/ern_site.erl           ->  src/tools/site/ern_site.erl, the
                                      generator's shim beside it, by 2
   tools/ keeps only what works on the repository: install.sh, version.sh,
   paragraphs.sh, comments.sh, strip.escript and unicode_width.escript;
   release/ leaves it too, by 3.

2. A library's shim stands beside its Ernest:
     erl/json/src/ern_json.erl      ->  src/libs/json/ern_json.erl
     erl/http/src/ern_http.erl      ->  src/libs/http/ern_http.erl
     erl/base64/src/ern_base64.erl  ->  src/libs/base64/ern_base64.erl
   Each test goes with it, erl/<lib>/test/ern_<lib>_tests.erl to
   src/libs/<lib>/test/. erl/ then holds the toolchain, the runtime and
   shared alone. The runtime's modules the standard library calls stay in
   erl/runtime: they are the runtime's, not a library's shim.

3. tools/release/ becomes a top-level release/. It holds no tool: its
   README.md and Makefile are the archive's own files, which
   tools/install.sh stamps with the version, the README kept by an
   installation as share/doc/ernest/README.md. They are the release's
   content as site/ is the site's: site/ holds what make site fills, and
   release/ what make release fills. tools/ is then the repository's
   scripts alone. Touches tools/install.sh's paths, the Makefile's comment,
   CLAUDE.md's owner row for tools/release/README.md, and the documents
   that cite it.

4. erl/ goes, and all the source stands under src/, named by role and not
   by language, as Go's tree is (src/cmd, src/runtime, a directory a package):
     src/toolchain/   lexer, parser, checker, emitter, formatter, cli
     src/shared/      what the toolchain and the runtime both use (ern_tree)
     src/runtime/     the runtime, its Erlang and its C helper
     src/stdlib/      the standard library, as now
     src/libs/<lib>/  each library, its Ernest and its shim together (2)
     src/shell/       as now
     src/tools/       the site generator and manual.ern, each with its shim (1)
   Why: once 1 and 2 place code by role, erl/ would hold most of the Erlang
   and not all, and its name would promise what the tree no longer keeps
   (principle 1). With every directory named by role, src/ holds all the
   source, as a newcomer expects, and no name needs explaining. The tree
   moves once, to a layout with no exception.

What it touches, to read before it is built
-------------------------------------------
- The size: every path under erl/ moves, the largest of the changes, in one
  commit with its sweep.
- The build: how a shim beside its library compiles. Today each is an OTP
  app with its own Makefile and ebin under erl/; a co-located one needs one
  rule for every library, its .beam written under build/libs/<lib>/. The
  Makefile, erl/app.mk and test/Makefile.
- The installation: where an installed library's .beam goes, and the
  launcher's -pa erl/*/ebin, which becomes the toolchain's and the runtime's
  ebin (docs/design/install.md, tools/install.sh). The
  installed layout may stay as it is; only the source moves.
- Report Appendix G and §11.2's --libs-dir and the toolchain's own
  libraries, wherever they name a path.
- docs/architecture.md, docs/development.md, docs/design/*.md, CLAUDE.md
  (its src/libs/ sentence), the site's decisions, every comment and test that
  names a moved path, and THIRD_PARTY_LICENSES if it names one.
- `make site`'s and `make man`'s paths to the generator and manual.ern.
- The ernest-template and the three application repositories, if any names
  a toolchain path; they should name none.

How the three harder parts are solved
-------------------------------------
1. A shim beside its library needs no OTP app. Report §11.2: a foreign
   fn's module is "a .beam file of that name in a directory of the load
   path", and a library's build directory, build/libs/<lib>/ beside its
   .erc, is one. So one Makefile rule compiles every src/libs/<lib>/*.erl
   into build/libs/<lib>/, its tests run with that directory on the code
   path, and the installation, which copies a library's build directory
   whole, takes the .beam with it. erl/json, erl/http and erl/base64, each
   an app with its own Makefile and ebin, go.
2. The launcher is the same script in the repository and an installation
   (docs/design/install.md), so the installed tree mirrors the source's new
   names: -pa src/toolchain/*/ebin and src/runtime/ebin, and
   tools/install.sh's copy list with them. Checked 2026-11-04: ernest-epx,
   ernest-httpd and ernest-template name no path inside Ernest's
   installation; their erl/ is their own host applications for --libs-dir,
   and they build through `ern` alone, so they are untouched.
3. The runtime finds its C helper by code:priv_dir(runtime), which follows
   the app's directory: src/runtime/ stays an app with ebin and priv. The
   rest is a search of the Erlang for paths made from "erl", each hit read
   and moved; make test-full, the documents test's check that a cited path
   exists, and the site's link check hold what the search misses.

One more: no src/ inside src/
-----------------------------
The example's src/toolchain/lexer/src/ern_lexer.erl names src/ twice. The
inner src/ is OTP's habit of an app's sources beside its ebin/; with every
ebin under build/, nothing in the app's directory needs it. So an app is one
directory, its modules beside its include/ and test/:

    src/toolchain/parser/ern_parser.erl
    src/toolchain/parser/include/ern_ast.hrl
    src/toolchain/parser/test/ern_parser_tests.erl
    src/runtime/ern_rt.erl, src/runtime/c_src/, src/runtime/include/

The headers are named by -include_lib("parser/include/..."), about a
hundred lines. The compiler looks for an -include_lib file along its include
path before it asks for the app's directory, so `erlc -I src/toolchain`
finds them in the source tree, with the ebin under build/. To confirm by a
probe before anything moves. erl/app.mk, which runs in each app's src/ with
-I ../include, is rewritten for the flat app.

Wrinkles found by reading the code, 2026-11-04
----------------------------------------------
Confirmed by a probe: -include_lib("parser/include/ern_ast.hrl") resolves
through `erlc -I src/toolchain` alone, the app on no code path.

Four change what Ernest does, not only where a file stands:

W1. A test is told from the toolchain's code by its place. app.mk compiles
    an app's tests into its own ebin, and three functions (ern_rt:is_test,
    ern_carrier:is_test, ern_cli's application_code) take a .beam for a
    test's where <app>/test/<module>.erl stands beside its ebin's parent.
    With ebin under build/ and the source under src/, that file is never
    there, so every test would count as the toolchain's own code.
    Solution: tests compile into a directory of their own,
    build/toolchain/<app>/test/, never the ebin, and the three is_test
    checks go: what is in an ebin is the toolchain's. An installation then
    holds no test by its shape, not by a filter in tools/install.sh.

W2. The node's code digest covers the shims today and would not after.
    ern_carrier:code_digest hashes erl/*/ebin/*.beam, json's, http's and
    base64's shims among them, with the stdlib's and the shell's libraries'
    .erc; it is a development build's floor (Floor, CodeDigest, Cookie).
    Moved to build/libs/<lib>/, the shims leave the glob, and two builds
    whose json shims differ would connect. Solution: the digest covers
    every .beam of build/libs/ too, or the library's .erc and its .beam
    together for every library the installation holds.

W3. The runtime's own modules: ern_rt:own_modules takes every non-test
    .beam of erl/*/ebin as the host's own, found first and never a
    program's foreign module (report §11.2's foreign lookup). The moved
    shims would become .beam files of the load path instead, a program's
    rank and not the toolchain's: a program's own ern_json.beam earlier on
    its load path could then shadow the library's. Solution: own_modules
    covers the libraries' .beam files under build/libs/ as the toolchain's
    own, and §11.2's sentence names them so.

W4. The toolchain's newest time: ern_cli:toolchain_modified takes the
    newest .beam of erl/*/ebin, which decides when make's markdown and man
    outputs are stale (§11.4); the shims count today. Solution: the same
    reach as W3's, so one function lists the toolchain's code and all three
    users ask it.

The rest is mechanical, each a path or a depth:
- ern_tree:tree() splits shared's ebin path as ["erl","shared","ebin",_],
  four deep; it becomes ["build","toolchain","shared","ebin",_], five.
- ern_cli:toolchain_modified climbs three dirnames from its own .beam.
- ern_doc_tests' ROOT "../../.." and ern_cli_tests' "../../..", the
  tests' working directory under their app.
- app.mk's -DVERSION ../../../VERSION, and -I ../include.
- The C helper's Makefile writes ../priv; it writes build/runtime/priv.
- 15 Makefiles name erl/ (one generic app rule replaces the per-app ones),
  4 shell scripts (bin/ern, tools/install.sh, and two more), .gitignore,
  THIRD_PARTY_LICENSES (the vendored getopt's path), and the dialyzer
  target's PLT over erl/*/ebin.
- 15 documents name erl/; the documents test lists each stale path.
- 21 Erlang files name erl/, most in comments.

One for the operator: an installation upgraded in place. tools/install.sh
must remove the old layout's lib/ernest/erl/ when it installs the new, or
an old prefix keeps both; how it uninstalls today, by its manifest or by
the directory, decides it.

Verdict, 2026-11-04: better on least surprise (src/ is the source, build/
what is built, tools/ the repository's scripts), on finding things (a
library is one directory, its Ernest, its shim and the shim's test; a role
is one directory), and on understanding (an installation is bin/ and build/,
the build laid out as installed). Ready to plan with W1 to W4 decided as above, after MVP 4.15 and
before MVP 4.4's full review; the include probe has held.

Kept as they are
----------------
- An application's erl/, in ernest-template and the programs begun from it:
  there everything is host applications for --libs-dir, so the name is its
  role, and an application's erl/ never meets Ernest's src/.
- host/ for erl/ was weighed and refused before erl/ itself went: the report
  uses "the host" for BEAM and OTP, so host/ would read as the host's own
  code, and the glossary's Host already names a node name's part after `@`.
- Tests in two places: each app's test/ beside it, under src/toolchain/ and
  src/runtime/ as under erl/ today, and the top-level test/ for the
  integration tests, OTP's convention.
- report/, guide/, tour/, examples/, docs/: the reader's doors.
- site/, the site's data; editors/, assets/, bin/: each one thing.

tools/ after the four changes
-----------------------------
Six scripts, each run by a make target on the repository or its build:
install.sh (stage, install, uninstall, the archive), version.sh (VERSION
and the lines that name it), strip.escript (an installation's modules
without the host's debug information), unicode_width.escript (the stdlib's
width table from Unicode's data), paragraphs.sh and comments.sh (the long
paragraphs and comments, listed). Nothing in it is shipped, built from or
read by a program: tools/ is the repository's own tools, as its name says.

Aside, not the layout's: CLAUDE.md has a tool's work written in Ernest
where it could be. paragraphs.sh, comments.sh and unicode_width.escript are
text processing Ernest can do; install.sh and strip.escript (the host's
beam_lib) have reasons to stay as they are. To weigh on its own.

The runtime and the toolchain, read 2026-11-04
----------------------------------------------
The runtime calls the toolchain's code at some 25 sites (ern_emitter,
ern_canonical, ern_interface, ern_prelude, ern_descriptor), since a node
compiles while it runs: the shell's inputs, an attached shell's, code
arriving from a peer. So src/runtime/ naming src/toolchain/ states a true
dependency, and moving the record headers into shared/ would untangle
nothing.

The cli app is two things under one name. Its command line: ern_cli,
ern_build, ern_examples, ern_page, ern_release, ern_out, ern_signals,
getopt. And the nodes: ern_node, ern_carrier, ern_gateway, ern_exchange,
ern_arrival, ern_epmd, ern_code_load, report §12.5 to §12.7, the component
docs/design/nodes.md describes, there only because a node starts from the
command line. Named by role they are src/nodes/, the component its own
directory as it is its own design note.

And ern_shell.erl, 5,292 lines, is "the shell's front end, the toolchain
behind the foreign interface the shell in src/shell/ calls": the shell's
host half, which change 2's rule puts beside its Ernest, in src/shell/.
cli/ then holds the command line and its jobs alone.

The layout, so: src/toolchain/ (lexer, parser, checker, emitter,
formatter, cli), src/shared/, src/runtime/, src/nodes/, src/stdlib/,
src/libs/<lib>/, src/shell/ (its Ernest and ern_shell.erl), src/tools/.

Change 1 revised, decided with the user 2026-11-04
--------------------------------------------------
Read against ernest-template, ernest-epx and ernest-httpd (docs/temp-other-repos.md):
each keeps an Ernest tool in tools/, tools/docs.ern, and an application's src/ is
its program's own source root, where a tool would become a module of the library.
So the rule across the four repositories is: src/ holds what a release ships, and
tools/ what works on the repository and is not shipped, in any language. Ernest's
Ernest tools, site.ern, site/ and manual.ern, stay in tools/, a source root as an
application's is; only the site's shim moves, tools/ern_site.erl to
tools/site/ern_site.erl, beside the generator it serves. src/tools/ is not made.
Every mention of src/tools/ above, in change 1, the layouts and the example,
stands corrected by this; the role-named src/ holds toolchain/, shared/,
runtime/, nodes/, stdlib/, libs/<lib>/ and shell/.

The build's rule corrected, decided with the user 2026-11-06
------------------------------------------------------------
Read by an independent reader, and run on a fresh copy of ernest-template: an
application's build/ mirrors its src/ (report §11.1) and is what its make
install and make release take, so its tools/, test/ and examples/ cannot build
under it. So each source root keeps a build/ of its own in an application.
Ernest divides its one build/ by role, for src/ and tools/, and its tests build
beside themselves, test/build/ and test/ebin/, as an application's do. Every
mention above of every build product standing under build/ stands corrected by
this.
