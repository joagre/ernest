Running Ernest

This guide is for the operator: the person who runs Ernest programs as nodes, programs started so that they talk with one another (section 1), reads what they write on standard error, and decides when to restart one. It assumes nothing of the language beyond what a program's author tells you about it, and it teaches only what happens at the machine: directories, commands, lines, and the move each line asks for.

A node runs on the Erlang runtime, OTP, which this guide calls the host; the host picks a port, compiles and loads what a peer sends, and counts what it holds. ern is Ernest's one command, whose first word is its job: ern build compiles a program, ern run runs it, and ern config, ern reload, ern stop and ern shell --attach are this guide's. A process in what follows is one of the program's own, thousands of which run inside one node, which is the operating system's one process; a process's address is where the program sends it messages, and a network-address is a peer's on the wire.

How a program is written to be found, placed and upgraded across nodes is the language guide's chapter 8, Programming in Ernest, which this guide points at and does not repeat. The rules themselves are the report's, Ernest's definition, §8.7, §11 and §12 above all, and every section here names the section that owns what it teaches.

The commands of sections 1, 5.3 and 8 and the shell sessions of sections 5.3, 6 and 8 are run as shown, with other directories and ports, each time Ernest is tested; the service manager's unit and the kill lines are shown and not run. The numbers quoted were measured in October 2026, on one machine, eight cores, and across three machines wired on one LAN, and each says which.

1. One node#

A program becomes a node by being started with a configuration directory, and nothing else: prog.erc is the compiled program, which ern build writes; ern run --config-dir dir prog.erc is a node, and ern run prog.erc is not (report §8.3). The directory is the node's identity, and it is made once.

1.1 The directory#

$ ern config --config-dir /etc/counter/b --listen 0.0.0.0:8654
-----BEGIN PUBLIC KEY-----
MCowBQYDK2VwAyEA...
-----END PUBLIC KEY-----

ern config creates the directory, which only its owner can open, and in it three files (report §11.3): private-key.pem, the node's ed25519 key, readable only by its owner; certificate.pem, which the node signs itself and whose dates mean nothing to a node; and ernest.conf, which lists nothing yet and listens where --listen says, here at port 8654 on every interface; section 1.2 says what goes in it. It prints the public key, which is what another node's configuration will list. It fails where the directory exists, empty or not; only --peer-dir, section 2.1, writes into one that exists.

The directory is made for one machine and never copied: a copied key gives two nodes one identity, which a third node cannot tell apart. A node also refuses a configuration that lists its own key under peers, a peer has this node's own key, and a node is no peer of itself.

The directory belongs to the user who runs the node. A node refuses to start from a directory, or a file of it the node reads, that is neither its user's own nor the superuser's, or that anyone but its owner may write, and from one whose private key any but its owner may read or write, and says so.

1.2 The configuration#

ernest.conf is JSON, and Appendix C of the report shows it whole. Its entries, in the order you will meet them:

  • listen: the address the node's listener binds to, what ern config --listen gave, an address of one interface, or 0.0.0.0 or :: for every interface of its family, and a port, and none where it gave none. Port 0 lets the host pick one. At every start the node says on standard error the address and the port it listens on, listening on 127.0.0.1:51204. Two words recur from here: a node listens for connections from its peers, and it dials a peer when it opens the connection itself, at the address its configuration lists for that peer (report §12.5). A node without listen does not listen and only dials; a bare node (section 3.4) must listen.
  • public-key: this node's, as ern config printed it. It cannot change while the node runs.
  • peers: a list, each peer with a name you choose, which the program uses, its public-key, and a network-address, host:port, which is left out where this node never dials that peer. A host name is resolved at each dial, not when the file is read.
  • services: a service is a process a program offers under a name, which a program on another node looks up, a find, to get its address; under each service's name, the peers that may offer it, in the order a find asks them. A service not listed here is found nowhere from this node.
  • measures, utilization and utilization-interval: what the node measures of itself, how busy it is on one scale among it, and tells its peers, section 3.
  • limits: the most processes and ports the node holds, processes and ports, each rounded up to a power of two; a node left without them holds the host's own, a table for 1048576 processes and one for 65536 ports or more, reserved as it starts. A small node, one of many on a machine, states smaller ones: "limits": {"processes": 65536, "ports": 4096} (report §12.5).
  • The node runs over one family of addresses, IPv4 or IPv6, its listener's, or IPv4 where it has no listener; a peer's address of the other family is refused when the file is read, and a host name's family is checked at each dial, which fails where the name resolves only to the other.

A file is refused before anything runs, with a line that names the fault (report §12.5, Its configuration), where it:

  • is not JSON;
  • names a field the node does not know;
  • names a field twice;
  • holds a number too large for the host to read;
  • names a peer twice;
  • names a service twice;
  • gives two peers one key;
  • lists this node's own key as a peer's;
  • names a peer with an empty name;
  • holds a certificate.pem that certifies another key or names another host;
  • names under a service a peer it does not list;
  • gives utilization a value that is neither of its two;
  • gives utilization-interval one that is no whole number of at least one;
  • gives limits a field other than processes and ports, or one that is no whole number from 1024 to 67108864;
  • gives a public-key that is not the node's private key's.

1.3 Starting, reloading and stopping#

$ ern run --config-dir /etc/counter/b --main Counter.serve /srv/counter/build/counter.erc

--main Counter.serve names the function the node runs first, its entry point, serve in the module Counter; without it the node runs the program's main, and the process that runs it is the entry process.

At its start a node computes the values of the program's top-level bindings, the named values a module declares outside any function, as any program does, and only once all have their values does it listen and dial (report §8.5, §8.7). It reads at its start every module of its load path, the program's root and every directory beneath it among them, where ern run without a configuration reads the modules the program uses alone, and refuses to start where an .erc there holds a module of another namespace than its path gives (section 5.1).

It writes its process number to ernest.pid in its directory and holds the file locked for its life; a second node started from the same directory finds the lock and refuses, and the ern run command, not a node, says ern run: dir is the configuration directory of the running node N, which ernest.pid names. The host releases the lock however the node ends, so a stale file from a crash is overwritten at the next start.

ern reload --config-dir dir sends the node the hangup signal, and the node reads ernest.conf again (report §12.5, A reload). A peer added is listed and nothing more happens until the program reaches for it, by a send, a call, a find, a spawn or a compute, or until it dials in. A send is a message to a process there, and a call a send that waits for its answer. A find looks up a service the peer offers, a spawn starts a process there, and a compute runs a function there for its value.

A peer removed, or one whose key changed, has its connection ended, and both nodes treat it as lost (section 2.3); a peer whose address changed keeps its connection, and the next dial uses the new address; a change to measures, utilization or utilization-interval holds from the node's next measure of itself and its next report to its peers (section 3); and a change to limits holds from the node's next start, which the node says.

The node says ernest.conf was read again and a line for each peer added, removed or renamed.

listen and public-key cannot change while the node runs: a file that changes either, or breaks a rule of section 1.2, is refused with the reload was refused, and the configuration stays as it was: ..., and the old configuration stays. ern reload first reads the directory as the node would, and refuses a configuration the node would refuse with status 1, before it signals, but for a changed listen or key, which it signals with status 0 and the node alone refuses, saying so on its standard error. kill -HUP by the number in ernest.pid signals without reading, and the node then refuses such a file itself; the service manager's reload, section 1.5, runs ern reload.

ern stop --config-dir dir sends the node the termination signal and returns once the node has ended, which it waits for on the lock (report §11.2). Termination is orderly: the processes that asked to be told of the end, its subscribers, are told and the end waits for each to answer, saying the end waits for 1 subscriber: Keeper.main while it waits, so that what a program keeps is written; then the node tells each connected peer that it ends and waits for each peer's answer, so that the peer says ended and not lost, and exits; a peer that has fallen silent holds the end until it is lost, 45 to 75 seconds (report §8.7, §12.6).

A second ern stop while the first waits is a second termination, which ends the node at once. kill -TERM by the number in ernest.pid signals without waiting.

Both ern stop and ern reload fail where no node holds the file, ern stop: dir/ernest.pid: no node holds it: no node runs from the directory, or no such file where an orderly stop removed it, so that no signal reaches a process whose number the file names by chance.

A bare node, ern run --config-dir dir with no program, ends by termination alone, since it has no entry point to return (report §8.7); section 3.4 says what it is for.

A program that is no node faults with deadlock where every process waits and nothing can deliver. A node detects no deadlock, and in that state waits on until it is stopped (report §8.6).

1.4 Exit statuses and the two streams#

A process faults when it meets an error it did not expect, a division by zero among them. A node exits with (report §11.8):

  • 0 when its entry point returns;
  • the status the program itself chose, where it calls Os.exit;
  • 1 when its entry process faults or is killed, and when the program exhausts the host's memory;
  • the termination signal itself when termination ends it, which a shell shows as 143 and a service manager counts as a clean stop;
  • 141 when its output can no longer be written, because what read it has ended.

A service manager that restarts on failure restarts every exit status but 0 and no clean stop, so a node stopped by ern stop is not restarted and one that crashed is.

Standard output is the program's own, and the node never changes it. Standard error is the node's: every fault, as Counter.serve:14 faulted: division by zero, and every line of section 7. Where standard error is a file or a pipe, and not a terminal or a service manager's journal (section 1.5), each line begins with its time in UTC, 2026-10-13T14:22:11.836Z the peer a connected, so that a file of them is a log (report §11.2). The two streams together are the node's record; keep both.

1.5 Under a service manager#

A node is run in the foreground and left to the operating system's service manager, which starts it, restarts it and keeps what it writes; ern has no mode of its own for it. A unit for systemd, running the counter's node, saved as /etc/systemd/system/counter-b.service:

[Unit]
Description=The counter, node b

[Service]
ExecStart=/usr/local/bin/ern run --config-dir /etc/counter/b --main Counter.serve /srv/counter/build/counter.erc
ExecReload=/usr/local/bin/ern reload --config-dir /etc/counter/b
WorkingDirectory=/srv/counter
Restart=on-failure
TimeoutStopSec=30

[Install]
WantedBy=multi-user.target

systemd keeps both streams in its journal, which stamps every line, and journalctl -u counter-b reads them. systemctl reload counter-b runs the reload, and systemctl stop counter-b sends the termination signal and waits TimeoutStopSec for the orderly end, after which it kills what still runs; set it longer than the slowest subscriber's answer. Restart=on-failure starts the node again after a crash and after an Os.exit with a status other than 0, and not after ern stop.

Without a service manager, nohup ern run --config-dir b ... >> b.log 2>&1 & keeps a node running once its terminal has closed, with the two streams in one file, stamped.

2. Two nodes#

2.1 Listing each other#

Each node is made on its own machine with ern config, and the two then list each other: node a's ernest.conf names b with b's public key and b's address, and b's names a with a's key, and a's address only where b is ever to dial a. A peer listed without an address is never dialed, and is out of reach until it dials in; a node that is to be reached must listen. Nothing is shared but the keys, by whatever means you move text between machines; the directories are never copied.

{
  "listen": "0.0.0.0:8654",
  "public-key": "<a's key>",
  "peers": [
    { "name": "b", "network-address": "b.example:8654", "public-key": "<b's key>" }
  ],
  "services": { "counter": ["b"] }
}

Two nodes on one machine list each other without an edit. ern config --config-dir b --listen 127.0.0.1:8655 makes b on a port of its own, since the two cannot share one, and ern config --config-dir a --peer-dir b lists b in a's file under the name b, with the key b's certificate holds and b's listen as its address, 127.0.0.1 for 0.0.0.0 (report §11.3); --peer-dir a does the same the other way. services is written by hand, on one machine or two.

2.2 The connection#

Two nodes hold at most one connection, opened by the first operation that needs it and over TLS 1.3 with a certificate on each side (report §12.5, Connections).

A node accepts a connection only from a peer whose key its configuration lists, and only under the name that key gives it: a node's name on the wire holds a digest of its key and its certificate carries that name, so a certificate that names another host than its key gives is refused. So is a dialed node that answers with another listed peer's key, as a listed key beside the wrong address makes one do. The dialing node then says the peer c was refused: it answered the dial of the peer b, and the answering node nothing. Two nodes started from one copied directory have one key, and are one node to their peers (section 7's replaced row).

The refusing node says why, a node with the key ... was refused: no peer has its key, naming an unlisted node by its key's digest since it has no name here.

Connections are not transitive: that a knows b and b knows c connects a and c in no way, and each pair lists each other.

Two nodes connect only where they stand on one floor: one major and minor release of ern on one major release of OTP, which the handshake proves before anything passes (report §12.5). A patch release stands on the floor of its minor, so 0.4.0 and 0.4.1 connect, and 0.4.x and 0.5.0 do not, each saying the peer b was refused: it stands on another floor, another release or build of ern or another major release of OTP.

A build of ern that is no release stands on the floor of its own code's digest, so two development builds connect only where they are the same build. Nodes of different builds of the program connect, and agree on the code they share by a hash of each definition (section 5): a definition is one function or type of the program, and its hash a number computed from its text, which changes when the text does.

The handshake proves the floor by its cookie, the digest of the protocol's version, the form's version, ern's major and minor and OTP's major release, or of a development build's own code, which every node's command line carries and ps shows, -setcookie and the digest. It is the same on every node of one floor, is no secret, and grants nothing: a connection is accepted by its key alone (report §12.5).

The node says the peer b connected as the connection opens, the peer b ended when b stopped in order, and the peer b's connection was replaced by another from the same node where b dialed anew while the old connection was alive, as after b's restart.

2.3 A lost peer#

A connection is lost when the network breaks it, when the node's own detector finds the peer silent, or when a faulty frame, one unit of what two nodes send each other, arrives (report §8.7, A loss). Any traffic is a sign of life; where nothing else was sent for 15 seconds a tick goes, and a peer from which nothing came in four such intervals is lost, so a silence is found between 45 and 75 seconds after the last traffic, as the host states it, while a peer that closes is found at once.

The node says the peer b was lost: it fell silent or the peer b was lost: it closed.

What the program sees is the loss run on this node: every process here that watches one of b's processes, through a monitor, is told so, a Down message with the reason Unreachable, where a peer that stopped in order gives ProgramEnd instead (the language guide's §5.2), every call waiting on one of them ends, and a process waiting forever on one faults. Nothing else ends.

A restart here of a process that one of b's processes monitors or calls waits for b's answer, at the latest until the loss or b's end (report §6.9, §8.7). While b is silent that service is down: its fault's line says restarted at once, and its new run begins at the peer b was lost. The window is the protocol's and fixed, since no setting of ernest.conf changes it (report §12.6, Appendix C), and nothing at this node shortens it; meanwhile the operator looks at the network and at b's machine, as section 7's table says.

The connection is opened again by the next operation that needs it, never in the background: a node that is lost stays lost until an operation that needs it reaches for it, a send, a find, a spawn, a compute or an ask of its utilization (section 3.2), or until it dials in, and a dial that nothing answers is given up after 7 seconds. A peer that cannot be dialed, listed without an address, is reached again only when it dials in.

A send to a process of a lost peer returns at once, unless what waits for that peer fills the host's buffer for it, 1 MB, when the sender waits until it drains (report §8.7). The message waits behind the dial, and is sent where the connection opens and dropped where it does not. The window in which a silence is found is the host's, and no entry of ernest.conf sets it.

The move: look at b's machine. If b stopped in order you would have read ended; lost means the network or the process. b restarting shows as connected again on a, or as replaced where a still believed the old connection alive.

3. Services and placement, as the configuration sees them#

How a program offers a service, finds one, places a computation and sets its own utilization is the language guide's §8.1 and §8.2. Here is the operator's half: the entries that govern them.

3.1 Services#

services lists, under a name, the peers that may offer it, in the order a find asks them (report §8.7). A find asks the first; where it holds the service the address comes back; where it does not, or is unreachable, the next is asked, and so on within the find's time; a name not listed answers Io.NotListed without asking anyone. The order is the preference you give the program, and a reload changes it live.

A service carries a hash of its message type, the type of the messages its process takes. A peer that offers the name at another type answers Io.OtherType: two builds of the program disagree on the protocol, and no retry mends it. The move is to align the builds (section 5), or to let the program's author know the type changed under a service that peers still find by its old shape.

3.2 How busy a node is#

A node measures how busy it is on one scale: 1.0 is every scheduler busy, below it room and above it work waiting (report §12.8). A scheduler is one of the host's threads that run processes, one for each core as a rule. utilization in ernest.conf says how: "run-queue", the default, divides the processes running or ready by the number of schedulers, an instant reading and not an average; "schedulers" gives the fraction of the schedulers' time spent running since the number was last read, which never passes 1.0 and smooths a spiky load.

A program may set the number itself, when it knows its load better than the host does; then this entry is the default it starts from.

A node that lists peers tells each of them its utilization, a telling, every utilization-interval milliseconds, 5000 where the entry is absent, and once as a peer connects; an attached shell's own node tells none, so that no compute that names no node runs on it (report §11.2, The attached shell). Each node holds the last number heard from each peer, and Peer.compute, the function a program runs a compute with when it names no peer, picks the less busy of two peers drawn from them; a number older than twice the interval of the peer that sent it is not used, and a peer never heard from is not chosen. Where a program places work by its own rule, the language guide's §8.1 shows it over Peer.utilizations().

The cost of the telling is one small frame per peer per interval, which replaces the host's own idle ticks rather than adding to them: three idle nodes exchanged about 1.2 packets a second at the default interval, on one machine and across machines alike, each connection carrying two packets a telling. A shorter interval buys fresher numbers for more frames; a longer one the reverse.

3.3 The host's measures#

measures turns on the host's own monitors of the machine, cpu, memory and disk, each with the host's parameters under it, check-interval and almost-full; a program reads them through the Utilization library (report Appendix G.4), and they change nothing of section 3.2's number. None runs where the section is absent, and a reload starts or stops them. They cost what the host's monitors cost and nothing of Ernest's.

3.4 A bare node#

ern run --config-dir dir with no .erc starts a bare node (report §8.7): it holds no program of its own, evaluates the standard library, the modules every Ernest program has and a node holds from its start, and waits, listening for what its peers spawn and compute on it. The code it needs crosses with the first spawn or compute of each function (section 4), and it offers what the processes spawned on it offer, so a bare node is a worker that any listed peer on its floor can give work to by its name.

It must listen, or no peer could reach it, and it ends by termination alone. Its first spawn is the slow one: about 250 milliseconds on a machine of eight cores and 650 on one of two, most of it the host's compiler starting, against the exchange's own cost for every spawn after (section 4.1).

4. Code across nodes, as the operator meets it#

4.1 What crosses, and when#

Code crosses between nodes with a spawn and a compute, and nowhere else: not with a message and not with a find; the report calls the crossing the exchange (report §8.7, The exchange). When a program spawns a function on a peer that lacks it, the peer asks for the definitions it lacks among the function and everything the function uses, directly or through others, its reach, each known by the hash of its definition, verifies each as it arrives, compiles them together as one module of the host's and loads it whole before the process starts. Nothing compiled ever crosses, and nothing of it runs before all of it is loaded.

A definition that arrived is kept, so the second spawn of the same function ships nothing. On one machine, a spawn whose code crosses costs about 7 milliseconds for one definition, 9 for five and 23 for twenty, against a third of a millisecond for a function the peer already holds; across a wire to a machine of two cores, 17, 27 and 72, most of it that machine's compiler, against about a millisecond and a half, the wire's round trip, for a function it holds.

Two things never cross: the value of a top-level binding a node evaluates, which each node computes from its own program at its start, and a module of the host's that the program calls directly, through a foreign declaration, which a node finds on its load path (section 4.3). A spawn whose function needs either on a node that lacks it is not started, and the node says so (section 4.3). A binding whose initializer is a constant, a literal, or a constructor, a tuple or a list of constants, is evaluated nowhere, and crosses with the code that names it (report §4.6).

A shell attached to a node sends it a module's source as text, which the node compiles as its own (section 6); there too nothing compiled crosses.

4.2 What a node keeps, and when to restart#

A node keeps every unit of code it loads, one module as the host counts them, its build's modules, the ones it was sent and the ones a program or a shell attached to it loaded, for its life (report §11.2, What a node holds). An input's unit at an attached prompt goes as section 6 says; what it added to the counts stays. The host counts what they add, in four tables it fills and never empties, module names, exported functions, defined functions and atoms, its interned names, which every new name in received code adds to, and never gives one back, so a node that is sent new code without end slowly uses the counts up.

The limits are the host's, 65,536 module names, 524,288 export entries, 524,288 function entries and 1,048,576 atoms, and a node says once, at four fifths of one, the host has used 52429 of its 65536 module names, which it never gives back. Past a limit the node runs on and serves what it holds; a spawn or a load that would pass it fails, and the program is given the error Io.Other as a Left, Ernest's failed result.

How fast the counts move is a question of how much new code a node is sent, not of how long it runs or how much work it does. A node that runs the same build as its peers is sent almost nothing.

One that developers spawn their edits onto, whose program loads new code into itself often, with Code.load (section 5.3), or at whose prompt an operator types often, each input a unit (section 6), moves them: on one machine, a small definition spawned costs one module name, about five exports, a function entry per lambda, a function written in place without a name, and an atom, so two hundred such spawns a day reach four fifths of module names after about 260 such days; a program of twenty modules upgraded whole through Code.load reaches four fifths of function entries after about 416 upgrades.

The move is a restart at a time of your choosing: a restarted node holds its build and is sent the rest again as its peers need it, and nothing is lost but what was in its memory, which a node never promises to keep.

4.3 The lines a spawn can leave#

A spawn or a compute a peer asked for that this node did not start is said on this node's standard error, naming the peer, the site in the program where the spawn is written, and what was lacking (report §12.5, What it says):

  • the peer a's spawn at Counter.main:13 was not loaded: the binding Counter.config has no value here: the function reads a top-level binding whose value lives only where the program that declares it was started. Run that program on this node, or place the work with a compute on a node that runs it.
  • the peer a's spawn at Counter.main:15 was not loaded: the module counter_host, which Counter.tick calls, is not here, or has no function tick/0 here: the program calls a module of the host's directly, through a foreign declaration, and this node finds no such module among the directories it loads code from, its load path, to which --load-path adds a directory and --libs-dir the ebin of each of the host's applications under one. Install the module there, or the right version of it.
  • the peer a's spawn at Counter.main:17 was not loaded: this node could not take the code it received: ...: the host refused to compile or load what arrived, a count of section 4.2 passed among the reasons. Restart the node.
  • the peer a's spawn at Counter.main:19 was not loaded: the spawner's node no longer holds the function's reach: the spawning side let go of the code between asking and sending. Nothing to do here; the spawner sees Io.Other.

The program on the spawning side sees each of these as a failed result, a Left, with Io.NotLoaded for the first two and Io.Other for the rest.

The list is a selection: report §12.5, What it says, names every line a spawn or a compute can leave, a compute's lines beside these and the exchange's time run out among them.

5. Builds#

5.1 Several builds on one floor#

Nodes of different builds of a program connect, as long as they stand on one floor of ern (section 2.2), and they agree on what they share by hash: a service names its message type by the hash of its definition, a spawn names its function by the hash of its definition, and a definition that did not change hashes the same in both builds.

A definition's hash covers the hashes of the definitions it uses, so a fix to one function changes its hash and the hashes of the functions that use it; those cross to a node at the old build, and nothing else; two versions of a type are two types, and a service offered at one is not found at the other, which Io.OtherType says (section 3.1).

Nodes on two floors never connect (section 2.2). A fleet moves to a new minor release of ern, or a new major release of OTP, whole, every node stopped and started again on the new floor, or as a second fleet beside the first, with directories of their own, its programs found or placed there and the first fleet stopped once nothing needs it.

A node reads at its start every module in its program's directory and every directory beneath it, and refuses to start where an .erc there holds a module of another namespace than its path gives, one built from another source root: ern run: old/counter.erc holds Counter, not Old.Counter; remove it, and build Old.Counter from its source root.

A build written into the directory a running node was started from, where ern build put its .erc, reaches the node at its next start and nothing before; code reaches a running node from disk through Code.load (section 5.3, report Appendix E.28), or through :load at a shell attached to it, which takes the node's own compiled form where its load path holds one (section 6). Put each build in a directory of its own, and point the service manager's unit at the one you mean.

5.2 A fix from a shell#

A fix reaches a running node from a shell attached to it (section 6). At the node's prompt, :reload compiles again a module of the node's whose source under the shell's source root has changed, and :load loads a module the node does not hold; the node compiles each from the source the shell sends as text, and the module's next version is the one the node's prompts use from then on (report §11.2).

A running process keeps its code until a message of its own type hands it the new, so a fix reaches only a service written to take that message, which section 5.3 sends at the node's prompt. The node keeps the code for its life, and a restart from the old build is the old build again. The shell's own commands are its :help.

5.3 A service moved to new code#

A running service is moved to new code by the program's own message, never by the runtime: the service is written to take a message that hands it its new function, and a function of the new build lists the processes running the old function and sends each of them that message (report §6.10, Appendix E.28). How a service is written to take it is the language guide's §8.9; the operator calls the function at the node's prompt.

A service under restarting, started so that the runtime restarts it at a fault, is moved so only until its next fault, when the restart runs the function the service was started with, the old code (report §6.9). Such a service takes new code as a new service, started when the new build's binding is evaluated, by Code.load, the program loading a build into itself (below), or a shell's :reload, which loads a module's new source in place of the old, and the old service runs on beside it (report §11.2, Appendix E.28).

So a reload starts the module's services again beside the old, unless the binding offers its service and, finding it held, waits for the holder to end (report Appendix E.27). The old version's processes are listed under the site their version gave them, the build's plain and a reload's with the version's number, by :processes and Process.status (section 6), which find them where their function can no longer be named, a fix in a callee having changed its hash. Each is ended by Process.kill. It is moved by a message of its own type only where the program kept an address of that type, since a Process takes no message.

The example examples/upgrade/ is one module, Counter, in two builds: the first, v1/counter.ern, is the counter alone, which section 8 starts on the peers, and the second, v2/counter.ern, the counter with a new loop, countAloud, a function moved that moves its node's counters to the new loop and answers how many it moved, and a tool. Run from examples/, with a counter of the first build on b as section 8 starts it, a shell attached to b from ops (section 6), its source root the second build's directory, moves it:

$ ern shell --config-dir ops --attach b --source-root upgrade/v2
the peer b connected
Ernest 0.10.0, session 1. :help for the commands, :quit to leave.
> :reload
Counter, compiled again
> Counter.moved()
1 : Int
> Counter.moved()
0 : Int
> :quit

:reload finds that the source of b's Counter has changed, and b compiles the second build from the text the shell sends. Counter.moved() runs on b, and the shell prints its value with its type: Code.running lists the processes running the old loop, count, by the hash of its definition, which both builds write alike, here the counter serve started, and moved sends each the Upgrade that hands it countAloud. Asked again, it finds none.

The tool, the second build's main, makes the move from a node of its own, for every peer at once: it moves a counter of its own first, then spawns on each peer a process that moves the peer's counters and tells it how many, one line a peer; the spawn carries countAloud to a peer at the first build, which lacks it and keeps it. Section 8 runs it, and a peer it could not start on is a line with the failure, c: Io.Unreachable.

A program may also load a build itself at run time, Code.load from its own load path, and list what runs an old function with Code.running, which moved uses (report Appendix E.28).

6. Looking in#

A shell attached to a node is the operator's window: ern shell --config-dir ops --attach b runs a session on b, each input checked against b's modules, compiled on b and run in a process there, while the terminal, the history and the files the session reads stay with ops, the node the shell starts from (report §11.2, The attached shell). Every module of b's build is in scope at the prompt. A file, --main, --load-path and --libs-dir are refused with --attach, since the program and the load path are the node's.

ops is a directory of its own, made with ern config and no --listen, since the shell dials in. It lists b with its address, and b lists it without one, and on one machine ern config --peer-dir lists each in the other (section 2.1). Every peer b lists may attach to it, as every one may spawn on it. Where b runs as a service's user and the operator is another, neither can open the other's directory, so the superuser makes both, lists each in the other with --peer-dir, and gives each directory with its files to its user, chown -R, which section 1.1 allows; a later --peer-dir into either directory, and an ern reload of b, as section 8's reload step runs them, are then that directory's user's or the superuser's too.

A session on section 8's b, whose counter --main Counter.serve started:

$ ern shell --config-dir ops --attach b
the peer b connected
Ernest 0.10.0, session 1. :help for the commands, :quit to leave.
> :processes
Counter.serve receiving
> List.map(Process.live(), Process.status)
[Some(Process.Status(site = "Counter.serve", queued = 0, activity = Process.Receiving))] : List(Optional(Process.Status))
> Peer.peers()
["a", "ops"] : List(String)
> :browse Counter
Counter.serve() : Unit receiving Counter.CounterMsg
> :quit

the peer b connected is said by ops as the shell dials, and b says the peer ops connected. The shell prints each value with its type. :processes lists b's live processes, each by its spawn site and what it does, running, receiving or calling, here the counter waiting for a message; a process in Clock.sleep is receiving too (report Appendix E.21). Process.live() and Process.status answer for b at its prompt, and Process.live(), as :processes, leaves out every session's own processes, this one's and another's (report Appendix E.21). Peer.peers() is b's configuration, and a binding of the program read at the prompt is b's value, as a function of the program called there runs on b.

A process's site is the declaration its spawn is written in, with the spawn's line, Counter.main:59 for the counter the second build's tool spawns. The entry process, which no spawn starts, has the entry point's name and no line, Counter.serve above (report §6.9). A site carries the number of the version that spawned it, fixed at the spawn: plain for the build and the first load, and with the version's number for a reload's, Counter$2.main:59 for that spawn in the module's first reload. A site of a process a session started carries the session, $Session2.input 3:1, in every shell's lines and on the node's standard error alike (report §11.2, Faults).

A type's number works the other way: the current version prints plain, and a number names a previous one (report §11.2, Loading and reloading).

What a process the session started writes is shown at the prompt, and what the node's program writes stays on the node's standard output. Every fault on b, the program's among them, is said at the prompt of each shell attached to it and on b's standard error, and :faults lists those said since the session attached; a fault of an input's own process is said at its prompt alone. A fault's trace names each function by the name its program gives it, code that arrived from a peer among it, and the fault's line says , spawned by the peer a where a peer spawned the process (report §11.2).

:load reads a module's source under the shell's source root, its working directory or the directory --source-root names, sends it to b as text, and b compiles it as its own, or takes its own compiled form where its load path holds one built from that source; a module of b's own build is refused by :load and compiled again by :reload where its source has changed (section 5.2). A module so loaded stays on b for its life (section 4.2).

:quit leaves, as C-d on an empty line does, and the shell exits with status 0. What the session started stays on b: a process an input spawned runs on, and writes to b's standard output from then on. Once the session has ended, an Os.exit in such a process ends the node; while the session runs, it faults its caller (report §11.2). b says the peer ops ended. Several shells may attach to one node at once, each from a directory of its own, each a session of its own.

A session ends with its node: where b ends, by ern stop or by its program's end, the shell says the node b ended under its last prompt and exits with status 0, as section 8's stop shows, and where the connection is lost, it says the node b is lost and exits with status 1 (report §11.8).

An attach that fails is refused with status 1 and a line that names why: ern shell: the peer b is unreachable where no connection opens, ern shell: the peer b did not answer in time where a connection opens and no session starts within twice a dial's 7 seconds, ern shell: the peer b is not listed where ops lists no b, and ern shell: the node b could not start the shell: followed by the reason where the session's root on b ends before the session starts.

A shell attaches with the node's own release of ern, since the session runs the toolchain's own code, which the node loads from its own installation (report §12.7): a node of another build on the shell's floor answers ern shell: the node b runs another build of ern than this shell; attach with its release, one that holds that code and could not load it ern shell: the node b could not load the shell: followed by the node's reason, and one on another floor refuses the connection, as section 2.2 says.

An attach takes about a second on an idle machine of eight cores, and longer under load, as a shell that is a node takes to start. Each input after it is a unit b compiles and loads, which the counts of section 4.2 count. b lets an input's code go as report §11.2 says: once its answer is in, where the input neither declares nor builds a function value; when a later expression replaces it; and at the session's end. A unit a process still runs is kept while it does, and one that declares a function or builds a function value is kept for the node's life. The host never gives its counts back.

7. What a node says, and what to do#

Every line below is written once, on the node's standard error, with its time where that is a file or a pipe. Two are written by the ern run or ern stop command instead of a node, and name the directory as the command line gave it. The table is a selection: report §12.5, What it says, and §11.2 name every line a node writes, the end's lines, a frame it cannot read and a dial refused for its family among them.

The first column is the line as it is written, with the peer's name from ernest.conf, or the node and its key's digest where it is not listed; Site stands for a place in the program, Module.function:line, Q for a name in the program, Module.name, M for a module and N for a number.

The line What happened The move
listening on 127.0.0.1:51204 The node listens; the port is the host's where listen had port 0. Tell the peers that dial it, where they do not know the port.
the peer b connected A connection opened, dialed by either side. None.
the peer b ended b stopped in order; a process here that monitored one of b's was told ProgramEnd. None; expected at b's stop.
the peer b was lost: it closed The connection broke at once: b's process died or its machine closed the socket. Look at b's machine and journal.
the peer b was lost: it fell silent Nothing came from b for 45 to 75 seconds: network, or a frozen machine. A restart here of a process that b monitored or called waited until this line, and so did this node's own end, where it had begun. Look at the network between them; b reconnects at the next operation.
the peer b's connection was replaced by another from the same node b dialed anew while the old connection was believed alive, as after a restart. None.
a node with the key ... was refused: no peer has its key A node dialed in whose key this node's peers does not list, named by its key's digest; or this node's own dial of a listed address reached a stranger, named the same way. Add its key under peers, then ern reload; or ignore a stranger.
a node named ... was refused: its key gives another name A node dialed in under a name that is not the one its key gives, named as it named itself. Check which key is listed beside which address on the dialing node; a copied directory is not the cause, since a copy has the same key and shows as replaced.
the peer c was refused: it answered the dial of the peer b This node dialed the address listed for b, and the node there holds c's key. Check which address is listed beside which key on this node; a copied directory is not the cause, since a copy has the same key and shows as replaced.
the peer b was refused: its certificate names another host than its key gives b's certificate and key disagree: a copied or edited directory. Make b's directory again with ern config on b's machine.
the peer b was refused: it stands on another floor, another release or build of ern or another major release of OTP The two run different minor releases of ern, different development builds, or different major releases of OTP. Install one release of each on both.
ernest.conf was read again A reload succeeded. None; the peer lines that follow say what changed.
the peer b was added / was removed / is now named c What the reload changed. None.
the reload was refused, and the configuration stays as it was: ... The new file breaks a rule, or changes listen or public-key. Fix the file and reload again; for listen or the key, restart.
the peer a's spawn at Site was not loaded: the binding Q has no value here A spawned function needs a binding only the declaring program evaluates. Run that program here, or compute on a node that does.
the peer a's spawn at Site was not loaded: the module M, which Q calls, is not here A foreign declaration's host module is missing on this node. Install the module on the load path.
the peer a's spawn at Site was not loaded: this node could not take the code it received: ... The host refused to compile or load the arrival, a count among the reasons. Restart the node when convenient.
the host has used N of its M module names, which it never gives back Four fifths of a host count, from the code the node was sent or loaded. Plan a restart at a quiet time; the node runs on meanwhile.
Counter.serve:14 faulted: division by zero, spawned by the peer a A process a peer spawned here faulted; its trace follows. The program's author's; the site says where.
the end waits for 1 subscriber: Keeper.main Termination has told a subscriber and waits for its answer. Wait, or a second ern stop ends at once, losing what it was writing.
ern run: dir is the configuration directory of the running node N, which ernest.pid names A second start from a directory whose ernest.pid a running node holds; the ern run command writes it, not a node. Stop the first, or you meant another directory.
ern stop: dir/ernest.pid: no node holds it: no node runs from the directory ern stop or ern reload with no running node there; no such file where an orderly stop removed the file. The command writes it. None; the node is already down.
ern run: the node's carrier did not start: ... The part of the node that listens for and dials its peers could not start, its port taken among the reasons; the node ended before its program ran, with status 1, as a job that cannot start, ern shell: for a shell's own node. Free the port or change listen, and start again.

Lines that begin with a site and faulted, with no peer named, are the program's own faults, as on one node, and so is one with , on the peer b after the cause: a compute this node ran on b faulted there, and faulted its caller here with its cause, the trace that crossed beneath it and the caller's frame last. The language guide's §6 and §8.1 teach what they mean to the program's author.

8. A deployment, end to end#

Three nodes on one machine, a counter served on two of them and a tool that moves both to new code while they run, all from the two builds of section 5.3's example, upgrade/v1, whose serve is the counter's old loop, and upgrade/v2, whose main is the tool. Every step is run from examples/ and shows the command and what each node says; the move when a step fails is in section 7.

Make the directories. On one machine b and c take ports of their own, since two nodes on one machine cannot share one; across machines each may listen on the same port on its own machine.

$ ern config --config-dir a
$ ern config --config-dir b --listen 127.0.0.1:8655
$ ern config --config-dir c --listen 127.0.0.1:8656

Each prints its key. Make a fourth, ops, for the shell a later step attaches, as a was made, with no --listen, since a and ops only dial.

Then --peer-dir lists each node where it is to be known (section 2.1). ern config --config-dir a --peer-dir b and --peer-dir c list b and c in a's file with their keys and addresses, and the same two commands with --config-dir ops list them in ops's. ern config --config-dir b --peer-dir a and --peer-dir ops list a and ops in b's file with their keys and no address, since neither listens, and the same two with --config-dir c list them in c's. Each node then lists exactly who may connect to it and whom it may reach.

Build and start the counters. The first build is the counter alone, and its serve runs the counter's loop, count, as the node's own process:

$ ern build upgrade/v1
$ ern run --config-dir b --main Counter.serve upgrade/v1/counter.erc &
$ ern run --config-dir c --main Counter.serve upgrade/v1/counter.erc &

Each says the address and the port it listens on, listening on 127.0.0.1:8655 from b, and nothing more until a peer connects. The counters wait.

Check from a shell. In a terminal of its own, attach a shell to b from ops, which lists b and c with their addresses and which they list without one (section 6), and look at b:

$ ern shell --config-dir ops --attach b
the peer b connected
Ernest 0.10.0, session 1. :help for the commands, :quit to leave.
> :processes
Counter.serve receiving

b says the peer ops connected as the shell dials it, and :processes lists the counter by its site, the entry point --main named, waiting for a message. Leave the shell attached.

Reload a configuration. Make a directory d as ops was made, with no --listen, list it in b's file with ern config --config-dir b --peer-dir d, and reload:

$ ern reload --config-dir b

b says ernest.conf was read again and the peer d was added. Nothing connects until an operation reaches for d.

Move the counters to new code. Build the second, which adds the new loop, countAloud, moved and the tool, and run the tool on a:

$ ern build upgrade/v2
$ ern run --config-dir a upgrade/v2/counter.erc
here: 1 moved
inc 3
total: Some(5)
b: 1 moved
c: 1 moved

a moves a counter of its own first, which on its new loop says each increment message it takes, an Inc, as inc 3, and answers its total when asked, total: Some(5), Some being how Ernest prints a value that is there; then it dials b and c, each saying the peer a connected; on each it spawns a process that lists the counters on the old loop and sends each its message, and the spawn carries countAloud, which the peers at the first build lack, with it. The two peers' lines come in the order they answer, each saying that it moved its one counter to the new code, and a ends with status 0, each peer saying the peer a ended.

Stop in order.

$ ern stop --config-dir b
$ ern stop --config-dir c

Neither writes a the end waits for line, since the counter subscribed to no termination; each tells every connected peer that it ends and exits by the termination signal, status 143 in a shell. The shell attached to b ends with it and exits with status 0 (section 6), its last prompt left as it stood and the shell's line under it:

> 
the node b ended

b and c never connected to each other, and a has ended, so no node hears c's end.

When a step fails. A refused line at the first connection is a key or a floor, section 7's refused rows; a not loaded line at the tool's spawn is a binding or a host module the peer lacks, section 4.3; a peer's line that shows a failure in place of a count, c: Io.Unreachable, is a peer the tool could not start on, and its reason. Nothing of the above changes the nodes' directories: a deployment that goes wrong is stopped, the files fixed, and started again.
